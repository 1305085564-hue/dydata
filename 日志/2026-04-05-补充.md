# 2026-04-05 补充

## 飞书远程助手重构细节（16:00-18:20）

### 初版链路为什么错
- 远程助手一开始把飞书主聊天连续性绑在 `~/.config/claude-remote/config.json` 的固定 `session_id`
- 表面上看像“持续对话”，其实连续性依赖 Claude 原生会话一直不被别处占用
- 一旦本地 Claude Code 终端也在使用同一个 `session_id`，飞书就会撞上 `Session ID is already in use`
- 这不是飞书没打通，而是连续性设计本身错位：把“记忆”寄托在了 Claude 会话，而不是自己的文件体系

### 为什么临时聊天兜底不是正解
- 中间做过一次兜底：主聊天会话被占用时，退到临时会话回复
- 这个兜底只能止血，不能作为正式方案
- 原因有两个：
  - 聊天状态会分叉：主聊天一套、临时聊天一套
  - 用户无法感知当前落在哪条上下文上，长期一定乱
- 阿禅明确指出，这种设计天然有 bug，不能靠“先回复出来”来掩盖连续性问题

### 和龙虾的真正差别
- 龙虾的连续性不是靠同一个会话一直活着
- 龙虾的连续性来自：
  - 主对话
  - 日志
  - 日志补充
  - 项目状态
  - 领域知识
- 也就是“聊天断了没关系，读文件可以把脑子接回来”
- 远程助手如果继续依赖固定 session，本质就是借 Claude 的会话帮忙记忆，不是自己掌控连续性

### 为什么最终收敛到轻记忆增强版
- 讨论过“中记忆版”更像龙虾：保留最近几轮摘要、更多连续感
- 但阿禅把稳定性提到第一位：设计再好，稳定性差就等于 0
- 所以最终定案：
  - 先做轻记忆增强版
  - 只保存：当前主题 / 最近目标 / 最近结论 / 下一步
  - 不保存大段原始聊天
  - 任务继续独立执行
- 这版不是最花，但最稳，符合当前阶段目标

### 记忆归属这次的纠偏
- 我最初把“飞书远程助手需持续跟踪”写到了项目记忆
- 阿禅指出：飞书通道会服务 3~5 个小项目，它本身属于跨项目基础设施，不是某一个项目的局部记忆
- 这条纠偏很关键，最终改成：
  - 飞书通道本身的规则 × 项目记忆
  - 飞书通道本身的规则 ✓ 全局记忆 + `~/.claude/CLAUDE.md`
  - 只有某个具体业务项目通过飞书执行的内容，才写回对应项目文件

### 今天不只是做功能，也在做记忆制度优化
- 阿禅进一步要求：今天这件事本身也要进入日志、项目状态和记忆规则
- 关键不只是“做了飞书助手改造”，还包括“我们把记忆制度优化到了哪一步”
- 也就是明天回看时，要同时恢复两层信息：
  - 今天推进了哪些功能与结构改造
  - 今天形成了哪些新的记忆归属、日志补充、跨项目规则
- 这条要求会改变以后写日志的视角：不仅记事情本身，也记规则体系是怎么被修正的

### 这次形成的硬规则
- 关键链路或持续项目，默认主日志 + 补充日志都要写
- 主日志不能只写一两行“完成了什么”，必须能扫出：背景 / 已完成 / 当前状态 / 未完成线索
- 补充日志不是备注栏，而是上下文恢复层：要写决策背景、问题经过、关键转折、被排除方案、后续线索
- 飞书通道属于跨项目基础设施，相关结构 / 规则 / 排障 / 跟踪要求优先进全局规则
- 遇到“今天不仅做事，也在修制度”的情况，日志和项目状态要把制度演进一并记下，不要只记功能结果

### 当前还需要盯的点
- 飞书普通聊天在新结构下是否足够稳定
- 主聊天摘要是否会漂移或过度简化
- 项目状态追加是否会把“项目状态.md”写得越来越像流水账，后续可能需要再收敛格式
- 以后每次涉及跨项目通道或关键链路时，要避免再犯“记忆放对了，但日志写浅了”的老问题
