## 一、结论先行

**合并后共 1 个 Critical、5 个 High、5 个 Medium、3 个 Low。两份报告没有一份覆盖全部问题，交叉命中的只有"详情状态与列表不一致"一条。**

最贵的是 Codex 独有、补充轮没碰的那条：**作品详情把明显不可能的比例（转粉率 5450%、互动率 31250%）直接渲染成"优"和达成率**。管理者会把脏数据当有效证据下判断——这是唯一一条会直接导致错误业务决策的问题，其余都是"用起来难受/判断不了"。

补充轮的独有价值在**反馈与性能**：视图切换 11.7 秒零加载态、筛选弹层残留遮罩吞点击、首屏 6 批请求白跑。这三条 Codex 完全没测到，其中遮罩那条是多轮"点击无效"误判的共同根因。

两份报告**在测试环境上是断开的**：Codex 打线上 `dydata.cc`（阿禅本人账号），补充轮打本地 dev（组长账号）。所以两份的"未覆盖"不能互相顶替——补充轮没有 375px 读数，Codex 没有组长视角、没有 dev 控制台报错。本轮合并后这些缺口仍在，需要单独补。

## 二、合并后的问题清单（按严重度）

### 🔴 Critical

#### C1 — 详情把不可能的比例当正常大盘展示，评级仍给"优" ✅ 两份合流（Codex 独有，补充轮未覆盖）

**现象**：作品《3.19盘前》（视频 `95ff6090`，播放量 2）详情首屏显示转粉率 `5450.0%`、互动率 `31250.0%`、点赞率 `20700.0%`，并进一步显示 `优545000% / 优976563% / 优1035000%` 达成率。列表对该视频有"上游数据异常"的提示，详情核心卡片没有同等醒目标识。

**复核（实测，回代码）**：根因不在"详情少了一个校验"，而在**两个入口喂给同一套评级函数的数据源不同**：

- 列表徽标走 [`getStatusDot()`](src/lib/content/domain/content-list.ts#L69-L76)，把 `anomaly_status` **和 `play_change_signal`** 一起传给 [`resolveVideoStatusLabel()`](src/lib/video-anomaly.ts#L107-L121)，所以同一条视频在列表里能显示"腰斩"。
- 详情走 [`content-detail-metrics.tsx L96-100`](src/app/(app)/admin/content/detail/content-detail-metrics.tsx#L96-L100)，只传 `anomalyStatus: video.anomaly_status`，**`playChangeSignal` 根本没传**。

这条同时解释了 Codex 的 High（去盘状态不一致），两条是**同一个根因**，不是两个 bug。

**评级侧复核**：[`breakoutAchievement()`](src/lib/breakout-rating.ts#L68-L77) 对达成率**不封顶**（注释明写"不封顶"），[`breakoutGrade()`](src/lib/breakout-rating.ts#L80-L94) 只判下限不判上限，所以 `actual` 脏到天上去也照样返回"优"。而 [`overallBreakoutGrade()`](src/lib/breakout-rating.ts#L136-L153) 有一条业务上**正确**的兜底：`playCount < 5000` 一律判"劣"——问题在于播放量 2 的那条视频，详情首屏三张卡走的是单项达成率口径，没走这道兜底。

**建议（推荐方案）**：在**比率计算层**加统一的合理性上界，而不是在详情页补一个补丁。比率类指标（互动率/点赞率/收藏率/转粉率）超过物理可能上界（建议 100%，即"互动数 > 播放数"即视为脏数据）时返回 `null`。这样列表、详情、评级、达成率**四处同时收口**，不会按下葫芦浮起瓢。返回 `null` 后现有链路自然降级为"数据异常/待核"（`status = "missing_metrics"`），无需新增文案分支。

**理由**：这是唯一一处"数据源不可信但界面看起来很权威"的地方。放在比率层收口，是本方案里性价比最高的一刀。

### 🟠 High

#### H1 — "去盘"打开的作品，详情状态与列表状态不一致 ✅ 两份交叉命中（唯一一条）

**现象**：从基线点"去盘 →"，抽屉打开作品 `ee56127e`《内外盘的重要性，你现在知道了吗》，抽屉头部显示"正常"；关闭后搜索同一作品，列表显示"腰斩"。用户无法判断这条到底要不要处理。

**复核**：与 C1 **同一根因**——详情调用 [`resolveVideoStatusLabel()`](src/lib/video-anomaly.ts#L107-L121) 时漏传 `playChangeSignal`。函数内 `if (playChangeSignal === "halve") return "腰斩"` 这一支永远走不到。

但这里还有**第二层问题**，光修标签不够：`play_change_signal` 是**服务端算出来的**（[`attachPlayChangeSignals()`](src/lib/loaders/admin-content-page.ts#L306-L315)，对比上一稿播放量算涨跌），列表接口会算、详情接口也走同一套 `normalizeVideoRows`。所以字段本身在详情载荷里**是有的**，只是前端没用。修法是前端一行的事；但"为什么被去盘选中"的原因，详情首屏仍然没有说明。

**建议**：① 详情调用补齐 `playChangeSignal`，与列表共用同一映射（已存在，别再写第二套）；② 详情首屏补一行"入口说明"——这条为什么被选中（腰斩/删稿/限流/异常），把判断依据写在用户看得见的地方。

#### H2 — 视图切换（全部 ↔ 归档）无任何加载反馈 ⚠️ 补充轮独有（Codex 未测到）

**现象（补充轮实测读数）**：点"归档"，`GET /api/admin/content/list?view=trash&scope=team` **耗时 11.7 秒**返回。期间分段控件仍高亮"全部"、仍显示 `共 2149 条`、URL 无变化，直到数据到达才一次性翻转。全程 `loading:false`、`aria-busy` 数量为 0。

**复核（实测，回代码）**：`isLoading` 其实是有的——[`content-page-client.tsx L209`](src/app/(app)/admin/content/content-page-client.tsx#L209) 会加 `opacity-65 pointer-events-none`。但这**不能解决问题**：整块列表连工具栏一起变淡 + 整块不可点，用户看不到任何"正在加载归档"的文字或转圈，且**工具栏自己被禁用了**——这正是"点了没反应、反复点"的成因。真正的加载指示器不存在。

**建议**：① 分段控件在切换期间显示 spinner 并禁用，文字改为"正在加载归档…"（**不要**把工具栏一起变淡禁用）；② 列表区给骨架而非整体调透明度；③ 顺带查这接口为什么 10s+——补充轮线索指向与选题库状态耦合，见 H4。

**待确认**：11.7s 是本地 dev 直连生产库的数字，不能直接等同于线上。需在线上复测一次再定性能整改的力度。

#### H3 — 375px 移动端列表不可读 ⚠️ Codex 独有（补充轮工具无法改视口，未覆盖）

**现象**：表格宽度约 `686px` 挤在 `332px` 容器里横向截断；"视频标题 / 账号"表头被压成竖排；行内标题、负责人、指标互相挤压；底部固定导航覆盖列表内容。页面没有整体横向滚动，用户得猜"要横向滚才能看到剩余指标"。工具按钮触控目标仅 23–28px。

**建议**：移动端改卡片/两层信息结构，至少固定"状态 + 标题"两列；放大触控目标；底部导航不得覆盖正在查看的行。

#### H4 — 键盘无法进入作品行，主任务不能纯键盘完成 ⚠️ Codex 独有（补充轮复核为一致）

**现象**：Tab 依次经过筛选、搜索、10 个排序按钮、页大小、页码，**没有任何作品行获得焦点**；无 Skip link。表格行无 `tabindex`/`role`。

**复核（实测，回代码）**：坐实。[`content-list-table.tsx`](src/app/(app)/admin/content/content-list-table.tsx#L150-L160) 的行只有 `onClick`，没有 `tabIndex`、没有 `onKeyDown`、没有 `role`。补充轮的键盘走查独立得出同一结论（Tab 顺序合理但表格行不可聚焦），**两份互证**。

**建议**：作品行做成可聚焦、可 Enter 打开的控件；补 Skip link、`aria-current`、详情抽屉打开/关闭的焦点回收。注意别做成 `<tr tabindex=0>` 一把梭——**建议把标题做成行内焦点入口**，改动面小、语义也正确。

#### H5 — 筛选弹层关闭后残留全屏透明遮罩，吞掉工具栏点击 ⚠️ 补充轮独有（Codex 未测到）

**现象（补充轮实测）**：打开"筛选"弹层 → 关闭（点别处/Esc）→ 再点"异常""时间"等控件，**点击无反应**。DOM 中残留一层 Base UI portal 的 `role="presentation" data-base-ui-inert` 全屏遮罩，用 `clip-path` 在弹层位置"挖洞"，其余区域仍覆盖整页，拦截所有底层点击。需再按 Esc 或再点一次空白才恢复。

**建议**：确认弹层关闭时 portal/遮罩是否被正确卸载；若依赖动画结束卸载，须保证关闭后遮罩**即时** `pointer-events:none` 或直接移除。

**影响面最大**：这条是此前多轮把"归档按钮点不动"误判为偶发的**共同根因**——修它能一次消掉一批"玄学点击无效"。优先级应高于其严重度标签。

### 🟡 Medium

#### M1 — 深链不恢复排序，静默回落默认排序 ✅ 补充轮代码坐实

**现象**：直接访问 `/admin/content?anomaly=1&sort=interaction_rate&dir=asc`，异常开关正确恢复（343 条），**排序不恢复**——表头仍是"▼ 发布时间"。

**复核（实测，回代码）**：坐实。[`content-list-state.ts L30-31`](src/lib/content/domain/content-list-state.ts#L30-L31) 的 `sortField`/`sortDir` 是 `useState` 硬编码初值，**从不读 URL**；而同文件其余筛选全部经 [`parseContentListFilters()`](src/app/(app)/admin/content/content-list-filters.ts#L198) 与 [`writeContentListFilters()`](src/app/(app)/admin/content/content-list-filters.ts#L250) 双向同步。属"半套 URL 状态"——`filters` 走 URL、排序不走。

**建议**：排序字段与方向一并纳入同一套 URL 读写（复用现有 `parse/write`，别新开一套）；入参非法时安全回落到默认排序。

#### M2 — 每次加载重复取选题库状态：12 批请求、6 批被 abort ✅ 补充轮实测 + 代码坐实

**现象**：任意一次进入/刷新页面，`POST /api/admin/content/topic-library-status` 共发 12 次，其中 **6 次被主动 abort**。

**复核（实测，回代码）**：坐实。[`content-topic-library.ts L99-106`](src/app/(app)/admin/content/content-topic-library.ts#L99-L106) 的 `useEffect` 依赖 `videos` **数组引用**；首屏 `videos` 会变化，effect 二次触发 → [`L59`](src/app/(app)/admin/content/content-topic-library.ts#L59) 的 `abort()` 取消在途的 6 批、再发 6 批新的。

关键点：**代码里已经写好了去重签名** [`buildTopicLibraryStatusSignature()`](src/app/(app)/admin/content/content-topic-library.ts#L22)，在 `L53` 做了比对——但它只能在**请求成功后**记录（`L88`），首屏第二次 effect 触发时第一批还没返回，所以拦不住。abort 本身是"取消过期请求"的正确设计，问题是**白白发了一倍的请求**。

**建议**：给 effect 加一个**同步**的在途签名守卫（`topicStatusPendingSignatureRef`），发现同一签名正在途中就直接跳过——复用已有的 signature 函数，不新增机制。顺带查 `videos` 引用为何在首屏变化。

#### M3 — 首屏 console 稳定报 hydration mismatch ⚠️ 补充轮独有（Codex 报"无 Console error"，两份冲突）

**现象（补充轮实测）**：首屏 `[error] A tree hydrated but some attributes of the server rendered HTML didn't match…`，栈回指 [`NavBarClient`](src/app/(app)/layout.tsx)（`isScrolled`），每次加载稳定复现。

**⚠️ 冲突裁决**：Codex 扫 123 个事件报"无 Console error"，补充轮报"稳定复现"。两份不矛盾但也不互证——**Codex 打的是线上生产包，补充轮打的是本地 dev**。`isScrolled` 这类滚动态在 dev 下因 Fast Refresh / 时序更易失配。**判定：以补充轮读数为准（本地 dev 确实有），但线上是否存在未证。** 这不是白屏级问题，排 P2，不阻塞前四项。

**建议**：定位 `isScrolled` 首帧差异来源，改挂载后计算，或精确收敛 suppress 条件（**不要全量 suppress**）。

#### M4 — 排序方向只有视觉箭头，未提供 `aria-sort` ✅ Codex 独有，本轮代码复核坐实

**复核（实测，回代码）**：[`content-list-table-header.tsx`](src/app/(app)/admin/content/content-list-table-header.tsx) 全文件无 `aria-sort`；排序状态只由 `▼/▲/↕` 三个字符表达，且未排序列的 `↕` 是 `opacity-0` + hover 才显形——**读屏用户和键盘用户完全无法知道当前按哪列、升序还是降序**。

**建议**：当前排序列标 `aria-sort="ascending|descending"`，按钮 `aria-label` 含"按播放量升序排序"等可理解状态。

#### M5 — 人员/账号下拉：35 项扁平、无搜索、无分组、混入测试账号、账号同名无区分 🔁 两份同源

**现象**：补充轮读 35 项扁平列表、无搜索框、无团队分组、混入 `批次5-A组员2`/`测试组员`/`测试组长` 等测试数据；Codex 读到"罗礼杰""小芸姐"同名选项无法区分。

**建议**：加搜索框与团队分组；同名时追加团队/账号 ID 等区分字段；清理测试账号。

## 四、冲突与缺口裁决

**冲突 1：Console 报错。** Codex（线上）报无错，补充轮（本地 dev）报 hydration mismatch 稳定复现。→ 见 M3，两份环境不同，**不构成矛盾**，均保留各自读数。

**冲突 2：归档详情里的操作入口。** Codex 说"归档详情里能看到恢复/永久删除"，补充轮说"两视图都无操作列"。→ **不冲突**：操作在详情抽屉内，列表层确实没有行内批量入口。补充轮的"列表层无批量处理，审阅 16 条需逐条开详情"是**产品取舍提示，不是缺陷**，交由阿禅决定是否加。

**缺口（合并后仍未覆盖，需单独补测）**：
- **第二受限角色**：两份都没拿到（Codex 缺账号、补充轮只有组长）。权限隔离在两份报告里**均未验证**。
- **破坏性写入终态**：恢复/永久删除只看到入口，未执行。
- **线上性能基准**：H2 的 11.7s 是本地 dev 直连生产库的读数，线上未复测。
- **375px 断点**：仅 Codex 一次读数，补充轮工具无法改视口。
- **线上 hydration**：见冲突 1。

## 五、推荐整改顺序

按"**先止血错误决策，再修断掉的闭环，最后补体验**"排：

| 批次 | 内容 | 为什么这个顺序 |
|---|---|---|
| **第 1 批（P0）** | **C1 + H1 合并修**：比率层加合理性上界；详情调用补齐 `playChangeSignal` | 两条同一根因，一次改完。C1 是唯一会导致**错误业务决策**的问题；H1 不修则"去盘"入口的优先级信号持续失真 |
| **第 2 批（P1）** | **H5**（遮罩吞点击）→ **H2**（视图切换加载态） | H5 影响面最大且**一次消掉一批"玄学点不动"**；H2 是高频动作的反馈缺失。两条都是"用起来怀疑页面坏了"级别 |
| **第 3 批（P1）** | **H4**（键盘不可达）+ **H3**（375px） | 可达性问题，改动面比前两批大（要动表格结构），但不修则两类用户主任务做不完 |
| **第 4 批（P2）** | **M1**（排序入 URL）→ **M2**（重复取数）→ **M4**（aria-sort） | M1 是"半套 URL 状态"，改动小、闭环价值高；M2 一行守卫；M4 纯属性 |
| **第 5 批（P2/P3）** | **M3**（hydration）→ **M5**（下拉治理）→ **L1/L2/L3** | 噪音级与文案级，可与其他批次并行 |

**建议先做第 1 批和第 2 批**：C1+H1 是两处小改动解决一个 Critical 加一个 High；H5 是一处遮罩生命周期问题解决一批玄学 bug。这四项做完，这个页面的"可信度"和"点得动"两个基本盘就稳了。

**推荐拆分方式**：第 1、4 批是纯逻辑改动（有明确对错、可回滚），适合单人一次做完；第 2、3 批涉及布局与交互结构，建议按"先 H5/H2 反馈层、后 H3/H4 结构层"分两次验收。二者风险不同，混在一起验收会看不清是哪一层出的问题。
