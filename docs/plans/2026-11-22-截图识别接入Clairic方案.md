> 接收方：[CC] 架构 / 技术负责人　|　提出：阿禅　|　2026-11-22　|　状态：**已落地发版（dydata-019 / dydata-020），上海实测达标，待阿禅拍板是否切流开启**
> 本方案只做到「实测结论 + 改动设计 + 验收清单」，实现与取舍由架构侧定夺。

## 0. 给阿禅看（一页话）

员工上传抖音数据截图，现在识别一次要 6～40 秒，慢得影响填报。我们拿同一张真实截图的三档模糊版本，直连 Cloudflare 的 Clairic 专项模型实测了 6 次：**平均 1.25 秒，字段基本全对**。速度是质变，识别结果不比现在差。

它不是聊天模型，网站现有的「新增 AI 渠道」表单塞不进去，必须给截图识别单独加一条通道。做法是**加第三条、可一键切回**，现有百度 / 看图两条一行不动。唯一要避开的坑是发布时间的字段类型，方案里给了验证过的写法。

**要你拍板的只有三件**：置信度阈值口径、preview 模型是否允许进主链路、上线前要不要补一批真实截图样本（建议补）。

## 1. 核心诉求与完成定义

| 项 | 内容 |
|---|---|
| 谁要办什么事 | 数据上传页的填数员工：上传截图后立刻看到识别结果，不用等 |
| 唯一目标 | **把识别耗时从 6～40 秒压到 1 秒级** |
| 现状精度 | 阿禅明确「够用，识别不准的是少数」→ 本次**不追求提升精度**，但**不许变差** |
| 成本 | 不参与决策。备注：官网现为促销价 $0.10/M input tokens（2026-12-01 后 $0.24/M），output 不计费，并非完全零成本 |
| 完成定义 | 新通道可开关、可切回；两类截图字段与置信度跟现状对齐；失败自动回退；L2 档端到端 P50 ≤ 2 秒；旧两条通道行为不变 |

**本次不做**：不改全站来源校验、不改 `/chat/completions` 拼接、不改「新增 AI 渠道」流程、不替换或删除旧通道、不动生产库写入、不把密钥写进代码或文档。

## 2. 为什么不能靠配置接进去（已实跑，非推断）

现有「新增 AI 渠道」整条流程只服务 OpenAI 兼容聊天模型，Clairic 原生端点从第一步就进不去：

| 层 | 现象 | 依据 |
|---|---|---|
| 最外层 | 后台写操作（获取模型 / 保存）走全站来源校验；从非登记域名打开后台 → 403「请求来源不可信」。**与填什么地址无关** | `src/lib/csrf.ts:68`、`src/middleware.ts:321`、`src/app/api/cloudbase/_shared.ts:26` |
| 录入 | 新增渠道第一步探测 `{base_url}/models`；`/ai/run` 无模型列表 → 界面到不了选模型那一步 | `src/app/api/admin/ai-config/route.ts:436-456`、`sync-models/route.ts:50` |
| 调用 | `buildUpstreamUrl` 与「测试模型」都固定拼 `/chat/completions` → 404 | `src/lib/ai/client.ts:191`、`src/lib/ai-config/model-tests.ts:446` |

出站安全检查（`src/lib/server-url-security.ts:112`）**只拦内网与云主机元数据，没有域名白名单**；`api.cloudflare.com` 解析公网直接放行，不需要「加白名单」。

纠正一个早期说法：`/ai/v1` OpenAI 兼容端点**不能跑 Clairic**（缺 `model/state/fields` 会 400），只适用于别的普通视觉聊天模型，也换不到 1 秒。

## 3. 实测证据（本方案的事实基础）

### 3.1 测法

同一张真实「作品数据详情」双机并排截图，三个模糊版本（L2 最清晰＝实际业务最差档 / L3 模糊加强化 / L4 极糊）。清晰度量级 367.8 / 191.6 / 144.2（拉普拉斯方差，仅用于排序）。因实际上传是单屏，每档裁成「数据页（左）」「留存页（右）」两张 → **3 档 × 2 类 = 6 个用例**，按现有 `ocr-prompts.ts` 两套字段逐字段对账。

密钥来源：`~/.local/share/dydata/keys/cloudflare.txt`（权限 600），直连 REST，无中转。

### 3.2 速度：达标

| 用例 | 耗时 | passes | input_tokens |
|---|---|---|---|
| L2 数据页 | 1883 ms | 6 | 6160 |
| L2 留存页 | 1412 ms | 18 | 5880 |
| L3 数据页 | 823 ms | 6 | 6160 |
| L3 留存页 | 1154 ms | 18 | 5880 |
| L4 数据页 | 889 ms | 6 | 6592 |
| L4 留存页 | 1362 ms | 19 | 6174 |

**平均 1254 ms，区间 823～1883 ms**，对比基线 6～40 秒。留存类 passes 明显更多但耗时不随之线性增长，说明瓶颈不在字段数。

### 3.3 结果：L2 / L3 达标

| 档位 | 数据页（8 字段） | 留存页（7 字段） | 说明 |
|---|---|---|---|
| L2 | **8/8** | **6/7** | 唯一错：发布时间分钟 |
| L3 | **8/8** | **6/7** | 同上；标题置信度由 0.914 降到 0.669 |
| L4 极糊 | 7/8 | 5/7 | 涨粉量误抄收藏量 674（conf 0.718）；标题乱读、时间连月份都错 |

L4 的实际表现比「肯定识别不了」略好：5 个核心百分比 / 秒数（56、23.02、21.53、57.61、14.81）**仍全中**，糊掉的是字段标签与文字。但该档超出业务最差水平，只作边界参考。

### 3.4 两个关键发现（都要写进实现约束）

1. **文字字段可以从图片直出**。早期担心 `text` 答案是 `state` 字符串的 span、纯图片输入会恒为 `null` —— 实测证伪：`state_text` 为空，标题仍正确读出（`3.6盘前光电+油气、半导体+商业航天 电力…`，conf 0.914 / 0.669）。**不必先做一遍 OCR 提字**，否则速度优势全丢。
2. **`datetime` 类型会把分钟归整成整点**。`20:42` → `2026-03-05T20:00:00`，conf 仅 0.05～0.08。追加探针证明换字段写法即可读准：

   | 写法 | 结果 | 置信度 |
   |---|---|---|
   | `text`：原样抽发布时间文字 | `2026-03-05 20:42 发布` | 0.985 |
   | `number` 拆 `pub_hour` / `pub_minute` | `20` / `42` | 0.998 / 0.980 |
   | `text`：`published_at_text` | `2026-03-05 20:42` | 0.996 |

   **实现约束：字段清单避开 `datetime`，用原样文本或时分拆分，再由转换层拼成现有 ISO 契约。**

### 3.5 置信度信号可直接用于「低置信度转人工」

正确项 conf 普遍 0.84～0.9999、`p_null` 极小；错项 conf 0.05 / 0.057 / 9.1e-8 或明显偏低（L4 涨粉量 0.718）。**设阈值即可把错项挡住转人工，不会静默填错**，这正好接上现有 `pending_confirm` 机制。

### 3.6 样本局限（必须说明）

6 个用例来自**同一张截图的三个模糊版本**，不是 6 张独立业务截图；标题、数值、版式只有一套。结论对「这套版式 + 中文数据截图」成立，**不能外推到所有截图版式**。上线前建议补 10～20 张真实截图复跑。

## 5. 建议方案：第三条独立通道

### 5.1 原则

- 改在根因所在的环节：新增 `clairic` 通道实现，**不复用、不改造** `callAi` 的 OpenAI 顺位链。
- 一条规则只有一个来源：字段清单与现有 `ocr-prompts.ts` 两套契约对齐，转换层集中一处，不在下游打补丁。
- 旧行为保持：默认通道仍是 `baidu`，新通道**默认关闭**，开关打开才生效。
- 不伪造：模型失败明确失败并回退，不用假数据装成功。

### 5.2 链路与改动点

```
上传截图 → 槽位类型(data/retention) → 通道开关（新增 clairic 枚举）
  → [改动点1] 组装 fields + 内嵌图片
  → POST /ai/run/@cf/cloudflare/clairic
  → [改动点2] answers → 现有 JSON 契约转换（含置信度、发布时间拼装）
  → parseOcrResponse → 置信度判定 → pending_confirm / 转人工
  → 落库 + OCR 日志 + 耗时台账
  ↘ 任一环节失败/超时/模型下线 → 自动回退 baidu（或 vision），用户无感
```

### 5.3 文件级改动清单（建议，最终由架构侧定）

| 文件 | 改动 |
|---|---|
| `src/lib/ai-config/ocr-channel.ts` | 枚举 `baidu \| vision` → 增加 `clairic`；解析默认值仍为 `baidu` |
| `src/app/api/ocr-screenshot/channel-config.ts` | 通道设置读取支持新枚举 |
| `src/app/api/ocr-screenshot/clairic-channel.ts` | **新增**：端点、鉴权读取、字段清单、请求组装、超时、响应解析、转换层 |
| `src/app/api/ocr-screenshot/route.ts:295-303` | 三分支分发；`timings` 增加 `clairic_ms`；日志 `channel` 记录新值 |
| `src/app/api/ocr-screenshot/ocr-contract.ts` | **不改动契约本身**；转换层按现有结构产出 |
| `src/app/api/admin/ai-config/*` | **不动**；Clairic 不进「新增 AI 渠道」表单 |
| 配置 | `CLOUDFLARE_API_TOKEN` 环境变量注入（`src/lib/server-url-security.ts` 出站检查已放行公网域名，无需改） |

### 5.4 字段清单设计（实测版）

- **数据页**：`play_count`（number/integer，指令里写明「6.8万→68000」换算）、`likes` / `comments` / `shares` / `favorites` / `follower_gain`（number/integer）、`video_title`（text）、`published_at`（**不要用 datetime**，见 3.4）。
- **留存页**：`video_title`（text）、`avg_play_duration`（number/decimals 1）、`avg_play_ratio` / `bounce_rate_2s` / `completion_rate_5s` / `completion_rate`（number/decimals 2）、发布时间同上。
- 指令用中文写「不是弹幕量」「不是 5s 完播率」这类消歧，实测有效（8/8）。

### 5.5 转换层与置信度口径

- `answers` → 现有 JSON 契约：数值直取 `value`，文本取 `value`，`null` 字段按现有规则置 null；`published_at` 用原样文本 / 时分拆分拼成带 `+08:00` 的 ISO（`normalizePublishedAt` 已能处理）。
- 置信度映射建议：`confidence ≥ 0.90` → `high`；`0.75～0.90` → `medium`；`< 0.75` 或 `p_null > 0.2` → `low` 并置 `pending_confirm`。**阈值口径待拍板**。
- 输出必须能被 `parseOcrResponse` 接受；已验证原生 `answers` 直喂会得到 `LOW_CONFIDENCE / 图片不清晰或未识别到数据`，转换层不可省。

### 5.6 失败回退

超时建议 5 秒（实测最慢 1.9 秒，留一倍余量）；401 / 5xx / 模型下线 / 转换后无有效字段 → 回退现有 `baidu`，并在日志标注 `channel_fallback`。通道开关可一键切回，旧两条代码不改。

### 5.7 日志与台账

复用现有 OCR 日志与耗时台账，新增记录：`channel=clairic`、端到端耗时、`usage.passes`、`input_tokens`、各字段置信度、回退原因。便于上线后核对「是否真的快了」。
