# 三大管理模块职责收敛设计

## 目标

把三个入口收敛到单一职责，并复用已经存在的真实接口，不另造一套审批或成员生命周期：

- `UnifiedCommandHub`：只承载需要立即处理的审批，以及与审批物理分栏的普通通知。
- `/admin/fulfillment`：承载全月作品数、应发目标、逐日发布/请假/待审状态和成员履约详情。
- `/admin/modules`：只承载入职、在职组织与权限、离职归档/恢复；移除发布考核展示与排序。

## 现状判断

当前代码已经具备单条/批量豁免审批、通知与审批 Tab、31 天矩阵、成员详情抽屉、入团审批、在职/归档切换和恢复能力。此次不重造这些能力，只补齐真实缺口：审批后的跨页面状态联动、待审批请假进入月历、作品“条数”与应发目标的正确口径，以及成员页去考勤化。

现有未提交改动把 `publishedToday`、`leaveToday` 等当天字段改写成“全月”文案，数据与标签不一致，不能保留为交付结果。

## 数据流

1. 待办抽屉调用现有 `/api/exemptions/review` 原子审批接口。
2. 成功后审批卡片立即从本地队列消解，并广播站内 `exemption reviewed` 事件。
3. 发布工作台监听该事件，只重新读取当前日历数据，不整页刷新。
4. 发布 loader 在原 `get_fulfillment_range` RPC 之外，并行读取当前范围内的 pending `exemption_request`，将申请覆盖日期附着到成员逐日记录；不修改数据库结构。
5. 月度作品数为 `published_count` 求和；应发目标为统计窗口自然日扣除已批准请假/豁免日，与成员 loader 的现行口径一致。

## 交互与视觉

- 审批卡片保持“姓名、公司、类型、日期、事由、通过/驳回”的单层纸面排版；成功结果就地消失，不弹成功 Toast。
- 发布矩阵：发布为低饱和绿，请假/豁免为暴雨灰蓝，待审批为低饱和琥珀黄，无记录为暖灰。一个日期有多条作品时直接显示数字。
- 成员页保留顶部入团便签、在职成员、归档专区；移除“按发布”排序、发布进度列和考勤豁免状态，改为角色与权限范围摘要。
- 遵守象牙画布、暖砂发丝边、单一陶土主行动、正文不小于 13px、数字 `tabular-nums`、结果可见时不弹 Toast。

## 边界与失败处理

- 不新增 migration，不改 RLS，不绕过现有审批原子函数。
- 待审申请读取仍按 `activeVisibleUserIds` 和团队范围过滤；归档成员不进入审批与发布当前操作。
- 单条审批失败时保留卡片并显示失败原因；批量审批按每条结果结算，成功项消解、失败项保留。
- 发布日历刷新失败时保留原画面并给出明确错误，不伪装已同步。

## 验收

- 单条通过/驳回和批量通过均有自动化测试；成功项立即从审批队列消失。
- 待审批申请在覆盖日期显示黄色；审批通过后同一已打开页面自动刷新为批准状态。
- 发布总览和成员行使用作品条数/应发目标，不再拿发布天数冒充作品数。
- 成员页不再出现发布排序、月度发布进度或考勤豁免展示；入团、角色/范围、归档/恢复仍可用。
- 类型检查、相关测试、全量测试与真实浏览器页面均通过。
