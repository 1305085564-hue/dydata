## 一、结论与升级目标

当前系统已经具备继续运行和迭代的基础，但性能、稳定性、安全边界和发布验证仍然分散在页面、loader、API、数据库函数和客户端组件中。问题不是单个查询慢，而是缺少一套统一的运行架构：

- 同一类数据在多个入口重复读取；
- 权限范围、查询口径和 service role 使用边界容易被各模块重复解释；
- 外部副作用失败后，核心业务结果与用户看到的结果不总是清楚分离；
- 缓存作用域、TTL、容量和失效策略没有形成统一契约；
- 性能门禁存在，但没有覆盖所有关键页面、API 和数据规模变化；
- 真实角色、真实数据、真实浏览器验收没有成为每类高风险改动的固定闭环。

本次升级完成后，系统必须达到以下状态：

1. **性能可预测**：页面和关键 API 有正式预算，查询次数、P95、超时率和缓存命中率可观测。
2. **失败可解释**：核心业务成功、审计失败、通知失败、待办失败和网络失败分别表达，不再用一个模糊 500 混在一起。
3. **权限可证明**：页面、API、Server Action、RPC 和 service role 路径遵守同一权限契约，并有真实角色允许/拒绝证据。
4. **数据链路可恢复**：非原子副作用有幂等、重试、补偿和审计证据，不能出现“用户不知道到底成功没有”。
5. **发布可回滚**：应用、数据库、配置和门禁有明确兼容顺序、回滚触发条件和真实恢复演练。
6. **架构可演进**：性能和安全边界进入领域服务、数据访问层和发布门禁，后续功能不再重新复制旧问题。

## 三、目标运行架构

### 3.1 页面和 API 分层

```text
页面 / API / Server Action
        ↓
身份与权限上下文
        ↓
用例编排层：输入、状态、事务边界、幂等
        ↓
领域服务层：业务规则和领域结果
        ↓
数据访问层：查询、RPC、缓存、批量、超时
        ↓
Supabase / 外部服务
```

硬约束：

- 页面组件不新增直连数据库；
- API route 不承载长业务分支和跨领域查询；
- service role 只能在完成当前用户、公司角色、集团会话、目标归属和影响行数核验后使用；
- loader 负责页面数据编排，但不能替代领域权限校验；
- 数据权限只能从统一权限上下文获得，不能在各模块重新拼接；
- 外部服务调用必须有超时、有限重试、错误分类和 requestId；
- 核心写入和通知/审计/待办等后置副作用必须分别表达结果。

### 3.2 统一请求上下文

必须建立统一 request context，贯穿页面服务端请求、API、Server Action、RPC 编排和外部调用：

```text
requestId
actorId
companyId / groupMode
route / operation
targetId
permissionScope
startedAt / duration
```

禁止：

- 只记录“请求失败”而不记录操作和目标；
- 把完整 token、密码、敏感正文写入日志；
- 用用户可见错误文案代替内部诊断；
- 在多个模块各自生成不同格式的错误对象。

### 3.3 统一业务结果

所有包含核心写入和后置副作用的用例，至少区分：

```text
businessSucceeded
permissionChecked
auditSucceeded
notificationSucceeded
todoMarked
compensationRequired
```

这套结果契约由可维护性治理方案提供代码规范，由审批专项先落地验证。

## 四、性能根治范围

### P0：必须完成

#### 4.1 串行分页和外部读取

涉及 `src/lib/loaders/admin-modules.ts` 等读取入口：

- 每页请求必须有超时；
- 必须有最大页数/最大记录保护；
- 可重试错误和不可重试错误分开；
- 不能用“返回部分数据但像成功一样”的方式掩盖缺失；
- 部分数据降级必须返回明确的 `incomplete` 状态并记录影响范围；
- 页面必须有可理解的降级提示或安全空态。

验收：

- 正常数据、空数据、单页超时、连续超时、部分成功、超过上限；
- P95 不超过对应页面正式预算；
- 不产生无限重试和无限分页。

#### 4.2 N+1 和连接池压力

涉及播放量变化、成员、日报、协作和 fulfillment 等批量读取：

- 同一请求内按实体批量查询；
- 查询数量不能随实体数量线性增长；
- 必须记录查询总数和总耗时；
- 对无法批量化的查询必须给出固定上限和理由；
- 不允许用无限 `Promise.all` 把数据库压力转成并发压力。

验收：

- 10、50、100、500 个实体数据集；
- 查询次数、P95、连接池和错误率对账；
- 结果和旧实现逐项对账。

#### 4.3 缓存作用域和生命周期

所有进程内缓存必须声明：

```text
key 作用域
TTL
最大条目/最大字节
主动失效
用户/公司隔离
并发请求复用
异常降级
```

不得直接新增无 TTL、无容量、无失效策略的 Map 缓存。

必须完成：

- 用户、公司、集团模式的缓存隔离；
- 页面切换、退出登录和用户切换后的失效；
- 过期条目定期清理；
- 最大内存预算；
- 缓存命中、未命中和失效指标；
- 缓存失败回退到安全的重新读取或明确空态。

不在没有基线的情况下引入 `node-cache`、Redis 或其他新基础设施。若内存缓存无法满足正式预算，必须另附容量和部署方案。

#### 4.4 页面性能预算闭环

以 `docs/工程运行事实.md` 的正式预算为唯一页面预算来源：

- `/dashboard`：首屏 2 秒、完整 3 秒、首屏业务请求不超过 15；
- `/admin/content`：首屏 2.5 秒、完整 5 秒、首屏业务请求不超过 20；
- 其他登录后页面：首屏 2.5 秒、完整 4 秒、首屏业务请求不超过 20；
- 单接口预算继续按工程事实文件执行。

必须按冷缓存、热缓存、空数据、大数据、权限拒绝和外部服务慢响应分别测量。

## 五、稳定性和数据一致性根治范围

### 5.1 超时、重试和降级

所有外部调用和长查询必须明确：

| 项目 | 要求 |
|---|---|
| 超时 | 单次调用有上限 |
| 重试 | 只重试幂等、可恢复错误 |
| 次数 | 固定最大次数，不能递归重试 |
| 抖动 | 有退避或请求间隔，避免雪崩 |
| 降级 | 明确返回部分、空态或失败，不能伪装成功 |
| 观测 | 记录最终失败和重试次数 |

### 5.2 写入和后置副作用

审批、导入、分配、通知、审计等流程必须定义：

```text
核心写入是否成功
审计是否成功
通知是否成功
待办是否成功
是否需要补偿
是否允许重试
```

本次行动中枢审批专项负责完整落地一个样板。其他模块必须复用同一原则，不得继续使用“接口 500 = 业务一定失败”的模糊语义。

### 5.3 幂等和重复请求

所有可能被重复点击、刷新重试或网络重放的写操作必须具备：

- 业务唯一键或幂等键；
- 已处理状态识别；
- 重复请求不会重复发通知、重复记账或重复审计；
- 结果可安全返回给前端；
- 补偿重试不会制造第二次业务结果。

### 5.4 失败恢复

必须至少演练：

- 数据库慢或短暂不可用；
- 外部通知失败；
- 审计写入失败；
- 页面请求中断后再次提交；
- 发布后发现权限越界；
- migration 已执行但应用未部署完成。

每类失败都要写清：发现方式、用户影响、恢复动作、是否需要人工介入、如何防止再次发生。

## 六、安全、权限和数据库根治范围

### 6.1 权限统一契约

严格以 `docs/权限与安全说明.md` 和现有权限核心为准：

- `resolvePermissionCore()` 是身份和范围核心；
- `company_role`、集团模式、公司范围、历史范围不能混用；
- `visibleUserIds` 与 `activeVisibleUserIds` 语义不能混用；
- 空范围表示没有可操作对象，不是全量；
- service role 不等于业务授权；
- 普通 token、Server Action、API、RPC 和 service role 路径必须分别证明权限边界。

### 6.2 真实角色验收

必须真实验证：

1. 组员；
2. 组长·管理；
3. 公司所有者；
4. 集团模式；
5. 归档成员；
6. 无公司归属成员；
7. 跨公司目标；
8. 伪造目标 ID；
9. 直接 API 调用；
10. 集团会话过期后恢复公司范围。

每个角色都要有允许和拒绝结果，不能只测前端隐藏按钮。

### 6.3 数据库和 migration

- 历史 migration 只能新增，不能改历史文件；
- migration 执行前必须确认应用代码已经兼容；
- 线上生效不能只看 `schema_migrations`，必须用 `pg_proc`、表结构、策略或功能性查询核实；
- RLS、函数、service role、索引和约束必须有线上证据；
- 数据清理和写入必须有授权范围、幂等边界和回滚方案；
- 数据口径改动必须先对真实数据抽查，不能凭代码直觉判断。

### 6.4 输入和输出安全

- 所有 API 输入明确解析、长度、枚举和 UUID 校验；
- 错误响应不返回堆栈、token、内部 SQL 或敏感业务正文；
- 内部日志脱敏；
- 文件、URL、重定向和外部来源按已有安全规范校验；
- 数据导出、下载、跨公司读取和 service role 写入必须有真实权限证据。

> | 日志脱敏 | `src/lib/sentry/privacy.ts`（含测试，禁止自写脱敏绕过它） |
> | 观测不伤业务 | 记录与上报全部失败静默，不改变响应和异常语义 |
> | 路由级错误上报 | `src/lib/sentry/capture-route-error.ts`，已被 5 个 `error.tsx` 使用 |
>
> **上表能力一律禁止重写。** 本方案真正要建的只有四项缺口：
>
> 1. `MutationRoute` 是写死的三条路由联合类型 → 放开为可扩展注册，新接口一处接入；
> 2. 只覆盖 POST 写链路 → 扩展到读接口与页面 loader；
> 3. 缺 §3.3 的分层结果契约（`businessSucceeded`/`auditSucceeded`/`notificationSucceeded`/`todoMarked`/`compensationRequired`），现靠 stage 序列凑 → 定义契约，由审批专项首个落地；
> 4. 超时上界、有限重试、缓存命中/TTL/容量/失效、每接口查询次数与 RPC 耗时**完全没有** → 本方案新建（对应 §四、§五、`timeout.ts`/`retry.ts`/`cache-policy.ts`）。
>
> **命名规矩**：链路 ID 沿用现有两个名字（响应头 `x-dydata-request-id` ＋ Sentry 标签 `dydata.request_id`），不得再造第三个。`unified-command-hub.tsx` 里的 `requestId`/`request_id` 是**豁免申请业务 ID**，与链路 ID 同名不同义，二者严禁在日志字段、接口入参或前端取数中混用；新增分层结果契约时业务 ID 一律显式命名（`appealId`、`exemptionRequestId`）。
>
> **待补接入清单**：`/api/admin/fulfillment/appeal/handle`（补交审批）、`/api/admin/fulfillment/mark`（改判）目前**未接**该底座，属缺口 1 的第一批消费者。

## 十、验收标准

### 10.1 性能

- `/dashboard`、`/admin/content` 和其他登录页满足工程事实中的正式预算；
- 关键 API P95 不超过既有预算；
- N+1 查询清零或有已批准例外；
- 所有缓存有作用域、TTL、容量和失效策略；
- 慢查询、超时、重试和连接池风险可观测。

### 10.2 稳定性

- 核心业务成功和后置副作用结果可区分；
- 重复提交不会产生重复业务结果；
- 外部调用不会无限等待或无限重试；
- 失败后有重试、补偿或明确人工处理入口；
- 关键流程错误率和恢复时间有基线。

### 10.3 安全

- 四类真实角色和集团模式允许/拒绝均通过；
- 跨公司、伪造 ID、归档成员、空范围均正确；
- 页面、API、Server Action、RPC 和 service role 路径一致；
- 线上 migration、RLS 和函数状态有真实核验；
- 日志和错误响应不泄露敏感数据。

### 10.4 发布

固定命令至少包括：

```bash
npm test
npx tsc --noEmit --pretty false
npm run lint
npm run build
npm run gate:static
npm run gate:roles
npm run gate:browser
node scripts/architecture-baseline.mjs
npm run gate:maintainability
```

其中 `gate:maintainability` 由可维护性方案建设，必须在接入前明确脚本存在；不存在时不能在验收记录中写成通过。

真实验收必须包括：

- 真实账号登录；
- 真实数据读取和写入；
- 真实权限拒绝；
- 真实浏览器关键路径；
- 真实失败或故障注入；
- 发布后线上状态核验。

## 十一、回滚、恢复和发布硬边界

### 11.1 回滚触发条件

任意一项发生，立即阻断发布或回滚：

- 数据泄漏或权限越界；
- 业务写入结果不一致；
- 审计、通知或补偿链路丢失；
- 关键页面或 API 超过正式预算；
- 5xx、超时或连接池压力明显回退；
- migration 已执行但应用不兼容；
- 观测缺失导致无法判断业务结果；
- 回滚后无法恢复原有权限或数据口径。

### 11.2 发布顺序

1. 先部署兼容代码；
2. 再执行已审查的 migration；
3. 核验线上函数、RLS、索引和配置；
4. 部署使用新契约的应用；
5. 执行真实 smoke、角色和关键页面验收；
6. 记录线上结果；
7. 未通过不得宣布完成。

禁止数据库先行发布，禁止只看 migration 账本，禁止用旧输出替代当前真实运行证据。

### 11.3 恢复原则

- 业务核心成功但通知/审计失败时，不随意回滚核心业务；
- 通过幂等补偿恢复后置副作用；
- 数据口径错误时先冻结错误入口，再做可审计修复；
- 每次恢复记录影响范围、时间、操作者、命令和结果。
