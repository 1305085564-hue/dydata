## 五、与既有口径的差异更正（重要）

1. **「无调用方」只在 2026-08-22~08-26 之后成立，不能当"生产从未使用"。** P1 草案（2026-09-08）写 `admin_sidebar_badges_summary`「轮询链 2026-08-26 已删，RPC 无调用方」——**代码侧复核成立**（`src/` 零引用），但生产 123 天窗口里它是**被调用最多的对象（12608 次）**。同理 `admin_analytics_first_screen`（50）、`admin_cockpit_summary`（91）、`admin_pending_submissions_today`（96）都是随页面下线才停止调用的。→ 这 4 个的删除前置是"4 周零调用窗口"，不是"代码零引用"。
2. **草案漏了 v1→v2 的函数内依赖。** `admin_cockpit_summary` 与 `admin_pending_submissions_today` 现在只是 `..._v2` 的包装（`language sql`，`select public.xxx_v2(target_date, null)`）。后果两条：① 删除必须**先 v1 后 v2**，顺序错会留下坏函数；② 因 SQL 函数被内联，`pg_stat_statements` 对 v2 的计数**恒为 0**，**不能拿"v2=0"当无调用证据**。
3. **`knowledge_cases` 家族的生产状态与草案描述不同。** 草案按"5 表"处理；实际生产只有 1 张，且这 1 张**本表虽 0 行，却有 20 次 PostgREST 全列读取**（发生在 2026-08-19 建表之后，原因未解释——可能是人工排障或残留脚本）。
4. **`violation_test_records` 与 `smart_alert_claims` 不该并列成同一档。** 草案 §2.2 把两者都写成"真死表"；实际前者有 40 行数据 + ≥27 次读取 + 一个现役触发器并维护 `violation_cases` 两列，后者 0 行零依赖。本批拆成"需确认"与"可删候选"两档。
