# `/admin/content` 首屏减重与服务端分页方案（第一轮纠错后）

> 状态：**已实施并完成两轮真实验收**（2026-10-21）。方案部分为动手前的设计；实施结果、与方案的偏差、最终读数见文末「实施后状态与偏差」。
> 需求书：`docs/plans/2026-10-20-数据管理页减重需求书.md`。
> 方案边界：只处理 `/admin/content`；不改票据、既有权限口径、回收站业务、截图存储和其他页面。
> 代码位置：**已上线**。远端 main `8fc083c2`（提交 `1f5a63d8` / `16381692` / `8fc083c2`，由工作分支 `3a06cf3d` / `1ee33ea7` / `7b414ed1` 逐笔 cherry-pick 重建，补丁逐字节一致）；其后 `41add6c7`（变体分析文档）、`77876b5b`（存储边界门禁）也在同一主干。

## 结论

采用已确认的 A：服务端分页。第一轮纠错指出的派生排序风险成立：原方案没有说明如何在切当前页之前得到派生排序/筛选值，因此仅“最终返回当前页”不足以证明是真分页。

本方案推荐由数据库端查询按完整筛选、排序、统计后只返回当前页，浏览器不再接收整份列表。它能显著减少传输、浏览器内存和客户端计算；但在没有预计算数据结构时，数据库仍需读取和处理匹配范围内的候选行来算派生指标、排序及总数，工作量仍随候选集增长。**本轮明确解决 4.5 MB 响应上限与首屏传输膨胀，不承诺服务端/数据库工作量与数据量无关。**

若“数据量翻 10 倍仍可稳定打开”也要求数据库计算成本不随数据量线性增长，则当前“不改表结构”的范围不足以证明该目标；需另行决定是否允许预计算列、物化结果或相应索引/迁移。本方案不擅自把这类数据库扩建纳入当前施工。

## 当前事实与数据基线

- **[代码核实，当前主工作区]** `src/lib/loaders/admin-content-page.ts` 使用 `fetchAllQueryPages` 读取完整生命周期列表；然后按全部可见视频 ID 批量取 24h 快照、内容分段和话题标签，再构造质量/就绪/播放变化数据。`summary.totalVideos` 来自完整过滤后数组长度。列表筛选、派生计算和排序目前由浏览器完成。
- **[实测，真实库报告]** 旧实现首屏为 3,677.9 KB（其中 document 3,145.9 KB、静态资源 532.0 KB）；旧列表 API 响应 13,398,821 B。两项分别来自 Playwright 资源统计和同库接口测量，不混为同一个响应指标。
- **[实测，真实库报告]** `docs/reference/2026-10-21-admin-content-真实数据库验收/报告.md` 记录：active 2,416 条、trashed 27 条；active 24h 快照 2,387 行，覆盖 2,387 个视频。旧链路的 `EXPLAIN ANALYZE` 行数为视频 2,416、24h 快照 2,387、分段 9、话题标签 2,315，合计约 7,127 行；这是报告列出的四类查询读数，不代表完整 loader 的所有 SQL 查询行数。
- **[实测，候选实现报告，非当前 main 完成证明]** 同一报告记录候选数据库查询 `rowsRead=2,391`、`snapshotRowsRead=2,362`、`returnedRows=20`。候选实现仍读取候选数据计算，但只回传 20 条，印证了“网络页容量固定、数据库读数仍接近全量”的区别。

## 排序字段清单与白名单

当前有 14 个可排序字段，来源为 `src/lib/content/domain/content-list.ts` 的 `SortField` 和 `src/lib/content/data/content-list.ts` 的排序计算：

| 字段 | 来源分类 | 说明 |
|---|---|---|
| `published_at` | `videos` 原生列 | 发布时间 |
| `overall_grade` | 派生值 | 最新 24h 数据、话题类型和既有评级规则 |
| `core_metric` | 派生值 | 按话题类型选择点赞率或收藏率 |
| `play_count` | 快照值 | 最新 24h 快照 |
| `follower_gain` | 快照值 | 最新 24h 快照 |
| `likes` | 快照值 | 最新 24h 快照 |
| `comments` | 快照值 | 最新 24h 快照 |
| `shares` | 快照值 | 最新 24h 快照 |
| `favorites` | 快照值 | 最新 24h 快照 |
| `interaction_rate` | 派生值 | `(likes + comments + shares + favorites) / play_count × 100`，沿用缺值与零播放规则 |
| `bounce_rate_2s` | 快照值 | 最新 24h 快照 |
| `completion_rate_5s` | 快照值 | 最新 24h 快照 |
| `avg_play_duration` | 快照值 | 最新 24h 快照 |
| `completion_rate` | 快照值 | 最新 24h 快照 |

除 `published_at` 外，没有其他排序字段是 `videos` 表原生列。上表中的快照值虽然不是派生公式，仍需从 `video_metrics_snapshots` 为每个候选视频选出最新 24h 值；不能只对当前页取快照再排序。

API 必须只接受上述枚举值，排序方向只接受 `asc | desc`；非法值统一回落到 `published_at desc`。现有浏览器 URL 解析已有回落，但使用 `rawField in DEFAULT_SORT_DIR`，施工时改为严格自有键检查；无论如何，浏览器回落不能代替服务端校验。每种排序继续保留 `id` 作为同值稳定排序键，并复用现有空值与无效比率规则。

## 接口与取数契约

列表接口查询状态包括：

- `view`: `all | trash`；
- 现有范围：`scope`、`teamId`，服务端仍从既有权限上下文生成可见 ID；客户端不得自行提供可信授权范围；
- 页码和页容量：`page` 从 1 开始，默认 20、最大 100；
- 全部现有筛选：成员、账号、关键词、发布日期、播放档位、自定义播放区间、评级、异常、选题库状态、高亮规则和只看高亮命中；
- `sortField` 与 `sortDir`。

响应只包含当前页展示所需的紧凑视频行、当前页最新 24h 快照及页面选项，详情文案/链接/截图和完整详情指标在打开详情时再取。筛选选项仍按完整可见范围提供，不能只从当前页生成成员或账号选项。

`page`、`pageSize`、筛选、排序和视图写入 URL。任何筛选、排序、视图、权限范围或页容量变化都清空旧游标并回到第 1 页。缓存键须包含范围、视图、页码/游标、页容量、规范化筛选和排序；`fresh=1` 绕过缓存并从第 1 页重新开始。

页码仍是用户可分享和直接选择的状态；直接输入/选择第 N 页时服务端按该页读取，不要求用户先从第一页逐页走到目标页。相邻上一页/下一页可使用 keyset 游标，但页码、方向和游标必须相互校验；随机跳页清除旧游标并按目标页重新定位。

详情抽屉的上一条/下一条在当前页内直接切换；到页边界时请求相邻页并继续切换；数据集首尾禁用对应方向。跨页切换失败时保留当前详情并明确提示，不跳到错误视频。

### 服务端计算与性能边界

1. 先在服务端应用既有可见范围与可下推条件：生命周期、成员、账号、发布日期和关键词。
2. 对播放/评级/异常/选题库/高亮筛选与排序，数据库端需要取得同一候选集的关联快照、标签和相关状态，按现有纯函数/规则等价计算，再完成筛选、排序、统计和切页。实现可用受限字段的 RPC/查询，但不得把全量候选行取回 Next.js 再逐行映射后声称“服务端只取当前页”。
3. 每次列表请求只向浏览器返回 `pageSize` 上限内的行；候选数据查询量、排序运算量、RPC 耗时和返回行数分开观测。
4. 候选行的数据库计算仍是 O(N) 的已知限制；多次筛选/换页可能重复计算，需实测耗时和行数。若它触及 10 秒函数上限或 1,200 ms 页面接口预算，当前范围不能以“响应体小”判为性能目标全通过。
5. 选题库状态需在数据库端按候选集筛选/排序所需口径完成；若现有接口依赖无法安全下推，必须记录剩余全量读取与其耗时，不能先切当前页再筛导致漏结果。

### `summary` 统计契约

- `totalVideos` 表示当前视图/权限范围和所有筛选条件（含派生筛选）应用后的总匹配数，在分页前计算；不能用当前页条数代替。纯原生筛选可以用数据库 `COUNT(*)`；派生筛选必须由相同派生计算口径统计全体候选结果。
- 异常徽标沿用当前页面语义，命名为 `anomalyCountForTime`：当前视图/权限范围内，按生效发布日期范围和成员筛选计算异常数；不受页码、关键词、账号、播放档位、评级、选题库、高亮或 `onlyAnomaly` 开关影响。现行实现见 `src/lib/content/domain/content-list-state.ts`。异常分类应与 `classifyVideoAnomalyBucket` 映射一致，并在数据库侧逐类对账。
- `totalPages`、当前范围起止、前后页状态均由服务端计算。合法空结果为 0；查询失败或部分数据失败须明确报错，不得伪装为 0。

### 稳定翻页与并发变化

- 固定数据集下按排序值 + `id` 建立确定顺序；页码跳转、前后页和游标的参数语义必须统一。若连续翻页使用 keyset 游标，游标必须绑定完整查询指纹，不能因页面与 API 对过滤参数的规范化不一致而错误返回 409。
- 数据不变时，遍历所有页必须无重复、无遗漏并与 `totalVideos` 一致。
- 其他用户插入/删除/恢复作品，或更新排序使用的快照/话题状态时，普通分页不能自动提供跨 HTTP 请求的数据库快照；仅有排序值 + `id` 游标不能证明并发期间绝对无重漏。推荐本轮明示“无并发写入时保证无重漏；发生并发写入时列表是逐请求实时视图，需刷新后重新遍历”，并对边界记录仍存在且排序值未变的游标做基本有效性检查。若要求所有插入/删除/更新都能被检测并强制重开列表，则需要数据版本号/快照机制，属于额外数据库设计，需单独评审；不能假称普通游标已提供该保证。
- 若服务端确实检测到游标边界失效或查询指纹改变，返回可识别的 `409 staleCursor`；客户端必须提示“列表已变化，请重新加载”并重置到第一页，不得静默展示旧结果。
- 若产品要求在并发写入期间也绝对无重漏，需要快照/版本化结果集设计，单独评审数据库范围。

## 详情深链与“直接去盘”

- `?videoId=<id>` 通过现有 `loadAdminContentVideoDetail` 按 ID 独立读取详情并执行现有范围检查，不先遍历列表或计算目标第几页。因此目标在第 7 页也可以直接打开详情；页面不承诺同时跳到该视频所在页。
- 不存在、生命周期与当前视图不匹配或范围外的视频沿用既有 not-found/权限语义，不以当前页第一条代替。
- “直接去盘”保留现有靶子规则：昨天发布的异常作品优先，其次近 7 天异常作品，最后回退到存量最高优先级异常作品。服务端必须从当前视图和权限范围内的完整候选集选出 `directReviewVideoId`（或对应详情），客户端再复用 `videoId` 详情路径；不能只从当前 20 条找。现行列表异常计数会跟随日期与成员筛选，但靶子选择本身基于完整可见列表；本轮照此分开保留，不顺手改产品口径。
