## 一、根因（实测，读源码）

- 截图类型不是识别出来的，是按位置定的：`buildOcrStorageRequestBody` 固定发 `screenshot_type: role === "screenshot_2" ? "retention" : "data"`，接口 `resolveScreenshotType` 优先用这个显式值，返回的 `screenshot_type` 原样回传。因此 upload-controller 里"智能对调"永远不会触发；先粘完播截图会被按互动截图识别。
- 多张上传串行：`handleUnifiedUpload` 逐张 `await handleSlotUpload`，两张时等待翻倍。
- A1：`截图槽位区.tsx` 的全局粘贴监听遇 `isEditablePasteTarget` 直接 return，文案框又不收图，图片无声丢失。
- A2：`shouldRequestScreenshotReplacement` 只在 `fileCount === 1` 时弹替换；两张时直接上传，槽满后全丢，只提示"仅上传了前 0 张"。
- A3：`summarizeMonthFulfillment` 的排除日只含按日期记的免交/请假/本地待审批，长期免交（`exempt_type: "permanent"`，无起止日期）没进来，页头"今天免交"与"漏 y 天"自相矛盾。

## 二、目标规则（唯一）

**截图上读到什么数字决定它是哪类；每类取最新加入的一张；位置和数字都由这条规则算出来。** 每张图从加入到出结果走一条直线，中途不搬位置。

## 三、任务

### T1 识别接口支持"自动判类型"（服务端）

文件：`src/app/api/ocr-screenshot/route.ts`、`ocr-contract.ts`、`baidu-channel.ts`、`input.ts`

1. 请求不带 `screenshot_type` 时进入自动模式；带了仍按显式类型走（给"这是互动 / 这是完播"重试用，也保证旧调用方行为不变）。
2. 自动模式只调用一次模型：视觉通道用一份合并提示词，同时要求两族字段（互动族：`play_count, likes, comments, shares, favorites, follower_gain`；完播族：`retention_metrics` 下 `avg_play_duration, avg_play_ratio, bounce_rate_2s, completion_rate_5s, completion_rate`），加上 `video_title / published_at / published_at_text / published_at_confidence / confidence`。百度通道同理合并结构化提示词。
3. 类型由代码判定，不信模型自报：新增纯函数 `classifyScreenshotByFields(parsed) → "data" | "retention" | null`。初版规则：某一族非空字段数 ≥ 2 且严格多于另一族 → 判为该族；否则 `null`。阈值以 T7 抽查结果为准，可调，调了写进本单第五节。
4. 判定为某类后，按该类现有解析逻辑产出与现在完全相同的返回结构（`screenshot_type`、`recognized_fields` 等），下游不需要区分是自动还是显式。判不出时返回 `screenshot_type: null`、`slot_status: "pending_confirm"`、`requires_manual_confirmation: true`，并新增 `screenshot_type_source: "auto_unknown"`；判出时 `screenshot_type_source: "auto"`。
5. `asset_role_fallback` 分支在自动模式下不再使用。

### T2 前端改为"图片清单 + 派生槽位"

文件：`video-submit-form-v2/upload-controller.ts`（重写）、`video-submit-form-state.ts`、`video-submit-form-model.ts`、`video-submit-form-v2.tsx`

1. 新状态：截图清单 `ScreenshotItem[]`，每项有自己的 `id`、加入序号 `seq`、`file`、`status`（uploading / recognizing / done / failed）、`screenshotType`（data / retention / null）、`recognizedFields`、`assetUrl`、`previewUrl` 等。识别任务、取消、过期结果判断全部按 `id`，不按位置。
2. 新纯函数 `deriveSlotsFromItems(items) → Record<"screenshot_1" | "screenshot_2", SlotViewState>`，输出现有 `slots` 结构，让 submit / draft / 截图槽位区等下游原样使用：
   - `screenshot_1` = 类型为 data 的项里 `seq` 最大且 done 的那张；`screenshot_2` 同理取 retention。
   - 还在上传/识别、或类型为 null 的项，按 `seq` 依次填进剩下的空位展示；没有空位时不占位，在状态行显示"还有 n 张在识别"。
3. 某项识别完成并判出类型后：同类里 `seq` 更小的旧项从清单移除（释放其 blob URL），提示一句"已换成新的互动截图 / 完播截图"。不弹框。
4. 数字回填：只有成为该类"当前那张"的项才写指标，沿用 `applyOcrMetricValues(..., { screenshotRefreshed: true, screenshotRole })` 的现有规则（data → screenshot_1 的字段，retention → `retention_metrics`）。标题、发布时间沿用现有"只在为空/有真实时间时写入"的规则，任何类型的截图都可以写。
5. 并发：所有新加入的图立即各自开始上传和识别，不排队。上传接口仍要求 `asset_role`，按加入时的空位传，只决定存储路径名，不代表类型；不改上传接口。
6. 类型为 null 的项：在该截图位上显示两个按钮「这是互动」「这是完播」，点后用显式 `screenshot_type` 对同一 `assetUrl` 重新识别，结果按第 3、4 条处理。
7. 编辑已交记录：已存截图转成清单项，类型取 `asset.screenshotType`；为空时按旧约定（screenshot_1 = data，screenshot_2 = retention）。
8. 删除 `findNextScreenshotUploadRole`、`shouldRequestScreenshotReplacement`、"智能对调"分支、"槽位已满，仅上传了前 x 张"提示，以及替换确认弹框（若无其他调用方）。清理完 grep 确认无残留引用。
