## 零、背景：为什么要做

老板（阿禅，非技术）反馈"网站对我像沙箱"——他看不到任何地方说明"这个数是怎么算出来的"。

export const CALIBER = {

## 二、任务 A：新建「数据口径说明」页面（主任务）

### 目标（产品语言）

让老板打开网站就能看到：**这个平台每个数字是怎么算出来的、为什么这么定**。看的人是业务负责人，不是工程师——不要出现字段名、表名、代码概念。

### 位置与入口

- 路由：`/admin/caliber`（新建）
- 导航：挂进 `src/lib/navigation/domain/navigation.ts` 的「管理中心」组，label 用「数据口径」，位置放在「AI 配置」之后
- 可见范围：仅管理员/公司所有者（沿用 `admin` 组的权限判断，不要新造一套）

### 页面结构

顶部一句话定性："下面写的就是这个平台里每个数字的算法。数字变了，这里会跟着变。"

然后按「一张卡一条规则」平铺，每条卡片三块内容：

1. **规则是什么**（一句话，大白话）
2. **为什么这么定**（老板拍板的业务理由，这是最有价值的部分）
3. **当前数值**（从 `CALIBER` 读，带单位）

### 必须包含的八条规则（内容已由规划方确认，照写）

| # | 规则 | 产品化表述（照抄） | 为什么这么定 |
|---|---|---|---|
| 1 | 产量口径 | 发了几条就算几条。被限流、被删稿的作品**照样算一条** | 这是考勤，不是评优。如果限流可以不算，那人人都可以说自己限流就不用发了 |
| 2 | 有效作品线 | 播放量低于 **[2000]** 的作品，不参与"平均播放"的计算 | 没跑起来的作品不代表真实水平。跑了一万被限流的，数据依然有效；无效的是压根没播放的 |
| 3 | 爆款判定 | 同时满足两个条件才算爆款：播放达到 **[3万]**，且超过这个账号自己最近 [5] 条平均水平的 [3] 倍（不足 [3] 条历史参照不判） | 不看绝对量，看的是"相对自己有没有起飞"。大号小号一视同仁 |
| 4 | 互动率/转粉率 | 先加总再相除，不是每条算完再平均 | 避免小播放量的作品把比率带偏 |
| 5 | 归属日期 | 按作品发布时间的上海日期算；认不出发布时间的，才按你填的归属日期算 | 以事实为准，不以填报时间为准 |
| 6 | 补交门禁 | 发布时间超过 **[72] 小时**才来填，不能直接交，要先申请补交 | 防止事后补录造假 |
| 7 | 三个岗位视角 | 文案、剪辑、运营是三个**看数据的角度**，同一条作品在各视角各出现一次。**看总产量请看达人列表** | 达人=账号主人，一条作品只归属一个达人，不会重复 |
| 8 | 数据来源 | 数据来自两张作品截图自动识别，识别完你可以逐项核对修改。识别不出来的数字，你自己填，系统照收 | 保留人工核对，防止识别错误污染报表 |

### 关键约束

- 卡片里所有方括号数字**必须**从 `CALIBER` 渲染，禁止硬编码
- 如果某个数字未来改成可配置（后台可调），页面要跟着变，不能出现两套
- 文案用业务语言，**禁止出现** `daily_reports`、`snapshot`、字段名、`RPC`、表名

### 验收

- `/admin/caliber` 管理员可打开，普通员工访问被拒（沿用现有权限，不新造）
- 页面上每个数字与 `CALIBER` 一致（手工对数一遍）
- 改一次 `CALIBER.effectiveMinPlay` 为 3000，页面数字跟着变成 3000（防漂移实测）
- `npx tsc --noEmit` + `npm run lint` 通过

### 禁区

- 不要做成可编辑的配置后台（本期只做"只读展示"，配置后台是另一个任务）
- 不要新造权限模型
- 不要动导航里其他条目

## 三、任务 B：平均播放排除低播放作品

### 目标

"平均播放"只统计真正跑起来的作品，不被没播放的作品拉低。

### 现状（实测）

- `src/lib/collaboration/domain/report-rules.ts:243` → `avgPlay = totalPlay / snapshotCount`（分母含全部有快照的作品）
- `src/lib/collaboration/domain/aggregates.ts:107` → `avgPlay = totalPlay / talentRows.length`（分母含全部条数）

这两处是**简单算术平均**，是唯一被低播放污染的指标。

### 不要动的地方（已核实无需修改）

- `countHits`（`report-rules.ts:186-210`）：已有 `play < 30000 continue`，低播放根本进不去，**不要改**
- `buildPerformanceMetrics` 的比率类（`report-rules.ts:243-256`）：先加总再相除，低播放权重天然极小，**不要改**

### 要做的事

1. 上述两处 `avgPlay` 的分母改为"排除 `play_count < CALIBER.effectiveMinPlay` 后的条数"
2. 分子同步排除（保持总和与分母同口径）
3. 分母为 0 时返回 0（不要 NaN，不要 null 破坏现有类型）
4. 抽一个共用函数（如 `avgPlayOf(rows)`），两处共用，避免再次分叉

### 验收

- 造 3 条数据（播放 100 / 5000 / 20000）：改前平均 8366，改后平均 12500
- 全部作品都低于 2000 时，平均显示 0，不报错、不 NaN
- 前后端：管理端「数据管理」与员工侧任何展示平均播放的地方同步（改前先 grep 全部 `avgPlay` 引用点，列清单再动手）

### 禁区

- 不改动 `reportCount`（产量照算全部，不排除）
- 不改动导出（`api/export/route.ts` 只出原始数据，不做口径加工）
- 不引入新的缓存

## 四、任务 C：快照同步的后果必须让用户看见

### 目标

历史手稿保存后，如果数据没能同步到管理端，**必须当场告诉用户**，不能静默成功。

### 现状（实测）

`src/lib/history-report-snapshot-sync.ts:56-63` `isHistorySnapshotSyncFailure`：有绑定视频但库里没有 24h 快照（0 行）时**判为不失败**，直接跳过。
设计意图正确（不凭空造底稿，避免伪造证据），但**后果对用户不可见**。

### 要做的事（三件，按顺序）

**C1 一次性补齐历史欠账（先做）**
查出所有"有日报、有绑定视频、但没有 24h 快照"的记录，按日报现有数据补建快照。
- 这不是伪造：数字本来就在日报里，只是搬到该在的地方
- 注意字段转换：日报里 `completion_rate` 等是字符串（`"12%"`），快照是数字，必须转换
- `follower_loss`、截图类字段日报没有，补建时留空（不要填 0 冒充）
- 补建动作必须先出只读报告（多少条、涉及哪些账号），确认后再写

**C2 保存时明确告知**
历史手稿保存成功提示改为：同步成功 → 现有文案；未同步 → 追加一句"该作品没有数据底稿，指标只更新到日报，管理端的表现不会同步更新"。
位置：`src/app/(app)/dashboard/history-report-edit-form.tsx:700` 附近的成功提示。

**C3 允许补建（可选，C1 之后仍有新增时才有意义）**
发现无底稿时提示"是否同时建立数据底稿"，用户确认则建。用户此刻手上的数字是他刚确认过的真实数据，此时建立不算伪造。

### 验收

- C1 出只读报告，数字经规划方确认后才执行写入
- 人工造一条"有日报无快照"的记录，保存后应看到 C2 的提示文案
- 提示文案不得出现 `snapshot`、`24h`、`video_metrics_snapshots` 等技术词

### 禁区

- **不得**为了让同步"成功"而凭空插入带 0 值的快照
- C1 写入必须单事务、失败即回滚、可回滚点明确
- 不改 `buildHistoryReport24hSnapshotPatch` 的字段清单（11 个字段是既定口径）

## 五、任务 D：缺勤对员工可见 + 被拒时有出路

### 目标

员工能看见自己哪天被记了缺勤、为什么、该找谁。**不开放"口供补交"通道**（业务已拍板：截图是内容凭证，不能开口子）。

### 现状（实测）

- 缺勤只存在于管理员的履约表（`fulfillment_records`），员工端工作台日历**没有任何缺勤状态**
- 补交被拒时提示为"请重新上传能看清发布时间的完播截图"（`src/app/api/video-submit/route-core.ts:298-305`）——对根本没有截图的人，这是死循环
- 管理员手工标记缺勤后，员工不收到任何通知

### 要做的事

**D1 员工端日历显示"缺勤"状态**
- 现状日历只渲染 submitted / waive / leave / pending（`src/components/submission/submission-calendar.tsx:47-70`）
- 新增 `absent` 状态：有视觉标识（不是空白），可点击
- 点击后展示：哪天、什么状态、原因

**D2 缺勤必须带原因**
- 缺勤原因区分三类：未提交 / 补交未通过 / 管理员认定
- 文案由服务端给出，前端不猜

**D3 补不上的情况给出明确指引**
- 当补交因"发布时间缺失"被拒且该作品已无法提供截图时，提示改为："这条无法自动补交，请联系管理员确认。"
- 不得再让用户在"重新上传截图"上死循环

**D4 管理员标记后通知员工**
- 复用现有通知系统（`notifications` / `todo` 行动项），不新造
- 通知内容：哪天被标记、什么原因、找谁

### 验收

- 用测试账号造一条缺勤：员工端日历能看到标识，点开有原因
- 造一条"作品已删除"的补交：提示是"联系管理员"，不是"重新上传截图"
- 管理员标记后，员工收到通知

### 禁区

- **不得**新增任何"无截图补交"的写入通道
- 不改动补交的审批逻辑与权限
- 不新增独立通知机制，复用现有
