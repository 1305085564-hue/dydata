# 线上质量观测与真实验收一期

日期：2026-09-08  
性质：只读基线审计 + 一期落地规划  
范围：Sentry、Web Vitals、性能专项、全站真实场景补验  
本轮边界：未安装依赖、未写 DSN、未建表、未执行 migration、未改生产库、未改权限/Auth/RLS、未做线上完成声明。

## 0. 结论

一期最建议做的不是马上优化页面，而是先补三条交付证据链：

1. **线上错误能被发现**：接入 Sentry，但必须先由阿禅拍板外部服务、隐私规则、项目归属和验收方式；接入先走 Preview/Sandbox，再进 Production。
2. **页面性能能被量化**：优先自建一张最小 Web Vitals 表，复用现有登录态和页面埋点思路，只收路由级指标；如果阿禅想最快看到现成 dashboard，再选 Vercel Speed Insights/外部平台。
3. **真实场景能补验**：用现有浏览器门禁和只读 sweep 先跑五条重点链路，补真实角色、真实账号、移动端、长会话和数据层证明；`/growth` 与 `/content-tools/rewrite` 已冻结重做，重做前只测故障，不投入大优化。

对线上交付的实际帮助：以后“用户说页面坏了/慢了/数据不对”时，不再靠感觉或单次本地截图判断，而能追到具体环境、页面、接口、角色、指标、数据库证据。

## 2. Sentry 接入评估

### 2.1 当前状态

只读检查结果：

- `package.json` 未发现 `@sentry/nextjs`、`@sentry/react`、`@sentry/browser`。
- `next.config.ts` 没有 `withSentryConfig`、source map 上传或 Sentry tunnel 配置。
- `.env.example` 和当前 `.env.local` 的 key 名称中未发现 `SENTRY_*` / `NEXT_PUBLIC_SENTRY_*`。
- `src/app/global-error.tsx` 与各路由 `error.tsx` 只做本地 `console.error` 和重试 UI，没有外部错误事件。
- `src/lib/api-logger.ts` 已有基础脱敏规则：token、secret、password、api_key、cookie、authorization 等敏感 key 会被重写，这是后续 Sentry 脱敏规则可复用的底线。

结论：**现在没有真正的线上错误监控**。Vercel 函数日志只能作为事后排查材料，不能替代 Sentry 事件、release、stack、source map 和告警。

### 2.2 一期最小接入方案

一期目标：先拿到“Preview 环境故意抛错 -> Sentry 收到脱敏事件 -> stack 可读 -> 不含隐私和密钥”的闭环，再进入 Production。

需要的环境变量：

| 变量 | 放置位置 | 用途 | 注意 |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_SENTRY_DSN` | Vercel Preview/Production + `.env.local` 示例只写 key 名 | 浏览器端上报入口 | public 变量会进前端包，只能放 DSN，不能放 token |
| `SENTRY_AUTH_TOKEN` | Vercel 构建环境 | 上传 source map/release | 绝不能写进仓库或日志 |
| `SENTRY_ORG` | Vercel 构建环境 | source map 所属组织 | 由阿禅或项目管理员提供 |
| `SENTRY_PROJECT` | Vercel 构建环境 | source map 所属项目 | 由阿禅拍板项目名 |
| `SENTRY_ENVIRONMENT` | Vercel + 本地 | 区分 local/preview/production | 不能靠域名猜 |
| `SENTRY_TRACES_SAMPLE_RATE` | Vercel + 本地 | 性能 trace 采样 | 一期建议 0，跑通错误后再开 |

| `next.config.ts` | 按 Sentry 官方 Next.js 文档包裹配置、上传 source maps |
| `sentry.client.config.ts` / `sentry.server.config.ts` / `sentry.edge.config.ts` 或 `instrumentation.ts` | SDK 初始化；具体文件命名按接入当天官方文档确认 |
| `src/app/global-error.tsx` | 捕获全局 React 渲染错误 |
| `src/app/(app)/**/error.tsx` | 捕获重点业务路由错误，并打 route/module tag |
| `src/instrumentation.ts` | 捕获 request/server 错误；Next 版本要求以本地 `node_modules/next/dist/docs/` 为准 |

一期只上报的事件：

- 客户端未捕获异常、React error boundary 异常。
- Server Component / route handler 未捕获异常。
- Next request 级异常。
- 仅在 Preview/Sandbox 放一个受保护的故意抛错验收入口；Production 不留普通用户可触发的测试按钮。

一期禁止上报的数据：

- 密码、token、cookie、authorization、service role key、Supabase key、Vercel token、Sentry token。
- 请求体、响应体、上传图片/OCR 原图、AI 提示词、AI 生成正文、剪贴板内容。
- 原始邮箱、手机号、姓名、完整 query string、完整 UUID 链路。
- localStorage、sessionStorage、浏览器 cookie。
- 数据库连接串、内部接口签名、第三方 API key。

推荐脱敏规则：

- `sendDefaultPii = false`。
- `beforeSend` 统一删除 request body、headers、cookies、query string。
- 只保留标准化 route，例如 `/admin/content`，不保留 `?videoId=...`。
- 用户信息默认只保留匿名 id 或角色 tag；是否允许保留真实 `user_id` 由阿禅拍板。
- 错误 tag 只放 `environment`、`release`、`route`、`role`、`company_scope` 这类排查需要的粗粒度信息。

### 2.3 阿禅必须拍板

1. 是否允许引入 Sentry 这个外部服务。
2. Sentry 组织、项目、管理员、告警接收人。
3. 是否上传 source map；推荐上传，否则线上 stack 很难读。
4. 是否允许记录用户粒度；推荐一期不记录姓名/邮箱/手机号，只保留匿名 id 或角色。
5. Production 是否启用 trace/performance；推荐一期先 0 或极低采样，先把错误闭环跑通。
6. Preview 验收时是否允许触发一次故意抛错。

### 2.4 完成标准

Sentry 真正完成必须同时具备：

- Vercel Preview 和 Production env 已配置，仓库无真实 DSN/token。
- Preview 故意抛错能在 Sentry 看到事件。
- 事件含 release/environment/route，source map 可读。
- 事件不含 cookie、authorization、service role、请求体、邮箱、手机号、AI 正文。
- `global-error.tsx`、至少一个 app route error、一个 API/server 错误都被验证。
- Production 开启后 24 小时做一次事件巡检，不能用本地 console 替代。

## 3. Web Vitals 上报评估

### 3.1 当前状态

只读检查结果：

- 全仓未发现实际 `useReportWebVitals`、`reportWebVitals`、`web-vitals` 接入。
- `src/app/(app)/layout.tsx` 已挂 `PageViewTracker`。
- `src/components/usage-events/page-view-tracker.tsx` 会对 app 内路径发送 `page_view`。
- `src/lib/usage-events/client.ts` 已使用 `navigator.sendBeacon`，失败时用 `fetch(..., keepalive: true)`。
- `src/app/api/usage-events/route.ts` 会登录态校验后写 `usage_events`。
- `supabase/migrations/20260714120000_add_usage_events.sql` 中的 `usage_events` 只有 `user_id/path/event_type/created_at`，不适合直接塞 Web Vitals 指标。

结论：**现在只有页面访问事件，没有页面性能真实用户指标**。现有 `usage_events` 能复用设计思路，但不建议硬塞 Web Vitals，避免把事件表变成混乱大表。

### 3.2 两个方案对比

| 方案 | 优点 | 成本/风险 | 验收方式 |
| --- | --- | --- | --- |
| 自建 Supabase 表 | 数据留在自家库；能按 route、环境、角色、构建版本聚合；复用现有登录态；和业务验收能对账 | 需要 migration、RLS、保留期、采样和聚合查询；做差会带来隐私和表膨胀风险 | 浏览器产生指标 -> `/api/web-vitals` 202 -> 表里有脱敏记录 -> SQL 查 p75 by route/env |
| 外部平台（Vercel Speed Insights / Sentry Performance 等） | 最快看到现成 dashboard；不用自建表；基础 Speed Insights 所有计划免费且接入轻；Plus 才解锁完整 Core Web Vitals、更多 breakdown 和 drains | 外部服务、费用、隐私、账号权限需拍板；和业务角色/数据层较难关联；Plus 在 Pro 上按项目计费 | 平台 dashboard 截图/导出 + 指标口径确认 |

推荐一期默认：**自建 Supabase 最小表**，原因是 DYData 是内部业务系统，最需要按登录角色、业务路由、部署环境追查问题；已有 `usage_events` 和 Supabase 权限基础，闭环更可控。

替代建议：如果阿禅希望“本周先看到现成可视化，不想先动数据库”，就选 Vercel Speed Insights。两者一期不要同时做，避免采集口径和隐私评审翻倍。

费用口径：按 2026-09-08 查询的 Vercel 官方文档，Speed Insights 基础版所有计划免费；Speed Insights Plus 在 Pro 上按项目计费，Enterprise 包含，完整 Core Web Vitals 与更多 breakdown 需要 Plus。

### 3.3 自建方案一期口径

只收这些字段：

- `metric_name`：`TTFB`、`FCP`、`LCP`、`CLS`、`INP`，不主动追历史 `FID`。
- `value`、`delta`、`rating`、`navigation_type`。
- `path`：标准化后的业务路由，不含 query string。
- `environment`：local/preview/production。
- `release` 或 build id。
- `user_id`：是否存原始 id 要阿禅拍板；推荐报表只展示聚合。
- `role` / `company_scope`：建议由服务端根据登录态补，前端不上报。
- `created_at`。
- 数据保留期：一期建议 30 天，后续按采样量、排查价值和表体量调整。
	
保留期建议一期设 30 天，后续按需调整。

明确不收：

- `metric.entries` 原始对象。
- 元素选择器、文本、图片 URL、请求 URL、query string。
- 设备指纹、IP、邮箱、姓名、手机号、cookie。
- 页面表单内容、AI 文本、OCR 图片内容。

后续可能涉及的文件：

| 文件 | 原因 |
| --- | --- |
| `src/components/web-vitals/web-vitals-reporter.tsx` | App Router 下的小型 client component，调用 `useReportWebVitals` |
| `src/app/(app)/layout.tsx` | 挂载 reporter，与 `PageViewTracker` 同层 |
| `src/lib/web-vitals/shared.ts` | 校验 metric 名称、数值、route、rating，做脱敏 |
| `src/app/api/web-vitals/route.ts` | 登录态校验、服务端补角色/环境、写入或丢弃 |
| `supabase/migrations/<timestamp>_add_web_vitals_events.sql` | 新表、索引、RLS、保留期策略；本轮禁止创建 |
| `next.config.ts` | 如开启 `experimental.webVitalsAttribution`，只允许在隐私规则批准后启用 |

### 3.4 完成标准

Web Vitals 真正完成必须同时具备：

- 阿禅已选目的地：自建 Supabase 或外部平台。
- 有隐私规则和采样规则。
- Preview 环境能产生指标并成功落点。
- Production 指标能按 route/env 聚合查看 p75。
- 不存 raw entries、不存 query、不存邮箱/手机号/cookie/body。
- 能覆盖 `/dashboard`、`/admin/content`、`/admin/collaboration`、`/growth`、`/content-tools/rewrite`。

## 4. 性能专项基线

### 4.1 当前已有工具和证据

已有能力：

- `npm run gate:browser`：首屏浏览器门禁，当前覆盖 `/topics`、`/dashboard`、`/admin/content`、`/admin/collaboration`，默认 timing 只报告，不直接失败。
- `scripts/perf-full-sweep.mjs`：覆盖更宽，包含 `/dashboard`、`/growth`、`/content-tools/rewrite`、`/admin/content`、`/admin/collaboration` 等页面和部分抽屉/长链路。
- `src/lib/perf.ts`：`DYDATA_PERF_LOG=1` 时输出局部耗时。
- `src/lib/admin-first-screen-observability.ts` + `/api/admin/first-screen-monitor`：后台首屏服务端观测，已有 Supabase 表与 cron 监控链路。
- `src/lib/performance-gate.ts`：有预算、重复请求、console、requestfail、HTTP 错误判定。

证据缺口：

- 现有历史基线主要是本地 production + company_owner，不等于 Vercel 线上。
- 缺真实员工账号、内容管理员、公司老板等多角色对比。
- 缺移动端视口证据。
- 缺长会话，尤其文案助手 SSE 生成、多轮历史、版本刷新。
- 缺写入后刷新消费者证据，例如提交日报后 Dashboard/协作/履约是否同时看到正确结果。

### 4.2 五个页面值得测的链路

| 页面 | 值得测 | 为什么 |
| --- | --- | --- |
| `/dashboard` | 首屏 SSR；`/api/dashboard/activity`；历史日期切换；豁免申请弹窗；编辑已有日报；OCR 上传耗时 | 员工每天使用，日期和日报主键绑定直接影响业务数据 |
| `/admin/content` | first-screen RPC；`/api/admin/content/list` 冷/热缓存；`topic-library-status` 初始 20 条和全量 400 条；直接 `videoId` 打开详情；返回历史 | 后台核心页面，当前已有显式加载全量列表和状态查询，最容易出现慢请求 |
| `/admin/collaboration` | 月份切换；共享月数据集；个人卡冷/热加载；`work-video?reportId=...`；异常状态映射 | 协作口径复杂，必须按 reportId 强绑定，不能回到账号/日期猜测 |
| `/growth` | 首屏 contract；趋势/排行榜接口；空状态/成熟员工状态 | 已冻结重做，只测是否故障和量化当前慢点 |
| `/content-tools/rewrite` | bootstrap；会话/技能/段落/历史/版本并发；SSE generate；生成完成后的重复刷新；长会话 | 已冻结重做，重做前只查故障、长会话稳定性和明显重复刷新 |

### 4.3 不值得现在优化的内容

- `/growth` 与 `/content-tools/rewrite` 已标记待整体重做；除非出现白屏、提交失败、严重超时，否则不做结构性能重构。
- timing warning 本身不等于功能 Bug；必须先确认用户可感知慢、线上 p75 或接口耗时证据。
- 已有热缓存命中的 `/api/admin/content/list` 不优先优化，先看冷启动和全量加载。
- UI 骨架屏、动画节奏、视觉细节不属于本轮质量观测一期。
- `/api/admin/first-screen-monitor` 现役保留；监控项里若存在历史路由残留，先记录，不在本轮顺手删除。

### 4.4 性能专项一期执行法

第 1 层：本地只读基线

- 用 production build 或现有可复用本地服务跑五个页面。
- 打开 `DYDATA_PERF_LOG=1` 收集服务端关键 loader 耗时。
- 跑 `npm run gate:browser` 保持现有四路门禁。
- 跑 `scripts/perf-full-sweep.mjs`，用 `DYDATA_SWEEP_ONLY` 限定五个页面。
- 产出只放临时目录或 acceptance 输出目录，避免把含账号视图的截图误提交。

第 2 层：Vercel Preview/Production 证据

- 只在阿禅确认测试账号和验收窗口后执行。
- 同一套页面至少跑 company_owner、admin/content role、真实员工账号。
- 只记录 route、HTTP 状态、请求数量、重复请求、p75/单次耗时、console error、截图编号。
- 禁止记录密码、cookie、token、service role、原始请求体。

第 3 层：是否优化的判断

- 只有线上或 Preview 证据显示“稳定慢/失败/重复请求导致用户动作受阻”才进入优化。
- `/growth`、`/content-tools/rewrite` 即使慢，也默认只作为重做输入，不在一期重构。

## 5. 全站真实场景补验清单

一期验收只覆盖“真实业务会出事故”的链路。每个场景都必须有页面、角色、动作、预期结果、数据层证明。

| 场景 | 入口页面 | 角色 | 动作 | 预期结果 | 数据层证明 |
| --- | --- | --- | --- | --- | --- |
| 低频查询：旧月份协作 | `/admin/collaboration?year=2026&month=07` | company_owner / admin | 切到 2026-07 或早期月份，打开成员与作品详情 | 页面不白屏；无权限外数据；作品打开的是对应日报 | `daily_reports.report_date >= 2026-07-27`；`visibleUserIds` 范围；`daily_reports.id -> video_id -> videos.id` |
| 低频查询：员工历史日期 | `/dashboard` | 真实员工账号 | 打开历史/日历，选择低频旧日期 | 有数据则可编辑/查看；无数据给明确空态；不误用今天 | `/api/dashboard/activity`；`daily_reports.user_id + report_date`；`is_void=false` |

   - 形成第一份“页面 -> API -> 数据层”验收表。

### 第 2 天：Preview 闭环与一期验收

前提：阿禅已拍板服务、隐私、账号、验收窗口。

## 9. 阿禅拍板清单

| 决策 | 推荐 | 理由 |
| --- | --- | --- |
| 是否引入 Sentry | 引入，但 Preview/Sandbox 先行 | 线上错误靠用户反馈太晚，Sentry 能定位 release/route/stack |
| Sentry 是否上 source map | 上 | 不上 source map，线上压缩 stack 很难排查 |
| Sentry 用户信息 | 不传姓名/邮箱/手机号；最多匿名 id/角色 | 够排查，不扩大隐私风险 |
| Sentry trace | 一期先 0 或极低 | 先把错误闭环跑通，避免采集面过大 |
| Web Vitals 目的地 | 默认自建 Supabase；要最快 dashboard 则选 Vercel Speed Insights | 自建更贴业务角色；外部平台更快，但完整 Core Web Vitals 通常需要 Plus，仍要隐私/费用拍板 |
| Web Vitals 是否存 user_id | 报表只展示聚合；原始 user_id 是否保留由阿禅定 | 追问题有用，但属于用户粒度数据 |
| 验收账号 | 需要 company_owner、admin/content、真实员工账号 | 一期目标是真实角色，不是只测老板号 |
| 验收窗口 | 选低峰期，先 Preview 后 Production | 避免把测试错误和慢请求打到业务高峰 |

## 10. 真正完成的验收标准

一期完成必须有这些证据，缺一项就只能叫“已接入部分能力”，不能叫完整完成：

1. Sentry：Preview 和 Production env 配好；故意抛错事件可见；source map 可读；事件脱敏通过；Production 24 小时巡检。
2. Web Vitals：明确目的地；生产真实用户指标可按 route/env 看 p75；不含隐私字段；能覆盖五个页面。
3. 性能专项：五个页面都有本地 + Preview/Production 记录；至少覆盖老板、管理员、真实员工；移动端单独记录。
4. 真实场景：每个场景都有页面截图/网络请求/API 状态/数据库只读证明；涉及写入的链路要证明刷新后的消费者页面也正确。
5. 边界声明：明确哪些是 local、Preview、Production；不把本地证据冒充线上。
6. 安全声明：报告不出现密码、token、cookie、service role、真实 DSN。
