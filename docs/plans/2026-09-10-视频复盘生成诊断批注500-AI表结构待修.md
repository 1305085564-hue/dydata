# 视频复盘「生成诊断批注」500 — AI 输入/结果表结构与代码不一致

> 状态：已定位根因，未修复。与 2026-09-10 抽屉精简（删漏斗图 + 台词切片，commit 3edf9f04）无关，属历史遗留，本次浏览器验收顺带暴露。

## 现象

视频复盘抽屉点「生成诊断批注」→ 前端提示失败。本地 dev 日志：`POST /api/admin/content-analysis 500`。

## 已确认的证据（本地 dev 连的是云端同一个 Supabase 库）

- 接口通、权限通（不是 403/404），错误发生在后端写库阶段。
- `ai_input_bundle` 表里**不存在 `insight_scope` 列**（按该列查询报 `42703 column does not exist`）。而 `content-analysis-service.ts` 生成前会先 `insert` 一个 `insight_scope` 输入包 → 写入即抛 `INPUT_BUNDLE_FAILED(500)`，在调用 AI 之前就崩。
- `ai_insight_result.insight_type` 的 CHECK 约束（`supabase/migrations/026_ai_input_and_result.sql`）只允许 `growth_edit`、`period_direction`，**不含 `content_analysis`**；即便过了第一关，写结果也会被约束拒。
- 两张 AI 表当前均为 **0 行**，说明这套输入包/结果表从未被 content_analysis 成功写入过。

## 影响

- 本地与线上同库 → 线上该功能大概率同样报 500、出不来批注。
- 归因对比、核心诊断、双截图等**不依赖 AI 的部分不受影响**（走 content-attribution 与快照数据）。

## 根因判断

`ai_input_bundle`/`ai_insight_result` 是 5 月为旧 AI 功能（growth_edit/period_direction）建的；后来接入 content_analysis 时，写入字段与 `insight_type` 白名单都没对齐当前库结构。属"未收口 / 迁移缺失"。注意：仓库 migration 026 定义 `ai_input_bundle` 有 `insight_scope`，但线上实测该列不存在 → 线上表结构与仓库 migration 已漂移，需先核对真实结构再决定改哪边。

## 修复待办（数据库高风险，禁止先行发布，先核对再动）

1. 先拿到两张表**线上真实列**：本地经 PostgREST 无法 introspect（OpenAPI 401、无 exec_sql、无直连 DB_URL）。用 Supabase SQL 编辑器跑 `information_schema.columns`，或补一个可连库的通道核对。
2. 据真实结构二选一（或组合）：
   - 补迁移让库对齐代码：给 `ai_input_bundle` 补 `insight_scope` 等所需列；给 `ai_insight_result.insight_type` CHECK 放开 `content_analysis`。
   - 或改 `content-analysis-service.ts` 的 insert 字段贴合现有库结构。
3. 迁移与代码同批发布，避免旧应用读已删表 / 新应用写不存在列的风险窗口。
4. 修复后必须真实点一次「生成诊断批注」跑通：确认能返回 `data_summary / copywriting_reason / abnormal_points`，并顺带确认 `suspected_stage / key_metric_evidence` 是否需要在前端补展示（当前后端算了但抽屉未渲染）。

## 验收

- `POST /api/admin/content-analysis` 返回 200，抽屉内出现「编辑部智囊 · 诊断思路批注」。
- `ai_input_bundle`、`ai_insight_result` 各新增一条 content_analysis 记录。
