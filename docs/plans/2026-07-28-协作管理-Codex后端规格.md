## 零、读前必看

### 项目惯例（违反会让 Antigravity 无法对接）

1. API 路由放 `src/app/api/admin/` 下，文件名用 `route.ts`
2. 权限校验统一用 `requireAdminActor`（见 `src/app/api/admin/auth-helper.ts`）
3. 数据库读写用 `createAdminClient()`（绕过 RLS），不用 `createClient()`
4. 权限作用域复用 `buildDataAccessScope` / `buildPermissionContextFromPermissionInfo`（`src/lib/data-access-scope.ts`）
5. 路径权限判定加到 `src/lib/analytics-access.ts` 的 `canAccessDailyManagementPath` 里
6. 导航注册加到 `src/components/admin-secondary-nav.tsx` 的 `ADMIN_SECONDARY_NAV_ITEMS`
7. 错误统一用 `assertSupabaseQuerySucceeded`
8. **不建新表、不改现有表结构**——三个岗位列已存在

### 数据口径（硬规则，不得自行调整）

- **统一从 `daily_reports` 算**，不从 `videos` 算。理由：daily_reports 有唯一索引 `(account_id, report_date)`，天然去重；全站其他分析页也走这张表，数字才不会自相矛盾。
- **统计起点下限：`2026-07-27`**。这天之前是单人全包时期，历史 NULL 是业务事实不是缺失，不纳入统计。所有接口的日期过滤必须加 `report_date >= '2026-07-27'`。
- **爆款判定**：`play_count >= 该账号窗口内播放中位数 × 2`。按账号算中位数（`src/lib/video-metrics.ts` 的 `median()` 和 `getAccountBaseline()` 可直接复用）。
- **环比**：本月 vs 上一个自然月，上月无数据返回 `null`，前端显示「—」。
- **`videos` 表只用于补录时的事务配对**，不参与任何聚合查询。

## 三、接口详细规格

### A · GET `/api/admin/collaboration/summary`

**用途**：顶部「归属健康度」窄条。只统计 2026-07-27 之后的记录。

**Query 参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `year` | number | 年，如 2026 |
| `month` | number | 月，如 7（1-12） |

**权限**：`requireAdminActor`，scope 用 `buildDataAccessScope`，`visibleUserIds` 过滤。

**查询**（伪 SQL，用 Supabase JS 链式写）

```sql
SELECT
  COUNT(*)                                              AS total,
  COUNT(*) FILTER (WHERE
    script_author_user_id IS NOT NULL
    AND video_editor_user_id IS NOT NULL
    AND operator_user_id IS NOT NULL
  )                                                     AS attributed,
  COUNT(*) FILTER (WHERE
    script_author_user_id = user_id
    AND video_editor_user_id = user_id
    AND operator_user_id = user_id
  )                                                     AS self_handled,
  COUNT(*) FILTER (WHERE
    operator_user_id IS NULL
    OR script_author_user_id IS NULL
    OR video_editor_user_id IS NULL
  )                                                     AS unattributed
FROM daily_reports
WHERE user_id = ANY(visibleUserIds)
  AND report_date >= '2026-07-27'
  AND report_date >= [月份起始]
  AND report_date <= [月份结束]
```

额外查询：「从不填分工的成员」= 本月所有记录都是 self_handled 的 user_id，join profiles 取 name。

**返回 JSON**

```jsonc
{
  "total": 48,
  "attributed": 30,         // 三个字段都不为 null
  "selfHandled": 12,        // 三字段全等于 user_id
  "unattributed": 6,        // 任一字段为 null
  "neverFillMembers": [     // 本月所有记录都是 selfHandled 的人
    { "userId": "...", "name": "小李" }
  ]
}
```

### B · GET `/api/admin/collaboration/operators`

**用途**：运营 Tab，每行一个运营，含「展开达人列表」所需数据。

**Query 参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `year` | number | 年 |
| `month` | number | 月 |

**权限**：同 A。

**核心逻辑**

```
1. 从 daily_reports 取目标窗口内 operator_user_id IS NOT NULL 的记录
2. 按 operator_user_id 分组
3. 对每组算：
   - operatorName：join profiles.name
   - reportCount：COUNT(*)
   - totalPlay：SUM(play_count)
   - avgPlay：totalPlay / reportCount（整数除法向下取整）
   - totalFollowerConvert：SUM(follower_convert)
   - hitCount：见爆款算法（下方）
   - momChange：本月 totalPlay vs 上月 totalPlay，null if 上月无记录
   - involvedAccounts：DISTINCT account_id 列表
   - operatedProfiles：
       每个 account_id → join accounts.profile_id → join profiles.name
       DISTINCT profile_id 计数 = "带了几个达人"
4. 展开子列表（每个达人一行）：
   按 account_id 分组，每行：
   - accountId、accountName（accounts.name）
   - ownerProfileName（accounts.profile_id → profiles.name）
   - reportCount、totalPlay、totalFollowerConvert
```

**爆款算法**（在应用层算，不在 SQL 里算）：

```
对该运营名下的所有记录，按 account_id 分桶。
每个桶内取 play_count 数组，用 video-metrics.ts 的 median() 算基线。
基线 × 2 为爆款线，play_count >= 爆款线 的记录计为爆款。
汇总各桶爆款数 = hitCount。
```

**返回 JSON**

```jsonc
[
  {
    "userId": "...",
    "name": "王运营",
    "reportCount": 20,
    "totalPlay": 1500000,
    "avgPlay": 75000,
    "totalFollowerConvert": 320,
    "hitCount": 4,
    "momChange": 0.12,        // +12%，null = 上月无数据
    "operatedProfileCount": 3, // 带了几个达人（反推）
    "accounts": [             // 展开用
      {
        "accountId": "...",
        "accountName": "账号A",
        "ownerName": "达人甲",
        "reportCount": 8,
        "totalPlay": 600000,
        "totalFollowerConvert": 120
      }
    ]
  }
]
```

### C · GET `/api/admin/collaboration/staff`

**用途**：文案 Tab 和剪辑 Tab 共用同一个接口，用 `role` 参数区分。

**Query 参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `year` | number | 年 |
| `month` | number | 月 |
| `role` | `"writer"` \| `"editor"` | writer=文案，editor=剪辑 |

**权限**：同 A。

**核心逻辑**

```
role="writer"  → 按 script_author_user_id 分组（IS NOT NULL）
role="editor"  → 按 video_editor_user_id  分组（IS NOT NULL）

每组算：
- name：join profiles.name
- reportCount：COUNT(*)
- totalPlay：SUM(play_count)（参考值，前端标注"不代表岗位成绩"）
- avgPlay：totalPlay / reportCount
- selfHandledCount：该人名下 script_author=video_editor=operator=user_id 的记录数
- involvedAccounts：
    DISTINCT account_id → join accounts(name)
    超过 3 个时返回前 3 个 + totalCount，前端负责折叠展示
```

**返回 JSON**

```jsonc
[
  {
    "userId": "...",
    "name": "张文案",
    "reportCount": 15,
    "totalPlay": 900000,    // 参考值
    "avgPlay": 60000,       // 参考值
    "selfHandledCount": 3,
    "involvedAccounts": [
      { "accountId": "...", "accountName": "账号A" },
      { "accountId": "...", "accountName": "账号B" }
    ],
    "involvedAccountTotal": 2
  }
]
```

### D · GET `/api/admin/collaboration/person`

**用途**：个人卡，跨三岗位看一个人。管理员看任何人，access_level=1 只能看自己。

**Query 参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `userId` | string (UUID) | 目标人员 ID |
| `year` | number | 年 |
| `month` | number | 月 |

**权限**：`requireAdminActor`，额外校验：`targetUserId` 必须在 `scope.visibleUserIds` 内，否则 403。

**查询**

```
1. profiles: name, team_id, group_id
2. daily_reports（目标月）：
   - 作为文案：script_author_user_id = targetUserId，IS NOT NULL
   - 作为剪辑：video_editor_user_id = targetUserId，IS NOT NULL
   - 作为运营：operator_user_id = targetUserId，IS NOT NULL
   同一条记录可能同时满足多个（一人多岗）
3. 近 6 个月（含当月）每月产量：按 role 分别 COUNT
   → 按 operator/script_author/video_editor 各自 GROUP BY month
4. 运营汇总（如果他本月有运营记录）：
   totalPlay, totalFollowerConvert, hitCount, momChange, operatedProfileCount
5. 明细列表：本月该人出现在任一岗位上的所有记录
   字段：report_date, account_id, accounts.name, title, play_count,
         roles(该人在这条里担任哪些岗位，数组),
         anomaly（软配对 videos 表，取 anomaly_status，配不上返回 null）
```

**返回 JSON**

```jsonc
{
  "userId": "...",
  "name": "李剪辑",
  "teamId": "...",
  "groupId": "...",
  "currentMonth": {
    "writerCount": 0,
    "editorCount": 12,
    "operatorCount": 0
  },
  "operatorSummary": null,   // 若本月有运营记录则填充，否则 null
  "trend": [                 // 近 6 个月，含当月，从旧到新
    { "year": 2026, "month": 2, "writerCount": 0, "editorCount": 5, "operatorCount": 0 },
    { "year": 2026, "month": 3, "writerCount": 0, "editorCount": 8, "operatorCount": 0 }
    // ...
  ],
  "records": [               // 本月明细，按 report_date 倒序
    {
      "reportId": "...",
      "reportDate": "2026-07-25",
      "accountId": "...",
      "accountName": "账号A",
      "title": "视频标题",
      "playCount": 120000,
      "roles": ["editor"],   // ["writer","editor","operator"] 三值之一或多个
      "anomaly": "正常"       // 软配对 videos.anomaly_status，配不上为 null
    }
  ]
}
```

**软配对规则**（取 anomaly_status）：

```sql
SELECT anomaly_status FROM videos
WHERE account_id = [report.account_id]
  AND lifecycle_state = 'active'
  AND (
    date(published_at AT TIME ZONE 'Asia/Shanghai') = report.report_date
    OR date(uploaded_at AT TIME ZONE 'Asia/Shanghai') = report.report_date
  )
LIMIT 1
```

配不上（0 行）→ `anomaly: null`。不抛错，不阻断主流程。

### E · PATCH `/api/admin/collaboration/attribution`

**用途**：单条归属补录。管理员修改一条日报的三个岗位字段。

**权限**：`requireAdminActor`，额外校验 `businessRole === "owner" || businessRole === "team_admin"`，否则 403。**本人不能改自己那条**（`targetUserId !== actorUserId`，否则 403）。

**Request Body**

```jsonc
{
  "reportId": "uuid",              // daily_reports.id
  "scriptAuthorUserId": "uuid",    // null = 清空（恢复默认自己）
  "videoEditorUserId": "uuid",
  "operatorUserId": "uuid"
}
```

**校验**

- `reportId` 必须存在且 `report_date >= '2026-07-27'`
- 三个 userId（非 null 时）必须在 `scope.visibleUserIds` 内
- 对应 `profiles` 记录必须存在

**事务逻辑**（两表必须同时改，否则报表和视频复盘显示不同责任人）

```
BEGIN TRANSACTION
1. UPDATE daily_reports SET
     script_author_user_id = $1,
     video_editor_user_id  = $2,
     operator_user_id      = $3
   WHERE id = $reportId

2. 软配对 videos：
   SELECT id FROM videos
   WHERE account_id = [report.account_id]
     AND lifecycle_state = 'active'
     AND (
       date(published_at AT TIME ZONE 'Asia/Shanghai') = report.report_date
       OR date(uploaded_at AT TIME ZONE 'Asia/Shanghai') = report.report_date
     )
   LIMIT 1

   如果找到 → UPDATE videos SET 三列 = 同样的值
   如果找不到 → 记录 videoUpdated: false，不报错，继续提交

COMMIT
```

**返回 JSON**

```jsonc
// 成功
{
  "ok": true,
  "videoUpdated": true,    // false = 软配对未找到对应视频，只改了日报
  "message": null          // videoUpdated=false 时填 "视频侧未找到对应记录，仅更新了日报"
}

// 失败
{ "ok": false, "error": "..." }
```

## 四、单元测试要求

以下场景必须覆盖，用项目现有测试框架（`vitest`）：

| 场景 | 接口 | 要测什么 |
|---|---|---|
| 空归属月份 | A、B、C | total=N，attributed=0，不报错 |
| self_handled 识别 | A | 三字段全等于 user_id 时正确计入 selfHandled |
| 软配对失败 | D、E | `anomaly: null` / `videoUpdated: false`，主流程不中断 |
| 上月无数据 | B、D | `momChange: null`，不返回 NaN 或 Infinity |
| 爆款基线不足 | B | account 内样本 < 3 条时 `hitCount: 0`，不崩溃 |
| 2026-07-26 之前记录 | 全部 | 不出现在任何返回数据里 |
| 本人改自己 | E | 返回 403 |
| access_level=1 看他人 | D | 返回 403 |
