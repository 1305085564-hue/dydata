## 三、新发现的独立根因（深度剖析）

### 1. [P0] 历史手稿弹窗点击事件被全局遮罩层拦截 (DialogOverlay Pointer Interception)
- **发现路径**：
  - 角色：普通员工 (`test-member@dydata.test`)
  - 页面：`/dashboard`
  - 操作：点击工作台控制栏右侧的【历史手稿】按钮，弹出“历史手稿纪事”浮层。
  - 异常：弹窗打开后，无论点击右上角【关闭】图标、左上角【返回手稿列表】还是内容区域，鼠标均无反应。
- **真实代码与 DOM 证据**：
  - 组件源码：`src/app/(app)/dashboard/video-submit-panel-v2.tsx:914-921`
    ```tsx
    <DialogContent
      className={cn(
        "fixed inset-0 m-auto z-50 flex flex-col ...", // ⚠️ 此处硬编码了 z-50 !
        ...
      )}
    >
    ```
  - 公共基元：`src/components/ui/dialog.tsx:34`
    ```tsx
    function DialogOverlay({ className, ...props }) {
      return (
        <DialogPrimitive.Backdrop
          data-slot="dialog-overlay"
          className={cn("fixed inset-0 isolate z-[80] bg-[#1C1917]/20 ...", className)}
          {...props}
        />
      );
    }
    ```
  - Playwright 实测截获：
    ```text
    <div data-slot="dialog-overlay" class="fixed inset-0 isolate z-[80] bg-[#1C1917]/20 ...">
    intercepts pointer events. Content sits at z-50, overlay sits at z-80.
    ```
- **技术根因与业务危害**：
  - 第一阶段/第三阶段 3C 施工包推行“全站统一分层契约（Dialog/Modal 为 `z-[80]`）”，将 `DialogOverlay` 设置为 `z-[80]`。
  - 然而在业务组件 `video-submit-panel-v2.tsx` 中，`DialogContent` 使用了 Tailwind 类 `z-50`，覆盖了基元原有的层级。
  - 导致遮罩层（z-80）浮在弹窗内容（z-50）上方，**形成透明遮罩拦截全部鼠标点击**。员工一旦打开历史手稿，不仅无法查看和编辑，甚至只能通过按键盘 `Escape` 键才能退出，严重阻断日常核心查阅动线。

- **真实代码与接口证据**：

  - 后端鉴权拦截：`src/app/api/admin/fulfillment/_shared.ts:116`

    export async function requireSystemPermission(req: NextRequest) {

      if (!ctx.permissions.manage_system) {

### 3. [P1] 成员管理组件维护“虚假权限开关”与混淆的角色文案 (Ghost Permission Editor)
- **发现路径**：
  - 角色：管理员 (`test-leader@dydata.test`)
  - 页面：`/admin/modules`
  - 操作：点击成员列表任意成员的“权限与数据范围”按钮，右侧拉出 Sheet 抽屉（`MemberPermissionEditor`）。
  - 异常：抽屉内渲染了 11 个权限勾选框（包含“系统配置管理”、“成员与团队架构”、“数据导出”等）以及“全团队/个人”数据范围单选框；然而在界面下方点击保存后，**对成员的实际权限没有任何改变**。
- **真实代码与设计契约证据**：
  - 界面实现：`src/app/(app)/admin/modules/modules-content-v3.tsx:1587-1647`
    ```tsx
    {ALL_PERMISSIONS.map((perm) => (
      <label key={perm.key} ...>
        <input
          type="checkbox"
          checked={permissions[perm.key] ?? false}
          onChange={(e) => handlePermissionToggle(perm.key, e.target.checked)}
        />
        <span>{perm.label}</span>
      </label>
    ))}
    ```
  - 运行时代理解析：`src/lib/company-permissions.ts:98-100`
    ```typescript
    export function fixedPermissionsForRole(role, legacyPermissions = null, groupMode = false): Permissions {
      void legacyPermissions; // ⚠️ 明确废弃了 profile 中的自定义 permissions 字段！
      const companyRole = resolveCompanyRole(role) ?? "member";
      return Object.fromEntries(DEFAULT_PERMISSIONS_BY_COMPANY_ROLE[companyRole].map((key) => [key, true]));
    }
    ```
  - 另外在升降级操作处（行 1687）：
    ```tsx
    <h4 className="text-[13px] font-semibold text-[#1C1917]">
      {member.role === "admin" ? "降级为组员" : "提升为组长 · 管理"}
    </h4>
    ```
    对于非公司所有者（`canManageCompany === false`），界面虽然禁用了按钮，但提示管理员“如需调整，请联系公司所有者”，却仍然允许管理员勾选保存那些根本无效的细粒度权限复选框。
- **技术根因与业务危害**：
  - 系统架构在前期已升级为“按角色固化权限模型（Fixed Permissions per Role）”，普通成员与管理员的权限完全由 `company_role` 派生，数据库里的自定义 `permissions` 字典已被彻底旁路。
  - 但前端成员管理抽屉仍保留了旧版的逐项权限配置界面。这给管理员造成严重假象，误以为自己为成员开通了“数据导出”或“素材管理”，实则成员依然无法操作，形成“系统失灵”的用户体验负反馈。

## 四、原根因未收口项与修复新回归

### 1. [修复新回归] 3C 浮层规范实施后业务组件层级反转 (3C Token vs Local Class Clash)
- **对应旧清单项**：第 3 阶段 `3C · 浮层层级、动态视口与 safe-area 契约`（对应 `P2-03` / `F-08` / `F-20`）
- **回归机制**：
  - 在 3C 施工中，统一建立了 `--z-modal: 80` 的层级阶梯，并在公共 `src/components/ui/dialog.tsx` 中把 `DialogOverlay` 与 `DialogContent` 均设为 `z-[80]`。
  - 但是，施工时未对业务页面进行全量 grep 排查，遗漏了 `src/app/(app)/dashboard/video-submit-panel-v2.tsx` 里的局部样式。该页面手写了 `z-50` 覆写在 `DialogContent` 上。
  - 结果公共层的 `DialogOverlay` 生效为 `z-[80]`，业务层的 `DialogContent` 被强行降为 `z-50`，直接引发本次 **P0 级点击穿透阻断**。
- **定性**：典型的**全局组件契约改造时，业务消费方覆盖类未彻底收口导致的新回归**。

## 五、第一轮漏检问题

### 1. [第一轮漏检] 权限拦截页文案误导与不可达申请 (PermissionGuard Dead End)
- **发现路径**：
  - 角色：普通员工 (`test-member@dydata.test`)
  - 访问路径：直接访问受控 URL，如 `/admin/settings` 或 `/admin/ai-config`
  - 页面表现：
    - 呈现提示文案：“该功能属于系统受控模块，当前仅对组长 · 管理开放。如有业务需要，请联系公司所有者或组长开通对应权限。”
    - 下方展示操作按钮：【申请查看权限】。
- **代码位置**：`src/components/permission-guard.tsx:60-63`
- **漏检原因与真相**：
  - 第一轮功能审计时，仅测试了未授权时“页面是否被挡住”，发现成功阻断即标记通过。
  - **但在真实业务中**：
    1. `/admin/settings` 需要的不是组长权限，而是专属的 `company_owner`（组长自身都无权进入）。
    2. 文案告知员工“联系组长开通”，但组长在固定权限模型下根本无法为员工开通该页面的权限。
    3. 点击【申请查看权限】后，没有对接真实的权限审批流工单，属于空挂按钮。

### 2. [第一轮漏检] 系统设置页 SSR 水化不一致 (SSR Date Hydration Mismatch)
- **发现路径**：
  - 角色：公司所有者 (`1305085564@qq.com`)
  - 页面：`/admin/settings` -> 【额度与业务规则】Tab
  - 控制台错误：
    ```text
    Error: Hydration failed because the server rendered text didn't match the client.
    - Server: "7/7/2026"
    + Client: "2026/7/7"
    ```
- **代码位置**：`src/app/(app)/admin/settings/components/quota-config-panel.tsx`
- **漏检原因**：第一轮主要采用静态构建与单测，未在真机浏览器中挂载老板权限页面检查 React Hydration 告警。服务端 Node 环境默认 locale 与客户端浏览器中文 locale 格式化日期字符串不匹配。

## 六、前端体验与响应式专项审查

### 1. 移动端小屏（375px / 430px）表现评估
- **优秀收敛项**：
  - 桌面端导航（`NavBarClient`）与移动端悬浮胶囊底栏（`MobileTabBar`）在 768px 断点切换利落，无重叠或闪烁。
  - 底栏悬浮胶囊样式优雅，具有毛玻璃背景（`backdrop-blur-xl`）与圆角阴影。
  - 点击“我的”触发的 `MobileMoreDrawer`，具备真实下拉手势与无障碍焦点回退（按 Escape 键聚焦原按钮）。
- **体验隐患（已查证）**：
  - **底栏入口与实际权限脱节**：
    普通员工登录移动端时，底栏 4 个快捷图标中包含【文案助手】（`/content-tools/rewrite`）；但当员工点击文案助手时，服务端检测到 `use_ai_copy: false`，立即重定向回 `/dashboard`。
    - 表现：员工在移动端点击底栏“文案助手”，界面闪烁一下后仍然停在工作台，没有给出任何“当前岗位无需文案助手”的提示。
    - 根因：`MobileTabBar` 内部提取 `directTabs` 时，默认提取了 `content-center` 分组的第一个子项，未结合当前登录账号的实际权限过滤可见性。

### 2. DOM 结构与无障碍 (A11y)
- **嵌套 `<main>` 违规**：
  - 页面全局外壳 `src/app/(app)/layout.tsx:40` 已声明顶级 `<main className="app-main ...">`。
  - 但在 `src/app/(app)/admin/modules/modules-content-v3.tsx:917` 中，内部容器再次手写了 `<main className="space-y-5">`。
  - 违反 W3C HTML5 标准（每个页面只允许存在一个活跃的顶级 `<main>` landmark），导致读屏软件混乱。
