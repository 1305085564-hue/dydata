# 成员生命周期管理方案

> 状态：本地施工完成，登录态异常分支与精确发布脚本已补齐，待生产 migration 与真实角色验收
> 日期：2026-08-04
> 范围：成员管理、团队归属、账号归档、账号恢复

## 一、结论

当前成员管理把两种不同动作混成了一个按钮：

- `removeMemberFromTeam` 已存在，但当前 `/admin/modules` V2 页面没有接入。
- 当前页面接入的是 `removeMember`，实际含义是封禁账号并清空团队归属。
- `profiles` 没有独立的账号生命周期字段，导致已封禁账号刷新后仍以“未分配团队”成员出现。

本方案将“团队归属”和“账号生命周期”拆成两条独立轴：

1. **移出团队**：账号仍在职，只是暂时没有团队，可再次分配。
2. **归档账号**：账号停止使用，但所有业务数据保留，只在归档入口查看。

不提供物理删除账号。业务上可以把归档理解为“删除使用资格”，数据库上必须保留账号和数据关联。

## 二、状态模型

新增 `profiles.membership_status`，不要复用现有 `profiles.status`。现有 `status` 只表示日报豁免状态，值域是 `active/exempt`。

### 2.1 成员状态

| membership_status | team_id | 含义 | 正常成员列表 | 归档列表 |
|---|---|---|---|---|
| `active` | 有值 | 在团队成员 | 展示 | 不展示 |
| `active` | `null` | 未分配成员 | 展示，可重新分配 | 不展示 |
| `archived` | `null` | 已归档账号 | 不展示 | 展示 |

归档状态下强制清空 `team_id/group_id`，避免归档账号继续参与团队权限、责任人候选和运营流程。

### 2.2 归档字段

建议新增：

- `membership_status text not null default 'active' check (membership_status in ('active', 'archived'))`
- `archived_at timestamptz`
- `archived_by uuid references profiles(id) on delete set null`
- `archive_reason text`
- `archive_snapshot jsonb`

`archive_snapshot` 保存归档前的角色、权限、团队和分组，仅用于审计与追溯，不用于自动恢复权限。这样恢复账号不会意外恢复旧的管理员权限。

## 三、操作语义

### 3.1 移出团队

复用现有 `removeMemberFromTeam` / `updateMemberTeam(userId, null)`：

- `team_id = null`
- `group_id = null`
- `membership_status` 保持 `active`
- 保留 Auth 登录能力
- 保留原角色和权限
- 保留日报、视频、账号、审计等全部数据
- 写入 `member_change_log.action_type = 'remove_from_team'`

页面提示必须明确：“账号仍可登录，数据保留，之后可重新分配团队”。

### 3.2 归档账号

新增独立 `archiveMember` 服务动作，第一版仅允许 owner 操作：

1. 校验目标不能是自己或 owner。
2. 保存归档前快照。
3. 设置 `membership_status = 'archived'`。
4. 清空 `team_id/group_id`。
5. 将角色降为 `member`，权限清空，避免恢复时自动复活管理权限。
6. 调用 Auth 管理接口设置长期封禁。
7. 清空 Auth 团队元数据。
8. 写入成员变更日志和审计日志。

不删除 `profiles`、`daily_reports`、`videos`、`accounts`、`exemption_*` 或历史审计数据。

### 3.3 恢复账号

新增 `restoreMember`，第一版仅允许 owner 操作：

- `membership_status = 'active'`
- 解除 Auth 封禁
- 保持 `team_id/group_id = null`
- 保持最低权限：`role = 'member'`、`permissions = {}`
- 清空归档字段
- 写入恢复审计

恢复后必须再走“团队分配”和“角色/权限调整”，不自动回原团队，也不自动恢复原管理员权限。

## 四、页面结构

### 4.1 正常成员工作台

保留当前团队架构树和成员卡片，增加两个明确入口：

- 成员详情/更多操作 → **移出团队**
- 成员详情/更多操作 → **归档账号**

“归档账号”必须使用高风险确认弹窗，并要求填写归档原因。

“全员大盘”仍然包含 `active + 未分配团队` 成员，但不包含 `archived` 成员。

### 4.2 已归档账号

在成员管理页面增加独立的“已归档账号”入口，展示：

- 姓名、邮箱、归档时间、归档人、归档原因
- 归档前团队和角色快照
- 保留数据入口
- 恢复账号操作

归档账号默认不出现在团队树、责任人下拉框、提醒名单、履约名单和权限管理正常列表。

## 五、读取范围与数据保留

### 5.1 操作数据

所有“当前有效成员”场景统一使用 `membership_status = 'active'`：

- `/api/dashboard/operator-members`
- 视频提交责任人候选
- 日报提醒和智能告警成员集合
- 履约工作台当前成员
- 成员分组与团队管理
- 成员权限修改候选
- 协作管理的当前成员筛选

需要区分“可操作成员”和“历史数据所有者”：

- 可操作成员只看 active。
- admin/content、admin/analytics、协作历史和审计页面仍可查看归档账号产生的历史数据。

### 5.2 权限范围

现有 `buildDataAccessScope` 的 `visibleUserIds` 不能直接粗暴改成只返回 active，否则可能让历史统计消失。建议增加 `activeVisibleUserIds`：

- `visibleUserIds`：保留现有语义，用于历史数据读取。
- `activeVisibleUserIds`：只包含 active 成员，用于当前操作和候选列表。

owner 的全公司范围尤其要使用 active 列表做操作过滤，不能因为 owner 看到全公司就把归档账号当作在职成员。

## 六、现有逻辑收口

以下旧逻辑必须统一，避免继续出现三种“踢出”：

1. `/admin/modules` V2 当前调用 `removeMember`，改为分别调用移出团队或归档动作。
2. 旧 `permission-manager` 继续复用统一的移出团队动作，确认没有独立语义。
3. AI `kickUser` 当前只封禁并修改角色，没有清空团队归属，不能继续保留独立实现；改为调用归档领域服务。
4. 原有 `removeMember` 不再作为模糊名称继续对外使用，改为 `archiveMember` 或内部兼容包装。

多表写入仍需处理部分失败：Auth 封禁、profile 更新、元数据同步任一步失败时，必须返回明确失败状态，并记录第一错误，不能只靠前端乐观回滚。

## 七、实施阶段

### 阶段 1：领域和数据库

- 新增 migration 和 `membership_status` 相关字段。
- 给现有 profiles 回填 `membership_status = 'active'`。
- 抽出成员生命周期类型、状态判断和权限决策函数。
- 统一 `member_change_log` action 类型。

### 阶段 2：后端动作

- 接入 `removeMemberFromTeam` 的正式语义和审计。
- 新增 `archiveMember`、`restoreMember`。
- 统一 Auth 封禁/解封和 profile 生命周期写入。
- 收口 AI `kickUser` 和旧成员管理动作。

### 阶段 3：读取链路

- 成员工作台拆分 active/archived 读取。
- 增加 `activeVisibleUserIds`。
- 更新责任人、提醒、履约、协作和管理候选查询。
- 保持历史数据查询不因归档而消失。

### 阶段 4：页面和验证

- 正常成员详情增加“移出团队”和“归档账号”。
- 增加“已归档账号”独立入口和恢复操作。
- 补充高风险确认、原因填写、加载、失败回滚和空状态。

## 八、验收标准

### 移出团队

- 点击后成员进入“未分配团队”。
- 账号仍能登录。
- 可重新分配团队。
- 角色、权限、日报、视频和账号数据不变。

### 归档账号

- 点击后账号不能登录。
- 正常成员列表、团队树、责任人候选和提醒名单不再出现。
- 归档列表可以看到账号和归档信息。
- 日报、视频、账号、审计历史仍可查询。
- 恢复后账号回到“未分配团队”，保持普通成员和空权限。

### 安全与回归

- team_admin 只能移出本团队普通成员，不能归档账号。
- owner 才能归档和恢复账号。
- 不能操作自己或 owner。
- 重复点击不会产生重复错误状态。
- Auth 写入失败、profile 写入失败、元数据同步失败均有明确错误和可重试结果。

## 九、测试清单

- 生命周期纯函数：active、未分配、archived、restore。
- owner/team_admin 权限矩阵。
- 移出团队后仍可登录，且数据保留。
- 归档后正常列表和候选列表排除。
- 归档历史数据仍可查询。
- 恢复后无团队、普通成员、空权限。
- 页面刷新后状态不反弹。
- AI `kickUser` 与页面归档结果一致。
- migration 字段存在、默认值和约束正确。

## 十、明确不做

- 不物理删除 Auth 用户。
- 不删除日报、视频、账号、审计或豁免历史。
- 不把 `profiles.status` 改造成成员状态字段。
- 不把所有 `team_id = null` 的账号直接当作归档账号。
- 不在恢复时自动恢复旧团队和管理员权限。
