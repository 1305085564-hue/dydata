## 二、全链路分析与改动点

### 2.1 现状链路（存在两处结构性缺陷）

```text
浏览器选图/粘贴
  ├─► [1] POST /api/submission-screenshots (上传至上海云托管)
  │         └─► PUT 新加坡 COS (ap-singapore) ── 跨海 ~1.5-2.2s
  ├─► (等上传完成后串行触发)
  │     ├─► [2a] GET /api/submission-screenshots/file ─► GET 新加坡 COS (跨海 0.5-1.1s)
  │     └─► [2b] POST /api/ocr-screenshot {bucket, path}
  │               └─► GET 新加坡 COS ── 并发跨海抖动撞 3000ms 硬超时 ─► 502 STORAGE_READ_FAILED ❌
  └─► (根本未进入 AI 识别)
```

### 2.2 改造后链路（双根治）

```text
浏览器选图/粘贴
  ├─► [改动点 1 · 并行支路 A] POST /api/submission-screenshots
  │         └─► PUT 腾讯云上海 COS (dydata-screenshot-sh-1409482292, ap-shanghai) ── 同城 ~30-150ms
  │               └─► 落盘后更新 assetUrl/bucket/path（仅用于草稿持久化与最终提交）
  │
  └─► [改动点 1 · 并行支路 B] POST /api/ocr-screenshot (FormData 直传本地 File + asset_role + screenshot_type)
            └─► 上海云托管直接内存读图送 AI 识别（零 COS 回读！）
                  └─► 两条支路统一经 Promise.allSettled 收口合并状态

刷新页面后 / 历史详情页预览 & 点击「重新识别」：
  └─► GET /api/submission-screenshots/file 或 POST /api/ocr-screenshot {bucket, path}
        └─► [改动点 2] 读取腾讯云上海 COS (ap-shanghai) ── 同城 ~10-50ms，恢复默认 3000ms 超时
```

## 三、模块详细设计

### 模块 A：上传页「存档与本地图识别并行」

1. **后端接口复核（零改动）**：
   - [`src/app/api/ocr-screenshot/route.ts`](../../src/app/api/ocr-screenshot/route.ts#L417-L433) 的 `parseMultipartPayload` 已完整支持 `FormData`（`file`、`asset_role`、`screenshot_type`），内置文件类型白名单、魔数校验、8MB 大小上限，并与 JSON 路径共用同一套鉴权、限流、通道切换与 `ocr_recognition_logs` 台账。无需改后端路由。
2. **前端控制器改造（[`upload-controller.ts`](<../../src/app/(app)/dashboard/video-submit-form-v2/upload-controller.ts>)）**：
   - 新增纯函数 `buildOcrMultipartFormData({ file, role })`（与现有 `buildOcrStorageRequestBody` 并列导出，便于单测直接断言显式携带 `asset_role` 与 `screenshot_type`）。
   - **首次放图 / 换图（`addFile -> runRecognition`）**：
     - 同一 `ocrTask`（单个 `AbortController`）同时驱动两条请求：
       - **存档支路**：`uploadSubmissionScreenshot({ accountId, role, file, signal: ocrTask.signal })`；一旦先完成且 `ocrTask.isCurrent()`，立即 `ocrTask.bindAsset(uploaded.url)` 并将 `assetUrl/bucket/path` 写入 item（若识别尚未完成，状态切为 `recognizing`）。
       - **识别支路**：`POST /api/ocr-screenshot` 发送 `FormData`（`file` + `asset_role` + `screenshot_type`），带 `signal: ocrTask.signal`。
     - 用 `Promise.allSettled([uploadPromise, ocrPromise])` 统一收口，严格按 4 种结果组合落终态（且落态前必须再检 `ocrTask.isCurrent()`，防止换图/取消后迟到回包覆写）：
       | 存档支路 | 识别支路 | 终态与约束 |
       | :--- | :--- | :--- |
       | 成功 | 成功 | `done`（或模型要求人工确认则 `pending_confirm`），写入 `assetUrl/bucket/path` + 识别指标/标题/发布时间 |
       | 成功 | 失败 | `failed`，保留 `assetUrl/bucket/path`，`ocrFallback: true`，文案「`<识别错因>，截图已保留，可直接手动填写指标`」 |
       | 失败 | 成功 | **必须判 `failed`**（未落盘的图绝不允许伪装为可提交），`assetUrl: null`、`ocrFallback: false`、文案为上传失败提示，不把槽位标成 `confirmed` |
       | 失败 | 失败 | `failed`，`assetUrl: null`、`ocrFallback: false`，展示上传失败提示 |
   - **点击「重新识别」（`retryItem`）**：
     - 若 `item.assetUrl && item.bucket && item.path` 已存在（截图已落盘），**不再重复上传 COS**，避免产生孤儿文件：
       - 若 `item.file` 仍在内存：直接走 `multipart/form-data` 识别；
       - 若刷新页面后 `item.file` 不在：走 JSON `{ bucket, path }` 识别。
     - 若之前是上传本身失败（无 `assetUrl`）：有 `item.file` 则重走完整「并行上传 + 识别」；无 `item.file` 则提示「截图文件已失效，请重新选择」。
   - **日志耗时口径**：保留 `[OCR 耗时]` 控制台输出，新增 `mode: "multipart" | "storage"`，便于线上验收确认首次上传确实走 `multipart` 且 `server_download_ms` 为空/0。

### 模块 B：腾讯云上海 COS 桶迁移与零丢失切流

1. **目标桶规格**：
   - 桶名：`dydata-screenshot-sh-1409482292`
   - 地域：`ap-shanghai`（与云托管服务 `dydata`、`dydata-d6g0gd1v37fcddf21` 同城上海）
   - 权限：私有读写（`private`），单 AZ 标准存储（与新加坡桶配置一致）
   - 访问凭据：继续复用现有子账号 `dydata-ai-ops`（`QcloudCOSFullAccess`），零新增密钥
2. **同步脚本设计（`scripts/sync-cos-sg-to-sh.mjs` + `scripts/sync-cos-sg-to-sh.test.mjs`）**：
   - 严格只读源桶（新加坡），只写目标桶（上海）；**不提供任何删除源桶/目标桶对象的功能**。
   - 参数模式：
     - `--dry-run`（默认）：列举双桶并输出差异统计，不写任何对象；
     - `--execute`：并发（默认 8）同步缺失或大小不一致对象；
     - `--incremental --since=<ISO>`：仅同步 `LastModified >= since` 的增量对象；
     - `--verify-only`：全量列举双桶比对 Key 集合与 `Size`，并按 `--sample=50` 随机抽样比对 `HEAD`/`Content-Type` 及字节 SHA-256。
   - **复制方式**：先单对象探测腾讯云 COS 跨地域 `PUT` + `x-cos-copy-source`（服务端直传，不经本机流量、极快，且 `x-cos-metadata-directive: Copy` 保留 `Content-Type` 与元数据）；若 COS 返回跨地域复制受限则自动回退为流式 GET→PUT 并校对字节数与 `Content-Type`。
   - **断点续传与幂等**：目标桶已存在且 `Size` 完全一致的对象直接跳过；重复执行输出 `copied: 0, skipped: N, failed: 0`。
   - **安全与审计**：清单报告写到 `output/cos-sh-migration/`（已 gitignore，不入库），任何日志/输出严禁打印 `COS_SECRET_ID`/`COS_SECRET_KEY`。
3. **零停机、零丢失切流步骤（架构师复核后统筹执行）**：
   - **Step 1**：新建私有桶 `dydata-screenshot-sh-1409482292`（`ap-shanghai`），确认私有 ACL（匿名 GET 返回 403）。
   - **Step 2**：跑 `--execute` 全量同步新加坡桶 → 上海桶（当前 4,995 个对象），再跑 `--verify-only --sample=50` 确认 0 缺失、0 字节不符、50/50 SHA-256 一致。
   - **Step 3**：记录切流前水位时间 `T0`，将合入 `main` 且过全套 6 项门禁的代码（含模块 A）发布至云托管，同时将云托管环境变量更新为：
     - `COS_BUCKET=dydata-screenshot-sh-1409482292`
     - `COS_REGION=ap-shanghai`
     - 删除临时止血项 `COS_READ_TIMEOUT_MS`（恢复代码默认 `3000ms`）
   - **Step 4**：确认新版本 100% 切流且 `/api/health?check=cloudbase` 返回 `200 up`、`deployment.json` 对齐 HEAD。
   - **Step 5**：立刻以 `--execute --incremental --since=<T0 提前 5 分钟>` 补同步切流窗口内写入新加坡桶的增量对象，再跑一次 `--verify-only` 确认上海桶完整包含新加坡桶全部对象（缺失 = 0）。
   - **Step 6**：同步更新 `.env.local`（仅本地参考）与 [`docs/reference/上线与运维.md`](../reference/上线与运维.md)、[`docs/reference/截图迁移进度.md`](../reference/截图迁移进度.md)，通知独立测试验收。
