这套系统缺一个状态：「这条渠道从此不供这个模型」。因为缺它，下架再上架会误点亮渠道、幽灵模型无法收走、检测动作会污染业务健康。你修的是这三条的**数据与逻辑根**。界面怎么排不归你。

## C-1 · 危险动作的执行前依赖计算（**最先交付**）

现有五类动作（停 / 删接入点、收走模型供应、全站下架、跨渠道批量启用）都是"点了就改，改完才知道影响了什么"。误停、误收是本轮唯一会伤到线上业务的动作。

给前端供一个**只读、执行前可调用**的查询，返回**真实名称**，不是数量：

| 输入 | 必须返回 |
|---|---|
| 停 / 删一个接入点 | 其下每条渠道的名称 + 每条线当前承载且正被业务使用的模型 + 受影响的业务功能名称 |
| 收走一个「渠道×模型」 | 该模型全站还剩几条可用线、是否仍被某业务独占解析 |
| 全站下架一个模型 | 会被连带关闭的渠道名单（C-2 拆级后此项**应为空**；不为空说明 C-2 没做完） |

**硬约束（冻结裁决③）**
- 名单逐条给真实对象。**只给计数算不合格。**
- **取不到完整名单时默认拒绝执行**，并返回可读的"为什么不能确定"（例：该接入点下有一条线从未成功同步，无法判断其在用模型）。**禁止用空数组代替"未知"。**
- 不得因成本高把依赖计算挪到执行之后。

**判据**：五类动作逐一实操，每类都能拦在一次点击之后、写入之前拿到名单。必测样本 `api1 default`（21 个死模型）、`api tang ChatGPT`。

## C-2 · 把「全站用不用」和「这条线供不供」拆成两件事

**现状（已核验，不得推翻）**
- 模型卡「在册/下架」开关与「模型管理与上下架」弹窗勾选框，接同一处理函数、同一后端动作。
- 该动作把这条模型在**所有渠道**的同一个开关一起推上或拉下（`app/api/admin/ai-config/route.ts:191-211`）。
- 逐渠道勾选写的是**同一列**（`lib/ai-config/batch-actions.ts:78-85`）。
- 不存在"全站上架"的独立记录：`isShelved` 由"任一渠道 is_enabled"推导（`components/compute-pool-panel.tsx:132-136`）。

**必须满足的约束（验收线，不是建议）**
1. 任一模型做一圈"全站下架 → 全站上架"，**每条线的渠道级状态逐条不变**。
2. **不得猜测历史意图**。今天所有"关着"的记录混杂着"用户主动关的""全站下架连累的""上游已不提供的"三种来历，数据上已不可区分。一律按「未表态」落，**且不得据"未表态"在任何后续全站动作里自动点亮**。
3. 合成口径改为：**业务能否用上这个模型 = 全站级要用 AND 这条线供**。三处显示（业务功能调度可用数、模型视角"N 渠道可用"、渠道视角挂载清单）必须是同一个数。
4. **不新增第三个全站概念**，只能在「接入点 / 渠道 / 模型」三层内解决。

> 总纲已把草案"三条意图"压成两个状态（渠道级 / 全站级）。"临时收起"与"恢复原样"不是新状态——约束 1 成立则"恢复"自动成立。**不要为它做快照或历史表。**

**迁移与对账**
- 对账对象是**"逐条线的渠道级状态不变"**，不是排序。导出每条「渠道×模型」改前 / 改后快照逐条比对。
- 不一致即回滚，回滚脚本单独成文件。
- 属数据库变更：按仓规走单迁移手工 apply + 登记版本号，**禁止对分叉本地树跑 `supabase db push`**。

**判据**
- 渠道 A 关掉模型 X → 全站下架 X → 全站上架 X → 渠道 A 的 X **仍为关**，同渠道其余逐条不变。
- 全站下架期间在渠道 A 把 X 勾上 → 该模型对业务的可用数**仍为 0**，且"这条线已就绪但模型全站未启用"这个判断结果**必须能在接口响应里读到**（供前端显示，不许静默）。

## C-3 · 检测动作不许改变供给

**现状（已核验）**
- 检测失败会写健康：`route.ts:507-517`。
- 超时被判为**渠道级**：`lib/ai/provider-health.ts:25`（timeout → `key`）。
- **成功不洗白渠道**：模型级通过只写模型行（`route.ts:535-536`），只有渠道级测试才洗白（`:465`）→ 这个按钮只会让渠道变红、永远不会变绿。
- **连败即退出调度**：`consecutive_failures` 达 3 且无到期时间即判不可用（`lib/ai/provider-routing.ts:170-183`）。注释自称"健康冻结 5 分钟"，但这条路径不写到期时间。
- 检测范围今天已扩到全部挂载行（`route.ts:797-798` 无 is_enabled 过滤）。

**已定口径（四条，缺一不可）**
1. 检测**只测上架中的**。
2. **不参与业务的模型的失败，一律不得计入业务健康度。**
3. **反复点检测，系统的实际供给关系与调度行为不许发生任何变化。** ← 这是"可以放心反复点"的硬版本，直接对应上面第 4 个根因：检测写的是调度真正读的字段，"不改熔断语义"挡不住它。
4. 一条渠道上只要有一个在用模型探测通过，该渠道不得停留在"故障"显示上。

**判据（全为硬断言，不接受"我测过没问题"）**
- 检测执行前后，业务功能调度那一栏的**数字与颜色逐格相同**。
- 同一条渠道**连点 5 次**，其下所有模型的可用渠道数零变化。
- 检测通过后渠道从「故障」回到「健康」，**不需要再点别的按钮**。

## C-4 · 幽灵模型：能收走，但不许据单一信号判定

**现状（已核验）**
- 同步**只登记新增、从不回收**：`app/api/admin/ai-config/sync-models/route.ts:118` 只有 `toInsert`，无回收分支。
- 存量真实数字：`api tang ChatGPT` 上游清单 5 个、系统挂 8 个、其中 3 个稳定 404；`api1 default` 挂 **21 个**；全池 **127 个**挂载关系。
- 取消勾选不收走，行仍留在检测面里。

**总纲已收回草案那句"清算不需要新增采集"。不许拿 `available_models` 当唯一依据**，三个硬伤：
1. 只在同步成功时写（`sync-models/route.ts:134-138`；失败分支 `:40-68` 直接抛错，字段不更新）。
2. 空值与"上游确实返回空清单"**不可区分**。
3. 上游清单本身不完整——实测出现过清单只列 5 个、其中 3 个调用时 404 的渠道。

**口径**
- 「上游已不再提供」= **两个独立信号同时成立**：清单里没有 **且** 实测调用不通。仅凭清单依据的降级为「疑似，未验证」，**不得进入可一键收走的集合**。
- 未成功同步或清单为空的渠道，一律返回「未知」。**禁止用 0 冒充"很干净"。**
- **不承诺自动发现**。时效改为可核事实：**每次同步成功后，当次必须对该渠道给出「已核对 / 未知」二选一结论**，不许沉默。
- **收走的防护与删渠道对称**（删渠道今天有依赖闸：`此密钥正在被【X】使用且无备用模型，禁止删除`；收走单个「渠道×模型」破坏半径相同却**没有任何闸**）。该模型全站只剩这一条线且正被业务解析使用时，**拦下并说明原因**，或强制先走"换模型"引导。

**判据**
- `api tang ChatGPT` 的"待收走"数量 = **3**（不是 5、不是 0）。
  **这是本轮唯一带真实期望值的判据，必须逐条对上。**
- 对一条从未成功同步过的渠道返回「未知」，**不返回 0**。
- 收走"全站唯一线路且业务在用"的模型 → 被 C-1 的依赖闸拦下。
