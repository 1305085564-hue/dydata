## 一、结论摘要（先看这 8 条）

1. **数据库规模比历史记录小一圈**：审查时库内实际是 **99 张业务表 / 61,301 行 / 81 MB**，不是此前记的"约 139 张表、约 7 万条"。139 是"public 下全部对象"（含 321 个索引等），7 万包含了 auth/storage 元数据。PG 版本 **17.6**，比 CloudBase 主推的 17 版本对齐，属于好消息。【已确认】

2. **有一个必须立刻知道的安全问题**：数据库里有 **31 个高权限函数（SECURITY DEFINER）没有收回匿名执行权限**，其中如 `admin_content_first_screen(p_visible_user_ids)` 完全信任调用方传进来的用户 ID 数组。我用 `SET ROLE anon` 实测，**匿名身份传一个负责人 ID 就拿到了 5 条真实作品数据（8,268 字节）**。前端公开的 anon key 人人可见，这意味着"知道地址的人可以绕过网站直接读公司数据"。这不是迁移造成的，是**现在就存在的漏洞**，迁移前修比迁移后修便宜得多。【已确认：库内实测】；【未确认：从公网 REST 端点是否真能打通——本机网络到 `*.supabase.co` 的 HTTPS 被重置，见 §8.4】

3. **"截图慢"这个问题已经解决了大半，但落点不是国内**：2026-10-19 21:06 生产已把截图读写切到 **腾讯云 COS**，3,264 个对象全部迁完并逐对象校验，Supabase Storage 退为只读备份（见 `docs/reference/截图迁移进度.md`）。但正式桶是**新加坡**（`dydata-screenshot-sg-…`），不是广州。当日实测：**新加坡桶读取 p50 33ms / p95 65ms；广州桶 p50 802ms / p95 1,214ms，37 次里 15 次超时**。原因是 Vercel 函数跑在新加坡（`sin1`），去广州属于跨境绕行。→ **"把数据搬回国内就会变快"这个前提，在这里不成立。**【已确认，有当日实测记录】

4. **"数据库读取慢"的根因不是数据库慢**。我在生产库上直接跑真实函数：`admin_content_list_page`（50 行）**48 ms**、`admin_content_first_screen` **48 ms / 返回 161 KB**、`admin_videos_first_screen` **122 ms**、`topics_pool_aggregates` **4 ms**、`get_leaderboard_rows` **44 ms**。单条查询都在 150ms 以内。慢在**一次页面要串很多条请求 + 一次拉全量 + 截图没有缩略图也没有懒加载**，属于应用侧问题，换数据库搬家解决不了。【已确认：`EXPLAIN (ANALYZE)` 服务端执行时间】

5. **认证是这次迁移唯一真正的硬阻塞**。84 个员工账号全部是"邮箱 + 密码"单一方式，没有第三方登录。腾讯云官方迁移文档明确写：`auth` schema 由平台管理，不能 dump/restore，建议"让用户重新激活账号，或与平台运营沟通批量导入"。也就是说 **84 个人的密码，自助迁移路径不存在**。用户 ID 本身可以保留（CloudBase 建号 API 支持自定义 uid，最长 64 字符，我们的 UUID 是 36 字符，放得下）。【已确认：官方文档原文】

6. **代码改动量比"换个地址"大得多**：生产代码有 **55 个文件**直接引用 Supabase SDK，**82 个文件**用服务端管理员客户端，**325 处**表查询，**32 处** RPC 调用（29 个不同函数），**63 处**认证调用。更关键的是 CloudBase 的 REST 路径是 `/v1/rdb/rest/<表>`，Supabase SDK 写死 `/rest/v1`，**不能靠改环境变量迁移**，必须换适配层。【已确认：全仓扫描】

7. **有一块"代码跑在结构前面"的漂移**：抖音账号同步功能有完整路由和页面，但它依赖的 5 张 `douyin_*` 表**在生产库里根本不存在**（对应迁移 `20261017170811_douyin_account_sync.sql` 未执行）。迁移时必须二选一：补表，或明确把这块推迟。【已确认】

8. **免费版撑不起生产**。CloudBase 免费体验版每月 3,000 资源点，PostgreSQL 按核·小时计费（官方产品页 0.342 元/核·小时，共享实例按 0.5 核计），3,000 点只够约 **17.5 个核·小时**，也就是每天不到 1 小时的数据库活跃时间。生产必须上个人版（40,000 点）或更高，且 40,000 点是否够用取决于"数据库活跃时长"，见 02 号报告 §7。【已确认：官方计费页】

## 三、系统架构现状

```
用户浏览器（中国大陆）
   │  HTTPS
   ▼
Vercel 边缘 / 函数（固定区域 sin1 新加坡）
   │                          │
   │ PostgREST + Auth (HTTPS) │ 私有读（服务端代理）
   ▼                          ▼
Supabase（新加坡）         腾讯云 COS（新加坡，私有桶）
 ├ PostgreSQL 17.6 / 81MB     └ 截图 3,264 个 / 约 890 MB
 ├ Auth（84 账号，邮箱密码）
 └ Storage（只读备份 3,646 条元数据）
```

| 项 | 现状 | 证据 |
|---|---|---|
| 框架 | Next.js 16.3.3 App Router，React 19.2.7 | `package.json` |
| 部署 | Vercel，`main` push 上线，固定区域 **sin1** | `vercel.json` 的 `"regions": ["sin1"]` |
| 数据库 | Supabase 新加坡，PostgreSQL **17.6**，81 MB | `select version()` |
| 认证 | Supabase Auth，仅 email/password | `auth.users` 的 provider 全为 email |
| 文件 | 生产已切 **COS 新加坡私有桶**；Supabase Storage 留只读备份 | `截图迁移进度.md` |
| 定时任务 | 全部在 Vercel Cron（3 个：保活 / 清理通知 / 抖音同步），**数据库里没有 pg_cron** | `cron.job` 不存在 + `vercel.json` |
| 实时订阅 | **零使用**（全仓 0 处 `.channel(` / realtime） | 代码扫描 |
| 服务端动作 | 9 个 `use server` 文件，25 个 API 路由目录 | 代码扫描 |

**这条架构事实决定了迁移的第一性问题**：计算（Vercel sin1）与数据（Supabase 新加坡）现在在**同一地域**，所以服务端查询延迟极低；用户在中国大陆，所以**用户侧**慢。如果只把数据库搬到上海、函数仍留在 Vercel，就会把"用户侧慢"换成"服务端跨境慢"，**总账可能更差**。详见 03 号报告 §2。

### 5.5 权限体系

- **角色**：标准 Supabase 三件套齐全（`anon` / `authenticated` / `service_role`），`service_role` 带 `BYPASSRLS`；无自定义应用角色。
- **RLS 覆盖**：99 张表中 **96 张已开启**，3 张未开启（见风险 R2）。
- **策略与 `auth.uid()` 的强耦合**：240 条策略里 **168 条**直接用 `auth.uid()` 与 `uuid` 类型列比较（如 `profile_id = auth.uid()`）。CloudBase 的 `auth.uid()` 返回 `text`，与 `uuid` 列比较会报"操作符不存在"，**这 168 条策略必须改造**（加 `::uuid` 或统一改列类型）。【已确认：`pg_policies` 统计】
- **表级 GRANT**：`anon` 对 `public` schema 有 USAGE；具体表权限被 3 张无 RLS 表以外的策略兜住，但 `anon` 对 `videos` 等表的直接 SELECT 会因策略里调 `is_admin()` 而报错（我实测报 `permission denied for function is_admin`）——属于"报错而非泄露"，可接受但不干净。

### 6.1 用户 ID 与业务数据的关系（迁移最关心）

- 用户 ID 为 `uuid`（36 字符），业务侧 **29 张表**用 `uuid` 类型存 `user_id` / `owner_id` / `created_by` 等。
- **public 下有 12 个外键直接指向 `auth.users(id)`**：`profiles.id`、`exemption_grant.user_id`、`exemption_request.applicant_user_id`、`fulfillment_records.user_id`、`fulfillment_records.marked_by`、`team_join_requests.applicant_user_id`、`usage_events.user_id`、`yike_*` 6 张。
- 其余 `user_id` 字段**没有外键**，靠应用层保证。

**结论**：只要 CloudBase 侧能把用户 ID 建成同一串 UUID，业务数据的关联**天然不断**；但上面 12 个外键必须处理（CloudBase 的 `auth.users.id` 是 `varchar(64)`，`uuid` 列无法直接建外键指向 `varchar`），最简单的做法是**迁移时去掉这些外键、保留列值**。

### 6.2 会话与登录链路

| 环节 | 现状实现 | 迁移影响 |
|---|---|---|
| 登录 | 浏览器 `supabase.auth.signInWithPassword`，**前端直连 Supabase** | 必须改为经本站服务端（境内可达性 + 凭证不外发） |
| 会话 | `@supabase/ssr` 写 HttpOnly cookie，middleware 每次 `auth.getUser()` 校验 | 需要重写一套 cookie/会话层 |
| 刷新 | SDK 自动 refresh token | CloudBase Access Token 默认 2 小时，需接入刷新逻辑 |
| 找回密码 | `resetPasswordForEmail` + 邮件链接回调 | CloudBase 有邮箱验证/找回流程，但**模板、域名、回调地址需重新配置** |
| 登出 | `signOut` 后清 cookie | 同左 |
| 封禁 | `auth.admin.updateUserById({ ban_duration })`（`member-lifecycle-service.ts` 3 处） | CloudBase 用 `userStatus: BLOCKED`，语义接近 |
| 建号/删号 | `signUp` / `auth.admin.deleteUser` | CloudBase `createUser` / `delete` |

**风险点**：登录页面是浏览器直连 Supabase Auth。这解释了为什么"境内登录偶发失败/慢"——本机实测 `*.supabase.co` 的 HTTPS 连接会被重置。

### 8.1 服务端查询实测（生产库，`EXPLAIN (ANALYZE)` 服务端执行时间）

| 函数 | 服务端执行时间 | 返回体积 |

| `topics_pool_aggregates` | **4 ms** | 25 KB |
| `get_leaderboard_rows`（近 30 天） | **44 ms** | — |

**结论：数据库本身不是瓶颈。**

### 8.2 慢的真实来源（应用侧）

| 问题 | 证据 | 影响 |
|---|---|---|
| 全量路径一次拉全库 | `loadAdminContentPageData` 按 200 条一批、并发 6，要查 `videos`(2,703) + `video_metrics_snapshots`(2,669) + `video_tags`(8,209) + 分段 + 上周期作品 | 一次请求几十条 SQL、十几 MB 载荷。**与历史"24 条 SQL / 5,011 条记录 / 13.7 MB"的口径吻合，属同一路径** |
| 该全量路径仍在用 | `/admin/pulse`（每日大盘）直接调它；`/admin/content` 保留为兼容入口 | 大盘一次全量 |

| 截图无懒加载 | 全仓未在截图组件上找到 `loading="lazy"` | 进页面即并发请求 |
| 首屏性能埋点污染 | `admin_first_screen_perf_events` 30 天内 n=2,431，`auth_ms` 中位数 **96 ms**——这是"中国大陆→新加坡跨境往返"的特征，而 Vercel sin1 同区应在 10ms 内；说明表里混入了本地开发/门禁采样 | 该表的 p95=28 秒、p99=53 秒**不能直接当作生产指标** |

【部分确认】生产真实 P95 未取得：Vercel 日志仅保留约 1 小时且无耗时字段，本轮窗口内 `/api/admin/content` 零请求。

### 8.3 网络可达性实测（新增发现）

从本机（中国大陆）直接访问：
- `db.*.supabase.co:5432` → **DNS 不解析**（Supabase 已停用直连域名）
- `*.pooler.supabase.com:5432`（aws-1 节点）→ **可连**，`select 1` 往返约 100 ms
- `*.supabase.co` 的 HTTPS（Cloudflare）→ **TLS 握手被连接重置**（`Recv failure: Connection reset by peer`）

**含义**：`NEXT_PUBLIC_SUPABASE_URL` 这条链路（浏览器 Auth / 直连 REST）在大陆网络下本来就不可靠。这是"境内用户觉得慢/偶发登录失败"的一个合理解释，也说明**迁移的真正收益在"用户→服务端"这一段，不在"服务端→数据库"那一段**。

### 8.4 截图下载的分解（已有实测）

| 环节 | 实测 | 来源 |
|---|---:|---|
| COS 新加坡 读取服务端耗时 | p50 33 ms / p95 65 ms | 10-19 验收 |
| COS 广州 读取服务端耗时 | p50 802 ms / p95 1,214 ms，37 次中 15 次超时 | 同上 |
| 单图端到端（新加坡桶） | p50 347 ms / p95 575 ms | 同上 |
| 服务端截图接口总耗时（生产 2 小时观察） | p50 63 ms / p95 147 ms | 同上 |

**结论**：截图"慢"现在主要是**用户到 COS 的跨境链路**，不是服务端。**广州桶反而慢 10–30 倍**，因为 Vercel 函数在新加坡。
