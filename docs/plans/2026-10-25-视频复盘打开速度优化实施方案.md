# 视频复盘打开速度优化实施方案

状态：A及本轮相关修复已本地提交；旧候选时间目标通过，当前候选的角色/更新/故障/性能与正式门禁未闭环，尚未 push。执行者：Codex。范围：视频复盘首屏、列表切换、详情返回的加载链路。

交付目标：遵循产品已确认的数据与权限口径，让视频复盘常用场景稳定在 1～2 秒可用，并交付可复现的前后对照证据。按本方案连续施工、分段验证、本地提交，不逐段等待指令；达到目标就停止，不为增加缓存而增加缓存。

事实依据：`docs/reference/2026-10-25-缓存现状复核与打开速度优化建议.md`。该报告用于定位，旧测速不能替代本次验收。本文件是实施入口，不再重做全站缓存盘点。

## 1. 冻结目标与边界

| 项目 | 必须满足 |
|---|---|
| 常用首次打开 | 点击导航/开始导航 → 真实列表可见且筛选、详情入口可操作，p95 ≤2,000ms；不能用骨架屏、响应首字节或后台接口时间替代 |
| 重访与切换 | 同条件重开、相邻日期来回切换、详情返回列表，分别 p95 ≤1,000ms；新日期第一次读取按首次打开验收 |
| 单列表接口 | p95 ≤1,200ms；独立于页面目标，两项都要过 |
| 内容一致 | 同一数据版本下，作品集合、顺序、总数、分页、日期目录、评级与筛选结果一致；时间/耗时诊断字段除外 |
| 更新可见 | 自己保存/回收/恢复/更新关联数据后，首次成功刷新就是新结果，不等缓存到期；他人修改最迟在源结果生成后 60 秒的下一次成功读取反映 |
| 权限 | 每次服务端读取确认当前权限；换号、调组、降权后不能复用旧范围的缓存；无权限不返回内部内容 |
| 故障 | 缓存不可用能有界回源；刷新失败明确提示，不能把旧结果当最新；不得缓存错误响应 |

2 秒是本专项的更严格交付目标，不顺手改全站预算。60 秒沿用既有列表上限，不增加过期后继续展示的宽限期；没有授权新增“更长时间旧数据也算成功”的产品口径。

**包含**：数据库查询编排、列表加载器、必要的共享结果缓存、当前浏览器会话内复用、依赖写入的缓存失效、定向观测和验证。

**排除**：全站批量提速、截图存储/授权/CDN、Cloudflare 规则、广州迁移、主库迁移、UI布局/视觉/动效、审批等业务逻辑、权限规则和账号配置、长期本地离线存储、新购服务。其他页面和截图的性能记待办，不扩大本任务。

## 2. 开工一次核对，之后开始首个改动

1. 读 `AGENTS.md`、`docs/DYData产品全书.md`，按索引读性能、后端、数据口径和权限相关章节；写 Next.js 代码前读安装版本的相关指南。只加载实际触发的 Skill。
2. 记录当前 HEAD、工作区差异、远端与生产 SHA；用隔离工作树承载改动，保留其他会话文件。以开工确认的代码基线做改前/改后对照；若与生产已有口径差异，分开记录，不能拿版本差异当性能收益。
3. 复核页面 → 首屏加载器 → SQL 与列表刷新接口；定位见下表。10～15 分钟内完成定位并开始复现测试或观测改动。遇到环境问题，继续完成可独立的代码/查询工作，不空转。
4. 固定同账号、同角色、同团队、同日期、同排序、同分页及网络；默认场景先各 5 次诊断。保存脱敏原始计时、版本和数据规模。

## 3. 按顺序执行，按达标情况跳过无收益工作

### A. 减少数据库重复工作（必做）

先补同结果回归，再优化：

- 将轻量日期目录/每日条数与当前日期范围的详细关联计算拆开；重关联之前尽量限定人员、账号、日期。
- 保持上海发布日期、默认最新有作品日、关键词、评级、指标、入库筛选、排序、回收站、游标与总数语义。不能先截取一页再对整套筛选/排序“补算”。
- 日期目录原有“不含日期过滤”的范围要保持，不因当前日期缩窄而丢掉其他日期；需要关联过滤时保留必要计算。
- 用实际执行计划决定是否补索引，禁止无证据批量加索引；先消除已证实的逐条关联放大。
- 独立成员选项读取可并行；权限上下文只在同请求内复用，不改授权规则、不跨请求缓存权限。
- 先在隔离数据库验证同结果和兼容性。生产只读对照可直接做；本方案不自动授权非止血生产迁移，执行前给出精确 SQL 范围、兼容结果与回滚办法。

阶段通过：同数据结果一致，重关联工作量确有下降，冷查询耗时没有回退。每次有实质改动才跑对应回归，不反复跑全仓门禁。

**分支判定**：A 后运行小样本页面检查；若已经接近/达到全部目标，直接做最终样本验收。最终全部通过则跳过 B/C，记录“无需新增”；若重访问题仍在，做 C；若重复服务端计算仍是主要瓶颈，做 B。首次冷打开不达标时继续修已定位的冷路径，不能只靠预热掩盖。

### B. 同区共享私有结果缓存（确有需要才做）

优先验证现有 Vercel 区域共享缓存是否满足下列契约；以当前官方文档和真实 Preview 能力为准。不能用单进程 Map 或 mock 冒充共享缓存。若能力不满足，才评估同区 Redis；需要新资源、费用、凭据时，把具体缺口交阿禅，不自己开通。

- 首个接入对象仅视频列表结果；鉴权在读缓存之前完成。缓存键包含用户、团队/公司边界、当前可见范围指纹、全部查询条件、数据版本和返回契约版本。
- TTL 上限 60 秒，保存原始生成时间；浏览器和服务端叠加时按剩余有效期使用，不能每一层都重新续 60 秒。保留 `fresh=1` 绕过旧结果的语义。
- 把既有实例缓存纳入同一失效机制或替换掉，避免旧层在上层失效后继续回送旧结果。当前部署实际单区，但应说明部署更新/回退时缓存命名空间如何隔离。
- 覆盖作品新增/编辑、快照更新、话题标签、入库状态、回收/恢复及其他实际依赖。失效以数据成功提交为前提；部分成功已改变依赖数据时也必须失效。
- 按受影响范围失效，不清全站。失效通知失败时，下一次读取须由可核验的数据版本或等价机制避开旧结果，不能只调用删除接口就认为闭环。
- 防止“旧查询在写入之后返回并重新填回旧缓存”；采用代际/版本校验或等价方案，写入前后的并发测试必须覆盖。
- 合并同键在途请求；说明只在进程内还是跨实例合并，不能混称。跨实例防击穿不得引入无限等待锁。
- 缓存读取超时建议上限 150ms，超时/错误回原查询并记录原因；短时故障避免每个请求都额外等待。故障注入验证缓存等待可终止；实际预算如需调整须给实测依据且仍满足页面目标。
- 记录 hit/miss/expired/bypass/error、age、耗时和 release；日志不存 token、业务正文、原始权限名单或完整缓存键。
- 保留单个可回滚开关。禁用后恢复原查询链路，并停止读取新缓存；不得依赖缓存才能正常工作。

阶段通过：两个独立应用进程或可辨识实例真实复用同一结果；在 A 更新后 B 不复用旧版本；缓存故障、到期、并发旧请求、权限变化均通过。无法证明跨实例行为记 BLOCKED，不用热跑一次代替。

### C. 浏览器复用（确有需要才做）

- 在现有数据层复用相同查询的近期结果，先查已有能力，避免再叠一套。范围仅当前登录会话；不落长期 localStorage/IndexedDB，不额外引入数据状态框架。
- 缓存键包含身份/范围和完整查询，遵守源结果生成后 60 秒总上限；限制容量，不能无界存下所有日期/详情。
- 重新进入受保护页面先确认当前身份与范围，再复用数据。换号、退出、范围变化立即清理；旧请求晚到不能覆盖新筛选。
- 写入后清理相关列表/详情，并取最新结果；失败保留已有明确错误提示。保持既有筛选、滚动和详情返回行为，不改视觉布局。
- 相邻日期/详情预取不是必做；仅在实测需要时按需、限量、可取消地预取，不扫整个月，不预加载全部截图。

阶段通过：命中可观察，重访更快；更新与权限测试通过；正常首次打开无重复列表请求；预取没有使首次打开请求量或耗时恶化。

## 4. 验收清单：不能只交测试全绿

| 验收组 | 场景与通过条件 |
|---|---|
| 数据一致 | 在同一隔离数据快照对照旧实现与新实现。覆盖默认最新日、指定单日、跨日/上海午夜、无数据；人员/账号/关键词/评级/指标/入库筛选；各支持排序升降序；50/100/500、跨页及游标失效；回收站。复用已有测试，不做所有条件的笛卡尔积 |
| 权限隔离 | 负责人、组长、普通成员、跨团队/跨Supabase项目、不登录；用户已确认一个Supabase项目就是一家公司，成员在视频复盘只读范围内可读本项目所有团队，不能读另一项目。列表、详情和截图按同一边界；写权限不扩大。相同 URL 不串数据，空范围不回全量 |
| 写后更新 | 依赖清单逐类验证；自己写后首次刷新新结果，他人更新后不超过总新鲜度上限；失效失败、跨实例、旧请求晚到不能复活旧结果。写测试仅隔离库 |
| 故障恢复 | 缓存失效/超时、数据库失败、过期、全新实例、发布切换；正确回源或明确失败，不能将权限错误/业务错误缓存为成功 |
| 真实页面 | 同权限/数据/网络/版本口径的改前改后，首次打开、重开、日期来回、详情返回分别计时；看见真实行且控件可用才停止计时 |

### 性能采样方法

1. 优先复用现有测速脚本；不适用才新增 `scripts/audit/content-open-performance.mjs`，支持目标 URL、用例文件、before/after 标签、次数和结果路径；交付报告记录实际可复制命令。凭据取已授权会话或被忽略测试文件，不写入参数/报告。
2. 先各 5 次定位。最终对默认单日主场景的首次打开、同页重开、日期往返、详情返回，改前/改后各 30 次，至少分两个时段；采集后统一计算，禁止删除慢样本。失败请求单列错误率，不能从性能结果中悄悄消失。
3. 首次打开用清空浏览器资源缓存的新上下文并保留合法登录态；服务端冷结果在隔离/Preview 通过测试命名空间实现。不得清空生产全局缓存、以随机业务条件伪装同条件、以 fresh 接口冒充正常首屏。热场景保留缓存，必须有命中证据。
4. 冷/热、首次新日期/重复日期分组，不混算。每组报告样本数、p50/p95/max、错误数、业务请求数、传输量、最慢请求、身份/数据/缓存耗时。p95 固定用最近秩法：排序后第 ceil(0.95×n) 项。
5. 100/500条、复杂筛选、无数据及不同合法角色用定向功能检查＋少量性能冒烟；不能把50条测速结论推广成500条保证。若用户实际主用100/500条，开工基线就将该档纳入主场景，不能自行降到50条过关。
6. 同期记录浏览器、地点、代理状态、边缘节点、应用区与 release；不同网络不相减当优化收益。采用生产构建；开发模式不作达标证据。
7. 分别记录改前、仅 A、最终方案；中间阶段只做小样本，正式全量验收只在最终候选跑一次。缓存关闭、开启、故障的控制对照必须仍保留。

达到第1节全部目标才称性能通过。若首次打开没达到2秒，即使提升30%也不能标全部达标；报告剩余等待在哪里并按第6节处理。若仅受外部网络阻塞，仍标本项目标的未达，不调低目标凑通过。

## 5. 本地交付与上线交付分开

本地交付：定向修复和验证完成、清理被替代代码、提交精确文件、更新本方案进度与 `日志/YYYY-MM-DD.md`，给出提交号、证据、缺项和回滚步骤。未上线明说“尚未 push；生产性能待验”，不把本地/Preview结果写成生产通过。

上线前一次性准备可审阅发布包：精确提交范围、应用与迁移兼容性、必要环境配置、回滚开关和旧函数恢复步骤。`push main`、非止血生产迁移和新增资源按当前授权处理；需要阿禅授权时把这些具体动作合并成一次明确请求，不按每个小步骤反复问。

授权后核对 `git log --oneline origin/main..HEAD` 和差异文件，不能夹带共享主干其他会话提交。发布后确认正式域名健康、生产实际 release、缓存行为与真实页面，生产正常路径按上述主场景采样；不得为了测冷路径清生产共享缓存。无法取得生产冷路径证据如实标缺项。

完整交付终点：目标全部通过、数据/权限/更新正确、生产版本与真实页面验证完成、报告及日志落盘。无发布授权时交付“已验证待发布候选”，保留上线事项，不声称线上任务完成。

## 6. 只在这些情况升级，不默认叫回高成本模型

- 需要新费用/凭据、产品口径变化、发布/生产迁移授权：给阿禅一个推荐和理由、精确操作及拿到支持后的下一步。
- 同一路径连续两次失败或冻结范围内两轮返工后仍有阻断：停止该路径，保留最小复现、已排除原因、候选方案和影响面；能独立继续的部分继续。禁止靠扩大缓存时长、放松权限或删断言过关。
- 浏览器不可用先换项目允许的可用验收环境；仍不可用，完成独立开发/测试并标真实页面 BLOCKED，写清需要恢复哪项环境。不把历史测速拿来补位。
- 数据库优化、缓存能力选择和常规测试由 Sol 自行解决。只有证据显示需要改产品规则或调整系统边界，才另作决策；不因任务涉及“架构”就自动升级模型。
