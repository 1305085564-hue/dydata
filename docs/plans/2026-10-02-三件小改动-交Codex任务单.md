## 零、开工前必读的四条纪律（违反=返工）

1. **迁移相关命令一律不可用**：`supabase db reset`、`supabase db push`、`supabase migration down` 在本仓库都跑不通或危险（迁移链无法从零重放，`补丁/` 子目录 CLI 不识别；线上另有已应用未登记版本）。本批不写 migration，所以正常用不到；若后续必须加，文件名用 14 位时间戳（对齐现役 `20261001120000_*`），生产上线走单文件手工 apply + 登记 `supabase_migrations.schema_migrations`（`on conflict (version) do nothing`）。
2. **留痕只有一个出口**：业务写操作一律 `writeAuditLog` → `audit_logs`（`src/lib/audit-log.ts:15`）。禁止为任何新功能另建历史/日志表。
3. **门禁在 handler 内部**：权限校验必须在服务端路由/action 里完成，UI 隐藏不算安全；已有的多层校验（角色 + 可见范围）只许加不许减。
4. **提交口径**：每条任务一个本地 commit，**不含 push**。push 需阿禅当前轮明确授权（push `main` 即触发 Vercel 上线）。

## 任务 1 · 导入批次计数失败不再抛 500（P0，最低风险，先做）

### 真实证据（已核）
- `src/lib/topics/import.ts:439-449`：批量/逐行写入完成、`successCount = insertedCount`（:437）**之后**更新 `topic_import_batches` 计数，失败即 `throw new Error("更新导入批次计数失败：...")`（:448）。
- 上层 `src/app/api/admin/topics-library/import/confirm/route.ts:84-93`：catch 后把原始 error.message 以 500 透给前端。
- 后果：选题**已经入库**，用户看到"失败"→ 重复导入。

### 复核后新增的关键事实
`topic_import_batches` 在全项目**只写不读**（仅 `import.ts:377` insert、`:440` update，无任何 select、无展示页）。所以：
- 用户侧看不到计数错，**但接口不该因此报错**；
- **不需要**为它加前端提示、重试按钮或"会话"机制（Kiro 方案 4 的 Phase 1/3/5 全部因此无必要）。

### 改动（就这一处）
1. `import.ts:447-449` 删除 `throw`。计数已在内存中算好，主结果照常返回。
2. 失败时 `console.error("[topics] import batch ledger update failed", { batchId, error })`，并在 `executeTopicImport` 返回体增加可选字段 `ledgerWarning?: string`（值示例：`"批次台账计数未能写入，选题已正常入库"`）。
3. `confirm/route.ts` 把 `ledgerWarning` 原样透出（`{ ok: true, ...result }` 已能带出，确认即可）。

### 前后端对账（项目规则强制）
后端新增字段必须说明前端是否消费。**本任务明确：前端不改**。理由：台账无任何读取方，加 UI 提示属过度设计。`ledgerWarning` 只用于日志/排障与将来接入时的契约预留。若阿禅要求前端显示，则另开小任务，不夹在本批。

### 禁区
- **严禁**删除或绕过 confirm 阶段的重新校验。`import.ts:296-323` 注释明写"绝不信任预览"，`confirm/route.ts:44-63` 只接收白名单字段并在服务端重解析指标——行数据由浏览器回传，可被篡改，这层是安全必需。
- 严禁改"批量插入失败→逐行重试"的降级策略（`import.ts:404-432`），它保证部分成功可解释。
- 严禁新建 `topic_import_sessions` 表或断点续传接口。

### 验收
- 先在 `src/lib/topics/import.test.ts` 补复现用例：mock `topic_import_batches.update` 返回 error → 断言 `executeTopicImport` **不抛**、`successCount` 等于实际写入数、`ledgerWarning` 非空。
- 命令：`npx tsx --test src/lib/topics/import.test.ts` → `npm test` → `npx tsc --noEmit --pretty false` → `npx eslint src/lib/topics/import.ts src/app/api/admin/topics-library/import/confirm/route.ts`。
- 纯后端改动，按分级不做浏览器验收。

## 任务 2 · 补交审批与"我的待办"收成一次服务端写入（P0）

### 先纠正 Kiro/CC 的范围误判（重要）
- **豁免审批不存在双写，本批不动**：它走单个原子 RPC `review_exemption_request_dates_atomically`（`src/lib/exemption-review.ts:118-141`），申请单状态与逐日明细已在同一事务内；其待办列表来自业务表本身（`/api/exemptions/pending`），不依赖通知表。
- **真双写只有一条链**：行动中枢的**补交审批**。`src/components/unified-command-hub.tsx:789-830` 先 POST `todo.action.endpoint`（:795，即 `/api/admin/fulfillment/appeal/handle`），成功后**再**PATCH `/api/notifications/{todo.id}/done`（:810）。中间失败时已有降级提示"申请已处理，但待办状态未同步，请刷新查看"（:816-818）。
- 该 handle 路由**已经**在服务端做了审计与给员工发通知（`src/app/api/admin/fulfillment/appeal/handle/route.ts:107` RPC、`:118+` `writeAuditLog` + `emit`）。缺的只有"审批人自己那条待办通知"。
- `handleToggleTodo`（hub:758-785）是用户主动叉待办，天然独立，**不属于本任务**。

### 改动
1. `handle/route.ts` 的 payload 解析（`parseHandleFulfillmentAppealPayload`）新增可选 `notificationId`，用现成 `UUID_PATTERN` 校验。
2. RPC 成功后服务端调用 `markDone(notificationId, auth.actor.userId)`（`src/lib/notifications/server.ts:78-101`，已按 `user_id` 限定归属 + 用 select 确认实际更新行数），把结果作为 `notificationMarked: boolean` 放进响应。未传 `notificationId` 时字段为 `false` 且不影响审批成功。
3. **幂等**：重复审批（申诉已是终态、RPC 返回已处理/409）时**仍要**允许标记待办成功，避免"已处理但红点永远叉不掉"。
4. 前端 `unified-command-hub.tsx`：删掉第二次 PATCH fetch，改为读 `notificationMarked`；仅当为 `false` 时保留现有那句"待办状态未同步"提示。成功/失败的 toast 文案不变。

### 禁区
- 不写 migration，**不改 `handle_fulfillment_appeal` RPC**（20260930163503 已重写过一次并删过 approve 副作用，再动风险高）。
- 不减权限层：`requireAdminServiceClient` + `requireOwnerOrAdminRole` + `requireActiveVisibleUsers` 三道保持。
- 不改 `markDone` 的归属校验与行数探针（防"叉不掉还假装成功"）。
- 不合并豁免/补交/日报三种审批的权限口径（Kiro 方案 3 的 `approve_requests` 统一权限会直接造成越权面扩大）。
- 不给 `notifications.status` 加新枚举值。

### 验收
- 先扩 `src/app/api/admin/fulfillment/appeal/handle/route.test.ts`：①带 notificationId 审批 → 响应 `notificationMarked=true` 且通知表 status=done；②notificationId 属于他人 → 不越权标记、审批仍成功、`notificationMarked=false`；③重复审批 → 待办能被标记。
- 命令：`npx tsx --test src/app/api/admin/fulfillment/appeal/handle/route.test.ts` → `npm test` → tsc → eslint 两文件。
- 涉及交互：真实浏览器只验"行动中枢补交审批卡"这一个入口（通过/驳回各一次，确认待办消失且刷新不复活）。`npm run gate:roles` 现已自带 harness（2026-10-02 `CX` 收口，不再需要手工预起 `:3100`，连跑两次 23/23），直接跑即可。

## 任务 3 · 选题入库门槛可配（**需阿禅点头后才开工**）

### 决定性事实：项目刚主动下线过同类机制
`src/lib/video-review-thresholds.ts:1-9` 白纸黑字记录：五项阈值**曾**可在管理中心「系统设置」页在线改值（存 `system_settings`），因"管理员改值也改不动顶部异常提醒"（两处口径分叉），**编辑入口已于 2026-09-26 下线**、规则回退成代码常量，并注明"改这里等于改口径，需走代码发布"。
→ 所以"阈值改成可配置"不是技术小改动，而是**重新引入一个被有意砍掉的机制**。是否要做，是产品决策，不是施工细节。

### 若阿禅确认要做，范围必须锁死在"入库门槛"
常量 `TOPIC_LIBRARY_QUALIFY_PLAY_COUNT = 30_000`（`src/lib/topics/metrics.ts:1`）共 10 个生产引用，**分属 4 种不同语义**，绝不能一起变成可配：

| 语义 | 引用点 | 本批是否可配 |
|------|--------|--------------|
| 入库门槛（够不够格进选题库） | `library.ts:71`、`library.ts:95` | ✅ 只做这两处 |
| 达标作品数口径 | `metrics.ts:30`、`service.ts:373`、`service.ts:984` | ❌ 不动 |
| 高性能筛选 | `service.ts:328` | ❌ 不动 |
| 优先分权重 | `service.ts:809` | ❌ 不动 |

好消息（已核）：两个入库门槛调用的宿主函数都是 async 且都在 `library.ts` 内部——`ensureInternalLibraryEntry:117`、`resolveVideoTopicLibraryStatuses:384`（唯一调用方 `src/app/api/admin/content/topic-library-status/route.ts:82`）。所以是"请求入口读一次、当参数传进纯函数"，不是 Kiro 式的全模块异步化重构。

### 改动
1. `library.ts:57` 与 `:81` 两个纯函数各加一个可选入参（如 `qualifyPlayCount?: number`），缺省回落常量 30000。对外契约不破。
2. `library.ts:117` 与 `:384` 在入口读一次配置值并向上传递（同请求内只读一次，不要每行查库）。
3. 配置读取/写入复用现役 `src/app/api/admin/system/settings/route.ts:53-100`（GET/POST + `requireSystemPermission`），**零 migration**（key-value upsert）。新增 key 语义单一，服务端必须做整数 + 范围校验（建议 1000–1000000），非法值 400，读不到时回落常量。
4. 后台 UI：在现有系统设置页加一个数字输入 + 当前生效值显示 + "仅影响之后新触发的入库判断"这行说明文案。

### 硬性安全前提
`system_settings` 是上一轮治理审计中**唯一实测成立的越权真洞**所在表，且刚由 `20261001040618_system_settings_service_role_only.sql` 收窄为 service_role 专用。**严禁**新增任何浏览器/anon 直读该表的路径，读写只能过上面那个 route 及其权限门禁。

### 必须防的新 bug（口径分叉）
阈值改动**不重算历史**：已入库的选题不会因为门槛调高而移出，但列表标记会显示它"不达标"。这是预期行为，必须在 UI 说明文案里写死。**禁止**顺手加"一键重算历史入库"——那会改历史台账，属新机制且不可回滚。

### 验收
- `src/lib/topics/library.test.ts` 补：自定义门槛低于/等于/高于播放量时的三种判定结果；`resolveVideoTopicLibraryStatuses` 与 `ensureInternalLibraryEntry` 使用同一个传入值（防两本账）。
- `src/app/api/admin/system/settings/route.test.ts` 补：非法数字/越界/非整数被拒。
- 注意 `src/lib/topics/service.test.ts:186` 断言常量 ===30000、`:189` 断言源码含该标识——保留常量作默认值即不会红，**不要**为了让测试过而删常量。
- 命令：`npx tsx --test src/lib/topics/library.test.ts` → `npm test` → tsc → eslint。
- 涉及管理页交互：真实浏览器验系统设置页改值 → 视频复盘选题库标记随之变化这一步。
