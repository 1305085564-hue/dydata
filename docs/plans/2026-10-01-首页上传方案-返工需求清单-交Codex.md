## R1（P0）修复 `gate:browser` 的环境不一致 —— 否则门禁永远"假红"
**问题**：`package.json` 的 `gate:browser = npm run build && node --env-file-if-exists=.env.ai-test.local … playwright`。`next build` 读 `.env.local`，会把**生产** `NEXT_PUBLIC_SUPABASE_URL`（gcrhh）**编译进客户端**；运行时 `next start` 却注入**本地测试库的 anon key** → 页面拿本地 key 打生产 → `/topics` 500、报 `Invalid API key`。这是 harness 接线 bug，不是被测代码坏。
**要做**：让 build 与 run 使用**同一套测试环境变量**（例如 gate 脚本在 build 阶段也带上 `.env.ai-test.local` 的 `NEXT_PUBLIC_*`，或统一走一个 CI env 文件）。
**验收**：本地起好 supabase 后 `npm run gate:browser` 能真正跑到用例、`/dashboard`、`/topics` 不再 500。（注：需先用隔离 worktree 或让阿禅授权清理占用 :3000 的旧 dev，避免 Turbopack 单实例冲突。）

## R2（P0）补 Phase 3 的"不留半成品"回滚行为测试
**现状**：`persist.test.ts` 只有 4 条单元断言（payload/错误码），补偿回滚代码仍在 `route.ts` 里，但**没有任何测试证明"某一步写库失败 → 已写的视频/快照/日报被回滚、库里不留半条"**。这是方案点名要求的核心正确性保证。
**要做**：为写入链每一步（视频→24h 快照→日报→标签/话术）构造"该步抛错"的用例，断言：(a) 触发回滚；(b) 失败响应能区分"核心保存失败"vs"标签补充失败"；(c) 三张核心表无残留。
**验收**：上述失败点均有测试且通过。

## R3（P1）Phase 1 做透：真正收敛巨型表单

**验收**：定向表单/门禁测试全绿；`useState` 数量与文件行数较改造前明显下降（给出前后数字）。

## R6（P1，来自真实浏览器验收）验收脚本对齐 + 门禁跑在 build 版
**发现**：`tests/roles/发布时间与补交门禁端到端.spec.ts`（未入库脚本）在本地真浏览器跑，7 条里 2 条红是脚本自身问题、非产品缺陷：
- 场景 1 断言"跨月→409 补交"，但现行规则（也是方案本意）是"跨月不单独触发、仅超 72h 才拦"，应用正确返回 200 → **脚本预期过时，需按新口径改**（阿禅已确认"跨月不拦"为有意口径，**改脚本、勿回退业务规则**）。
- 场景 2/7 在 `loginAs*` 的 `waitForURL("**/dashboard")` 上偶发 30s 超时——`next dev` 按需重编译导致；单跑即过。
- 场景 6 的 API 断言（PUBLISH_TIME_CONFIRM_REQUIRED 409）通过，但点"更多设置"后找 `发布时间` 文案的 UI 断言失败——需核对近期 publishedAt 控件改动后对齐选择器。
**要做**：① 把场景 1 的跨月预期改成与"72h 口径"一致；② 登录等待改为轮询 cookie/`main` 可见而非死等 URL；③ 对齐 publishedAt 的 UI 选择器；④ 该脚本纳入版本管理（当前是游离的未跟踪文件）。
**验收**：`DYDATA_E2E_BASE_URL=http://localhost:3100 npx playwright test --config playwright.role.config.ts 发布时间与补交门禁端到端` 在 **build 版（`next start`）** 上 7/7 稳定绿。
**注意**：验收须在浏览器 origin 用 `localhost`（非 `127.0.0.1`），否则被 `middleware.ts` 的 CSRF 同源校验挡成 403"请求来源不可信"。
