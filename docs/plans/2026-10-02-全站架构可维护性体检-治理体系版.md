# 全站架构可维护性体检与根治升级方案

**方案日期**：2026-10-02  
**方案性质**：一次性根治性升级，不是止血清单  
**施工目标**：在一次受控施工周期内，完成全站性能、稳定性、可测试性和可维护性的结构性收口，并让后续新增代码自动遵守同一套边界。  
**施工状态**：待施工方案，不能把本文件中的目标、计划或待核验数字当成已完成事实。

## 一、最终结论

本次不采用“先修几个问题、剩下以后再说”的方式。全站治理必须一次性完成以下四件事：

1. **建立可信基线**：所有规模、性能、错误、缓存、耦合和测试数字都能用固定脚本复现。
2. **完成根因改造**：不只给大文件加注释、不只给异常加日志，而是收口模块边界、数据访问、错误处理、缓存、外部副作用和测试接缝。
3. **完成全量迁移**：旧入口、旧调用方式、旧门禁和重复实现必须清除或明确隔离，不能长期保留两套规则。
4. **完成强制治理**：门禁、技术债台账、架构决策和季度体检进入 CI 和发布流程，后续新增债务不能绕过治理。

本方案与《统一行动中枢审批-架构重构方案》关系如下：

- A 是全站治理和根治工程的总方案。
- B 是审批域的专项施工方案，必须遵守 A 的统一错误、可观测性、依赖注入、性能和回滚标准。
- B 的审批链改造是 A 的第一个完整领域迁移样板，但不能以单点成功代替全站完成。

## 三、根治目标架构

### 3.1 目标分层

全站业务代码统一按以下边界组织：

```text
页面 / API / Server Action
        ↓
用例编排层（输入、权限、状态、事务边界）
        ↓
领域服务层（业务规则，不直接依赖页面）
        ↓
数据访问层（查询、RPC、写入、缓存）
        ↓
Supabase / 外部服务
```

硬约束：

- 页面组件不得新增直接数据库访问；现有例外必须迁移到 loader 或领域数据入口。
- API 路由只负责解析输入、身份权限、调用用例、映射响应，不承载大段业务分支。
- 领域服务不返回 `NextResponse`，只返回稳定业务结果或结构化错误。
- 外部副作用必须通过可注入依赖访问：通知、审计、邮件、文件和第三方调用均适用。
- 数据权限范围只能由统一权限上下文产生，业务模块不能自行拼接 `role + team_id + permissions`。
- 缓存必须声明作用域、TTL、容量、失效策略和失败降级行为。

### 3.2 目标状态机与副作用规则

涉及审批、提交、导入、分配等操作的用例必须显式定义：

```text
输入校验
 → 身份与权限
 → 目标存在与范围
 → 核心业务写入
 → 审计
 → 通知/待办
 → 返回业务结果和后置结果
```

核心业务写入与后置副作用不能被错误文案混为一个状态：

- `businessSucceeded`：核心业务是否已成功；
- `auditSucceeded`：审计是否成功；
- `notificationSucceeded`：通知是否成功；
- `todoMarked`：待办是否成功完成。

对于无法跨表原子化的链路，必须提供：

- 明确的失败字段；
- 结构化日志；
- 可重试或人工补偿入口；
- 幂等键或重复执行保护；
- 失败率和延迟指标。

### 3.3 目标文件边界

一次性治理不是按“每个文件必须 500 行”机械切割，而是同时满足职责和规模：

| 层级 | 新文件目标 | 既有文件处理 |
|---|---:|---|
| 推荐 | ≤500 行、≤15 个导出 | 无需强行拆分 |
| 预警 | >800 行或 >20 个导出 | 必须写入台账并在本次工程中安排迁移 |
| 阻断 | >1000 行或 >30 个导出 | 禁止继续新增业务逻辑，必须完成拆分或批准例外 |
| 聚合层 | ≤200 行 | 只做编排，不保留业务实现 |

测试文件、类型文件和生成文件必须在脚本中单独分类，不得偷偷混入或排除。

## 八、回滚和失败处理

### 8.1 回滚原则

- 应用代码、测试和门禁按阶段提交，禁止把全站根治压成一个不可定位的大提交。
- 数据库若不新增 migration，则应用按 commit 回滚；若确需 migration，必须先有正向兼容、回滚或前向修复方案。
- 旧入口只在迁移期间保留，切换完成后删除；不得永久双写。
- 任何性能、权限、数据一致性或关键回归失败均可阻断发布。

### 8.2 回滚触发条件

满足任一条件立即停止当前阶段并回滚：

- 真实角色出现越权或数据泄漏；
- 核心业务成功率下降；
- 页面或 API 超过正式性能预算；
- 审计、通知、待办出现不可追踪的丢失；
- 新旧实现结果对账不一致且无法定位；
- 门禁无法区分既有债务与新增违规，导致发布判定失真。

### 8.3 不能回滚时

如果核心业务已经成功而后置副作用失败，不能简单回滚核心业务。必须：

- 保留业务成功状态；
- 记录 requestId、actor、target、失败副作用；
- 通过幂等补偿或人工处理恢复副作用；
- 将该情况计入稳定性指标和台账。
