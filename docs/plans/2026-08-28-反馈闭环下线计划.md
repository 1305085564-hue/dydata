# 视频复盘反馈闭环下线计划（F3R3）

> 日期：2026-08-28
> 状态：应用层与数据库 migration 已完成；数据库已在线执行，应用代码已获授权随本次 `main` 推送发布
> 目标：保留选题、上传、管理端分析三项核心价值；删除无法持续维护的视频复盘反馈闭环。
> 说明：协作管理、文案改写与成长分析均不在本次改动范围；协作管理只记录未来可能与发布管理合并，目前保持现状。

## 一、最终产品边界

| 模块 | 决定 | 唯一保留价值 |
| --- | --- | --- |
| 选题库 `/topics` | 保留 | 帮员工决定做什么 |
| 今日工作台 `/dashboard` | 保留 | 上传作品和数据，支撑公司考勤与统计 |
| 视频复盘 `/admin/content` | 保留并收窄 | 帮管理者定位作品问题；只做内部分析，不再承担反馈投递 |
| 文案改写 `/content-tools/rewrite` | 保留、待重做 | 本次不动任何前后端链路 |
| 成长分析 `/growth` | 保留、待重做 | 本次不动任何前后端链路 |
| 反馈闭环 | 删除 | 不再做投递、员工已读/回复、管理者验证和反馈资产沉淀 |
| 协作管理 `/admin/collaboration` | 保留、不动 | 未来可能与发布管理合并，但合并方案尚未形成 |

## 二、方案比较

### 方案 A：直接整块硬删

一次删除页面、接口、数据库表和函数。速度最快，但会连带破坏 `/admin/content` 首屏队列、视频回收站和历史分析数据，不采用。

### 方案 B：分层下线（推荐）

先解除视频复盘对反馈状态的依赖，再删除反馈入口和业务代码，最后单独清数据库。每批都可独立验收和回退，能做到真正清干净而不伤分析主流程。

### 方案 C：只隐藏入口

页面看不见，但接口、查询、类型、通知和数据库触发器仍运行，维护成本没有消失，不采用。

## 三、必须保留的边界

### 视频复盘保留

- 异常视频队列、视频指标、截图/OCR 数据、内容拆段、账号基线和前后作品对比。
- AI 或规则生成的内部诊断：问题位置、指标证据和原因判断。
- `ai_insight_result`、`video_metrics_snapshots`、`video_content_segments` 等分析资产。
- 视频资产生命周期：回收、恢复、永久删除及其审计记录。

### 明确不动

- `/content-tools/rewrite`、`src/lib/rewrite/` 及其接口、配置、表和测试。
- `/growth` 及其加载器、接口、图表、数据契约和测试。
- `/admin/collaboration` 及其页面、组件、接口、统计、权限、导航、责任归属补录 RPC 和测试。
- `/admin/fulfillment`、`/admin/videos` 和 `/admin/modules`；本次不做协作能力迁移或页面合并。
- `daily_reports`、`videos` 表结构与现有统计口径。
- 通用通知系统；只删除“内容反馈卡”这一种通知消费链路。

## 四、分批施工

### 第 0 批：锁定契约与删除清单（已完成）

1. 为视频复盘内部分析主链写回归测试，确保删除反馈后仍能查看异常、证据和分析结果。
2. 用静态扫描列出反馈卡的页面、接口、类型、测试、通知挂载、RPC 和数据库引用。
3. 核对线上真实反馈表、函数和 RPC 是否存在及是否仍有调用；同时查 Vercel 请求日志，确认反馈专属 API 没有仓外或人工调用方。只读确认，不写生产数据。

验收：删除前的保留能力都有测试保护；没有把“文件名像旧代码”当作可删证据。

### 第 1 批：把视频复盘改成纯内部分析（已完成，待最终验收）

前端清理：

- 删除反馈编辑框、保存草稿、确认、投递、复制员工反馈、上次反馈对比及反馈状态展示。
- 删除员工端反馈弹窗和全局反馈通知桥接；保留普通站内通知。
- 视频列表和诊断舱不再按反馈卡状态排序或判断“已完成”，改为按异常程度、数据完整度和分析状态组织；不再制造新的流程完成状态，仅区分“尚无分析/已有分析”。
- 页面文案从“复盘反馈与沉淀”收窄为“定位作品问题与内部分析”。

后端清理：

- 删除管理端反馈卡接口和员工端反馈卡读取/已读/回复接口。
- 删除反馈卡状态机、拼接外发文案、员工回复类型和只服务于反馈闭环的测试。
- 删除“经验标记/资产沉淀”的前端动作、`content-experience-marks` 接口、领域逻辑和测试；它没有其他页面调用，不为保留分析而继续维护。
- `admin-content` 加载器停止读取 `content_feedback_cards`，页面契约移除 `feedbackCards`。
- 内容分析输出去掉 `feedback_draft`、`message_for_member`、`reusable_experience` 等面向投递或沉淀的字段；保留诊断、证据和原因。读取历史 AI JSON 时兼容旧字段，不能让旧分析记录打不开。
- 重写复盘队列规则，使其完全不依赖反馈卡状态。

关键风险：`content_feedback_cards` 当前参与复盘首屏 RPC 和队列状态，不能先删表或接口再改加载器。

### 第 2 批：数据库与历史资产清理（已在线执行）

先确认应用层已连续稳定运行且全仓无调用，再新增 migration：

1. 从 `admin_content_first_screen` 返回值和查询中移除 `feedbackCards`。
2. 从视频永久删除/回收相关函数中移除对反馈卡表的依赖。
3. 历史经验标记先随反馈历史一并导出；确认无需追溯后删除 `content_experience_marks` 及其策略、索引和触发器。
4. 删除反馈任务触发器和函数、`feedback_action_tasks`、`feedback_card_replies`、反馈回复 RPC。
5. migration 已包含删除 `content_feedback_cards`；必须先只读导出并由阿禅确认无需在线追溯，之后才能执行。

协作管理相关的 `update_collaboration_attribution`、表字段和统计函数不在本批清理范围。

这批禁止修改旧 migration，只能新增 migration；执行后要刷新 PostgREST schema cache，并用真实管理角色做只读/可撤销验收。

## 五、验收清单

### 产品验收

- 员工只看到选题、上传等仍能完成的动作，不再看到无法闭环的反馈承诺。
- 管理者能找到异常作品、查看证据并完成内部诊断。
- 协作管理、发布管理和视频管理的页面与能力与施工前一致。
- 文案改写和成长分析页面、入口与数据完全不受影响。

### 技术验收

- 定向测试：反馈链删除边界、视频复盘队列、内容分析契约、通用通知不受影响。
- 全量：`npm test`、`npx tsc --noEmit`、改动文件 ESLint、`npm run build`、`git diff --check`。
- 静态反查：应用代码不再引用反馈接口和反馈类型；协作管理代码仍完整存在。
- 浏览器：管理角色只读检查视频复盘，并确认协作管理、视频管理和发布管理仍可正常进入；不新增账号、不写无关业务数据。
- 数据库：migration、schema cache、真实角色接口三项分别留证，不能只凭本地构建判完成。

## 六、发布与止损

- 两个实施批分别提交和验收：应用层反馈下线与数据库反馈清理不得混成一次上线。
- 任一批若导致上传、发布统计或视频资产修改失真，立即停止下一批；不靠前端隐藏掩盖数据问题。
- 默认不 push；每次准备推送 `main` 前由阿禅当次明确确认，并只提交本计划涉及的白名单文件。

## 七、完成定义

不是“导航里看不见”就算完成。只有以下同时成立才算真正下线：

1. 用户入口消失；
2. 前端组件和状态消失；
3. 专属接口和业务逻辑消失；
4. 视频复盘分析及所有明确不动模块均通过回归验收；
5. 数据库残留已明确标成历史保留或完成独立清理；
6. 全站文档不再把反馈闭环描述为在用能力；协作管理仍明确标为保留在用。
