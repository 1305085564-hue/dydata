# 阶段 7 三波派令（5 份施工提示词）

**建立**：2026-10-04 [QW]　**结构依据**：`2026-10-04-阶段7全站运行能力根治-任务规划.md` §四
**用法**：每波开工前两个窗口先 `git pull` 对齐同一 commit，再各自粘贴对应派令开工。全程**只 commit 不 push**，[QW] 逐笔复验攒批推送。

## 全局执行纪律（五份派令共用，粘贴时随派令一起给）

1. **不理解需求不自行发挥**：目标、验收命令、禁区照抄执行；拿不准就停下在交付报告里标注疑点，禁止猜。
2. **行为红线**：契约接入只允许"补分层结果记录＋统一错误出口"，**禁止改业务判断、权限范围、数据口径**；改行为＝判不通过。
3. **禁止伪接**：不许用假数据、空 catch、`console.log` 冒充接入；接不动就明确失败或在报告登记"未接入＋原因"。
4. **每批收尾自查**：`git diff --cached --stat` 全量核对暂存区，发现非本任务文件先 `git restore --staged`；只 commit 本任务点名文件。
5. **验收命令组**（交付报告必须带真实退出码）：`npx tsc --noEmit --pretty false`；`npm test`；`npm run gate:static`；`git diff --check`。
6. 交付报告格式：改了什么（文件清单＋每文件一句话）／验收命令退出码／未接入项与原因／疑点。**读数不实＝该批直接打回。**

## 派令 3｜窗口 A · P2 性能治理（复杂度 **F4 · 8/10**）⚠️ 第 2 波才开工：P1a＋P1b 全部合入并经 [QW] 复验后

2. 按对账后的清单逐域改，一笔一域；每处 N+1 改造必须带**前后对比数据**（查询次数：改前 N＋1 → 改后常数，写进测试或报告，项目硬约束）。

**验收标准**：

## 派令 4｜窗口 B · P3 权限与数据核验（复杂度 **F4 · 8/10**）｜第 2 波与 P2 并行

**目标**：四件事——①真实角色允许/拒绝矩阵补齐（四类角色 × 关键接口，含直接 API 调用测试）；②service role 使用点收口盘点；③RLS／函数线上**只读**核验（`pg_policy`/`pg_proc` 实测，按 `docs/权限与安全说明.md` A.9）；④`daily_reports` 读取按领域 loader 收口。判据读 B 方案 P0-3 与 A 方案 §十 Phase 3。

**开工前必读**：`docs/权限与安全说明.md`、`src/lib/data-access-scope.ts`（`inferDataScope` 是唯一真值来源）、现有 `gate:roles` 测试形态。**写任何查询前先核对线上真实字段**（项目规矩）。

**施工顺序**：
1. 第一笔只做**盘点**：grep 全部 service role 使用点＋`daily_reports` 直读点，列清单（文件×行号×一句话用途×判定），停下等 [QW] 对账。
2. 角色矩阵：按对账后的接口清单补测试，一笔一个角色域；测试必须打真实函数行为，**禁止源代码字符串匹配式断言**（项目硬约束）。
3. RLS 线上核验：只读 SQL（`pg_policy`/`pg_proc`），输出贴进报告；生产库有凭据就直连核，不得推脱。
4. `daily_reports` 收口：把散读点归到领域 loader，逐点行为等价测试。

**禁区**：

- 生产库**只读**：任何写/清理动作一律先停在报告申请
- 不改历史 migration；不新增表/字段

**验收标准**：
1. 每笔：全命令组 0；`gate:roles` 亲跑退出码 0 且新增用例数写进报告
2. 矩阵覆盖表：角色 × 接口 × 允许/拒绝 × 测试文件名，[QW] 逐格对账
