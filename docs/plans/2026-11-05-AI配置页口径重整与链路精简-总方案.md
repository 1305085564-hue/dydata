## 一、为什么要改

### 起因
阿禅在渠道「api1 claude」里打开了 Haiku 5.5，模型视角却显示这张卡下面「暂未接入可用渠道」。

### 根因（实测：生产库只读 + 本地重放 `computeAvailability`）
新同步进来的模型，「全局状态」默认是「没表态」（`global_is_enabled = null`）。系统里有两条规则对它下了相反的结论：
- 上架判断（`src/lib/ai-config/availability.ts` 的 `resolveModelGlobalEnabled`，10-10 写入）：没表态时，只要有渠道开着，就算上架。所以卡片出现了。
- 调度判断（`src/lib/ai/channel-governance.ts:42`，11-04 `fee65fa3` 写入）：没表态就等于停用。所以渠道被判成停用，收进了折叠区，运行时也不会调用它。

受影响的模型：claude-haiku-5-5、claude-opus-5-5、claude-sonnet-5-5（卡片显示在册，可用渠道都是 0）。

### 整页审计发现：6 簇问题
| 簇 | 问题 | 证据 |
|---|---|---|
| ① 模型能不能用有 5 套标准 | 上架、调度、同步弹窗的「现役」、渠道视角的提示、前端重算各自判断，结论互相矛盾。接入渠道、同步模型、渠道开关这三条路径产生的都是「没表态」记录 | 实测 |
| ② 业务实际用哪个模型说不清 | 「钉渠道」字段页面上已经没有入口，但保存时会原样带回；运行时有模型时忽略它，依赖检查却还算它。默认绑定的记录自相矛盾（模型写 Gemini 2.5 Flash，钉住的却是 GPT-6.1 Sol）。绑定的模型全挂时，系统会静默改用任意模型的渠道 | 实测 |
| ③ 三个优先级只有一个生效 | 模型内的渠道顺序只看 `sort_order`；渠道和接入点的优先级只影响跨模型兜底；渠道视角的「改顺位」是死代码（没有按钮触发，后台也拒绝） | 实测 |
| ④ 健康状态会连坐 | 一个模型超时或返回 5xx，会记在整条渠道上，兄弟模型一起休眠。失效后运行时永远不再尝试。两种测试按钮清理状态的口径不一样 | 实测 |
| ⑤ 同一个模型有多个身份 | `5-5` 和 `5.5` 被当成两个模型；显示名靠子串匹配，「4.5 thinking」与基础款同名；上游下线的旧记录有 22 条没清；后台还允许改 `model_id` | 实测 |
| ⑥ 写入与保护不一致 | 停用前的校验：接入点会拦，渠道只预览，模型不查。多步写入没有事务 | 实测 |

### 另外两处会误伤的陷阱（实测）
- 陷阱 A：模型卡渠道行上的开关，实际控制的是整条渠道（`model-family-card.tsx:487` → `onToggleKeyEnable`），而且没有确认。
- 陷阱 B：关闭渠道时，会把这条渠道下所有模型的勾选清零（`route.ts:452-458`）；再打开渠道，勾选也不会恢复。

### 生产快照（2026-11-05 只读）
- 模型记录共 136 条，其中「没表态」115 条（4 条渠道开关是开着的）。
- 全局默认 Gemini 2.5 Flash 的 3 条渠道全部失效，其中一条连续失败 301 次。8 个业务功能正在靠静默兜底运行。
- 6 个模型在不同渠道上的显示名不一致；22 条模型记录在上游清单里已经不存在。

## 二、核心心智与 8 条口径（阿禅已拍板）

**一句话心智**：业务功能选一个模型，模型由几条渠道排队供货，渠道就是买来的 API。页面上只有这三样东西，所有状态都从它们推出来，不再出现第四个概念。

| # | 口径 | 用户感受 |
|---|---|---|
| 1 | **一个开关说了算**。取消独立的「上架」概念，「渠道 × 模型」开关打开即可用。模型卡上的「停用 / 恢复」是批量动作，会记住原来开着哪几条 | 在渠道里打开模型，它立刻出现在模型视角和业务下拉里。两个视角看到的是同一个开关 |
| 2 | **兜底只有一层，而且看得见**。顺序是：业务选的模型 → 全局默认 → 停摆标红并提醒。去掉「随便抓一个模型顶上」那一层 | 每行写明「实际在用：X」，顶班时写清「X 挂了，由默认 Y 顶班」 |
| 3 | **业务只选模型，不选渠道**。删除「钉渠道」字段 | 少一个看不见的设置 |
| 4 | **只剩一种顺序**，就是模型卡里渠道的排队顺序。删除渠道优先级数字和 #N 序号 | 想调顺序只有一个地方 |
| 5 | **渠道状态只说三句人话**：「能用」「暂时歇着（系统会自己再试）」「需要你处理（附原因）」。你自己关掉的显示灰色。系统自动重试，单个模型故障不再连坐同渠道 | 不用一个个点测试，坏了自己会回来 |
| 6 | **测试按钮只有一种效果**：通过就恢复正常（包括解除休眠），不通过就显示原因 | 测一下就知道，测通就好了 |
| 7 | **同步时把模型理清楚**：同一模型的不同写法合并成一行，变体收进「更多版本」，名字规整不撞名，上游已下线的可一键清理 | 不再分不清哪个是哪个 |
| 8 | **关任何东西都用同一条规则**：如果关掉后会有业务没模型可用，先列出受影响的业务，确认后才执行；不影响的直接关 | 接入点、渠道、模型三层行为一致 |

## 四、分批施工

> 一次性交付的规则（阿禅 11-05 定，Codex 必须遵守）：
> 1. **施工顺序不变**：按第零批到第四批的顺序做，后一批依赖前一批的口径。每批做完自测通过再往下，不等外部验收。
> 2. **按批分组提交**：每批至少一组独立提交，提交说明标明批次。验收出问题时可以只回退某一批。
> 3. **第零批照常先做**：一开工就实测 Haiku 5.5，结果报给阿禅；阿禅同意后上架并切默认。这一步是线上运营动作，和写代码并行，不阻塞后面的施工。
> 4. **数据迁移只写不跑生产**：迁移文件随代码交付，本地和测试库上跑通。生产库等验收通过、阿禅授权上线时，按「先上应用，后跑迁移」执行。
> 5. **删列单独放**：第四批的删列迁移单独一个文件，不随这次上线执行。上线后观察 3 天无相关报错，CC 复核没有读取点，阿禅确认后再执行。
> 6. **交付前自证**：把第五节每一条验收逐条写成「问题 → 证据（测试名、截图或回放结果）」，和代码一起交给 CC。缺证据的条目要写明原因。
> 7. **只上线一次**：CC 验收通过后，阿禅授权，一次 push 上线。
> 8. **界面不归 Codex**：Codex 只做逻辑、数据、接口、迁移，以及前端的数据层（取数、类型、去掉前端重算、删掉纯逻辑的死代码）。页面组件的样子和交互不改。为了编译通过或自测必须动界面时，只做最小接线，并在代码里标注「一次性、待删、勿参考」。
> 9. **Codex 交付数据契约**：逻辑做完后，交一份数据契约，写清楚界面每个位置该读哪个字段、有哪几种状态、每种状态对应的文案键（统一在 `presentation.ts` 里）、每个操作调哪个接口、确认弹窗要传什么。Antigravity 只依据这份契约和本方案第三节的取舍清单做界面，不参考 Codex 动过的界面代码。

### 第零批：线上止血（运营动作，不改代码，先于第一批）
- 全局默认改为 **Claude Haiku 5.5**（阿禅 11-05 已定，模型 ID 用 `claude-haiku-5-5`，这是已打开并测通过的写法），替换当前 3 条渠道全部失效的 Gemini 2.5 Flash。
- 原因：第一批会去掉「静默跨模型兜底」，默认模型不健康的话，跟随默认的 7 个业务会立刻停摆。
- 步骤：① Codex 在「api1 claude」上实测 `claude-haiku-5-5` 的普通文本生成和带图识别（截图识别的模型挂掉时由默认顶班，所以默认模型必须能看图）；② 把结果报给阿禅，阿禅回复同意后，在「模型管理」里把它上架，再把全局默认切过去（现有代码下，没上架的模型不会被调度）；③ 切完后在业务视角确认 7 个跟随默认的功能能正常调用。
- 风险（11-05 只读实测）：全系统只有「api1 claude」这一条渠道提供 Haiku 5.5。第一批上线后，这条渠道一挂，跟随默认的 7 个功能就会停摆标红。阿禅 11-05 已接受这个单点，见第六节第 1 条。

### 第一批：口径统一（口径 1、2、3、4、8，陷阱 A/B，D1/D3/D4/D6/D8/D9/D10，S3/S4/S5，N1/N4）
**目标**：「能不能用」「实际用谁」「按什么顺序」三件事，各自只有一个计算来源。运行时和三个视角都只读这个来源。

施工要点：
1. **唯一判定**：渠道 × 模型能否调度，由 `channel-governance.ts` 统一判定，判定中不再读取 `global_is_enabled`。模型是否可用，由 availability 汇总得出：至少有一条可调度渠道即为可用。前端不再自行重算，具体去掉以下几处：`compute-pool-panel.tsx:144-173` 的分组、业务面板与 `model-family-select` 里各自调用的 `useAvailabilityReport`、`business-functions-panel.tsx:124-130` 自带的五态字典。
2. **模型停用 / 恢复**（N4）：停用 = 把该模型所有渠道开关关掉，并给这些记录打上「由模型停用关闭」标记；恢复 = 只打开带标记的记录。标记放在哪个字段由实现方决定，但必须能区分「用户逐条关的」和「模型停用连带关的」。
3. **陷阱 A**：模型卡渠道行上的开关，改为「渠道 × 模型」开关（写 `ai_provider_key_models.is_enabled`），不再控制整条渠道。
4. **陷阱 B**：去掉 `route.ts:452-458` 里「关渠道时清零模型勾选」的级联。渠道关闭后，调度判定本来就会把它判为不可用，不需要靠清零。
5. **口径 2：解析唯一化**。把「功能 → 实际服务模型」写成一个共用函数：显式模型 → 全局默认 → 无。运行时（`client.ts` 的 `resolveFeatureChannelChain`）和 availability 的 `businessAssurances` 必须调用同一个函数。去掉「全量任意模型」那一层兜底：无可用模型时，直接返回明确的错误「无可用模型」。业务视角改为读 `businessAssurances`，输出三种状态（正常 / 顶班 / 停摆）以及实际服务的模型。
6. **口径 3**：前端不再提交 `provider_key_model_id`；运行时和依赖检查（`route.ts:247`、`:472`）不再读取它。数据迁移时，`model_id` 为空、但钉了渠道的绑定（content_analysis、sample_quality_check），**直接清空钉渠道字段，`model_id` 保持为空（跟随全局默认）**。不再把钉住的模型写进 `model_id`：页面上这两个功能现在显示的就是「跟随默认」，阿禅从没主动选过钉住的 Gemini 2.5 Flash，而且这个模型的渠道已经全部失效，写进去只会让它们永远处于顶班状态。字段本身在第四批删除。
7. **口径 4**：页面不再展示和填写 `key.priority`；跨模型兜底去掉之后，运行时也不再读取 `key.priority` 和 `provider.priority`。这两列在第四批删除。
8. **口径 8**：停用接入点、停用渠道、关闭渠道 × 模型、停用模型，这四类动作统一走同一个依赖检查。凡是会让业务（已考虑全局默认之后）没有可用模型的，前端弹窗列出受影响的业务，后端要求请求带确认标记才执行。这一条把现有接入点层的 409 硬拦截放宽为「确认后执行」，属于有意的口径变化。
9. **数据迁移**（先上应用，后跑迁移，保证向后兼容）：
   - `global_is_enabled = null`：没有语义了，忽略。
   - `global_is_enabled = false` 且渠道开着：改为关闭，并打上模型停用标记。
   - `global_is_enabled = true`：不变。
   - 上述三种迁完后，列本身在第四批删除。

### 第二批：健康与测试（口径 5、6，D2，S1/S2，N3）
1. **故障归属**：401/402/403 记在渠道上；超时、5xx、模型类报错，只记在对应的「渠道 × 模型」上。同一渠道在一个时间窗内有多个不同模型都失败时，再升级为渠道级故障。窗口长度和阈值由实现方提出，阿禅确认。
2. **自动重试**：采用「半开」方式，不另起定时任务。冷却期到了以后，下一次真实调用**先试一次**这条故障供应（不是排在最后，排在最后的话，前面一直成功它就永远轮不到）；成功就恢复，失败就继续走正常渠道，并延长冷却。细则见第八节第 6 条。不做定时探测，因为近期刚处理过 Vercel CPU 超额，定时探测会增加 CPU 消耗。
3. **去掉「无新证据也判死」**：现在只要首次失败满 24 小时、期间没有成功，就会被判失效。改为必须有持续失败的证据才判失效。
4. **测试统一**：渠道级测试和模型级测试，通过后都清除对应的失败记录与休眠，包括手动休眠的遗留；测试失败不写入健康状态。
5. **D2 去掉手动休眠**：截至 11-05 快照，没有处于手动休眠的渠道，迁移时直接清空即可。
6. **状态展示**：「待复测」并入「能用」；「失效」显示为「需要你处理 · 原因」；「停用」显示为灰色。统一从 `src/lib/ai-config/presentation.ts` 取文案。

### 第三批：接入与同步（口径 7，D5/D7，S6/S7/S8/S9，N2）
1. **同模型多写法**：同步弹窗内，把写法相近的模型 ID（例如 `5-5` 与 `5.5`、带或不带日期后缀）合并成一行展示，默认勾选推荐写法。库里存的仍是上游接受的真实 ID，不自动合并已有记录。
2. **显示名**：改为按规则生成，不再依赖手写名单；变体带后缀（Thinking / Agentic）；禁止用子串规则把变体折叠成基础款。回填存量时，只回填显示名等于模型 ID、或等于旧规则自动生成名的记录，人工改过的不动。
3. **上游下线判定收紧**：只认 404，或明确的「模型不存在」类文本。不再只要报错里出现 model 字样就判定下线（`sync-models/route.ts:117`）。
4. **禁止改 `model_id`**：`modelPatch` 只在 update 时禁止修改 `model_id`。
5. **接入流程**：按 S6、S7、D5 执行。N2 读取各渠道的 `available_models`，与该模型已打开的渠道做差集。

### 第四批：结构清理（D11/D12，写入可靠性，删列，拆文件）
- 删除不再使用的列：`global_is_enabled`、`ai_feature_bindings.provider_key_model_id`、`ai_provider_keys.priority`、`ai_providers.priority`。删之前先 grep，确认没有任何读取点。

- 删除死代码：渠道顺位编辑（`channel-pool-view.tsx:113/155/206-216`）、模型卡 `onSwapPriority` 分支、同步弹窗里永远不会出现的提示条、`add-key-dialog` 的 `providerId` 入参。

## 五、验收标准

验收标准写成「用户能回答什么问题」，不写成「界面上有什么」。

### 第一批
| 场景 | 通过标准 |
|---|---|
| 在某条渠道里打开 Haiku 5.5 | 不刷新页面，模型视角就出现这个模型，并显示「1 条能用」；业务下拉里可以选到它；真实调用确实走这条渠道 |
| 业务功能所选的模型，渠道全部挂掉 | 业务行显示「X 挂了，由默认 Y 顶班」；运行时实际调用的确实是 Y |
| 选的模型和全局默认都挂了 | 业务行标红「停摆」，运行时返回明确报错，不会改用其他模型 |
| 关掉某条渠道再打开 | 原来供应的模型全部恢复，一个不少 |
| 在模型卡上关掉某条渠道的开关 | 只停这一个模型在这条渠道上的供应，同渠道其他模型不受影响 |
| 停用一个模型，再恢复 | 恢复后，开着的渠道和停用前一致 |
| 关掉某个业务唯一可用的渠道 | 先弹窗列出受影响的业务，确认后才执行；三个层级（接入点、渠道、模型）行为一致 |
| 对照生产数据回放 | claude-haiku-5-5、opus-5-5、sonnet-5-5 的可用渠道数与真实开关一致；业务视角显示的「实际在用」与运行时解析结果逐个对得上 |

### 第二批
- 让一条渠道上的单个模型连续超时：同渠道其他模型仍显示「能用」，并且照常被调度。
- 失效渠道恢复正常后：不需要人工测试，冷却期过后会自动回到「能用」。
- 测试按钮：测试通过后，状态立即回到「能用」，包括原来处于休眠的渠道。

### 第三批
- 同步一条同时提供 `claude-haiku-5-5` 和 `claude-haiku-5.5` 的渠道：弹窗里只显示一行「Claude Haiku 5.5」，展开后能看到两种写法。
- 上游返回 429 或参数错误时，不会被误判为「上游已下线」。
- 「为此模型找渠道」：列出的渠道，打开开关后都能测通。

### 交付通用（整体验收时一次核对）
`tsc`、`lint`、`build` 全部通过；`availability`、`channel-governance`、`route`、`real-db` 相关测试通过，并为每批新口径补上回归测试；按「浏览器验收分级」做完整验证。另外检查是否残留重复实现和死代码。
