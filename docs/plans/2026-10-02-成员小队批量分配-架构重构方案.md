# 成员小队批量分配：批量安全护栏与部分成功一致性方案

**日期**：2026-10-02  
**所属根治工程**：`docs/plans/2026-10-02-全站架构根治工程-任务总纲.md` 阶段 5（调度与出口条件以总纲为准）  
**状态**：建议施工，收敛为明确的小范围安全改造。2026-10-02 阿禅确认后修订两处：上限维持 20；取消前端禁选与人数计数器（见 §2.2）。  
**性质**：解决真实的无上限和部分写入风险；不做无证据的大型批处理重构。

---

## 一、最终判断

不施工初版的五阶段“大重构”是正确的，但原结论“只保留观测点”不够：

当前真实链路是：

```text
work-group-manage-drawer.tsx
 → assignWorkGroupMembersAction
 → work-groups.ts:659
 → 逐人调用 assignWorkGroupMember
 → 每人多次数据库往返
```

当前存在一个真实稳定性敞口：

- 前端没有批量人数上限；
- 全选在职成员时，串行往返数量可能迅速增加；
- 服务端可能已经写入前一部分成员后超时；
- 前端收到失败后会按“全员失败”路径整体还原；
- 结果可能变成“界面显示没有写入，数据库实际已经写入”。

因此本次不做新表或大规模批处理引擎，但必须补上服务端硬上限和前端一致性护栏。

## 二、施工范围

### 2.1 服务端硬上限

真实入口不是 REST，而是：

```text
src/app/(app)/admin/collaboration/work-group-actions.ts:104
 → src/lib/work-groups.ts:659
```

在 Server Action 和领域函数两层都校验批量人数：

```ts
const MAX_WORK_GROUP_BATCH_ASSIGN_USERS = 20;
```

规则：

- 去重后人数为 0：保留现有空操作语义；
- 去重后人数 ≤20：按现有逐人分配逻辑执行；
- 去重后人数 >20：在任何数据库写入前直接拒绝；
- 返回稳定错误 code，例如 `WORK_GROUP_BATCH_LIMIT_EXCEEDED`；
- 错误中返回允许上限和当前数量，但不返回敏感成员信息；
- 服务端限制不能只放在 UI，避免伪造 Server Action 输入绕过。

20 是本次初始硬上限，依据是当前逐人多次数据库往返和在职成员量级；施工后以真实 P95 和查询数复核，不得通过偷偷提高上限掩盖串行实现。

**2026-10-02 阿禅确认：上限维持 20，不收紧。** 实际用量最多 10 人，取 20 是刻意留出余量，确保护栏只挡误操作、绝不挡正常用法。本节风险等级相应下调：真实逐人往返规模远小于原预估，本方案的价值是"堵住一键全选导致的半写入错觉"，不是性能优化。

### 2.2 前端选择和反馈

修改：

```text
src/app/(app)/admin/collaboration/work-group-manage-drawer.tsx
```

必须做到：

- 服务端返回超限时不执行乐观写入；
- 现有成功、部分失败和全员失败的乐观更新/回滚逻辑保持不变；
- 部分成功必须继续只还原失败成员；
- 前端不得把服务端“超限拒绝”当成已经写入；
- 超限时给出明确可读的提示（说明被拒绝、上限是多少、本次选了多少），不做静默失败；
- 不删除现有原小队名提示、审计失败回滚和乐观更新。

**2026-10-02 修订（阿禅确认）：取消本节原先两条前端要求**——"选择人数达到 20 后禁止继续选择"和"提交按钮显示当前人数和上限"均**不做**。理由：阿禅确认实际一次分配最多不超过 10 人、15 都已非常难，为几乎不会发生的场景增加禁用态和人数计数器属于把系统不确定性转嫁给用户，且违反简洁优先。防线只留在服务端（§2.1），前端只负责在真被拒绝时把话说清楚。**后续施工与验收不得把这两条补回来。**

### 2.3 可观测性

在 Server Action/领域函数的统一观测入口完成后记录：

```text
actorId
teamId
groupId
requestedCount
deduplicatedCount
assignedCount
skippedCount
failedCount
durationMs
resultCode
```

这不是替代上限的”只记日志”，而是用于验证上限是否合理、是否存在大量超限需求，以及后续是否值得做真正的批量查询优化。

> **独立执行口径（不需要另读总纲）**：本链路的入口是 **Server Action，不是 API Route**。现役观测底座 `src/lib/observed-mutation.ts` 的形态是”包裹一个返回 `Response` 的 route handler 并回写响应头”，**不能直接套用在 Server Action 上**，硬套即为伪接。Server Action 侧的统一观测入口属于全站方案的扩展缺口，本阶段不等它：
>
> - 现在就记：复用 `src/lib/api-logger.ts` ＋ `src/lib/sentry/capture-mutation-error.ts` 的既有字段与 outcome 词汇（`success`/`rejected`/`failed`/`thrown`），带上 `actorId`、`teamId`、`groupId`、去重前后人数、成功/跳过/失败数、`durationMs`、`resultCode`；
> - 链路 ID 沿用响应头/日志里已有的 `x-dydata-request-id` 语义，不新造第三个名字；
> - 在 `docs/tech-debt-ledger.md` 登记”Server Action 观测入口未收口”这一例外，等全站方案对应缺口落地后迁移；
> - 禁止为了”看起来接了统一观测”而给领域函数包一层 route wrapper，也禁止只写 `console.log`。

### 2.4 明确不做

- 不新增 `work_group_batch_assignments` 表；
- 不新增 REST API；
- 不删除 audit_logs；
- 不取消审计失败回滚；
- 不删除前端乐观更新；
- 不把部分成功伪装成全量成功；
- 不把整个 `work-groups.ts` 在本任务中重构；拆分属于可维护性方案的领域迁移阶段。

## 三、测试和验收

### 3.1 领域测试

扩展：

```text

```

8. 审计失败：保留现有回滚语义；
9. 归属、公司范围和 manage_members 权限仍由现有门禁控制。

### 3.2 Server Action 和 UI 测试


## 四、后续升级条件

只有以下证据同时成立，才允许把本方案升级为真正的批量性能重构：

- 超过 20 人的真实需求持续出现；
- 真实 P95 超过页面/操作预算；
- 查询次数和数据库连接压力证明逐人读取是瓶颈；
- 能设计批量预检、批量写入和逐项审计的事务边界；
- 能保持部分成功、补偿、权限和回滚语义；
- 完成与 `work-groups.ts` 拆分迁移的依赖排期。

在这些证据出现前，新增新表、后台任务或批处理引擎属于过度设计。
