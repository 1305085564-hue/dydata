# 成员小队批量分配：批量安全护栏与部分成功一致性方案

**日期**：2026-10-02  
**所属总方案**：`docs/plans/2026-10-02-全站架构体检报告-性能稳定性安全合并版.md`  
**状态**：建议施工，收敛为明确的小范围安全改造  
**性质**：解决真实的无上限和部分写入风险；不做无证据的大型批处理重构。

---

## 一、最终判断

不施工初版的五阶段“大重构”是正确的，但原结论“只保留观测点”不够：

当前真实链路是：

```text
work-group-manage-drawer.tsx
 → assignWorkGroupMembersAction
 → work-groups.ts:659
 → 逐人调用 assignWorkGroupMember
 → 每人多次数据库往返
```

当前存在一个真实稳定性敞口：

- 前端没有批量人数上限；
- 全选在职成员时，串行往返数量可能迅速增加；
- 服务端可能已经写入前一部分成员后超时；
- 前端收到失败后会按“全员失败”路径整体还原；
- 结果可能变成“界面显示没有写入，数据库实际已经写入”。

因此本次不做新表或大规模批处理引擎，但必须补上服务端硬上限和前端一致性护栏。

---

## 二、施工范围

### 2.1 服务端硬上限

真实入口不是 REST，而是：

```text
src/app/(app)/admin/collaboration/work-group-actions.ts:104
 → src/lib/work-groups.ts:659
```

在 Server Action 和领域函数两层都校验批量人数：

```ts
const MAX_WORK_GROUP_BATCH_ASSIGN_USERS = 20;
```

规则：

- 去重后人数为 0：保留现有空操作语义；
- 去重后人数 ≤20：按现有逐人分配逻辑执行；
- 去重后人数 >20：在任何数据库写入前直接拒绝；
- 返回稳定错误 code，例如 `WORK_GROUP_BATCH_LIMIT_EXCEEDED`；
- 错误中返回允许上限和当前数量，但不返回敏感成员信息；
- 服务端限制不能只放在 UI，避免伪造 Server Action 输入绕过。

20 是本次初始硬上限，依据是当前逐人多次数据库往返和在职成员量级；施工后以真实 P95 和查询数复核，不得通过偷偷提高上限掩盖串行实现。

### 2.2 前端选择和反馈

修改：

```text
src/app/(app)/admin/collaboration/work-group-manage-drawer.tsx
```

必须做到：

- 选择人数达到 20 后禁止继续选择新的成员，或明确显示超限提示；
- 提交按钮显示当前人数和上限；
- 服务端返回超限时不执行乐观写入；
- 现有成功、部分失败和全员失败的乐观更新/回滚逻辑保持不变；
- 部分成功必须继续只还原失败成员；
- 前端不得把服务端“超限拒绝”当成已经写入；
- 不删除现有原小队名提示、审计失败回滚和乐观更新。

### 2.3 可观测性

在 Server Action/领域函数的统一观测入口完成后记录：

```text
actorId
teamId
groupId
requestedCount
deduplicatedCount
assignedCount
skippedCount
failedCount
durationMs
resultCode
```

这不是替代上限的“只记日志”，而是用于验证上限是否合理、是否存在大量超限需求，以及后续是否值得做真正的批量查询优化。

### 2.4 明确不做

- 不新增 `work_group_batch_assignments` 表；
- 不新增 REST API；
- 不删除 audit_logs；
- 不取消审计失败回滚；
- 不删除前端乐观更新；
- 不把部分成功伪装成全量成功；
- 不把整个 `work-groups.ts` 在本任务中重构；拆分属于可维护性方案的领域迁移阶段。

## 三、测试和验收

### 3.1 领域测试

扩展：

```text
src/lib/work-groups.test.ts
```

覆盖：

1. 0 人：保留成功且 0 人；
2. 1 人：现有单人语义不变；
3. 20 人：进入原有批量逻辑；
4. 21 人：写入前拒绝，mock 数据库零写入；
5. 重复 userId 去重后不超过上限；
6. 去重前超过、去重后不超过时按去重后判断；
7. 批量中部分失败：成功成员保留、失败成员列明；
8. 审计失败：保留现有回滚语义；
9. 归属、公司范围和 manage_members 权限仍由现有门禁控制。

### 3.2 Server Action 和 UI 测试

扩展：

```text
src/app/(app)/admin/collaboration/work-group-workbench.test.ts
```

验证：

- UI 不允许继续选择第 21 人，或提交时给出明确超限提示；
- 超限响应不触发错误的乐观写入；
- 部分失败只回滚失败成员；
- 原小队名提示仍展示；
- `assignWorkGroupMember` 单人入口不受影响。

### 3.3 真实浏览器验收

使用真实角色和真实成员数据：

1. 1 人加入；
2. 20 人加入；
3. 尝试选择 21 人；
4. 部分成功场景；
5. 审计失败恢复；
6. 跨公司成员被拒绝；
7. 刷新后页面与数据库一致；
8. 单人调整不受影响。

固定命令：

```bash
npx tsx --test src/lib/work-groups.test.ts
npx tsx --test src/app/'(app)'/admin/collaboration/work-group-workbench.test.ts
npm test
npx tsc --noEmit --pretty false
npm run gate:roles
npm run gate:browser
```

### 3.4 回滚

本次无 migration、无新表。出现任何界面与数据库不一致、权限越界、审计丢失或单人入口回归时，回滚前后端同一 commit。回滚后必须重跑领域测试和真实浏览器验收。

## 四、后续升级条件

只有以下证据同时成立，才允许把本方案升级为真正的批量性能重构：

- 超过 20 人的真实需求持续出现；
- 真实 P95 超过页面/操作预算；
- 查询次数和数据库连接压力证明逐人读取是瓶颈；
- 能设计批量预检、批量写入和逐项审计的事务边界；
- 能保持部分成功、补偿、权限和回滚语义；
- 完成与 `work-groups.ts` 拆分迁移的依赖排期。

在这些证据出现前，新增新表、后台任务或批处理引擎属于过度设计。

**完成定义**：批量人数有服务端硬上限、超限零写入、前端不再误报全量回滚、部分成功语义保持、真实权限和浏览器验收通过。
