## 结论先行（合并三方后的五条判断）

1. **唯一已实测的权限真洞**：普通组长可绕过系统配置接口，直接读生产系统配置（`system_settings` 的 RLS 对所有在职 admin 放行）。其余"越权"疑点（owner 默认全库、团队缺写策略、组员借集团令牌扩权）线上**均不成立**，是假警报。
2. **性能锅基本不在数据库**：索引问题≈0（库仅 63MB、最大表两千行级）。现网真慢的是应用层取数习惯——协作岗位管理每请求重算整月、成员管理首屏五段串行。这两处**不动库就能修**。
3. **你原定的四条链路里，"视频复盘"和"数据管理"拆不开**：数据管理复用了视频复盘的详情引擎（`ContentDetailDialog` + `loadAdminContentVideoDetail`）。这既是架构地雷，也已被权限侧确认为**受控只读**（`canReadWorkVideo`）——所以它是"该显式化为共享层"的雷，不是"该修的 bug"。
4. **权限/数据范围栈是全局耦合中心，但现状是对的**：`data-access-scope` 相关符号被 48 个生产文件引用、鉴权在四层各查一遍。它牵连最广却不宜夹在某条业务链路里重构，应留到有契约测试兜底后单独收口。
5. **最脏的是"豁免（补交/请假）"链路**：一个提交动作两条写入入口、审批界面散在三个模块。属"再不管会长歪"的那种，建议做一次收口而非新功能。

## 三、权限审计（四层交叉对账：角色→菜单→接口→数据库）

> 连接：`.env.local.prod-bak`（文档登记主库），命令均带 `default_transaction_read_only=on`。分类三档：真洞 / 改到一半 / 假警报。

- **【真洞·1】普通组长可直接读取系统配置**
  接口要 `manage_system`（`api/admin/system/settings/route.ts:52`），但生产策略 `system_settings / Admins manage system settings` = `USING(is_admin_or_owner())`、`cmd=ALL`，`authenticated` 还握有 INSERT/UPDATE/DELETE。只读事务内切换组长身份 `SELECT count(*) FROM system_settings` = **2**，组员 = **0**（两条为飞书催交总开关、选题库飞书工作区地址）。**读取越权已实测；实际写入成功待核。** 归"系统配置接口—数据库能力门禁"链路，第二轮先收窄直连权限再验接口允许/拒绝。
- **【改到一半·2】补交申请缺公司范围限制**
  `fulfillment_appeals` 策略只判 `is_admin_or_owner()`、无 restrictive 公司范围。但该表生产行数 **0**，组长读取也 0 → **宽策略确认存在，但不能宣称已实测跨公司越权**。归"补交—审批—数据库直连"链路，第二轮用专用可回收样本验证跨公司拒绝。
- **【假警报·3】owner 默认返回全库，线上不成立**
  生产 `visible_user_ids` 转调 `visible_user_ids_v2`、`get_data_scope` 对 owner 返回 `team`。设老板身份实测：`get_data_scope=team`、固定能力 12、当前可操作成员 43（库总资料 84），**未返回全库**。存量 `role=owner` 仅 1 行且为 `company_owner` 归一。归"角色兼容收口"，不按线上全库漏洞修。
- **【假警报·4】company_owner 运行时映射为 admin，有兼容边界**
  生产角色分布：admin/admin 在职 19、member/member 44（归档 20）、owner/company_owner 1，双列冲突 0。核心范围用归一后公司角色，非原始 admin。遗留：`has_permission/is_admin` 用 `coalesce` 而 `company_role_for_user` 遇冲突报错，异常处理两套方式——列为"双角色字段迁移"改版收口项，不以不存在的异常行报现存越权。
- **【假警报·5】teams 缺 permissive 写策略，是受控设计**
  生产 `teams` 只有 `teams_read` permissive、其余 restrictive，无 permissive 写；建/删走 `adminSupabase`。真实身份模拟：组长/组员/老板各读到 **1** 个本人公司，跨公司 0。**不要补 permissive 写放行策略**（会开越权门）。服务端写入成功仍待真实动作验收。
- **【假警报·6】组员不能凭伪造集团标识扩大范围（部分待核）**
  会话绑定 `s.user_id=auth.uid()` 且需老板资格；组员身份 `get_data_scope=self`、可见 1 行。未在prod找到"老板未撤销且未过期"的会话样本 → **"组员持真实有效老板会话"的功能性复验待核**，第二轮补正反例。
- **【假警报·7】`/admin` 菜单与接口路径不同，非漏洞**
  组员不能进完整复盘页，但可经 `work-video` handler 显式 `canReadWorkVideo` + 按岗位范围过滤后看本公司作品——是受控只读，不靠菜单拦截。接口真实登录态 HTTP 结果待核。

> 本报告不构成全站权限安全通过：真实登录态接口、实际写入拒绝、有效集团会话正反例均未覆盖。

## 四、三份报告的交叉印证（合并的关键结论）

1. **复盘详情引擎耦合** —— 架构侧判为"最大并发地雷"，权限侧独立确认该跨链读取（组员经 `work-video` 看本公司作品）是**受控只读**、非漏洞。合并结论：把它从"视频复盘私有"**提升为共享基础层 + 加引用契约测试**，只划边界不改行为；**不是**要修的 bug。
2. **数据范围层（data-access-scope/visible_user_ids/get_data_scope）** —— 架构侧是"48 引用的全局耦合中心"，权限侧实测其现状**正确**（owner 不放大、组员不越界）。合并结论：现状可信赖，但**别夹在业务链路里重构**，单独收口、有契约测试兜底后再动。
3. **`.env.local` 被并发切换** —— 数据库审计与权限审计**各自独立**撞到同一现象，权限审计还因此废弃过一批本地结果。合并结论：这是**多会话协作的真实风险**，第二轮前必须约定连接配置归属，实测一律带行数探针。
4. **过时信息（两份报告顺手纠正，待回写文档）** —— 待办/文档里的"/admin/modules 逐字符重取最痛待修"**已修复并上线**（`e6000ad3`）可销账；`/growth` 已删除；排行榜"无前端入口"文档偏差（`collaboration/leaderboard-tab.tsx:31` 实调）；`adaptive-sheet` 文档号称统一基座实为低采用；`middleware.ts:170,172` 残留 `/violations` 死路由判断。
