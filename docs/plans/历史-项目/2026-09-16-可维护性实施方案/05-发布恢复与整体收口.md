# 第 5 批：发布恢复与整体收口

前置：第 0–4 批本地证据齐全。先读 `00-执行基线与交接.md`、`docs/工程运行事实.md`；不能把本文视为当前会话的 main 推送授权。

## 1. 交付与文件范围

目标：本专项提交可追踪，实际部署可识别，关键操作有生产证据，后续维护者有准确入口和可执行恢复步骤。

- 新建 `docs/reference/可维护性维护入口.md`：只放模块→代码入口→定向测试、日志查找、发布恢复的索引，不复制业务/权限规则。
- 修改 `docs/工程运行事实.md` 的必要目录/观测事实和维护入口链接，先完整备份；不扩大为工程规范重写。
- 修改总进度书、当日日志；新建 `output/maintenance/05-验收.md` 汇总版本、发布、真实验收与恢复清单。
- 默认不改应用源码和数据库。前批缺陷退回对应批次精确修复，再复跑受影响检查；本批不新增功能。

## 2. 发布前逐项检查

- [ ] 05.1 逐一核对六份记录：任务勾选、命令退出码、实际场景、未覆盖项；本地通过不等于已发布。专用测试数据清理失败是阻塞，不能写“无残留”。
- [ ] 05.2 将第 1–4 批提交 SHA 列成清单，核对 Git diff 只含约定改动。迁移目录、角色契约、权限收尾的其他提交不得顺带发布。
- [ ] 05.3 只针对冻结范围检查旧 import、被替代函数和测试引用。组件已提取职责不能同时留两套实现；不全仓新增审查清单。
- [ ] 05.4 核对当前本地、远端 main、生产 Ready SHA；说明本专项应用在何种权限基线上。若所需权限补丁尚未发布，等待原权限任务完成，不能自行把它包进维护性发布。
- [ ] 05.5 核对浏览器门禁目标和数据库环境，准备下方命令；第 3、4 批操作矩阵必须另有证据。门禁在 05.8 最终候选代码形成后运行，不沿用合入前输出。

```bash
npm run gate:static
npm run gate:browser
git diff --check
```

`gate:browser` 默认启动本地生产服务，设置 `DYDATA_E2E_BASE_URL` 才是指定部署。记录环境，不在日志输出账号；缺登录配置则阻塞，不能跳过。现有 gate 会重复 build，这是现有发布命令行为，本专项不顺手改脚本。

## 3. 精确发布流程

- [ ] 05.6 确认当前执行会话已明确授权 main 推送；有授权直接继续，无授权只在此处请求，不逐批询问。
- [ ] 05.7 确认目标提交序列已独立保存。若工作分支含其他任务提交，使用已核对远端 main 的隔离分支承接本专项提交；冲突不得选择全盘 ours/theirs。明确冲突来源后最小处理，无法保持行为则阻塞。
- [ ] 05.8 每批一个领域提交，按 1→2→3→4 顺序保留。逐个文件暂存，检查 staged diff；已有批准提交不重复提交。形成最终候选 SHA 后运行上述三条门禁，记录 SHA 与结果，再推送本专项批准的提交序列，不 force push。合入、解冲突或后续代码变化后，重新验证受影响检查和发布门禁；旧工作树通过不能替代候选版本通过。
- [ ] 05.9 通过当前可用 Git/Vercel 工具核对生产 deployment 为 Ready、commit SHA 与最终提交一致，域名确实指向该 deployment。工具不可用或状态未知即记阻塞，不能用健康接口代替。

本专项不执行 migration；若落地时发现必须改数据库才能通过，说明前批已超出冻结方案，回退至对应批次重新裁决，不在发布阶段临时跑 SQL。

## 4. 生产验收矩阵

统一用第 0 批记录的专用账号与对象。已有授权覆盖的操作直接执行；禁止发飞书催交、调用收费 AI、改真人角色或删除真人数据。

| 场景 | 要证明什么 |
|---|---|
| `/api/health` 及 `?check=supabase` | 服务/数据库连通；仅作健康证据，不算业务验收 |
| `/dashboard` 专用 member 新建提交、编辑同一测试作品、刷新 | videos/snapshot/report 关联仍正确；新建与编辑行为保持；页面与只读数据核对一致 |
| dashboard 豁免申请、重复日期、非重叠日期 | 共享预检与原行为一致，拒绝无额外写入，成功刷新可见 |
| 豁免审批：本团队允许、跨公司/自审拒绝 | 原权限边界保持；审批/授予不因共享预检被改写；只操作已准许测试申请 |
| `/admin/modules` 选人、搜索、审批区和指定提取区域 | 角色入口、选择状态和切换不变；无需为结构验收真实调动员工 |
| `/admin/content` 测试视频切换、详情/提取区域、返回 | 无旧请求覆盖新对象；链接/队列行为与基线一致，不触发付费分析 |
| 诊断编号查日志、Sentry 合成事件收件 | 版本/阶段可定位，隐私字段仍被过滤；缺查看权限单列阻塞 |

记录入口、角色别名、操作、预期/实际、环境、对象核对和恢复结果；用户 ID、凭据、正文不进入报告。生产不可安全写的场景不得以本地 fake 冒充通过。

## 5. 恢复方案（发布前填实际值）

在 `05-验收.md` 记录：上一个可用 deployment ID/URL、其 SHA、本专项最终 SHA、1–4 批提交清单、执行当时数据库迁移状态、恢复执行工具与权限。

- 触发条件：本专项造成核心提交不可用、授权边界回归或关键页面持续异常。先停止继续测试/写入，保留失败请求编号与版本证据。
- 应用恢复：按工程运行事实优先回到已记录的前一个 Ready 部署；先确认该旧版本与当前数据库及权限状态兼容。不能随便选更老的部署。
- Git 恢复：部署回退不等于源码回退；在干净分支逆序撤销本专项提交后重新验证/发布。不 reset 共享工作区，不撤销其他任务的权限 migration。
- 数据恢复：代码回退不自动撤销已产生业务数据。只清理已登记的测试对象；真实数据异常先冻结写入并报告，不自动批量修正。
- 恢复后复验健康、核心提交/读取、原拒绝边界。不要为了“演练成功”故意把生产切回旧版本；本轮要求核实可用恢复目标与步骤，未实际回滚就写“未演练”。
