# 页面功能说明体系构想

> 状态：灵感记录，尚未定方案
> 记录日期：2026-09-24
> 下一步：2026-09-25 再讨论范围、结构和落地方式

## 一、想解决什么问题

目前项目里的文档主要按工程视角组织：项目事实、权限安全、数据口径、接口文档、施工方案、审查报告等。它们对 AI 和工程执行有帮助，但不适合不懂代码的人快速理解：

- 网站到底有哪些页面；
- 每个页面是做什么的；
- 谁会使用它；
- 用户在页面上能完成什么；
- 页面之间有什么关系；
- 一个页面发生变化时，可能会影响哪些业务；
- 某个页面现在是正常使用、待重做、归档，还是已经跳转到别处。

目前虽然有《全站模块地图》，但它更像总览地图，不能替代每个页面的“使用和维护说明书”。

## 二、初步想法

在 `docs/` 下新增一个专门的页面功能说明文件夹，例如：

```text
docs/页面功能/
```

这个文件夹不写代码实现，也不要求负责人阅读 API、数据库、RPC 或 React 组件。它只从产品和用户角度，整理全站页面的功能说明。

初步可能的结构：

```text
docs/页面功能/
├── README.md                  # 页面总索引和页面之间的关系
├── 员工端/                    # 普通成员会使用的页面
├── 管理端/                    # 管理人员会使用的页面
├── 公共页面/                  # 登录、注册、找回密码等
└── 已下线页面/                # 只保留必要的历史说明
```

具体目录和文件名明天再决定，不在今天冻结。

## 三、每个页面可能记录什么

每个页面说明可以只回答这些人话问题：

- 页面叫什么；
- 页面地址是什么；
- 谁能使用；
- 这个页面解决什么问题；
- 用户可以完成哪些事情；
- 最主要的操作流程是什么；
- 页面会产生或影响什么结果；
- 和哪些页面有关；
- 当前状态是什么；
- 常见的异常或容易误解的地方；
- 如果要修改它，应该先看哪些相关资料。

不希望它变成技术文档，也不希望把源代码、数据库表、接口细节大量抄进来。技术资料仍然放在现有的 `reference/`、项目事实和专项维护入口中。

## 四、可能解决的问题

### 1. 让不懂代码的人能理解产品

不用翻代码，也不用在几十份施工方案之间来回找，就能知道页面的用途、角色和操作范围。

### 2. 让 AI 更快定位正确资料

AI 可以先根据页面功能说明判断要处理哪个页面，再按页面说明中的入口去读取权限、数据口径、接口或维护资料，而不是先全库搜索。

### 3. 减少旧文档误导

页面说明可以明确标记：

- 当前使用；
- 待重做；
- 只读保留；
- 已下线；
- 重定向到其他页面。

这样历史方案和当前页面不会轻易混在一起。

### 4. 建立“页面变化”的文档入口

以后页面新增、下线、合并或主要功能变化时，可以知道至少需要检查哪份页面说明，而不是凭记忆找文档。

### 5. 形成产品层和技术层之间的桥梁

页面功能说明负责“用户看到和使用什么”；现有技术文档负责“代码、接口、权限和数据怎么实现”。两层分开，但可以互相链接。

## 五、与现有文档的关系（初步设想）

- `docs/全站模块地图.md`：保留为全站总览和模块关系图。
- `docs/页面功能/`：新增为页面级、产品视角的说明层。
- `docs/reference/`：继续保存接口、维护手册、契约和专项资料。
- `docs/plans/`：继续保存尚未完成的施工方案。
- `docs/reviews/`：继续保存审查和验收证据。
- `docs/archive/`：继续保存历史资料，不作为当前页面说明。
- `docs/文档维护入口.md`：未来补充页面功能说明体系的入口和维护规则。

原则上不急着搬迁现有 300 份文档。可以先建立页面说明层，再逐步把真正有价值的资料链接进去。

## 六、明天需要讨论的问题

1. “页面”按路由划分，还是按用户任务/业务模块划分？
2. 员工端、管理端、公共页面是否足够，是否还需要按角色细分？
3. 哪些页面必须先写，哪些可以后写？
4. 页面说明是一个页面一份文件，还是一个业务模块一份文件？
5. 页面说明是否需要截图、流程图或操作示例？
6. 谁负责确认页面的业务描述是准确的？
7. 页面状态和最后核对日期怎样记录最省事？
8. 技术维护入口链接到什么程度才不会让文档变成代码说明书？
9. 是否需要把旧页面、重定向页面和废弃页面单独整理？
10. 这个体系是否先从 5～10 个核心页面试做，而不是一次性覆盖全站？

## 七、今天不做的事情

- 不创建页面功能文件夹；
- 不批量创建页面说明文件；
- 不搬迁现有文档；
- 不重新分类全部 `docs/`；
- 不改页面代码、接口、权限或数据库；
- 不制定最终模板；
- 不把这个灵感记录当成已经批准的实施方案。

## 八、一句话总结

建立一个面向产品和用户的“页面功能说明层”：让负责人能看懂每个页面做什么，让 AI 能从页面快速找到相关工程资料，同时把页面说明与代码实现、历史方案和审查证据分开维护。

## 九、文件名称维护也是问题

当前 `docs/plans/` 里大量文件以日期开头，Finder 按名称排序时会先看到一排相同的 `2026-09-xx`，真正有用的主题被截断，人工很难快速判断文件内容。这说明日期适合做时间记录，但不适合成为文件名最醒目的第一信息。

明天需要单独讨论一套文件命名方式，例如：

- 主题优先，日期放末尾：`岗位管理对组员放开本公司范围-实施方案-2026-09-23.md`
- 或用编号/状态做目录，文件名只保留内容主题：`plans/进行中/岗位管理对组员放开本公司范围-实施方案.md`
- 页面功能类文档直接按页面名称命名：`页面功能/管理端/岗位管理.md`
- 日期保留在文档正文、元信息或历史归档目录中，而不是让日期遮住主题。

需要同时考虑：搜索、排序、历史追溯、重复主题、同一主题多轮方案、现有链接和 Git 历史。今天只记录问题，不批量改名，避免产生大量链接失效。
