## 一、问题

**P1 页面上的现象**：首页「创作表达录入」上传互动截图后，卡片显示「截图识别通道暂不可用，请手动填写或稍后重试」／后来变成「识别超时，请稍后重试」，指标栏空着，顶部提示「1 张截图识别未确认，请对照原图核对指标后提交」。失败状态会停留在「待核对」，页面不会自动重新识别，用户点截图卡片的重试按钮或重新上传才会重跑。

**P2 稳定性问题未根治（已知、已接受）**：识别走的是共享 AI 渠道，速度波动大（同一种真实截图实测 5–18 秒）。2026-10-03 15:2x 起超时线已从 20 秒放宽到 45 秒（整链 60 秒），但两个机制仍会造成"连续几分钟都失败"：
- 渠道连续失败后会被熔断拉黑（`ai_provider_keys.unhealthy_until`），拉黑期间该渠道不可用；
- 被拉黑后顺位链退到"全渠道兜底"，会去试已欠费/已下线的渠道，报 `402 Insufficient account balance`、`404 Model "gemini-2.5-flash" is not supported`、`已尝试 5/6 个渠道` 之类的错。

**P3 待人判断的问题（成本 vs 稳定）**：
- 截图识别当前绑定 `gpt-6.1-sol`（阿禅新加的便宜渠道）。实测最快的稳定选项是 `claude-opus-4-6`（4/4 通过、4–6 秒），但单价更贵。要不要换，属成本决策。
- "同模型多渠道备份＋关掉坏渠道"这组做法已验证可行（见 事实 F6），阿禅 2026-10-03 的决定是「先能用就行，今天我会重构这个页面，问题太多了」，即随页面重构再处理。

**P4 版本状态不一致**：远端 `main = 0eacdc8c`（含超时修复的 cherry-pick 副本），本地 `main` 领先 24 笔未上线（阶段 6 导航/选题拆分、门禁收紧、履约补交修复等）。两边已分叉，下次推送前需要 `git pull --rebase`；本地那笔原始修复提交 `397a040f` 会因内容已应用被跳过，属正常现象。剩余批次里含一笔数据库迁移 `supabase/migrations/20261003132000_fulfillment_appeal_submission_payload.sql`（补交 submission_payload，来自另一条线），上线那批时代码与迁移需同批。

**P5 同类坏掉的其他功能**：`content_analysis`（内容分析）、`sample_quality_check` 仍绑定已下线的 `gemini-2.5-flash`，现在也是坏的，同样的改法能修。

**P6 可观测性缺口**：生产实际运行的提交号取不到（`vercel logs`／`vercel whoami` 在本机都是 `TypeError: fetch failed`，而 `api.vercel.com` 本身可达），只能用 GitHub 上的 Vercel 部署状态＋健康检查作间接证据。`/api/health` 不回 commit。

## 二、事实（全部实测确认）

**F1 识别代码没坏，是模型死了**。截图识别分两步：百度提字 → 文字结构化。百度那步一直正常（实测正常返回文字行，token 与配额都正常）。坏的是第二步：结构化功能 `ocr_screenshot_structure` 原绑定 `gemini-2.5-flash`，该模型 2026-10-03 上午被上游下线，实测报 `404 "Model \"gemini-2.5-flash\" is not supported by any configured account in this group"`（api9 渠道），另一条渠道（api7）间歇 `503 No available channel`。

**F2 后台有两行配置，主链路用的是没改的那行**。阿禅 2026-10-03 13:29 新增渠道 `api9 / gpt 特惠 0.12` 上的 `gpt-6.1-sol`（`ai_provider_key_models.id = 5106dbfc-de57-4d3f-93a7-9ee8e01ade67`），并切了「截图识别·看图回退」（`ocr_screenshot`）和「全局默认」（`default`）两行；但识别主链路走的是「截图识别·文字结构化」（`ocr_screenshot_structure`），这行没动。这是"后台测试通过、页面还是报错"的直接原因。后台的"测试"是普通文本测试，不带 `response_format=json_object`，测不出 F3 的坑。

**F3 `gpt-6.1-sol` 的 JSON 模式有个坑**：`response_format=json_object` ＋ 极简提示词（如 `只返回 {"ok":true}`）实测报 `400 invalid_request_error`；但用真实结构化提示词（含"只返回 JSON"字样）3/3 正常返回可解析 JSON。判断该模型是否可用必须用真实提示词。

**F4 候选横评（真实结构化提示词 ＋ 真实解析器 `parseOcrResponse`，数据图＋完播图两种）**：

| 模型（渠道） | 通过 | 耗时 |
|---|---|---|
| `claude-opus-4-6`（api7/claude，`0a3eb452-3de2-4809-a812-30799272f0ad`） | 4/4 | 4.2–6.5s（一次 18s） |
| `gpt-6.1-sol`（api9/gpt特惠，`5106dbfc-…`） | 3/4 | 5.4–16s |
| `gemini-3.5-flash-lite`（api7/gemin，`08d4939a-f6d1-4df7-b940-e26c68f887fc`） | 3/4 | 5.3–15s |
| `gpt-5.6-luna`（api9/gpt特惠，`2d3bb485-759b-4ea5-adc5-075b63cd8758`） | 3/4 | 4.5–20s+，超时最多 |

模拟 OCR 文字（8 行）时 `gpt-6.1-sol` 双图 10/10 通过（数据图 13–16s、完播图 6–8s，字段全部识别出）；用整页密集截图（74 行 OCR 文字）时耗时反而降到 5–6 秒。**耗时与文字量不是简单正相关，波动主要来自共享渠道负载**。

**F5 熔断与兜底的机制**（`src/lib/ai/client.ts` + `src/lib/ai/provider-routing.ts`）：调用失败会累计 `ai_provider_keys.consecutive_failures` 并写 `unhealthy_until` 拉黑该钥匙；`listRankedProviderKeyModels` 会把被拉黑／被禁用的渠道过滤掉；当绑定模型一条健康渠道都不剩时，`resolveFeatureChannelChain` 退到"全量顺位"（所有健康渠道、不分模型）去试。这解释了两个现象：①绑定写着 A 模型、实际走 B 渠道；②报错里出现欠费渠道的 402／已下线模型的 404。

**F6 同模型跨渠道的可行性已探明**：实测 8 条渠道里 **7 条都支持 `gpt-6.1-sol`**（`api7/default`、`api7/gemin`、`api7/claude`、`api1/default`、`api1/claude`、`api2 gemin/default`、`api9/gemin`；唯 `mimo` 报 `400 Unsupported model`）。`ai_provider_key_models` 一个模型可以挂多把钥匙，顺位＝`key.priority + provider.priority` 升序，同模型跨渠道自动切换。也就是说"给 `gpt-6.1-sol` 加几条备份渠道"这条路是通的，不需要换模型。另查明 `api1`、`api2` 渠道本身活着，此前报错是因为挂了不支持的模型行。

**F7 当前生效的配置（2026-10-03 06:14 UTC 起）**：`ocr_screenshot`、`ocr_screenshot_structure`、`default` 三行的 `model_id = 'gpt-6.1-sol'`、`provider_key_model_id = '5106dbfc-de57-4d3f-93a7-9ee8e01ade67'`。配置每次请求直读库、60 秒缓存，改完即生效，不需发版。

**F8 超时相关代码改动（2026-10-03 15:2x 随 `0eacdc8c` 上线）**：结构化调用 `timeoutMs` 20→45 秒、`totalTimeoutMs` 30→60 秒（`src/app/api/ocr-screenshot/baidu-channel.ts`），视觉回退同口径 25→45 秒（`route.ts`），`/api/ocr-screenshot` 声明 `export const maxDuration = 60`。上线前真图全链路集成 3/3 通过（10–16 秒），改前同用例 3/3 触发超时或兜底渠道报错。

**F9 2026-10-03 上午的渠道集体故障**（生产库实测，UTC 05:28–05:31 ＝ 上海 13:28–13:31）：mimo `402 余额不足`、api2 gemin `403 额度不足（负余额）`、api1 `503 No credentials`、api8 `fetch failed`、api9 gemin `404 模型已下线`。识别失败是这次故障＋F1 绑定错位叠加的结果。
