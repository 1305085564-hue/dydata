## 三、已确认事实与根因定位

### 1. 为什么会出现「暂无其他可对比的成员」？
- **排查点 1：前端过滤逻辑**（`src/app/(app)/admin/content/content-diagnosis-workbench.tsx:1077`）：
  ```tsx
  {profiles.filter((p) => p.id !== video?.user_id).length > 0 ? (
    <Select value={selectedRefUserId || undefined} onValueChange={...}>...</Select>
  ) : (
    <span className="text-[11px] text-[#78716C]">暂无其他可对比的成员</span>
  )}
  ```
  只有当传入的 `profiles` 中存在除了当前视频作者 `video.user_id` 以外的其他成员时，才会渲染下拉框；否则直接落入“暂无其他可对比的成员”。

- **排查点 2：首屏数据源缺陷（首屏 RPC `admin_content_first_screen`）**：
  - 查看 `supabase/migrations/20260828120000_remove_content_feedback_workflow.sql:152-155, 221-232`：
    ```sql
    visible_profile_ids as (
      select distinct coalesce(owner_profile_id, user_id) as profile_id
      from scoped_videos
    )
    ...
    'profiles', coalesce((
      select jsonb_agg(
        jsonb_build_object('id', p.id, 'name', coalesce(p.name, '未命名成员'))
        order by p.name asc
      )
      from public.profiles p
      where p.id in (select profile_id from visible_profile_ids)
    ), '[]'::jsonb)
    ```
  - **严重结构缺陷**：RPC 返回的 `profiles` 并不是当前团队的全部成员，而是**当前首屏候选视频（`scoped_videos`，最多60条）里出现过的作者/归属人**！
  - 如果一个团队刚上线只有某一个人的视频，或者某个运营人员名下仅有自己的作品，`visible_profile_ids` 就只有他一个人。此时 `profiles` 只有 1 项，过滤掉自己后数组为空！

- **排查点 3：协作工作台调用缺失传参**（`src/app/(app)/admin/collaboration/collaboration-workbench.tsx:399`）：
  ```tsx
  <ContentDiagnosisWorkbench
    video={diagnosisDetail.video}
    snapshot={diagnosisDetail.snapshot}
    reviewReadiness={diagnosisDetail.reviewReadiness ?? undefined}
    canOperateLifecycle={isOwnerOrTeamAdmin}
    onLifecycleChanged={() => {}}
    onClose={() => setDiagnosisDetail(null)}
  />
  ```
  协作页面调用 `ContentDiagnosisWorkbench` 时，完全**漏传了 `profiles` 属性**！导致 `profiles` 缺省为 `[]`，在协作页点击诊断抽屉时「指定成员」必报“暂无其他可对比的成员”！

- **排查点 4：后端归因接口权限约束**（`src/app/api/admin/content-attribution/[videoId]/route.ts:107-112`）：
  ```ts
  const activeVisibleUserIds = getActiveVisibleUserIds(access.scope);
  if (requestedRefs.includes("user")) {
    if (!refUserId || !activeVisibleUserIds.includes(refUserId)) {
      return NextResponse.json({ error: "无权限对比该指定成员" }, { status: 403 });
    }
  }
  ```
  后端归因接口严格校验了 `refUserId` 必须在当前用户的 `activeVisibleUserIds`（团队或全公司在职成员）范围内。如果前端从外部拉取成员，必须确保只拉取在当前用户可见范围内的在职成员，否则后端会 403。

## 四、已做决策与禁止重做

1. **数值对比视觉与文案**：
   - 必须维持极简直觉：红涨（`↑ 5.2%`）、绿跌（`↓ 3.1%`）、持平（`—`）。
   - 禁止恢复冗余的汉字（如“▲ 领先”与“↑”并存）。
   - 禁止泄漏原始 key（如 `refKey === "user"` 时必须使用传入的真实人名，如 `阿强`，不能漏出英文或 fallback 为 `user`）。
2. **禁止数据库先行发布 / 改动 RPC 签名**：
   - 根据《全站模块地图》及《工程运行事实》，`admin_content_first_screen` 属于现役首屏核心 RPC，改动其签名会破坏线上加载。
   - 优先在应用层与组件层自愈解决，禁止粗暴修改线上 RPC 签名。

## 六、交接给 Codex 的任务与排查重点

### 1. 核心修复任务：「指定成员」全链路自愈与闭环
- **前端自愈（Self-Healing）**：
  - 在 `content-diagnosis-workbench.tsx` 中：
    1. 候选成员合并：不要仅仅依赖 `profiles` prop，同时合并扫描 `videos` prop 中的 `v.user_id` 和 `v.profiles?.name`，自动去重生成候选池。
    2. 缺失兜底补全：如果可用候选成员（`p.id !== video?.user_id`）依然为空，组件在打开或激活 `user` 参照时，异步拉取当前用户可见的在职成员列表。
    3. 自动选中第一个有效成员：当 `selectedRefUserId` 为空且有可用成员时，自动设置 `selectedRefUserId = firstMember.id`，触发归因拉取，杜绝假死。
- **调用方修复**：
  - 在 `collaboration-workbench.tsx` 中调用 `ContentDiagnosisWorkbench` 时，补全 `profiles`（可以从已有数据或协作成员列表中传入）。

### 2. 结构性 Bug 深度排查重点（Codex 专项任务）
用户明确要求：**“围绕着结构 bug，我会让 codex 做更多的 bug 搜查”**。建议 Codex 重点排查以下结构性脆弱点：
1. **跨页面 props 契约不对齐**：
   - 排查 `ContentDiagnosisWorkbench` 的所有调用方（如 `content-page-client.tsx`、`collaboration-workbench.tsx` 等），检查是否存在缺漏必填/关键 props（如 `profiles`、`reviewReadiness`、`videos`、`snapshots`）导致的功能降级。
2. **首屏 RPC vs 全量 Loader 字段漂移**：
   - 对比 `admin_content_first_screen` RPC 返回的 json 结构与 `loadAdminContentFullData` 返回的数据结构，检查是否有字段在 RPC 模式下缺失、类型不一致或命名不一致（例如 `profiles` 在全量模式下取自 `public.profiles`，在首屏模式下仅取自 `scoped_videos`）。
3. **归因 API（content-attribution）权限与状态边界**：
   - 当选中的对比成员近 3 条作品无 24h 快照、或被对比视频无 24h 快照时，API 返回的 `sample_status`（如 `insufficient_sample` / `missing_snapshot`）在 UI 上是否能优雅提示，会不会导致整屏红字崩溃或静默白屏。
4. **视频切换时的状态清理**：
   - 在复盘抽屉中通过快捷键 `J/K` 切换视频时，检查 `selectedRefUserId`、`multiAttribution`、`abortController` 等是否发生竞态、未取消旧请求或未重置选中状态。
