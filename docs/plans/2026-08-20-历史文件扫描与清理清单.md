# 历史文件扫描与清理清单

## 任务

扫描本项目，找出以下三类问题，输出清理清单：

### 第一类：可删除的废弃文件

真正没人用、删了不影响运行的文件：
- 旧的临时脚本、调试脚本
- 已被替代但没删的旧版文件（不是 migration）
- 注释掉大量代码的"尸体文件"
- 重复的配置文件

### 第二类：不能删但会造成 AI 误导的文件（重点）

这类文件不能删除（比如 Supabase migration 是数据库变更历史，删了会破坏迁移记录），但它们会干扰 AI 搜索——AI 搜到旧版就以为是当前实现。

具体排查：
- supabase/migrations/ 里哪些 migration 修改过同一个函数/表，列出"当前生效版本"和"已被覆盖的旧版本"
- src/ 里有没有同名但不同版本的文件（比如 xxx-v1.ts 和 xxx-v2.ts）
- docs/ 里有没有内容已过期但文件名没有标记"废弃"的文档

### 第三类：入口缺失或路径不清晰

- 有没有功能存在但前端没有入口的（比如后端 API 写了但页面没调用）
- 有没有配置散落在多个位置但没有统一索引的

## 输出格式

每类输出一个表格：

| 文件路径 | 问题描述 | 建议处理方式 | 风险等级 |
|---------|---------|-------------|---------|

## 处理方式标注

- **删除**：确认无人引用，可安全删除
- **标记废弃**：文件名或文件头加 `[DEPRECATED]` 标记
- **加索引**：在 CLAUDE.md 或模块地图里补充"当前生效版本"的明确指向
- **不处理**：历史文件，保留但不需额外操作

## 特别注意

1. Supabase migration 文件**绝对不能删除**，只能标注"已被后续 migration 覆盖"
2. 扫描时不要只搜文件名，要检查**文件内容里的函数/表名是否被后续文件修改过**
3. 对于同一个函数出现在多个 migration 里的情况，要按时间戳排序，指明哪个是当前生效版本
