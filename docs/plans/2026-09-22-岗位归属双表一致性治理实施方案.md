# 岗位归属双表一致性治理实施方案（修订版）

## 目标

修复历史手稿编辑会清空日报负责人、会误关联视频、以及日报和视频半成功的问题；保留 `videos` 与 `daily_reports` 的不同作品集合，岗位管理继续按日报行计量。

## 本轮冻结范围（批次 0-2）

- 做生产只读基线；
- 历史编辑加载未完成或接口错误时禁止保存；
- 区分“有绑定视频”和“合法无绑定视频”；
- 读取侧不再按账号+日期猜视频；
- 历史编辑改走服务端权限校验后的历史编辑原子 RPC；
- 原子 RPC 同时覆盖日报字段、标题/正文同步和三岗位归属；
- 不新建第三张归属表、不做全量历史回填、不改投稿主链路、不执行生产写库。

## 明确不采用的方向

- 不以 `videos` 或 `daily_reports` 作为全局唯一主表；
- 暂不新建 `content_attributions`：当前没有闭合的作品身份，新增事实层会形成第三份副本，且必须同步投稿入口、RLS 和历史灌入，短期风险更高；
- 不把“无视频”视为编辑失败；日报-only 记录必须仍能修改指标和岗位。

## 已核实的当前问题

1. `src/app/(app)/dashboard/history-report-edit-form.tsx:522-528,647-667,892-899`：负责人初始为 `unassigned`，详情异步加载，保存按钮只受 `isPending` 控制；详情未完成时可提交空负责人。
2. `src/app/api/video-submit/edit-detail/route-core.ts:125-140`：`daily_reports.video_id` 为空时按账号和日期寻找视频；0 条返回 404，多条返回 409，恰好 1 条则把猜中的视频返回给表单。
3. `src/app/(app)/dashboard/actions.ts:107-173`：当前历史编辑先写 `daily_reports`，再单独写 `videos`，不是事务。
4. `supabase/migrations/20260907113000_daily_reports_video_link.sql:154-205`：现有 `update_collaboration_attribution` 有事务，但无绑定视频时仍按账号+日期猜视频；只允许 `service_role` 执行，并且限制 `report_date >= 2026-07-27`，不能直接覆盖全部历史编辑。
5. 投稿主链路在 `src/app/api/video-submit/route.ts`，本轮不改，但后续若引入归属事实层必须纳入该入口。

## 目标行为

```text
编辑详情状态：
loading              -> 禁止保存
ready_with_video     -> 可改日报，并在同一事务同步绑定视频
ready_without_video  -> 可改日报；不写、不猜视频
error                -> 禁止保存，可重试
```

## 批次 2：历史编辑专用原子写入

不要直接复用现有协作补录 RPC；新增版本化的历史编辑 RPC（通过 `supabase migration new` 创建 migration）。

建议函数：`update_history_report_edit_atomic`。

输入至少包括：

- `p_report_id`；
- `p_video_id` nullable；
- 日报可编辑字段（标题、正文、指标、发布时间等）；
- 三个负责人 UUID nullable；
- 调用方用户 ID/必要的服务端权限上下文。

事务规则：

- 锁定并校验日报归属、当前用户和可编辑范围；
- 必写 `daily_reports`；
- `p_video_id` 非空时，校验它等于日报绑定的 `video_id`，再同步 `videos.video_title`、`videos.content` 和三岗位负责人；
- `p_video_id` 为空时，只写日报，不猜视频、不创建绑定；
- 不限制 `report_date >= 2026-07-27`，覆盖历史编辑实际可见范围；
- 任一步失败整体回滚；
- 函数只授予 `service_role`，调用前由 Server Action 完成用户身份、账号归属和可编辑权限校验。

  - 处理无视频成功和事务失败两种返回。

完成条件：历史编辑不再绕过事务；不丢标题/正文同步；不误写无绑定视频；旧日期不被协作统计起点挡住。

## 验收结论与下一步（WorkBuddy 复核，2026-09-22）

### 一、已交付部分：验收通过，但不能单独上线

| 项 | 结果 |
| --- | --- |
| 工作区改动 | 2 个文件、+22/−2（`history-report-edit-form.tsx` 15 行、其定向测试 9 行） |
| `npm test` | 1738 通过 / 0 失败（本地实跑复现） |
| `npx tsc --noEmit` | 通过（本地实跑复现） |
| 「详情未就绪即保存 → 署名被空值覆盖」 | 已堵住 ✅ |

**阻断项 1：门禁依赖的「合法无绑定视频」状态还没做，上线即锁死 188 条日报。**

`fetchVideoSubmissionEditDetail`（`video-submit-panel-v2.tsx:92-94`）对无绑定视频的日报抛的是「该账号该日期没有可编辑的原视频」（404）或「存在多条视频，无法安全编辑」（409）。三态门禁把这两类都判为 `error` → 保存按钮永不可用。历史手稿列表只展示每人最近 30 条，生产实测其中 **188 条是 `video_id` 为空的日报（98 条带署名）**。保存被禁用是**整张表单**，连指标都改不了，与本文档「批次 1 完成条件：无视频日报不再被 404/409 卡死」直接冲突。代码是三态（`loading | ready | error`），方案要四态。

**阻断项 2：错误状态的重试是假的。**

失败被 `editDetailCache.set(cacheKey, null)` 缓存（`history-report-edit-form.tsx:638`），重新打开读同一缓存立刻回到 `error`，组件 key 变化也不清缓存。文案「请重新打开后重试」不成立，实际只能刷新整页。同一个弹层文件里早有解法：`video-submit-panel-v2.tsx:835-880` 把「没有可编辑」判为**合法缺失**（另给文案），只有真错误才给「重新载入」按钮（`setEditDetailRequestVersion` 版本号重试）。**应复用该判定，不要新造状态机。**

**阻断项 3：详情接口是双调用方，改返回值会波及投稿弹窗。**

`/api/video-submit/edit-detail` 同时被历史手稿（`history-report-edit-form.tsx:610`）与投稿面板重传模式（`video-submit-panel-v2.tsx:380`）调用。若把「无绑定视频」改成合法 200：历史手稿可编辑日报侧 ✅，但投稿弹窗会从「未寻得该日期的视频底稿」变成能进表单 ❌（那里的目的是重传视频，没有视频就没有可编辑对象）。**DTO 层表达「无绑定视频」，由调用方决定呈现**——方案批次 1 缺这一条。

**阻断项 4（次要）：锁的是整表，不是署名字段。**

方案要求「只有用户明确选择未指定才提交 `null`」，这需要后端支持「字段未提交 = 保留原值」。当前 `formData` 传 `""` → 后端 `|| null`，无法区分「未提交」与「明确清空」。前端门禁只是第一道闸，**后端拒绝空值覆盖**这道闸仍缺。
