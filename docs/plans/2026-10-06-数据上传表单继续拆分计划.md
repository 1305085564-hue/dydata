# 数据上传表单继续拆分计划（2026-10-06）

## 1. 目标

把首页数据上传表单的业务编排从单个 2146 行组件中继续拆出，降低后续修改和排错成本，同时保持现有页面、接口、数据口径和用户行为不变。

目标结果：

- `video-submit-form-v2.tsx` 只保留页面级状态组装、跨模块协调和渲染入口。
- 上传、OCR、提交、补交、人员选择、草稿恢复各有清晰的职责边界。
- 保留一份共享的 workflow/ui 状态，避免拆分后出现多份表单数据。
- 连续替换截图时，旧 OCR 响应不能覆盖新截图。
- 新建、异常补交、历史编辑、草稿恢复和质量检查行为不变。
- 主文件初步降到约 800–1100 行；最终以职责边界和回归结果为准，不以机械减行作为唯一验收。

## 4. 方案选择

### 采用：渐进式业务边界拆分

每一步只抽一个职责域，保留主组件作为协调层；新模块通过明确的输入、回调和共享 workflow dispatch 工作。

优点：

- 改动面小，容易逐步回滚。
- 保留已有 reducer、selectors、OCR task registry 和 UI 组件。
- 每个阶段都能做定向测试，不必一次性重写页面。

代价：

- 第一阶段会产生少量适配 props。
- 主文件不会一次降到很小，需要在阶段 4 再收口初始化和 JSX。

### 不采用：一次性重写为全新容器

这会同时改变状态、异步请求和页面接缝，回归面过大。

### 不采用：只把代码按行搬到多个文件

这种方式会保留原有耦合，只是换文件位置，不能降低维护成本。

## 7. 状态与数据流

- 页面持有唯一 `workflow`：`meta / fields / slots`。
- 页面持有唯一 `uiState)：提交中、补交弹窗、质量检查、已提交等 UI 状态。
- `upload-controller` 只产生上传/OCR 事件，不直接改多个 React state。
- `draft-controller` 只读当前 workflow/ui 必要字段并调用恢复 action。
- `assignee-controller` 只通过 meta 更新岗位和手工编辑标记。
- `submit-controller` 从当前 workflow 快照构造 payload，成功后按既有顺序触发 submitted、usage tracking、清草稿。
- 旧 task、旧 asset、旧草稿均以当前 key/requestId 为准，晚到结果直接丢弃。

## 8. 错误、空态和兼容行为

- 未选择账号：继续显示现有提示，不发上传或提交请求。
- 成员列表为空或加载失败：保留现有岗位默认值，不伪造成员。
- OCR 失败：保留截图资产，允许现有手工确认/重试路径。
- 上传取消或槽位删除：撤销本地 blob URL，忽略晚到响应。
- 提交失败：继续显示稳定错误文案，不清除用户输入和草稿。
- 补交申请失败：保留原表单和原始 `submissionPayload`，允许重试。
- 历史编辑缺少完整详情：继续阻止保存并使用现有错误提示。
- controller 初始化失败：页面不伪造成功状态，保留现有降级提示。

## 10. 风险、回滚和延期项

- 每个 Phase 单独提交，精确暂存点名文件；不使用 `git add .`、`git add -A` 或 `git add -u`。
- 任一阶段出现行为回归，先回滚该阶段 controller 接线，不回滚其他会话改动。
- 不调整维护性 baseline 上限；如需下调，交给复验方登记。
- 若 controller props 超过原组件复杂度，停止该阶段并改为先抽纯函数/domain，不强行拆组件。
- 历史编辑 DTO 合流、API route 持久化编排、数据库事务化列为后续独立任务。
- 当前工作区已有 UX 审计相关未提交改动，本计划不包含、不暂存、不提交。
