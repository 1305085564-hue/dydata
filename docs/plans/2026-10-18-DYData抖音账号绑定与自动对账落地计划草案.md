# DYData 抖音账号绑定与自动对账落地计划（草案）

> 状态：草案，供运营负责人、产品和 AI/技术共同评审。
> 本文只定义业务流程、接口边界、数据关系、里程碑和待核事项，不代表代码、数据库或生产配置已经施工。

## 0. 先看结论

本项目分两条通道推进：

1. **通道 1：账号授权与绑定**——让员工或指定操盘手把抖音账号安全绑定到 DYData 的业务账号。
2. **通道 2：数据自动同步与对账**——把官方返回的作品和指标送入现有日报、履约、视频复盘和选题关联链路。

推荐采用“先绑定、再同步、匹配后入账”的顺序：

```text
抖音授权
  → DYData 保存账号关系和授权状态
  → 定时任务拉取官方数据
  → 外部作品进入待同步/待关联层
  → 精确匹配成功后写入现有 videos / snapshots / daily_reports
  → 无法确认的作品进入待人工确认，不自动改履约
```

当前可以直接复用的 DYData 能力：

- `accounts`：现有业务账号归属；
- `videos`：作品标题、链接、发布时间和负责人；
- `video_metrics_snapshots`：24h/72h 指标快照；
- `daily_reports`：日报与业务日绑定；
- `fulfillment_records`：发布履约状态；
- `video_topic_claims`：作品与选题/子题关联。

当前不能当成已确认事实的内容：抖音网站应用审核状态、实际可用权限、视频数据接口字段、配额、粉丝门槛、Token 有效期和共享账号规则。它们必须先通过平台控制台和真实接口响应核实。

## 1. 目标、范围和成功标准

### 1.1 三个业务目标

| 目标 | 用户得到的结果 | 第一阶段成功标准 |
|---|---|---|
| 减少填报 | 发布后不再重复填写标题、发布时间和基础指标 | 绑定成功的试点账号能自动带回作品基础信息；不能自动带回时仍可手工提交 |
| 减少履约争议 | 以官方发布时间为依据，延迟识别也能继续对账 | 精确匹配的作品能进入现有履约判断；未匹配作品不被误判为已履约 |
| 沉淀账号趋势 | 负责人能看账号和作品的长期变化 | 在平台真实提供字段且权限通过后，按日保存可追溯的指标快照 |

### 1.2 本轮范围

- 账号绑定、授权状态、续签、撤销和多账号归属；
- 作品基础信息与可用指标的同步；
- 作品与现有 `videos`、`daily_reports`、`video_metrics_snapshots` 的安全关联；
- 48~72 小时延迟识别的对账候选方案；
- 未匹配、接口失败、平台审核延迟时的人工兜底；
- 运行日志、同步批次、失败重试和审计记录。

### 1.3 明确不纳入第一阶段

- 不承诺 5 秒完播率、留存曲线等未获平台确认的字段；
- 不自动替用户认领选题或绕过现有撞车检测；
- 不取消手工填报、补交申请和管理员审批；
- 不把抖音接口返回的异常直接改写成现有异常状态；
- 不做抖音发布、私信、评论、粉丝画像或内容创作能力；
- 不在没有真实平台权限和真实角色验收前上线全员使用。

## 2. 当前事实与前置条件

### 2.1 已确认的 DYData 约束

1. 作品主日期是 `videos.published_at` 的上海自然日。
2. 上传日只用于补交、审批、审计和核实先后。
3. `account_id + report_date` 是日报业务归属组合；当前有效作品级唯一约束是 `video_id`，同一账号同一业务日可以有多条日报，但每条必须绑定不同作品。
4. 同月且不超过 72 小时的普通提交可直接进入现有链路；跨月或超过 72 小时走补交申请。
5. 选题关系走 `video_topic_claims` 及现有认领/撞车规则。
6. 权限按当前公司范围收口：成员处理自己的账号和作品，管理员/公司所有者按现有角色处理本公司数据。
7. Vercel Cron 当前只承担既有保活和通知清理任务；抖音同步需要新增独立任务和独立观测。

### 2.2 交接文档中的平台声明

交接文档声称网站应用已创建并提交审核，并列出视频列表、发布时间、互动数据和账号趋势等字段。它们作为待核清单保留，不能替代以下证据：

- 控制台实际审核状态；
- 当前应用实际开通的权限名称；
- 每个 endpoint 的真实响应示例；
- 不同账号规模、内容状态下的返回差异；
- Token 过期、撤销、限流和错误码行为。

### 2.3 前置阻塞项

| 阻塞项 | 影响 | 解除证据 |
|---|---|---|
| 网站应用审核/转正状态不明 | 不能确定是否能发起正式授权 | 控制台截图或可审计后台状态 |
| 视频数据权限不明 | 不能承诺自动作品对账 | 真实测试账号的 endpoint 响应 |
| 用户数据权限和粉丝门槛不明 | 不能承诺账号趋势 | 真实授权账号的字段与错误码 |
| 多账号/共享账号模型不明 | 不能确定绑定页面和权限归属 | 平台规则＋业务负责人确认 |
| Token 生命周期不明 | 不能设计续签提醒和失效处理 | 授权、刷新、撤销实测 |

## 3. 推荐的产品决策（待负责人拍板）

以下是建议方案，不把未确认事项写成既定规则。

| 决策 | 推荐方案 | 原因 |
|---|---|---|
| 绑定入口 | 工作台首页提供主入口；首次填报时就地提示；账号管理抽屉可查看和续签 | 员工不用寻找设置页，日常工作流中能自然完成绑定 |
| 绑定粒度 | 一个 DYData 业务账号对应一个抖音授权关系；一个员工可管理多个业务账号 | 与现有 `accounts` 结构一致，避免用一个授权覆盖多个业务归属 |
| 公用大号 | 指定一名业务负责人完成授权，管理员可查看状态和发起更换 | 避免多人重复授权、离职后没人知道谁能续签 |
| 履约延迟 | D+0 首次拉取，持续追踪到 D+3；只有官方作品精确匹配后才自动恢复履约 | 允许平台延迟，但不因标题相似或模糊时间误判成功 |
| 选题关联 | 先自动推荐候选，员工一键确认；关联失败不阻断履约 | 作品是否发布与作品属于哪个母题是两个动作 |
| 异常兜底 | 自动同步失败、平台查不到或匹配不确定时，保留手工填报/补交入口 | 自动链路不能让员工失去完成业务的路径 |
| 首批范围 | 先做绑定和基础作品识别；趋势指标、深层播放数据等以平台实测结果为准 | 先解决真实填报和履约争议，再扩展分析能力 |

## 4. 通道 1：账号授权与绑定流程

### 4.1 用户流程

```text
员工进入工作台
  → 看到“绑定抖音账号”状态
  → 选择一个 DYData 业务账号
  → 查看用途、数据范围和解绑说明
  → 点击授权/扫码
  → 跳转抖音官方授权页
  → 回调校验成功
  → 显示账号名称、授权状态、最后同步时间
  → 后续到期前提醒续签
```

### 4.2 关键节点

| 节点 | 页面/服务行为 | 成功结果 | 失败结果 |
|---|---|---|---|
| B1 状态展示 | 查询当前用户可操作的 `accounts` 及绑定状态 | 用户知道哪些账号已绑定、待续签或失败 | 显示可解释的加载/失败状态，不伪造未绑定 |
| B2 创建授权意图 | 服务端生成短时 `state`，绑定当前用户、公司和 `account_id` | 得到一次性授权地址 | 参数非法、越权或重复意图返回结构化错误 |
| B3 官方授权 | 用户在抖音完成登录和数据授权 | 平台返回 `code/state` | 用户取消、权限不足、平台拒绝 |
| B4 回调换 Token | 服务端校验 `state` 后用 `code` 换取 Token | Token 加密落库，写入授权范围和过期时间 | 不保存半成品；记录失败原因和可重试状态 |
| B5 账号确认 | 用官方返回的账号标识和名称回读 | 绑定关系可展示 | 账号已被其他业务账号占用时进入冲突处理 |
| B6 续签/重签 | 到期前提醒，一键重新授权 | 原关系更新，历史同步记录保留 | 旧 Token 继续标记失效，不影响手工填报 |
| B7 撤销/解绑 | 仅允许有权限的操作者解除关系 | 停止自动同步，历史作品保留 | 不删除历史 `videos`、日报或快照 |

### 4.3 绑定状态

建议内部状态使用固定枚举：

```text
UNBOUND       未绑定
AUTHORIZING   授权进行中
ACTIVE        授权有效
EXPIRING      即将过期
EXPIRED       已过期，需要续签
REVOKED       用户或平台撤销
ERROR         最近一次授权/同步失败
```

页面只展示用户能理解的文案：未绑定、正常、即将续签、需要重新授权、同步异常。

### 4.4 通道 1 API 契约（建议）

统一错误格式：

```json
{
  "error": {
    "code": "AUTHORIZATION_REQUIRED",
    "message": "请重新授权抖音账号",
    "details": {}
  }
}
```

| 接口 | 用途 | 关键输入/输出 | 状态码 |
|---|---|---|---|
| `GET /api/douyin/accounts` | 查询当前用户可见业务账号及绑定状态 | 返回分页账号、绑定状态、展示名、过期时间、最后同步时间；绝不返回 Token | 200/401/403 |
| `POST /api/douyin/authorizations` | 创建一次授权意图 | 入参 `accountId`；返回短时授权 URL、过期时间、意图 ID | 201/400/403/409 |
| `GET /api/douyin/oauth/callback` | 接收平台回调 | 校验 `state`，换取 Token，重定向到结果页 | 302；失败转结果页并带机器码 |
| `POST /api/douyin/accounts/:bindingId/refresh` | 主动续签/重签 | 返回新的授权 URL 或已恢复状态 | 201/400/403/404/409 |
| `DELETE /api/douyin/accounts/:bindingId` | 解除自动同步 | 仅解除外部关系，不删历史业务数据 | 204/403/404/409 |
| `GET /api/douyin/accounts/:bindingId/sync-status` | 查看最近同步状态 | 返回最近批次、成功/失败计数、可读错误 | 200/403/404 |

### 4.5 通道 1 数据模型建议

建议新增独立的外部绑定表，不直接把 Token 塞进 `accounts`：

```text
douyin_account_bindings
- id
- company_id
- account_id                  → accounts.id
- authorized_by               → profiles.id
- platform_account_id         （平台 open_id/唯一账号标识，字段名待平台确认）
- platform_union_id           （如平台提供）
- display_name
- scopes                      （实际授权范围）
- access_token_ciphertext
- refresh_token_ciphertext
- access_token_expires_at
- status
- last_sync_at
- last_error_code
- last_error_at
- created_at / updated_at
```

约束建议：

- 同一公司内，同一 `platform_account_id` 不能同时绑定到两个业务账号；若业务确认允许共享，再改成“一个外部账号对应多个授权关系”；
- Token 只存服务端加密值；日志、前端响应、错误详情不得出现 Token；
- 所有查询必须带当前公司范围，成员只能操作自己有权限的业务账号；
- 删除绑定采用软失效/撤销状态，保留审计和历史同步记录。

## 5. 通道 2：自动同步与作品对账流程

### 5.1 推荐流程

```text
定时任务触发
  → 读取 ACTIVE 绑定
  → 按游标/时间窗口请求抖音接口
  → 校验第三方响应
  → 写入同步批次与外部作品暂存
  → 先按 platform_account_id + platform_video_id 精确去重
  → 尝试关联现有 videos
  → 精确匹配：更新/补齐作品和快照
  → 业务日按官方发布时间转上海日期
  → 进入现有日报/履约查询链路
  → 无法确认：进入待关联，不自动改履约
  → 重试、告警和人工处理均留审计
```

### 5.2 作品匹配优先级

| 优先级 | 匹配条件 | 自动动作 |
|---|---|---|
| M1 | 同一授权账号 + 同一平台作品 ID | 自动绑定到对应 `videos`，幂等更新基础信息/快照 |
| M2 | 同一授权账号 + 官方发布时间窗口 + 已有外部 ID 缺失的历史作品 | 只生成候选，不直接绑定；提示人工确认 |
| M3 | 标题、链接或时间相似 | 只做搜索建议，不能自动入账 |
| M4 | 无法确定 | 进入“待关联”，不写日报、不改履约 |

平台作品 ID 是后续自动化的唯一主键。标题、发布时间和链接只能用于辅助，不得作为唯一自动绑定依据。

### 5.3 对账状态

```text
DISCOVERED        已从平台发现
MATCHED           已精确关联现有作品
PENDING_REVIEW    待人工确认关联
RECONCILED        已进入日报/履约对账
UNAVAILABLE       平台暂时查不到/受限
FAILED            拉取或写入失败，可重试
IGNORED           明确不属于 DYData 业务范围
```

### 5.4 延迟对账规则（建议版本）

以官方 `published_at` 的上海自然日 D 为业务日：

| 时间 | 系统动作 |
|---|---|
| D 日 | 首次拉取；查到且 M1 匹配则进入正常链路 |
| D+1 | 再拉取一次，补齐作品和基础指标 |
| D+2 | 对仍未发现的作品继续追踪；显示“平台数据待确认” |
| D+3 | 最后一次自动追踪；M1 成功才允许自动恢复履约 |
| D+3 后 | 未匹配作品转人工补交/申诉，不自动判成功 |

这只是建议口径。若负责人决定“D+3 未找到即视为漏发”或“允许人工证明后恢复”，需要同步写入履约规则和员工 SOP。

### 5.5 现有业务写入边界

| 数据 | 自动链路可以做什么 | 不可以做什么 |
|---|---|---|
| `videos` | 精确匹配后补齐官方标题、链接、发布时间和外部 ID | 不覆盖人工已确认的业务归属，不因模糊匹配新建错误作品 |
| `video_metrics_snapshots` | 按平台返回字段写入对应观察批次；字段缺失保持 `null` | 不把“没有返回”写成 0，不臆造 5 秒完播等指标 |
| `daily_reports` | 仅在作品和业务账号关系明确时，生成或补齐可审计的日报关联 | 不因发现一条平台作品就直接覆盖已有日报；必须遵守 `video_id` 唯一约束 |
| `fulfillment_records` | 仅对 M1 精确匹配且满足最终规则的记录触发对账 | 不对 `PENDING_REVIEW`、`UNAVAILABLE`、`FAILED` 自动判定成功 |
| `video_topic_claims` | 提供候选题目和一键确认入口 | 不自动认领、覆盖他人认领或绕过撞车检查 |

### 5.6 通道 2 API 契约（建议）

| 接口 | 用途 | 关键输入/输出 | 状态码 |
|---|---|---|---|
| `POST /api/cron/douyin-sync` | 定时拉取所有到期绑定 | 仅 Cron 鉴权；支持批次上限、游标、重试；返回批次摘要 | 200/401/429/500 |
| `POST /api/douyin/bindings/:bindingId/sync` | 有权限用户主动同步一个账号 | 返回 `syncRunId`，不等待全部第三方请求完成 | 202/403/404/409 |
| `GET /api/douyin/sync-runs/:runId` | 查看同步批次 | 返回状态、计数、失败原因、下一次重试时间 | 200/403/404 |
| `GET /api/douyin/unmatched` | 查询待关联作品 | 分页返回外部作品摘要和候选 DYData 作品 | 200/403 |
| `POST /api/douyin/unmatched/:externalVideoId/link` | 人工确认绑定 | 入参 `videoId`，服务端重查公司范围和冲突 | 201/400/403/404/409 |
| `POST /api/douyin/unmatched/:externalVideoId/ignore` | 明确忽略外部作品 | 需要原因；保留审计 | 204/400/403/404 |
| `GET /api/douyin/accounts/:bindingId/metrics` | 查询已确认的账号趋势 | 分页/时间范围；只返回已授权且已保存字段 | 200/403/404 |

所有列表接口必须分页或有固定上限；所有写接口必须支持幂等键或以外部作品唯一键保证幂等。

### 5.7 同步批次与重试

建议新增：

```text
douyin_sync_runs

- requested_by / trigger_type
- window_start / window_end
- status
- discovered_count / matched_count / pending_count / failed_count
- cursor_before / cursor_after
- started_at / finished_at
- error_code / error_summary

douyin_external_videos
- id
- sync_run_id
- binding_id
- platform_video_id

- reconciliation_status
- first_seen_at / last_seen_at
```

原始响应只保留必要、脱敏和可追溯字段；不得把完整 Token、请求头或敏感原文写入数据库或日志。

## 6. 接口与安全要求

### 6.1 第三方响应

- 所有平台响应先做 schema 校验，再进入业务逻辑；字段类型、缺失值和分页游标都必须校验。
- 平台错误码映射为内部固定码，例如 `PLATFORM_PERMISSION_REQUIRED`、`PLATFORM_RATE_LIMITED`、`PLATFORM_TOKEN_EXPIRED`、`PLATFORM_DATA_UNAVAILABLE`。
- 不把平台原始错误直接展示给员工；页面展示可行动的中文提示。

### 6.2 权限

- 登录、公司归属、角色权限和目标 `account_id` 必须在服务端逐层校验。
- 成员只能绑定/续签/解绑自己的业务账号；管理员和公司所有者按当前公司范围处理。
- Cron 只能处理数据库中有效、未撤销且属于当前公司的绑定。
- 绑定、续签、解绑、人工关联、忽略、自动对账都写审计记录。

### 6.3 幂等、并发和限流

- 授权回调的 `state` 一次性使用并设短时过期。
- 同一绑定同一时间只能有一个活跃同步批次；重复触发返回已有 `syncRunId`。
- 外部作品以 `binding_id + platform_video_id` 唯一去重。
- 每次同步有固定页数、记录数、超时和重试上限；限流按退避重试，不无限循环。
- 第三方接口慢或失败时，员工仍能使用手工填报和补交流程。

### 6.4 观测

每次请求至少记录：`requestId`、路由、操作、操作者、绑定 ID、批次 ID、状态、耗时、发现/匹配/失败数量。禁止记录 Token、密码、完整授权码、请求正文和原始敏感响应。

## 7. 里程碑与交付物

| 阶段 | 目标 | 交付物 | 通过条件 |
|---|---|---|---|
| P0 平台核实 | 确认能不能做、能拿什么 | 权限/endpoint/字段/错误码矩阵；真实响应样本 | 平台事实不再靠猜测；未开放能力明确排除 |
| P1 契约设计 | 锁定内部边界 | 绑定表、同步批次表、外部作品表、API 契约、权限登记 | 产品、技术、权限口径一致 |
| P2 通道 1 试点 | 让少量账号完成授权和续签 | 绑定入口、回调、状态页、撤销/续签 | 至少两个不同角色、一个多账号场景实测通过 |
| P3 同步试点 | 只拉取并保存，不自动改履约 | Cron、批次、失败重试、待关联列表 | 重复拉取不重复写；错误可追踪；Token 不泄露 |
| P4 对账试点 | 精确匹配后进入现有链路 | 作品绑定、快照、日报/履约对账和人工兜底 | D+0~D+3 场景、查不到、重复、跨月场景通过 |
| P5 小范围推广 | 先让少量成员使用 | 员工 SOP、管理员处理说明、监控看板 | 连续运行稳定，人工兜底可用 |
| P6 全员推广 | 扩大使用范围 | 发布公告、培训、回滚方案 | 真实角色、线上版本和生产数据核对通过 |

### 7.1 每阶段固定验收证据

1. 平台能力证据：控制台权限、真实响应、错误码和配额。
2. 本地证据：契约测试、幂等测试、权限测试、迁移检查。
3. 线上证据：部署 SHA、健康检查、Cron 实际运行、同步批次和数据落库。
4. 真实角色证据：成员、管理员、公司所有者分别完成绑定、续签、查看、人工关联和兜底。

静态测试通过不能代替平台真实调用、生产数据核对或真实角色验收。

## 8. 待核事项清单

### A. 平台能力

- [ ] 网站应用是否已转正；当前审核状态和应用环境是什么？
- [ ] 授权入口是网页 OAuth、二维码还是其他形式？回调域名和安全要求是什么？
- [ ] 能否读取作品列表？是否包含平台作品 ID、标题、发布时间、链接？
- [ ] 能否读取播放、点赞、评论、分享、收藏、涨粉和账号趋势？每个字段的权限门槛是什么？
- [ ] 视频数据能力是否仍处于改造/白名单状态？
- [ ] 单账号最低粉丝量、企业认证和数据范围限制是什么？
- [ ] access token / refresh token 的有效期、刷新方式、撤销行为和错误码是什么？
- [ ] 速率限制、分页上限、单次时间范围和企业配额是什么？

### B. 产品口径

- [ ] 一个抖音账号是否允许绑定多个 DYData 业务账号？
- [ ] 公用大号由谁授权、谁负责续签、谁可以解绑？
- [ ] D+3 仍未找到作品时，状态是“待人工补交”还是“判定漏发”？
- [ ] 作品精确匹配后，是否自动创建日报，还是只补齐已有日报？
- [ ] 选题自动推荐是否第一阶段上线？推荐失败是否完全不影响履约？
- [ ] 自动同步期间，员工是否仍需上传截图作为人工证据？
- [ ] 哪些字段属于员工可见，哪些只给管理员看？

### C. 工程与运维

- [ ] 绑定关系是否需要公司级 `company_id`，当前 `accounts` 是否需要扩展归属字段？
- [ ] Token 加密密钥由哪个服务端变量管理，轮换和恢复怎么做？
- [ ] Cron 运行频率、单批上限、超时和退避上限是多少？
- [ ] 外部作品原始字段保留多久，谁可以查看失败详情？
- [ ] 需要哪些线上告警：Token 失效、连续失败、匹配率下降、平台限流、批次超时？

## 9. 当前建议的下一步

1. 运营负责人先确认第 3 节的产品决策，特别是入口、公用号归属、D+3 规则和人工兜底。
2. 技术侧拿到平台控制台权限后完成 P0 能力矩阵，不先写“假接口”。
3. P0 通过后，再冻结 P1 的表结构和 API 契约；若视频接口仍不可申请，则把第一阶段切为“账号绑定＋用户数据”，作品自动对账顺延。
4. 任何“自动判定履约”的实现，都必须以 M1 精确匹配和真实角色验收为前提。
