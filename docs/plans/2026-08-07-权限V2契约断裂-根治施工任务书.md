## 给阿禅的话（结论先行）

这次连环出错，**不是十几个独立的 bug，是同一个动作留下的十几颗雷**：上次删掉了「小组」这张表和 `profiles.group_id` 这一列，但全项目还有十几处代码在到处找「小组」，谁先被点开谁先炸。所以你才会「以为修完又冒新的」。

我们这次的做法是**删干净、不留小组**：把所有还在找「小组」的地方，一次性改成只认「团队」，然后用真实账号（老板 / 管理员 / 普通成员）挨个跑一遍确认不炸。跑完这一批，这类错误就从根上没了。

要注意：**这份文件只是方案，还没改任何东西。** 交给执行 AI 跑完、并且过了本文最后的「验收矩阵」，才算真正生效。数据库改动必须上线（跑 migration）后才生效，前端改动要部署后才生效——执行 AI 每步都会标清楚。

## 根因与目标

### 根因

迁移 `20260805120000_permission_v2.sql` 物理删除了 4 个对象：表 `groups`、表 `leader_daily_reports`、列 `profiles.group_id`、列 `profiles.access_level`；并把「数据范围」从权限 JSON 搬到独立列 `profiles.data_scope`（配套函数 `get_data_scope()`）。

但删除时**没有把所有依赖这批对象的下游一起改**：数据库函数、RLS 策略、页面加载器、API、前端 UI 各有一套逻辑，谁也没被当成「同一个发布单元」验收。于是删除动作在四个层面各自留雷。

### 目标（三条，缺一不算根治）

1. **删干净**：所有仍引用 `groups` / `group_id` / `content_items`（从未存在）/ 已删列的活代码，全部改掉或删掉，一个不留。
2. **收敛为一套规则**：数据范围判断只认 `data_scope` + `team_id`，只保留一个权威函数，其余全部调用它，不再各写各的。
3. **立卡门**：以后删/改表列的迁移，合并前必须过「真实库 + 真实角色」验收清单，否则「migration 成功」不算数。

### 唯一事实源（施工时的判断基准）

| 字段 | 唯一负责 | 说明 |
|---|---|---|
| `role`（owner/admin/member） | 身份粗分 | 只用于默认模板和 owner 直通，**不作为功能鉴权最终依据** |
| `permissions`（JSON） | 功能开关 | 能否进某功能只看它，经 `has_permission()` |
| `data_scope`（self/team/all） | 数据范围 | 能看多少数据只看它，经 `get_data_scope()` |
| `team_id` | 组织归属 | 配合 `data_scope='team'` 使用 |
| `groups` / `group_id` | **永久废弃** | 不重建、不兼容 |

### 一个必须显式处理的语义（不许静默改）

exemption 三个原子函数原来用「小组组长能审批本组申请」。删小组后，审批权必须**改判为按权限**（如 owner / 有 `manage_fulfillment` 或 `review_violations` 权限者），**不得**悄悄放宽成「谁都能批」或收紧成「只有 owner 能批」。执行 AI 要把新的审批边界写清楚，并在验收时用三种角色实测。拿不准就停下问阿禅。

## 施工方案（分阶段）

> 原则：先建一个权威可见范围函数，让所有 RPC 都调用它——这是「收敛为一套规则」的落点，也是防下次再裂的关键。每阶段独立可回滚。

### 阶段 0 · 止血（当天）

- 修 P0 `get_fulfillment_range`：`content_items` → `daily_reports`（发布计数来源）。
- 修 `资料加载.ts:68`：移除 `profiles.group_id` 选择（这是页面级活炸点）。
- 目标：管理员「发布管理」和相关后台页不再 42P01 / 未定义列报错。

### 阶段 1 · 数据库收口（一个发布单元）

1. 新建权威函数 `public.visible_user_ids()`：按 `get_data_scope()` 返回当前用户可见的 user_id 集合——`all`→全体，`team`→同 `team_id`，`self`→仅自己。
2. 在**同一个 migration** 里重写全部 P1 函数 + 2 条 RLS 策略：删除所有 groups/group_id 逻辑，改成 `where user_id in (select visible_user_ids())` 或等价的 team/data_scope 判断；exemption 三函数按上节语义重写审批权。
3. P2 传递性函数不单改，但纳入本单元一起验收。
4. 整个单元过阶段验收（见下）后才算完成，不许拆散上线。

### 阶段 2 · 应用层收口

- 删 `data-access-scope.ts:50` 旧 key 逻辑，改读 `data_scope`。
- 清 `fulfillment-page.ts` 的 group 维度、`history/route.ts` 与 `export-violations/route.ts` 的 `p_group_id` 入参。
- 删 `modules-content-v2.tsx` 的分小组 UI，保留团队维度。
- 清理各类型文件里的 `groupId` 残留占位。

### 阶段 3 · 错误可观测性

- 建统一 RPC 调用包装：服务端必记 `{RPC 名, error.code, 受影响模块}`；用户侧文案不泄露内部信息。
- 把当前约 70–80 处「直接吞错、只弹检查网络」的 catch 逐步收敛到该包装。目标：下次一眼能看出是 42P01（表/列不存在）还是 42501（RLS 拒绝）。

### 阶段 4 · 立卡门（防复发）

固化一份「数据库契约测试」清单为 PR 硬门槛：凡删/改表或列的迁移，合并前必须——
1. 对每个受影响函数取线上生效定义，核对其引用的表/列当前真实存在；
2. 用真实角色 + 真实参数把每个受影响 RPC 只读试跑；
3. 关键页面/接口冒烟。
「构建通过」「页面能打开」都不作为通过标准。

## 验收与回滚

### 验收矩阵（每格都要用真实库跑过）

- 行：本文清单里的全部函数（含 P2 传递性）+ 2 条 RLS 策略 + 受影响页面（发布管理 / 案例库收件箱 / 发布草稿审核队列 / 履约日历 / 豁免审批 / 后台成员管理）。
- 列：`owner` × `admin` × `member` 三种真实角色。
- 期望：能返数据 / 按范围返空 / 明确权限拒绝——**均不得抛数据库结构错误（42P01 / 42703）**。
- 附加：故意用一个越权角色触发拒绝，确认服务端日志里有 RPC 名 + error.code。

### 回滚

- **阶段 0 / 1（数据库）**：每个被改函数在施工前先存一份「当前生效定义」快照；回滚 = 重新 `CREATE OR REPLACE` 回旧定义（注意：回滚只是回到「现在这种坏」，不会更糟）。RLS 策略同理保存原策略体。
- **阶段 2 / 3（前端与 API）**：`git revert` 对应提交即可。
- **本任务书本身**：只是文档，删文件即撤销，无副作用。

### 交接边界（给执行 AI）

- 不许为了止血重建 `groups` 或放宽 RLS。
- 施工前先用线上库确认每个函数生效版本，别只信 migration 顺序。
- exemption 审批语义、以及任何会改变「谁能看/谁能批」的判断，必须写清楚并实测，拿不准就停下确认，不许静默决定。
