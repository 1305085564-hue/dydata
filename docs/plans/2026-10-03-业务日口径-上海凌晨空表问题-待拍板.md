# 2026-10-03 业务日口径：数据库按 UTC 记「今天」，上海凌晨 0—8 点整页空表

状态：**待阿禅拍板**（一句话就能开工：业务日是否定义为「上海日历日」）。本轮只取证与出方案，未改生产 SQL、未改函数。

## 一、现象（用户视角）

1. 每天 00:00–08:00，发布管理的「今天」列必然没有数据 —— 这段时间里成员即使发布了，也显示不出来。
2. 每月 1 日 00:00–08:00 打开发布管理，**整页空表**：这个月被判成"未来"，一条记录都不返回。
3. 同类风险面（同源判定，尚未逐个取证）：侧栏徽章、首页待提交、今日提交状态、排行榜、管理驾驶舱等 12 个数据库函数都在用同一个「今天」。

## 二、证据（全部实测，非推断）

- 本地与生产库 `show timezone` 均为 `UTC`；2026-10-03 01:06（上海）实测两边 `current_date = 2026-10-02`。
- 发布日历 RPC `get_fulfillment_range` 定义（`pg_get_functiondef` 实测）里有两处硬判定：
  - `range_end := least(p_end_date, current_date);` —— 区间上限被 UTC 的今天卡住；
  - `if p_start_date > range_end then return; end if;` —— 起始日超过上限就**直接返回零行**（不是返回部分数据）。
  于是上海 11 月 1 日 00:30 时，`p_start_date = 11-01 > range_end = 10-31` → 整月零行。
- 应用侧算「这个月」用的是上海时区（`resolveFulfillmentYearMonth` → `getShanghaiYearMonth`），页面默认视图「今天」用 `formatShanghaiDateOnly()`；**两边时钟不同源**，空表就是这个错位的直接结果。
- 引用 `current_date` 的生产函数（`pg_proc` + `pg_get_functiondef` 实测，共 12 个）：
  `get_fulfillment_calendar`、`get_fulfillment_range`、`get_today_submission_status`、`get_leaderboard_rows`、
  `admin_pending_submissions_today`、`admin_pending_submissions_today_v2`、`admin_pending_videos_today`、
  `admin_sidebar_badges_summary`、`admin_cockpit_summary`、`admin_cockpit_summary_v2`、
  `set_permanent_exemption_owner_atomically`、`clear_permanent_exemption_owner_atomically`。

## 三、为什么不能算「只是测试问题」

上一轮为了让角色门禁不红，把测试的月份改成按浏览器 UTC 推 —— 那是**绕开现象**，不是修因。本轮已经把测试改成读种子脚本落盘的时间锚点（`output/gate-roles-anchor.json`），测试不再依赖时钟；但线上用户看到的行为一个字都没变：阿禅们要在 1 号早上开月度全景，仍然是一片空白。

## 四、方案（推荐 A）

**A. 在这些函数里把「今天」显式定义为上海日历日**（改动集中在一个表达式，语义唯一）：

- 统一口径：把函数体内的 `current_date` 换成 `shanghai_today()` —— 新建一个 `immutable`? 否，用 `stable` 的辅助函数：

```sql
-- 建议迁移（未执行）。放在 supabase/migrations/<新时间戳>_business_day_shanghai.sql
create or replace function public.business_today()
returns date
language sql
stable
set search_path to 'public'
as $$
  select (now() at time zone 'Asia/Shanghai')::date
$$;

-- 然后逐个把 12 个函数体内的 current_date 替换为 public.business_today()。
-- 替换必须逐函数重写完整定义（pg_get_functiondef 取当前线上定义为准，勿用仓库迁移链重建）。
```

- 为什么不设 `role`/`database` 时区：改 `timezone` 会话参数会影响 `timestamptz` 的展示与 `::date` 隐式转换，波及面不可枚举；只在"业务日"这一个概念上收口，风险可控且可回滚（`drop function public.business_today()` 前需先还原引用它的函数）。

**B. 应用层把日期当参数传进去，库不再自己算「今天」**：更彻底，但要动 12 个函数签名 + 所有调用点，本轮不推荐。

## 五、验收清单（拍板后按此执行，不接受"看起来好了"）

1. 生产只读核对：逐函数 `pg_get_functiondef` 留存改前定义（回滚依据）。
2. 单测/集成：注入"上海 1 日 00:30"的时刻，断言 `get_fulfillment_range` 返回零行的分支被绕开（改后该月首日应返回该月已有数据，而不是零行）。
3. 真机复验：在 00:00–08:00 窗口内用组长与组员各一个账号打开发布管理，确认「今天」列与月度矩阵都有数据。
4. 数字对账：改动前后的**日报提交时间归属**是否变化（例：上海 23:30 提交、UTC 已跨日的记录），确认对"应发/实发"口径无追溯影响。
5. 受控上线：单个迁移手工 apply + 登记 `supabase_migrations.schema_migrations`（`on conflict do nothing`），**禁止 `supabase db push`**。

## 六、需要阿禅回答的一句话

「我们的业务日是不是上海日历日？」

- 是 → 按方案 A 做，12 个函数一次收口，凌晨不再空表；
- 否（例如按 UTC 记） → 那要改的是应用侧（页面月份、"今天"标签都改成 UTC 口径），且后台数字会与员工体感差 8 小时，需要明确公告口径。
