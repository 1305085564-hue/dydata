## 一、时间效率分析

### 耗时分布

| 阶段 | 预期 | 实际 | 偏差 | 原因 |
|------|------|------|------|------|
| 诊断和设计（10:00-18:00） | 2小时 | 8小时 | +300% | owner 权限边界模糊，方案反复调整 |
| 代码实现（18:00-04:45） | 4小时 | 11小时 | +175% | 856行 migration 复杂度超预期 + 多轮修复 |
| Migration 对账（13:30-18:25） | 2小时 | 5小时 | +150% | 16个漂移 migration + knowledge_cases 阻塞 |
| 生产写入（18:25-21:45） | 2小时 | 3小时 | +50% | 逐步执行 + 刷新 schema cache |
| 真实角色验收（21:45-22:10） | 0.5小时 | 0.5小时 | 0% | 最后阶段提示词清晰 |

### 最大时间黑洞

**黑洞 1：诊断和设计阶段（预期 2 小时 → 实际 8 小时，+300%）**

- **问题：** owner 角色同时管公司和集团，权限边界模糊，方案在"剥离集团属性"和"保留集团属性"之间反复
- **具体表现：**
  - 10:00-12:00 初步诊断，发现 manage_system 被锁死
  - 14:00-16:00 设计 company_role 方案
  - 16:00-18:00 编写 migration
  - 直到第二天 11:51 才发现 P1 阻塞：集团资格表无发放路径，方案需要调整
- **根因：** 没有在设计阶段穷举所有边界条件，导致实现阶段才发现方案缺陷
- **改进：** 设计阶段必须做"边界条件穷举清单"，特别是：谁能做 X？谁不能做 X？如果没有人能做 X 怎么办？

**黑洞 2：代码实现阶段（预期 4 小时 → 实际 11 小时，+175%）**

- **问题：** 856行 migration 文件复杂度远超预期，且凌晨多轮修复消耗大量时间
- **具体表现：**
  - 01:13 修复 visibleUserIds 误用
  - 01:30 修复 owner 被旧 data_scope 限制
  - 03:40 权限模型本地收口
  - 04:00 新增集团表显式拒绝策略
  - 04:20 前端权限入口修复
  - 04:35 迁移安全复核：移除 permissive deny policy
  - 04:40 新表权限再明确
  - 04:45 最终本地验收
- **根因：** 一个 migration 文件承载了太多功能（新表、新字段、新函数、数据回填、RLS 策略），任何一处修改都需要重新验证整个文件
- **改进：** 856行的 migration 应该拆成 5-8 个独立 migration，每个只做一个原子操作

**黑洞 3：Migration 对账（预期 2 小时 → 实际 5 小时，+150%）**

- **问题：** 16个漂移 migration 的状态判定复杂，且遇到 knowledge_cases 缺失阻塞
- **具体表现：**
  - 需要逐个判定：已执行未记账 vs 部分执行 vs 未执行
  - knowledge_cases 缺失导致按止损规则暂停
  - 需要幂等恢复后再继续
- **根因：** 没有提前建立 migration 状态分类标准，导致逐个 case-by-case 判断
- **改进：** 对账前先建立分类矩阵（已执行/部分执行/未执行 × 记账/未记账），批量处理

### 改进建议

1. **提前拆分任务：** 超过 4 小时的任务必须拆成多个独立对话
2. **设计阶段穷举边界：** 不要等到实现阶段才发现方案缺陷
3. **Migration 原子化：** 每个 migration 只做一个操作，不超过 200 行
4. **对账建立分类矩阵：** 批量处理，不要逐个 case-by-case
5. **验收明确禁止自动化：** 手工任务必须写"不要写脚本""不要自动化"

## 二、上下文压缩分析

### 压缩触发点

Codex 在第二天下午 3 次压缩上下文，分别在：

1. **第一次（约 15:00）：** 第一批生产写入后，累积大量 SQL 查询结果和 migration 执行日志
2. **第二次（约 17:00）：** 验收开始前，携带所有历史上下文（诊断 + 设计 + 实现 + 对账）
3. **第三次（约 18:00）：** knowledge_cases 阻塞处理后，新增大量错误处理和恢复日志

### Token 消耗大户

1. **SQL 查询结果：** 每次生产查询返回完整 JSON（pg_policies、pg_class 等），单次查询 500-1000 行，累积 10+ 次查询
2. **Migration 文件内容：** 856行的 migration 文件被多次全文引用（至少 3 次）
3. **测试输出：** 全量测试 1123 项的完整输出被保留在上下文中
4. **错误处理日志：** knowledge_cases 阻塞、幂等恢复等详细日志

### 改进建议

1. **SQL 查询结果只保留摘要：** 不要把完整 JSON 放进上下文，只保留关键行数和状态
2. **Migration 文件只读一次：** 后续用摘要替代全文（"856行，包含 X 表、Y 函数、Z 策略"）
3. **测试输出只保留失败项：** 全量测试输出只保留失败的 5 项，不要保留通过的 1118 项
4. **提前拆分对话：** 生产写入和验收应该是两个独立对话
5. **每 4 小时强制拆分：** 不管任务是否完成，超过 4 小时就开新对话

## 三、提示词设计分析

### 失败案例：第二批验收

**原始提示词问题：**

```
你负责真实角色验收与证据采集。
用 owner / admin / member 三类真实会话做页面和 API 验收。
```

**AI 理解：** "我要搭建完整的自动化测试框架"
**实际行为：** Codex 花了 1.5 小时搭建 Playwright 自动化环境，而不是直接手工测试
**应该这样写：**

```
你负责手工测试，不要写脚本，不要自动化。

第一步：打开浏览器
第二步：输入邮箱和密码
第三步：点登录
第四步：点"系统设置"
第五步：记录能不能打开

就这么简单，不要复杂化。
```

### 成功案例：第一批生产写入

**提示词特点：**

- 明确顺序："先 A，再 B，最后 C"
- 明确禁止："不要批量，不要跳过"
- 明确输出格式："每一步后立刻复查"

**结果：** Codex 严格按顺序执行，没有过度工程化

### 失败案例：截图验收

**原始提示词问题：**

```
验证截图权限边界
```

**AI 理解：** "我要验证所有可能的截图路径和权限组合"
**实际行为：** 尝试了多种路径组合，遇到 400 误判为权限问题
**应该这样写：**

```
只验证这一个路径：/api/screenshots/xxx
预期结果：
- 本人请求 → 307（跳转签名地址）
- 越权请求 → 403
- 未登录 → 401
- 如果返回 400，是文件不存在，不是权限问题
```

### 改进原则

1. **用祈使句，不用描述句：** "点登录" > "需要登录"
2. **列出具体步骤，不要抽象目标：** "第一步...第二步..." > "完成验收"
3. **明确禁止，不要依赖推理：** "不要写脚本" > "手工测试"
4. **给出示例，不要让 AI 猜：** 附上 curl 命令示例
5. **明确错误含义：** "401 = 未登录，403 = 权限拒绝，400 = 文件不存在"
6. **给出时间上限：** "20 分钟内完成，超时立刻停下"

## 四、任务拆分分析

### 拆分决策点

| 时刻 | 状态 | 决策 | 结果 |
|------|------|------|------|
| 第一天晚上 22:00 | Antigravity 完成代码 | 不拆分，继续验收 | 上下文开始膨胀 |
| 第二天凌晨 04:45 | Codex 完成本地验收 | 不拆分，继续生产写入 | 上下文继续膨胀 |
| 第二天下午 17:36 | Codex 完成生产 migration | 拆分：主线 + 验收分支 | 加速完成 |
| 第二天晚上 21:45 | 部署完成 | 拆分：验收独立对话 | 30 分钟完成 |

### 应该提前拆分的信号

1. **预期超过 4 小时的任务：** 第一天晚上就应该拆分
2. **需要切换工具或环境的任务：** 代码编写 → 浏览器测试，应该拆分
3. **有明确交付物的独立模块：** 生产写入的快照文件，应该拆分
4. **上下文开始膨胀：** SQL 查询结果累积超过 5 次，应该拆分
5. **AI 开始"遗忘"之前的内容：** 这是上下文压缩的前兆

### 拆分粒度

- **太粗：** 所有工作在一个对话（导致压缩）
- **太细：** 每个小步骤一个对话（导致协调成本高）
- **合适：** 按"独立交付物"拆分

**推荐拆分方案：**

1. 对话 1：诊断和设计（2-3 小时）
2. 对话 2：代码实现（3-4 小时）
3. 对话 3：本地测试（1-2 小时）
4. 对话 4：生产 migration 对账和执行（2-3 小时）
5. 对话 5：部署和验收（1-2 小时）

## 五、沟通成本分析

### 重复沟通

从日志中提取的典型重复沟通模式：

1. **"AI 理解错误，需要重新解释"：** 至少 5 次
   - owner 权限边界反复解释
   - 集团模式 vs 公司模式的区别反复说明
   - 截图权限的 307/400/403 含义反复澄清

2. **"AI 等待用户许可，其实已授权"：** 至少 3 次
   - Codex 问"可以执行这个 migration 吗"——已经说过可以
   - Codex 问"可以修改这个文件吗"——已经说过可以
   - Codex 问"可以重启服务吗"——已经说过可以

3. **"AI 做了不需要的工作"：** 至少 4 次
   - 搭建 Playwright 自动化环境（应该手工测试）
   - 尝试所有可能的截图路径（应该只测一个）
   - 生成详细的测试报告（应该只记录结果）
   - 尝试连接数据库直连（应该用 Management API）

### 常见误解

1. **"可以用浏览器吗"：** AI 以为需要许可，其实已授权
2. **"找不到密码"：** AI 不知道可以重置或用 service role 创建
3. **"这个 migration 要执行吗"：** AI 不确定，其实已经确认过
4. **"需要回滚吗"：** AI 遇到错误就想回滚，其实应该继续

### 改进建议

1. **提示词开头明确授权：** "你已被授权使用账号 X，直接登录，不需要再问"
2. **提前列出备选方案：** "密码不对就试这几个，还不对就写'未验证'"
3. **明确决策边界：** "遇到错误先诊断，不要自动回滚"
4. **给出"不要问"清单：** "以下操作不需要问许可：执行 migration、修改文件、重启服务"

## 六、错误处理分析

### 误判案例

**案例 1：验证截图时全返回 401**

- **AI 判断：** 权限不对，验收失败
- **实际原因：** 登录态过期
- **改进：** 提示词应该说"如果返回 401，先确认是否已登录，不要直接判断为权限失败"

**案例 2：截图返回 400**

- **AI 判断：** 权限不对
- **实际原因：** 文件不存在（283 行中个别对象损坏）
- **改进：** 提示词应该说"307 = 权限通过，400 = 文件不存在，403 = 权限拒绝"

**案例 3：knowledge_cases 缺失**

- **AI 判断：** migration 失败，需要回滚
- **实际原因：** 历史 migration 已执行但表被删除
- **改进：** 提示词应该说"如果表不存在，先查历史 migration 是否已执行"

**案例 4：组员系统设置 API 返回 404**

- **AI 判断：** 权限不对
- **实际原因：** API 路由不是页面，不能用浏览器直接访问
- **改进：** 提示词应该说"API 路由用 curl 测试，不要用浏览器"

### 错误处理原则

1. **明确区分错误类型：** 环境问题 / 配置问题 / 功能问题
2. **给出诊断清单：** "如果 401，检查登录态；如果 403，检查权限；如果 400，检查文件是否存在"
3. **不要自动回滚：** 遇到错误先诊断，确认是功能问题再回滚
4. **记录错误但继续：** 非关键错误记录后继续执行，不要停下

## 九、给未来的建议

### 遇到类似任务时

1. **先拆分再开始：** 不要等上下文压缩了才拆
2. **提示词写 3 遍：** 第一遍写完整，第二遍删废话，第三遍加禁止项
3. **明确时间上限：** "20 分钟内完成，超时立刻停下"
4. **预留缓冲时间：** 预期 X 小时 → 实际可能是 2X
5. **设计阶段多花时间：** 设计阶段多花 1 小时，实现阶段少花 3 小时
6. **验收阶段用对的工具：** 手工测试用 Claude Code，自动化测试用 Codex

### 经验数据

- 极难任务预期时间 × 2 = 实际时间
- 每 4 小时对话 = 建议拆分点
- 验收类任务容易被过度工程化（× 3-4 倍时间）
- 856行 migration 文件 = 至少拆成 5 个原子文件
- 16个漂移 migration 对账 = 至少需要 3 小时
- 上下文压缩阈值 ≈ 100K tokens（约 4 小时连续对话）

### 提示词模板

**验收类任务：**

```
你负责手工测试，不要写脚本，不要自动化。

测试目标：[具体功能]

3. [第三步]
```

```
- 每步执行后立刻复查结果

- 记录每步的执行时间和结果
```
