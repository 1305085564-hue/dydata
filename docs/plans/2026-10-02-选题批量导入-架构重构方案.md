**日期**：2026-10-02  
**所属总方案**：`docs/plans/2026-10-02-全站架构体检报告-性能稳定性安全合并版.md`  
**状态**：建议施工，唯一已核实的业务缺陷  
**性质**：一次性修正导入结果语义；不引入会话表、断点续传或第二套批处理系统。

## 一、最终判断

初版提出的五个问题中，只有“批次计数更新失败导致接口 500”成立：

- `src/lib/topics/import.ts:437` 已经得到实际成功数；
- `:447-449` 更新 `topic_import_batches` 失败后抛异常；
- 选题数据已经入库，但接口返回 500；
- 用户会把“观测台账失败”误判成“业务导入失败”，随后重复导入。

其余初版方向不施工：

- confirm 阶段重新校验是浏览器输入不可信时的安全防线，不能删除；
- 批量失败后的逐行重试已有成功/跳过/失败分类，当前不证明需要新会话系统；
- `topic_import_batches` 当前只有写入，没有读取方，不能为了“架构完整”新增 session 表、重试接口或 cron；
- 前端预览/确认编排已有明确边界，不做无证据的重构。

## 二、施工内容

### 2.1 服务端结果处理

修改：

```text
src/lib/topics/import.ts
```

在批次台账更新失败时：

1. 不再抛出会让接口变成 500 的异常；
2. 记录结构化运行错误，至少包含 `batchId`、导入操作、错误信息和 requestId；
3. 继续返回已经计算出的 `successCount`、`skippedCount`、`failedCount`；
4. 不新增响应字段，不改变 `confirm/route.ts` 当前响应契约；
5. 明确记录：选题业务写入成功，批次台账计数属于非阻断观测失败；
6. 台账计数不作为最终业务事实，最终对账以 `sub_topics.import_batch_id` 聚合为准。

本次施工必须接入全站运行架构方案定义的统一观测能力。如果运行观测基础层尚未完成，不得伪造不存在的 API；临时日志必须在技术债台账中登记，待 `src/lib/observability.ts` 落地后立即迁移。

### 2.2 测试必须改写现存错误用例

现有测试已经有相反预期：

```text
src/lib/topics/import.test.ts:345-358
```

该用例当前断言“批次计数更新失败时抛错”。施工时不是“新增一个测试”而是必须改写这条旧用例：

- 断言 `executeTopicImport` 不抛异常；
- 断言成功/跳过/失败计数仍等于实际写入结果；
- 断言批次更新错误被记录；
- 断言响应结构不增加新字段；
- 断言 confirm API 仍返回既有字段。

### 2.3 明确不做

- 不删除 confirm 阶段服务端重校验；
- 不改批量插入失败后的逐行重试策略；
- 不新增 `topic_import_sessions`；
- 不新增断点续传、失败行重试 API 或 cron；
- 不引入 migration；
- 不增加没有消费者的 `ledgerWarning` 响应字段。

## 三、验收

### 3.1 单元和静态验收

```bash

```

### 3.2 真实行为验收

使用真实本地数据验证：

1. 选题实际写入成功、批次 update 成功：返回既有成功结果；
2. 选题实际写入成功、批次 update 失败：仍返回业务成功结果，日志可定位；
3. 选题写入失败：仍按现有失败分类返回，不能被本次改动吞掉；
4. 重复导入：现有唯一约束和 skip 语义不改变；
5. 前端不出现“导入失败但实际已入库”的误导。

### 3.3 回滚

本次无数据库变更，前后端契约不变，可通过回滚应用 commit 恢复原行为。但原行为会重新出现“业务成功却返回 500”的错误语义，回滚只能用于发现新回归时临时恢复，不能作为最终完成状态。

## 四、与全站架构方案的关系

本方案是全站方案“核心业务结果与观测/后置状态分离”的第一个导入域落地。当前单点修复不扩展为完整结果对象，但必须在全站运行观测层完成后迁移到统一的 `businessSucceeded` / `compensationRequired` 语义，避免导入、审批、分配各自发明结果格式。

**完成定义**：旧测试改写、批次失败不再误报业务失败、实际结果和日志可追踪、无新增无消费者契约、全量测试通过。
