# 首页数据上传架构优化方案（2026-10-01）

## 目标

把首页“数据上传”从一个 3110 行的客户端巨型表单，收敛为清晰的“状态机 + OCR 任务 + 提交服务”三层，降低 OCR 回写错位、草稿恢复污染、重复提交、接口部分成功和历史编辑口径漂移的概率。

成功标准：

- 同一个截图槽位连续替换或重试时，旧 OCR 结果不能覆盖新截图。
- 页面只通过一个规范化提交模型向服务端提交；创建、补交、编辑的差异由服务端明确判定。
- `videos`、`video_metrics_snapshots`、`daily_reports`、标签写入失败时，用户能得到稳定错误码，数据库不会留下半成品。
- 首页主表单与历史编辑不再各自维护发布时间、标题和指标保存规则。
- 现有正常提交、补交、编辑、OCR 失败手填、草稿恢复、权限校验行为保持不变。

## 当前事实与调用链

### 现有链路

`src/app/(app)/dashboard/production-control-system.tsx`
→ `VideoSubmitPanelV2`
→ `src/app/(app)/dashboard/video-submit-form-v2.tsx`
→ 上传截图到 `submission-screenshots`
→ `POST /api/ocr-screenshot`
→ 客户端把 OCR 结果拆回 `meta / fields / slots`
→ `POST /api/video-submit`
→ 写入 `videos`、`video_metrics_snapshots`、`daily_reports`、`video_tags`
→ `onSubmitted` 回写首页本地摘要。

历史编辑还有另一条链路：

`VideoSubmitPanelV2`
→ `HistoryReportEditForm`
→ `submitReport` Server Action
→ `update_history_report_edit_atomic` RPC 或直接写 `daily_reports`，再同步视频和 24h 快照。

### 已确认的结构风险

1. `video-submit-form-v2.tsx` 约 3110 行，同时承担状态、草稿、OCR 上传、槽位调换、指标回填、责任人、选题、提交、补交申请、质量检查和渲染。
2. 表单有大量相互独立的 `useState`：`meta`、`fields`、`slots`、`hasManualEdit`、责任人、草稿、质量检查、提交状态等。状态更新依赖 `metaRef`、`slotsRef` 和多个回调，容易出现“显示值、草稿值、提交值”不同步。
3. `handleSlotUpload` 从第 1354 行起同时负责文件预览、Storage 上传、OCR 请求、结果归槽、槽位自动调换、指标回填和错误降级。当前没有按槽位的请求序号或取消机制；同一槽位快速重试时，旧请求返回后可能覆盖新请求。
4. 客户端先完成多步写入，再由 `src/app/api/video-submit/route.ts` 用补偿闭包回滚。该路由约 997 行，包含门禁、权限、视频写入、快照写入、日报写入、标签写入、AI 标签和回滚，失败边界多。
5. 创建/补交/编辑在客户端通过 `SubmitPanelMode` 映射为服务端 `create/edit/abnormal`，规则分散在 `video-submit-form-state.ts`、`video-submit-deadline.ts`、`validation.ts` 和路由内，新增字段容易漏同步。
6. 首页主表单和 `history-report-edit-form.tsx` 都维护标题、发布时间、指标和草稿，但保存入口不同，存在字段契约漂移风险。
7. OCR 结果契约已在 `ocr-contract.ts`，但客户端仍直接读取 `recognized_fields` 的动态对象，字段名错误只能到运行时暴露。

## 推荐方案

采用“渐进式边界收口”，先解决高频错误源，再考虑数据库事务化：

- 第一优先级：提取纯状态机，统一表单状态和可提交选择器。
- 第二优先级：提取带请求隔离的 OCR 任务服务，禁止旧响应覆盖新截图。
- 第三优先级：把 `/api/video-submit` 的输入门禁、持久化步骤和错误码拆层；短期保留现有补偿回滚，避免直接引入大 migration。
- 第四优先级：让历史编辑复用同一份字段契约和保存服务，逐步下线重复保存逻辑。

不建议第一轮直接重写成全新页面或一次性把所有写入改成数据库 RPC。当前链路已经有大量真实角色、截图资产和历史编辑兼容逻辑，大爆炸重构会扩大回归面。

## 文件地图

### 新建

- `src/lib/video-submit-workflow/types.ts`：统一 `create / backfill / edit / abnormal`、字段来源、槽位状态、错误码和提交 DTO。
- `src/lib/video-submit-workflow/reducer.ts`：用事件驱动更新 `meta / fields / slots / submitStatus`，所有更新保持不可变。
- `src/lib/video-submit-workflow/selectors.ts`：提供 `buildSubmissionPayload`、`summarizeIssues`、`canSubmit`、`isDraftEmpty` 等纯函数。
- `src/lib/video-submit-workflow/ocr-task.ts`：管理每个槽位的请求序号、AbortController、上传资产与 OCR 结果绑定。
- `src/lib/video-submit-workflow/*.test.ts`：覆盖替换竞态、重试竞态、草稿恢复、OCR 失败手填、字段来源和模式转换。
- `src/app/api/video-submit/persist.ts`：承载视频、快照、日报、标签的持久化顺序和补偿动作，路由只负责鉴权、门禁和响应映射。

### 修改

- `src/app/(app)/dashboard/video-submit-form-v2.tsx`：第一阶段改为 reducer + selectors；第二阶段只调用 OCR task；第三阶段只组装规范 DTO 和渲染。
- `src/app/(app)/dashboard/video-submit-panel-v2.tsx`：只保留日期、账号、编辑详情加载和面板级视图状态，移除与表单保存规则重复的判断。
- `src/app/(app)/dashboard/video-submit-form-model.ts`：兼容迁移期间的初始值和编辑回填，最终收敛到 workflow types。
- `src/app/(app)/dashboard/video-submit-form-state.ts`：保留 UI 展示辅助函数，删除与提交契约重复的模式和 DTO 规则。
- `src/app/api/ocr-screenshot/ocr-contract.ts`：将动态 `recognized_fields` 收敛为版本化字段解析结果，并保留未知字段隔离。
- `src/app/api/video-submit/validation.ts`：只做请求 schema 和边界校验，不再承担持久化策略。
- `src/app/api/video-submit/route.ts`：保留鉴权、scope、deadline 和稳定错误码，调用 `persist.ts`。
- `src/app/(app)/dashboard/history-report-edit-form.tsx`：复用统一字段 DTO、时间事实策略和错误码。
- `src/app/(app)/dashboard/actions.ts`：与统一保存服务对齐历史编辑字段，保留已有权限和 RPC 兼容分支。
- `src/app/api/video-submit/*.test.ts`、`src/app/(app)/dashboard/*.test.ts`：将竞态、契约和持久化失败场景补为行为测试。

### 保持不变

- `src/app/api/ocr-screenshot/input.ts` 的 Storage 越界校验。
- 现有 `submission-screenshots` 私有桶和访问权限。
- 现有 `video-submit-deadline.ts` 的业务口径：真实发布时间超过 72 小时才需要补交，跨月不单独触发。
- 与本次首页上传无关的管理端视频复盘、选题库和豁免日历。

## 分阶段实施

### Phase 0：建立基线

- [ ] 固定正常首次提交、跨月 72 小时内、超过 72 小时、编辑、异常提交五组请求样例。
- [ ] 固定 OCR 成功、OCR 失败后手填、同槽位快速重试、两槽位同时上传四组浏览器场景。
- [ ] 验收条件：现有定向测试、`tsc`、静态门禁均能在改造前复跑。

### Phase 1：状态边界收口

- [x] 创建 workflow types、reducer、selectors，并把现有 `meta / fields / slots` 映射为一个 `SubmissionWorkflowState`。
- [x] 先让旧 UI 继续渲染，只替换 `updateMeta`、`updateField`、`updateSlotsState` 和 `restoreDraft` 的内部实现。
- [ ] 把 `buildSubmissionPayload`、`summarizeIssues` 和草稿序列化移出组件（本轮先移出状态构造与截图资产选择器，提交 DTO 与摘要函数留在下一小步）。
- [x] 验收条件：表单组件中的业务状态 `useState` 减少 2 个，`npm test`、`tsc` 与新增 workflow 定向测试通过；剩余 DTO/摘要迁移继续在 Phase 1。

### Phase 2：OCR 请求隔离

- [x] 每个槽位生成递增 requestId；开始新上传、重试或删除时使旧 requestId 失效。
- [x] OCR 响应提交前校验 requestId、asset URL 和当前槽位文件是否仍匹配。
- [x] 使用 AbortController 中止可取消的 OCR 请求；不可取消的服务端响应也必须被丢弃。
- [ ] 将“识别结果归槽”和“指标/标题/发布时间回填”变成 reducer 事件，禁止异步函数直接多处 setState。
- [ ] 验收条件：旧响应不能覆盖新截图；两槽位并发、自动调换、失败后重试均有行为测试。

### Phase 3：提交服务拆分

- [ ] 从 `route.ts` 提取 `persist.ts`，固定写入顺序：视频 → 24h 快照 → 日报 → 标签。
- [ ] 每一步返回稳定的内部错误码和可回滚快照；路由统一映射用户文案。
- [ ] 把编辑模式的不可变事实字段（发布时间、原视频绑定、历史快照）在服务端统一保留。
- [ ] AI 标签生成从核心写入路径移出为提交后可重试步骤；AI 失败不能让已完成的核心日报变成假失败。
- [ ] 验收条件：每个写入失败点都有单测；核心三表不出现半成品；失败响应可区分“核心保存失败”和“标签补充失败”。

### Phase 4：历史编辑合流

- [ ] 让 `HistoryReportEditForm` 与 V2 使用相同的字段 DTO、时间事实策略和错误码。
- [ ] 保留旧 Server Action/RPC 作为兼容后端，但由统一适配层调用，避免两套字段拼装。
- [ ] 当 V2 与历史编辑的行为测试稳定后，再删除重复的 `PublishedAtPicker`、草稿字段和重复校验。
- [ ] 验收条件：历史编辑不改发布时间；标题/指标/文案保存行为与首页编辑一致；无绑定视频仍按既有规则提示。

## 风险与回滚

- 第一阶段只替换状态内部实现，可按提交逐阶段回滚，不改数据库。
- 第二阶段涉及请求取消和异步竞态，必须保留旧 OCR API 响应格式，失败时允许用户重试。
- 第三阶段不要在同一提交里新增数据库 migration；先维持现有补偿回滚，待真实失败证据证明需要事务化后再单独设计 RPC。
- AI 标签从核心路径移出会改变“提交成功后标签稍后出现”的时序，需要产品确认是否接受；未确认前只做服务拆分，不改变可见时序。
- 现有 `HistoryReportEditForm` 是独立旧入口，第一轮不直接删除，避免历史数据无编辑入口。
