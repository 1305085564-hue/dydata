## 一页一问

出事时打开这一页：**最近 AI 调用有没有在失败、在变慢？坏在哪个功能、哪个模型的哪条渠道？系统救回来没有？我要不要出手？**
日常维护（加渠道、排顺位、改模型）是第二件事，放到下面。

## 两个指标的口径（阿禅 2026-11-19 拍板）

| 指标 | 算法 | 窗口 |
|---|---|---|
| **成功率（稳定程度）** | 渠道级：该渠道每次尝试成没成。功能级：用户的一次请求最后成没成（中途换渠道成功也算成） | **近 1000 次**看长期稳定；**近期 = 近 3 天内最近 50 次**看眼下（3 天内不足 50 次就按实际次数，写「近 3 天 N 次」；3 天内没有调用写「近 3 天没有调用」） |
| **速度** | 只算成功调用的**平均耗时**（不同模型差别大：4 秒多、8 秒多、十几秒都有，看均值就够） | 同上两个窗口 |
| **救回** | 一次请求里前面的渠道失败、后面的渠道成功 | 失败流水里逐条标「已救回 / 没救回」 |

不做「偏慢」、中位数、P90。
颜色（配色规则①：绿 = 安全、红 = 异常）：近期成功率 < 90% 红；90%–98% 黄；其余不上色。近 1000 次只上黄不上红（长期偏低提醒维护，不算急事）。
手动「检查一遍 / 测试」产生的调用单独标记，**不计入成功率和速度**，但出现在失败流水里并标「手动检测」。

## 一、后台：每次 AI 调用记一笔（交 Codex）

**记录点**：`src/lib/ai/client.ts` 的 `runAi` 渠道尝试循环（所有功能都经 `callAi` 走这里：截图识别、截图结构化、内容分析、分段、视频诊断、成员 AI 建议、样本质检、内容工具）。每次向一条渠道发出请求，成功或失败后写一行。旁路写入：写失败只 `console.warn`，不影响业务结果，与 `markChannelSuccess` 同样处理。

**新表 `ai_call_attempts`**（建议名，Codex 可按现有命名调整）：

| 字段 | 说明 |
|---|---|
| id, created_at | |
| request_id | 同一次 `runAi` 的所有尝试共用，用来算功能级成功率与「救回」 |
| attempt_no | 本次请求里的第几次尝试 |
| feature_key | 哪个功能；无 featureKey 的直连调用记 null |
| model_id | 规范模型标识（与 availability 里 family.modelId 同口径） |
| key_model_id, key_id | 哪条渠道供应 |
| is_success | |
| error_kind | 失败时：超时 / 限流 / 额度 / 鉴权 / 模型不存在 / 网络 / 服务端 / 内容不合格 / 其他（由现有 errorType 映射，映射表写进代码一处） |
| error_message | 已脱敏（复用 `sanitizeProviderErrorMessage`），截 200 字 |
| duration_ms | 这一次尝试的耗时 |
| is_probe | 手动检测 / 试跑为 true |

索引：`(key_model_id, created_at desc)`、`(feature_key, created_at desc)`、`(created_at)`。保留 90 天，并入现有 `notifications/cleanup` 的清理任务（与 `ocr_recognition_logs` 同做法）。RLS 只开 service_role。

**统计接口** `GET /api/admin/ai-config/call-stats`（`manage_system` 权限，与 `/api/admin/ai-config` 同校验）。页面先出配置，统计随后到，不拖首屏。返回：

```ts
type Window = { calls: number; successRate: number | null; avgMs: number | null };
type CallStats = {
  generatedAt: string;
  channels: Array<{
    keyModelId: string; modelId: string;
    recent1000: Window;      // 该渠道最近 1000 次尝试
    recent: Window;          // 近 3 天内最近 50 次尝试
    lastFailure: { at: string; kind: string; message: string; featureKey: string | null } | null;
  }>;
  features: Array<{
    featureKey: string;
    recent1000: Window & { rescuedCount: number };  // calls = 请求数
    recent: Window & { rescuedCount: number };
  }>;
  recentFailures: Array<{ // 最近 100 条失败尝试
    at: string; featureKey: string | null; modelId: string; keyModelId: string;
    kind: string; message: string; rescued: boolean; isProbe: boolean;
  }>;
};
```

## 二、前端：页面从上到下（CC）

1. **页头答案**（随统计变）：
   - 出事：「文案生成、选题分析出错中 · 已切到备用模型」/「全局兜底模型的渠道在出错」
   - 没事：「近 3 天调用都正常 · 成功 99.6%」
   - 统计未到：沿用现在的功能正常 / 顶班 / 停摆一句
2. **最近调用值班表**（第一屏主角，紧凑表格，行高 36）：按模型分组，**兜底模型组排第一并标「兜底」**；组头写模型名 · 在给谁用。每行一条渠道：
   `渠道名 ｜ 近期成功率（近 3 天最近 50 次） ｜ 近 1000 次成功率 ｜ 平均耗时 ｜ 最近一次失败（多久前 · 原因） ｜ 现在状态 ｜ 暂停 · 测试 · 调到第一`
   有问题的组和行排最前。只列在用的模型；没调用记录的格子写「还没有调用记录」。
3. **最近失败流水**：最近 100 条，`时间 ｜ 功能 ｜ 模型 · 渠道 ｜ 原因 ｜ 已救回 / 没救回 / 手动检测`。点值班表一行，流水只剩那条渠道；再点取消。
4. **功能用哪个模型**：现有功能表压成紧凑行，加两列「近期成功率」「平均耗时」（功能级）。出事时在这里换模型。
5. **渠道维护**：现有模型 / 渠道两个视角、找渠道、接入新渠道，默认收起成一行「渠道维护 · N 条渠道 ›」，点开后与现在一致。

**密度**：去掉区块之间大段留白和卡片套卡片；表格统一 36 行高、12–14px；第一屏（1440×900）装得下页头 + 值班表全部在用渠道（≤ 12 条时）+ 流水前几条。

**分两步交付**：
- 第一步（不等后台）：按上面结构重排，值班表先用现有健康数据（现在状态、连续失败、最后一次失败时间与原因），截图识别的成功率与速度从测速台账取；其余格子写「还没有调用记录」。
- 第二步（统计接口上线后）：接上 `call-stats`，格子自动补齐，页头切到统计口径。

## 前端实施记录（CC，2026-11-19）

- 页面顺序：最近调用值班表 → 最近失败流水 → 功能用哪个模型（加近期成功率、平均耗时两列）→ 渠道维护（默认收成一行；「去修 →」自动展开并定位）。
- 统计接口返回结构的唯一定义：`src/lib/ai-config/call-stats-contract.ts`；读取：`hooks/use-call-stats.ts`（接口 404 / 失败时页面如实说「调用记录还没接上 / 读取失败」，格子显示「—」，不拿别的数凑）。
- 口径代码：`duty-view.ts`（上色、排序、最近失败的取法：调用记录优先，没有就用渠道上记的最后一次失败并标「之后已恢复」）；页头：`ai-config-headline.ts`。
- 值班表行内操作：测试、设为首选（和现在的首选互换顺位，沿用原换位接口）、暂停（只停这条渠道给这个模型供货，沿用原开关接口）；与渠道维护区共用 `hooks/use-channel-commands.ts`。
- 组内按真实顺位排（第一位 = 首选），不按问题重排行，避免「设为首选」后行乱跳；有问题的组整体排最前。
