复制以下内容给 Claude Code：

---

你是本轮方案审查者，不是执行者。请在 `/Users/mac/Projects/dydata` 对以下方案做一次独立、只读审查：

`docs/plans/文案内容质量/2026-09-30-文案内容质量后三个入口实施方案.md`

目标是把已经完成的个人 30 日曲线、文案岗位表、个人本月文案明细继续扩展到三个入口：

1. 视频复盘作品列表：综合评级、对应核心指标、按综合评级筛选；
2. 文案小队汇总与成员表：评级分布、良＋优占比，成员点击进入现有个人档案抽屉；
3. 选题库关联作品：内容达成率、综合评级、互动率和对应核心指标，权限允许时打开视频复盘。

先执行：

```bash
git status --short --branch
git log -n 6 --oneline --decorate
```

读取当前 `AGENTS.md` 和命中场景的文档。方案创建时前三个入口已经完成，但必须以当前源码为准重新核对，不要相信旧交接中的提交、行号或代理自报。

本轮只读审查：不要改代码、不要改文档、不要提交、不要推送、不要写生产数据库、不要运行全量发布门禁。

## 一、数据和口径

1. `content-quality-contract.ts`、`breakout-rating.ts` 和现有 `buildWorkContentQuality` 是否真的能支持三个新入口？
2. 方案是否保持“内容达成率”和“综合评级”分离：内容达成率只看互动率＋话题核心指标；综合评级继续受 5千/1万/1.5万播放封顶影响？
3. 良＋优占比是否使用 `overallGrade` 非空作为分母，是否错误地使用内容档位或播放达标作品数？
4. admin/content、文案小队、选题库是否都能按最新 24h 快照和话题标签得出同一结果？特别检查选题库现有 `maxSnapshotPlayCount()` 是否会导致旧快照/最大值污染评级。
5. 混合干货和复盘时，是否逐篇按话题标准归一后再汇总；是否把原始比率加权均值与达成率等权均值混用？

## 二、调用链和性能

6. admin/content 首屏已全量加载视频和快照，新增质量字段应放在哪一层，才能避免组件等待另一套 topic 状态接口后自行计算？
7. `video_tags` 与最新 24h 快照是否会按批次读取；是否可能退化成 N+1 查询或调用完整选题库状态链？
8. 小队质量汇总是否基于作品级结果重新聚合，而不是平均成员百分比？是否会把每篇作品全部塞进小队首屏造成 payload 膨胀？
9. 选题库作品分页、排序、缓存和旧响应兼容是否保留？

## 三、权限和用户动作

10. 普通无 `review_content` 权限用户能否看到不该看的 admin/content 写操作？选题库“点击复盘”是否只增加合法读入口，不扩大编辑、入库、移出或回收站权限？
11. 小队成员点击是否确实复用 `role="writers"` 的现有个人档案，而不是另造一份小队作品数据？
12. 无关联、无快照、缺指标、播放0、标签缺失、标签读取失败、全未评级等状态是否各有真实语义？有没有把失败当作 `other` 或 0%？

## 四、前端拆分判断

13. 重新统计实际需要改动的前端文件、组件、测试和角色场景，判断前端是“小改动”还是“中等偏大”。
14. 明确给出推荐：
    - 单一 Codex 全栈完成；
    - Antigravity 做表现层、Codex 做数据链；
    - 或拆成更多独立批次。
15. 如果推荐 An/CX 分工，列出双方互不重叠的文件白名单和交接契约；如果不推荐，说明为什么不值得拆。
16. 检查“小队展开作品”是否已经被方案收窄为点击成员进入个人档案；若仍需要内嵌作品列表，标为范围扩大，不要默认为本批任务。

## 输出格式

先给结论：`可实施`、`修订后可实施` 或 `存在业务阻塞`。

随后按以下格式列问题：

```text
[阻断/高风险/一般]
业务影响：
方案章节：
当前源码证据：文件 + 函数/符号 + 行号
最小修订建议：
```

最后必须给出：

1. 前端工作量判断和推荐拆分方式；
2. Antigravity 开工条件；
3. Codex 开工条件；
4. 需要阿禅新增确认的业务问题（没有就写“无新增业务问题”）；
5. 方案中明确可以冻结的范围和明确延期的范围。

只报告会影响数据正确性、权限安全、核心闭环或验收有效性的问题。视觉细节交给 Antigravity；不要为了凑数量提出无关重构。
