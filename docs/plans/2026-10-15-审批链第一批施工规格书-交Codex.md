## 3. 逻辑规格

### 3.1 FR-05 计数同源

**根因（已实测）**：头部"总数"来自后端 summary（`unified-command-hub.tsx` L838-841：`approvalCount`/`todoCount`），筛选行来自前端加载卡片（`approvals-tab.tsx` L49-50：`groupedApprovals.length + appealItems.length + todoItems.length`），两套无一致性保证。

**改法：工作台头部改为与卡片列表同一数据源。**

```ts
// unified-command-hub.tsx（L838-841 替换）
// 头部计数一律由渲染卡片所用的同一批数组派生，禁止再取 summary
const approvalPendingCount = groupedApprovals.length + appealItems.length; // 以组件内实际数组名为准
const todoPendingCount = todoItems.length;
```

- 若 `groupedApprovals/appealItems/todoItems` 当前只在 approvals-tab 内部计算，则把该计算**上提**到 unified-command-hub，作为同一 props 同时传给 WorkbenchHeader 与 ApprovalsTab——两处消费同一份数组即为同源。
- `summary` 仍保留给导航角标（navigation-shell）使用，本文件内不再用于工作台计数；`todos-tab.tsx` L37"共 X 项待跟进"同步改传 `todoPendingCount`。
- 加载中（数组为空）：徽章不渲染，与现状一致。

### 3.2 FR-03 执行状态派生与透传

**状态真源（无迁移）**：`_resume-submission.ts` 已保证——续交成功即把 `submission_payload` 置 null（L58-62），失败/未执行则 payload 留存。因此：

```ts
// appeals/route.ts：返回前对每条申诉派生
resume_pending = status === "approved" ? submission_payload != null : null;
// true  → 等成员补传
// false → 数据已提交
// null  → 尚未批准，无执行状态
```

- select 增加 `submission_payload`，**返回体只输出布尔 `resumePending`，不透出 payload 原文**。
- 该 route 内所有返回申诉列表/历史行的查询都要加（L27 待处理列表、L119/L131 附近的其他查询逐一核对；用 `rg -n "fulfillment_appeals" src/app/api/admin/fulfillment/appeals/route.ts` 枚举收口）。
- 前端类型（appeal 条目 interface）加 `resumePending: boolean | null`，前后端字段名对齐。

**文案真源（view-rules.ts 新增）：**

```ts
export function getAppealExecutionLabel(resumePending: boolean | null): string | null {
  if (resumePending === null) return null;
  return resumePending ? "已批准·等成员补传" : "数据已提交";
}
```

history-appeal-card 与 fulfillment-appeal-card 一律调用此函数，不得各自硬编码。

**批准即时反馈（unified-command-hub.tsx）：** 原规格此处有误——`autoResumeStatus` 此前只出现在内部观测与员工通知里，**响应体并未返回**，导致前端只能走失败分支、常态成功也报"数据未写入"。改法：裁决接口成功路径的响应体增补该字段（纯新增、向后兼容，不动裁决逻辑）；前端按三态显示：

- `succeeded` → `已批准，数据已自动提交`
- `failed` → `已批准，数据未写入，等待成员补传`
- 其余（`skipped` 或字段缺失，如幂等 already_handled 路径）→ `已批准`（不得把未知当失败）

不改变撤销（undo）窗口等既有交互。

### 3.3 FR-04 回退确认文案（history-exemption-card.tsx L100）

整句替换为：

> 打回后，这段时间的请假/免交生效将被撤销，对应日期的发布履约会按未审批状态重新计算；成员需要重新等待审批，该申请会重新回到「待审批」列表。

补交回退文案（history-appeal-card L94）已合格，**不动**，仅作风格基线。

## 4. 数据与边界

| 场景 | 行为 |
|---|---|
| approved 但 payload 因清空失败留存（_resume-submission L64-66 的 warn 分支） | 显示"等成员补传"属可接受降级（数据可能已写入）；不为此加新状态 |
| 历史行早于 payload 机制的旧 approved 记录（payload 为 null） | 显示"数据已提交" |
| 非管理员打开工作台 | 只显示"待办 M" |
| 筛选后列表变化 | "当前筛选"数随筛选变化；头部"待审批"数**不随筛选变化**（始终为全量待处理） |
| 日期显示 | 一律上海自然日 `M.DD` 格式，与全站作品日期口径一致 |
