# DYData 文档维护收口方案

> 目标：以最低日常维护成本，让 AI 和负责人能找到当前有效资料、少被历史文档误导，并尽早发现关键入口损坏。
> 规划日期：2026-09-24。范围是维护机制，不是全量修复现存文档。

## 1. 结论与选择

采用“少数现行入口 + 任务闭环更新 + 低噪声只读检查”的组合。不引入知识图谱，不批量重分类 300 份文档，不自动修复链接或搬迁文件，不把不稳定检查设为合并/发布硬门禁。

仓库现有分层已足够：`docs/plans/` 放待施工方案，`docs/reference/` 放长期有效入口和契约，`docs/archive/` 保存历史，`docs/reviews/` 保存审查证据，`docs/待办清单.md` 只放仍需处理的事项。维护重点应放在少量现行入口，而不是治理整个历史库。

## 2. 成功标准

1. 新参与者能从 `AGENTS.md` 找到按任务分类的当前事实入口，不需要每次遍历全库。
2. 当前事实只在指定主文档维护；审查、方案和归档不意外变成第二份现行规则。
3. 涉及事实变化的任务明确交代相关文档是否更新、为何无需更新，未核验的线上事实不标为已核验。
4. 文档工具只提供可复核的问题报告，不静默改写、归档或删除内容。
5. 不要求给全部历史文件补标签、日期或负责人，不增加持续人工台账。

## 4. 维护口径

### 4.1 文档职责

| 位置 | 职责 | 当前施工时如何使用 |
| --- | --- | --- |
| `docs/plans/` | 尚未完成的施工方案 | 完成后按是否仍有复用价值由人决定迁移目标 |
| `docs/reference/` 与 `docs/` 根部指定事实文档 | 当前事实、稳定契约、可复用入口 | 命中任务触发条件时读取，是现行信息的主来源 |
| `docs/reviews/` | 审查过程和证据 | 结论经采纳并核实后回写当前入口，报告不自动变成规则 |
| `docs/archive/` | 历史方案、旧报告、仅供追溯的记录 | 不作为当前施工依据；只有追溯任务才加载 |
| `docs/待办清单.md` | 仍需继续处理的项目待办 | 完成/拆出后及时移除已结项条目 |

### 4.2 当前事实入口

以 `docs/文档维护入口.md` 第 1 节的表格为当前导航。主题主文档负责维护现行结论，其他文档优先链接回主文档，不复制另一份看似同等权威的规则。模块专项接口/维护入口仍由懒加载索引按需引用。

### 4.3 状态和日期

- 只维护当前事实入口已经使用的“最后核对日期/最后核对代码日期”；不创建覆盖全库的新元数据体系。
- 日期只在对应范围被实际核验时更新。纯格式调整不更新。
- 日期说明的是核验时间，不代表文件每个段落或生产环境均已验证；局部核验要注明范围。
- 不按固定天数判过期，不根据文件年龄或“已完成”自动归档。需要复核时由相关任务或负责人触发。
- 新方案的待办状态由方案和待办清单表达；完结后按复用价值人工归入 reference 或 archive。

### 4.4 每项任务的文档闭环

涉及权限、路由、接口、数据库结构/口径、部署、模块职责或文件迁移时，执行者在交付时说明：

1. 更新了哪些现行入口；
2. 检查后确认哪些入口无需更新；
3. 哪些事实未能核验，尤其是生产部署、数据库或真实角色证据。

普通纯视觉/机械修改仅在确实影响当前事实时更新文档，不强制制造文档改动。该检查是任务范围内的定向核对，不要求每次扫描整个 `docs/`。

## 5. 工具方案

### 第一阶段：不安装额外工具

先使用当前已存在的 Git、文本搜索和文件存在性检查；继续观察现有入口实践。`scripts/文档体检.py` 暂不作为正式维护工具，不运行其 `--fix`，也不在本方案内扩充其规则。保留该未跟踪实验文件供后续单独决定；本方案不替用户删除它。

### 第二阶段：只读检查的小范围试运行（另批授权后）

先以根 `AGENTS.md` 和本页导航所指向的当前入口为范围，验证工具对以下链接的识别：普通相对链接、括号路径、`#L` 锚点、历史/代码示例。输出分类清晰的报告，人工抽样确认误报后才决定是否扩大范围。

可评估成熟链接检查工具（如 Lychee）检查外链/普通链接；必须以本仓库实跑结果为准。内部带行号路径、路由组括号、代码片段及历史绝对路径需单独分类。检查先做建议性报告，不阻断 push；工具未装好或网络失败记为未验证，不改由猜测补结论。

### 明确不做

- 不全库自动修复或批量格式化 300 份 Markdown。
- 不自动判断目标文件、迁移文件、归档或删除。
- 不因文档日期旧或含“已完成”文本就认定内容失效。
- 不为文档治理引入知识图谱、专用平台、AI 向量库或新增付费服务。
- 不在工具误报未量清前加 GitHub Actions 阻断门禁。
- 不补写未真实核验的文档日期，不批量给所有文档添加 metadata。

## 6. 推进步骤与验收

### 步骤 A：入口落位（当前已部分完成）

- [x] 在 `AGENTS.md` 懒加载索引中加入该入口。
- [ ] 核对全部相对链接存在且索引指向正确文件。
- [ ] 报告 `git diff --check` 结果和实际工作区改动；不包含其他任务未提交变更。

**完成条件：** 新增入口及其链接均有效，工作树差异边界可读。

### 步骤 B：现行入口日期清点（不批量改业务事实）

- [ ] 只读列出第 1 节现行入口当前已有的日期字段、日期值和文档内定义的核验范围。
- [ ] 对未核验或无日期的文档标为“尚未建立基线”，不自行补日期。
- [ ] 后续每次对应事实被真实核对时按 §4.3 更新。

**完成条件：** 清点报告区分现有证据、未核验范围和待决定事项；不声称内容全部最新。

### 步骤 C：检查工具验证（独立小任务）

- [ ] Lychee 可用后，对固定的小样本和全量 docs 分别只读试跑，保留版本、参数、退出码和分类汇总。
- [ ] 对至少 20 条命中项人工核对真实结果，重点覆盖括号、行号、代码围栏、归档和本机路径；不足 20 条时说明实际样本量。
- [ ] 将误报、漏报和真实问题分类；只有误报足够可控、重复运行稳定，才提议定期或 CI 建议性报告。
- [ ] 不使用当前实验脚本的自动修复。修复方案另开任务，先有候选 diff、唯一目标证据及自动化测试。

**完成条件：** 能复跑、误报已量化且用户能看懂报告；否则停止在只读本地检查，不接 GitHub Actions。

### 步骤 D：后续轻量闭环

- [ ] 每次实际修改当前事实时更新其对应入口和核对日期；只检查受影响主题。
- [ ] 新文档按目录职责存放，完结后根据是否还要复用人工决定 reference/archive。
- [ ] 发现事实冲突时，将“本地代码、生产数据库、部署版本、真实角色验收”分别记录，不用一层证据代替其他层。

**完成条件：** 每次交付能说明文档更新/不更新/未核实，历史资料未被无授权改写。

## 7. 验收命令

入口落位的定向验收：

```bash
git diff --check
python3 - <<'PY'
from pathlib import Path
import re
files = [Path('AGENTS.md'), Path('docs/文档维护入口.md')]
for source in files:
    text = source.read_text(encoding='utf-8')
    for target in re.findall(r'\[[^\]]+\]\(([^)]+)\)', text):
        if target.startswith(('http://', 'https://', 'mailto:', '#')):
            continue
        path = (source.parent / target.split('#', 1)[0]).resolve()
        if not path.exists():
            raise SystemExit(f'{source}: missing link target {target}')
print('入口文件的相对 Markdown 链接均存在')
PY
git status --short
```

该链接检查是针对两个入口文件的定向检查，不声称覆盖所有 Markdown 语法，也不证明链接语义必然正确。

## 8. 风险、待办和停止点

- 关键入口若只写“最后核对”但没说明范围，可能让读者误以为整份文档都已复核；因此应记核验范围，或保留“只代表本次任务范围”的限制。
- 检查器的高误报会制造维护噪音；误报未分类前不得接入阻断门禁。
- 当前脚本 `scripts/文档体检.py` 的 `--fix` 有直接写文件行为，不能作为只读工具运行；需要独立授权和安全改造后方可评估。
- 此方案不授权对现存文档做批量整理，不授权删除实验脚本，不授权提交或推送。
- 步骤 A 定向验收通过后，本规划交付即完成；步骤 B/C 为未来单独任务，不自动续做。
