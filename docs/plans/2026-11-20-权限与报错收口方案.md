## 〇、给执行者的第一句话

**本任务的终点是第三节 10 项全部为「通过」。全部通过立刻停止并汇报。** 第三节以外的任何事都不属于本任务。**任何人能看到什么、能做什么，一律保持不变**：本任务只改"由谁来判断"和"报错怎么说"，不改判断结果。

## 一、为什么做（实测，2026-11-20）

权限有两种把门方式：① 用"万能钥匙"（服务端管理员连接）进数据库，由代码判断能看什么，约 80 个文件是这种；② 用"员工本人身份"连接，由数据库自己的门禁规则和数据库函数判断。同一个功能一旦混用，就会静默出错，而且已经出过两次事：

| 问题 | 已发生的事 | 本方案对应 |
|---|---|---|
| 依赖"数据库认出是谁"的操作，被人用万能钥匙调用 | 11-17 排行榜整片空白：切 CloudBase 时改成了万能钥匙读法，切回后没改回，数据库认不出人就返回 0 行，没有任何报错 | A1 |
| 只靠数据库门禁规则保护的读写，规则一丢就静默变空 | 11-18 发现员工"逐日审批结果"只靠一条门禁规则撑着，规则一删就静默消失 | A2、A3 |
| 数据库原始英文报错直接显示给员工 | 17 处，其中 4 处在交作品接口；项目里已有统一报错工具 `src/lib/errors.ts`，只有 2 个接口在用 | B |
| 两个在用的检查工具放在已删除模块的文件夹里 | `api/admin/cockpit/_shared.ts`、`api/admin/ai-channels/_shared.ts`，被 8 个文件引用，容易被当成死代码误删 | C |

**生产实测**：生产库 31 个函数用到"数据库认出当前用户"（`auth.uid()`），其中被应用直接调用的是下面 12 个：

| 业务 | 数据库函数 | 调用位置 |
|---|---|---|
| 请假/免交审批 | `review_exemption_request_dates_atomically`、`reopen_exemption_request_atomically`、`set_permanent_exemption_owner_atomically`、`clear_permanent_exemption_owner_atomically` | `src/lib/exemption-review.ts` |
| 发布管理标记 | `mark_fulfillment_status`、`mark_fulfillment_status_batch`、`remove_fulfillment_mark` | `api/admin/fulfillment/mark`、`bulk-mark`、`remove` 等 |
| 申诉 | `handle_fulfillment_appeal`、`reopen_fulfillment_appeal_atomically` | `api/admin/fulfillment/appeal/*` |
| 入团审批 | `review_team_join_request` | `src/lib/team-join/service.ts` |
| 排行榜 | `get_leaderboard_rows` | `api/dashboard/leaderboard` |
| 提醒计数 | `count_remind_logs_for_user` | `api/remind/count` |

## 二、施工步骤与时间上限

**开工前置**：搬迁方案第三节全部通过，通过后**立即**开工，基于当时最新的 main。搬迁没通过就不开工，只汇报。**和搬迁一起在最近 2 天内连续做完：上一步通过就立刻做下一步，不按钟点排班，不准以"留到晚上 / 明天再做"为由停下。** 下表的"上限"是止损线：单步超过上限就停下，记录卡点，按第四节处理。

| 步 | 做什么 | 上限 |
|---|---|---|
| P1 | **防止用错钥匙（A1）**：在统一的万能钥匙连接入口（`src/lib/supabase/admin.ts`，以及 CloudBase 下对应的管理员连接 `src/lib/cloudbase/data-client.ts`）对上表 12 个函数加拦截：用万能钥匙调用时立刻报错并记录，不再静默返回空。先全仓查一遍现在有没有路径正在用万能钥匙调用它们，有就改成本人身份连接 | 1.5 小时 |
| P2 | **只靠数据库规则的读写改为代码判断（A2）**：先出精确清单。候选：`src/lib/account-actions.ts`、`api/ocr-screenshot`、`api/usage-events`、`api/submission-screenshots/grant`、`api/submission-screenshots/file`（30 分钟内定稿）。逐个改为"万能钥匙 + 代码里按本人或可见范围过滤"，复用 `getCurrentUserContext` 和 `src/lib/data-access-scope.ts`，不新建权限判断。P1 表里的函数调用保持本人身份连接，不在本步改 | 2 小时 |
| P3 | **自动看守（A3）**：照 `src/app/api/route-auth.coverage.test.ts` 的写法，新增一条测试：服务端代码用本人身份连接直接读写数据表的，必须登记在清单里并写明理由，否则测试失败。浏览器端登录页读本人资料属于登记例外 | 1 小时 |
| P4 | **报错改中文（B）**：下列 17 处不再把原始报错发给前端。提示文字取 `src/lib/errors.ts` 里现成的 `publicMessageForCode`（不新增另一套文案），后面附请求编号（见第七节第 2 条）；原始报错写进服务端日志，带同一编号。**返回格式保持 `error` 为一句字符串**，另加 `requestId` 字段：前端现在大多按字符串读 `error`，直接换成 `toErrorResponse` 的对象格式会让页面显示 `[object Object]`。`cloudbase/_shared.ts:47`、`video-submit/route-core.ts:218/422/523/602`、`admin/ai-config/call-stats/route.ts:21`、`admin/ai-config/ocr-logs/route.ts:33`、`admin/collaboration/handlers.ts:68`、`admin/content-analysis/route.ts:55`、`admin/execute-tool/route.ts:204/311`、`exemptions/review/route.ts:90`、`exemptions/permanent/route.ts:75/95`、`exemptions/reopen/route.ts:53`、`notifications/cleanup/route.ts:18`、`topics/_shared.ts:109`（行号以开工时为准）。原来就是业务含义明确的中文提示（例如选题关联失败的原因），保留原文 | 1.5 小时 |
| P5 | **挪位置（C）**：两个工具文件挪到 `src/lib/` 下对应位置，函数名不变，改 8 处引用，删掉两个空文件夹 | 0.5 小时 |
| P6 | 推送前六项检查 → push main → 按搬迁方案定下的新发布方式上线 → 第三节第 8–10 项线上验收 → 回写文档、写日志、汇报 | 2 小时 |

**合计上限 8.5 小时。**

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 拦截生效 | 单元测试：12 个函数每个都有"用万能钥匙调用即报错"的用例，Supabase 和 CloudBase 两种连接各覆盖一次；先红后绿，有提交记录可证 |
| 2 | 现存误用为 0 | 全仓清单：12 个函数的每个调用点各用哪种连接，逐条列出，用万能钥匙的为 0 |

| 5 | 原始报错为 0 | 把 17 处的写法在 `src/app/api` 下再搜一遍（不算 `douyin/`），命中为 0；交作品接口至少一条测试证明：返回里不含原始报错原文，`error` 仍是字符串，`requestId` 能在服务端日志里查到 |
| 6 | 挪位置 | `api/admin/cockpit/`、`api/admin/ai-channels/` 两个文件夹不存在；鉴权清点测试通过 |

| 8 | 行为不变·组员 | 新站上测试组员：登录 → 工作台显示正常 → 提交一条作品（含截图识别）→ 能看到自己的截图 → 提醒计数正常显示；之后删除测试数据 |

## 四、遇到问题怎么办

| 情况 | 动作 |
|---|---|
| 某步超时 | 同一处最多再试一次；仍不行就跳过这一步，在汇报里写明，继续下一步 |
| 第 8、9 项任一项不通过 | 先查是不是本次改动导致的：是的话，用发布平台回到上一个版本；不是（搬家本身就有的问题）就记录交阿禅，不修 |
| 发现改了某处会改变"谁能看到什么、能做什么" | **停止该处修改**，写进汇报交阿禅拍板 |
| 发现第三节以外的问题 | 只记录，不修 |

## 五、明确不做

- 不改那 31 个数据库函数，不写任何新的数据库变更脚本
- 不统一 18 个鉴权入口的名字
- 不改其他 242 处本来就是中文的报错
- 不碰抖音相关代码（另有下线任务）
- 不改任何人的权限、可见范围和页面
- 不删数据库里两份角色字段（生产实测 85 个账号两边全部一致，属历史遗留，另议）
