## 目录结构

| 位置 | 放什么 |
| --- | --- |
| 本目录根 | 在办的计划，**一律平铺单文件**，命名 `YYYY-MM-DD-主题.md`；同一任务多份也平铺，不建子文件夹 |
| `历史-方案/` | 已办：方案、规格书、需求书、实施计划 |
| `历史-报告/` | 已办：审查、盲审、排查、验证报告、进度台账、决策报告 |
| `历史-项目/<任务名>/` | 已办：同一任务的多份文件整包（不拆散） |
| `上下文交接/` | 会话交接，常驻（模板见 `docs/通用管理/上下文交接.md`） |

## 什么时候归档（触发点）

1. **本任务收尾**——本轮确认完成的计划、派单和进度材料当轮归入 `历史-方案/` 或 `历史-报告/`，不等 5 天；仍有未完成部分的保留在根目录并注明状态。
2. **批量历史整理**——整理其他任务的历史材料，先核完成证据和当前引用，再列候选交阿禅确认；已获明确范围授权的按授权执行，不凭文件日期或「已完成」字样搬迁。
3. **5 天保护**——仅用于批量历史候选筛选及多文件整包：看最后提交时间，5 天内仍有改动的先留原位；未提交材料也不按文件日期推断过期。满 5 天只代表可复核，不证明任务已完成。
4. **多文件打包**——同一任务累计 ≥3 份、都有完成证据且整包超过 5 天未改，再一起移入 `历史-项目/<任务名>/`；本任务刚收尾的先按第 1 条归档，冷静期后再整包。

## 归到哪一类（判断顺序）

1. 同一任务 ≥3 份且符合整包条件 → 一起进 `历史-项目/<任务名>/`；否则按用途分别归档，保留相互引用，待整包时一起核对。
2. 按文件用途，一句话判据：
   - **给人照着干活用的**（方案、规格、需求书、实施计划、派单提示词）→ `历史-方案/`
   - **给人看结论和证据用的**（审查、盲审、排查、验证报告、进度台账、决策报告）→ `历史-报告/`
3. 只有 1 份、执行完不再有参考价值的一次性提示词 → 直接删（git 历史可查），不进归档。

**不要按业务主题分类**（治理 / UI / 架构 / 性能）。主题会互相重叠，每次归档都要犹豫「这份到底算哪类」——而犹豫就是当初忘记归档的原因。

## 给 AI 的提示

- 写新方案：命名 `YYYY-MM-DD-主题.md` 平铺放本目录根。同一任务要拆多份（规格书 / Codex 提示词 / Antigravity 提示词 / 续派令）也**照样平铺**，靠文件名区分。
- **在办期不建任务文件夹**：先平铺，确认完成的本任务材料当轮归档；整包均有完成证据且超过 5 天未改后，再一起收进 `历史-项目/<任务名>/`，同步核对引用。
- 文件内互相引用写仓库相对全路径（`docs/plans/xxx.md`），不要写裸文件名；搬迁时一并更新这些引用。
- **任务做完的同一轮，把对应 plan 归入 `历史-*`**。收尾报告里要说明归档了哪些文件。
- 一次性施工产物（.sql / .json 快照、回滚脚本）不提交，用完即删。
- 归档是移动不是复制：同一结论只保留一份原文，历史文件里已有的路径引用要跟着改。
