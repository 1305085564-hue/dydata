### R01：封禁、未激活、归档身份的旧会话门禁

**证据边界**：报告证明“只把 Auth 状态设为封禁，旧 JWT 和站点 Cookie 仍可用”；A13 的“归档+封禁”在该次样本已经拒绝，只是返回 503。分项还有归档构造态旧 JWT 可提交申诉的证据。因此不能笼统写成所有归档场景都已证实失效，也不能只修一个样本。

**本版元数据实测**：当前 public 共 99 张表、全部已开启 RLS；anon 无常规表读写权限，authenticated 可读 89 张、可增改删 80 张。其余 10 张无客户端常规读写权限，保留现状，不因总表数是 99 就全部加策略。89 张为常规表门禁起点；仍须另查可执行 RPC/视图等实际入口，不能把表权限数量当全部网关边界。

`is_admin()`、`is_admin_or_owner()` 当前只检查档案在职状态，`visible_user_ids_v2()` 也没有读取 Auth 封禁状态；**已有在职检查未接入 `auth.users.status`**，不是重新发明身份体系。函数属主对 `auth.users` 有 SELECT 权限，并为 profiles 属主且 `rolbypassrls=true`。因此统一 SECURITY DEFINER 状态函数读取 profiles 不会在当前配置下触发其 RLS 递归；profiles 本身必须纳入门禁，不能据“可能递归”把它排除。

**方案**：

1. 在既有 CloudBase 身份校验中补查可信的当前 Auth 状态和档案状态，页面、API、Server Action、站点数据代理、截图授权共用判定。仅按请求内去重，不用长缓存延迟封禁生效。
2. 建立**一个统一的 SECURITY DEFINER 当前身份状态函数**，从真实 JWT 身份求当前 Auth 状态和档案状态，默认拒绝缺失/停用身份；只返回必要判断、固定安全 search_path，不接受普通调用方指定“代查并授权的用户”。应用层按相同状态判定读取最小字段，不另写一套停用语义。
3. 数据库网关可以绕开站点，必须同时覆盖它：为当前可读的 89 张表设置 authenticated 限制性状态策略，覆盖其中 80 张的正常写操作，检查全部 permissive 策略不会把限制放开。复用统一状态函数，不逐表复制 Auth/profiles 查询，不改变既有对象可见范围；无常规客户端权限的 10 张和 anon 不机械加策略，不增授权限。
4. 对实际用户可执行的 `SECURITY DEFINER` 函数单独接入同一个状态函数；此类函数可能绕过表行级权限，不能认为表策略已覆盖。已有入口目录作为起点，核对当前执行权限与依赖，不重做迁移理论审计。
5. 状态读取不暴露密码、邮箱清单或平台 Auth 管理权限。保持已验证的属主/权限条件并在应用前复核，不把 profiles 查询内联进其策略；平台 `auth.uid()` 和托管 Auth 结构不改。状态检查与 R03 的对象可见范围函数职责分开，不能借本包扩大数据范围。

**通过标准**：自建组员、管理员、负责人先登录，分别转为封禁/未激活/归档后，旧 Cookie、JWT、刷新和相关票据都不能继续获取业务数据或产生写入；直接网关与用户可调用 RPC 同样拒绝。已在职同角色正例、合法服务端任务及归档历史查询不受误伤。并发中已完成请求不倒推撤销，以状态变更完成后的新请求判定。

### R10：选题状态的只读查询

代码已核对：GET 和只读 POST 都要求 `review_content`，员工没有该写权限；后续查询本身已经调用 `resolveVideoReviewReadOnlyScope()`。建议只读查询改按 `view_video_review` 及共享只读范围授权，不给员工 `review_content`，不开放选题入库、移出或复盘写入。

### R12：旧豁免审批入口与逐日一致性

**推荐**：确认无合法客户端调用后，撤销旧入口对 PUBLIC/anon/authenticated 的执行权限，保留数据库内部必要依赖，不直接删除函数。如果仍有合法调用，兼容入口委托现行逐日事务实现，并保留原签名与必要返回契约。不能仅改应用调用而留下旧函数公开，也不能全撤销豁免 RPC 使现行审批失效。

**通过标准**：每个旧重载均拒绝普通直调或等价进入现行原子流程；同队审批、部分日期审批、打回、授权撤销和重复操作保持原业务定义；主单/逐日/授权/档案投影一致，故障注入时整批回滚。历史分叉数据不在本轮自动修补。
