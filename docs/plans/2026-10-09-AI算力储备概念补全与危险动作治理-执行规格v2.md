## 二、P0 · 概念缺陷与危险动作

### P0-1 「全站用不用」和「这条线供不供」必须拆成两件事

**现状（实测）**：全站只有一个开关承载两件事。
- 模型卡上的「在册/下架」开关与「模型管理与上下架」弹窗里的勾选框，接的是同一个处理函数、同一个后端动作；
- 那个动作是把这条模型在**所有渠道**上的同一个开关一起推上去或拉下来；
- 系统里不存在"全站上架"的独立记录，"这个模型现役吗"是从"有没有任何一条渠道开着它"**推导**出来的。

**后果（三个 P0 同根）**：下架再上架会点亮所有渠道；取消勾选表达不了"从此不供"；检测面里混着从不参与业务的模型。

**需要用户能表达（v2 压成两个独立状态）**
1. **渠道级**：这条线供不供这个模型。由这条线的 owner 决定，会被记住。
2. **全站级**：这个模型全站现在要不要用。只影响业务能不能解析到它，**不改动任何一条线的渠道级决定**。

（草案的意图 2「临时收起」和意图 3「恢复原样」不是新状态——只要"下架不碰渠道级开关"成立，"恢复"自动成立，不需要快照。）

**必须满足的约束（代替草案"允许改动数据层"这句无限授权）**
- 对全站级开关做开→关→开这一圈，**每一条线的渠道级状态逐条不变**。这是硬约束，任何实现形态都必须满足。
- 迁移时**不得猜测历史意图**：今天所有"关着"的线路记录，混杂着"用户主动关的""全站下架连累的""上游已不提供的"三种来历，数据上已不可区分。它们一律按「未表态」落，**不得据"未表态"在任何后续全站动作里被自动点亮**。
- 合成口径要重定并写进《数据口径》：**某个业务能不能用上这个模型 = 全站级要用 AND 这条线供**。上半部业务功能调度、模型视角的"N 渠道可用"、渠道视角的挂载清单，三处必须显示同一个数。草案没定这条，改完会出现"下架期间能否给某条线单开供应"两种相反解释。

**验收判据（可观察，施工方自证 + Claude 复验）**
- 在渠道 A 关掉模型 X 的供应 → 对 X 执行全站下架 → 再全站上架 → 回到渠道 A，X **仍为关**；同渠道其余模型状态逐条不变。
- 全站下架期间，任一业务的"可用渠道数"为 0；此时在渠道 A 把 X 勾上，该业务的可用渠道数**仍为 0**（全站级未开），且页面必须能说出"这条线已就绪，但模型全站未启用"——**不许静默**。

**依赖**：P1-4、P1-5、P2 的「现役」归一三条**必须等本条口径定稿**才能开工，否则会返工（见第七节）。

### P0-2 接入点管理只允许两处写入口，停与删必须说清连锁后果

**现状（实测）**：管理接入点的入口有**三处**，且全部自称"渠道"。

| 位置 | 实际操作的层 | 界面自称 |
|---|---|---|
| 齿轮 →「渠道管理」弹窗 | 接入点 | 标题「渠道管理」、按钮「新建渠道」、开关「是否启用渠道」、按钮「保存渠道」 |
| 渠道工作台 · 接入资料区 | 接入点（改 API 地址） | 「已更新接入点 API 地址」（这一处说对了） |
| 渠道工作台 · 下拉 | 渠道（改所属接入点） | 「所属接入点」（说对了） |

最危险的一条：**在「渠道管理」弹窗里点「是否启用渠道」，停的是整个接入点**——该服务商下所有线路一起停，全站相关业务瞬间无可用算力，且没有任何提示告诉用户按错了。删除同理：弹窗里删的是接入点，toast 写的是「已删除渠道「X」，5 秒内可撤回」。

**需要用户能表达**
- 「停这一条线」与「停这个服务商下的所有线」是两个动作，不能同名、不能长一样、不能在同一层界面里顺手做。
- 接入点的写入口**只允许两处**（详见第十一节裁决②）：渠道工作台只读展示归属并提供改所属 / 改接入资料，接入点管理弹窗提供停 / 启 / 改名 / 改接入资料。**不允许第三个。**

**验收判据（可观察）**
- 从任何界面停/删一个接入点，**执行前**必须出现一段列出真实对象的提示：它下面哪几条渠道（名称逐条）、涉及哪些业务功能（名称逐条）。提示里只写"共 N 条"视为不通过。
- 全站搜索「是否启用渠道」这一句，命中处必须能一句话说清"关掉的是渠道还是接入点"，两句完全相同的文案不允许存在。
- 停一个接入点后，其下每条渠道在业务功能调度那一栏的变化可被逐一核对（不许"整片红但说不出为什么"）。

### P0-3 上游已不提供的模型：要能收走，但**不许据单一信号自动判定**

**现状（实测）**
- 同步**只登记新增、从不回收**：`sync-models/route.ts:118` 只有 `toInsert`，没有任何回收分支。
- 幽灵模型是真实存量：`api tang ChatGPT` 上游清单只给 5 个、系统挂 8 个，其中 3 个稳定报 404；`api1 default` 挂 **21 个**死模型。全池共 **127 个**挂载关系。
- 取消勾选也不收走：行仍留在清单里，继续出现在检测面里。

**草案说"清算不需要新增采集"——这句话要收回。** 唯一可用的比对依据 `available_models` 有三个硬伤：
1. **只在同步成功时写入**。同步失败即抛错退出，该字段不更新（`sync-models/route.ts:134-138`，失败分支见 `:40-68`）；全池同步里单条失败只记进 failed 列表。
2. **空值与"上游确实返回空清单"不可区分**。据此判"上游全不提供了"会得出荒谬结论。
3. **上游清单本身不完整**：实测出现过清单只列 5 个、而其中 3 个真实调用是 404 的渠道——清单口径与能不能用是两件事。

**产品口径**
- 「上游已不再提供」必须**两个独立信号同时成立**才算：清单里没有 **且** 实测调用不通。只有清单依据的，降级为「疑似，未验证」，**不得进入可一键收走的列表**。
- 没有成功同步过、或清单为空的渠道，该状态一律显示**「未知 · 尚未成功同步」**。**禁止用 0 冒充"很干净"**。
- **不承诺自动发现。** 时效承诺换成一条可核事实：**每次同步成功后，当次必须对该渠道给出「已核对 / 未知」二选一的结论**，不许沉默。

**收走的防护必须与删渠道对称**（今天删渠道有依赖闸：`此密钥正在被【X】使用且无备用模型，禁止删除`；而收走单个"渠道×模型"破坏半径相同，却**没有任何闸**）。
- 收走 = 删除这行的供应关系。若该模型全站只有这一条线挂着、且正被业务解析使用 → 收走的瞬间该业务断供。此类情形必须**拦下并说明原因**，或强制先走"换模型"引导。
- 收走要有执行前确认（见第五节闸门要求）。
- **收走的留痕**：必须能事后回答"这个模型当初是被谁、在哪天收走的"。理由：`api1 default` 那 21 个死模型的来历今天已经查不到了，不能再制造一次。

**验收判据（可观察）**
- 在 `api tang ChatGPT` 上，页面给出的"待收走"数量 = **3**（清单没有且实测 404 的那三个），不是 5、不是 0。这条是本轮唯一带真实期望值的判据，施工方必须逐条对上。
- 对一条从未成功同步过的渠道，页面显示「未知」，**不显示 0**。
- 收走一个"全站唯一线路且业务在用"的模型 → 被拦下，并给出原因与下一步入口。

### P0-4 检测只测在用的，且不许改变供给

**根（已复核，草案写对了）**
- 检测不是只读的：失败会写健康状态。
- 超时被归类为**渠道级**故障（`classifyProviderFailure` timeout → `key`，`provider-health.ts:25`）。
- **成功不洗白**：模型级检测通过只写模型行（`route.ts:535-536`），不写渠道行；只有渠道级连通测试才洗白（`:465`）。→ **这个按钮只会让渠道变红，永远不会让它变绿。**
- **连败即退出调度**：`consecutive_failures` 达 3 且无到期时间 → 判定为不可用（`isProviderKeyModelHealthy`，`provider-routing.ts:170-183`，注释自称"健康冻结 5 分钟"但这条路径不写到期时间）。

**已定口径**
1. 检测只测**上架中的**。
2. **不参与业务的模型的失败，一律不得计入业务健康度。**
3. **反复点检测，系统的实际供给关系与调度行为不许发生任何变化。**（草案的"可以放心反复点"是软承诺；这一条是它的硬版本，并直接对上第 4 个根因——检测写的是调度真正读的字段，"不改健康熔断语义"这句挡不住它。）
4. 检测通过要能洗白：一条渠道上只要有一个在用模型探测通过，该渠道不得停留在"故障"显示上。

**验收判据（可观察，全部为硬断言）**
- 检测执行前后，业务功能调度那一栏的**数字与颜色逐格相同**。出现任何一次"点出来的红"即不通过。
- 对同一条渠道**连点 5 次**检测，该渠道及其下所有模型的"可用渠道数"零变化。
- 检测**通过**后，渠道显示从「故障」回到「健康」，不需要额外再点别的按钮。
- 空结果反向断言：全池 0 个模型时，**禁止**显示「全部渠道模型检测通过（测了 0 个模型，覆盖 0 个渠道，全部正常）」——这句今天真实存在（`compute-pool-panel.tsx:411`），上一版返工专门骂过 0/0，判据却漏写，本轮补上。

### F-1 · 新增缺陷：「测试连通」这个按钮测的不是它说的（草案未发现，实测核出）

**事实**：模型视角渠道行的按钮文案「测试连通」、tooltip「只测通不通，最快」，实际调的是 `testKeyModel` → `test_key_model`，即**测"这条线供这个模型"**（`model-family-card.tsx:116-122, 558` + `compute-pool-panel.tsx:656`）。它连的是模型标识、写的是模型级失败计数。
**并且**：前端规格 §4.1 的映射表写的是「测试连通」→ `test_key`（渠道级）。**规格说一套，代码做一套。** 渠道级的那个动作今天只剩业务页的「试跑」在用。

**为什么是 P0 而不是改名**：阿禅按 tooltip 理解"只测通不通"，点完看到某模型未通过，会得出"这条线整体没问题、是模型的事"；而实际语义相反——这一测本来就是针对那个模型的，还会给它记一次失败。**他会用错误的因果做换线决策。**

**处置**：并入 P0-2 的"同一句文案不许指向不同对象"一起收，且**必须同步修正规格 §4.1 映射表**，不允许只改代码或只改文档（否则下一轮又是两本账）。

## 五、横切要求 · 危险动作的执行前确认闸门

草案五轮 P0 全在描述动作**之后**的界面，没有一个动作描述**之前**。误停、误收、误覆盖是本轮唯一会伤到线上业务的三类动作，必须先有闸。

**适用**：停/删接入点、收走模型供应、全站下架、跨渠道批量启用。

**闸门最低要求**
1. 执行前显示**被牵连对象的真实名单**（渠道名、业务功能名逐条列出），只给计数不给名单视为不通过。
2. 提供**更窄的替代动作**（"只想停这一条线？"），不能只给"确定/取消"。
3. 破坏半径不明时（清单未同步、依赖未知）**默认拒绝执行**，并说明为什么不能确定。

**判据**：上述五类动作逐一实操，每一类都要能拦在一次点击之后、写入之前看到名单。

## 十一、三条冻结裁决（两份任务书必须逐字一致，任何一方不得自行改判）

### 裁决① 那个名不符实的按钮：**改名字，不改行为**

模型视角渠道行的这个按钮，行为保持"测这条线供这个模型"不变，**文案与提示语改为说清这件事**；同时**修订前端规格 §4.1 的映射表**，让文档与代码一致。
**为什么不改行为**：改成渠道级测试会让人在模型行上看不出自己测的是哪个模型，且会把渠道级失败写进一个本该按模型判断的位置。
[CX] 不得自行改这个按钮实际调用的动作；[An] 不得自行改成别的措辞或再造一个同义按钮。

### 裁决② 接入点管理**允许两处写入口**

渠道工作台可**只读展示归属**并提供改所属接入点 / 改接入资料；接入点管理弹窗提供停 / 启 / 改名 / 改接入资料。**不允许第三个写入口。**

### 裁决③ 危险动作的确认信息必须在执行前、且必须是名单

凡会一次影响多条线或多个业务的动作，执行前必须显示**被牵连对象的真实名称逐条列出**＋一个更窄的替代动作；**取不到完整名单时默认拒绝执行**并说明为什么不能确定。只给计数、只给"确定/取消"、或把名单塞进 toast，一律算不合格。
[CX] 不得因依赖计算成本高而降级为只报数字；[An] 不得为省版面把名单折叠成"展开查看"。
