## 0. 这份文件怎么用

本文件是移动端适配的唯一总控入口，同时承担五件事：

1. 保存后续不能丢失的架构、范围和验收上下文。
2. 维护全站移动适配目录、任务编号、负责人和完成进度。
3. 作为向 Antigravity、GLM 发提示词时的共同依据。
4. 记录每次执行、验收、返工、提交和剩余问题。
5. 区分“完整修复”“止血未完整”“预存问题”“新增问题”。

后续所有移动端提示词必须引用本文件中的任务编号，并在提示词中明确要求执行方读取本文件。它不写入全局 Agent 索引，避免所有无关任务都被迫加载。代理开工和收工都必须更新任务账本，并在文末追加执行记录。旧移动端交接文档只作历史线索，不再作为当前完成状态依据。

### 0.1 更新纪律

- 不删除历史执行记录；结论变化时追加更正。
- 任务状态只使用：`未开始`、`待提示词`、`执行中`、`待验收`、`返工中`、`已完成`、`已暂停`、`已取消`。
- “代码写完”不是“已完成”。必须同时具备代码结果、验收命令、真实移动视口证据和未完成项说明。
- 每次任务开始：更新任务状态、负责人、预计影响文件。
- 每次任务结束：更新进度汇总、任务卡、验收证据，并在“执行记录”追加一条。
- 项目主日志 `日志/YYYY-MM-DD.md` 只记一句摘要；完整细节留在本文件。
- 同一组共享文件同一时间只允许一个执行方修改，避免 Antigravity 与 GLM 互相覆盖。
- [CX] 负责拆批、发提示词、控制依赖和最终验收；执行代理不能自行领取或扩展到下一批。

## 1. 目标、边界与当前判断

### 1.1 本轮真实目标

不是另做一套 App，也不是把桌面页整体缩小，而是让现有业务在小屏设备上形成完整任务闭环：

- 用户能找到当前角色最常用的入口。
- 页面在 320px 起不横向溢出，不被刘海、底部手势区或软键盘遮挡。
- 表格、筛选、抽屉、弹窗和固定操作区在手机上可读、可点、可返回。
- 数据、权限、提交、审批、导出和错误状态继续复用网页端真实契约。
- 桌面端行为不因移动适配退化。
- 后续每批改动都有可重复的自动门禁和人工验收证据。

### 1.2 “App 端”的定义

当前仓库是 Next.js 响应式网页，不是原生 App，也没有完整 PWA 能力。目前未发现可安装清单、Service Worker、离线缓存或系统推送闭环。

因此本总纲默认：

- 手机：宽度 `< 768px`，采用移动任务视图。
- 平板：重点验证 `768×1024` 与横屏，按页面密度决定沿用桌面视图还是进入中间布局。
- 桌面：`≥ 1024px`，保持现有网页端体验。
- PWA、原生壳、离线、推送：列入 M5 决策，不与当前适配混做。

如果阿禅后续明确要“安装到桌面”“离线可用”或“原生 App”，需要单独立项，不能把响应式完成误报为 App 产品完成。

### 1.3 本轮明确不做

- 不复制一套移动端 API、权限判断、缓存或业务状态。
- 不为移动端伪造数据、替换真实接口或绕过失败状态。
- 不把所有宽表简单改成横向滚动后宣布完成。
- 不在本轮深改即将重写的 `/growth` 和 `/content-tools/rewrite`；只修影响使用的 P0 阻塞。
- 不在视觉任务中改数据口径、权限、请求流程或业务提交行为。
- 不在非视觉任务中自行重做视觉风格。

## 2. 当前代码基线与核心问题

### 2.1 已有能力，继续复用

仓库不是从零开始，已有以下移动基础：

- `src/components/mobile-tab-bar.tsx`：移动底部导航。
- `src/components/mobile-more-drawer.tsx`：移动“更多”抽屉。
- `src/components/ui/adaptive-sheet.tsx`：按视口切换的抽屉基座。
- `src/styles/tokens.css`：移动导航和安全区相关 Token。
- `src/app/(app)/layout.tsx`：为底部导航预留内容空间。
- 第一批员工页已有零散响应式处理。

本轮先修正和统一这些能力，不另起炉灶。

### 2.2 核心问题清单

| 编号 | 核心问题 | 实际影响 | 处理方向 |
| --- | --- | --- | --- |
| P0-01 | 移动导航由桌面分组机械截取前四项 | 不同角色的高频任务可能被藏进“更多”，导航不代表真实工作流 | 基于任务优先级配置，但继续复用现有权限可见路由 |
| P0-02 | 顶栏与“更多”抽屉重复放置通知、账户等入口 | 小屏空间浪费、入口认知重复 | 统一移动信息架构，只保留一个主入口 |
| P0-03 | 底栏、Toast、批量栏、弹窗按钮等固定层缺少统一安全区规则 | iPhone 手势区、刘海或软键盘可能遮挡关键操作 | 建立安全区、键盘和层级契约 |
| P0-04 | 管理页大量宽表和矩阵依赖桌面横向结构 | 手机端只能缩字或横向拖动，无法完成操作 | 桌面表格与移动任务卡共享同一控制器 |
| P0-05 | 点击热区没有全局移动标准 | 小图标按钮难点中，误触率高 | 在组件层统一移动端最小热区 44×44px |
| P0-06 | 现有响应式测试以源码正则为主 | 静态测试通过不代表真实页面没有溢出、遮挡或错位 | 增加移动 Playwright 项目和真实尺寸断言 |
| P0-07 | 历史交接对完成状态相互冲突 | 容易把旧组件或旧截图当作当前页面已适配 | 从当前代码和真实浏览器重新建基线 |
| P0-08 | Dashboard 已切换到 V2，旧适配主要针对已删除的 V1 | 核心填报页可能名义已完成、实际未覆盖当前实现 | 以 `VideoSubmitPanelV2` 重新验收 |
| P1-01 | Loading、空态、错误态、超长内容缺少移动矩阵验收 | 正常数据看起来可用，异常状态仍可能断链 | 每页按完整状态矩阵验收 |
| P1-02 | `/growth` 与 `/content-tools/rewrite` 已计划重写 | 现在深度适配会产生重复成本 | 当前只做 P0 止血，重写时完成结构适配 |

### 2.3 当前结论不能被误读

- 历史提交和交接证明“做过移动工作”，不证明当前版本“移动端已完成”。
- 现有静态响应式检查通过，只能证明部分源码规则存在，不等于真实浏览器通过。
- 当前网页端已经具备成熟数据和权限契约，移动适配的重点是视图、交互容器和验收体系，不是重做后端。
- 管理页的核心矛盾不是配色，而是桌面信息架构无法直接缩进手机。

## 3. 总体架构

### 3.1 单业务系统、双视图

```text
现有 Loader / API / 权限契约
              ↓
页面 Controller（唯一的数据、状态、动作、错误来源）
              ↓
      ┌───────┴────────┐
      ↓                ↓
Desktop View      Mobile Task View
      └───────┬────────┘
              ↓
响应式组件 + 移动 Shell + 浏览器门禁
```

原则：同一业务只有一套数据和动作。复杂页面允许桌面表格与移动卡片使用不同视图，但不允许两套视图各自发起重复请求、维护不同权限或复制业务判断。

### 3.2 全局基座

| 基座 | 职责 | 预期归属 |
| --- | --- | --- |
| `MobilePageShell` | 统一顶部、底部、安全区、固定层和键盘底部空间 | [GLM] 逻辑，[An] 视觉 |
| `mobileNavigationConfig` | 按角色和任务排序移动入口，路由可见性继续源于现有导航权限 | [CX] 契约，[GLM] 实现，[An] 呈现 |
| `ResponsiveDataView` | 桌面表格与移动卡片共享数据、选中态和操作 | [GLM] |
| `MobileFilterSheet` | 手机上统一筛选、重置、确认与已选条件反馈 | [GLM] 逻辑，[An] 视觉 |
| `MobileActionBar` | 统一主要操作、批量操作和安全区 | [GLM] 逻辑，[An] 视觉 |
| `AdaptiveSheet` 扩展 | 统一 Drawer / Sheet 的尺寸、返回、焦点和键盘行为 | [GLM] 逻辑，[An] 手感 |
| 移动浏览器门禁 | 检查溢出、热区、固定层、角色导航和桌面回归 | [GLM] 建设，[CX] 终验 |

名称是规划名，不要求实现时机械照搬。开工前先查现有组件，能扩展就不新增。

### 3.3 页面改造模式

- 简单页面：一套 DOM，用响应式布局调整。
- 中等页面：共享 Controller，局部切换桌面/移动组件。
- 宽表、矩阵、批量操作页：Desktop View 保留表格；Mobile Task View 改为摘要卡、逐层查看和聚焦操作。
- 详情与编辑：优先复用 `AdaptiveSheet`；手机全高、桌面侧边抽屉。
- 筛选：桌面行内筛选；手机集中到 `MobileFilterSheet`，主页面只显示生效条件摘要。
- 批量操作：手机仅在进入选择态后显示 `MobileActionBar`，不能长期占用首屏。

## 4. 角色分工与交接边界

### 4.1 [An] Antigravity

负责“怎么看起来、摸起来”：

- 移动视觉层级、留白、字号、卡片密度。
- 导航、筛选、抽屉、弹窗、固定操作栏的布局和动效节奏。
- 不同宽度下的视觉收敛和桌面回归。

禁区：

- 不改 API、数据结构、权限、缓存、业务状态机和提交规则。
- 不用假数据掩盖真实空态或失败。
- 发现逻辑问题时写入执行记录，交给 [GLM]/[CX]。
- 动手前必须读 `docs/Claude设计哲学.md` 与 `docs/Claude设计规范.md`。
- Antigravity 改动必须经阿禅确认后才允许推送。

### 4.2 [GLM] GLM-5.3-Flash

负责非视觉主力执行与第一轮验收：

- 共享响应式组件、移动状态映射、导航逻辑、安全区和软键盘处理。
- 保持前后端字段、按钮动作和错误处理闭环。
- 建立并运行移动浏览器门禁。
- 对 Antigravity 结果做功能、回归和可操作性验收。

GLM 每次只接收一个已编号批次。第一次参与移动任务时完整读取本总纲；同一连续会话后续至少重读第 4、6、7、8 节、当前任务行和新增执行记录。总纲是 GLM 的上下文和验收依据，不代表把总调度权交给 GLM。

禁区：

- 不自行改变业务口径、权限模型、RLS 或 API 契约。
- 不复制移动专用请求链路。
- 不以静态类名扫描替代真实浏览器验收。
- 不在未登记任务编号时批量改全站。
- 不自行拆分、合并、领取或发放后续批次。
- 不把自己的第一轮验收直接登记为最终验收通过。

### 4.3 [CX] Codex

负责架构和终验：

- 统一划分批次、逐批生成提示词、控制文件边界、维护本总纲。
- 开工前核对当前代码和真实调用链，给出受影响文件与风险。
- 审查共享架构、业务契约、性能和测试覆盖。
- 对 [GLM] 验收结果进行独立复核；没有 [CX] 终验，不把任务改为“已完成”。
- 根据上一批证据和未完成项决定下一批是否发放，避免连续放大错误。

### 4.4 阿禅

- 决定产品取舍、任务优先级和争议方案。
- 确认 Antigravity 改动和最终视觉方向。
- 明确是否推送 main，以及 PWA/原生 App 是否另行立项。

### 5.2 第一优先任务路径

移动端首轮优先保障员工高频闭环：

1. 登录后找到首页和核心任务。
2. Dashboard 填报、查看状态、处理失败。
3. 选题库浏览、筛选、查看详情和执行已有操作。
4. 查看通知、审批或个人账户入口。
5. 正确退出、返回和深链恢复。

管理端第二轮优先保障：异常处理、内容诊断、协作管理、视频管理。系统级配置放在最后。

## 7. 统一验收标准

### 7.1 设备矩阵

每个核心任务至少覆盖：

- `320×568`：最窄手机基线。
- `375×667`：常见小屏。
- `390×844`：当前主验收尺寸。
- `430×932`：大屏手机。
- `768×1024`：平板竖屏。
- `1024×768`：平板横屏 / 小桌面边界。
- `1440×900`：桌面回归。

### 7.2 硬性通过条件

- 页面根节点和关键业务区无意外横向溢出。
- 移动端交互热区实际尺寸原则上不小于 `44×44px`；隐藏 input、非交互标签等需明确排除。
- 高频任务从落地页到主操作不超过两次明确点击。
- 刘海、底部手势区、浏览器工具栏和软键盘不遮住输入框、主要按钮或提示。
- 底栏、Toast、批量栏、Drawer、Dialog 不互相盖住，层级稳定。
- 宽表不能仅靠缩小字号解决；只有任务卡明确批准时才允许保留横向滚动。
- Loading、空态、错误态、超长文本、大数据量、权限不足都能正确呈现。
- 提交、审批、导出、删除、编辑等动作有真实后续结果，不以 Toast 代替闭环。
- 前后端字段、权限范围、缓存和数据口径与桌面端一致。
- 桌面端主要流程、布局和性能不回退。
- 不新增无必要请求，不同时挂载两套会重复拉数的视图。

### 7.3 角色与状态矩阵

至少以以下身份验证：

- 普通成员。
- 运营或管理角色。
- Company Owner / 最高权限角色。

每个页面按实际能力验证：首次加载、刷新、返回、深链、筛选、编辑/提交、失败重试、无数据、权限不足。不存在的能力不造测试假象。

### 7.4 性能边界

移动适配不能推翻现有性能总纲。继续遵守：

- 页面只有一个加载协调层。
- 首屏只拉首屏数据，详情和弹窗按需加载。
- 不因桌面/移动双视图重复请求。
- 保持 `docs/架构与性能总纲.md` 中各页面预算；移动网络实测另记环境，不把本地热缓存成绩冒充生产结论。

### 7.5 验收命令与证据

当前通用门禁：

```bash
npm run gate:static
npm run gate:browser
```

`gate:browser` 目前以桌面代表页为主，不能独立证明移动端完成。M1-04 完成后，应新增稳定的移动门禁命令；在命令建立前，每个任务提示词必须给出明确的 Playwright 视口、路由、身份和交互步骤。

证据至少包含：

- 执行命令和结果摘要。
- 浏览器环境：本地开发、本地生产构建或 Vercel 生产。
- 实测视口、角色和关键状态。
- overflow、热区、固定层等自动断言结果。
- 截图或视频仅作辅助，不能替代交互断言。
- 未实测生产环境时必须写“未实测”，不能推断通过。
- 不提交带真实业务隐私的截图、登录态或测试凭据。

## 8. 提示词发放顺序

### 8.0 调度归属

- [CX] 是移动适配的总调度：负责拆批、确定先后依赖、为 Antigravity/GLM 分别生成提示词，并维护总进度。
- [GLM] 是非视觉主力和第一轮验收方：只执行收到的当前批次，并验证 Antigravity 的功能闭环与回归。
- [An] 是视觉执行方：只执行收到的当前视觉批次。
- 阿禅负责转交提示词、确认视觉和产品取舍。
- 总纲要给两类执行方，但用途是共同约束和上下文，不是让任何一个执行方自行管理整套任务。

读取方式：新会话第一次接任务时完整阅读本总纲；连续会话后续可按提示词指定章节增量读取。每份提示词仍需完整写明当前任务的目标、范围、禁区和验收，不能只写“按总纲执行”。

### 8.1 推荐顺序

1. **GLM：M0-03 基线审计。** 只测不改视觉，形成当前失败清单和页面分级。
2. **GLM + CX：M1-01/02 契约。** 先定导航、安全区和固定层行为。
3. **Antigravity：M1-05 全局 Shell 视觉。** 在确定的业务契约上执行布局和手感。
4. **GLM：M1-03/04。** 收口共享逻辑并建立移动门禁，验收 Antigravity 结果。
5. **Antigravity → GLM：M2-01/02。** 先做 Dashboard、Topics 视觉执行，再做逻辑收口和自动验收。
6. **Antigravity → GLM：M3 各管理页。** 一页一批，视觉和非视觉顺序交接，不并发改共享文件。
7. **M4 低频配置。** 前面基座稳定后再批量复用。
8. **M5 决策。** 响应式完成后再决定是否需要 PWA 或原生 App。

### 8.2 每份提示词必带内容

- 任务编号、目标和用户价值。
- 开工必读文件。
- 当前代码事实和已知风险。
- 允许修改的路由、组件和文件范围。
- 明确禁区。
- 业务闭环要求；涉及前后端时写明同步核对。
- 验收命令、视口、角色和状态。
- 留痕要求：更新本文件任务账本、进度和执行记录。
- 提交与推送边界。

没有任务编号、不写验收、不写禁区的提示词不发出。

### 8.3 共享文件冲突规则

- 导航、Layout、Token、AdaptiveSheet、Playwright 配置视为共享文件组。
- 共享文件组任务按顺序施工；后一执行方先读取前一方最新提交和执行记录。
- Antigravity 只改视觉时，也要写明是否触碰共享组件行为。
- GLM 验收发现视觉返工时，只登记问题和逻辑证据，不擅自重做设计；由 Antigravity 返工。
