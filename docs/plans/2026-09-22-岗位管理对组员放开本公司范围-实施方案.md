# 岗位管理对组员放开「本公司范围」实施方案（2026-09-22，v2）

> 状态：**待施工（v2 已修正第一轮审查的 3 项阻塞；第 10 节 D-1~D-6 已于 2026-09-23 全部裁定，具备开工条件）**。阿禅已确认思路：岗位管理页面对组员放开，能看本公司所有人的数据，不再只有自己。
> 性质：权限 / 数据范围改动（高风险），施工前需完成第 8 节验收。
> 配套：`2026-09-22-岗位管理对组员放开本公司范围-需求实现提示词.md`（供独立对话做方案审查，v2 已同步更新）。
> 术语：本文「本公司」= 该账号 `team_id` 指向的范围（`docs/权限与安全说明.md` A.1）；「集团」= 跨公司，仅公司所有者在集团模式可进，本次不涉及。
> 修订：v1 → v2 的逐条裁定见第 11 节。

---

## 1. 目标

组员（`company_role = member`）打开 `/admin/collaboration` 时，看到**本公司全体成员**的岗位数据：四个页签（达人 / 运营 / 文案 / 剪辑）、首屏汇总、个人档案卡、作品明细、待补归属弹窗、按团队视图。

**明确不做**：

- 不改全局数据范围（组员在数据分析 / `growth` / 导出 / 工作台仍只看自己）。
- 不给组员任何写权限。
- 不改视频复盘（`/admin/content`）的权限。
- 不动集团模式（`kind === "all"`）行为。

## 3. 不采用的路线（含第一轮审查确认）

### 3.1 不改全局数据范围

`inferDataScope()` 对 `member` 返回 `self`（`data-access-scope.ts:54-65`）。改成 `team` 会连带放宽：数据分析 / `growth` / 导出、以及 **12 处 `requireAdminActor()` 不传 `requiredPermission` 的接口**（「有任意一项权限即放行」，`auth-helper.ts:44-46`）；其中 `content/comparison-members`、`cockpit/_shared`、`production/_shared`、`admin-scoped-video`、`video-lifecycle` 的可见对象直接来自该范围。权限文档 A.2 / A.6.1 的定义也会整篇失效。**不采用。**

### 3.2 不激活既有 `perspective` / `teamId` 参数

`getCurrentPermissionContext(perspective, teamId)` 与 `buildPermissionContextForActor(actor, { perspective, teamId })` 确实带这两个参数，但：

- `buildDataAccessScope` **完全不读** `options.perspective`，且显式忽略 `options.teamId`（`data-access-scope.ts:109,126-135`，注释写明「Request parameters must never create or replace an actor's team assignment」）→ 传参不会改变 `visibleUserIds`。
- 该机制的真实用途是集团模式公司所有者的「按公司 / 按公司下某队」视角切换（`content/page.tsx:33-45`，`canSwitchPerspective = perm.groupMode === true`），与组员无关。
- 它的入参来自 URL（`content/page.tsx:33` 的 `params.scope`）。把它激活成「能放宽范围」，等于让 URL 参数改变数据范围，属安全倒退。

**不采用。本次新增一个显式的、模块限定的解析函数（见 4.1）。**

## 4. 施工设计

### 4.1 范围解析落在唯一入口 `src/lib/data-access-scope.ts`（先做）

项目硬约束：**「成员可见性 / 协作者范围判断的唯一入口」是 `src/lib/data-access-scope.ts`，禁止在各接口内联实现 `team_id` / `data_scope` 范围逻辑**（`docs/权限与安全说明.md:318`，B.5；该节同时把 `/api/video-submit`、`/api/dashboard/operator-members` 的独立实现点名为**已知架构债务**）。

因此解析函数**不放在 `_shared.ts`**，而是落在 `data-access-scope.ts`，岗位管理模块（页面与接口）只消费结果、不做任何 `kind` / `team_id` 判断。

新增导出：

```ts
/** 岗位管理模块（/admin/collaboration）的可见范围解析结果。 */
export interface CollaborationScopeResolution {
  visibleUserIds: string[];
  activeVisibleUserIds: string[];
  /** true = 该账号在本模块内仍只看自己（无公司归属的安全降级）。 */
  restrictToSelf: boolean;
}

/**
 * 岗位管理模块的可见范围。
 * 唯一判定处：调用方只消费结果，不得自行判断 kind / team_id。
 * 当前唯一调用方：/admin/collaboration 页面与其 3 个只读接口。
 */
export async function resolveCollaborationScope(
  supabase: ScopeSupabase,
  scope: DataAccessScope,
): Promise<CollaborationScopeResolution>;
```

规则表（**唯一判定依据**）：

| `scope.kind` | `scope.teamId` | `visibleUserIds` | `restrictToSelf` |
|---|---|---|---|
| `"all"`（集团模式所有者） | — | `scope.visibleUserIds`（原样） | `false` |
| `"team"`（组长 / 所有者） | 有 | `scope.visibleUserIds`（原样） | `false` |
| `"self"`（组员） | **有** | 本公司可见成员 id（**本次新增行为**） | `false` |
| `"self"`（组员） | 空 | `[scope.userId]` | `true` |

`activeVisibleUserIds` 一律取与 `visibleUserIds` 同一批行经 `filterActiveMemberships` 过滤后的 id，`all` / `team` 时沿用 `getActiveVisibleUserIds(scope)`。

**结构同源要求（不靠口头约定）**：把 `buildDataAccessScope` 现 `kind === "team"` 分支的加载逻辑（`data-access-scope.ts:152-174`）抽成**模块私有**函数供两处共用：

```ts
async function loadCompanyVisibleRows(supabase: ScopeSupabase, teamId: string) { … }
```

- 函数体 = 现 152-174 行**原样搬运**：并行两查（`profiles.eq("team_id")` + 全量 `profiles` 取 `membership_status, archive_snapshot`）→ 只保留 `membership_status === "archived"` 且 `archive_snapshot.team_id === teamId` 的归档行 → 与队内行合并。
- **`archive_snapshot` 的查询与过滤必须在函数内部保留**（这是范围口径的一部分，不能因为返回类型里没有该字段就省掉）。返回类型只需 `{ id, membership_status }` —— 归档行最终只进 `visibleUserIds`，经 `filterActiveMemberships` 后不进 `activeVisibleUserIds`；但这一点由测试断言守住，不靠推理。
- **不导出**该函数（减少被误用面）；`buildDataAccessScope` 的 team 分支改为调用它 → 「组员放宽后的范围」与「组长范围」在结构上同源。
- 重构完成后的行为不变性由 4.1 与第 6 节的测试独立验证，**不预先声称"无行为变化"**。

## 6. 测试

### 6.1 新增（`data-access-scope.test.ts` + collaboration 相关测试）

1. `resolveCollaborationScope`：`kind="self"` + 有 `teamId` → 返回本公司可见成员 id；**含** `archive_snapshot.team_id` 属本公司的归档行，**排除**他公司归档行。
2. **结构同源**：同一 `teamId` 下，组员解析结果 `visibleUserIds` == 该公司 admin 的 `scope.visibleUserIds`（保证抽取重构与放宽口径一致）。
3. `kind="self"` 无 `teamId` → `restrictToSelf === true` 且 `visibleUserIds === [userId]`。
4. `kind="team"` / `kind="all"` → 两个集合与 `scope` 原值完全一致，`restrictToSelf === false`。
5. **全局未被放宽（防误用的核心断言）**：`inferDataScope("member") === "self"`；`buildDataAccessScope` 对 member 返回的 `scope.kind === "self"` 且 `scope.visibleUserIds` 仍只有自己。
6. **同源消费断言**：`buildUnattributedResponse` 的范围来源与首屏一致（注入假 `buildPermissionContextForActor`，断言两者拿到同一个 `visibleUserIds`）。
7. **拒绝边界继续成立**：`attribution`（member 403）、`writer-certification`（member 403）、`work-group-write`（member 403）、`work-video`（member 403）。
