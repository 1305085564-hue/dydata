# 不参与考核（发布豁免）· 规划思路 —— 交 Codex

> 状态：**规划思路，未施工**。请 Codex 审查本思路、补出完整执行计划并实现；需阿禅拍板的取舍已在 §5、§6 标出，先对齐再落地。
> 本文引用的文件行号为截至 2026-10-02 实测，动手前重跑 `rg -n` 取新行号（并发提交会漂移）。

## 一、痛点（业务语言）

达人文案每天要上传发布数据，这没问题；但运营、剪辑、行政**本就不靠发作品干活**，后台的"作品发布情况 / 履约 / 日报应发"里却还是把他们列进去，没数据的日子还填成"未交 / 缺席"。更麻烦的是，**达人里也有人是不发布的**——所以不能简单按岗位一刀切。

目标：给负责人一个开关，**手动标记"这个人不参与考核"**；被标的人从"要不要交数据 / 有没有交"这类看数据的页面里直接消失，也不再算缺交。

## 二、已确认的三条规则（阿禅拍板，写死）

1. **只有 company_owner（所有者）能设置这个开关**，admin 没有此权限。
2. **改动留痕**：谁在什么时候标了 / 撤了谁，必须进审计。
3. **隐藏范围的具体清单留到施工方案再定**（见 §5.3），本文不替阿禅拍。

## 三、关键发现：这套机制已经存在，禁止新造开关

实测结论——**"不参与考核"就是项目里已有的"永久豁免（permanent exemption）"，语义、数据投影、下游过滤口径全部现成，缺的只是"入口 + 权限"**：

- **数据模型现成**：源单据在 `exemption_request / exemption_grant`（`supabase/migrations/030_exemption_tables.sql`），枚举含 `'permanent'`。它投影到 `profiles` 四列：`status='exempt'` + `exempt_type('permanent'|'temporary')` + `exempt_start_date/end_date`；`008_structured_exemption.sql` 的 CHECK 约束强制 **permanent 的起止日期为 NULL（= 无限期）**，只有 temporary 才有日期区间。
- **下游过滤口径现成，且已同时覆盖履约 + 日报应发**：
  - 履约/发布战况 `get_fulfillment_range` 的 `eligible_members` 已用 `COALESCE(exempt_type,'')<>'permanent'` 把永久豁免者从"应发人整列"剔除（`20260603070000_fulfillment_workbench_backend.sql`、`20260603050000`）。
  - 今日日报应发 `get_today_submission_status` 同样排除（`008_structured_exemption.sql`）。
  - 口径文档 `docs/数据口径.md` 的"应发目标"已含豁免扣减。
- **唯一缺的是入口**：成员弹窗 `exemption-dialog-v2.tsx` 目前只能产出 `mode:'range'`（临时/请假式）；带 permanent 分支的授权 RPC `apply_exemption_grant_atomically_v2` 虽在 `20260819120000_company_role_and_group_mode.sql` 里实现了，但**前端从不触发、只有测试引用**。也就是说 permanent 是一条"模型和过滤都在、但没人能点"的半废弃能力。

**因此本次的真正工作量**：
1. 给 owner 一个入口，创建/撤销一条 **permanent 豁免**（把已有的 permanent RPC 分支接上前端触发，**不新加独立布尔列**）。
2. 权限收紧到 **仅 company_owner**（现有豁免权限是 `manage_fulfillment / review_violations`，见 `exemption-permissions.ts`，比 owner-only 宽，需另卡一层）。
3. 补齐隐藏范围盘点 + 撤销路径 + 审计留痕。

## 四、范围界定

**做**：owner 专属的"不参与考核"开关 → 复用 permanent 豁免 → 让其在 §5.3 认定的所有"看数据/考核"视图一致生效 → 撤销即时恢复 → 审计。

**不做**：不新增"是否发布岗"的岗位属性、不新建与豁免分叉的第二套"不参与考核"字段、不删任何历史数据、不改现有临时豁免/请假流程对 admin 的行为。

## 五、核心设计张力（Codex 必须解决，其中标注 ⚑ 的需阿禅拍板）

1. **走审批单据流 vs owner 直接标记**：permanent 现在挂在 `exemption_request→grant` 这套"申请→审批"单据流上。owner 自己点一个人"不参与考核"，是走这条单据流（有申请链但偏重），还是给一个"直接标记 / 直接撤销"的快捷开关（贴合"owner 说了算"，但要复用同一套 `profiles` 投影列以免两本账）？**倾向后者**，但需确认。
2. **permanent = 无限期，误设代价大**：勾上后此人长期从所有考核消失，呼应 §2 的"默认参与、显式关、留痕"。撤销入口要显眼，别让 owner 勾完找不到怎么取消。
3. ⚑ **隐藏范围清单（决策项，留给施工方案）**：permanent 目前已从"履约应发 + 今日日报应发"消失。阿禅说的"需要看数据的页面都隐藏"可能更广也可能有例外。请 Codex 逐一盘点每个按人视图并给"隐藏 / 保留 / 灰显"建议，至少覆盖：发布战况、履约工作台、日报应发/实发统计、催交名单、视频复盘按人筛选、成员数据看板、导出报表。**建议原则：只从"要不要交 / 有没有交 / 缺不缺交"类视图消失；纯历史统计与详情页保留可见，避免总数凭空对不上。** 最终范围请阿禅确认。
4. **与历史数据的关系**：隐藏人 ≠ 删除其已交数据。历史日报/发布记录仍应可追溯（审计、翻旧账）。
5. **与现有临时豁免共存**：一个人可能先请假（temporary）后被标不参与（permanent），或反之。定义清楚两者优先级与互转，别互相覆盖出脏状态。

## 六、必须防的坑（禁区）

- **禁止新造第二本账**：绝不加一个独立于 `exempt_type` 的"不参与考核"布尔列——这正是 DYData 现存最大的口径债来源。一律复用 permanent 投影。
- **改 permanent 语义前先 grep 全部引用点**：`eligible_members`、`get_today_submission_status`、应发口径、`豁免.ts` 展示（permanent 现显示为"长期"）都依赖它，改前评估连带影响。
- **别把 admin 现有的请假/临时豁免权限一起改坏**：owner-only 只卡"permanent/不参与考核"这一动作，临时请假仍按现状。
- **生产库直连与迁移纪律照旧**：迁移链账实漂移，禁 `db push`；如需改 RLS/RPC 走受控单迁移手工 apply + 登记版本。

## 七、验收建议（真实数据抽查，符合口径纪律）

- **权限**：owner 号能看到并操作该开关；admin 号看不到 / 点了被拒。
- **生效**：把某非发布成员标为不参与 → 验证其从履约应发整列消失、今日日报应发消失、催交名单不含他。
- **留档**：确认其历史已交日报/作品仍可见、总数不失真。
- **撤销**：取消标记后重新出现在应发。
- **留痕**：审计里能查到标 / 撤的操作人、时间、对象。
- **门禁**：定向测试 + 相关 loader/RPC 回归；口径改动先拿线上真实数据抽查验证假设再动。
