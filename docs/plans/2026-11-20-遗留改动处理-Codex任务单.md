## 二、判定规则（按顺序套用，命中一条就定案）

**判定单位**：未提交改动按文件判；分支提交按提交判，一笔提交里的所有文件按其中最严的那条规则定案。

**第一步：命中以下任一条，直接丢弃**（备份保留，不用另外处理）

| 编号 | 规则 | 为什么 |
|---|---|---|
| D1 | 内容和 `origin/main` 完全相同；分支提交用 `git cherry` 判定为已在主线 | 已经上线了 |
| D2 | 这个文件在 `origin/main` 上已经不存在（被删掉或挪走） | 线上已经重新整理过，以线上为准 |
| D3 | `origin/main` 上这个文件最后一次提交的时间，晚于这条遗留改动的修改时间 | 线上后来又改过并且已经上线，以线上为准。主目录那 15 处代码就属于这一类：它们早于 19:16 的上线合并，上线后的版本当晚已经由 [An] 验收通过 |
| D4 | 修改时间早于 2026-11-13（放了 7 天以上） | 主线这些天变化太大，强行合入的风险大于收益 |
| D5 | 数据库迁移文件（`supabase/migrations/`、`supabase/deferred-migrations/`），或配置、密钥类文件（`.env*`、`.mcp.json` 等） | 迁移必须单独授权才能执行，配置不进仓库 |
| D6 | 和项目无关的个人文件（例如根目录的 html 小实验） | 不属于项目。另外复制一份到 `~/Downloads/DYData根目录个人文件-2026-11-20/`，方便阿禅找到 |

**第二步：剩下的，同时满足以下四条才合入；有一条不满足就丢弃**

| 编号 | 条件 | 怎么查 |
|---|---|---|
| M1 | `日志/`（14 天前的在 `docs/archive/日志/YYYY-MM/`）里能找到对应记录，写明这项改动**已经完成**（记录里写的是进行中、待返工、被叫停、已撤销的，都不算） | 按文件名和改动内容搜日志，记下日志文件名和行号 |
| M2 | 改动是完整的 | 在临时隔离区里应用到最新 main：代码改动要求推送前六项检查全过；文档改动要求 `npm run doc:scan` 通过 |
| M3 | 和线上不冲突 | `git apply --3way` 或 `git cherry-pick` 没有冲突，不需要手工改 |
| M4 | 不改变谁能看到什么、能做什么，也不改变钱、计薪和统计口径 | 涉及权限、计薪、统计口径的文件一律算不满足（这类改动要先由阿禅立项） |

**日志文件特殊处理**：`日志/*.md` 的遗留改动，只要是主线上没有的整行记录，就追加回主线对应日期的日志里；已有的行一字不改。

**合入的方式**：每个来源单独一笔提交，提交说明写清来源目录或分支、合入了哪些文件、依据哪条日志。合完推送到 main：推送前检查必须全部通过，禁止 `--no-verify`。推送后按上线与运维「部署」一节核对线上。
