# 2026-10-12 豁免审批台修复计划

**状态**：待实施；本文件的交互调整是推荐方案，尚未作为产品口径批准。

## 目标

让管理员在桌面、键盘和手机上都能准确完成一条或一批审批，并且始终知道：当前还有多少件待处理、待办是否等于审批、历史记录是否可追溯。

本计划依据合并审计报告：[docs/archive/ux-audits/ux-audit-2026-10-12-merged.md](../archive/ux-audits/ux-audit-2026-10-12-merged.md)。本轮是施工计划，不改代码、不改数据库、不执行生产写入。

## 证据与范围冻结

### 已确认的证据

- 生产确认：筛选后明细数口径不随当前视图变化；完成待办后同源补交审批仍可操作；弹窗焦点可逃到背景，Esc 行为不稳定；历史约 50 条平铺且无检索入口。
- 本地确认：触屏/窄屏无法发现主要审批按钮；补交待办与审批卡形成一物两现；批量同意无确认；375px 中文断行；豁免历史打回无确认；审阅时间按上海业务日显示有偏差。
- 代码确认：`handleToggleTodo` 只完成通知；审批和待办由 `UnifiedCommandHub` 分流；操作行使用 hover-only；历史接口固定 `limit=50`；日期工具没有对带时间的 ISO 值显式指定上海时区。

### 本轮施工范围

- 页面：行动中枢审批工作台、待办页、已处理历史页。
- 组件：审批卡、逐日操作、补交卡、待办卡、历史卡、工作台头部、弹窗焦点与快捷键。
- 数据/接口：优先保持现有 API 和状态模型；首轮不扩审批接口/数据库；历史全量检索独立第二批实施。
- 验收角色：管理员/公司所有者、受限组员；生产写入验收需另行授权，计划先用本地隔离数据完成回归。

### 明确不做

- 不重做整个工作台视觉，不改权限模型，不引入新的审批业务类型。
- 不把本地 Playwright 结果写成生产通过，不因测试全绿跳过真实角色验收。
- 不在本轮强行实现半天审批数据模型；先保留问题并确认数据口径。
- 不把历史分页做成只在前端截断的假分页；接口没有游标/总数时先补接口契约或把它列为阻塞。
- 不改与审批台无关的模块、迁移、部署和缓存配置。

## 推荐方案与产品取舍

### 1. 补交申诉使用单一状态链（推荐）

补交申诉待办保留提醒和「去处理」入口，去到对应审批卡；不再提供独立的「完成」圆圈。只有同意/驳回审批结果才算业务结案，并由现有同源审批处理关闭待办。

理由：审批结果决定补交能否继续履约，通知完成只代表“看过提醒”，两者不能共用一个完成动作。这个方案保留提醒能力，也消除假闭环。

### 2. 破坏性操作采用一次确认 + 现有撤回

批量同意和豁免历史「打回待处理」增加确认层；单卡/单日同意继续使用当前 5 秒撤回，驳回继续要求原因。确认文案必须显示影响数量、范围和后果。

理由：批量和重开会影响多条业务状态，用户需要在动作发生前看到范围；普通单条审批已经有撤回，不再叠加多余确认。

## 当前调用链与关键约束

- `UnifiedCommandHub` → `fetchPendingApprovals` → `/api/exemptions/pending` → `splitApprovalItems/groupPendingApprovals` → `buildVisibleApprovalCards` → 审批卡。
- `summary.topItems` → `getTodoItems` → `TodoItemCard` → `handleToggleTodo` → `PATCH /api/notifications/:id/done` → “本次已处理”；它不会调用补交审批。
- `ActionItem.action.type === "review-fulfillment-appeal"` 携带 `appealId`（`src/lib/action-center/types.ts:108`）；用这个明确动作识别关联审批，不能把全部 `source=fulfillment` 的提醒都禁用完成。
- `summary.topItems` 上限 8 项（`src/lib/action-center/types.ts:3`），`summary.todoCount/approvalCount` 是摘要总数。已加载卡片数、当前筛选数、全局总数必须分开标明；不能用 8 张卡覆盖完整总数。
- `src/lib/command-hub/data/approval-api.ts:13` 固定取 `history?limit=50`；`src/app/api/exemptions/history/route.ts` 返回 `count=data.length`，没有游标和总量，按 created_at 排序。当前“共 N 条”应改成“最近 N 条”，检索只查加载数据时必须注明范围。
- 日期字符串格式化在 `src/lib/exemption-approvals.ts:162` 截取年月日，非连续 >=3 天路径在 `:260` 使用首尾区间；`src/lib/command-hub/types.ts:17` 相对时间使用设备时区。带时间值另用上海格式化，保留纯业务日期语义。
- 已有 `src/components/ui/dialog.tsx`、`src/components/ui/confirm-dialog.tsx`，优先复用，不新增第二套弹窗/确认基础设施。

## 分工与执行顺序

首批顺序：**B（手机核心阻断）→ A（状态/计数）→ C（误操作保护）→ D（键盘）→ E 的日期修正**。每阶段先定向验收，再进入下一阶段；历史全量检索和 F 打磨为第二批。

- CX：A/C/D、日期格式化与日期集合、接口证据、逻辑回归。
- An：B 的布局/可见性/触控及历史信息排版；读设计哲学和规范，保留微符处理和高密度布局，不平铺大量新按钮。
- 交接同一组件时串行编辑，以文件 diff 对账；本计划不启动代理施工。

## 风险与停止条件

- 补交审批提醒已有明确 action/appealId；历史脏提醒若缺 ID，只提供查看入口并保留待核状态，不能把所有履约来源提醒一刀切禁用，也不清理生产通知。
- 历史 API 当前没有游标/总数：首批仅修“最近 N 条”口径，第二批制定双来源分页契约；未实施前保持“待实施”，不能声称完整历史可搜索。
- 如果半天需要数据库字段或统计口径调整，另立数据口径任务；本计划只修展示误导，不擅自改变成员应发/实发统计。
- 如果焦点修复与现有弹窗组件冲突，先复用项目已有 Dialog 模式；不在本任务中引入第二套弹窗基础设施。
- 每轮最多两轮返工；若同一问题两轮仍未下降，停止继续堆补丁，转产品/架构复评。

## 状态、失败与回滚

- 提醒 → 去审批（不写完成）→ 审批待撤回 → 撤回则恢复待审；倒计时到期才调用原审批接口 → 成功后刷新审批/摘要/历史，失败则恢复对应项并显示失败。批准补交仅开放后续补提入口，不代表作品/日报已经补存。
- 批量部分失败：保留成功结果，失败项恢复；分别说明成功/失败数量，不输出整批成功；已有通知关闭失败必须单独提示待核。
- 打回：确认 → 请求中禁用重复动作 → 成功后离开历史并进入待审；失败保留历史原状态。取消确认零请求。
- 加载/空态/无权限：保留现有重试与空态；组员不挂载管理操作，接口 401/403 不显示伪成功。
- 兼容/回滚：首批无 migration；按 B/A/C/D/日期分别提交与定向回归，回滚指定提交而非整仓重置。关闭弹窗不得偷偷改变现有 5 秒撤回提交时机，重开后计时和队列要实测。

## 决策与延期清单

| 项目 | 推荐 | 实施前需要确认的内容 |
|---|---|---|
| 关联补交待办 | “去审批”+业务审批关闭提醒 | 采用单一处理入口与计数口径 |
| 批量/重开 | 先确认范围，再保留撤回 | 确认文案和范围快照 |
| 历史检索 | 第二批做全量服务端分页；首批只标最近 N 条 | 是否需要全量检索、搜索字段和排序口径 |
| 半天 | 独立业务规格，不解析理由猜半天 | 半天是否改变应发/履约、申请粒度 |
| 成员申请进度 | 保留已有入口；新增集中进度另立范围 | 是否需要集中进度、状态与通知的关系 |

以上为修复推荐；本轮只交付合并报告与计划，不因报告中的建议自动授权新功能。
