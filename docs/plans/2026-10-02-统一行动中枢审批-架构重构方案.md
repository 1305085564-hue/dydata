# 统一行动中枢审批后置状态收口与一致性改造方案

**方案日期**：2026-10-02  
**所属根治工程**：`docs/plans/2026-10-02-全站架构可维护性体检-治理体系版.md`  
**方案性质**：审批域一次性根治，不是只删除第二次 PATCH 的补丁  
**施工状态**：代码施工已完成；真实浏览器九类场景待外部验收
**责任边界**：本方案只处理补交审批链；豁免审批、通用待办和其他审批权限口径不在本次改造内。

---

## 一、问题和最终目标

当前补交审批链是：

```text
前端 POST 审批
 → 服务端 RPC 修改申请状态
 → 前端再次 PATCH notifications/:id/done
```

这会产生：

- 审批已成功，但第二次 PATCH 失败；
- 用户看到“待办未完成”，再次点击审批；
- 重复审批触发 RPC 已处理错误；
- 前端无法区分业务失败和后置状态失败；
- 审计、员工通知、审批人待办之间缺少统一结果契约。

最终目标不是简单把 PATCH 搬进 POST，而是形成一个可测试、可观测、可幂等、可补偿的审批用例：

```text
输入校验
 → 身份和角色权限
 → 目标归属与可见范围
 → 核心审批 RPC
 → 幂等分流
 → 审计
 → 员工结果通知
 → 审批人待办完成
 → 返回稳定结果
```

本次明确接受的边界：`handle_fulfillment_appeal` RPC 与 notifications 写入暂不合并为跨表数据库事务。因此本方案必须用稳定结果字段、结构化日志和补偿入口弥补非原子后置步骤，不能宣称已经实现数据库级原子一致性。

## 三、稳定契约

### 3.1 输入契约

```ts
type HandleFulfillmentAppealInput = {
  appealId: string;
  decision: "approve" | "reject";
  reason?: string;
  notificationId?: string;
};
```

规则：

- `appealId` 必须为 UUID；
- `notificationId` 有值时必须为 UUID；
- `reject` 必须有 reason；
- reason 最大 1000 字；
- 未传 `notificationId` 的旧调用方仍能完成审批，但 `notificationMarked=false`；
- `notificationId` 只作为当前操作者名下通知的待办完成目标，不能改变审批对象权限。

### 3.2 输出契约

成功响应统一为：

```ts
type FulfillmentAppealSuccess = {
  ok: true;
  status: "approved" | "rejected" | "already_handled";
  notificationMarked: boolean;
  businessSucceeded: true;
  auditSucceeded: boolean;
  employeeNotificationSucceeded: boolean;
};
```

失败响应统一为：

```ts
type FulfillmentAppealFailure = {
  ok: false;
  code:
    | "INVALID_INPUT"
    | "UNAUTHENTICATED"
    | "FORBIDDEN"
    | "APPEAL_NOT_FOUND"
    | "APPEAL_OUT_OF_SCOPE"
    | "RPC_FAILED"
    | "AUDIT_FAILED"
    | "EMPLOYEE_NOTIFICATION_FAILED";
  error: string;
  businessSucceeded: boolean;
  notificationMarked: boolean;
};
```

说明：

- `businessSucceeded=true` 但接口为 500 时，表示核心业务已生效、后置副作用失败，前端不得提示“审批未处理”；
- 对外 `error` 保持用户可理解，不返回堆栈和敏感数据；
- 内部日志必须包含 requestId、actorId、appealId、notificationId、decision 和各副作用结果；
- `status='already_handled'` 是幂等成功，不是业务失败。

如果当前项目不适合一次性给前端增加全部字段，必须在同一提交中完成前后端类型同步，不能出现后端字段先变、前端继续按旧结构解释的过渡状态。

## 四、依赖注入和用例边界

先把 POST 主体抽成纯业务编排函数：

```ts
export async function buildHandleFulfillmentAppealResponse(
  input: HandleFulfillmentAppealInput,
  deps: HandleFulfillmentAppealDeps,
): Promise<Response>
```

依赖至少包括：

```ts
type HandleFulfillmentAppealDeps = {
  requireAdminServiceClient: () => Promise<AuthResult>;
  loadAppealOwner: (appealId: string) => Promise<AppealOwnerResult>;
  requireOwnerOrAdminRole: (auth: AuthResult) => Response | null;
  requireActiveVisibleUsers: (auth: AuthResult, ids: string[]) => Response | null;
  handleAppealRpc: (input: RpcInput) => Promise<RpcResult>;
  markDone: (notificationId: string, userId: string) => Promise<boolean>;
  emit: (input: EmployeeNotificationInput) => Promise<EmitResult>;
  writeAuditLog: (input: AuditInput) => Promise<AuditResult>;
  observe: (event: ApprovalObservation) => void;
};
```

POST 只做：

1. 读取 JSON；
2. 解析输入；
3. 调用用例；
4. 返回响应。

不得在 POST 中重新堆积业务分支。

`markDone` 必须通过服务端函数调用，不能再由前端直接模拟；函数内部继续按 `notificationId + actor.userId` 限定归属，并以实际更新行数确认结果。

## 五、A-F 分支和副作用顺序

| 分支 | 条件 | HTTP | 核心业务 | 审计 | 员工通知 | 待办完成 |
|---|---|---:|---|---|---|---|
| A | RPC 返回 approved/rejected，后置均成功 | 200 | 已成功 | 按现有规则成功 | 成功 | 返回真实结果 |
| B | RPC 明确返回 already handled | 200 | 已成功 | 跳过 | 跳过 | 尝试完成并返回结果 |
| C | 申请不存在或不在权限范围 | 4xx | 未执行/未成功 | 不执行 | 不执行 | 不执行 |
| D | 其他 RPC 失败 | 500 | 未确认成功 | 不执行 | 不执行 | 不执行 |
| E | 核心业务成功，审计失败 | 500 | 已成功 | 失败 | 按现有顺序不继续发送 | 必须尝试 |
| F | 核心业务成功，员工通知失败 | 500 | 已成功 | 已成功或无需审计 | 失败 | 必须尝试 |
| G | 核心业务和后置都成功，但 markDone 失败 | 200 | 已成功 | 已完成 | 已完成 | `notificationMarked=false` |

### 5.1 幂等识别

当前 RPC 对已处理申请返回：

```text
appeal already handled
```

本次不改 RPC，但必须隔离为：

```ts
isAlreadyHandledAppealError(error): boolean
```

要求：

- 只识别已确认的 RPC 错误形态；
- 非目标错误不能误判为 B；
- 空错误、包装错误、不同错误文案必须有测试；
- 后续若 RPC 增加稳定错误码，只替换该识别函数，不改业务流程。

### 5.2 副作用失败原则

- 核心业务已经成功时，不能把 500 当作“审批没有发生”；
- E/F/G 均要记录结构化观测；
- `markDone` 失败不能反向撤销核心审批；
- B 分支严禁重新 emit 员工通知和重新写审计；
- 所有副作用结果必须进入响应或日志，不能只依赖 console 文本。

## 六、前端改造范围

只修改 `handleFulfillmentAppealReview`：

1. 请求体增加 `notificationId: todo.id`；
2. 删除第二次 `/api/notifications/{todo.id}/done` PATCH；
3. 解析稳定响应契约；
4. A 且 `notificationMarked=true`：显示成功提示并移除待办；
5. A 且 `notificationMarked=false`：显示“申请已处理，但待办状态未同步，请刷新查看”，不得伪装成功同步；
6. B：显示“该申请已处理过”，并根据 `notificationMarked` 决定是否移除待办；
7. E/F：根据 `businessSucceeded` 显示“业务已生效，但后置步骤失败”，不能显示“审批失败”；
8. 网络异常：显示“无法确认审批结果”，不得直接断言审批未处理；
9. `handleToggleTodo` 一字不动；
10. 组件拆分属于全站治理方案 Phase 3，本方案只保持此处逻辑可测试和边界清晰。

## 九、回滚和补偿

### 9.1 回滚判据

满足任一条件必须停止发布并回滚应用代码：

- 真实角色出现越权；
- 审批结果与原实现不一致；
- 审计或员工通知重复发送；
- 核心审批已成功但结果无法追踪；
- 审批 P95 超过工程预算；
- 关键页面或通用待办回归失败；
- 重复审批被误当成新审批。

### 9.2 回滚方式

- 前后端同一提交切换；
- 本次无 migration，应用代码可通过 `git revert` 回滚；
- 回滚后必须重新执行单测、静态门禁和真实审批浏览器验收；
- 不允许只回滚前端或只回滚后端，避免请求契约不一致。

### 9.3 非原子副作用补偿

如果核心审批已经成功但审计、通知或待办失败：

- 不撤销核心审批；
- 保留结构化失败事件；
- 通过幂等重试或人工补偿恢复副作用；
