## 二、修复详情

### H1 · 手工豁免旁路写入修复

**问题定性（来自 Codex 深审）：**

- `data-correction.ts::grantExemption` 直写 `profiles`（`status:'exempt'+exempt_type:'temporary'`），与迁移 030 的 `profiles_exemption_fields_check` 约束冲突 → 直写易报错
- 随后向 `exemption_grant` insert 用 `exemption_type`/`grant_mode`/`reason` 列 —— 但表真实列是 `grant_type`（030），这三个列都不存在，insert 必败
- 失败被 `.then(()=>{},()=>{})` 静默吞掉 → 正是 P0-01 点名的"已批准但无 active grant"缺发错账根因

**根因：**
1A 声称"所有数据写路径已统一"，但手工豁免仍是旁路写，且表列名错误未被发现。

**修复方案：**
创建统一的 `admin_grant_exemption_for_dates` RPC，替代直写逻辑：
- 使用正确的列名 `grant_type`（而非不存在的 `exemption_type`/`grant_mode`）
- 先检查是否已有 active grant，避免重复授予
- 创建 grant 后触发投影重算，保持 profiles 与 grant 状态一致
- 仅 service_role 可调用（与 createAdminClient 权限对齐）

**修改文件：**
1. `src/lib/admin-tools/data-correction.ts:75-136` — 改用 RPC 调用，删除直写 profiles 和错误列名 insert
2. `supabase/migrations/20260903170000_admin_grant_exemption_rpc.sql` — 新增 RPC 定义

**验证点：**
- RPC 参数使用 `p_grant_type`（对应表真实列 `grant_type`）
- 创建 grant 前检查是否已存在，避免重复
- 投影重算确保 profiles 与 grant 一致
- 权限限制为 service_role

### H2 · 历史编辑按 published_at 猜写禁用

**问题定性（来自 Codex 深审）：**

`dashboard/actions.ts::submitReport` 历史编辑仍留有"按 `published_at` 猜写视频"路径：
- `video_id` 为空时走 `.eq("published_at", ...)` 猜写（用户态 RLS + 无 id 限定）
- 命中"无视频的手工历史手稿/详情未加载/详情失败"时可能改错多视频或静默 0 行
- 正是 1B 明令禁的路径

**根因：**
1B 声称"历史编辑按 video_id 绑定"，但实际代码留有 `published_at` 猜写分支。

**修复方案：**
历史编辑必须有 `video_id` 才能写 videos 表，禁止按 `published_at` 猜写：
- `video_id` 为空时跳过 videos 写入，只更新日报
- `video_id` 非空时使用 service_role + `.eq("id", video_id)` 精确绑定
- 删除 `.eq("published_at", ...)` 猜写分支

**修改文件：**
`src/app/(app)/dashboard/actions.ts:153-172` — 禁用 published_at 猜写路径

**验证点：**
- `video_id` 为空时不写 videos 表
- `video_id` 非空时必须 `.eq("id", video_id)` 精确绑定
- 删除所有 `.eq("published_at", ...)` 猜写逻辑

### M1 · 历史编辑详情加载失败处理

**问题定性（来自 Codex 深审）：**

`history-report-edit-form.tsx` 详情加载失败被 `.catch(()=>{})` 吞掉 → `video_id` 变空喂给 H2 的猜写路径。

**修复方案：**
- 详情加载失败不能静默吞掉，必须记录错误日志
- 缓存一个错误标记（`null`），防止重复请求
- 配合 H2 修复后，即使详情失败也不会误写视频

**修改文件：**
`src/app/(app)/dashboard/history-report-edit-form.tsx:473-494` — 改为记录错误并缓存失败标记

### M2 · 视频提交回滚失败幂等键泄漏

**问题定性（来自 Codex 深审）：**

回滚 RPC 失败会泄漏 SHA256 幂等键 → 永久 409 无法重试：
- `assertVideoSubmissionRollbackResult` 抛出的 Error 会被 `rollbackSafely` catch 并继续
- 但前面的 409 conflict 检测会阻止后续重试，导致永久卡死

**修复方案：**
回滚失败记录日志但不抛错，让主流程能清理幂等键：
- 删除 `assertVideoSubmissionRollbackResult` 调用
- 失败时 `console.error` 记录但不抛错
- 让调用方能继续清理幂等键等后续步骤

**修改文件：**
`src/app/api/video-submit/route.ts:115-121` — 回滚失败非阻断式记录

**未修复（script_usage_records 孤儿）：**
Codex 提到"script_usage_records 无回滚快照留孤儿"，但该表写入在 `replaceDailyReportUsageRecord` RPC 内部，且：
1. 回滚只在视频/快照写入失败时触发
2. `replaceDailyReportUsageRecord` 是幂等 RPC（replace 语义），重试会覆盖
3. 孤儿话术记录不影响核心数据一致性（属于附属统计数据）
4. 清理孤儿话术记录需要额外的回滚快照和删除逻辑，成本高

因此本次不纳入修复范围，列为低优先级技术债。

## 八、教训

1. **"完成"声明需代码级核查**：不能只看主路径，必须 grep 全项目确认无旁路
2. **表列名变更需全局搜索**：030 改 `grant_type` 但代码未同步，需 migration 后立即全局 grep
3. **错误处理不能静默吞掉**：`.catch(()=>{})` 和 `.then(()=>{},()=>{})` 是隐患温床
4. **回滚不能阻断清理**：回滚失败不应阻止幂等键清理等后续步骤
5. **深审是必要环节**：Codex 发现的 H1/H2 都是第一阶段"完成"声明下的未收口残径
