## 发现清单

### 一、工作台 /dashboard 与日报录入

#### D-01　审批请假/改判后，整张工作台被打回骨架闪现

- **路由/入口 + 触发操作**：用户站在工作台 `/dashboard`，从顶部"今日待办/行动中枢"里审批通过或改判一条请假/豁免，回到工作台。
- **定位**：`src/app/(app)/dashboard/production-control-system.tsx` → `ProductionControlSystem` 组件内监听 `FULFILLMENT_DATA_CHANGED_EVENT` 的 `useEffect`（`detail?.source === "command-hub"` 分支里直接 `router.refresh()`，未包 transition）。事件由全局挂载的行动中枢 `src/components/unified-command-hub.tsx`（`commitReview`、`handleReopenReviewDecision` 成功后 `dispatchFulfillmentDataChanged({source:"command-hub"})`）派发，经 `src/components/nav-bar-client.tsx` 全站常驻。被刷新的服务端容器是 `dashboard-data-container.tsx → loadDashboardPageData`（`page.tsx` 标了 `force-dynamic`）。
- **现象**：整页（含控制栏、月历、概览、填报面板）被拆掉、露出 `dashboard/loading.tsx` 的 `DashboardLoading` 全幅骨架，再重新装配——典型 (a)+(b)。
- **根因归类**：高信号第 **1** 条（裸 `router.refresh()`，未包 `useTransition`）。
- **分档**：**尽量做**（偏一定要做）。刷新本身是**正确的**——实发/应发、月历状态由服务端 `loadDashboardPageData` 计算，客户端无法纯乐观重算，必须回服务端取一次；问题只在"没包 transition → 露骨架打断"。频率上取决于管理员在工作台停留时顺带审批的频次：单条不算每次浏览都点，但一次批量通过会连发多条事件、每次都全页闪一下，体感差。
- **建议修法**：完全照搬范本 `health-bar.tsx` 第 96/143 行的写法——组件里加 `const [, startRefresh] = useTransition();`，把 `router.refresh()` 改成 `startRefresh(() => router.refresh())`。刷新逻辑、取数、口径**一律不动**，只是保帧不闪。若要进一步，可把"连发多条审批"合并成一次 refresh（事件侧节流），但非必需。
- **涉及层**：页面（纯呈现）。
- **风险**：**低**。改动只加一层 transition 包裹，不触碰取数与 `revalidatePath`，不改变本公司/只看自己的数据范围、不改变实发/应发统计口径、不碰权限/RLS。伪风险提醒：不要为了"消除闪烁"错误地把这条 refresh 删掉或改成纯客户端乐观——那会导致月历/应发数字长期对不上（真口径在服务端）。
- **复杂度**：F1（一行包裹）。

#### D-02　提交/编辑/切换类交互：已做对，**排除为伪问题**（留证）

以下动作逐一读码核实，**均不触发整页刷新感**，列出以防后续误判：

- **提交今日日报**：`video-submit-form-v2.tsx` 提交成功走 `setIsSubmitted(true)` + `router.prefetch("/growth")`（仅预取、不跳转）+ `onSubmitted(...)`；`video-submit-panel-v2.tsx` 的 `handleSubmitted` 做**乐观** `setReportOverrides` + 客户端 `loadActivity()` 拉活动记录 + `scrollIntoView` 把表单滚进视野（是"滚到目标"，非"跳回顶部"）。无 `router.refresh`。✅ 符合范本⑤。
- **改历史手稿**：`history-report-edit-form.tsx` → `handleSubmit` 把 `submitReport(formData)` 整个包进 `startTransition`；保存后 `onSaved` 关详情视图 + 客户端 `loadActivity()`。对应的 `actions.ts → submitReport` 里 `revalidatePath("/dashboard")` 是在**服务端 action 的 transition 内**生效，保帧不闪骨架；且工作台 `page.tsx` 的 Suspense **无 key**，不会因 revalidate 重挂。✅
- **切换账号 / 选日期 / 开合日历·历史抽屉·豁免弹窗**：`production-control-system.tsx`、`video-submit-panel-v2.tsx` 全部是 `useState`/自定义事件（`dydata-dashboard-action`）驱动的纯客户端切换；日期切换 `selectBizDate` 只在历史日期时客户端 `loadActivity()`。无路由、无 refresh。✅

### 三、文案助手 /content-tools/rewrite

#### C-01　初始化失败的"重试加载"用了 `window.location.reload()`——**判为可接受（不用做）**

- **路由/入口 + 触发操作**：文案助手首屏 bootstrap 拉取失败，出现"初始化异常"错误卡，用户点"重试加载"。
- **定位**：`src/components/content-tools/rewrite-v3/RewriteWorkbenchV3.tsx → RewriteWorkbenchV3`，错误分支 `if (state.errorState)` 里"重试加载"按钮 `onClick={() => window.location.reload()}`。
- **现象**：整页硬刷新。但它**不是本应局部的动作**触发的——bootstrap 已经失败、页面处于"没起来"的错误态，此时没有任何客户端局部恢复手段，硬刷新是合理的升级兜底。
- **根因归类**：形式上命中高信号第 **3** 条（`location.reload`），但语境是错误恢复，非交互打断。
- **分档**：**不用做（伪 refresh，排除）**。理由：触发点是"初始化异常"错误态下的显式重试，页面本就没渲染，硬 reload 是正确降级；不应为了"优雅"改成客户端重跑 bootstrap（那会引入新的部分加载态与竞态，属于过度设计，见编码原则"简洁优先"）。
- **建议修法**：如坚持消除，可把按钮改为重跑 `state` 的 bootstrap 拉取（客户端 retry），但收益极低、风险是新 bug，不建议现在做。
- **涉及层**：页面。
- **风险**：改则引入重试竞态风险；不改无风险。
- **复杂度**：F1（若改）。

#### C-02　改写工作台主体交互：已做对，**判为干净**

- 页面 `content-tools/rewrite/page.tsx` 仅做权限/登录判定后挂 `RewriteWorkbenchV3`，无 Suspense key、不读 searchParams；工作台内会话切换、发消息、定稿阅览、导出、设置抽屉等（`rewrite-v3/**` 全量 grep）无 `router.refresh/push`、无 `<a href>` 整页导航，`key=` 均为列表渲染 key，非重挂触发器。✅ 不命中。

### 四、选题库 /topics

#### T-01　选题池每次"筛选/搜索/排序/翻页"把已有卡片整块换成转圈占位

- **路由/入口 + 触发操作**：用户站在 `/topics`，切换视图（全部/…）、选时间范围、勾选母题、改"更多筛选"、改排序、输入搜索、点上一页/下一页——任意一项。
- **定位**：`src/components/topics-v2/TopicHubV2.tsx → TopicHubV2` 的 `beginPoolQueryChange()`（每次筛选都 `setPoolLoading(true)`）→ 子组件 `src/components/topics-v2/TopicPoolExplorer.tsx` 主展示区 `{loading ? (<div className="py-20 …"><RefreshCw …/><p>选题库加载中…</p></div>) : …}`——loading 为真时**整列卡片被替换**成居中转圈块。
- **现象**：命中判据 (a)——原本铺开的选题卡片瞬间消失、换成一个 `py-20` 的占位，取回后又重新铺出；列表高度塌缩，若用户已向下滚动，视觉内容会跳动（近似 (c)）。注意：这是**客户端 fetch**（`/api/topics/pool`），**不是**整条路由服务端重取（无 `router.refresh`/导航），影响面局限于选题列表区。
- **根因归类**：近似高信号第 **7** 条（loading 布尔把已有内容整块拆掉重装），本质是"服务端分页列表的加载态呈现过粗"。
- **分档**：**尽量做**。这是本范围**第二高频**的动作（组员整天在选题库里搜/筛/翻页），每次都"抖一下"很扰；但客观上它确实在重新向服务端要一页（每页 50 条）新数据，给一个加载指示**是诚实且必要的**——问题只在"把旧结果整块拆掉"而不是"旧结果先留着、盖一层轻进度"。
- **建议修法**：对齐范本精神做"陈旧数据在屏 + 轻量进度"（stale-while-revalidate）：loading 时**保留上一批 `items` 以 `opacity-60`/顶部一条细进度条呈现**，仅首屏无数据时才用大占位；翻页同理。`beginPoolQueryChange` 里不要直接清掉列表可见性，改为"置 `isRefreshing` 标记"由 `TopicPoolExplorer` 决定叠加态。取数、分页参数、请求去重（`poolRequestId`/`AbortController`/`skipPoolEffectPage`）**全部保留不动**，纯改呈现层。
- **涉及层**：页面。
- **风险**：**低**。不触碰选题的数据范围（本公司/只看自己由服务端 `loadTopicsTeamScope`/pool 接口决定）、不改任何统计口径、不碰权限/RLS。唯一要守住的：改呈现别把"loading 期间禁用重复点击/防抖"这套现有的 `beginPoolQueryChange + 300ms debounce + 竞态丢弃`逻辑弄丢，否则会引入"旧请求覆盖新结果"的真 bug。
- **复杂度**：F2–F3（要动 `TopicPoolExplorer` 的 loading 分支 + `TopicHubV2` 的 loading 语义拆分）。

#### T-02　选题库主体动线：架构已对齐范本，**判为干净（并显式说明一个"非缺陷")**

- **抽屉/弹窗懒加载**：`TopicWorkBreakdownDrawer`、`TopicMoreFiltersDrawer`、`TopicCreateModal` 全部 `next/dynamic` + 条件挂载（`inspectTopicId`/`isMoreFiltersOpen`/`isCreateModalOpen` 客户端 state 控制），开合**零路由、零整页**。`dynamic(` 的真实挂载点已在 `TopicHubV2` 组件树内逐一核实（记忆点：dynamic 追不到挂载需复核，此处已证实均在用）。✅ 符合范本①④。
- **改在写状态/编辑/移出选题**：`handleMarkWriting` 成功后本地 `setWritingTopicIds` + `refreshAll()`（客户端 fetch，非 router）；抽屉内 `onSubTopicUpdated`/`onSubTopicRemoved` 直接**乐观** `setPoolItems`。✅
- **深链关闭清理 URL**：抽屉 `onClose` 用 `window.history.replaceState({}, "", "/topics")`——只清地址栏不触发重取/重载。✅
- **跨页"在工作台录入"**：`TopicWorkBreakdownDrawer` 用 `next/link`（`href=buildDashboardTopicHref(...)`）跳 `/dashboard?topic_id=`，是**有意的跨页导航**（本就该整页换路由）→ 不用做。行动中枢/选题卡里跳飞书外链用 `window.open`/`location.assign`（新标签，非应用内刷新）→ 不用做。
- **说明（非缺陷、但提请产品知悉）**：选题池的视图/筛选/排序/搜索/页码**全部不写进 URL**（与协作模块"保留 `router.replace` 同步地址栏守可分享链接"的范式不同）。这**不是刷新感问题**，反而是"零重挂零闪烁"的来源；代价是选题筛选态不可分享/刷新后回默认。是否要补 URL 同步属**产品取舍**，不在本次刷新感排查的"该修"清单内。
