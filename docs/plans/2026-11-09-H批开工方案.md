> **执行方**：Haiku 5.5 中等思考  
> **复杂度**：F2-R2（中等复杂度 - 中等工作量）  
> **开工前提**：F、G 批完成后，有返工率基线数据

---

## 一、目标与约束

### 目标
- **#5 补丁债**：识别补丁堆积模块，评估根治成本
- **#17 热点返工**：统计返工频次，找出需求边界未稳定的模块
- **#24 性能**：建立性能基线，识别用户可感知的慢点

### 施工红线（Haiku 5.5 必须遵守）
1. **只读 + 报告**：本批不改代码，只收集数据和出报告
2. **数据来源**：日志、git 历史、测速结果，不猜测
3. **不自作主张优化**：实际优化等阿禅拍板后再做
4. **报告格式**：红绿灯 + 证据对 + 优先级排序

## 二、施工步骤

### 阶段一：返工率统计（补丁债 + 热点返工）

**目标**：从 git 历史和日志识别高返工模块

#### 1. 数据收集（只读）

```bash
# 统计近 3 个月每个文件的修改次数
git log --since="2026-08-09" --pretty=format: --name-only | sort | uniq -c | sort -rn | head -30

# 统计 commit message 中的"修复"、"返工"、"再次"等关键词
git log --since="2026-08-09" --oneline --grep="修复\|fix\|返工\|revert\|再次" --all
```

读取日志文件：
- `docs/reference/2026-11-07-截图识别止血修复推送核对.md` — 11-07 故障
- `docs/reference/` 下所有 2026-08-09 之后的日志
- 搜索 commit message 中提到"R1/R2/R3"（返工轮次）的提交

#### 2. 输出：返工热点清单

| 模块/文件 | 修改次数 | 返工原因 | 是否补丁堆积 | 优先级 |
|---|---:|---|---|---|
| `video-submit/route-core.ts` | X 次 | 业务逻辑分叉、异常处理不全 | 是 | 高 |
| `ocr-screenshot/route.ts` | X 次 | 类型错误、异常被吞 | 是 | 高 |
| `admin/ai-config/*` | X 次 | 口径多次调整 | 否（已重整） | 中 |
| ... | ... | ... | ... | ... |

**判断标准**：
- **补丁堆积** = 同一模块 3 次以上修改，且 commit message 提到"绕开"、"临时"、"先这样"
- **热点返工** = 同一模块 5 次以上修改，且跨越多个批次

#### 3. 输出：补丁债分级

| 等级 | 定义 | 处理建议 |
|---|---|---|
| 红灯 | 返工 ≥5 次，补丁堆积明显 | 立即根治（下一批优先） |
| 黄灯 | 返工 3-4 次，或单次大返工 | 观察，下次改到时根治 |
| 绿灯 | 返工 ≤2 次 | 正常，不处理 |

**测速方法**：

- 用 `curl -w "@curl-format.txt" -o /dev/null -s <URL>` 测 3 次取中位数
- 或用浏览器开发者工具 Network 面板记录

从热点页面（首页、视频复盘、协作管理）测：

| 页面 | 首屏时间 | 请求数 | 最慢接口 | 是否可感知慢 |

**判断标准**：
- 首屏 >3s = 红灯（用户可感知慢）
- 首屏 2-3s = 黄灯（边缘）
- 首屏 <2s = 绿灯

## 四、估算与风险

### 工作量估算
- 返工率统计：约 2 小时（读日志 + 跑 git 命令）
- 性能测速：约 3 小时（启动服务 + 测 10+ 个接口/页面）
- 报告撰写：约 1 小时

**总计**：约 6 小时纯执行时间

### 风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| git 历史太长，统计慢 | 低 | 只统计近 3 个月 |
| 本地测速不准（网络抖动） | 中 | 每个测 3 次取中位数 |
| 测速时数据库没起 | 低 | 先 `npm run test:real-db` 确认库正常 |
| Haiku 5.5 误判补丁债 | 中 | 报告只列证据对，判断交阿禅 |
