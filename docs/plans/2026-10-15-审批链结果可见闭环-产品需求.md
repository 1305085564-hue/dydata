# 审批链"结果可见"闭环 — 产品需求

> 状态：待阿禅评审 ｜ 提出：2026-10-15 ｜ 依据：审批链 UX 审计（2026-10-15，ux-1015-2）+ 产品经理视角审查
> 本文替代审计原"Priority Recommendations 1-5"清单，作为本轮施工的唯一需求依据。

## 1. 背景与目标

审计证据显示：审批工作台的功能都在（能筛选、能批、能回退、有测试），但**审批链在"结果"这一段对参与者失明**——

- 员工提交申请后，系统里没有任何地方能看到审批结果，只能靠问人；
- 有权审批的人可能收不到提醒，单子积压没人知道；
- 审批人批完补交，不知道数据到底写进去没有；
- 审批人打回豁免/请假，不知道会撤销已生效的免交结果。

这四条是同一个根因的四次发作，不是四个独立小问题。

**产品目标：** 审批链的每个参与者，不离开系统、不问任何人，都能回答"我的/手头的申请现在到哪一步、结果是什么、下一步该谁做什么"。

**完成的观察判据：**
1. 组员能在自己的工作台查到每一笔申请的状态和结果，驳回能看到原因；
2. 审批提醒与审批权限完全一致：能批必收到，不能批收不到；
3. 审批人在工作台/历史记录能区分"已批准且数据已写入"与"已批准、等成员补传"；
4. 打回豁免/请假的确认框写清会撤销什么、影响哪些日期的履约。

## 2. 角色与用户故事

| 角色 | 定位 |
|---|---|
| 成员 | 请假/豁免/补交申诉的提交人 |
| 审批人 | 组长·管理、公司所有者；对本公司在职成员的申请有裁决权（沿用权限矩阵，不改） |

- **US-01** 作为成员，我提交申诉/豁免/请假后，能在系统里看到每一笔的进度（待处理／已批准／已驳回／已批准·等我补传），被驳回时能看到原因，不需要私聊问组长。
- **US-02** 作为审批人，凡是我有权批的申请，我都会收到待办提醒；没收到提醒就说明没有需要我批的单。
- **US-03** 作为审批人，我批准补交后，能在卡片和历史记录里看到数据是"已自动提交"还是"等成员补传"，不用去数据库或员工页面求证。
- **US-04** 作为审批人，我在打回豁免/请假前，能从确认文案里预知后果：这段时间的免交/请假生效会被撤销、发布履约重新计算、成员需重新等审批。
- **US-05** 作为审批人，工作台头部的数字直接告诉我"待审批几条、普通待办几条、当前筛选几条"，批量按钮管到谁一目了然。

## 3. 范围

**P0（链路断点，业务真实损失）：** US-01、US-02
**P1（信任层，批错风险与误判）：** US-03、US-04、US-05
**本轮明确不做：** 历史记录筛选/搜索、快捷键写入验收、暗色模式、响应式整改、批量审批改版。**注：** 生产实测单量约 10 笔/天（见 §7），历史"最近 50 条"只够回看约 5 天，历史筛选/搜索**升为下一轮 P1**，本轮不做但不可再当作"可无限期搁置"。

**边界约束（不改的东西）：**
- 不改审批裁决逻辑本身：谁能批什么、批准/驳回/打回的状态流转、履约计算口径，全部沿用现行规则（权限与访问控制 §4、核心业务流程 §1-2/§4）；
- 不新增审批类型；团队待办与正式审批只做展示区分，不合并业务；
- 本轮属高风险改动（涉及"提醒发给谁"的权限条件），施工前必须先列受影响文件清单再动手。

## 4. 功能需求

### FR-01 成员申请进度自查（P0，对应 US-01）

**目的：** 员工提交后结果可回查，闭环终点落到员工眼前。

| 项 | 规格 |
|---|---|
| 入口 | 成员工作台新增"我的申请"区块（或标签页），与提交入口同层级可达 |
| 列表内容 | 本人提交的全部申请（请假、特殊豁免、补交申诉），按提交时间倒序 |
| 状态展示 | 待处理 ／ 已批准·已生效 ／ 已批准·等待我补传（仅补交） ／ 已驳回 |
| 驳回原因 | 已驳回条目必须直接显示审批人填写的原因，不折叠、不另跳 |
| 行动引导 | "等待我补传"状态旁给"去上传数据"入口，点击直达对应补交表单 |
| 空状态 | 无申请时显示一句引导文案（说明什么情况下需要申请），不出现内部术语 |
| 权限 | 仅本人可见自己的申请；审批人权限不受影响 |
| 通知渠道 | 审批结果通过右上角铃铛推送给申请人（恢复铃铛"消息"本意——现状是结果通知已写入但员工侧看不到，展示链路要修通）；铃铛＝推送，"我的申请"＝可翻查的台账，两者互补 |
| 双重身份 | 管理员自己也是员工、也要上传数据：铃铛里"要你批的"与"你提交等结果的"是两类消息，必须可区分，不混成一堆 |

**异常边界：** 申请被打回后回到"待处理"，员工侧同步可见；同一申请重复审批不产生第二条记录。

### FR-02 提醒发对人（P0，对应 US-02）

**目的：** 消除"有权批但不知道有单"的丢单风险。

**规则（唯一口径）：** 审批提醒的收件人 = 对该申请有审批权的人。即：本公司在职的组长·管理与公司所有者都收到；不能批这条单的人（跨公司、归档成员的申请、自己的申请）都不收到。现状"接口允许 admin 批、提醒却只发给带 `manage_members` 的人"两类不一致全部消除，以权限矩阵为准绳。

**结果判据：** 任取一条待审批申请，"能对它执行同意/驳回的人"与"收到它提醒的人"两个名单完全相同。

**注意：** 只调整"谁收到提醒"，不扩大任何人的审批范围；改动属权限链路，施工前列受影响文件清单，改完必须做 admin＋member 第二角色真实验收（本轮审计 BLOCKED 项）。

### FR-03 执行状态回显给审批人（P1，对应 US-03）

**目的：** "批准"与"生效"是两个状态，审批人要都看得见。

- 补交申诉批准后，卡片与历史记录显示两种结果之一：**"数据已自动提交"** 或 **"已批准·等待成员补传"**；
- "等待成员补传"时补充一句"成员补传完成后自动生效，无需再次审批"，避免审批人误以为要重批；
- 成员完成补传后，该记录状态更新为"已生效"；
- 请假/豁免批准后显示"已生效（免交/请假已计入 X 月 X 日–X 日）"。

### FR-04 回退后果说全（P1，对应 US-04）

**目的：** 批错能安全回退的前提是知道回退会撤销什么。

豁免/请假"打回待处理"的确认区，在现有"回到待审批"之外增加：

> 会撤销这段时间的免交/请假生效，相关日期的发布履约将按未审批状态重新计算；成员需要重新等待审批。

文案与补交回退确认（"通知作废、回到待审批、重发待办"）保持同等具体度。措辞遵循人文风格：写"撤销免交生效"，不写"撤销授权记录"这类内部词。

### FR-05 审批计数口径拆分（P1，对应 US-05）

- 工作台头部并列拆成两个数：**"待审批 N"**（请假/豁免/补交）与 **"普通待办 M"**；
- 筛选区显示"当前筛选 K 项"，与头部数字不再混排；
- "一键同意"按钮旁标注"仅处理请假/豁免/补交，不含普通待办"；
- 发布管理页入口标注"今日履约待审"，与行动中枢"全公司审批池"区分口径。
- **同源硬要求：** 头部数字与筛选行数字必须取自同一份计数，禁止两套算法并存。

**根因已实测（2026-10-15 代码核对）：** "总数 8"与"全部 9"是两个不同来源各自计算的结果——头部"总数"取后端汇总计数（审批数＋待办数相加），筛选行"全部"取前端实际加载的卡片数（含团队待办）。两者没有任何机制保证一致，所以同一屏会并列出现 8 和 9。这不是数据错了，是两套口径并存的设计缺陷；修复必须同源化，不是改文案。

## 5. 共用规则（真源引用，不重复定义）

| 规则 | 真源 |
|---|---|
| 谁能批什么 | [权限与访问控制](../业务逻辑/权限与访问控制.md) §4 豁免申请和审批 |
| 批准/驳回/打回的状态流转与履约影响 | [核心业务流程与异常边界](../业务逻辑/核心业务流程与异常边界.md) §1、§2、§4 |
| 面向用户文案风格 | 人文风格：不用内部术语、不误导、给出口（全站既定） |

**全链统一状态命名（FR-01/03 共用）：** 待处理 ／ 已批准·已生效 ／ 已批准·等待成员补传 ／ 已驳回 ／ 已打回待重新审批。同一状态在员工侧、审批侧、历史记录三处用词必须一致。

## 6. 验收标准

**功能测试（第二角色真实登录态，admin＋member 各一）：**
1. 成员提交一笔补交申诉 → 员工"我的申请"显示"待处理"；
2. 组长批准且自动续交成功 → 员工侧变"已批准·已生效"，审批人卡片显示"数据已自动提交"；
3. 组长批准但续交失败 → 员工侧显示"已批准·等待我补传"＋"去上传数据"入口可用；员工补传完成后状态变"已生效"，无需任何二次审批；
4. 组长驳回并填原因 → 员工侧直接可见该原因；
5. 仅有权无提醒的 admin 账号：修复后能收到新单提醒；无权账号（跨公司/自己的单）：收不到；
6. 打回一笔豁免 → 确认文案含"撤销生效＋履约重新计算＋重新等审批"三要素；打回后发布管理页该成员对应日期恢复为待交；
7. 头部"待审批/普通待办/当前筛选"三数与实际条目逐一对得上；"一键同意"执行范围与标注一致。

**边界 case：**
8. 重复批准同一单 → 不产生重复记录、不重复提醒；
9. 申请被打回 → 员工侧状态同步回"待处理"；
10. 无任何申请的组员 → "我的申请"空状态文案正常，不报错。

**门禁复跑（把审计 BLOCKED 项转为证据）：**
11. 隔离环境重跑九类门禁端到端测试（含提醒收件人新口径）＋375px 移动宽度走查，页面/接口/数据三层留证。

**代码检查：**
12. 提醒收件人条件与审批接口条件引用同一份权限判断，不允许两处各写一套；
13. 状态文案从单一真源派生，员工侧/审批侧/历史三处不各自硬编码。

## 7. 待决问题与已确认结论

**审批量与审批人分布（2026-10-15 生产库只读实测，近 30 天）：**

| 指标 | 实测值 |
|---|---|
| 申请总量 | 302 笔（补交 158、请假 66、豁免 78），约 10 笔/天 |
| 当前待处理 | 8 笔（补交 1＋请假 2＋豁免 5） |
| 组长·管理（admin）处理 | 234 笔 ≈ 79%，分布在 10 个人身上（最高一人 81 笔） |
| 公司所有者处理 | 62 笔 ≈ 21% |

**据此定案：**
1. **核心用户是组长，不是老板**——组长处理了近八成审批。原审计以公司所有者视角走查，等于低频用户评高频用户的工具；FR-02（提醒发对人）对 10 位组长的实际伤害比审计评估的更大，第二角色验收必须用真实组长账号。
2. **"总数 8"与实测吻合**：当前待处理正式审批恰为 8 笔，"全部 9"＝8＋1 条团队待办。审计的推断被生产数据证实，根因仍是两套计数并存（见 FR-05）。
3. **历史搜索升为下一轮 P1**：10 笔/天下"最近 50 条"只能回看约 5 天。

**其余已确认（2026-10-15，阿禅提供＋代码实测）：**

- **员工获知结果的渠道现状：** 不稳定——数据上传有提示，其他页面没有。右上角铃铛本应承担此职责（本意是"消息"，含审批结果），后因"管理员自己也是员工、也要上传数据"导致定位漂移。据此 FR-01 采用"铃铛推送＋我的申请台账"双通道设计，并明确区分"要你批的"与"你提交等结果的"两类消息。
- **"总数 8 / 全部 9"不一致根因：** 两个数字来源不同、各算各的（详见 FR-05 实测说明），修复方向为同源化。
