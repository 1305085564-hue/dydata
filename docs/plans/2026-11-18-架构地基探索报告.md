## 三、本地一次性测试库可行性

**结论**：可行且很快——本机已有本地 Supabase 全栈在跑（PG 17.6 @54322 + Kong @54321），生产结构导出+预置替身后**全量 242 个迁移重放约 10 秒，239 过 / 3 败**；一次性重建全结构约 30 秒级。3 个失败根因都是迁移史/生产漂移的真实缺陷，不是环境缺东西。PGlite 不建议。

### 3.1 现有 real-db 测试的环境要求（实测 scripts/run-tests.mjs:54-68）

- 连接串取 **`.env.ai-test.local` 的 SUPABASE_DB_URL**（不是 .env.local），强制 127.0.0.1/localhost，否则拒绝执行；实测指向 127.0.0.1:54322/postgres。
- 无建库/重置/seed 步骤，只做 TCP 探活；默认库由 `colima start + supabase start` 起好。串行（--test-concurrency=1）因多文件改表结构，并行 DDL 死锁。
- 主树 11 个 real-db 测试：6 个直连 pg、3 个纯 PostgREST、2 个混合（实测逐文件 grep）；走 REST 的需要本地 Kong+service_role key。11 个里 10 个在 AI 配置域，业务侧仅 content-quality-parity 一个。

### 3.2 本机已具备（实测）

colima 运行中；dydata 本地 Supabase 全栈在跑（PG 17.6.1.113、gotrue/storage/realtime 齐全）；supabase CLI 2.122.0；psql 16.15 + **pg_dump 17.11**（/opt/homebrew/opt/postgresql@17/bin/）；node_modules 有 pg 8.23.1，无 PGlite。**supabase/config.toml 不存在**（磁盘与 git 均无）——`supabase start` 会按默认配置重建，需留意。

### 3.3 结构导出与替身清单（实测）

- 生产 PG17，pg_dump 16 报版本不匹配终止，换 17.11 成功。public 结构 15379 行（101 表/110 函数/240 策略/30 触发器/1 视图），导出 11.8s；auth 2065 行、storage 2668 行、private 172 行，均无数据。
- 迁移对 Supabase 设施的依赖（grep 242 文件）：auth.uid×605、auth.role×178、auth.users×24、auth.jwt×5；storage.buckets×3；角色 authenticated×522 / service_role×406 / anon×184。扩展只需 pgcrypto、btree_gist、uuid-ossp；无 pg_cron/realtime/net 引用。
- 在现有本地集群建一次性库：角色集群级已存在，只需灌 auth+storage 结构+3 扩展。裸 Postgres 才需手建三角色。

### 3.4 重放实验读数（实测：本机 54322 新建 dydata_schema_probe，已 DROP）

| 步骤 | 结果 |
|---|---|
| 裸灌 public 结构 | 238 错（234 缺 auth schema、3 策略、1 缺 btree_gist），1.3s |

3. `20261019120000`：回填真实生产数据行，需预置特定 UUID 的 accounts/auth.users 种子。

### 3.5 路线判断

- 推荐直接在现有本地 Supabase 集群建一次性库：角色/扩展/PostgREST 全现成，5 个用到 REST 的测试也能跑。

## 四、推送与上线防护

**结论**：GitHub main **零保护**（无 branch protection、无 rulesets，可强推、无必需检查）；唯一关口是本机 pre-push 六项门禁，`--no-verify` 可绕过；Vercel 构建失败不会把坏版本推上线（类型错误已拦构建）；多工作树并发推 main **没有任何排队机制**。

| 项 | 事实 | 证据 |
|---|---|---|
| 分支保护 | 未开启 | 实测 `gh api repos/1305085564-hue/dydata/branches/main/protection` → HTTP 404 "Branch not protected"；`gh api …/rulesets` → `[]` |
| 强推/必需检查 | 均无约束 | 同上（无保护即无禁止强推、无 required status checks） |

4. **迁移史不自包含**：20261005024700 drop 的策略没有任何迁移创建过（线上手工产物）；4 个迁移以不同版本号入账。任何"按仓库迁移重建生产"的假设都不成立。（实测）
