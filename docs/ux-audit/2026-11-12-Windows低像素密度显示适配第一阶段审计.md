# DYData Windows 低像素密度显示适配专项任务

## 第一阶段审计报告

- 审计日期：2026-11-12
- 审计范围：Mac 源码审计、Mac 浏览器 1920 / 1440 / 1200 / 960 CSS 宽度检查、登录后核心页面只读布局检查
- 当前版本：`252d966d`
- 当前状态：只完成审计和报告，未修改代码，未部署，未进行 Windows 实机验证
- 状态标记：`【Mac 已验证】` 表示源码或 Mac 浏览器已复核，`【Windows 待验证】` 表示必须在真实 Windows 设备复核，`【推测，证据不足】` 表示只有风险线索

## 审计结论

Mac 侧已确认一处明确的布局问题。CSS 网页宽度处于 768–1023px 时，桌面主导航和移动主导航都隐藏。960px 本地登录后工作台截图中只剩 DYData 标识、通知按钮和账号按钮，主导航入口不可见。

字体、低对比度文字、半透明发丝边框、细 SVG 线条和动效滤镜存在 Windows 低像素密度下的视觉风险，但 Mac 代码和截图不能证明 Windows ClearType、实际命中字体、100% / 125% 缩放或 Chrome / Edge 的最终观感。

1920、1440、1200、960 四档宽度下，公开首页、工作台、选题库、数据复盘、协作管理、发布管理、每日大盘和抖音账号页面都没有页面级横向溢出。数据复盘、协作管理、发布管理和工作台履约日期带使用内部横向滚动容器，属于需要在 Windows 普通窗口复核的适配观察项。

## 问题 1：768–1023px 主导航断档

问题编号：W-01

问题描述：桌面主导航在 `lg` 断点才显示，移动主导航在 `md` 断点以下才显示。768–1023px 之间两套导航均隐藏。

影响范围：登录后的全部工作台页面。用户在约 960px CSS 宽度的普通窗口中无法从顶部导航进入工作台、协作管理、数据复盘、每日大盘和选题库等入口，只能依靠直接地址访问。

源码位置：

- `src/components/navigation/navigation-shell.tsx:130-173` 同时挂载桌面导航和移动导航。
- `src/components/navigation/desktop-nav-menu.tsx:97-100` 使用 `hidden ... lg:flex`。
- `src/components/navigation/mobile-navigation-shell.tsx:47-54` 使用 `block md:hidden`。
- `src/components/navigation/navigation-header.tsx:96-123` 在中间宽度只保留标识和右侧操作区。

Mac 检查结果：

- `【Mac 已验证】` Playwright 宽度探针显示 767px 时移动导航为 `display:block`，768px 和 960px 时桌面、移动导航均为 `display:none`，1024px 时桌面导航恢复为 `display:flex`。
- `【Mac 已验证】` 960×900 工作台截图中顶部没有主导航文字入口。
- `【Windows 待验证】` Windows 显示缩放和普通窗口下的实际 CSS viewport 需要记录。Windows 100% / 125% 不能用 Mac 结果代替。

Windows 实测要求：

- Windows 100% 和 125% 缩放分别打开最大化窗口和普通窗口。
- 在 Chrome、Edge 开发者工具记录 `window.innerWidth`。
- 当 CSS 宽度落在 768–1023px 时确认主导航是否消失，记录是否能通过可见入口进入其他模块。

修复建议：先根据 Windows 实测确定中间宽度的唯一导航形态，再做最小断点调整。建议保留桌面导航结构，在中间宽度缩短间距或收纳部分入口，理由是 960px 已经是桌面普通窗口，底部移动导航不适合承担主要入口。

风险等级：高

验收标准：在 768、960、1023、1024px CSS 宽度分别存在可见且可操作的主导航入口，页面没有导航入口空档。Windows 100% / 125%、Chrome / Edge、最大化 / 普通窗口均通过。

## 问题 2：系统字体栈可读，但 Windows 实际命中字体未被证明

问题编号：W-02

问题描述：项目只使用系统字体栈，没有项目自带字体文件。拉丁文字、中文文字和衬线标题依赖操作系统字体回退，源码无法证明 Windows 实际使用了哪一种字体。

影响范围：全站正文、中文标题、英文和数字、表格元数据、登录页和页面定名。

源码位置：

- `src/app/globals.css:14-16` 定义 sans、serif、mono 字体栈。
- `src/app/globals.css:162-171` 将 sans 应用到 `html`，全局正文为 14px。
- `src/app/layout.tsx:58-60` 使用全局字体和 `tabular-nums`。
- `src/styles/css-tokens.test.ts:66-79` 反向断言当前字体栈不引入 Inter 或 webfont。
- `docs/系统架构与设计/视觉与数值手册.md:107-120` 将 Windows Segoe UI / 微软雅黑 UI / 中易宋体列为基线。

Mac 检查结果：

- `【Mac 已验证】` `document.fonts` 未发现项目自带 woff、woff2、ttf 或 otf 字体资源，源码也没有 `@font-face` 或 `next/font`。
- `【Mac 已验证】` Mac Chromium 计算样式返回 sans 栈 `-apple-system, system-ui, Segoe UI, PingFang SC, Microsoft YaHei UI, Microsoft YaHei...`，衬线栈为 `Iowan Old Style, Charter, Georgia, Songti SC, SimSun...`。
- `【Windows 待验证】` 计算样式是候选栈，不等于 Windows 的 Rendered Fonts 结果。

Windows 实测要求：

- Chrome、Edge 各记录一次 `body`、28px 页面定名、20px 空间定名、14px 正文、12px 表格元数据的 Rendered Fonts。
- 100% / 125% 缩放分别记录中文、英文、数字的实际字体。
- 记录中文衬线标题是否实际落到中易宋体，英文是否落到 Georgia 或 Segoe UI。

修复建议：先回填 Windows DevTools 的 Rendered Fonts 证据，再决定是否调整栈顺序。没有实机证据时不改字体栈，也不引入 webfont。

风险等级：中

验收标准：Windows Chrome / Edge 在 100% / 125% 下记录到预期 sans 与 serif 字体，中文、英文和数字没有意外落到替代字体，Mac Retina 与 4K 现有字体观感保持不变。

## 问题 3：12px 小字号与浅色信号色在低密度屏幕上可能偏弱

问题编号：W-03

问题描述：全站存在大量 12px / 13px 元数据和表格辅助文字，其中部分使用信号色或主色。源码可计算出部分组合的静态对比度不足以承担普通小字的清晰度要求。

影响范围：表头、作品责任人、缺省值、截图状态、登录辅助链接、首页状态标签、筛选器和高密度数据表。

源码位置：

- `src/components/ui/table.tsx:92-110` 表头默认 12px、元数据色 `#78716C`。
- `src/app/(app)/admin/content/content-list-table.tsx:353-367` 责任人旁注使用 12px `#A8A29E`。
- `src/app/(app)/admin/content/content-list-table.tsx:462-478` 缺省值和发布时间使用 12px。
- `src/app/(app)/admin/content/detail/content-detail-evidence.tsx:94-100,165-171` 截图类型和“点击全屏”使用 12px `#A8A29E`。
- `src/app/page.tsx:160-162` 首页状态标签使用 12px `#D97757`。
- `src/styles/design-tokens.css:4-7` 定义 `#A8A29E` 信号墨和 `#78716C` 元数据墨。

Mac 检查结果：

- `【Mac 已验证】` 源码与 Mac 浏览器确认主要密集文字档位为 12px、13px、14px，没有发现 9px、10px、11px 的生产页面字号。
- `【Mac 已验证】` 静态对比度计算为 `#A8A29E` 对 `#FCFCFB` 约 2.46:1，`#D97757` 对 `#FCFCFB` 约 3.04:1，`#78716C` 对 `#FCFCFB` 约 4.67:1。浅砂底色会进一步降低相对比度。
- `【Windows 待验证】` 低像素密度、ClearType、实际字体和 100% / 125% 缩放下的可读性尚未观察。

Windows 实测要求：

- 放大检查表头、作品责任人、缺省值、截图类型、首页状态标签和登录辅助链接。
- 100% / 125% 分别记录“看清 / 费力 / 看不清”，并附原始截图。
- 记录同一文字在 Chrome 与 Edge 是否有可观察差异。

修复建议：若 Windows 实机确认文字发虚或看不清，只调整承担业务信息的具体颜色或字号。优先把重要的小字从 `#A8A29E` 提到 `#78716C`，保留装饰性信号墨，不做全局缩小或全局放大。

风险等级：中

验收标准：业务信息在 1920×1080、100% / 125%、Chrome / Edge、最大化 / 普通窗口均可读，装饰性信号仍保持层级，Mac Retina 与 4K 不出现明显变重。

## 问题 4：半透明发丝边框和 backdrop blur 可能在 1x 屏幕上偏灰

问题编号：W-04

问题描述：表格表头、导航、Toast 和部分卡片使用低透明度边框、半透明背景与 backdrop blur。源码静态对比度很低，Windows 1x 下需要实机确认边框是否仍清楚、文字是否被背景拖灰。

影响范围：顶部导航、表格吸顶表头、Toast、筛选浮层、数据卡片和所有使用发丝边的区域。

源码位置：

- `src/app/globals.css:214-220` Toast 使用 `backdrop-filter: blur(12px)` 和半透明边框。
- `src/styles/components/dashboard.css:20-28` Dashboard Toast 使用 `backdrop-filter: blur(24px)`。
- `src/components/ui/table.tsx:48-49,97-98` 表头使用 `bg-[#FCFCFB]/85`、`backdrop-blur-md` 和 `border-[#E2E2DF]/60`。
- `src/components/navigation/navigation-header.tsx:71-76` 导航使用半透明背景和 backdrop blur。
- `src/styles/design-tokens.css:18` 边框色为 `#E2E2DF`。

Mac 检查结果：

- `【Mac 已验证】` 代码中存在上述半透明边框与 blur 组合，Mac 960px 工作台截图中边框可见，但整体较轻。
- `【Mac 已验证】` `#E2E2DF` 对 `#FCFCFB` 的静态对比度约 1.26:1。
- `【Windows 待验证】` Windows 1x 显示器对低透明度边框、发丝线和 blur 的实际呈现尚未观察。
- `【推测，证据不足】` 目前没有 Windows 截图证据证明这些边框已经消失或文字已经发灰。

Windows 实测要求：

- 检查导航底线、表格表头底线、卡片边框、Toast 边界和浮层边界。
- 在 100% / 125% 下分别看静止态和滚动吸顶态。
- 记录边框是否连续、是否明显发灰、是否与背景混在一起。

修复建议：如实机确认边界过淡，只调整受影响组件的边框透明度或局部背景。保留现有层级和 blur 目的，不做全站统一加深。

风险等级：中

验收标准：边框在 Windows 100% / 125% 下连续可辨，表头文字与背景有清晰分界，Mac Retina 与 4K 视觉层级保持一致。

- 记录衬线标题旁的插图线条是否仍能和文字层级区分。

修复建议：如实机确认关键线条过淡，优先把承担识别作用的线宽调整到整数 CSS 像素或局部提高颜色。保留装帧插图和衬线标题设计。

风险等级：中低

验收标准：Windows 100% / 125% 下关键轮廓、图标和空态刻度连续可辨，Mac Retina 与 4K 下不出现明显变粗。

- `【Windows 待验证】` 1x 屏幕下曲线斜率、端点和 1.5px 描边的实际观感尚未观察。

风险等级：低

## 问题 7：动效期间存在 scale、zoom 和 blur 的瞬态清晰度风险

问题编号：W-07

问题描述：页面静止态没有发现长期作用的 CSS transform、zoom 或 Canvas 绘图。按钮按压、导航 hover、浮层开合、Toast 和 Dialog 入场使用 scale、zoom 或 blur，Windows 1x 下需要确认过渡期间文字和图标是否出现短暂发虚。

影响范围：按钮、导航图标、下拉菜单、Dialog、Toast、截图预览和页面切换。

源码位置：

- `src/styles/animations.css:3-81` 使用 translate 和 scale 关键帧。
- `src/lib/animations.ts:72-138` 列表、Toast、Modal 使用 scale 与 blur。
- `src/components/ui/button.tsx:9-45` 按钮和图标按钮使用 active scale。
- `src/components/navigation/desktop-nav-menu.tsx:120-182` 导航 hover scale 与 zoom-in。
- `src/app/(app)/admin/content/detail/content-detail-evidence.tsx:130-136,201-207` 截图 hover scale 1.01。

Mac 检查结果：

- `【Mac 已验证】` 源码确认这些效果仅在交互或过渡阶段触发，静止态没有全局缩放或图片插值规则。
- `【Windows 待验证】` Windows 低密度屏幕下的过渡瞬态尚未录制。
- `【推测，证据不足】` 目前没有证据证明这些动效会在 Windows 上造成用户可感知的清晰度问题。

Windows 实测要求：

- 快速打开和关闭下拉、Dialog、Toast、截图预览。
- 反复按压按钮并 hover 导航图标，观察文字边缘和 SVG 描边是否在过渡中发虚。
- 同时检查 `prefers-reduced-motion` 开启后的稳定态。

修复建议：若仅在 Windows 1x 过渡中出现短暂发虚，优先去掉具体组件的 blur 或减少 scale 幅度，不改全站动效体系。

风险等级：低

验收标准：动效结束后文字和图标稳定清晰，过渡期间没有明显闪烁、重影或边缘模糊。Windows Chrome / Edge 均通过。
