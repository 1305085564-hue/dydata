# 后端工程规范

> 写后端代码时的七条硬规矩，按"你要做什么"查。每条都是铁律，违反即返工。
> 最后核对：2026-10-14

## 一、查询与数据访问

### 数据库查询

页面和 API 使用 loader/领域服务编排查询，批量读取优先于实体循环。分页必须有页数或记录上限，长查询和外部依赖必须有超时；无法批量化时写明固定上限和理由。

查询失败、部分成功和空数据必须分别表达。统计口径以 [数据口径与计算规则](../业务逻辑/数据口径与计算规则.md) 为准，不能因为查询失败把未知值填成 0。

### 全局耦合点

成员可见范围统一从 `src/lib/data-access-scope.ts` 和权限上下文获得。新代码禁止自行拼接角色、团队和数据范围；`activeVisibleUserIds` 只用于当前操作，`visibleUserIds` 保留历史数据可见性。

跨模块读取 `daily_reports`、权限范围和 service role 数据前，必须写清调用者、目标范围和错误出口，并在基线报告中登记耦合点。

## 二、错误、超时与重试

### 错误处理

业务错误使用 `AppError` 的固定 code 和 HTTP 状态。用户响应只返回稳定文案、错误码和 requestId；内部错误通过结构化日志记录操作和目标，禁止把 SQL、token、密码或原始请求体返回浏览器。

`success/rejected/failed/thrown` 沿用现役 `observed-mutation` 语义。超时、依赖失败、权限拒绝和业务冲突必须可区分，不能用一个 500 覆盖所有情况。

### 外部调用与重试

外部请求和长查询必须有明确超时上限，统一使用 `src/lib/timeout.ts` 的 `withTimeout`。重试最多三次，只对超时、网络中断、429 和 5xx 等可恢复错误重试；输入错误、权限错误和业务冲突不得重试。

每次重试记录尝试次数。重试失败必须返回明确的依赖失败或超时结果，不能把部分数据伪装成完整成功。通知、审计等非核心副作用失败时，核心业务结果仍需单独表达，并保留人工补偿或再次执行入口。

## 三、缓存

新增进程内缓存必须使用 `BoundedTtlCache` 或提供等价证据，并声明作用域、TTL、最大条目数、主动失效和失败回退。用户、公司和集团数据的 key 必须显式隔离；空范围不能回退到全量。

基线和运行观测至少记录命中、未命中、过期、淘汰和失效次数。缓存读失败时重新读取或展示明确空态，不能把旧值当成成功结果。

## 四、发布与恢复

发布顺序固定为：先部署兼容代码，再执行已审查 migration，核验函数/RLS/索引和配置，最后部署使用新契约的代码并做真实 smoke 与角色验收。禁止数据库先行发布，也不能用 migration 账本代替线上状态核验。

恢复时先判断核心业务是否已经成功。通知、审计或待办失败优先走幂等补偿；数据口径错误先冻结入口再做可审计修复。每次恢复记录影响范围、时间、操作者、命令和结果。

正式部署与发布硬边界（Vercel 唯一入口、migration 只增不改）见 [工程运行事实](工程运行事实.md) 第五、六节。

## 五、观测与告警

所有 API、Server Action 和页面 loader 使用同一个 `RequestContext`，至少记录 `requestId`、路由、操作、操作者、目标和耗时。日志只记录结构化字段，禁止请求正文、token、密码和数据库原始错误。

关键指标分为请求结果、性能和后置副作用三类：

- 请求结果：状态码、`success/rejected/failed/thrown`、5xx 和超时率；
- 性能：P50/P95/P99、查询次数、RPC 耗时、缓存命中/未命中/失效；
- 业务结果：核心写入、审计、通知、待办和补偿分别记录。

基线由 `node scripts/architecture-baseline.mjs` 生成。静态脚本没有真实请求数据时必须保留空测量数组，不能用估算数字填充。
