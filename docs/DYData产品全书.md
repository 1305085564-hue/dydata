## 二、文档各放哪里

- `docs/系统架构与设计/` 写现在怎样运行，包括业务流程、权限、统计口径、模块和设计规范。
- `docs/reference/` 放以后还会用的已确认依据，包括设计与决策、契约和验收。引用时遵守记录的版本和范围。
- `docs/plans/` 放待做和在办材料。完成后把可复用结论写进参考，其余归档。
- `docs/archive/` 放只供追溯的历史。日常从本索引找当前依据。
- 通用管理和 UX 审计各自保留原用途，目录分工见[文档与维护规范](通用管理/文档与维护规范.md)。

## 三、长期事实文件的行数上限

只在本表维护，其他文件不再重复。按文件性质分三档，不逐个文件定数字：

| 档 | 上限 | 文件 |
|---|---:|---|
| **大**（天天查、内容厚） | **250** | 设计与决策下的每份页面和链路文件 |
| **中**（地图、索引、规范类） | **150** | 设计与决策总目录、纠错索引、文档与维护规范、CLAUDE.md写作指南 |
| **小**（附属文件） | **70** | 产品全书、待办清单、上下文交接 |
| **设计系统**（两卷一档） | 主卷 **450** · 辅卷 **400** | 效率美学（主卷：内核 / 决策树 / 任务型路由 / 失败模式）、美学宝典（数值与组件字典） |

**测试账号**是 gitignored 凭据文件，不受行数上限约束；只维护账号与用途，不堆背景和过程。

**设计系统为什么单列一档**：主卷是"开工必读量"与"总行数"分离的文档——开工先读 §0 内核 + §4 任务型路由，再按 §1 / §2 决策树走；§3 质感执行与 §5 失败模式按需下钻。按总行数套用"大档 250"会逼着人把判据和缘由拆散，判据一旦脱离缘由就会被机械执行（见主卷 §0 铁律）。辅卷是纯字典，行数可控。

**超限时按顺序处理，不跳步**：① **压缩**——重复条目合并、长段落改表格，信息不丢；② **清理**——删掉已下线/已失效的内容和"某次改成什么"这类变更流水（历史看 git 或 `docs/archive/`）；③ **拆子文件**——前两步做完仍超才拆，母文件留索引。硬规矩只有两条：**不许上调上限、不许硬破**。

## 四、纪律

1. **与代码冲突时以代码为准** —— 发现冲突当场修正文档
2. **执行方案不在这里** —— 一次性方案进 `docs/plans/`，完成后不回流
3. **已完成的不记录** —— 只记当前状态，历史看 git；**不写"某次改成什么、上限从多少调到多少"这类变更流水**
4. **同一结论只留一份原文** —— 其他文档只链接它，不复制第二份现行规则
5. **新增共用文件时同步更新本表** —— 否则下一个 AI 找不到它
