## 主要发现

### F-01｜"10/10 浏览器验收通过"不覆盖本批任何入口（P1）

实跑 `playwright.role.config.ts` 两条 spec（与方案 §9 的主验收命令一致），10 条用例逐条核对访问路径：

| 用例 | 实际访问 | 是否覆盖本批入口 |
|---|---|---|
| 组员在数据管理可打开本公司作品复盘（抽屉只读） | `/admin/collaboration?view=roles&tab=writers` | 否（上一批抽屉） |
| 组员仍进不了 `/admin/content`，写接口 403 | `/admin/content` 访问性 | 否 |
| 组长侧不回归 | `/admin/content` + 复盘抽屉综合徽章不变式 | 否 |
| 公司所有者侧不回归 | 同上 | 否 |
| 准则 1–4（契约占位 4 条） | 不打开页面（纯源码/类型断言） | 否 |
| 岗位表文案视角 16 列 | `/admin/collaboration?view=roles&tab=writers` | 否（上一批） |
| 个人档案抽屉「本月文案作品」+ 折线胶囊 | 同上 | 否（上一批） |

本批新增的三处可交付面——`/admin/content` 的综合评级列与评级筛选、`/admin/collaboration?view=teams` 的综合良优率列、`/topics` 抽屉的作品质量块与复盘入口——**没有任何一条浏览器用例**。用例中也不存在 `qualityGrade`、`view=teams`、`topic_id` 任一关键字。

后果：方案 §9 的"主验收命令"被**执行了**，但它证明不了本批完成度。汇报里"10 项真实角色浏览器自动化测试 100% 绿灯"字面为真，作为"后三个入口已验收"的证据不成立。

（本轮由审查方另起浏览器实测补齐了这三处：见下"已达标项对照表"。）

### F-02｜待采集行把"话题未知"当成"其他"（P2）

`qualityGrade=unrated` 下 4 行实测：

| 作品 | 综合评级 | 综合评级 title | 核心指标 |
|---|---|---|---|
| 4.15盘前 · 猎龙侦探 | 待采集 | 数据待采集 | **— 其他·点赞** |
| 未命名视频 · 罗礼杰 | 待采集 | 数据待采集 | **— 其他·点赞** |
| 反量化套路 · 股痴阿龙 | 待采集 | 数据待采集 | **— 其他·点赞** |

根因在 `content-list.tsx`（本批新增）：

```ts
const isDryGoods = quality?.topicKind === "dry_goods" || quality?.coreMetric === "favoriteRate";
const coreMetricTopicText = isDryGoods ? "干货·收藏" : quality?.topicKind === "review" ? "复盘·点赞" : "其他·点赞";
```

`topicKind === null`（尚无 24h 快照、话题未识别）落进最后分支，被标成"其他·点赞"。方案 §4.2 明确要求"标签查询失败返回明确 error 状态，**不把失败当作 other**"，§7 对 `topic_unavailable` 要求"不猜复盘口径"。这里虽然数值是"—"没造假，但**话题标签造假**了：把"不知道"显示成"其他"，会让人以为已确认过分类。正确形态是 `topicKind` 为 null 时不渲染话题标签。

### F-03｜未评级原因在组件内另有一份映射（P2）

`content-list.tsx` 可见文本用自写 if 链，`title` 才用契约函数：

| status | 组件内可见文本 | 契约 `getContentQualityStatusText` |
|---|---|---|
| unlinked | 未关联 | 未关联视频 |
| pending_snapshot | 待采集 | 数据待采集 |
| invalid_play | 不可计算 | 播放不可计算 |
| missing_metrics | 缺指标 | 指标数据缺失 |
| topic_unavailable | 分类未就绪 | 分类状态未就绪 |
| **其他/未来新增** | **待采集（兜底）** | 数据未就绪 |

同一枚举两份文案已经把组件变成第二个真相源；更实际的风险是最后那个 `else`：将来 `ContentQualityStatus` 新增任一取值，列表会**静默显示"待采集"**（tooltip 却是新状态文本，同一格自相矛盾）。方案 §阶段B 要求"所有未评级原因使用后端状态映射"，此处未做到。

### F-04｜"达人/运营零回潮"与实测不符（P2）

实测 `/admin/collaboration?view=teams&year=2026&month=9`（单表混排，文案与达人同表）：

| 行 | 列数 | 综合良优率格 |
|---|---|---|
| 达人一组 达人 | 11 | `—` |
| 达人三组 达人 | 11 | `—` |
| 文案二组 文案 | 11 | `7% 优4·良6·普21·劣120` |
| 文案一组 文案 | 11 | `6% 优2·良8·普16·劣149` |

达人/运营行的列数从原来的 10 变成 11，**多了一列空位**。汇报"达人与运营小队严格保持原列数与原有绩效结构，零回潮"因此不成立；方案 §阶段B"其他工种列数不变"在单表结构下也无法字面成立。

这不是 bug，是**产品判断没拍板**：单表混排只能共享列头。两种收法——(a) 接受共享列，把达人/运营格的"—"删掉只留空白；(b) 仅当列表中存在文案小队时才渲染该列（现在就是这个行为），但文案/达人混排时无法两全。建议阿禅拍板，别让它以"汇报说零回潮"的状态混过去。

### F-05｜权限别名被测试锁进断言（P3）

`TopicHubV2.tsx:696` 写的是 `canReviewContent={canManageTopicLibrary}`。两个名字底层的值恰好同源（`topics/page.tsx:54` 的 `hasCompanyPermission(companyRole, "review_content")`），**功能正确、无越权**；但名字把"复盘入口"和"选题库管理动作"耦合在一起。同批新增的 `topics-v3-frontend-contracts.test.ts` 又把这一行原文锁进断言：

```ts
assert.match(hub, /canReviewContent=\{canManageTopicLibrary\}/);
```

将来任何一次权限拆分或重命名都会误转红，且这条断言不验证任何真实权限行为。建议改成显式传 `review_content`，断言改测行为而非字符串。

### F-06｜只读视角"作品可读但无复盘入口"无真实数据可验（P3）

方案 §6 阶段D 第 5 条要求"用无 `review_content` 权限账号确认选题作品仍可读，但不能打开越权的复盘写入口"。实测：

| 账号 | 角色 | 该选题（`60f6dad7`）抽屉作品数 | 复盘入口 |
|---|---|---|---|
| 阿禅 | company_owner | 1 条（龙头二进三） | 有（2 处链接） |
| 测试组长 | admin | 1 条 | 有 |
| 测试组员 | member | **0 条**（同团队但作品对其不可见） | 无（因为没卡片） |

三个账号同属一个团队（`c6f07b84-…`），但组员看不到阿禅的作品，所以**没有任何作品卡**，"有作品但不显示复盘入口"这一半永远走不到。该条验收目前只有源码级契约测试支撑，浏览器层面**未验证**。

汇报中"无写权限的普通成员只保留只读卡片，无法打开越权写入口"属于把一个未验证项写成了已验证结论。

本次 `git status` 里同时存在**不属于本批**的改动：`src/lib/video-submit-deadline.ts(+test)`、`src/app/api/ocr-screenshot/*`、`src/app/api/video-submit/route.ts`、`src/app/api/admin/fulfillment/*`、`src/app/(app)/dashboard/video-submit-form-v2.tsx`、新 migration `20260930163503_add_account_scoped_video_submission_appeals.sql`（即"上传日期 / 72 小时补交 / 截图日期识别"那条线）。
