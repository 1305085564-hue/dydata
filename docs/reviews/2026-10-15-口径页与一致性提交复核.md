## 三、必须记入待办的问题

### H1（High）补交提示误伤异常作品，且可能没覆盖到真正的死循环

`src/app/api/video-submit/route-core.ts:298-305`（本次新增）：
无 `screenshot_2` 时一律返回"这条无法自动补交，请联系管理员确认。"

但 `src/app/(app)/dashboard/video-submit-form-state.ts:300`：
**只在 `anomalyStatus === "normal"` 时强制两张截图**——异常（限流/删稿）作品允许不传完播截图。

后果两面：
1. **误伤**：限流作品、员工合法未传完播截图 → 被告知"没救了找管理员"，而正确动作是"去补传一张"。可补救的被判成不可补救，且会制造无效的管理员咨询。
2. **没兜住**：真正补不上的场景（作品已删除、手上无图）且状态为 normal 时，员工其实**没有截图可传**，前端 `assetRoles.size !== 2` 会先拦下，根本到不了这条后端提示。D3 想解决的死循环没有被覆盖到。

**修法**：判据不能只看"有没有截图"，要看"是否真的无法提供截图"（如 `anomaly=deleted` 或视频已 purge）。
- 可补传 → "请补传能看清发布时间的完播截图"
- 确已无法提供 → "这条无法自动补交，请联系管理员确认"

### M1（Medium）"有效"现在有两个门槛，口径页会误导

口径页写"低于 **2,000** 播放不参与平均播放"，但 `work-quality.ts:3` 的 `EFFECTIVE_PLAY_THRESHOLD = 500` 才是数据管理里"有效作品数 / 结算基数"的线，且 **500 未收进 `CALIBER`**。
业务方看完页面会以为"有效 = 2000"，而报表里的"有效作品数"用的是 500——两个"有效"同名不同义。

### M2（Medium）优秀线被绑死在爆款门槛上

`work-quality.ts:4` `EXCELLENT_PLAY_THRESHOLD = CALIBER.hitMinPlay`（当前同为 3 万，行为未变）。
但两者是不同概念：爆款＝相对自己起飞，优秀＝绝对量。将来调爆款门槛会**静默改动**优秀线与结算基数。应拆成独立常量。

### M3（Medium）非缺勤标记也返回 `employeeNotificationStatus: "succeeded"`

`mark/route.ts` 最末 return 无条件带该字段。没发通知却报"成功"，语义不准，排障会误导。

### M4（Medium）路由模块互相 import

`buildAbsenceNotification` 定义在 `mark/route.ts` 并被 `bulk-mark/route.ts` 导入。Next.js 路由模块交叉 import 是脆弱写法（路由段配置、打包边界）。应挪到 `_shared` 或 lib。

### L1（Low）469 条日报无绑定作品

生产侧 2,229 条有效日报中 469 条 `video_id` 为空。这类在数据管理里永远取不到快照、`avgPlay` 直接 skip（属既有设计），但口径页未说明。建议补一句或至少知会业务方。

### 一审"未覆盖边界"的 BLOCKED 理由不成立

一审写"当前会话没有可用的认证浏览器角色条件"。实测：
- `docs/通用管理/测试账号.md` 提供 owner / admin / member 三档账号；
- 本机凭据文件 `.env.ai-test.local` 存在（2026-10-01）；
- `psql` 可用，生产池化串可读。

**缺的不是凭据，是没跑。** 补跑要点（踩过的坑）：
- dev server + Playwright **必须访问 `localhost`**，`127.0.0.1` 会被 Next 16 拦，表现为恒骨架态、零报错，极易误判为"功能坏了"；

### 新引入的问题（需阿禅拍板）

**N1（High）"限流"被顺带豁免了 72 小时补交门禁**

`shouldCheckPublishDeadline` = `punishType === "deleted" || (mode !== "abnormal" && anomalyStatus !== "abnormal")`。

改动前门禁条件是 `mode !== "abnormal"`，即只豁免「异常上报」这一种模式；
改动后 `create` 模式 + 状态=限流 → `anomalyStatus === "abnormal"` → **门禁被跳过**。

后果：任何人新建日报时把作品标成「限流」，即可补录任意久远日期的数据，**不再需要走补交审批**。
这与阿禅 2026-10-15 拍板的口径相反——当时的原话是「你限流不上传，那我天天都说自己限流了是不是一个月就不用发视频了」。

根因是 codex 把两件事混成了一个判据：**「提示该说什么」**（能否自助补救）与 **「要不要做 72 小时门禁」**（防事后补录造假）。限流作品同样可能是补录旧数据，不该豁免。

建议改回：门禁豁免只保留「删稿」与「异常上报模式」，限流照常受 72 小时约束。

**N2（Medium）删稿但已上传完播截图时，提示过早指向管理员**

`resolvePublishEvidenceFailureMessage` 把 `punishType === "deleted"` 放在最前，优先级高于「有截图、只是没认出来」。
若用户手上有图、只是 OCR 没读出来，仍会被直接告知「联系管理员」，而正确动作是换一张更清楚的图。
建议顺序改为：有截图 → 提示重传；无截图且删稿 → 才指向管理员。
