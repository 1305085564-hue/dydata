### R-06｜notifications 去重键 UTC fallback 未收口
- 优先级：P3（原定中危，当前为死路径，活跃影响低）
- 问题类型：时区口径 / 原根因未收口
- 对应旧根因：1A-1B返工记录:132「1D notifications/server.ts 去重键用 UTC 日期」→ 列入 1D 补充包；1D 标记"已部署并验收"。
- 结论：1D 实际工作（`1-P0与系统根因.md` 109-131 行）只改了 `formatShanghaiDateOnly`/`日报.ts` published_at/趋势榜，**未触碰 `src/lib/notifications/server.ts`**；当前代码 `server.ts:19` 仍为 `input.sourceId?.trim() || \`${input.type}:${new Date().toISOString().slice(0, 10)}\``，UTC 切日。该 `source_id` 参与通知唯一去重索引，北京 0–8 点跨 UTC 午夜时同源通知会被拆成两条（重复推送、已读/已办状态被重置）。
- 代码证据：`src/lib/notifications/server.ts:18-20`；旧登记 `docs/plans/全站质量审计-2026-09-03/1A-1B-返工记录.md:132`。
- 影响链路：通知去重与已读/已办状态。当前唯一 emit 调用方 `src/app/api/permission-requests/apply/route.ts:117` 传了稳定 `sourceId`（`${user.id}:${moduleTitle}`），故 fallback 为死路径，无活跃触发；但任何新增 emit 调用方若省略 sourceId 即落入此隐患。
- 复现/验证方式：对 `permission-requests/apply` 链路，在北京 00:05 与 01:00（同上海日、不同 UTC 日）各触发一次同源通知，观察是否生成两行；或新增一个省略 sourceId 的 emit 调用方后复测。
- 建议处理方向：将 fallback 改为 `formatShanghaiDateOnly()`（与全站业务日入口统一），或强制 emit 调用方必传 sourceId（类型层去可选）。

## 六、第一轮漏检问题

### R-01｜fulfillment 写 RPC 对 authenticated 开放且仅全局角色校验（跨团队越权写）
- 优先级：P0
- 问题类型：权限越权 / 入口安全（SECURITY DEFINER RPC 过宽授权）
- 结论：`mark_fulfillment_status` / `mark_fulfillment_status_batch` / `remove_fulfillment_mark` / `handle_fulfillment_appeal` 四个 SECURITY DEFINER RPC 均 `GRANT EXECUTE ... TO authenticated, service_role`，函数体内只调用 `public.is_admin_or_owner()`；而 `is_admin_or_owner()`（`059_admin_cockpit_rpc.sql:5-16`）只判 `auth.role()='service_role' OR EXISTS(profiles where id=auth.uid() and role IN ('admin','owner'))`，**无 team/company 维度**。任意团队的 admin/owner 用自身 authenticated 会话直调 RPC，即可对其他团队任意成员写履约标记 / 处理申诉，完全绕过 API 层 `requireActiveVisibleUsers`。违反 `docs/权限与安全说明.md` A.4「页面、Server Action、API、RPC、RLS 都必须做同一套检查」。
- 代码证据：
  - `supabase/migrations/20260806090000_fix_fulfillment_drop_group_refs.sql:331-334`（mark/batch GRANT）、`20260603070000_fulfillment_workbench_backend.sql:410-413`（remove GRANT）、`20260903153000_fix_fulfillment_appeal_drop_group_refs.sql:136`（appeal GRANT）。
  - `supabase/migrations/059_admin_cockpit_rpc.sql:5-16`（is_admin_or_owner 定义，无 team 维度）。
  - `20260603070000_fulfillment_workbench_backend.sql:218-260`（mark_fulfillment_status 函数体：permission check → status 校验 → member 查找 → INSERT，无目标归属校验）。
  - 对照正确范式：`20260728120000_atomic_collaboration_attribution.sql:57-60` 仅 grant service_role。
- 线上实测证据（阶段二，零写入）：用 `.env.ai-test.local` 测试账号（DB role=admin/owner）authenticated 会话调用：
  - `POST /rest/v1/rpc/mark_fulfillment_status {p_user_id:<zero-uuid>, p_record_date:"2026-09-04", p_status:"waived"}` → `{"code":"P0001","message":"member not found"}`（越过 is_admin_or_owner，停在 member 查找，未写入）。
  - `POST /rest/v1/rpc/handle_fulfillment_appeal {p_appeal_id:<zero-uuid>, p_decision:"approve"}` → `{"code":"P0001","message":"appeal not found"}`（越过权限校验，停在 FOR UPDATE select，未写入）。
  - 两返回均为 in-function RAISE（P0001），证明函数已对 authenticated 开放且 is_admin_or_owner 通过；若换真实他团队 user_id/appeal_id 即进入写入分支。
- 影响链路：发布管理（履约标记、申诉处理）。跨团队 admin 可伪造他人的请假/豁免/缺勤标记、批准/驳回他人公司的申诉，污染发布考核与应发口径。
- 复现/验证方式：A 公司 admin 登录后，浏览器 console 用 `supabase.rpc('mark_fulfillment_status',{p_user_id:'<B公司成员id>',p_record_date:'2026-09-04',p_status:'waived'})`，预期返回成功即确认。
- 为什么可能漏检：第一轮 P1-03/2C 只处理了同函数 `handle_fulfillment_appeal` approve 分支引用已删除 `profiles.group_id` 的运行时错误，未审查这些写 RPC 的 GRANT 与授权模型；且 `1A-1B返工记录.md` 自承"1E 静态 RLS 门禁未成通用守卫，admin_first_screen_perf_events 是一次性补丁"，即旧审计已知安全门禁未通用化，却未对 SECURITY DEFINER 写 RPC 做授权扫描。
- 建议处理方向：将四个函数的 `GRANT` 收敛为仅 `service_role`，或在函数体内增加目标成员归属校验（复用 `active_visible_user_ids_v2` / 目标 team_id 与调用者 team_id 一致），与 API 层 `requireActiveVisibleUsers` 同口径；并补一条"SECURITY DEFINER RPC 必须 service-role-only 或带归属校验"的通用门禁（回应旧审计 S6 自承的未通用化）。

### R-04｜video-submit 多表写入无事务边界，崩溃窗口留孤儿数据
- 优先级：P2（系统性观察）
- 问题类型：多表写入一致性 / 事务边界
- 结论：`/api/video-submit` 顺序写 videos → video_metrics_snapshots → daily_reports → video_tags → script_usage_records，仅靠 `rollbackActions` 数组在 **API 层捕获的错误路径**做补偿回滚；进程崩溃（非 API 错误）发生在任一写入后、回滚前，会留下"有视频无日报"或"有日报无标签"等孤儿态。`daily_reports(account_id, report_date)` 有唯一索引兜底重复（`009_accounts_and_account_reports.sql:65`），但跨表一致性无 DB 层保证。
- 代码证据：`src/app/api/video-submit/route.ts:469-803`（顺序写入 + rollbackActions.push）；`:95-107` rollbackSafely 仅在 catch 路径调用。
- 影响链路：核心作品数据一致性。`generateAiTags`（`:714`，12s 超时）发生在快照与日报已落库之后、标签写入之前，延长了不一致窗口。
- 复现/验证方式：在 daily_reports insert 后、video_tags delete 前 kill 进程，检查库中是否存在"有日报但无对应 ai 标签且 video 存在"的记录；属破坏性测试，建议在隔离环境做。
- 为什么可能漏检：旧审计 P0-02/1B 聚焦"误删/误回收/改错作品"的编辑绑定安全，已修 `edit-binding.ts` 重核对；但"多表写入无 DB 事务"这一系统性形态未被收口（S7/P1-09 标记"非视频模块"多表半成功，而 video-submit 是视频模块，反而在 P0-02 范围外）。
- 建议处理方向：将核心四表写入收敛进一个 SECURITY DEFINER RPC（参考 `update_collaboration_attribution` 同事务范式），或接受现状但在文档明示"崩溃窗口由唯一索引兜底重复、跨表孤儿需对账脚本修复"。

- 结论：V3 移除排他认领，claim 与 start-scripting 均调 `startWritingClaim`，并发第二人靠唯一索引 `sub_topic_claims_one_writing_per_user_topic` 兜底；`service.ts:702-713` 用 `error.message.includes("<索引名>")` 做撞车回读，若 DB 报错被包装/本地化则第二并发者偶发 500。
- 代码证据：`src/lib/topics/service.ts:702-713`；migration `20260829091000:35-37`。
- 影响链路：选题认领并发。低频，仅偶发 500。
- 复现/验证方式：两人同时对同一 sub_topic 发 start-scripting，第二人应得"已在写"提示而非 500；本地化 DB 错误信息后复测。
- 为什么可能漏检：旧审计 D 区覆盖并发但未触及 topics V3 认领链路（V3 较新）。
- 建议处理方向：改用 `error.code === '23505'` 判唯一约束冲突，不依赖消息串。

### R-10｜recent7dParticipants 全量 vs claimCount 范围口径不一致
- 优先级：P3（口径）
- 问题类型：数据范围口径不一
- 结论：池 `claimCount` 走 scope（`buildTopicPoolItem:879/871`），但 `recent7dParticipants` 来自 RPC/`loadRecent7dHeat:1551`（忽略 scope，全量）。普通成员可见"X 人在写(受限)"却见"Y 人参与(全量)"。
- 代码证据：`src/lib/topics/service.ts:871,879,1551`。
- 影响链路：选题池展示口径。轻微信息差。
- 为什么可能漏检：旧审计 P1-11 涉及业务常量/状态集合收敛，但 participants 口径未纳入。
- 建议处理方向：`recent7dParticipants` 按 scope 过滤，或文档明示其全量语义。

### R-11｜feishu-workspace URL 校验未封内网/元数据地址
- 优先级：P3（SSRF 硬化）
- 问题类型：输入校验 / SSRF
- 结论：`validateFeishuWorkspaceUrl`（`feishu-workspace.ts:22`）只验 `https:`+非空 hostname，未封 `169.254.169.254`/`127.0.0.1`/`localhost` 等内网/元数据地址；配置由 admin/manage_system 写入，前端浏览器打开可泄露云元数据。
- 代码证据：`src/lib/topics/feishu-workspace.ts:22`。
- 影响链路：选题库飞书空间地址。仅 owner 可配，影响有限。
- 为什么可能漏检：旧审计未对 admin 配置类 URL 做 SSRF 专项。
- 建议处理方向：加内网/环回/元数据地址黑名单。
