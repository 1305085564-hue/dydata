# DYData 后端与数据说明

> 本文件是"后端与数据"领域的入口分诊页：接了接口/数据相关的活，动手前先读这里，知道该看哪几处、边界在哪、有哪几条死规矩、出问题按什么顺序查。
> 它只做串联和立规矩，不重抄数据口径和数据库规范——那些在现成资源里，本文件只指路。
> 用途：任何 AI 动"接口对不对、数据准不准、快不快"的活之前，先在这里对齐领域边界和必读清单。
> 面向阿禅：你不用懂代码。这份是给做后端的 AI 立的规矩和指路，保证它接手时不乱查、不改坏数据。术语一律就地用大白话解释。
> 面向 AI：这里是后端与数据领域的分诊入口，事实已按当前代码核实。与代码冲突一律以代码为准并当场修本文件。
> 最后核对代码日期：2026-08-07

## 〇、这个领域管什么（给阿禅）

网站分七个领域，这份管其中一个——后端与数据。用大白话说，就是管三件事：接口对不对（点一下按钮，后台给的数据对不对）、数据准不准（那些播放量、涨粉率算得对不对）、快不快（接口响应慢不慢，含 AI 接口）。它不管页面长什么样（那是前端体验领域）。

---

## 一、领域边界（这活归不归我、哪部分要转派）

管：接口逻辑、数据查询、数据准确性、数据库结构（表和字段）、AI 接口的调用与配置。主要执行是 Codex。

不碰、要转派的：
- 页面样式、交互、动效 → 转前端体验领域（`docs/美学规范.md`）。后端任务不改页面长相。
- 权限规则本身（谁有资格看/改、角色和开关怎么定）→ 转权限与安全领域（`docs/权限与安全说明.md`）。但注意：后端查询普遍直接用权限领域算好的 `visibleUserIds`（能看见哪些人）做范围过滤，"数据查不出/查错人"的后端排查绕不开它，不能简单转走——见第四节。边界是"权限规则归权限领域，范围过滤的落地在后端查询里，两边都要看"。
- 页面慢、首屏慢、请求数多 → 转性能领域（`docs/架构与性能总纲.md`）。后端只管单个接口/查询快不快，整页性能走总纲。
- 出线上故障（白屏/登录挂/报错）→ 先走 `docs/运维排查手册.md` 急救，再回本领域查根因。

一个任务只落一个领域，跨领域先拆、产出提示词转派，不越界顺手改。

## 二、动手前必读（散在多处的现成资源，这里串成入口）

后端与数据的知识刻意复用现成资源，不单独造百科。接活前按需读：

- `docs/数据口径.md`：6 个核心指标（24h 播放、互动率、粉转率、导粉率、主页访问率、爆款系数）的定义、公式、代码来源、爆款判定标准。凡涉及指标怎么算，先读它，别自己推。
- skill `supabase-postgres-best-practices`：数据库和 Postgres 的写法规范（查询、迁移、索引等）。写数据库相关代码前对照。
- skill `nextjs-supabase-auth`：Next.js + Supabase 的登录认证写法。碰认证相关接口时读。
- `docs/架构与性能总纲.md` 第三节"页面→加载器→表→接口映射"：核心页面的依赖图（指向 `docs/全站模块地图.md` 各模块明细）。查"这个接口连哪张表、改了连累谁"。
- `docs/全站模块地图.md`：哪张表连哪些页面、哪些接口是活的还是废的。动一张表前先查它的连累面。
- `docs/权限与安全说明.md`：service role（绕过数据库门禁的超级权限）和 RLS 的规矩。写用 service role 的接口前必读。

### 选题库 V2 接口契约

- 正式入口为 `/topics`，由 `TopicHubV2` 渲染；V2 首屏读取 `active`、`options`、`pool?view=my_claims`、`pool` 和 `comparison`，详情抽屉按需读取 detail、works、claims。`/topics/[id]` 作为外部深链兼容详情页保留。
- `GET /api/topics/pool` 接收 `view`、`time_range`（含 `all`）、重复 `topic_id`、`q`、`sort`（`latest`/`avg_play`/`claim_count`）、`page`、`page_size`；返回 `pagination.totalItems`，服务端完成筛选、排序后再分页。
- pool/detail 的 `myClaim` 只对应当前登录用户，状态为 `candidate` 或 `scripting`；团队 `sub_topic_claims` 只用于撞车统计。
- `GET /api/topics/active` 返回 `focusTopics`，每项带 `reasonType`、`reasonText`、`latestWorkedAt` 和 `summary`；V2 前台不展示 AI 推荐入口。
- 选题接口成功响应是业务 JSON 本体，不包 `{ ok, value }`；V2 前端统一使用 `src/lib/topics/v2-client-contract.ts` 检查 HTTP 状态并解析。

只读这些、不在本文件重抄它们的内容。

## 三、数据库访问死规矩（原来散着，收口到这里）

这些是从代码和 CLAUDE.md 收口的硬规矩，不是新造，写接口/查询时必须守：

- 选对数据库连接：`src/lib/supabase/` 四种客户端（`client` 浏览器端 / `server` 服务端受 RLS 约束 / `admin`·`service` 同一把超级钥匙绕过 RLS）。完整说明和安全规矩见 `docs/权限与安全说明.md` 第四节。
- 只查线上真实存在的字段。`select` 里写的字段，必须是线上数据库已经有的；不确定先查真实表结构和已跑过的 migration，别凭旧记忆写字段。
- **含新字段的接口，发布三连卡点缺一不算完成**：① migration 已在生产执行；② PostgREST schema cache 已刷新（验证方法：用 service-role key 对 `/rest/v1/<表名>` 发 GET，新字段出现在 OpenAPI 字段列表里才算刷新完）；③ 用真实角色（成员/管理员）发一次 API 请求，确认字段可读。忘掉任何一步都可能让线上组员撞到"字段不存在"错误。
- 缺字段要降级、别崩。读可能缺列的表时做兼容降级（查不到就返空/默认值），不要让整个页面因为一个缺列直接报错。
- migration 只增不改。数据库结构变更只能新增 migration 文件，禁止改任何旧 migration。
- 不留幽灵字段。前端传给后端、但后端没有接收逻辑的字段，要么补后端接收、要么删掉，不留半截。
- **多表伪事务（rollback 模式）**：提交链路对多张表做先写后回滚，不是真正的数据库事务。回滚失败必须保留第一个错误并上报，不能让 rollback 报错覆盖原始错误（`rollbackSafely` 返回的 Error 不能丢弃，调用后必须处理返回值）。回滚操作如涉及成员 RLS 受限表（如 `video_metrics_snapshots`），需走 service role 客户端，否则 delete 静默 0 行但不报错，造成半提交残留。
- **"找不到"有四种原因，不要混淆**：(a) 记录真的不存在；(b) 权限不足（RLS/鉴权过滤）；(c) lifecycle 状态过滤（如只查 `lifecycle_state='active'` 而记录在回收站）；(d) PostgREST schema cache 未刷新（字段层面的"不存在"）。接口报 404/not found 时按这四类依次排查，别只看前两类。
- **成员生命周期读取边界**：`profiles.membership_status` 区分 `active`（可操作）和 `archived`（已归档）。当前操作（指派、提醒、履约、协作、权限修改）必须使用 `activeVisibleUserIds`（只含 active）；历史数据查询（日报、视频、协作统计、审计）继续使用 `visibleUserIds`（含 archived）。归档不删除任何历史业务数据。
- **新字段发布三连（`membership_status` 实例）**：生产历史中的 `member_change_log` 与新库结构不同，必须先执行幂等的 `20260805113000_member_lifecycle_production_compat.sql`，再执行 `20260805100000_member_lifecycle_write_protection.sql`；随后将旧生命周期版本、写保护版本和兼容版本精确 repair 为 applied，再刷新 schema cache 并做真实角色验收。禁止用 `supabase db push` 带上无关 pending migration。执行前代码走 fallback（缺字段按 `active` 兼容读取，页面不崩），fallback 仅用于发布窗口过渡期，不代表生产已完成。
- **归档服务接口语义**：`archiveMember`（owner-only）清空团队、降为 member、封禁 Auth 并保存快照；`restoreMember`（owner-only）回到 active、无团队、member、空权限并解封。`removeFromTeam` 仅清空 team_id，账号仍可登录。
- **生命周期写权限**：浏览器认证会话只允许更新自己的 `profiles.name`，不能直接 insert profile，也不能修改生命周期、角色、权限或团队字段；管理页统一通过 service role 生命周期服务写入。`20260805100000_member_lifecycle_write_protection.sql` 同时用列权限和触发器保护生命周期字段。
- **生命周期发布脚本**：`scripts/member-lifecycle-release.sh` 默认只打印 dry-run 步骤；生产兼容与写保护 migration 必须在 Supabase SQL Editor 中逐条执行，确认成功后脚本才允许对三个生命周期版本执行精确 `supabase migration repair`。脚本不依赖未部署的 `exec_sql` RPC；schema cache reload、OpenAPI 字段确认、真实角色验收和历史数据对账仍是人工强制卡点。

## 四、数据/接口问题排查顺序

聚焦数据层，和运维手册的"线上急救"分工（急救先看那份）：

1. 数据算得不对（口径类）：先翻 `docs/数据口径.md` 的公式，再对 `src/lib/video-metrics.ts` 的实现，确认是口径理解错还是计算错。
2. 数据查不出/查错人：分三类查，别只看前两类——(a) 权限规则（RLS/service role，转权限领域）；(b) 字段（查真实表结构和已跑 migration）；(c) 范围过滤，最常被漏：查询是否按 `visibleUserIds` 过滤、团队/组范围对不对、RPC 的范围参数（如 `p_visible_user_ids`）传对没、业务筛选条件是否把数据滤掉了。数据"凭空消失"多半在第三类。
3. 接口报错：去 Vercel 后台看这个接口的运行日志（Functions/Logs），报错信息在那；再顺模块地图找它依赖哪张表。
4. AI 接口相关：配置有多条并行路径，排障别只盯 `admin/ai-config` 中枢——还有环境变量兜底（`AI_BASE_URL`/`AI_API_KEY`/`AI_MODEL`，见 `src/lib/ai/client.ts`）、旧表 `ai_feature_config` 和旧接口 `/api/admin/ai-rewrite` 仍在读写。先确认这次调用实际走的是哪条路径，再查配置对不对。相关表和接口见模块地图 AI 配置中枢一节。
5. 单接口慢：查询本身的慢属本领域（看有没有该加的过滤、该走的 RPC）；整页慢转性能总纲。
