## A. 新权限契约（2026-08-19 对齐，代码待迁移）

> **状态：规则已对齐，核心代码已接入，生产数据库尚未核对和执行新 migration。**
> 在 migration 执行、Vercel Ready 和真实角色测试完成前，不得把本节当成“线上已经生效”。本节是后续施工唯一依据。

### A.1 业务名称

为避免“团队、公司、全公司”混用，今后统一使用下面的词：

| 业务名称 | 当前代码名称 | 含义 |
|---|---|---|
| 公司 | `team` / `team_id` | 例如“深圳二部”。成员属于一个公司。 |
| 集团 | 当前所有 `team` 的总范围 | 例如深圳一部、深圳二部等所有公司。 |
| 公司所有者 | 当前旧称 `owner` 的目标含义 | 管理一个公司内的全部人员和业务。 |
| 集团权限 | 当前旧称“全公司权限”的目标含义 | 临时跨公司管理集团内所有公司。不是普通组长默认拥有的权限。 |
| 归档 | `membership_status = archived` | 账号状态，不是角色。保留历史，禁止当前操作。 |

当前数据库只有 `team_id`，没有 `company_id` 或独立集团表。因此本阶段的“公司”实际仍落在 `team_id` 上，“集团”实际是当前项目内所有团队的集合；不能把本系统误认为已经支持多家相互隔离的外部公司。

### A.2 身份和范围

| 身份 | 默认范围 | 能做什么 | 明确不能做什么 |
|---|---|---|---|
| 组员 `member` | 自己 | 查看和提交自己的业务数据、个人导出、个人数据分析、只读岗位管理、提交自己的豁免申请 | 不能审批、不能管理其他成员、不能跨公司读取或写岗位归属 |
| 组长 · 管理 `admin` | 当前公司 | 处理本公司的日常业务、审批本公司在职成员的申请、管理本团队组员 | 不能跨公司审批，不能管理组长、公司所有者或自己，不能把组员升为组长，不能修改系统安全配置 |
| 公司所有者 `company_owner` | 当前公司 | 管理本公司全部成员、组长、业务数据和审批流程；可手动切换集团视角 | 默认仍是当前公司；集团视角不能由页面参数伪造 |
| 集团视角 | 由在职公司所有者手动开启后为集团 | 临时管理集团内所有公司的权限范围和业务 | 普通组长、组员和归档账号不能进入 |
| 归档账号 | 无当前操作范围 | 只能保留历史记录供有权人员查询 | 不能登录、提交、审批、指派、提醒、上传、修改或恢复其他数据 |

集团视角不是独立的日常角色，也不是服务器申请事项。阿禅的账号默认仍是深圳二部公司模式，需要时在网页内一键进入；底层权限仍由服务端按 `company_role` 校验。

### A.3 集团模式

集团模式是一个由服务端保护的视角切换器：

1. 只有在职 `company_owner`（旧 `role=owner` 作为迁移兼容）可以进入。
2. 进入集团模式只验证当前有效登录会话，不填写进入原因；这不是严格意义上的二次认证。
3. 进入和退出都通过服务端签发/作废 HttpOnly Cookie；不再设置 30 分钟强制过期，由老板手动退出。
4. 页面、Server Action、API、RPC 和 RLS/helper 必须同时检查集团模式，不能只改页面显示。
5. 退出、过期和每次跨公司写操作都要留下审计记录。
6. 普通组长即使知道其他公司的用户 ID，也不能伪造集团模式或跨公司操作。

当前实现入口为 `/api/group-mode/enter`、`/api/group-mode/status` 和 `/api/group-mode/exit`。令牌只以哈希保存，数据库会话用户、当前公司角色和撤销状态必须同时匹配；旧会话的 `expires_at` 仍兼容，但新会话不写过期时间。有效登录会话被盗时，仍存在进入集团模式的风险，不能把当前流程宣传为真正二次认证。

### A.4 权限类别总表

以后每个权限判断都必须同时写清下面六件事，缺一项就算权限定义不完整：

| 权限类别 | 要回答的问题 | 统一规则 |
|---|---|---|
| 身份权限 | 这个人是谁 | 组员、组长 · 管理、公司所有者；集团权限单独记录；归档是状态 |
| 功能权限 | 能不能做这件事 | 由固定身份规则决定，不再由个人随意拼装权限开关 |
| 数据范围 | 能对哪些人的数据做事 | 组员=自己；组长 · 管理/公司所有者=当前公司；集团模式=集团全部公司 |
| 当前/历史 | 归档成员是否还存在 | 当前操作只认 active；历史查询保留 archived |
| 对象归属 | 这个申请、成员、记录属于谁 | 由服务端从数据库读取并核对，不能相信浏览器传来的 `user_id`、`team_id` |
| 入口安全 | 绕过页面能不能操作 | 页面、Server Action、API、RPC、RLS 都必须做同一套检查 |

### A.5 豁免申请和审批

| 动作 | 组员 | 组长 · 管理 | 公司所有者 | 集团模式 |
|---|---|---|---|---|
| 提交自己的申请 | 允许 | 允许 | 允许 | 允许 |
| 查看待审批申请 | 不允许 | 当前公司在职成员 | 当前公司在职成员 | 集团全部公司在职成员 |
| 审批本公司成员 | 不允许 | 允许 | 允许 | 允许 |
| 审批其他公司成员 | 不允许 | 拒绝 | 默认拒绝 | 允许 |
| 审批自己的申请 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 审批归档成员 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |

审批必须按以下顺序执行：登录 → 身份和功能权限 → 当前模式 → 目标成员所属公司 → 目标成员状态 → 申请状态 → 原子写入。审批成功必须同时更新申请状态、豁免授予和目标资料；任一步失败都不能提示成功。

### A.6 固定权限开关的处理规则

当前代码仍有 11 个 `PERMISSION_KEYS`：

`view_analytics`、`export_data`、`view_conversion`、`review_content`、`manage_fulfillment`、`manage_videos`、`manage_members`、`review_violations`、`manage_system`、`use_ai_copy`、`use_ai_assist`。

这些开关在运行时由 `src/lib/company-permissions.ts` 按 `company_role` 固定生成；`profiles.permissions` 里的 legacy JSON 只保留兼容数据，不决定当前权限。进入集团模式时统一使用 11 项集团权限。迁移期间必须遵守：

- `manage_members` 不能单独推导出豁免审批权。
- `review_violations` 不能顺带推导出豁免审批权。
- 不能因为某个权限开关打开，就把组长 · 管理范围扩大到其他公司。
- 不能用 `permissions = {}`、字段缺失、`null` 或空数组解释成“全集团”。
- 新增功能必须先在本节登记“身份、范围、当前/历史、对象归属、入口和数据库检查”，再写代码。
- 迁移完成后，删除不再需要的个人权限开关和 `data_scope` 组合；不得长期保留两套规则同时生效。

### A.7 统一数据范围语义

- 当前公司范围：只包含该公司成员；当前操作只包含 `active` 成员。
- 集团范围：只在可信的集团模式中出现，包含集团内所有公司的 `active` 成员。
- 历史范围：可以查询权限范围内的历史记录，包括 archived 成员；归档不能让历史数据消失。
- 空范围：表示“没有可操作对象”，不是“全部对象”。查询、计数、汇总、导出、详情和下载必须保持同一范围。
- 没有公司归属的成员：不能自动回退到集团范围；只能按明确的“自己”范围处理，管理操作需明确拒绝或由公司所有者补齐归属。

## B. 迁移前旧实现（仅作代码事实，不是新规则）

系统里"角色"和"数据范围"分开看，别混：

- 数据库角色（`role`）：存在数据库里的原始身份，只有三种——`owner`（老板）、`admin`（组长 · 管理）、`member`（组员）。
- 数据范围（`data_scope`）：这个人能看到多少人，只有三种——`all`、`team`、`self`。
- 程序判断时直接看 `role + permissions + data_scope + team_id`，不再用小组/组长那套旧边界。

为什么要分开：`role` 只管身份，`permissions` 只管能不能做某件事，`data_scope` 只管能看到多少人。判断一个人能干什么、能看谁，别再混成一把。

## B.1 旧角色映射表（谁是谁、能到哪）

程序怎么把角色和范围落地（逻辑分散在 `src/lib/permissions.ts`、`src/lib/data-access-scope.ts`）：

| 角色/范围 | 成立条件 | 数据可见范围 | 默认权限 |
|---|---|---|---|
| owner | 数据库 `role = owner` | 全部（all） | 全开 |
| admin | 数据库 `role = admin` | 由 `data_scope` 决定（all/team/self） | 部分开（见第二节） |
| member | 其他所有情况 | 只有自己（self） | 全关 |

补充：owner 的有效范围固定为 all；即使数据库残留旧的 `data_scope=team` 或 `self`，应用层和数据库范围函数也不能把 owner 限制成团队或本人。

`visibleUserIds`（`data-access-scope.ts`）是程序给你算出的"你有权看到数据的那批人"；`activeVisibleUserIds` 只保留 active 成员，给当前操作用。历史查询继续用 `visibleUserIds`。

### 权限作用域原则

- 所有权限相关逻辑（成员可见性、数据筛选、指派范围）默认以**团队（team）+ 数据范围（data_scope）**为单位。
- 小组（group）已废弃，不再作为权限边界。
- 涉及权限改动时，必须向阿禅说明：影响范围（谁能→谁能操作/看到什么）、边界条件（没团队的人怎么处理）。

## B.2 旧权限开关清单（PERMISSION_KEYS）

所有细粒度权限开关统一定义在 `src/types/index.ts` 的 `PERMISSION_KEYS`，共 11 个，分四组。每个人的 `permissions` 字段就是这 11 个开关的开/关状态。

业务/内容/管理/AI 四组：

| 开关 | 中文名 | 管什么 |
|---|---|---|
| view_analytics | 数据分析 | 能否进数据分析页 |
| export_data | 导出数据 | 能否导出 |
| view_conversion | 转化中心 | 能否看转化数据 |
| review_content | 视频复盘 | 能否进视频复盘 |
| manage_fulfillment | 发布管理 | 能否管履约/豁免相关动作 |
| manage_videos | 素材库 | 能否管视频素材 |
| manage_members | 成员管理 | 能否管成员状态 |
| review_violations | 违规复核 | 能否复核违规/案例 |
| manage_system | 系统设置 | 能否改系统参数 |
| use_ai_copy | AI 文案助手 | 能否用文案改写工具 |
| use_ai_assist | AI 管理助手 | 能否用后台 AI 助手做查询/执行 |

各业务角色的固定开关（`src/lib/company-permissions.ts` 的 `DEFAULT_PERMISSIONS_BY_COMPANY_ROLE`）：

- `company_owner`（兼容旧 `owner`）：11 个全开。
- `admin`：固定开 `view_analytics`、`export_data`、`view_conversion`、`review_content`、`manage_fulfillment`、`manage_videos`、`manage_members`、`review_violations`、`use_ai_copy`，共 9 项。
- `member`：固定开 `view_analytics`、`export_data`，共 2 项。

重要规则：运行时权限由 `fixedPermissions(...)` 按公司角色生成，`profiles.permissions` 里的 legacy JSON 不会覆盖固定角色表。组员的 `view_analytics` 只表示个人数据分析和只读岗位管理，`export_data` 只表示个人 `daily_reports` 导出；组长的两项权限分别按当前团队范围执行。`manage_members` 也不允许普通组长管理组长、公司所有者或自己，不能把组员升为组长。

关于 `data_scope` 的坑：它才是"能看到哪些人的数据"的主链路，不再靠 `view_all_data` 这种旧权限键。`visibleUserIds` / `activeVisibleUserIds` 都从这里出发，改范围逻辑要回到 `data-access-scope.ts` 看。

## B.3 旧鉴权链路（三层）

权限不是靠数据库一层，是应用层为主、数据库为辅。理解这个分工是安全判断的关键。

第一层 · 登录闸机（`src/middleware.ts`）：所有受保护页面（dashboard/admin/growth/content-tools，以及历史遗留的 violations 路径——该模块已下线但 matcher 未清，命中只会被正常登录闸机处理）以及带认证 cookie 的 API 请求先过 middleware。它校验有效登录态和 `profiles.membership_status`：明确 session 无效返回 401 并清理会话，明确归档返回 403 并清理会话，生命周期核验暂时失败返回 503 但保留会话；同时负责限流和清缓存开关。它不判角色或功能级细粒度权限。

第二层 · 接口鉴权（多种入口，`requireAdminActor` 是其中之一）：后台管理接口的权限关卡。`src/app/api/admin/auth-helper.ts` 的 `requireAdminActor` 做四步——确认已登录、读出 profile、算出业务角色和权限、比对本接口要求的权限（`requiredPermission`），不满足返回 403；约 9 个 route 文件直接用它。**但接口鉴权不是只有这一种**：还有的接口走 `getUserPermissions` 自行判权限、走 `requireAuth` + 对象归属校验（如改写接口用 `requireConversationOwner` 校验会话归属）、或走 cron 密钥（定时任务接口，`src/lib/cron-auth.ts`：Vercel Cron 的 `Authorization: Bearer CRON_SECRET` 或 `?secret=`（值必须来自 `CRON_SECRET`/`REMIND_SECRET` 环境变量，vercel.json 禁止写明文，2026-08-22 起泄露的旧明文已从 vercel.json 移除并要求轮换））。判断一个接口安不安全，不能只看它有没有 `requireAdminActor`，要看它有没有"某种等价的登录 + 权限/归属/范围校验"。`requireAdminActor` 不传 `requiredPermission` 时，退化成"有任意一个管理类权限就放行"（`hasAnyAdminPermission`）。第三层 · 数据范围过滤（`current-permission-context.ts` + `data-access-scope.ts`）：确认"能进这个接口"之后，还要限定"只能看到你范围内的人"。它算出 `visibleUserIds` 清单，查询按这份清单筛，member 就只筛出自己。owner 范围是 all，不筛。

性能补充：第一、三层的权限查询用 React `cache()` 做了"同一次请求内去重"（`permissions.ts` 的 `loadUserPermissions`、`current-permission-context.ts` 的 `getCurrentPermissionContext`），同一个请求里重复问权限不会重复查数据库。

## B.4 service role：绕过所有权限的"万能钥匙"（安全重点）

术语：正常情况下数据库有一层叫 RLS（行级安全）的门禁，规定每个登录用户只能读到自己该读的行。但有一把"服务端密钥"（service role key）能完全绕过 RLS，用它连数据库等于以超级管理员身份操作，谁的数据都能读能改。

关键事实（`src/lib/supabase/admin.ts`）：
- `createAdminClient()` 用环境变量 `SUPABASE_SERVICE_ROLE_KEY` 建连接，绕过 RLS。`service.ts` 里的 `createServiceClient` 只是它的别名，同一把钥匙。
- 全站约 61 个后台 route 文件在用这把钥匙。这是刻意的架构选择：后台接口不靠数据库 RLS 控权，而是先在应用层挡住没权限的人（用第三节的接口鉴权），进来之后用 service role 直连数据库。
- 连权限本身的读取（`permissions.ts`、`data-access-scope.ts`）都用 service role 读 profiles——因为要在"判断你是谁"这一步先绕过 RLS 才能读到完整信息。

安全含义（务必守住）：
- service role 用得对不对，全压在应用层鉴权上。任何用了 `createAdminClient`/`createServiceClient` 的接口，必须先有等价的鉴权——登录 + 权限校验（`requireAdminActor` 或 `getUserPermissions`），或对象归属校验（如改写接口的 `requireConversationOwner`），或按 `visibleUserIds` 的范围过滤。三者一个都没有、直接拿 service role 返数据，才是越权漏洞。别一看到"没走 requireAdminActor"就判成漏洞——很多接口走的是等价的另一种校验。
- service role key 是服务端机密，绝不能出现在发到浏览器的代码里，绝不写进前端，绝不 log。
- 判断一个后台接口安不安全，先看两点：有没有某种等价鉴权（`requireAdminActor` 传对 `requiredPermission`，或 `getUserPermissions` 自判，或对象归属校验，或 cron 密钥）；返数据时有没有按 `visibleUserIds` 限范围。

## B.5 数据库 RLS：第二道纵深防御

虽然后台接口普遍用 service role 绕过 RLS，RLS 仍是重要的兜底——面向浏览器直连的普通客户端（`client`/`server`）仍受 RLS 约束。**RLS 策略散落在多份 migration 里，不止下面几份**，改任何表的读写权限前，先扫一遍 `supabase/migrations/` 里所有涉及该表 `create policy` / `enable row level security` 的文件，别只看这几份早期核心的：

- `002_invite_rls.sql`：邀请码表的 RLS（注册时按规则可读、只能标记自己用过）。
- `007_owner_role_and_permissions.sql`：加 owner 角色，并建数据库端 helper 函数 `is_admin()`（admin 或 owner 视为管理级）、`is_owner()`、`has_permission(perm)`（owner 恒真，admin 看 jsonb 开关）。这套函数供 RLS 策略调用。
- `033_rls_policies.sql`：一大批表的读写策略，普遍模式是"按范围读、仅管理角色写/改/删"（脚本文档、AI 输入包、AI 洞察、团队、分组、豁免申请/授予、审计日志等）。
- `035_screenshot_slot_roles.sql`：截图槽位相关的角色策略。
- 后续 migration 还在陆续给新表加 RLS/策略，例如产量对账（`daily_quota_config`、`work_submissions`）、案例库重构、履约申诉等（文件名带日期戳的那批）。这类表改权限时，务必找到对应最新 migration。
- `20260723090000_video_review_thresholds.sql` 收紧 `system_settings`：所有 `authenticated` 用户可读；只有 `owner` 或 `role = admin` 且 `permissions.manage_members = true` 可插入/更新，服务端 API 的 PATCH 另做同等应用层校验。
- `20260727193000_allow_members_delete_own_video_tags.sql` 补齐 `video_tags` 删除策略：组员只能删除 `user_id = auth.uid()` 的自有视频标签，保证视频提交替换标签时不会因旧标签残留撞唯一约束；组长仍沿用原有全量管理策略。
- ~~**已知漏洞（2026-07-27）**：`video_metrics_snapshots` 无成员 DELETE 策略。~~ **已修复（2026-07-27）**：`20260727210000_allow_members_delete_own_video_snapshots.sql` 已在生产执行，补齐成员 DELETE 策略（通过 `videos.user_id = auth.uid()` 判断归属，非全表放开）；`/api/video-submit` 快照回滚路径已改走 `adminSupabase`（commit `ce1d1fbb`），双层防御均已到位。

规矩：RLS 策略变更只能新增 migration，禁止改旧 migration。数据库 helper（`is_admin`/`has_permission`）和应用层判定（`business-role.ts`）是两套实现，改权限规则时要留意两边是否需要同步，别只改一边导致数据库和应用层判定不一致。

**成员可见性/协作者范围判断的唯一入口**：任何"哪些成员可以被当前用户指派/看到"的逻辑，必须复用 `src/lib/data-access-scope.ts`（`visibleUserIds` / `activeVisibleUserIds`），禁止在各接口内联单独实现 team_id/data_scope 范围逻辑。现有例外：`/api/video-submit` 内的被指派者校验和 `/api/dashboard/operator-members` 各有一套独立实现，两者逻辑等价但不共用，属已知架构债务，下次动这两处时顺手收口。

**成员生命周期安全边界**：
- `archiveMember` 和 `restoreMember` 仅 owner 可操作；`removeFromTeam`（移出团队）仅 owner 或 `manage_members` 生效的组长可操作。
- 不能操作自己（禁止自归档/自移出），不能操作 owner。
- 组长只能移出本团队组员，不能归档账号。
- `activeVisibleUserIds`（`src/lib/data-access-scope.ts`）只含 `membership_status='active'` 成员，用于当前操作候选（指派、提醒、履约、协作、权限修改）；`visibleUserIds` 保留历史数据查询（含 archived），历史日报、视频、协作统计、审计不因归档消失。
- 当前操作必须使用 `activeVisibleUserIds`；历史数据读取继续使用 `visibleUserIds`。
- 管理首屏、队列统计、侧边栏徽标属于当前操作范围，必须传 `activeVisibleUserIds`；`admin_pending_submissions_today` 和首屏汇总 RPC 同步排除 archived 成员。
- 登录 action 在 Auth 登录成功后再次检查 `membership_status`，归档账号立即登出；Auth 返回 banned 时映射为归档提示；middleware 对已有认证 cookie 的受保护页面和所有 API 统一检查账号状态，明确归档清理会话并拒绝访问，暂时无法核验时返回 503 且不清会话；登录页消费 `archived=1` 展示归档提示。生产仍需用真实账号验证 Auth 封禁和旧会话失效。
- `20260805100000_member_lifecycle_write_protection.sql` 重申 `authenticated` 只能更新 `profiles.name`，并通过触发器只允许 `service_role` 修改生命周期字段；owner 页面动作走 service role，不依赖浏览器直写。
- `archiveMember` 清空团队、降为 `member`、封禁 Auth 并保存快照；`restoreMember` 回到 `active`、无团队、`member`、空权限并解封；`removeFromTeam` 只清空 `team_id`，账号仍可登录。
- 成员生命周期生产发布必须先在 Supabase SQL Editor 中按顺序逐条执行 `20260805113000_member_lifecycle_production_compat.sql` 和 `20260805100000_member_lifecycle_write_protection.sql`，再精确 repair 对应版本；随后刷新 schema cache、确认 OpenAPI 字段、做真实角色验收和历史数据对账。`scripts/member-lifecycle-release.sh` 默认只打印 dry-run 步骤，不替代这些人工卡点，也不得用 `supabase db push` 带上无关 pending migration。

## B.6 改权限先查哪几处（AI 用）

要改任何"谁能看/谁能改"的逻辑，先按这条链查全，别只改一处：

1. 权限开关本身：`src/types/index.ts`（`PERMISSION_KEYS` / 默认权限）。加/减开关从这里起。
2. 业务角色与默认值：`src/lib/business-role.ts`（`resolveBusinessRole` 判定、各角色默认开关表、`hasBusinessPermission`）。
3. 权限读取入口：`src/lib/permissions.ts`（`getUserPermissions`，请求内缓存）。
4. 数据范围：`src/lib/data-access-scope.ts`（`visibleUserIds` 怎么算）+ `current-permission-context.ts`。
5. 接口关卡：`src/app/api/admin/auth-helper.ts`（`requireAdminActor`）——顺带确认相关接口传了正确的 `requiredPermission`。
6. 数据库端：对应 RLS migration 和 helper 函数，判断是否要同步新增 migration。

## B.7 常见越权/权限问题排查顺序

- 该看的看不到 / 不该看的看到了：先看这个人算出来的业务角色对不对（`resolveBusinessRole`），再看 `visibleUserIds` 范围算得对不对（`data-access-scope.ts`），最后看具体接口有没有正确按范围过滤。
- 某后台接口谁都能进：查它有没有等价鉴权。常见合格链路包括 `requireAdminActor` 并传对 `requiredPermission`、`getUserPermissions` 自行判权限、`requireAuth` + 对象归属校验、cron 密钥、或按 `visibleUserIds` 做范围过滤。用了 service role 又完全没有这些校验，才是漏洞。
- 改了权限没生效：留意请求内 `cache()` 去重（同一请求不重查）和是否 profiles 里显式开关覆盖了角色默认值。
- 数据库直连（非后台接口）读不到数据：查对应表的 RLS 策略和 helper 函数。RLS 分散在多份 migration，不只 `033_rls_policies.sql`；先扫 `supabase/migrations/` 里所有涉及该表的 `CREATE POLICY` / `ENABLE ROW LEVEL SECURITY`。
- owner 相关异常：旧 `owner` 在应用层映射为 `company_owner`；公司所有者默认是本公司范围，只有集团模式才是集团范围。

## B.8 迁移前维护规则

- 新增/删除权限开关、改角色判定或默认值 → 当场更新第一、二节，并按第六节把链路各处同步改全。
- 新增用 service role 的后台接口 → 确认已有等价鉴权（`requireAdminActor` / `getUserPermissions` / `requireAuth` + 对象归属 / cron 密钥 / `visibleUserIds` 范围过滤），并在第四节安全含义里守住"先鉴权或限范围，后返回 service role 数据"的铁律。
- RLS 策略或数据库 helper 有变 → 更新第五节，且只能新增 migration。
- 与代码冲突一律以代码为准并立即修本文件。
- 本文件管"谁能看/谁能改/怎么鉴权"；模块归属在 `docs/全站模块地图.md`，出事急救在 `docs/运维排查手册.md`，配合使用。
- 顶部"最后核对代码日期"每次核对后更新。

## C. 常见问题排查

### Q1: 公司所有者打不开系统设置

**检查清单：**
1. 确认 `profiles.company_role = 'company_owner'`
2. 确认代码已部署（Vercel Ready）
3. 确认接口返回 200，不是 404 或 403
4. 查看 `src/lib/company-permissions.ts` 的 `DEFAULT_PERMISSIONS_BY_COMPANY_ROLE.company_owner` 是否包含 `manage_system`

**SQL 验证：**
```sql
SELECT id, email, company_role, role
FROM profiles
WHERE id = '<user_id>';
-- 预期：company_role = 'company_owner'
```

### Q2: 组长 · 管理能看到"修改角色"按钮

**检查清单：**
1. 确认 `profiles.company_role = 'admin'`（不是 `company_owner`）
2. 查看 `src/app/(app)/admin/modules/modules-content-v3.tsx` 中角色切换是否只对公司所有者或集团模式开放
3. 确认普通 admin 虽有固定 `manage_members`，但 `canChangeMemberRole` 不允许升降组长

**SQL 验证：**
```sql
SELECT id, email, company_role, role, permissions->>'manage_members' AS has_manage_members
FROM profiles
WHERE id = '<user_id>';
-- 预期：company_role = 'admin'；固定权限含 manage_members，但角色切换仍由公司所有者/集团模式控制
```

### Q3: 截图返回 403 或 401

**检查清单：**
1. 确认已登录（cookie 有效）
2. 确认截图路径格式：`/api/submission-screenshots/file?path=<user_id>/...`
3. 确认 `<user_id>` 在当前用户的 `visibleUserIds` 范围内
4. 查看 `src/app/api/submission-screenshots/file/route.ts` 的鉴权逻辑

**调试命令：**
```javascript
// 浏览器 Console
fetch('/api/submission-screenshots/file?path=xxxxx')
  .then(r => console.log(r.status))
```

### Q4: 集团模式返回 404 而不是 403

**原因：** 集团模式路由存在，但请求路径错了。

**正确路径：**
- 状态查询：`GET /api/group-mode/status`
- 进入：`POST /api/group-mode/enter`
- 退出：`POST /api/group-mode/exit`

**验证集团模式是否可用：**
```sql
SELECT COUNT(*) FROM group_permission_qualifications
WHERE user_id = '<user_id>' AND revoked_at IS NULL;
-- 该表只作历史兼容，不再决定 company_owner 是否有资格。
SELECT id, role, company_role, membership_status
FROM profiles
WHERE id = '<user_id>';
-- 预期：company_role = 'company_owner' 且 membership_status <> 'archived'
```

### Q5: 某个接口谁都能进（越权排查）

**检查清单：**
1. 查该接口有没有等价鉴权：`requireAdminActor`（传对 `requiredPermission`）、`getUserPermissions` 自判、`requireAuth` + 对象归属校验、cron 密钥、或按 `visibleUserIds` 做范围过滤
2. 用了 service role 又完全没有上述校验 → 确认越权漏洞
3. 有 `requireAdminActor` 但没传 `requiredPermission` → 退化为"有任意管理权限就放行"

### Q6: 改了权限没生效

**检查清单：**
1. 请求内 `cache()` 去重——同一请求不重查数据库，需等下次请求
2. `src/lib/company-permissions.ts` 的固定角色表是否已部署；不要用 `profiles.permissions` 里的 legacy JSON 判断当前权限
3. 前后端是否同步：前端 `current-permission-context.ts` 和后端 `permissions.ts` 可能缓存不同步
