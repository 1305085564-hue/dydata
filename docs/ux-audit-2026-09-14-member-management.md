**URL**：https://dydata.cc/admin/modules  
**浏览器**：当前已登录 Google Chrome（复用现有 DYData 标签页）  
**当前角色**：阿禅 / 公司所有者  
**范围**：只读审查；不保存、不删除、不上传、不提交、不修改成员、权限或数据，不跳转外部飞书  
**Persona**：公司负责人 / 公司所有者；需要快速核对成员、团队归属和权限，熟悉业务但不应被系统术语阻塞，时间紧，最在意“我看到的范围是否真实、动作会影响谁、刚才的操作是否生效”。

## Summary

结论：本轮浏览器审查为“不通过”，不是因为列表主流程不可用，而是成员/权限管理仍存在高风险信任缺口，且没有完成管理员、组员等真实角色的拒绝路径验收。当前公司所有者能看到成员、按姓名或邮箱搜索、打开权限抽屉、切换在职/归档视图；但自我管理入口、权限范围控件、归档恢复结果、键盘可达性都没有形成足够可靠的闭环。

已确认可用：目标页加载正确；44 名在职成员和 8 个归档账号可见；姓名搜索、邮箱搜索、空结果、团队架构只读打开/关闭、成员详情抽屉、角色权限明细、归档大盘筛选均能工作；全程没有写入成员、权限或数据。

主要阻塞：

- H-01：公司所有者查看自己的成员详情时，仍出现可操作外观的“所属团队”组合框和“移出团队 / 保留账号”，没有说明自我操作是否允许及后果。
- H-02：归档列表只给“恢复”，成员行不能打开历史详情；团队列显示“未分配”，没有在行内展示原团队、归档时间、原因或恢复后的角色/团队结果。
- H-03：组长详情中的“仅自己 / 同团队 / 全公司”权限范围按钮、角色固定说明与底部“已是最新”同时出现，但没有清晰的提交语义；只读约束下无法确认点击后是否立即写入。
- M-01：实际无障碍树中“管理”不是可聚焦控件，Tab 从首行复选框直接跳到下一行复选框；复选框也没有带成员姓名的可读标签。
- M-02：归档页保留搜索词会直接得到 `0 / 8` 空结果；浏览器返回会离开目标页，刷新后筛选最终回到默认状态，均缺少状态解释或恢复提示。

## Findings

（随审计推进追加；历史报告和代码结论不替代本轮浏览器证据。）

### H-01 自我成员详情仍暴露高风险团队操作

**影响**：负责人点开自己的成员行后，看到的不是明确的只读身份信息，而是可操作外观的团队组合框和“移出团队 / 保留账号”。用户无法从当前抽屉判断“我能否移除自己”“移除后权限/登录/数据会怎样”，容易误触或形成对权限边界的不信任。

**复现**：

1. 以当前 Chrome 的“阿禅 / 公司所有者”进入 `/admin/modules`。
2. 在职列表首行找到带“我”的公司所有者，点击该行右侧“管理”。
3. 抽屉显示“超管拥有全站最高权限，无需单独配置”，同时显示 `所属团队` 组合框和按钮 `移出团队`，右侧文案为 `保留账号`。

**浏览器证据**：`owner-detail` 截图；AX 状态将 `所属团队`识别为 `组合框 (settable)`，将 `移出团队 保留账号`识别为启用的按钮，未标记 disabled。未点击该动作，未验证后端结果。

**建议**：对当前登录者/公司所有者自身明确显示只读状态；若业务确实允许自我移除，必须在动作旁展示影响范围、登录状态和恢复路径，并用专门确认文案区分“移出团队”和“删除账号”。

### H-02 归档恢复缺少历史 provenance 和结果预览

**影响**：归档成员只能看到“未分配”和“恢复”，无法在执行前确认原团队、归档时间、归档原因、原角色以及恢复后的归属。恢复是生命周期动作，但当前界面不提供足够的复核信息；同时归档成员不能打开详情，历史核对被迫依赖猜测。

**复现**：

1. 点击 `归档 8`。
2. 若搜索框仍有 `张超`，页面显示 `0 / 8` 和“没有找到成员”；清空搜索后才显示 8 条归档记录。
3. 归档行统一显示团队 `未分配`、状态 `已归档`，操作区只有 `恢复`。
4. 点击团队选择器后可见 `归档大盘 (8)`；点击归档成员姓名本身没有打开详情的变化。

**浏览器证据**：`archive-list` 截图及归档状态 AX 树。未点击“恢复”，所以没有产生任何生命周期变更。

**源代码线索（不替代线上验收）**：当前工作区的 `modules-content-v3.tsx` 里恢复确认文案写明恢复后成为“未分配团队的在职组员”，归档动作文案写明会“封禁登录并移出团队”。这正说明恢复结果需要在浏览器确认框/归档行中提前可见，而不是只让用户点击“恢复”。

**建议**：归档行增加原团队、原角色、归档时间、归档人/原因；恢复前明确“恢复到原团队”还是“恢复为未分配”，并在确认态展示新旧值。归档页的顶部默认直接使用“归档大盘”，不要让团队名称和归档范围混在同一个选择器语义里。

### H-03 权限范围控件的提交语义不可信

**影响**：组长详情里同时出现数据范围按钮 `仅自己 / 同团队 / 全公司`、按角色固定权限说明，以及底部 disabled 的 `取消修改 / 已是最新`。用户无法判断这些按钮是当前值展示、待保存草稿还是点击即生效；权限管理页面在没有明确提交边界时不适合让管理员凭感觉操作。

**复现**：

1. 搜索 `张超`，打开其“管理”抽屉。
2. AX 树显示数据范围下的三个按钮，列表行当前范围为 `仅自己`；抽屉底部显示 `取消修改`（disabled）和 `已是最新`（disabled）。
3. 展开“查看此角色包含的具体功能明细”，可看到组长权限为按角色派生的分类计数和具体功能。

**浏览器证据**：`leader-detail` 与 `permission-details` 截图；全程没有点击范围、角色或保存相关动作。

**建议**：权限范围只保留一个明确的有效值展示，或明确设计“选择 → 影响预览 → 保存 → 成功回读”的闭环；若角色已固定派生范围，应移除看起来可切换的独立按钮，并将“公司 / 集团 / 团队”术语统一。

### M-01 行管理入口和复选框对键盘/辅助技术不友好

**影响**：鼠标用户可以点击整行进入详情，但键盘用户无法按 Tab 进入行的“管理”入口；无障碍树中的复选框只有 `复选框 0`，无法知道对应哪位成员，批量选择会变成逐个猜测。

**复现**：

1. 在页面内容上聚焦搜索框。
2. 依次 Tab：`团队架构设置` → `在职 44` → `归档 8` → `全选当前可见成员` → 首行 `复选框 0` → 第二行 `复选框 0`。
3. 首行的“管理”在 AX 树中是普通文本，Tab 不停留其上。

**浏览器证据**：当前 Chrome AX 状态；首行“管理”与连续的无描述复选框均在可访问性树中得到确认。视觉上管理文案还依赖桌面 hover 提亮，进一步增加发现成本。

**建议**：每一行提供真正的、带成员姓名的 `管理「成员名」` 按钮或让整行 role/button 被稳定暴露；每个复选框绑定 `选择「成员名」` 的 accessible name，并保持触控热区不小于项目约定。

### M-02 筛选、刷新和浏览器返回缺少状态恢复解释

**影响**：筛选词不会因为切换“在职/归档”自动清空；用户很容易把 `0 / 8` 误解为没有归档成员。浏览器返回会直接离开成员页，刷新后筛选最终回到默认状态，用户无法依靠 URL 恢复到刚才的核对上下文。

**复现**：

1. 搜索 `张超` 后点击 `归档 8`，得到 `0 / 8`。
2. 清空搜索才恢复 8 条归档列表。
3. 在目标页点击浏览器返回，实际离开到 `/dashboard` 的工作台/历史岗位管理链路；再用用户给定 URL 才能回到成员管理。
4. 重新加载目标页，页面最终回到空搜索、在职视图和默认团队选择。

**建议**：切换状态标签时提供“已保留搜索条件”的显式提示和一键清除；把团队、状态、搜索词至少编码进可恢复的 URL 或提供“恢复上次筛选”；返回/离开前不应让用户误以为抽屉状态会进入浏览器历史。

## Positive Evidence

- 页面用途和当前角色在首屏可见，成员行同时给出团队、系统角色、数据范围和上次登录，适合快速盘点。
- 搜索支持姓名和邮箱；`张超`得到 `1 / 44`，不存在的查询得到明确空状态，清空后能恢复完整列表。
- 团队架构入口能打开说明性弹层，`创建`在空输入时 disabled；未输入或提交任何新团队。
- 角色权限明细默认折叠，展开后按类别给出 `已启用 / 总数` 和具体功能，信息密度控制合理。

## Read-only Boundary and Uncovered Checks

- 未点击：数据范围按钮、角色切换、所属团队选择器、移出团队、归档账号、恢复、重置密码、AI 诊断、全选/成员复选框；未输入新团队名称，未确认任何弹窗。
- 未保存、删除、上传、提交、修改成员/权限/团队或跳转外部飞书；页面数据在审查前后未做写入验证，但本轮只执行筛选、打开/关闭、展开、滚动和导航。
- 未覆盖精确 1440×900/1280/1024/768/375、暗色模式、真实 Network/Console、500+ 数据量和第二角色。当前结论不把静态检查或本地源码当作这些门禁的替代证据。
