> 只管当前施工会引用的文档；`docs/archive/` 默认只作历史追溯，不自动搬迁、不自动改写。
> 最后核对：2026-09-27

## 二、文档放置规则

- `docs/plans/`：尚未完成的施工方案（在根目录）；完成后往本目录的 `历史-方案/`·`历史-报告/`·`历史-项目/` 归，不再移到 `docs/archive/`，规则见 [plans 文件夹约定](../plans/README.md)。
- `docs/reference/`：留档与局部契约——带日期的验收报告、线上核对记录，以及单个功能的接口契约（如协作管理、选题库）。**入口类文档不放在这里**，它们已收进 `docs/业务逻辑/`·`docs/系统架构与设计/`·`docs/通用管理/`。
- `docs/archive/`：历史材料；**只装非计划类历史**（审计快照、规范旧版、验收报告、批次归档），计划类的已办内容归 `docs/plans/历史-*`。
- `docs/reviews/`：审查记录；结论生效后必须回写到对应当前入口，审查报告本身不替代当前事实文档。
- 不自动依据日期或"已完成"字样搬迁文件；只列候选，由负责人确认。

## 三、最低维护信息

不要给所有文档增加重复标签。目录和文件职责已能表达的内容不再重复：`plans` 是待施工，`archive` 是历史，`reviews` 是审查证据。

只对"当前有效事实入口"维护已有的 `最后核对代码日期` 或 `最后核对日期`：

- 文档内容因代码、线上事实或业务决策被实际核验时，更新日期；纯文字润色不更新。
- 更新日期只代表当次核对的范围，不代表整份文档每一项都重新验过；有局部范围时在文档正文说明。
- 不以固定天数自动判过期。日期较旧只提示负责人按任务需要复核，不把旧日期当作错误或自动归档依据。
- 新建文档只在目录不能表达用途时补充状态；不强制加"负责人"等目前没有明确归属机制的字段。

暂不要求一次性补齐 300 份历史文档；只维护本页第一节中的当前入口和后续新建的长期事实文档。

## 四、维护动作

1. 改权限、路由、接口、数据库字段、部署方式或文件位置时，交付前按第一节逐项检查受影响入口；确实相关才更新，不相关则不改。
2. 施工完成后，更新对应入口的事实和核对日期；未做真实线上验证时，不把本地结果写成线上已生效。
3. 同一结论只保留一份当前原文，其他文档只链接它；历史文档保留追溯价值，但不作为施工依据。
4. 审查报告、施工方案中的结论只有在采纳并核实后，才回写当前入口；报告本身不自动成为规则。
5. 链接检查、路径对账和复核提醒只做报告；任何批量修复、归档或删除都必须单独确认。
6. 发现当前入口与代码或线上证据冲突时，记录冲突和证据；按项目验收规则确认哪个环境为准，再修正文档，不以脚本猜测代替判断。
7. 一个任务的文档闭环只需报告"更新了哪些入口 / 已核对无需更新哪些入口 / 未能核实哪些入口"，不要求每次扫描全库。

## 六、诊断查询

| 目标 | 查法 | 边界 |
| --- | --- | --- |
| 定位一次写请求 | 从响应头读取 x-dydata-request-id，在服务端日志按 requestId、route、stage、outcome 查同一条记录；detail.release 用于核对版本 | 不把请求体、SQL、员工信息或业务正文写入报告 |
| 判断写链路阶段 | 关注 auth、read、validate、scope、write-*、review-rpc、compensate、finalize 及 primaryStage | 日志或 Sentry 失败不能改变业务响应；补偿发生时同时保留主失败阶段 |
| 核对 Sentry 事件 | 按白名单标签 dydata.request_id、dydata.stage、dydata.outcome 筛选；事件收件需用真实项目查看权限确认 | 隐私过滤会丢弃请求参数、正文、用户信息和 breadcrumb；未收到事件不能写"线上可观测已完成" |
| 区分服务与数据库连通 | 访问 /api/health，再访问 /api/health?check=supabase | 健康接口只证明服务/数据库连通，不证明业务权限、数据口径或页面写入 |
| 核对版本与部署 | git rev-parse HEAD、git log -1 --format='%H %s'；有部署权限时再用 vercel inspect <deployment> | Ready、commit SHA、域名指向必须同时可见；缺任一项记为阻塞 |

## 七、发布与恢复

| 场景 | 步骤 |
| --- | --- |
| 形成候选 | 从已核对的 origin/main 建隔离分支，按维护专项第 1→4 批逐个保留领域提交；只暂存本页、工程事实、进度和日志等约定文件，不带入权限任务脏改动 |
| 发布前 | 运行最终候选的 npm run gate:static、npm run gate:browser、git diff --check，保存退出码、候选 SHA、环境和未覆盖项 |
| Vercel 核对 | 用 vercel ls 找到候选 deployment，用 vercel inspect <deployment> 核对 Ready、commit SHA 和正式域名；promote 只用于已验收的同一构建 |
| 触发恢复 | 核心页面不可用、权限边界回归或持续异常时先停止测试/写入，保留请求编号和版本证据，再确认旧版本与当前数据库/权限状态兼容 |
| 应用恢复 | 优先在 Vercel Promote/Instant Rollback 到已记录的上一个 Ready deployment；未实际回滚只能记录"未演练" |
| 源码恢复 | 部署回退不等于源码回退；需要源码恢复时在干净分支逆序撤销本专项提交并重新验证，禁止 reset 共享工作区，也不撤销权限 migration |
| 数据恢复 | 代码回退不会撤销已产生的业务数据；只处理已登记且有安全回收入口的测试对象，真实数据异常先冻结写入并报告 |
