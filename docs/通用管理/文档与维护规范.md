# DYData 文档与维护规范

> 本文件只管文档放置、事实回写和证据生命周期。Agent 的修改顺序、架构调查、影响分析与验收要求以 [`AGENTS.md`](../../AGENTS.md) 为准；任务入口以 [`DYData产品全书`](../DYData产品全书.md) 为唯一索引。
> 最后核对：2026-10-31

## 一、目录凭直觉划分

| 目录 | 只回答一个问题 |
| --- | --- |
| `docs/业务逻辑/` | 业务必须怎样运行：规则、口径、权限、流程和异常边界 |
| `docs/系统架构与设计/` | 系统由谁负责、从哪里进入：模块地图、调用边界、工程事实和实现规范 |
| `docs/系统架构与设计/架构决策/` | 哪些跨模块取舍已经拍板且长期有效 |
| `docs/通用管理/` | 文档、待办和交接怎样维护 |
| `docs/plans/` | 还没有完成的方案和执行规格 |
| `docs/reference/` | 已发生的验收、接口契约、审查和调查证据 |
| `docs/ux-audit/` | UX Skill 固定映射的审计产物，独立保留 |
| `docs/archive/` | 只供历史追溯，不作为施工依据 |

高频高风险模块的长期地图统一写入 [`全站模块与数据关系`](../系统架构与设计/全站模块与数据关系.md)，至少包含模块职责、真实入口和调用链、唯一规则来源、必须保持的不变量、主要数据/权限边界和定向验证命令。稳定的跨模块取舍才另写入架构决策目录；两处互相链接，不复制正文。

## 二、写入与归档

1. 新增文档前先查产品全书和现有入口；同一现行结论只保留一份原文，其他地方只链接。
2. 业务规则回写 `业务逻辑`，模块边界和工程事实回写 `系统架构与设计`，已拍板的跨模块取舍回写 `架构决策`；施工过程留在 `plans`。
3. `reference` 只保存证据，不自动变成规则。`reference/reviews` 保存审查，`reference/investigation` 保存调查、实验和根因分析；结论采纳并复核后，再回写当前事实入口。
4. 计划完成后按 [`plans 文件夹约定`](../plans/README.md) 归入 `历史-方案`、`历史-报告` 或 `历史-项目`；计划类材料不搬到 `archive`。
5. `archive` 只保留不再作为施工依据的历史材料；不按日期或“已完成”字样自动搬迁、改写或删除。

## 三、保持事实可追溯

- 只有代码、线上事实或业务决策实际核验过，才更新当前入口的核对日期；日期只代表本次核对范围。
- 发现文档与代码或线上证据冲突时，记录证据并标记待核；不能用猜测或脚本输出替代判断。
- 任务收尾只需说明：更新了哪些当前入口、核对后无需更新哪些入口、哪些内容仍未核实。
- 诊断、发布和恢复的运行事实看 [`工程运行事实`](../系统架构与设计/工程运行事实.md)；后端实现硬规则看 [`后端工程规范`](../系统架构与设计/后端工程规范.md)。

本文件不重复维护 Agent 行为规则、业务口径、模块事实、部署数字或测试命令。
