```typescript
// 文件路径：src/lib/loaders/dashboard-page.ts
export async function loadDashboardPageData({ supabase, userId }) {
  // 并行加载当前用户的账号和 profiles 豁免信息
  // accounts 只按 accounts.profile_id = userId 查询
  // 没有账号时尝试创建一个默认账号；创建失败时继续返回空态

  // 以 Asia/Shanghai 计算 today
  // 查询当前用户账号今日 daily_reports
  // 查询本月 daily_reports 完整日报并按 account_id + report_date 去重，同时生成已提交日期
  // 并行查询：active exemption_grant、待审批申请、最近审批结果
  // 根据今日豁免状态计算 summary，但当前 redesign 没有使用 summary

```

关键查询与转换：

- `accounts`：读取 `id, name, content_direction`，按 `profile_id = userId`、`created_at` 升序。
- `profiles`：读取 `name, role, status, exempt_type, exempt_start_date, exempt_end_date, exempt_reason, exemption_category`；缺少 `exemption_category` 列时降级为旧字段查询。
- 当前数据：读取当前账号的 `daily_reports`，`report_date = today`，按 `uploaded_at` 倒序。
- 本月数据：读取当前账号本月到今天的完整日报，按 `account_id + report_date` 去重后返回 `monthReports`，并生成 `monthSubmittedDates`。
- 豁免记录：优先读 `exemption_grant`；表不存在时回退到 `exemption_request(request_status = approved)`。
- 账号空态：调用 `ensureDefaultDashboardAccount` 尝试按用户名称创建默认账号；创建成功后本次请求会重新查询并返回新账号。
- 当前业务日期使用 `formatShanghaiDateOnly()`，日期展示和数据库 `report_date` 均为 `YYYY-MM-DD`。

### 2.4 仍保留的完整提交状态机

```typescript
// 文件路径：src/app/(app)/dashboard/video-submit-panel-state.ts
export function resolveSubmitPanelMode({ summary, requestedMode }) {
  if (requestedMode === "editToday") return "editToday";
  if (requestedMode === "backfill") return "backfill";
  if (summary) return "summary";
  return "create";
}

export function resolveSubmissionDayStatus({ date, today, report, exemption }) {
  if (report) return "submitted";
  if (exemption.isExempt && exemption.category === "leave") return "leave";
  if (exemption.isExempt) return "waive";
  if (date > today) return "future";
  if (date === today) return "unsubmitted";
  return "missing";
}
```

状态流转规则：

```text
今日有数据 -> summary（显示已提交摘要）
今日无数据 -> create（新建今日提交）
点击“修改今日数据” -> editToday
选择过去日期 -> backfill
报告存在 -> submitted（不能再次补交同一天，旧面板可进入编辑）
豁免命中且 category=waive -> waive（视作完成，隐藏填报表单）
豁免命中且 category=leave -> leave（不计为提交，隐藏填报表单）
过去日期无报告/豁免 -> missing（允许补交）
未来日期 -> future（禁止提交）
```

### 2.5 旧提交表单的关键规则

文件：`src/app/(app)/dashboard/video-submit-form.tsx`、`src/components/submission/提交状态机.ts`。

- 初始默认：状态为 `normal`，话题标签为“复盘”，视频形式为“出镜”，脚本作者/剪辑/运营默认当前用户。
- 正常提交必须有两张截图：`screenshot_1` 互动数据、`screenshot_2` 完播留存。
- 异常提交不强制截图，但异常提交时文案仍必填，标题可以为空。
- 正常提交时视频标题和文案必填；话题标签必填（“干货”或“复盘”）。
- `follower_convert > 0` 时，导粉话术必填，并写入 usage record。
- 数字字段由前端转为数字；API 对非数字归一为 `0`，文本字段空值归一为 `null`。
- 互动数据总和超过播放量时显示警告，但不是唯一的阻断条件。
- 截图识别失败时允许“手输”；已上传但 OCR 失败的截图可保留并重试。
- OCR 识别出的 `data` 自动填充播放/互动/涨粉字段；`retention` 自动填充均播、2 秒跳出、5 秒完播和整体完播。
- 截图识别出类型与当前槽位不一致时，会尝试在互动槽与完播槽之间自动归位；多图上传必须串行，避免两个槽位互相占用。

提交状态机：

```text
empty -> uploading -> recognizing -> confirmed -> 可提交
                              \-> pending_confirm -> 手动确认/重试
                              \-> failed -> 手输/重试
可提交 + 表单校验通过 -> POST /api/video-submit -> 已提交
可提交 + 校验失败 -> 定位到第一个问题区域 + 表单抖动
```

## 4. API 接口清单

### 4.1 当前 redesign 的页面业务接口

当前 redesign 没有调用任何页面级 HTTP API。初次加载由服务端 loader 直接通过 Supabase 查询：

| 资源 | 读写 | 查询条件/用途 |
|---|---|---|
| `accounts` | 读；空账号时尝试写入 | `profile_id = 当前用户`；账号 Tab、名称、话术方向 |
| `profiles` | 读 | 当前用户名称、旧角色、豁免资料 |
| `daily_reports` | 读 | 当前账号今天的指标；本月提交日期 |
| `exemption_grant` | 读 | 当前用户 active 豁免；缺表时回退申请记录 |
| `exemption_request` | 读 | 已批准、待审批、最近审批结果；兼容缺 `exemption_category` 列 |

因此当前页面没有“提交成功/失败”接口反馈。表单提交不会触发 `POST /api/video-submit`。

主要错误：

- `401`：未登录。
- `400`：请求体、账号 ID、UUID、截图地址、标题/文案等校验失败。
- `403`：账号不属于当前用户、截图不属于当前用户、责任人不是当前团队在职成员、账号已归档。
- `409`：稳定 ID 对应的视频被其他成员占用，或已永久删除。
- `500`：视频、快照、日报、标签或 usage record 写入失败；可能伴随回滚失败日志。

## 6. 用户交互流程

### 流程 1：当前 redesign 初次进入

1. 用户通过登录后进入 `/dashboard`。
2. 路由布局先显示全局导航、网络状态条和页面骨架。
3. 服务端根据当前用户加载账号、今日日报、本月提交日期和豁免兼容数据。
4. 页面默认选中第一个账号，业务日期为上海时区今天。
5. 用户看到标题、账号 Tab、本月提交天数、发布链接和四个简单指标输入框。

### 流程 2：切换账号

1. 用户点击账号 Tab。
2. 只更新 `selectedAccountId`。
3. `selectedAccount` 变化后，话术方向下拉框最多显示该账号自己的 `content_direction`。
4. 页面不会重新请求该账号数据，也不会把已有日报填回表单。

### 流程 3：切换日期

1. 用户点击“今日提交”标题。
2. Popover 打开；用户可切换月份并点选日期。
3. 选择后更新 `activeBizDate` 并关闭 Popover。
4. 标题变为“补交历史”；但当前 loader 只加载今天的报告，且提交按钮仍无真实补交逻辑。

### 流程 4：当前表单提交（实际结果）

1. 用户填写发布链接、播放量、点赞、评论、转发、话术方向和备注。
2. 用户点击“提交数据”。
3. 浏览器阻止原生提交并把本地状态打印到 Console。
4. 不调用 API、不写数据库、不显示 loading、不显示成功 Toast、不显示失败状态。

### 流程 5：旧完整提交链（重写必须保留的业务流程）

1. 用户选择账号和日期。
2. 页面根据当天是否已有报告/豁免决定 `summary/create/editToday/backfill` 模式。
3. 用户填写视频链接、标题、文案、发布时间、话题标签、视频形式、异常状态和责任人。
4. 用户上传一张或多张互动/完播截图；系统上传到私有 bucket，再调用 OCR。
5. OCR 自动填充指标；用户可以核对、手输、重试或删除截图。
6. 系统校验必传截图、标题、文案、话题标签和导粉话术。
7. 点击提交后调用 `/api/video-submit`，后端写入视频、快照、日报、标签和可能的 usage record。
8. 成功后前端更新本地报告 override，显示已提交摘要；首次新建今日数据时可预取 `/growth`。
9. 失败时显示错误 Toast，表单保持可编辑；后端失败会尝试逆序回滚。

### 流程 6：旧历史记录与编辑

1. 用户点击“历史记录”。
2. 首次打开时按需加载 `/api/dashboard/activity`。
3. 用户可按账号、月份筛选；默认最多显示 10 条，点击展开查看更多。
4. 点击某条日报打开编辑 Dialog。
5. 修改标题、文案、发布时间和指标，提交给 `submitReport` Server Action。
6. 成功后关闭 Dialog 并重新加载历史记录；该流程只改 `daily_reports`，不重跑 OCR 或视频素材写入。

### 流程 7：旧豁免/请假申请

1. 用户点击“申请豁免”。已有待审申请时入口禁用。
2. 弹窗打开时请求 `/api/remind/count?date=today`。
3. 用户在日历中离散选择日期，或一键选择近 7 天尚未提交且没有豁免/请假的日期。
4. 用户选择“请假（该交不交）”或“豁免（不该交不交）”，并填写最多 100 字原因。
5. 未选日期或原因为空时显示字段错误，不提交。
6. 调用 `submitExemptionRequest`，成功后关闭弹窗并将本地状态变为“申请审批中”。

## 7. 状态与权限规则

### 7.1 当前 redesign 的编辑/显示规则

- 账号 Tab：所有返回的账号都可切换；当前代码没有额外的角色按钮限制。
- 发布链接、指标、话术方向、备注：当前代码始终可编辑，没有按“已提交/历史日期/豁免”禁用。
- 提交按钮：始终可点击，没有 `isSubmitting`、请求中禁用或权限提示。
- 历史记录：按钮视觉存在，但没有交互处理器。
- 豁免：当前 redesign 没有按钮，loader 的豁免数据未传入客户端。
- `userDisplayName`、`userRole`、`userId`、`accountDisplayNameMap` 虽传入 Props，但当前组件没有使用。

### 7.2 旧链的业务权限事实

- 页面入口依赖已登录会话；`getCurrentUserContext` 只负责取得用户，受保护页面和 API 的登录/归档检查还由 middleware/API 负责。
- 账号查询和提交 API 都按 `accounts.profile_id = 当前用户` 校验，成员只能操作自己的账号。
- `/api/video-submit` 会再次校验账号归属、截图路径归属和归档状态，不能只依赖前端。
- 责任人默认是本人；手动选择时只允许当前团队的在职成员。后端再用 team_id 与 membership_status 校验。
- 当前代码旧表单使用 `UserRole = member | admin | owner`，但项目权限文档的新契约是 `member | admin | company_owner`；重写时不要把旧 `owner` 类型直接当作新集团权限。
- 当前 dashboard 本身没有按 admin/member/owner 展示不同提交表单；管理角色主要影响全站其他模块和团队数据范围。
- 历史数据查询使用 `visibleUserIds` 的项目约定；当前用户自己的 dashboard 账号和日报主要按自身 ID/账号归属查询。
- 归档账号不能登录、提交、上传、指派；当前 API 对归档成员返回 `403`。

### 7.3 豁免权限

- 成员可以提交自己的豁免/请假申请，不能审批。
- 管理员可处理当前公司在职成员的审批；公司所有者可管理本公司并按项目权限契约进入集团模式。
- 申请对象、团队归属和申请状态必须由服务端读取，不信任浏览器传来的用户/团队 ID。
- `leave` 表示该交但不交，`waive` 表示不该交不交；两者的考核口径不同，重写不可合并成一个“免交”状态。

## 8. 边界情况处理

### 8.1 当前 redesign

| 场景 | 当前行为 | 重写注意 |
|---|---|---|
| 没有账号 | loader 尝试创建默认账号；本次数据仍可能为空；客户端没有明确空态 | 创建后需刷新/重新加载，且应明确提示联系管理员或显示默认账号 |
| 没有今日数据 | 表单为空，可继续填写 | 应明确“未提交”而不是只显示空表单 |
| 已有今日数据 | `currentReport` 只用于展示区；表单不会回填 | 字段需和 `TodaySubmissionReportLike` 对齐，决定查看/编辑模式 |
| 选择历史日期 | 标题显示“补交历史”，但今日数据查询不会匹配历史日期 | 必须补历史日报加载或限制可选日期 |
| 选择未来日期 | 本地日历允许选择；没有未来日期校验 | 应禁用未来日期或后端拒绝 |
| 加载中 | `DashboardRedesignSkeleton`；脉冲动画 2.5 秒 | 骨架需对应实际内容高度，不能把加载完成误当成功 |
| loader 查询失败 | 进入 `dashboard/error.tsx`，显示“数据台加载失败”和重试 | 应保留错误原因边界，不用空数据伪装成功 |
| 网络错误/提交失败 | 当前 redesign 没有提交请求，因此没有处理 | 重写必须增加 loading、错误、重试和保留草稿 |
| 字段校验 | 当前 redesign 没有必填/格式校验 | URL、数字范围、标题/文案、截图和异常分支需接入旧契约 |
| 报告字段不匹配 | loader 返回 `play_count`，当前展示读 `views`；视频链接字段也不在日报返回中 | 统一 DTO，避免“有数据但显示空” |

### 8.2 旧完整链

- 截图为空、格式错误、超过 8MB、签名不匹配：上传接口返回 `400`，前端显示错误。
- OCR 超时、模型不可用、低置信度、解析失败：截图进入失败/待确认，可手输或重试；不应阻塞用户完成必要的手工填报。
- 截图属于其他用户：上传或提交返回 `403`。
- 必传截图缺失、识别失败、待确认：提交前定位到截图区并阻止提交。
- 正常状态下标题/文案缺失：阻止提交；异常状态下标题可空，但文案仍必填。
- `follower_convert > 0` 且话术为空：阻止提交并展开导粉话术错误提示。
- 空历史记录：显示 `EmptyState`“暂无历史记录”。
- 历史筛选无结果：显示“没有符合该账号/月份的日报记录”，可清空筛选。
- 归档账号、跨团队责任人或账号归属不匹配：服务端拒绝，不信任前端候选列表。
- 多表写入部分失败：服务端执行补偿回滚；回滚错误必须保留并记录。

## 重写时不可遗漏的业务断点

1. 当前页面的简单字段不是旧提交 API 的完整字段；至少要补回标题、文案、发布时间、异常状态、话题标签、责任人、11 项指标、截图资产和导粉话术。
2. 不能把 `views` 映射假设留在客户端；统一 `play_count`、日报、视频快照三套数据字段。
3. 日期切换必须决定是只看摘要、编辑今日，还是补交历史，并加载对应日期的报告。
4. 账号/截图/责任人校验必须在服务端重复执行；不能只依赖前端下拉选项。
5. `leave` 与 `waive` 需要保留不同状态和考核含义。
6. 先确认新权限 migration/线上状态，再把旧 `owner` 类型替换为 `company_owner`；不要在页面层自行扩大范围。
7. 提交成功必须有真实 API 响应、页面刷新或本地 DTO 更新、失败可重试，以及 usage/标签/快照写入结果的一致反馈。

## 编辑链路安全契约（2026-08-25 补充）

### POST /api/video-submit 编辑模式独立安全边界

- 编辑 POST 不信任 GET：在任何写入前重新核对——原 `video_id` 存在且归当前用户（他人记录统一 404，不泄露存在性）、原视频匹配请求业务日期（上海时区 published_at/uploaded_at）、该账号+日期恰好一条属于当前用户的日报、原视频恰好一条 24h 快照。绑定不一致 409，缺日报 404，缺快照 422，重复日报/快照 409。
- 编辑模式禁止创建新日报或新快照：绑定校验后若记录意外缺失，立即回滚并阻断，不走 insert 分支。
- 实现位于 `src/app/api/video-submit/edit-binding.ts`（`validateEditSubmissionBinding`），路由层通过注入适配器调用。

### 编辑时不可编辑指标由服务端保留

- 快照写入前用 `mergePreservedEditSnapshotFields` 以数据库原值覆盖：`follower_loss`、`homepage_visits`、`fan_play_ratio`、`cover_click_rate`、`avg_play_ratio`。数据库原值包括 `null`，前端固定发送的默认值（如 `follower_loss: 0`）不会覆盖历史数据。
- 新建模式继续使用原有默认口径。

### 旧截图复用严格校验

- `hasReusableConfirmedScreenshots` 要求：恰好两个截图角色、地址均为合法站内截图 URL、OCR asset 恰好各一条且无重复、全部 `confirmed === true`。缺失/损坏/重复/未确认一律返回 400 并提示重新上传；异常免截图逻辑不变。

### 草稿 key 隔离

- 新建 / 补交 / 编辑草稿 key 互不相同，统一由 `src/lib/video-submit-draft-key.ts` 的 `buildVideoSubmitDraftKey` 生成，至少包含 userId、mode、accountId、bizDate，编辑态再加原 videoId。
- 新建态通过 `resolveVideoSubmitCreateDraftStorageKey` 兼容读取旧共享 key `dydata.draft.videoSubmit.${userId}`（只在新建态读，不迁移不删除）；编辑保存只清当前编辑草稿。

### 历史责任人

- GET 编辑详情 DTO 返回 `assigneeProfiles`（仅按原记录精确的三个责任人 ID 查询；service role 读 profiles 前已完成用户/账号/视频归属校验；查询只使用真实存在的 `id/name/membership_status` 字段，展示名由 `name` 映射）。
- 前端显示规则见 `resolveAssigneeDisplay`：本人→“(我)”；在职候选→正常可选；不在候选但有档案→“旧姓名（历史成员 · 不可选）”；无档案→“历史责任人（不可选）”。
- 后端规则：编辑时未修改的旧责任人仅在同一岗位保留原值（即使已归档）；同一人员被新指派到其他岗位仍视为新指派，必须是在职同队成员，否则 403。岗位级校验由 `collectAssigneeIdsRequiringValidation` 统一生成待验证人员清单。
