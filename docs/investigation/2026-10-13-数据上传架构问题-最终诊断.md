## 修复方案

### 已执行的修复

创建了 migration 文件：[supabase/migrations/20261013100000_fix_fulfillment_rpc_content_items_typo.sql](../../supabase/migrations/20261013100000_fix_fulfillment_rpc_content_items_typo.sql)

**修复内容**：
1. 将发布履约 RPC 中的错误表名 `content_items` 改回 `daily_reports`
2. 增加 `is_void = false` 过滤，确保只统计有效记录
3. 保持与历史手稿页面的数据源一致

**修复前**（错误的代码）：
```sql
daily_publish_counts AS (
  SELECT
    ci.user_id AS pub_uid,
    ci.published_date AS pub_date,
    count(*)::int AS pub_count
  FROM public.content_items ci  -- ❌ 错误：表不存在
  WHERE ci.published_date BETWEEN p_start_date AND range_end
    AND (p_visible_user_ids IS NULL OR ci.user_id = ANY(p_visible_user_ids))
  GROUP BY ci.user_id, ci.published_date
)
```

**修复后**（正确的代码）：
```sql
daily_publish_counts AS (
  SELECT
    dr.user_id AS pub_uid,
    dr.report_date AS pub_date,
    count(*)::int AS pub_count
  FROM public.daily_reports dr  -- ✅ 正确：查询实际存在的表
  WHERE dr.report_date BETWEEN p_start_date AND range_end
    AND dr.is_void = false  -- ✅ 增加：过滤无效记录
    AND (p_visible_user_ids IS NULL OR dr.user_id = ANY(p_visible_user_ids))
  GROUP BY dr.user_id, dr.report_date
)
```

## 根本原因分析

### 为什么会出现这个问题？

1. **20260806 的修复引入了错误**
   - 原始目的：修复 `profiles.group_id` 删除后的引用问题
   - 意外副作用：将 `daily_reports` 改为了不存在的 `content_items`

2. **缺少数据库结构验证**
   - migration 没有检查 `content_items` 表是否存在
   - 没有单元测试覆盖发布履约 RPC

3. **新旧架构混用**
   - `content_item`（单数）表是新架构的一部分
   - 但新架构尚未完全启用
   - 导致混淆了表名

### 为什么没有早发现？

1. **RPC 没有立即报错**
   - PostgreSQL 对不存在的表查询的行为可能因权限设置而异
   - 可能返回空结果而不是报错

2. **发布履约页面仍然可用**
   - 因为其他数据源（`fulfillment_records` 表）仍然有效
   - 只是发布统计不准确

  IF NEW.published_at IS NOT NULL THEN

      user_id, account_id, report_date, video_id,
