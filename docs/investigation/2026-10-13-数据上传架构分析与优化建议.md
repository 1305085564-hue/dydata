# 数据上传架构分析与优化建议

> 分析日期：2026-10-13  
> 背景：修复 `report_date` 写错导致数据找不到的问题后，全面梳理数据上传架构的稳定性、可维护性、性能问题

---

## 一、当前架构现状

### 1.1 数据流概览

**用户上传一条视频数据 → 系统顺序写入3张表：**

```
videos (视频基础信息)
  ↓
video_metrics_snapshots (24h数据快照)
  ↓
daily_reports (日报记录)
```

**涉及的文件：**
- 28个 TypeScript 文件在 `src/app/api/video-submit/` 目录
- 核心文件：
  - `route-core.ts` — 主流程（800+ 行）
  - `persist.ts` — 数据写入逻辑
  - `edit-detail.ts` — 编辑逻辑
  - `validation.ts` — 数据校验
  - 另外24个辅助文件（标签、权限、截图、回滚等）

### 1.2 日期字段混乱

**4个日期字段，容易混淆：**

| 字段 | 含义 | 来源 | 用途 |
|------|------|------|------|
| `published_at` | 视频在抖音实际发布时间 | 用户选择 | **全站主日期**：展示、排序、统计 |
| `uploaded_at` | 数据提交到系统的时间 | 系统自动 | 审计、补交判定 |
| `report_date` | 日报归属日期 | **之前用 `biz_date`（错）** | 月度统计、履约判定 |
| `biz_date` | 前端表单的"业务日期"输入 | 用户填写 | **应该只用于回填 `report_date`** |

**问题：**
- `report_date` 之前直接用 `biz_date`（用户今天上传历史数据时默认填今天）
- 导致今天上传3月的数据，`report_date` 写成今天，数据哪边都找不到

---

## 二、主要问题（按严重程度排序）

### 🔴 P0 — 数据一致性风险

#### 问题1：三表顺序写入，缺乏事务保护
- **现状**：videos → snapshots → daily_reports 顺序写入
- **风险**：中途失败导致数据不一致
  - videos 写入成功，但 daily_reports 失败 → 视频存在但无日报
  - snapshots 写入失败 → 无法复盘分析
- **影响**：数据完整性问题，难以排查

#### 问题2：日期逻辑分散在多处
- **现状**：`persist.ts` 和 `edit-detail.ts` 都在构建 `report_date`
- **风险**：一处修了另一处忘了（这次就是这样）
- **影响**：维护成本高，容易遗漏

#### 问题3：缺乏数据库约束
- **现状**：`report_date` 和 `published_at` 的日期对齐只靠代码
- **风险**：任何绕过代码的写入（手动SQL、其他入口）都会错
- **影响**：数据质量无法保证

### 🟡 P1 — 可维护性问题

#### 问题4：28个文件，职责不清晰
- **现状**：主流程 `route-core.ts` 800+ 行，import 了24个辅助模块
- **风险**：改一个逻辑要翻很多文件，容易改错或遗漏
- **影响**：开发效率低，bug修复困难

#### 问题5：缺乏单一数据源
- **现状**：`buildDailyReportPayload` 和 `buildEditSubmissionContract` 各自构建数据
- **风险**：两处逻辑不一致（这次就是）
- **影响**：维护成本翻倍，容易遗漏

### 🟢 P2 — 性能问题

#### 问题6：三表串行写入
- **现状**：videos 写完 → snapshots 写完 → daily_reports 写完
- **风险**：总耗时 = 三次写入时间之和
- **影响**：用户等待时间长（目前尚可接受）

## 三、优化建议

### 短期修复（1-2周，快速见效）

#### ✅ 优化1：数据库约束保底（已完成部分）
**目标**：即使代码错了，数据库也能保证一致性

**方案**：
```sql
-- 添加检查约束：report_date 必须等于 published_at 的日期
ALTER TABLE daily_reports
ADD CONSTRAINT report_date_matches_published_at
CHECK (
  published_at IS NULL 
  OR report_date = (published_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Shanghai')::date
);
```

**收益**：
- ✅ 防止任何途径写入错误的 `report_date`
- ✅ 数据质量有底线保障

**成本**：低（一个 migration）

---

#### ✅ 优化2：统一日期计算函数
**目标**：所有地方都用同一个函数计算 `report_date`

**方案**：
```typescript
// src/lib/video-submit/report-date.ts
export function computeReportDate(publishedAt: string | null, fallbackBizDate: string): string {
  if (!publishedAt) return fallbackBizDate;
  return new Date(publishedAt).toISOString().split('T')[0];
}
```

然后 `persist.ts` 和 `edit-detail.ts` 都调用这个函数。

**收益**：
- ✅ 单一数据源，改一处生效
- ✅ 逻辑清晰，易于测试

**成本**：低（抽取函数 + 改两处调用）

---

#### 🔄 优化3：添加数据写入前置校验
**目标**：写入前校验数据一致性，提前发现问题

**方案**：
```typescript
function validateSubmissionData(payload) {
  // 校验 report_date 是否等于 published_at 日期
  if (payload.published_at) {
    const expectedReportDate = new Date(payload.published_at).toISOString().split('T')[0];
    if (payload.report_date !== expectedReportDate) {
      throw new Error(`report_date 不匹配：期望 ${expectedReportDate}，实际 ${payload.report_date}`);
    }
  }
  // 其他校验...
}
```

**收益**：
- ✅ 提前发现数据错误，不写入数据库
- ✅ 清晰的错误提示

**成本**：低（加一个校验函数）

---

### 中期改进（1-2个月，架构优化）

#### 🔄 优化4：引入数据库事务
**目标**：三表写入要么全成功，要么全失败

**方案**：
```typescript
await supabase.rpc('submit_video_transaction', {
  p_video: videoPayload,
  p_snapshot: snapshotPayload,
  p_report: reportPayload
});
```

在数据库端用存储过程包装三次写入，保证原子性。

**收益**：
- ✅ 数据一致性有保障
- ✅ 不需要复杂的回滚逻辑

**成本**：中（需要写存储过程 + 测试）

---

#### 🔄 优化5：重构为领域模型
**目标**：用面向对象的方式组织代码，职责更清晰

**方案**：
```typescript
class VideoSubmission {
  private video: VideoData;
  private snapshot: SnapshotData;
  private report: ReportData;

  constructor(userInput: SubmissionInput) {
    this.video = this.buildVideo(userInput);
    this.snapshot = this.buildSnapshot(userInput);
    this.report = this.buildReport(userInput); // 统一计算 report_date
  }

  async save() {
    // 事务写入三张表
  }

  validate() {
    // 统一校验
  }
}
```

**收益**：
- ✅ 代码组织清晰，易于理解和维护
- ✅ 数据构建逻辑集中，不会遗漏

**成本**：高（大重构，需要充分测试）

---

#### 🔄 优化6：文件合并与拆分
**目标**：28个文件 → 按领域重新组织

**建议结构**：
```
video-submit/
  domain/          # 领域模型
    submission.ts  # 提交模型
    validation.ts  # 校验规则
  
  infra/           # 基础设施
    persist.ts     # 数据持久化
    transaction.ts # 事务管理
  
  adapters/        # 适配器
    api-handler.ts # API 路由
    dto-mapper.ts  # DTO 转换
```

**收益**：
- ✅ 职责清晰，容易找到代码
- ✅ 降低耦合，易于测试和修改

**成本**：高（大重构）

---

### 长期优化（3个月+，可选）

#### 🔄 优化7：事件驱动架构
**目标**：解耦写入流程，提升扩展性

**方案**：
```
用户提交 → 发布 VideoSubmitted 事件
  ↓
监听器1：写入 videos
监听器2：写入 snapshots
监听器3：写入 daily_reports
监听器4：AI 标签生成（异步）
监听器5：触发飞书通知（异步）
```

**收益**：
- ✅ 核心流程和辅助功能解耦
- ✅ 易于扩展新功能
- ✅ 失败重试更灵活

**成本**：很高（引入消息队列、改造现有流程）

## 五、总结

### 核心问题
1. **日期逻辑分散**：多处构建 `report_date`，容易遗漏
2. **缺乏数据约束**：只靠代码保证一致性，容易出错
3. **三表顺序写入**：缺乏事务保护，有数据不一致风险

### 推荐优先级
1. **P0（本周）**：数据库约束 + 统一日期函数 + 前置校验
2. **P1（下月）**：数据库事务 + 领域模型重构
3. **P2（可选）**：事件驱动架构

### 投入产出比
- **短期修复**（3天）：立竿见影，防止同类问题
- **中期改进**（1个月）：架构优化，长期可维护
- **长期优化**（3个月+）：投入大，适合系统规模继续扩大时
