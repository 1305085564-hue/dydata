## 一、摘要

**结论：没有阻断性问题。一线填报人能走完"填数据 → 提交"全流程。** 卡点集中在三处，都是"用户会停下来想一下"的摩擦，不是走不通：

1. **底部提示写「⌘/Ctrl+Enter 提交」，但 macOS 上只有 ⌘+Enter 生效，Ctrl+Enter 完全无反应、无任何提示。**（实测 3 次 A/B）
2. **提交前看不到"还差什么"。** 缺项清单（缺少互动截图、缺少 6 项必填指标、缺少视频标题、缺少视频文案）只在**点过一次提交按钮之后**才出现；且 11 个指标里只有「导粉数」标了"可选"，用户看不出另外 10 个里哪 6 个是必填。
3. **打开「关联选题」会把整个表单横向推走 269px**，左侧两个截图上传区被挤出屏幕外，关闭弹层后不回位。

另有 6 项 Medium、6 项 Low。**权限与响应式两块表现明显好于预期**：0 控制台错误 / 0 失败请求，1440/1280/1024/768/375 五档均无横向溢出、无文本裁切，越权路由文案清晰。

| 严重度 | 条数 | 定义 |
|---|---|---|
| Critical | 0 | 用户无法完成任务 |
| High | 3 | 困惑、摩擦、信任受损 |
| Medium | 6 | 次优，能用 |
| Low | 6 | 打磨项 |

## 三、Findings（按严重度）

### High

#### H1 · 底部提示「⌘/Ctrl+Enter 提交」，但 Ctrl+Enter 完全无反应

- **证据**：同条件下 A/B 三次（光标都在 `#metric-play_count` 内，值 1234）：
  | 按键 | 提交缺项提示是否出现 |
  |---|---|
  | `Control+Enter` | ❌ 否 |
  | `Meta+Enter` | ✅ 是 |
  | `Control+Enter`（复测） | ❌ 否 |
- **截图**：`60-hotkey-ctrl.png`（与初始态逐字节相同）/ `60-hotkey-meta.png`（出现缺项条）
- **影响**：一线填报人按提示按 Ctrl+Enter，以为提交了，实际什么都没发生，也没有任何反馈。
- **口径**：本次只在 macOS 上验；Windows 上 Ctrl+Enter 是否生效**未验**。
- **位置**：`src/app/(app)/dashboard/video-submit-form-v2.tsx`（快捷键提示文案与 keydown 判定）

#### H2 · 提交前看不到"还差什么"；必填/选填标记与实际不符

- **现状**：`hasAttemptedSubmit` 为 false 时，底部只渲染一句很淡的「⌘/Ctrl+Enter 提交」，按钮呈灰态。缺项清单（`video-submit-form-v2.tsx:2689-2768`）只在提交尝试后才出现。
- **证据**：
  - 空表单按 Ctrl+Enter → **页面逐字节无变化**（`10-empty-submit-hint.png` 与 `03-dashboard-fold.png` md5 相同）
  - 点击提交按钮后 → 出现「待补全：缺少互动截图、完播截图 · 缺少 6 项必填指标 · 缺少视频标题 · 缺少视频文案」（`81-submit-missing.png`）
- **配套问题**：11 个指标里**只有「导粉数」标了"可选"**，其余 10 个没有任何必填/选填标记；实测必填 6 项、选填 5 项。视频标题/文案有红色 `*`，指标全都没有。
- **影响**：填报人填完 11 格才被拒，才知道还要传两张截图——这是本页最可能卡住的地方。
- **建议**：底部常驻一行状态（"还缺 4 项 · 点击查看"），或给 6 个必填指标加 `*`、5 个选填加"可选"。

#### H3 · 打开「关联选题」把表单横向推走 269px，关闭后不回位

- **证据**（1440×900）：
  | 指标 | 打开前 | 打开后 | 关闭弹层后 |
  |---|---|---|---|
  | 卡片 `scrollWidth` / `clientWidth` | 1024 / 1024 | **1306** / 1024 | **1306** / 1024（不回位） |
  | 卡片 `scrollLeft` | 0 | **269** | 269 |
  | 「正常发布/作品异常」x | 352 | 83 | 83 |
  | 互动数据截图槽位 x | 232 | **-37**（被挤出屏幕） | -37 |
- **截图**：`15-topic-link.png`、`53-topic-picker.png`、`70-topic-t200.png`（打开瞬间即位移，200ms/600ms/1200ms/2600ms/4200ms 五次采样位移量恒为 -269，**不是动画过程**）；`80-overflow.png`、`A1-1440x900-reset-scroll-clip.png`（把 `scrollLeft` 归零后的原始形态）、`B1-left-edge-clipped.png`（用户实际看到的左边缘）
- **机制**：卡片容器是 `overflow-hidden`，所以不出现滚动条，而是内容被直接裁掉、左侧控件被推出可视区。

**根因（2026-09-28 二次取证，已证实，非推断）**：

| 验证 | 结果 |
|---|---|
| 弹层锚点 | `TopicSelectDropdown.tsx:184` 面板为 `absolute left-0 top-full w-80 sm:w-96`，**内联渲染、无 portal**，落在卡片（`overflow-hidden`）内部 |
| 面板实际位置 | 锚点位于该行最右（1440 下 trigger x=1130），面板左对齐向右展开 384px → 右边缘 1514，**越出卡片右缘 282px** |
| 触发者 | `TopicSelectDropdown.tsx:110-117` 打开后 50ms 调 `searchInputRef.current?.focus()`；焦点处理会滚动最近的可滚动祖先（`overflow:hidden` 仍是滚动容器） |
| 因果对照 | 原生 `focus()` → `card.scrollLeft = 269`；改 `focus({ preventScroll: true })` → **`card.scrollLeft = 0`**（1920/1440/1280/1024 四档一致） |
| 常量性 | 282px 溢出量在四档视口下完全相同（`1306-1024`、`1258-976`），与位移 269 恒定吻合 |

- **附带缺陷（同一根因）**：位移发生后面板右边缘仍越出卡片 13px，被硬裁（圆角与阴影缺失）；若把 `scrollLeft` 归零，则面板被卡片右缘**拦腰切掉 282px**——搜索框文字、面板右边框都在切口处断掉（`A1-*.png`）。
- **纵向余量仅 2px**：搜索命中 5 条（列表 `max-h-64` 打满）时面板底边 856 vs 卡片底边 858；卡片 `overflow-y: hidden`、`maxScrollTop = 0`。按同口径外推，若再叠加选中态的底部操作条（实测 41px），面板底边约 894 → **被切掉约 36px 且无法滚动查看**（该组合未直接跑到，标为外推）。
- **实际影响**：一线填报人点「关联选题」想找选题，结果表单左半边（两张必传截图的上传区）跑出屏幕，容易误判"控件没了"；即使看懂了，面板右侧/底部仍被切。
- **最小修法（两处，均低风险）**：① `focus({ preventScroll: true })` —— 单独即可消除 269px 位移（已实测归零）；② 面板锚点 `left-0` → `right-0`（触发点在行尾，向左展开），消除 282px 越界与 13px 裁切。彻底的修法是换成 portal + 碰撞检测（仓库有 `ui/dropdown-menu.tsx` 可参考），但会牵动现有的 `containerRef` 点击外部关闭逻辑，非最小改动。

### Medium

#### M1 · 两个截图上传区看起来像禁用态，但它们是必填项

- **实测属性完全正常**：`cursor: pointer`、`opacity: 1`、`pointer-events: auto`、`aria-disabled` 为 null，点击能唤起系统文件选择器（`fileChooserFired = true`）。
- **但视觉上**：底色 `#F1F1F0` 与"禁用态按钮"同色（`确认提交立卷` 禁用态也是 `#F1F1F0`），图标近乎不可见，无虚线边框，默认没有任何"点击上传"文案。悬停后才出现「也可直接 ⌘V / Ctrl+V」（`12-hover-slot.png`）。
- **影响**：截图是必填项（缺项清单第一条），而它长得最不像能点。填报人很可能在"缺互动截图"那里反复找入口。
- **建议**：改成虚线边框 + 常驻「点击或拖拽上传」，与禁用态做出明确区分。

#### M2 · 数值字段零校验，任何输入照单全收

7 组边界输入全部无字段级错误提示：

| 输入 | 落到输入框的值 | 错误提示 |
|---|---|---|
| `abc`（播放量） | `abc` 原样保留 | 无 |
| `-5` | `5`（吞掉负号） | 无 |
| `1.23456789` | `1.23456789`（8 位小数） | 无 |
| `999999999999999` | 原样 | 无 |
| `150`（5s完播率 %) | `150` | 无 |
| `-3`（2s跳出率 %） | `3` | 无 |
| `0`（点赞数） | `0` | 无 |

- **口径提醒**：比率越界按本项目既有口径属"真实脏数据"，由显示层 `metric-bounds.ts` 原值+标记兜底，所以 150% 不拦**可能是有意的**。但"非数字能填进去"、"8 位小数"、"15 位数字"未见任何拦截。
- **无长度上限**：视频标题实测收下 **1350 字**（无 `maxlength`），文案收下 **4000 字**。
- **截图**：`63-validation.png`、`64-longtext.png`

#### M3 · 提交立卷没有二次确认

全页唯一的确认弹窗是"互动数之和 > 播放量"这一条例外（`video-submit-form-v2.tsx:2822`）。正常提交直接落库，无"你确认提交吗/提交后将计入履约"这一步。
- **缓解**：数据可在「历史记录」再编辑（编辑链路本次**未实测**）。
- **参考**：本页密集度与后果（影响履约与实发）不低，建议至少在首次提交/跨日补录时给一次确认。

#### M4 · 组员也能打开「审批工作台」，里面全是他无权处理的事

- 组员（member）点击右上角铃铛 → 弹出「**审批工作台**」，分区标题「团队待办事项（自动同步系统风险与权限申请）」，空态"待办已全部完成"，底部快捷键提示「J/K 选卡 · A 同意 · R 拒绝 · Z 撤回 · 1-3 视图 · Esc 关闭」。
- 同一账号访问 `/admin/content`、`/admin/modules` 等均为"需访问权限"。所以这个入口对组员**没有可执行动作**，而界面暗示他能审批。
- 三档对比：组员无角标 / 组长角标 1 / 负责人角标 7。
- **截图**：`54-command-hub.png`

## 四、逐条任务线结果

### T1 · 首次进入 → 填报一条作品数据（主线）

点击成本（从 `/login` 登录成功算起）：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 登录 | 落 `/dashboard` |
| 2 | 传两张截图 | 可点，唤起文件选择器；**但看起来像禁用按钮**（M1） |
| 3 | 填 11 个指标 | 无提示哪些必填（H2） |
| 4 | 填标题 + 文案 | 有 `*`，清楚 |
| 5 | 挂选题（可选） | 「关联选题」一开，左半边跑出屏幕（H3） |
| 6 | 点提交 | 按钮灰态，点了才告诉你缺什么（H2） |

**三个自问**：
- **结束得清楚吗？** 不清楚。提交前没有任何"你要提交的是这些"的汇总确认（M3）。
- **我会再来吗？** 会。草稿自动保存 + 恢复可用，是本页最让人安心的设计。
- **一件让难度减半的事？** 底部常驻"还缺 N 项"，并把 6 个必填指标标出来。（即 H2）

### T2 · 查看历史 / 补交

「历史记录」→ 弹层标题「历史手稿纪事」，2.5s 内停在"加载历史记录..."，**30s 内加载完成**并给出空态「历史手稿静待立卷 · 完成创作立卷或补交后，这里将收录最近 30 份纪事手稿。」
- 网络：`GET /api/dashboard/activity → 200`。属正常加载延迟，**不是卡死**（我一开始怀疑是挂起，复验后否掉了）。

### T3 · 请假 / 报备

本次做得最扎实的弹层：日历禁用未来日期、区分「已交/特殊豁免/请假/未交」图例、明确劝阻"今天已发但被限流请走「作品异常」"、理由框带 `0/100` 计数、「提交申请」在未选日期+未填原因前保持禁用。
- `role=dialog` + `aria-labelledby` 可解析出标题「停笔调养 · 申请请假或特殊豁免」。

### T4 · 团队进度 / 待办

见 M4：组员进「审批工作台」是死路。

## 七、做得好 / 明确否掉的假警报

### 做得好

- **草稿自动保存 + 恢复**：分键到 `用户+账号+日期`，跨刷新可用。本页最实用的设计。
- **权限门禁文案**：不是干巴巴的 403，而是"还没有「视频复盘」权限 · 该功能属于系统受控模块，当前仅对组长 · 管理开放"。
- **请假/报备弹层**：日历状态图例 + 未来日期禁用 + 明确劝阻走错入口 + 字数计数，完整度很高。
- **焦点可见性**：键盘聚焦时指标框、标题框、文案框边框变深，清楚可辨；其余控件保留浏览器默认 outline。**没有"焦点看不见"的问题。**
- **表单无障碍基础**：11 个指标输入 + 标题 + 文案都有 `<label for>` 与 `id` 正确配对（不是只有视觉标签）。
- **弹层结构**：`role=dialog` + `aria-labelledby` 均可解析出标题，`Esc` 能关。

### 明确否掉的假警报（查过、不是缺陷，别再当 bug 修）

| 候选 | 复核结论 |
|---|---|
| 11 个指标输入"没有无障碍名" | ❌ 假的。我第一版探针只认 `aria-label`，漏了 `<label for>`。实际全部配对正确 |
| 「历史记录」一直卡在"加载历史记录..." | ❌ 假的。30s 内加载完并给出空态（该账号 0 条日报），是正常延迟 |
| 文案输入框"聚焦没有可见焦点环" | ❌ 假的。它用的是 `focus:border-[#78716C]`，边框会变深，截图可辨 |
| 提交按钮"点了没反应" | ⚠️ 一半是真的：Playwright 把 `aria-disabled=true` 当禁用元素，常规点击必然超时——这是**测试工具行为**；真实点击会触发缺项提示。但由此暴露 L6（语义与行为不一致） |
| 多个控件"点不动 / 被挡住" | ❌ 假的。加了 `animation:none` 后全部可点；`elementsFromPoint` 命中栈也证明无遮挡。是 Playwright 稳定性检查的 harness 现象 |
| 缺项 chip 点击"无跳转/无高亮" | ⚠️ 未能证实。当前视口下页面总高 1008/900，本就不需要滚动，`scrollY` 0→0 不能作为"没跳转"的证据。**建议在有滚动的数据量下复测** |
