# 视频复盘 × 素材库：技术依赖与合并可行性报告

- 日期：2026-09-20
- 方法：静态分析（前端调用点 + 后端路由 + loader + RPC/迁移），未运行代码
- 范围：`/admin/content`（视频复盘）、`/admin/videos`（素材库）
- 结论口径：只描述现状与合并代价，不含实施改动

---

## 一、结论摘要

| 判断 | 结论 |
|------|------|
| 底层数据模型 | **同一个 `videos` 主表，写入列完全不重叠**，天然适合合并 |
| 表级耦合 | 交集 5 张（videos / video_metrics_snapshots / video_content_segments / accounts / profiles），各自独占表极少 |
| API 层 | 两套 list 接口形态几乎对称，且有 1 个接口**已经被双方共用**（lifecycle） |
| 权限层 | `review_content` 与 `manage_videos` 由公司角色固定捆绑，**不存在只能进其中一个的角色** |
| 组件层 | 页面外壳同源，业务组件零复用；列表内 4 个工具函数 + 状态色板**各自复制了一份**（已出现取色值不一致） |
| 合并结论 | **可行，且是净收益**。主要成本在「两套 payload 契约 + 一套内存缓存 + 一处浏览器直连 Supabase」三件事，不在表结构 |
| 不建议做 | 直接删掉其中一个路由或直接改 RPC 签名；两者的首屏 RPC 目前不带 active 之外的过滤语义差异，但入参语义已被线上加载器依赖 |

### 2.3 `videos` 表列级分工（关键证据）

| 列组 | 复盘 | 素材库 |
|------|:----:|:----:|
| `id, account_id, user_id, video_url, video_title, content, published_at, uploaded_at, anomaly_status, created_at` | ✅ | ✅ |
| `review_status, reviewed_at, reviewed_by` | ✅ 读写 | ❌ **全目录 grep 零命中** |
| `asset_level, asset_note, asset_reviewed_by, asset_reviewed_at` | ❌ **全目录 grep 零命中** | ✅ 读写 |
| `lifecycle_state, trashed_at, trashed_by, purged_at, purged_by` | ⚠️ 仅 `lifecycle_state='active'` 过滤 + 调 lifecycle 接口 | ✅ 读写 + 回收站视角 |

即：**两个模块在 `videos` 上各占一半列，互不读写对方的列。**

### 2.4 已知不一致（顺手记录）

- `src/app/api/admin/settings/thresholds/route.ts:17` 描述为「视频复盘与素材库异常警戒阈值」，但 grep 确认 `video_review_thresholds` 的消费方只有 `content-list.tsx:135` 与 `content-diagnosis-workbench.tsx:226`（经 `lib/review-queue.ts`）。**素材库代码里没有任何 threshold 引用**。命名与实现不符，配置面板承诺的"素材库警戒"目前不存在。
- 异常状态标签色板两处不一致：复盘 `content-list.tsx:85,91,101,107` 用 `#C9604D / #B98A54 / #6FAA7D / #A8A29E`；素材库 `video-list.tsx:155-215` 用 `#C0685C / #8A6A2F / #6FAA7D / #78716C / #E2E2DF`。同一状态在两端显示不同颜色。

## 五、权限与角色

| 维度 | 视频复盘 | 素材库 |
|------|----------|--------|
| 路由权限键 | `review_content`（`route-permissions.ts:18`） | `manage_videos`（`route-permissions.ts:19`） |
| 导航显示条件 | `hasNavPermission("review_content")` | `hasNavPermission("manage_videos")` |
| 页面守卫 | `canAccessAdminPath("/admin/content", …)` | `canAccessAdminPath("/admin/videos", …)` |
| 额外闸门 | 无 | `view=trash` 需 `manage_videos === true` |
| 数据范围 | 同一套 `buildDataAccessScope`（company / team 视角） | 同 |

**是否存在只能进其中一个的角色：不存在。**

`docs/权限与安全说明.md` 与 `lib/company-permissions.ts::DEFAULT_PERMISSIONS_BY_COMPANY_ROLE` 表明权限按公司角色**固定生成**，legacy `profiles.permissions` JSON 不覆盖固定表：

- `company_owner`：11 项全开（两个都开）
- `admin`：固定开 9 项，含 `review_content` + `manage_videos`（两个都开）
- `member`：固定开 2 项，**两个都没有**

所以现状是 `review_content` 与 `manage_videos` 恒等捆绑，无法拆出"只看复盘"或"只进素材库"的角色。

> ⚠️ 注意一个隐藏耦合：`/api/admin/videos/{videoId}/lifecycle` 的鉴权**不看权限键**，走 `canOperateVideoLifecycle()` 的公司角色/集团模式判定（`lib/video-lifecycle.ts:31`）。复盘页能调这个接口，靠的是角色而不是 `manage_videos`。合并权限键时不能顺手把它改成 `manage_videos` 校验，否则会改变 owner/admin 的现有能力语义。

## 七、合并后的数据流设计建议

核心原则：**一个入口页面 + 一个视频主表 + 一个视图枚举**，把"复盘待办"降级为素材库页面的一个视图切片，而不是独立模块。

```
/admin/videos?view=pending | all | trash
        │
        ├─ 首屏（服务端 RSC）
        │   └─ loadAdminVideosInitialData → RPC admin_videos_first_screen
        │        返回超集：videos(+review_status,asset_*) / snapshots /
        │                 profiles / accounts / videoTags / assetLibrary /
        │                 reviewReadiness / summary / assetSummary
        │
        ├─ 全量（客户端按需）
        │   └─ GET /api/admin/videos/list?view=…&mode=full
        │        （沿用 content/list 的 60s 内存缓存策略，key 增加 view 维度）
        │
        ├─ 单视频抽屉（合并 content-diagnosis-workbench + video-detail-dialog）
        │   ├─ PATCH /api/admin/videos/{id}            ← review_status / asset_*
        │   ├─ PATCH /api/admin/videos/{id}/lifecycle  ← 不变
        │   ├─ POST  /api/admin/videos/{id}/snapshot-24h ← 从浏览器直连收口
        │   ├─ POST  /api/admin/videos/{id}/topic-library
        │   ├─ POST  /api/admin/content-analysis       ← 保留（AI）
        │   └─ GET   /api/admin/content-attribution/{id} ← 保留（归因）
        │
        └─ 共享：/api/admin/settings/thresholds
```

**视图语义映射（迁移期双轨，旧路由 301/redirect 到新参数）**

| 旧入口 | 新入口 | 视图内容 |
|--------|--------|----------|
| `/admin/content?view=pending` | `/admin/videos?view=pending` | 待盘队列（未分析 + 异常） |
| `/admin/content?view=all` | `/admin/videos?view=all` | 全量作品账本 |
| `/admin/videos?view=pending` | 并入 `/admin/videos?view=pending` 的一个筛选分组 | 待整理（缺标签/快照/拆段/评级） |
| `/admin/videos?view=trash` | 不变 | 回收站 |

**落地顺序建议（每步可独立验收）**

1. 抽公共件：把 §4.2 的 4 处重复函数与状态色板抽成 `lib/video-status-display.ts` + `lib/format-video-metrics.ts`，先修掉颜色不一致（纯前端，零数据风险）。
2. 出参超集：给 `GET /api/admin/videos/list` 补 `reviewReadiness`，给 `admin_videos_first_screen` 补 `review_status / reviewed_at` 字段，双写不删旧。
3. 合并单行写接口，保留旧路由做转发。
4. 素材库页面接入"复盘视图"，复盘路由改为重定向；观察一轮（≥1 周）确认无深链断裂。
5. 最后才清理旧 loader（`admin-content-page.ts`）与旧 RPC。

## 八、技术风险评估（合并会破坏什么）

| # | 风险 | 影响面 | 触发条件 | 等级 | 缓解 |
|:--:|------|--------|----------|:---:|------|
| 1 | **缓存语义不一致** | 数据新鲜度 | `content/list` 有 60s 内存缓存 + `Cache-Control: private, max-age=60`；`videos/list` **完全无缓存**。合并成单一接口后必须选一个策略 | 高 | 按 `view` 分策略；或统一保留 60s 并在**所有**写路径（asset / lifecycle / patch-24h / review-status）挂 `clearAdminContentListCache()`——现状只有 review-status 挂了 |
