# DYData 项目规则

> 本文件供多 Agent 共用。

## 一、行为准则

一、摸索与思路对齐，收到需求先判断是否意图清晰，目标明确。如果需求模糊禁止直接执行，主动补全完善真实目标，并复述目标跟用户确认。如果信息不足，最多提三个关键问题后立即施工。

二、阿禅不懂技术，需要选择时必须给出推荐和理由，最终由阿禅决定。主动提示高成本或偏离真实业务目标的需求风险。

## 四、开发规范

### 业务闭环与防伪规则

- 前后端必须对账：前端新增/修改字段、参数、按钮行为时，必须检查后端是否接收、存储、返回；后端不接就补后端或删前端。
- 禁止伪接和伪造：没有真实接口就提示未接入，数据加载失败就明确失败或降级为空，禁止接到不相干接口或用假数据假装成功。
- 用户动作必须闭环：提交/审批/导出后，后续处理入口必须真实存在且可用，不能只靠提示信息就认为完成。
- 高风险链路（权限、登录、RLS、Auth 封禁）首次改动前，先 grep 调用点列出受影响文件清单，清单列完即动手。
- 交付报告必须分层：最终报告必须分清"完整修复""止血未完整""预存问题""新增问题"，禁止把临时方案说成完整完成。

### 数据与发布硬规矩

- `select` 只能写线上真实存在的字段；不确定先查真实表结构和已执行 migration。
- 数据库结构变更只能新增 migration，禁止修改旧 migration。
- 前端传给后端但后端没有接收逻辑的字段，必须补后端或删除，不能留下幽灵字段。
- 含新字段的接口必须完成“生产 migration → 刷新 PostgREST schema cache → 真实角色请求验收”三步；详细卡点见 `docs/代码治理手册.md`。

### 架构与性能

- 代码改动涉及页面增删、接口增删或加载器变更时，同步更新模块地图、对应模块接口文档或数据口径文档。其他过时内容记入待办，不当场修。
- 文档与代码冲突时以代码为准，并立即修正对应的权威文档。
- 声称「已实测某步骤耗时」前，该页面加载器必须已有对应 `[perf]` 埋点；无埋点先补埋点，否则只能记「未实测」。
- 体检 Skill 不可用时，按 `docs/全站模块地图.md` 的性能红线和排查流程手动排查，并回填 `docs/plans/_跨模块/性能优化台账.md`。

### 文档写入规则

写文档前先判断类型，路径不匹配时必须指出：

- `plans/` — 还没做的事
- `reference/` — 已完成，未来遇到相关问题会翻出来看
- `archive/` — 已确认不再需要，仅保留历史
- 不提交 — .sql/.json 等一次性施工产物

### 编码与工具链

- `docs/plans`、`docs/reference`、`docs/archive` 是本项目固定英文目录名；其他文件和目录仍优先中文。
- `docs/plans` 文件命名：`M.DD-主题.md`，多文件加后缀（`-规格书`/`-Codex后端规格`/`-Antigravity前端规格`/`-提示词`）。
- 中文组件名内部用英文 PascalCase，导出时再用中文别名。
- 执行 SQL：`psql "$SQL_DSN" -c "..."`
- 执行 migration 文件：`psql "$SQL_DSN" -f supabase/migrations/xxx.sql`
- 查 migration 状态：`supabase --workdir ~/Projects/dydata migration list --linked`

### 排查顺序

- 线上问题先看 Vercel 最近部署，再区分代码、数据库、权限、缓存。
- 数据库问题先查真实字段和已执行 migration；`select` 只写线上已存在字段。
- RLS/权限问题先查 helper、policy、service role 调用链路。
- 前端传给后端的字段，如果后端没有接收逻辑，直接删或补后端，不能留幽灵字段。
- 使用项目封装 UI 组件前，先看 `components/ui/*` 的真实 Props，不能套原版 shadcn/Radix 写法。
- 涉及「组员提交/替换/重试」类接口报错 → 整读 `docs/reference/纠错索引.md`

### 部署禁令

- 代码改完默认 commit + push main（自动合并）
- Antigravity改动必须确认后才能 push

## 五、协作分工

### 三方代理

- [CC] Claude Code：总览与统筹，负责架构设计与 0→1 需求探索；与用户交互最多，负责阶段总结与对齐。
- [An] Antigravity：仅负责前端的「怎么看起来」——视觉风格、动效节奏、布局适配、交互手感；遇代码逻辑问题交 Codex。
- [CX] Codex：负责所有代码的「怎么跑起来」——逻辑、数据、接口、功能 bug（含前端组件逻辑）；遇审美需求交 Antigravity。
- 跨领域任务通过提示词交用户转派，简单改动可以直接说明。
- 委托弱模型时，提示词必须包含：目标、验收命令、禁区。涉及前后端联动时加同步要求。

### 日志规则

- 本项目所有日志统一写入 `日志/YYYY-MM-DD.md`，所有 agent 共用，按时间线记录关键结论，任务完成必写。
- 主日志：每次任务完成后追加，记结论/事件，一行一条，带时间（要能扫一眼知道：背景 / 已完成 / 当前状态 / 未完成线索）
- 补充日志：同目录 YYYY-MM-DD-补充.md，记关键细节/过程/上下文
- 日志前缀与上方代理简称一致（[CC] / [CX] / [An]）

### 任务难度标注

写任务提示词时名称后备注复杂度：

| 标签 | 标准 |
|------|------|
| 极难 | 新架构/新范式/新约束，没见过，需要探索和大量校验 |
| 较难 | 知道大致怎么做，但链条长/分支多，需要持续跟踪 |
| 简单 | 改几个文件就能完事，路径清晰 |
| 零错 | 零推理，纯搬运/机械执行/格式转换 |

### 子代理分工

- 简单搜索、批量读写、机械改动 → 子代理用 haiku
- 中等复杂度执行（需要一点推理） → 子代理用 sonnet
- 交叉验证、复杂判断 → 主代理自己做，不另派
