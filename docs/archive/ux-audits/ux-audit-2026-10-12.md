# UX Audit: 豁免审批台（行动中枢）

**Date**: 2026-10-12
**URL**: https://dydata.cc/dashboard（导航栏“行动中枢”抽屉）
**Persona**: “需要在碎片时间快速处理团队待办的公司所有者/管理员；对日期、审批范围和后置结果敏感，技术熟练度中等，工作压力高，使用桌面 Chrome。”
**Browser**: Chrome MCP（生产已登录会话，公司所有者）
**Viewport**: 生产 Chrome 当前桌面视口（截图约 1440×900）；响应式/深色模式受当前 Chrome MCP 封装限制，见覆盖说明
**Reference extract used**: none

## Summary

豁免审批台能把请假、特殊豁免、补交申诉、团队待办和历史记录集中到一个入口，日期级批注和按天处理路径清楚。当前最影响信任的是数量口径：切换分类后顶部分类数会变化，但内容区仍显示“共 6 份明细”；标记待办完成后，待办总数减少但关联的补交审批卡仍留在可处理列表里。键盘路径也没有真正形成模态焦点闭环，页脚写着 Esc 关闭，但焦点逃到背景后 Esc 不再关闭工作台。

| Dimension | Tested | Total | % |
|-----------|--------|-------|---|

**Elements not tested**（避免生产审批副作用或工具能力缺口）：

- “同意全部 / 拒绝全部 / 仅准许 / 仅驳回 / 驳回 / 同意补交”：会写入生产审批结果，未点击。
- “确认同意并附批注”、历史记录“打回待处理”：会改变审批状态，未点击。
- 500/1000 条重数据：当前账号现场仅返回 50 条历史记录，未造数。
- 1280/1024/768/375 与深色模式：当前 Chrome MCP 封装没有可用的 viewport override；未用未登录 Playwright 替代。
- 第二用户：当前只有一个已登录生产 Chrome 会话，未登出公司所有者或另开隔离登录。
- 网络请求与控制台：当前浏览器封装未暴露 request/console 读取接口，标记 BLOCKED，未以静态推测代替。

## Findings

### High（会误导审批或阻断键盘操作）

- **分类筛选后的总数仍显示“共 6 份明细”**
  - *复现*: 工作台打开 → 点击“请假(1)”或“补交申诉(1)” → 内容区只剩对应卡片，但右上仍显示“共 6 份明细”；点击“团队待办与权限”进入空态时同样显示“共 6 份明细”。
  - *影响*: 管理员无法确认当前筛选结果是否完整，容易把全量数量当成当前待处理数量。
  - *截图*: CUA capture：筛选“补交申诉(1)”时只显示王艺博一张卡片，右上仍为“共 6 份明细”。
  - *建议*: 内容区数量与当前 `visibleCards` 同源；筛选后显示“共 1 份明细”，空态显示“当前筛选 0 份”，全量才显示总数。

- **“完成待办”会先从待办数移除，但关联审批仍可操作**
  - *复现*: 初始全量显示 6 份明细 → 点击“完成待办：王艺博申请补交数据” → 顶部总数变为 5，出现“本次已处理(1)”，但补交申诉卡和“驳回/同意补交”仍在当前工作台；切换“补交申诉(1)”仍能看到该卡。
  - *影响*: 用户可能把“完成待办”理解成整个补交事项已结案，随后漏掉真正的审批决定；同一事项同时出现在已处理和待审批两个区块，状态心智模型冲突。
  - *截图*: CUA capture：顶部 5、内容仍保留补交卡、底部“本次已处理(1)”。
  - *建议*: 对与审批绑定的待办，按钮文案改成“标记提醒已读”，或在完成待办后把关联审批卡置于明确的“仍需审批”区块；不要只减少待办总数。

- **模态焦点未锁定，Esc 提示与实际行为不一致**
  - *复现*: 打开审批台 → Tab 一次，焦点跳到背景右上角的公司所有者菜单，审批台仍在；此时按 Esc 无法关闭审批台。展开日期批注并把焦点放进输入框后按 Esc，也不会关闭审批台；只有先点“取消”收起批注，再把焦点回到工作台内部，Esc 才能关闭。
  - *影响*: 键盘用户无法预测关闭行为，焦点可落到被遮罩的背景控件，存在误操作风险。
  - *截图*: CUA AX capture：审批台打开时 Tab 后焦点为背景 `阿禅 z 公司所有者`；页脚仍展示“Esc 关闭”。
  - *建议*: 打开时将焦点放到“关闭工作台”，在弹层内循环 Tab；Esc 统一关闭当前子面板再关闭弹层；背景设置 inert/aria-hidden。

### Medium（可完成，但增加复核成本）

- **历史记录只有 50 条平铺列表，没有搜索、类型筛选或分页入口**
  - *复现*: 打开审批台 → “查看已处理记录” → 加载完成后显示“共 50 条记录”，连续平铺补交、请假、免交，只有每条“打回待处理”。
  - *影响*: 返回用户要找某个成员或某个日期时只能滚动，历史越多越难追溯。
  - *建议*: 增加成员/日期/类型筛选和分页或“加载更多”，并在卡片上保留明确的审批类型标签。

- **全量工作台把正式审批与一般待办混排，批量动作范围需要额外判断**
  - *复现*: 全部视图同时出现特殊豁免、补交申诉、请假和普通待办；顶部“一键全部同意(5)”与内容“共 6 份明细”不一致，用户必须自行推断哪些卡片会被批量同意。
  - *影响*: 高压场景下容易把“提醒类待办”和正式审批当成同一类动作。
  - *建议*: 将“审批”与“待办”分成两个明确区块；批量按钮直接写明“同意 3 份请假/豁免 + 1 份补交申诉”，并隐藏不参与批量的普通待办。

### Low（可发现性）

- **快捷键提示默认隐藏**
  - *复现*: 工作台初次打开时，页脚通过透明度隐藏；只有 hover/focus 才能看到 J/K、A/R、Z、1-3、Esc。
  - *影响*: 新用户几乎不会发现已有快捷键。
  - *建议*: 首次打开显示一次轻量提示，之后保留“快捷键”入口或 tooltip。

## Thread Results

### Thread 1：审核一笔多日特殊豁免

- **入口**: 工作台 → 行动中枢 → 特殊豁免
- **可完成**: 部分；审批按钮未执行（生产写入边界）
- **点击数**: 3（打开、切换分类、展开单日批注）
- **决策点**: 整单同意/拒绝、按天处理、是否写单日批注
- **死路**: 无；取消批注可返回卡片
- **中断恢复**: 关闭再打开后筛选和展开批注状态保留
- **结束是否清楚**: 审批结果无法在本轮确认；动作范围文字基本清楚
- **最有效简化**: 在整单按钮旁显示“含 2 个日期”，并把当前筛选数量修正为当前卡片数

### Thread 2：处理补交申诉

- **入口**: 工作台 → 补交申诉
- **可完成**: 部分；可看到业务日期、事由、2 个附件和驳回/同意补交入口，未执行审批
- **点击数**: 2（打开、切换分类）
- **决策点**: 是否先看附件、是否进入履约管理、同意还是驳回
- **死路**: 未发现；附件链接可见，正式处理入口在全量视图中可见
- **中断恢复**: 关闭再打开后仍回到上次筛选
- **结束是否清楚**: “本次已处理”与仍待审批卡片并存，结束边界不清
- **最有效简化**: 把“标记待办完成”和“审批补交”合并成一条状态链，明确显示“待审批/已标记跟进/已结案”

### Thread 3：查看已处理记录并返回

- **入口**: 工作台 → 查看已处理记录
- **可完成**: 是（只读浏览）
- **点击数**: 1（打开历史）+ 1（返回待处理）
- **决策点**: 是否打回待处理（本轮未执行）
- **死路**: 无；返回按钮可回到待处理工作台
- **中断恢复**: 返回后保留上次筛选
- **结束是否清楚**: 历史数据加载完成后“共 50 条记录”清楚，但没有继续翻页/搜索
- **最有效简化**: 历史入口增加成员、日期、类型筛选

## Scenario Results

### First Contact

- **Time to first value**: 1 次点击打开行动中枢即可看到待办和审批
- **Self-explanatory score**: 4/5
- **Terminology barriers**: “特殊豁免”“补交申诉”“团队待办与权限”需要管理员上下文；“完成待办”与审批卡的关系不够直观
- **2-minute guide**: “在工作台点击右上角‘行动中枢：待办、审批与风险’，按‘请假 / 特殊豁免 / 补交申诉’筛选；整单可选‘同意全部/拒绝全部’，多日申请也可按日期单独处理，需要留痕时展开单日批注。历史记录从右上角进入，处理后再返回待处理工作台。”
- **缺口**: 筛选计数与内容区总数不一致，第一次使用会误判还有多少事项。

## What Works Well

- 行动中枢从工作台单击即可打开，入口命名直接说明包含待办、审批与风险。
- 多日申请支持整单和单日两层处理，单日批注明确写着只记录在该日期明细中。
- 历史记录加载完成后给出“共 50 条记录”，每条显示申请人、业务日期、事由和审阅人，返回待处理入口清楚。

## Priority Recommendations

1. **先统一筛选数量和状态口径**：所有数量从当前可见卡片同源计算，修复“共 6 份明细”与分类结果不一致。预计 S。
2. **拆开“标记待办完成”和“审批结案”**：审批相关事项要持续显示“仍需审批”，避免从总数消失后仍留在可操作卡片。预计 M。
3. **补齐模态焦点管理和 Esc 行为**：焦点首置、循环 Tab、背景 inert、子面板 Esc 分层关闭。预计 S-M。
4. **为历史记录增加成员/日期/类型筛选或分页**：降低第 50 条之后的追溯成本。预计 M。

## Fix-and-Verify

本轮只做审计，没有修改代码；因此没有进入修复回归环节。

## Audit Boundaries

- 本轮以只读浏览为主；为确认“完成待办”与审批卡的状态关系，生产工作台实际执行过一次“完成待办”。页面显示“本次已处理(1)”且关联审批卡仍可见，未发现明显的撤回入口，已记录为 High finding。
- 审批、驳回、打回待处理、提交批注均未执行。
