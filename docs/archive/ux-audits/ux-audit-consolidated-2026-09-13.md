## 三、三处冲突的裁决

### 冲突 A（最危险）：提交按钮到底该禁用还是该可点？

- **千问**：按钮 `disabled` 导致已写好的"抖动 + 滚动定位"逻辑永远触发不了（form L1866-1881），建议取消禁用。
- **luna**：OCR 失败后显示"信息已具备，可提交"，模拟点击真的发出 `POST`，11 个指标全转 0。

**代码复核结果：两者都对，但根因在第三处。**

`video-submit-form-v2.tsx:1651-1652`：
```js
status:   data.slot_status === "failed" && assetUrl ? "pending_confirm" : data.slot_status,
confirmed: Boolean(assetUrl),   // ← 只要图传上去了，confirmed 无条件为 true
```
状态机 `提交状态机.ts:147` 只在 `pending_confirm && !confirmed` 时计为待确认。图在、confirmed=true → **一个 issue 都不计**。此时只要标题/文案/选题填了，就放行。
下游 `stability.ts:62` `normalizeNumber(value, fallback = 0)` 把空值兜成 0，实打实落库。

**裁决：先修状态机，再动按钮。顺序反了会放大损失。**
1. P0-1 第一优先：`confirmed` 不能只看 assetUrl，必须"有值且用户确认过"；必填指标全空时计为 issue 阻断提交。
2. 状态机修好后，**再**做千问的按钮改造（取消 disabled + 抖动定位），此时已无假阳性风险。
3. 千问提到的 `canAutoResolve`（L1855）保留，但它的触发条件应改为"对应指标有非空值"，而非 `hasManualEdit`——现在只要用户改过标题（hasManualEdit=true）就能把失败槽位漂白成 confirmed，这是 P0-1 的旁路入口。

### 冲突 B：历史修改表单是补草稿还是整个换掉？

- **千问**：给 `history-report-edit-form.tsx` 接上同一个 `useFormDraft`。
- **gemeni**：直接废掉弹窗里的旧版表单，历史「修改」改成带日期参数切换到主页面的编辑态，顺便解决字段命名双轨。

**裁决：分两步，但别把第二步当第一步。** 接草稿是半天工作量且零风险；统一表单会动到今日/历史的编辑链路，属于另一个量级的改动，应排在 P0 全部修完之后单独排期。当前先做 P1-3（接草稿），把丢数据风险止住。

### 冲突 C：移动端槽位到底并排还是堆叠？

- **09-12**：标签被截成「互动...」，建议改单列堆叠。
- **gemeni**：保留双列省纵向空间，但把"重试/手输/删除"收纳进折叠浮层。
- **luna**：320px 下输入框仅 61px 宽、底部导航覆盖指标区。

**裁决：三者说的是同一个区域的三个不同毛病，不是同一个问题的三种解法。** 合并成一个改动：窄屏（<400px）槽位单列堆叠 → 标签有完整宽度；同时把槽位顶栏的次要操作收进浮层（无论单双列都该做）；提交区加安全区 padding 避开底栏。
