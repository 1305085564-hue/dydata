# 豁免审批台 UX 全链路审计合并报告

**日期**：2026-10-12
**审计对象**：导航栏「行动中枢」弹窗（`UnifiedCommandHub`）
**合并来源**：

- 生产 Chrome 审计：[ux-audit-2026-10-12.md](ux-audit-2026-10-12.md)
- 本地隔离库 Playwright 审计：[ux-audit-2026-10-12-qw.md](ux-audit-2026-10-12-qw.md)

这份报告只合并观察和证据，不把本地结果冒充生产结果，也不把代码静态检查冒充真实浏览器验收。

## 结论

审批台的审批、驳回、逐日批注、5 秒撤回和权限边界已经形成可用闭环。当前最需要先修的是四条用户心智断裂：

1. **手机和触屏无法稳定找到逐条操作**：审批卡的主要操作依赖鼠标悬停，触屏没有 hover。
2. **补交申诉同时出现在审批和待办里**：完成待办不等于批准补交，用户可能以为已经结案。
3. **同一屏的数字没有统一口径**：工作台角标、明细数、批量同意数同时出现，无法快速判断还要处理多少条。
4. **弹窗焦点没有被锁住**：生产实测 Tab 可以落到背景，Esc 在输入框或背景焦点下也不稳定。

这四条会直接影响能不能完成审批、是否误以为完成、是否敢于批量操作，优先级高于历史检索和文案打磨。

## 证据边界

| 来源 | 环境与角色 | 覆盖 | 能证明什么 | 不能证明什么 |
|---|---|---:|---|---|
| 生产审计 | `https://dydata.cc/dashboard`，真实 Chrome，公司所有者 | 3 条线程、5/8 场景、18/30+ 可见控件 | 生产数据下的入口、状态关系、弹窗焦点和历史列表问题 | 手机/响应式、网络/控制台、第二用户、破坏性审批写入 |
| QW 审计 | 本地隔离库、`next dev :3100`、Playwright，组长/管理员 | 4 条线程、6/8 场景、375/768/1024/1440 | 本地种子下的响应式、触屏、批量确认、日期展示和完整操作流 | 生产部署、生产数据、线上性能与生产权限 |
| 代码核对 | 当前工作区源码与现有测试 | 相关组件、状态编排、API 调用 | 发现问题的真实实现位置和可回归入口 | 不能单独证明用户实际能完成任务 |

生产审计为只读为主，唯一写入动作是点击一次「完成待办」以确认状态关系；未执行生产同意、驳回、打回待处理或提交批注。QW 审计在本地执行了完整种子流程。

## 合并后的问题清单

### P0：触屏逐条审批不可用（本地实测；生产响应式证据 BLOCKED）

- **现象**：豁免卡、逐日操作和补交申诉的主要按钮使用 `opacity-0 group-hover:opacity-100`，没有鼠标 hover 的手机上看不到或难以触发「同意、驳回、批注」。
- **影响**：手机用户只能使用批量同意或离开页面，无法安全地逐条驳回和留痕。
- **实现位置**：`src/components/command-hub/exemption-approval-card.tsx`、`src/components/command-hub/fulfillment-appeal-card.tsx`，逐日操作还在 `exemption-approval-card.tsx` 的 `group/daily` 区域；待办跳转操作在 `todo-item-card.tsx` 也使用同类隐藏方式。
- **证据**：本地截图 `docs/archive/ux-audits/screenshots-qw/05-resp-375.png`、`06-resp-768.png`。生产审计没有 viewport override，因此只标记为 BLOCKED，不外推为线上移动端已复现。

**同根问题合并：桌面操作也不可发现（QW H2）**。不悬停时卡片看起来没有操作入口；首次用户不知道可整单/逐日处理。这与 P0 触屏问题共用 hover-only 根因，一起修。卡片级操作常显，逐日维持微符密度并提供可见的处理入口，具体布局交 An 落地。

### P1：审批与待办形成假闭环（两份报告均发现，生产状态关系已实测）

- **现象**：同一条补交申诉既作为「补交申诉」审批卡，又作为「团队待办」出现；勾掉待办只调用通知完成接口，不会批准申诉。生产点击一次「完成待办」后，待办数减少，但关联审批卡仍保持可操作。
- **影响**：管理员可能以为事项已处理，实际补交仍停在待审批；状态、数量和后续履约入口不一致。
- **实现位置**：`src/components/unified-command-hub.tsx` 的 `handleToggleTodo`、`todoItems`/`appealItems` 分流；`src/components/command-hub/todo-item-card.tsx`；`src/lib/command-hub/domain/view-rules.ts` 的 `getTodoItems`、`splitApprovalItems`。
- **推荐方向**：补交来源的待办只显示「去处理」并定位到审批卡，审批成功或驳回时继续由同源审批结果关闭待办；不再给补交待办一个看似等价的「完成」圆圈。

### P1：数量口径互相打架（两份报告均发现）

- **现象**：顶部角标统计审批与待办总数；审批栏的「共 N 份明细」统计原始 `pendingApprovals.length`；「一键全部同意 (N)」统计当前可批审批卡。筛选后仍可能显示原始明细数，用户无法判断当前筛选下的剩余工作量。
- **影响**：首次使用和批量处理时都容易误判范围。
- **实现位置**：`src/components/command-hub/workbench-header.tsx` 的 `totalPendingCount`；`src/components/command-hub/approvals-tab.tsx` 的 `pendingApprovals.length`、`approvalCardsCount`；`src/lib/command-hub/domain/view-rules.ts` 的 `buildVisibleApprovalCards`。
- **推荐方向**：当前视图统一显示「当前筛选下待处理 N 项」；批量按钮明确为「一键同意当前 N 条」；卡内「同意全部」改为「同意整单」。原始申请明细数只有在确实需要时以辅助说明展示。

### P1：弹窗焦点和 Esc 行为不可靠（生产实测；本地报告未覆盖同一焦点路径）

- **现象**：打开工作台后 Tab 可以进入背景导航，焦点离开弹窗；Esc 在批注输入框或背景焦点下不能稳定关闭，页脚却承诺 Esc 关闭。
- **影响**：键盘用户无法确认自己正在操作哪个区域，误操作风险增加，辅助技术用户不能完成稳定退出。
- **实现位置**：`src/components/unified-command-hub.tsx` 的全局 keydown、弹窗 wrapper/backdrop 和 footer；当前自定义弹层没有焦点首置/循环/恢复闭环；仓库已有 `src/components/ui/dialog.tsx` 可复用。
- **推荐方向**：打开时焦点进入标题或关闭按钮；Tab 只在弹窗内循环；关闭时恢复到触发按钮；Esc 按层级先关闭批注，再关闭弹窗；背景内容不可聚焦。

### P1：批量同意缺少二次确认（本地实测；生产写入未执行）

- **现象**：点击「一键全部同意」会把当前可见的所有审批排入同意队列，只依赖 5 秒撤回，没有确认范围。
- **影响**：手滑可能一次放行多条申请；撤回窗口结束后没有第二道保护。
- **实现位置**：`src/components/command-hub/approvals-tab.tsx` 的 `handleApproveAll` 入口，`src/components/unified-command-hub.tsx` 的 `handleApproveAll`、`scheduleReviewWithUndo`、`scheduleAppealReviewWithUndo`。
- **推荐方向**：批量操作先显示确认层，列出当前数量和类型；确认后仍保留 5 秒撤回。单卡单日操作保留现有即时处理和撤回机制。

### P1：375px 中文头部和筛选标签断裂（本地实测）

- **现象**：申请人姓名被压成一字一行，筛选标签出现「补交/申诉」「团队待办与权/限」等断行。
- **实现位置**：`exemption-approval-card.tsx` 头部 flex；`approvals-tab.tsx` 顶部筛选行；`workbench-header.tsx` 标题和操作区。
- **推荐方向**：姓名和关键标签使用不拆字的最小宽度与省略；筛选条允许横向滚动，不能靠折行维持布局。

### P2：历史记录没有检索和分页（生产、本地均发现）

- **现象**：历史页一次平铺约 50 条，没有成员、日期、类型筛选，也没有分页/加载更多。
- **影响**：追溯具体申请的成本随记录量线性增加；500+ 数据量尚未验证。
- **实现位置**：`src/components/command-hub/history-tab.tsx`、`history-exemption-card.tsx`、`history-appeal-card.tsx`；`src/lib/command-hub/data/approval-api.ts` 的 `fetchHistoryApprovals` 当前固定 `limit=50`；`src/app/api/exemptions/history/route.ts`。
- **推荐方向**：先确认接口是否能稳定返回游标/总数，再决定客户端筛选还是服务端分页；不要在前端假装拥有完整历史。

### P2：豁免历史“打回待处理”无确认（本地实测）

- **现象**：`HistoryExemptionCard` 直接调用 `onReopen`；补交历史卡有确认层，两类动作不一致。
- **影响**：误点会撤销已发决定并重发管理员待办，且没有撤回窗口。
- **实现位置**：`src/components/command-hub/history-exemption-card.tsx`、`src/components/unified-command-hub.tsx` 的 `handleReopenReviewDecision`。
- **推荐方向**：豁免与补交统一使用确认文案；确认前说明会退回待审批、原决定不再生效。

### P2：时间显示没有明确使用上海业务日（本地实测；代码可确认）

- **现象**：历史审阅时间按 ISO 字符串日期截取/本地时区渲染，QW 在上海时间凌晨观察到审阅日提前一天。
- **实现位置**：`src/lib/command-hub/types.ts` 的 `formatRelativeTime`、`src/lib/command-hub/domain/view-rules.ts` 的 `getCommandHubRelativeTime`、`src/lib/exemption-approvals.ts` 的 `formatShortDate`，以及两张历史卡的 `reviewed_at` 展示。
- **边界**：业务日期字符串（如 `2026-10-20`）按原日期展示；只有带时间的审阅/提交时间需要显式用 `Asia/Shanghai`。

### P2：非连续日期展示误导；半天支持待产品决策

- **非连续日期**：当前存在以最小日到最大日加「共 N 天」表示的路径，可能把 18、22、23 日读成连续区间。`src/lib/exemption-approvals.ts` 已有日期并集逻辑，需让非连续集合始终列出日期。
- **半天**：当前申请展示和 `dayCount` 以天为单位，事由中的「半天」不会自动改变审批粒度。若要真正支持半天，需要先确认数据字段与统计口径；事由里的“半天”不能证明用户实际选择了半天，不能据此断言系统多给半天。首轮不按文本推断日期粒度；是否支持半天另行决策。

### P2：同意命名、待办入口和撤回反馈仍有可发现性问题（本地实测）

- 卡内「同意全部」和顶部「一键全部同意」容易混淆：改为「同意整单」与「一键同意当前 N 条」。
- 待办使用空心圆完成入口，像复选框但没有动作说明：补交改「去处理」，其他待办提供「完成」文字或明确按钮。
- 5 秒撤回条会堆叠，底部 toast 又同时出现「已撤回」：需要合并反馈层级，确保同一动作只有一个主状态。
- 新建项显示「0 小时前」：小于 1 小时改为「刚刚」。
- 底部快捷键图例默认透明：改为默认可见，焦点/hover 只增强。
- 成员端标题为「通知与待办」，QW 当前种子未看到通知和自己的申请进度：现有待办来源包含通知，空样本不能证明通知能力不存在。先核对实际成员入口；增加申请进度属于新增能力，待产品决策。
- 申请人与团队同名时去掉重复显示。

### 待核：历史卡信息丢失（QW M7）

QW 观察到批准天数不清、事由不全。当前 `HistoryExemptionCard` 直接输出完整 `item.reason`，没有前端文本截断；待处理聚合卡会合并多条申请事由，历史卡却按原始申请逐条显示，两者本就不同粒度。因此暂不确认“历史卡截断了事由”为根因。需要对同一 request ID 核对 API 返回的 reason/daily_items 后决定补展示还是修数据，不能先改历史聚合或补造内容。

## 两份报告的差异处理

- **键盘**：QW 证明快捷键在非输入焦点下可用；生产证明 Tab 会逃到背景且输入框内 Esc 失效，两者覆盖路径不同。保留生产缺陷，验收补齐输入框、背景和子确认层。
- **网络/控制台**：QW 记录本地运行无稳定接口/控制台错误；生产工具无法读取这两类证据，仍为 BLOCKED。冷启动水合告警未稳定复现，单列待核，不写成已经确定的编译产物问题。
- **历史数量**：生产看到了 50 条；源码固定只取最近 50 条，`count` 是本次返回条数，没有完整总量。不能把“共 50 条”当成历史总量。
- **响应式**：合并时已查看 QW 的 375px 截图，确认姓名单字断行和筛选标签折行；触屏按钮实际点击能力仍来自 QW 的本地测试报告，本轮没有重新跑手机审批。

## 已验证的优点

- 驳回原因必填、未填写时不能确认，并明确提示会通知成员。
- 多日申请支持整单处理、逐日处理和单日批注，批注范围清楚。
- 5 秒撤回能覆盖常见误操作；生产审计未执行审批写入，因此撤回对生产数据的完整闭环仍需另行授权验收。
- 组员权限边界正确：本地复跑中组员看不到审批和历史入口。
- 空态、刷新失败和返回待处理入口有明确反馈。

## 未覆盖与 BLOCKED

- 生产移动端/响应式和深色模式：当前 Chrome MCP 没有 viewport override。
- 生产网络请求与控制台：当前 Chrome MCP 没有读取接口。
- 生产第二用户：只有一个已登录公司所有者会话。
- 生产同意、驳回、打回、批注：未执行写入动作。
- 500+ 历史和审批数据量：两份报告都没有真实大数据量证据。
- 关闭标签页、断网期间撤回：本地代码路径存在，但没有真机网络中断证据。
