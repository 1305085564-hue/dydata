# 岗位管理页面体验审计（2026-09-12）

## 一、结论先行

岗位管理目前“能看报表”，但还不是一张顶级的岗位经营台：负责人可以看到产量和数据，却不能稳定、快速地回答“哪里有问题、谁需要处理、处理后是否真的闭环”。

最严重的问题不是视觉，而是信任问题：当“待补岗位归属”接口失败时，页面仍然把有待补记录显示成“归属完整”。这会直接误导管理者以为数据已经收口，属于 P0 级产品缺陷。

本次在生产站点 `https://dydata.cc/admin/collaboration` 使用公司所有者会话完成桌面走查，覆盖达人、运营、文案、剪辑四个入口，以及月度切换、岗位完整度、人员档案、作品诊断、展开明细和空状态。全程未执行认证、归属指派、移入回收站等任何写操作。

## 三、真实用户旅程

### 旅程 1：进入页面，判断本月是否需要处理

管理者从工作台进入数据中心，再进入岗位管理，路径清楚，月度与岗位 Tab 也能通过 URL 复现。

问题在于首屏给的是“报表入口”，不是“决策摘要”：没有把本月作品总量、归属覆盖率、待补数量、异常作品数、需要优先处理的人放在同一层。岗位完整度按钮虽然存在，但在页面上属于轻量状态提示，不能承担管理者的行动导航。

**判断：可进入、可浏览，但首屏到达价值不够快。**

### 旅程 2：从岗位汇总定位到具体人员和作品

运营、文案、剪辑支持姓名按钮、账号展开和作品展开；作品标题可以进入作品诊断，再关闭回到原上下文。这条链路是目前页面最接近“可用闭环”的部分。

达人表格则不同：整行依靠鼠标 `onClick` 打开个人档案，但视觉上没有明确的“打开档案”动作；无障碍树里姓名只是普通文本，行也没有可聚焦或可按键触发的语义。鼠标用户能猜到，键盘用户和第一次使用的人不一定能发现。

**判断：明细能力存在，但不同岗位的可发现性和可访问性不一致。**

### 旅程 3：发现待补归属并完成处理

七月页面显示“岗位完整度 95%（1 条待补）”。第一次打开待补列表时，页面出现“网络异常，无法加载待补归属”，但抽屉同时显示“待补岗位归属 (0)”和“本月作品岗位归属均已完备”。第二次重新进入后，列表才正常显示 1 条待补作品，并提供文案、剪辑、运营三个责任人补录入口。

这说明正常路径的“发现 → 选择责任人”是存在的，但失败路径会把“未知”伪装成“完成”，且抽屉里没有清晰的重试行动。

**判断：这是整页的核心阻断，必须先修状态真实性，再谈效率优化。**

### 旅程 4：查看人员档案和岗位贡献

人员档案能展示岗位计数、趋势和经手作品，作品可以继续进入诊断。可是档案的核心摘要固定写成“本月运营概览”。纯剪辑人员文叶帆进入档案后，看到的是“本月暂无作为独立运营负责的协同作品记录”，这不是他的主要任务，也不能帮助他判断剪辑交付。

七月运营人员吕琛的个人档案里还能看到一条作品状态为“异常”，但主表没有把这个异常显露出来，管理者必须逐层点进个人档案才会发现。

**判断：档案有信息，但没有按岗位回答岗位问题；异常也没有在上游被优先暴露。**

## 四、按严重程度排序的问题

### P0：待补归属加载失败时显示“已完备”

**现场证据**

- 页面摘要仍显示“岗位完整度 95%（1 条待补）”。
- 点击后出现“网络异常，无法加载待补归属”。
- 同一抽屉显示“待补岗位归属 (0)”和“本月作品岗位归属均已完备”。
- 再次打开后才加载出真实的 1 条待补记录。

**根因线索**

`health-bar.tsx` 的失败分支只弹错误提示，没有把加载状态保存为 error；`reports` 仍为空时，渲染条件把“空结果”和“请求失败”都当成完成状态。源码位置：`src/components/collaboration/health-bar.tsx:71-88`、`:208-222`。

**业务影响**

管理者可能跳过真实待办，导致文案、剪辑或运营责任人长期缺失，后续岗位月报和结算继续带着错误数据运行。这个问题伤害的是数据可信度，不只是提示文案。

**建议**

明确区分 `加载中 / 成功有数据 / 成功无数据 / 加载失败` 四种状态。失败时显示“暂时无法确认待补情况”、保留摘要里的待补数量、提供明确的“重新加载”按钮；只有接口明确返回成功且结果为空时，才能显示“归属完整”。

### P1：2026 年 9 月运营 Tab 在生产连续失败

从九月达人 Tab 切换到运营 Tab 后，页面先出现骨架，随后显示“管理后台加载失败 / 暂时无法取得管理后台内容，请检查网络后重试”。按规则只重试一次，仍失败；之后停止重复尝试。七月同一运营页面可正常加载，因此这不是“运营 Tab 永远不可用”的结论，而是九月生产路径未通过验收，需要进一步查接口、部署版本和真实错误日志。

**业务影响**

当前月正是管理者最关心的月份，运营岗位无法查看会直接阻断岗位核对。页面给了重试按钮，但没有告诉用户失败发生在哪一步，也没有降级为可用的摘要或明确的待处理状态。

**建议**

补充服务端和前端关联错误标识、请求耗时和失败阶段；在页面上区分“接口失败”和“本月确实没有记录”；在不泄露技术细节的前提下给出可行动的重试/稍后再试状态。

### P1：当前月份仍显示可点击的“下一月”，点击后静默无反应

九月是当前月份。点击“下一月”后 URL、月份和页面内容均不变，没有禁用态、边界说明或反馈。源码中 `handleNextMonth` 在超出当前月份时直接 `return`，按钮本身没有 `disabled` 状态：`src/components/admin/collaboration/collaboration-workbench.tsx:249-260`、`:297-304`。

**业务影响**

用户无法判断是没有下一月、点击失效、还是页面加载慢。这种“死按钮”会消耗信任，尤其容易被误判为数据未更新。

**建议**

当前月份禁用按钮并暴露无障碍状态；如产品希望保持可点，则给出“已是当前月份”的即时反馈。推荐禁用，因为这是稳定、低认知成本的边界表达。

### P1：达人表格的整行操作不可见，且键盘无法触发

达人行通过 `onClick` 打开人员档案，源码位置为 `src/components/admin/collaboration/talent-tab.tsx:198-204`。但行没有按钮、链接、`tabIndex`、键盘事件或可访问角色；生产页面无障碍树中姓名也是普通文本。鼠标点击第一行确实能打开“叶颜”的档案，因此这是可用性/可访问性不一致，而不是功能不存在。

**建议**

把“打开档案”做成明确按钮，或让整行成为具有正确语义的可聚焦行，并提供 `Enter/Space` 行为、焦点样式和可访问名称。四个 Tab 应统一交互模型。

### P1：文案认证是影响结算的单击操作，却没有确认和成功反馈

文案列表中“未认证”按钮的可见帮助是“点击认证为文案人员”。源码显示点击后立即 POST；没有确认弹窗、影响说明或成功 Toast：`src/components/admin/collaboration/writer-certification-button.tsx:42-76`。本次看到该入口但没有点击，避免产生业务写入。

**业务影响**

认证会改变岗位身份和当月绩效结算范围。管理者可能把“查看/核对”误操作成“立即生效”，而刷新页面也不能让用户确认到底是否成功。

**建议**

确认文案至少说明“认证后将参与文案岗位统计与当月绩效结算”；成功后给出明确反馈并刷新局部数据。取消认证目前已有二次确认思路，可将同一安全等级应用到认证。

### P2：指标能看，但不能在页面内支持可靠决策

达人表里“有效作品”“优秀作品”有帮助说明，但“爆款作品”“独立完成”没有同等可见的定义；不同 Tab 对“本月作品 / 本月篇数 / 本月条数 / 绩效条数”的叫法也不统一。文案表虽有“绩效条数”的解释，但大量 0 作品、未认证成员与有产出成员混在同一列表，Tab 右侧的成员数量容易被理解成“本月有贡献人数”。

**建议**

在首屏或指标标题旁给出统一口径：统计范围、阈值、是否参与结算、是否只统计服务他人账号。对 0 作品成员明确标注“待产生 / 无记录 / 未认证”中的实际状态，并将“成员总数”和“本月有作品人数”拆开。

### P2：页面是四张报表，尚未成为“待处理队列”

当前默认排序偏向数量或播放量，管理者仍要自己找异常、找未归属、找没有作品的人。七月运营页中，吕琛个人档案里的作品状态为“异常”，但主表没有状态提示或优先级标记。

**建议**

首屏增加四个决策数字：本月作品数、归属覆盖率、待补数、异常数。默认把待处理人员/作品排在前面，并让主表直接显示异常、未归属、未认证等状态；绩效排行作为次级视图保留。

### P2：个人档案没有按岗位切换内容

纯剪辑人员的档案仍展示“本月运营概览”和“暂无作为独立运营负责的协同作品记录”。这会让用户怀疑自己是否点错人，或怀疑系统把岗位算错了。

**建议**

按人员当月实际岗位动态生成摘要：文案显示文案产出/认证/结算，剪辑显示剪辑产出/账号覆盖，运营显示负责账号/播放/导粉；多人多岗时分区展示，避免用运营内容填充所有人的档案。

### P2：Tab 和排序缺少屏幕阅读器状态

Tab 当前是普通按钮，没有暴露 `role=tab`、`aria-selected` 与关联面板；排序按钮也没有明确 `aria-sort`。视觉上能看出当前选中项，但无障碍树无法同样表达。键盘测试已确认顶部控件和 Tab 可以进入，但没有完成全链路键盘验收。

### P3：抽屉关闭按钮没有可访问名称

健康度抽屉和人员档案抽屉的关闭按钮是图标按钮，无障碍树中没有名称。源码位置：`health-bar.tsx:197-203`、`personal-card.tsx:161-167`。应补充“关闭待补岗位归属”“关闭个人岗位档案”等具体名称。

## 六、视觉与结构判断

当前桌面视觉整体克制，表格、抽屉、展开明细和作品诊断的层级基本清楚，没有明显装饰性干扰；运营页的账号展开按钮、作品标题按钮也有较好的可发现性。

但文案表最小宽度为 1440，剪辑表约为 1200，运营表约为 1000。当前只完成桌面生产验证，不能把“桌面看起来整齐”当成移动端通过。下一轮必须在 1024、768、375 宽度真实检查：确认是横向滚动、字段折叠，还是需要卡片化的岗位摘要；不能只依赖缩小字体解决。

## 七、推荐修复顺序

1. **先修真实性（P0）**：健康度加载失败必须进入 error 状态，禁止用空数组推断完整；失败时保留待补摘要并提供重试。
2. **再修当月可用性（P1）**：九月运营 Tab 查清生产失败原因；当前月份“下一月”改为禁用或明确反馈。
3. **补齐操作闭环（P1）**：达人行改为显式、可键盘触发的档案入口；认证增加影响说明、确认和成功反馈。
4. **把报表升级成管理台（P2）**：增加待补/异常/未认证的决策摘要和主表状态，默认优先处理而非只按产量排行。
5. **按岗位重做档案信息结构（P2）**：去掉对文案、剪辑无关的运营空提示。
6. **完成可访问性与响应式复验（P2/P3）**：Tab、排序、抽屉关闭按钮补语义；真实验证 1024/768/375 和深色模式。

## 八、收口

本次结论是：岗位管理的基础数据浏览和作品下钻能力已经存在，但“发现问题 → 判断责任 → 处理 → 确认收口”还没有达到顶级产品的可信闭环。当前不建议先做视觉装饰或复杂动效，优先修复错误状态伪装成完成、当月运营入口失败、隐式行操作和结算相关误触这四类问题。

本报告为新增审计文档；本次未修改业务代码、未写入数据库，现有工作区内与选题库、数据上传相关的脏改动保持原样。
