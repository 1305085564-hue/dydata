# UX Audit: DYData「日报上传 → 数据引用」端到端链路

**Date**: 2026-10-15
**URL**: https://dydata.cc（生产站公开探针可达；认证页面未能进入）
**Persona**: 团队负责人/内容管理者，每天处理成员日报、查看作品数据和发布履约；时间紧、非技术用户，桌面为主，偶尔用手机核对。
**Browser**: Chrome MCP 初始化连续两次超时，真实登录态、截图、控制台和网络面板均 `BLOCKED`；本报告以代码、迁移、现行文档和生产公开 HTTP 探针为证据。
**Viewport**: 未执行（1440×900 及响应式均 `BLOCKED`）
**Reference extract used**: `docs/页面功能/数据管理/数据管理.md`

## Summary

这条链路的真实主干已经明确：用户在 `/dashboard` 填写日报，上传的是两张数据截图而不是视频文件；截图先进入 `submission-screenshots` Storage，再由 `/api/ocr-screenshot` 识别，表单将 OCR 结果与人工修正一起提交到 `/api/video-submit`。服务端按当前 `video_id` 写入 `videos`、24h `video_metrics_snapshots`、`daily_reports`，再补写标签、导粉话术使用记录、来源和截图替换留痕。

跨模块引用并非单一表：员工工作台和历史手稿主要读 `daily_reports`，视频复盘读 `videos + video_metrics_snapshots + video_tags`，数据管理以 `daily_reports` 统计并按 `video_id` 取快照，发布履约通过 `get_fulfillment_range` RPC 从有效日报推导每天发布数量，再叠加 `fulfillment_records` 的人工改判。链路在数据库层可追溯，但用户界面仍有两个高风险断点：日期级工作台会把同一账号同一发布日的多条作品合并成一条；历史手稿异步列表默认只取 30 条且没有看到分页/继续加载入口。真实页面、真实角色、接口状态和视觉细节尚未验收。

## 端到端链路地图

```text
/dashboard
  选择账号 + 选择日期
  → 填写标题/文案/题材/视频形式/责任人
  → 上传「互动截图」和「完播截图」
      → POST /api/submission-screenshots (multipart)
      → Storage bucket: submission-screenshots
      → POST /api/ocr-screenshot (bucket + path + asset_role)
      → OCR 返回指标、发布时间、标题、置信度
      → 页面按槽位回填，可人工核对/补填
  → POST /api/video-submit
      1. 校验登录、成员、账号、截图归属、字段边界、重复提交、72h/补交
      2. videos
      3. video_metrics_snapshots(snapshot_type=24h)
      4. daily_reports
      5. video_tags（AI + 手工）
      6. script_usage_records（导粉话术有值时）
      7. daily_reports.data_source + 截图替换历史
      8. 返回 video_id + daily_report_id

引用：
  员工日历/今日状态       ← daily_reports + published_at 日期
  历史手稿                ← /api/dashboard/activity → daily_reports
  视频复盘 /admin/content ← videos + video_metrics_snapshots + video_tags
  数据管理 /admin/collaboration ← daily_reports + 24h snapshots + profiles/accounts
  导出 /api/export         ← daily_reports（不读取 snapshots/videos/tags）
  发布履约 /admin/fulfillment ← get_fulfillment_range RPC
                              ← daily_reports 有效行计数 + fulfillment_records 改判
```

## Thread Results

### Thread 1: 上传当日日报（含两张截图和 24h 数据）

- **Completable end-to-end**: 代码链路可闭合；真实页面未验收。
- **入口**: `/dashboard` → `ProductionControlSystem` → `VideoSubmitPanelV2` → `VideoSubmitFormV2`。
- **用户输入**: 账号、视频标题、文案、题材标签、视频形式、责任人；当前表单没有 `video_url` 输入控件，也没有视频文件上传步骤，本平台实际只登记日报和数据。正常提交必须有互动截图和完播截图；异常提交可不带截图。
- **文件处理**: 接受 jpg/png/webp，单图最大 8MB；服务端校验文件签名，JPEG 大于 250KB 时尝试压缩，Storage 路径包含用户、账号、槽位和随机 UUID，禁止覆盖。
- **OCR**: 先存储后识别。后端从受保护 Storage 下载图片，按 `asset_role` 与显式 `screenshot_type` 决定 data/retention 识别；返回识别字段、置信度、失败/需确认状态和发布时间证据。低置信度不会伪造成功，页面保留截图并允许手填。
- **日期**: 正常新建必须拿到 OCR 确认的真实 `published_at`；识别不到时返回 400/409，提示重新上传能看清“发布”时间的完播截图。72 小时外或补交门禁要求审批。
- **服务端落库顺序**: 校验登录/账号/截图归属/字段边界 → 72h 与补交门禁 → 重复提交检查 → 当前作品 `videos` → 24h 指标快照 `video_metrics_snapshots` → 日报 `daily_reports` → AI 三维标签与手工标签 → 导粉话术使用记录 → `data_source` → 截图替换历史。每一步都会登记反向补偿动作，失败按倒序回滚，避免半条链残留；编辑模式缺原快照或原日报时分别返回 422/404，不新建替代记录。
- **完成反馈**: 返回 `video_id`、`daily_report_id`，页面显示“今日创作已成功立卷”，并提供去选题库、查看并修改、留在工作台、AI 检查样本质量。
- **真实验收状态**: `BLOCKED`（Chrome MCP 超时，无截图、请求、响应、点击证据）。

### Thread 2: 回到日历和历史手稿查看/编辑

- **日历引用**: `/dashboard` 首屏读取当前账号最近约 60 天有效 `daily_reports`；提交日期集合由 `published_at` 的上海自然日生成，缺发布时间时才回退 `report_date`。选中日期后，`activeDateReport` 按账号+发布日取一条，决定“已交/未交/补交/编辑”状态。
- **写后刷新**: 成功提交先写本地 `reportOverrides`，再异步拉 `/api/dashboard/activity`，让当前工作台立即显示新记录。
- **历史手稿入口**: 工具栏打开历史弹窗；活动接口查询当前用户账号下 `daily_reports`，`is_void=false`，按 `published_at`、`uploaded_at` 倒序，默认 `pageSize=30`。
- **历史列表展示**: 桌面表格/移动卡片显示发布日、账号、标题、播放、完播、均播、互动数据；按账号和月份筛选；点击行进入编辑。
- **编辑**: `/api/video-submit/edit-detail?account_id&biz_date` 读取原日报、绑定视频、24h 快照、标签、话术和责任人；有视频时走编辑模式，只更新原绑定视频/快照/日报；无绑定视频时允许“只更新日报数据”的历史分支。
- **日期语义**: UI 对外显示“发布日”；`uploaded_at` 仅表示实际上传时点；`report_date` 是内部追溯/编辑键。数据库约束要求有 `published_at` 的日报 `report_date` 必须等于上海自然日。
- **真实验收状态**: `BLOCKED`。

### Thread 3: 管理侧引用与履约闭环

- **视频复盘 `/admin/content`**: 先按权限范围读取 active `videos`，再按视频 ID 批量读取 `video_metrics_snapshots`、`video_tags`、拆段资料和内容质量；详情抽屉按 `video_id` 直接打开。日报不会直接驱动复盘列表，但日报的 `video_id` 是从数据管理/协作入口跳入复盘的绑定桥。
- **数据管理 `/admin/collaboration`**: 共享月度数据集以 `daily_reports` 为产量和责任人事实源，再按这些日报的 `video_id` 批量读取 24h 快照和话题标签；岗位/小组页面在内存中按 `script_author_user_id`、`video_editor_user_id`、`operator_user_id` 分发。作品排序和月度归属优先用 `published_at`，没有发布时间才回退 `report_date`。
- **数据管理打开作品复盘**: `/api/admin/collaboration/work-video?reportId=` 先检查可见日报；若有 `video_id` 直接加载该视频详情；无绑定视频时才按账号+上海业务日匹配 active 视频，找不到返回 404，多条候选返回 409，避免打开错作品。
- **发布履约 `/admin/fulfillment`**: 页面调用 `get_fulfillment_range`。当前最新迁移把误写的 `content_items` 改回 `daily_reports` 并过滤 `is_void=false`；其 `published_count` 静态上按 `daily_reports.report_date` 聚合。`fulfillment_records` 不是日报提交的产物：日报触发器只会删除同成员同日期的 `absent` 标记，用于补交销账；请假/豁免/缺勤/人工确认来自 `mark_fulfillment_status()`、批量 RPC 和履约申诉处理 RPC。人工记录优先于日报计数。
- **履约日期口径风险**: 员工日历、历史手稿、数据管理和导出都优先用 `published_at` 的上海自然日；当前履约 RPC 静态代码却按 `report_date` 计数。两套口径即使历史数据已批量对齐，也会在未来出现“发布日期与归属日再次不一致”时重新分叉。
- **履约豁免风险**: 10-10 版本曾包含 `exemption_grant` CTE；10-13 最新替换函数体没有该 CTE，只保留 profile 上的临时豁免字段。若生产已按序执行，已批准的 `exemption_grant` 可能不会在履约矩阵中显示为豁免；这是独立的生产只读核对项。
- **补交**: 首次提交超 72 小时会返回 `SUBMISSION_APPEAL_REQUIRED`；员工提交 `fulfillment_appeals` 后，管理员审批。批准不等于日报已经存在，实际 `/api/video-submit` 成功写入后才恢复对应业务日的履约状态；`resumeAppeal` 可自动续交。
- **历史编辑**: `published_at` 不可改，编辑态保留原 `report_date`；无 `video_id` 时只更新日报，不按发布时间猜视频。若存在 24h 快照，只同步表单中的 11 个指标；没有快照不新建，截图、`follower_loss`、`vs_previous` 等字段不被历史手稿覆盖。
- **导出**: `/api/export` 是独立的第七个引用方，只读有效 `daily_reports`，最多 10,000 行；导出指标不读取 `videos`、`video_metrics_snapshots` 或 `video_tags`，因此与数据管理/视频复盘的快照值不一致时，首先应判断为数据源设计差异。
- **真实验收状态**: `BLOCKED`。

## Findings

### Critical（阻断任务）

- **C1 认证浏览器不可用，无法完成真实用户链路验收**
  - *Where*: 全链路。
  - *Evidence*: Chrome MCP `getState()` 连续两次初始化超时；生产公开请求只返回 `/login` 重定向。
  - *Impact*: 没有真实点击、截图、网络、控制台、角色权限证据，不能把静态链路结论写成“页面已验收”。
  - *Fix*: 打开 Chrome，连接 Chrome MCP，并用真实组长/成员角色重跑三个线程；补齐截图和 `read_network_requests`。

### High（混淆、摩擦、信任损伤）

- **H1 日期级工作台会折叠同一账号同一发布日的多条作品**
  - *Where*: `src/lib/dashboard-submission-state.ts:79-116`、`src/app/(app)/dashboard/video-submit-panel-v2.tsx:210-257`。
  - *Evidence*: `mergeDashboardReports` 用 `account_id:report_date` 作为唯一键；`activeDateReport` 用 `find` 取第一条；`getTodaySubmissionSummary` 也只返回同账号最新一条。现行规则明确允许同一账号同一业务日有多条日报，但每条绑定不同 `video_id`。
  - *Impact*: 一天发两条及以上作品时，日历只显示“已交”，表单/摘要只展示一条；用户无法在日历入口确认当天全部作品，容易把“已交”误解为“只交了一条”。
  - *Screenshot*: 无（浏览器 BLOCKED）。
  - *Fix*: 日历状态按日期聚合，摘要改为“当天 N 条”并提供作品列表；编辑入口必须按 `report.id`/`video_id` 精确选条。

- **H2 历史手稿默认只拉 30 条，当前组件未见继续加载入口**
  - *Where*: `src/lib/loaders/dashboard-activity.ts:22-64`、`src/app/(app)/dashboard/video-submit-panel-v2.tsx:440`、`src/app/(app)/dashboard/history-list.tsx:58-111`。
  - *Evidence*: 活动接口支持 `page/pageSize`，默认 pageSize=30；面板只调用无参数 `fetchDashboardActivity()`，历史列表只对已拿到的数组做前 10 条展开，没有“加载更多/分页”调用。
  - *Impact*: 超过 30 条的老日报不在历史手稿里；用户会把“历史没有”误判为上传丢失，尤其与数据管理、发布履约能看到的记录形成信任冲突。
  - *Screenshot*: 无（浏览器 BLOCKED）。
  - *Fix*: 历史弹窗增加明确分页/加载更多，并显示“已加载 N 条”；筛选条件与页码联动，编辑后保持当前页。

- **H3 员工侧与履约侧使用两套日期口径**
  - *Where*: `supabase/migrations/20261010123000_fulfillment_use_video_published_date.sql`、`supabase/migrations/20261013100000_fix_fulfillment_rpc_content_items_typo.sql`。
  - *Evidence*: 静态上已确认最新替换函数按 `daily_reports.report_date` 聚合；员工日历、历史手稿、数据管理、导出按 `published_at` 上海日优先。历史修复只能消除已有错位，不能阻止未来新错位。
  - *Impact*: 同一作品可能在员工日历/数据管理显示在发布日期，在发布履约显示在日报归属日；负责人会得到“作品已发布但当天未履约”或相反的错误解释。
  - *Screenshot*: 无（浏览器 BLOCKED）。
  - *Fix*: 先做生产 `pg_proc` 只读核对并留档；随后产品上统一履约的日期真源，推荐采用“有视频按上海发布日期、无视频回退日报日”，与员工侧和数据管理一致。

- **H5 最新履约 RPC 可能漏掉已批准豁免**
  - *Where*: `supabase/migrations/20261010123000_fulfillment_use_video_published_date.sql`、`supabase/migrations/20261013100000_fix_fulfillment_rpc_content_items_typo.sql`。
  - *Evidence*: 10-10 版本有 `exemption_grant` CTE；10-13 最新函数体没有该 CTE，只保留 profile 上的 temporary exemption 判断。静态代码已确认，生产最终函数体仍需只读核对。
  - *Impact*: 已批准但未写入 profile 的豁免可能仍显示为“未确认/缺交”，直接影响履约统计和管理者判断。
  - *Screenshot*: 无（浏览器 BLOCKED）。
  - *Fix*: 生产核对 `pg_proc` 与一条已批准 `exemption_grant` 的只读样本；若确认漏算，恢复 grant CTE 或建立统一豁免事实源，再做履约矩阵回归。

- **H4 上传成功反馈和跨模块可见性缺少同一条可核对线索**
  - *Where*: `src/app/(app)/dashboard/form-v2/submitted-view.tsx:60-77`、`src/app/api/video-submit/route-core.ts:944-953`。
  - *Evidence*: 成功态只展示“归属日期”和“记录已安全落库”，虽然接口返回 `video_id`/`daily_report_id`，页面没有把可复制的作品标题、发布日、日报编号或“去历史/去复盘/去履约核对”作为用户可见确认。
  - *Impact*: 用户提交后若在某个模块找不到记录，缺少一条稳定的核对凭据，容易重复提交或认为数据丢失。
  - *Screenshot*: 无（浏览器 BLOCKED）。
  - *Fix*: 成功态展示“作品标题 + 发布日 + 已写入日报/24h 数据”，提供“查看这条历史手稿”“打开视频复盘”的直接入口；重复提交时引用同一作品标识。

### Medium（可用但增加成本）

- **M1 正常上传是“截图上传”，页面没有把“视频本体不上传”说清楚**。当前表单没有视频链接输入，也不上传视频文件；建议在入口旁写“本平台只登记日报和数据，不上传视频文件”，不要引导用户填写不存在的链接。
- **M2 OCR 失败后的降级是可继续提交，但需要用户自己判断哪些数字该补**。截图会保留并提示手填，但没有在成功态复述“哪些字段来自 OCR、哪些字段是手工”；`data_source` 只在历史列表用标签体现，管理侧不一定显眼。
- **M3 数据管理的产量来自日报，指标来自 24h 快照**。`daily_reports` 是岗位/小组产量和责任人事实源，但指标通过 `video_id` 读取 `video_metrics_snapshots`；导出则只读日报。跨模块数字不一致时，应先显示数据源，而不是让用户猜“哪一页错了”。
- **M4 无绑定历史日报不能按发布时间反查视频**。数据管理 work-video 已有 404/409 保护，仍需把“未同步到视频复盘”显示为可理解的状态。
- **M5 `data_source` 需要成为可解释来源**。实际只落 `ai` 或 `manual`：手工修改优先级最高，重新上传并识别可把旧来源更新为 `ai`，没有新证据时保留旧值；历史列表只显示简化标签，无法解释具体是哪种动作导致来源变化。
- **M6 `/admin/content` 使用 60 秒缓存和批量读取，数据管理使用月度缓存；写后短时间内不同模块可能看到不同版本。项目已有 `FULFILLMENT_DATA_CHANGED_EVENT`，但上传成功后的跨模块失效/刷新策略未在本链路中看到统一事件。
- **M7 组员/管理员权限范围由不同入口各自计算：工作台读用户账号，数据管理和视频复盘走 `visibleUserIds`。真实角色复验缺失，不能假设“在履约看得到”就等于“在历史手稿/复盘也看得到”。

### Low（文字与发现性）

- **L1** “历史手稿”“视频复盘”“数据管理”“发布管理”是四个不同入口，用户需要自己理解“日报、作品、快照、履约”的关系；建议在历史弹窗或空态放一行关系说明。

## What Works Well

- 上传链路把“存储”和“OCR”分开：截图先留存，OCR 失败不会丢证据，用户可以手填后继续。
- 正常提交的截图槽位、发布时间证据、72 小时补交门禁在服务端再次校验，页面绕不过关键条件。
- 写入顺序清楚且有补偿回滚；不会把“视频有了、快照有了、日报没了”当成成功返回。
- 新建提交按当前 `video_id` 插入日报，编辑按原绑定精确更新，避免复用同账号同业务日另一条日报；这是对历史绑定覆盖问题的直接收口。
- 数据管理跳复盘时对无绑定和多候选分别返回 404/409，优先保护“打开错作品”的风险。
- 发布履约 RPC 已有 `is_void=false` 过滤，作废日报不会继续被计入发布数。

## Priority Recommendations

1. **先修日历/历史的多作品可见性**（H1，M）：日历保留日期状态，但提供“当天 N 条作品”清单，编辑必须按日报/视频 ID 选条。
2. **补历史手稿分页或加载更多**（H2，S）：默认只取 30 条与“历史”命名冲突，且容易制造跨模块数据丢失错觉。
3. **做生产只读核对并统一履约最终日期口径**（H3，S/M）：核对 `pg_proc` 最终函数体、迁移是否已按顺序执行，再决定是按视频上海发布日期还是日报归属日计数。
4. **把提交成功后的追踪线索露出来**（H4，S）：展示标题、发布日、日报编号/作品入口，并提供到历史手稿和视频复盘的直达按钮。
5. **补真实浏览器验收**（C1）：连接 Chrome MCP 后按三个线程重跑，记录每个关键状态的截图、请求、响应、控制台和真实角色权限。
