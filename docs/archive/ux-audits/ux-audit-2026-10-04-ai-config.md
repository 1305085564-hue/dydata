# UX Audit: DYData AI 配置中心

**Date**: 2026-10-04
**URL**: https://dydata.cc/admin/ai-config?tab=providers
**Persona**: 公司所有者/系统管理员；中等技术熟练度；日常需要快速确认 AI 是否可用、调整业务模型、维护渠道密钥；桌面端，时间紧，不能承担误停用或误删。
**Browser**: 已登录 Chrome（本机现有管理员会话，通过 CUA 原生窗口复验）
**Viewport**: 当前 Chrome 窗口截图（约 1536px 宽）；未能通过扩展通道固定 1440×900，响应式宽度/暗色仍待补证。
**Reference extract used**: none

## Summary

页面能把业务功能、模型系列、服务商和密钥集中到一个入口，真实数据可读，权限入口和状态反馈基本清楚。主要风险集中在高密度算力池、隐含在悬停里的批量操作、健康状态口径不一致、全池体检结束后提示不收口，以及“全局默认兜底”的调整入口实际无响应。

本报告只审计真实可见链路和不产生业务写入的交互。停用、下架、删除、接入新渠道等会改变线上配置的动作未提交。

- 全池体检：已在当前管理员会话中执行并观察到 8/11、73% 的结果变化；一键模型测试/一键渠道测试属于悬停后的真实渠道动作，本轮未执行完整错误矩阵。
- 低权限第二用户：当前 Chrome 只有公司所有者会话，未切换账号。
- 1440/1280/1024/768/375 与暗色：原生 Chrome 扩展通道不可用，暂未取得可控 viewport。

## Findings

### High（混淆、摩擦、信任风险）

- **健康状态互相打架**：页面顶部显示“7/11 密钥健康在线 · 所有业务功能正常运行中”，算力池又显示“健康率 64%”，业务模型下拉还出现“gpt-6.1-sol（0 个密钥就绪）”。管理员无法判断“全站正常”是功能开关正常、还是实际有可用渠道；在故障排查时会先怀疑数据不一致。
  - *Where*: `/admin/ai-config` 顶部总览、业务调度卡、算力池概览条。
  - *Evidence*: 2026-10-04 线上基线截图（首屏）与 AX 状态均同时出现上述文案。
  - *Fix*: 统一健康口径，至少拆成“功能开关状态”和“当前可用渠道数”；当选定模型为 0 个就绪时，业务行应显示“无可用渠道/将走全局兜底”，不能仅显示“运行中”。

- **全池体检结束后仍显示“正在检测 API 密钥...”**：点击全池体检后按钮在约 12 秒后恢复为“全池体检”，顶部统计也从 7/11、64% 变为 8/11、73%，但右下角通知在继续等待约 45 秒后仍保留“正在检测 API 密钥...”。结果已经变化，加载提示却没有结束，管理员无法确认动作是否已完成或是否仍有请求挂起。
  - *Where*: 顶部“全池体检”按钮与全局通知区域。
  - *Evidence*: 2026-10-04 线上实测；按钮恢复且统计变化后再等待约 45 秒，通知仍在；刷新深链后约 3 秒仍可见。静态实现 `src/app/(app)/admin/ai-config/hooks/use-ai-config.ts:229-250` 先调用 `feedbackToast.loading`，完成后只追加 success/warning，没有关闭 loading toast。
  - *Fix*: 为加载提示保存并关闭对应 toast，完成时把“已测试 N 个、正常/异常各多少、最后更新时间”合并成一条结果；请求超时或部分失败要明确落到结果条。

- **全局默认兜底的“调整”按钮是静默无效操作**：业务表首行给出了可点击的“调整”，但点击后没有弹窗、提示或页面变化。代码只在 `featureControls` 中找到 `key === "default"` 时才打开弹窗，而当前页面的默认项来自 `featureBindings`，所以 `defCtrl` 为空时点击直接结束。
  - *Where*: 业务模块调度列表第一行“✦ 全局默认兜底”。
  - *Evidence*: 线上点击 AX 99“调整”无任何变化；静态实现 `src/app/(app)/admin/ai-config/components/business-functions-panel.tsx:51-53,155-163`。
  - *Fix*: 要么移除该按钮并把入口文案改为“调整全局模型”，要么为 default 建立完整控制对象；在入口未准备好时至少禁用按钮并说明原因，不能让点击无反馈。

- **批量测试入口默认藏在悬停层**：算力池概览条只常显“模型管理/管理服务商/接入渠道”，而“一键模型测试/一键渠道测试”通过 hover 才出现。键盘用户、触屏用户和第一次进入页面的人都看不到这两个关键维护动作。
  - *Where*: 算力储备与渠道底座概览条。
  - *Evidence*: 静态实现 `ComputePoolPanel` 使用 `opacity-0 max-w-0 pointer-events-none group-hover/overview:*`；首屏截图默认不可见。
  - *Fix*: 将批量测试放入显式“更多操作”菜单或直接保留可见按钮，并提供键盘可达焦点状态。

- **算力池信息密度高但缺少筛选/折叠策略**：模型按组展开，所有渠道行同时展示，重复的优先级、服务商、脱敏 key、健康、测试、编辑、删除控制堆叠在一起。真实规模扩大后，定位某个故障渠道需要长距离滚动；页面没有搜索、按健康筛选或仅看异常的入口。
  - *Where*: 算力储备与渠道底座模型列表。
  - *Evidence*: 线上主列表包含 8 个模型系列、11 个活跃密钥和多条故障行；AX 树约 290 个节点。模型管理弹窗虽有模型搜索和服务商筛选，但主列表没有复用这些筛选，也没有健康/无可用渠道过滤。
  - *Fix*: 在主列表增加“仅看故障/仅看无可用渠道”、服务商/模型搜索、折叠全部/展开异常，并把删除等低频动作收进行菜单。

- **模型选择器允许直接选到 0 个密钥就绪的模型**：业务和 OCR 下拉把大量“0 个密钥就绪”的模型作为普通选项展示；当前 OCR 实际选中 `gpt-6.1-sol (0 个密钥就绪)`，页面仍标为“运行中”。管理员需要自己推断这个选择是否会回退、失败或等待接入渠道。
  - *Where*: 截图识别卡片与业务模块调度表的“调度模型”下拉。
  - *Evidence*: 线上打开下拉后看到多个 0 个密钥就绪选项；静态实现 `model-family-select.tsx:35-62,77-83` 直接渲染 `availableKeyCount`，没有禁用或风险提示。
  - *Fix*: 默认隐藏不可用模型，或把它们分组到“无可用渠道”并在选择前说明回退规则；选中 0 就绪模型时同步改状态文案。

### Medium（可用但增加理解成本）

- **“一键模型测试”与“一键渠道测试”名称不够可区分**：前者实际是同步/探测模型并写入新发现模型，后者是测试密钥连通；两者都在同一工具区，动作后果不同但文案只差一个词。
  - *Fix*: 明确成“探测并同步模型”和“测试全部渠道”，并在按钮旁说明是否会新增模型记录。

- **业务功能使用“停用该功能”作为行级图标操作，缺少持续状态说明**：首屏“运行中”状态与行末图标并列，停用按钮没有在表格中明确表达“停用后前台不会发起 AI 请求”的影响；用户需打开高级参数才看到说明。
  - *Fix*: 给停用动作提供 hover/键盘说明，并在确认层展示影响范围与恢复入口。

- **模型系列名称与渠道显示名混在同一视觉层**：如 `gemini-2.5-flash-lite`、`api9 (gemin)`、`api2 gemin (default)`，普通管理员难以判断哪个是模型、哪个是供应商、哪个是 key 别名。
  - *Fix*: 将“模型系列 / 服务商 / 密钥别名 / 优先级”分列或加固定字段标签，不依赖括号和缩写。

- **“试跑真实用例”结束后没有卡片内结果**：点击后按钮显示“试跑中…”，约 20 秒后恢复原文案；成功/失败只依赖右下角临时通知。当前页面同时残留全池体检的加载通知，试跑结束后看不到明确的通过、失败或使用了哪一把密钥。
  - *Where*: 截图识别与结构化提取卡片右上角。
  - *Evidence*: 线上实测按钮进入和退出 loading；静态实现 `screenshot-recognition-card.tsx:72-88,123-132` 只在成功时追加 toast，卡片本身不保留结果。
  - *Fix*: 在卡片内保留最后一次试跑时间、结果、耗时和实际模型/密钥；没有可用密钥时把原因放在按钮旁，而不是只发一次通知。

### Low（细节）

- **页首与首个业务卡之间留白较大**：在当前宽屏截图里，标题、健康条、业务卡之间形成大块空白，首屏能承载的有效信息减少。
- **底部“算力底座静候调度 · 智能容灾与高可用”是装饰性文案**：占据滚动末端位置，但没有提供诊断或下一步动作；可保留，但不应与可操作信息争夺视觉注意。

## Thread Results

### Thread 1: 查看当前全站 AI 是否可用

- **Completable end-to-end**: Partially。能看到总览、功能开关和模型/渠道健康状态；全池体检会更新数字，但通知不收口，三套口径仍不能快速合并成一个可信结论。
- **Click count**: 0（直接进入深链）；从导航进入约 2 clicks（管理中心 → AI 配置）。
- **Decision points**: 2 — “7/11 健康在线”与“64% 健康率”是否同一口径；“运行中”但模型 0 个密钥就绪是否可用。
- **Dead ends**: 1。全池体检结果已更新，但“正在检测 API 密钥...”仍留在通知区；全局默认兜底的“调整”按钮点击无响应。
- **Interrupt recovery**: 未进入可编辑表单；刷新后可回到同一深链，页面 URL 保留 `?tab=providers`。
- **Did it end clearly?**: No。页面没有“当前需要处理的故障渠道”摘要，体检也没有稳定的完成态。
- **Would I come back?**: Maybe。日常可读，但故障排查需要逐组滚动。
- **One thing to make it twice as easy**: 顶部直接给出“可用业务数 / 无可用渠道数 / 待处理故障数”。

### Thread 2: 调整某个业务功能的模型与高级参数

- **Completable end-to-end**: 可进入业务行弹窗并检查字段；OCR 高级参数可打开、Escape 可关闭；全局默认兜底首行的“调整”按钮无法进入弹窗。未保存以免改线上策略。
- **Click count**: 1（点击“调整参数”）。
- **Decision points**: 3 — 模型为空是否跟随全局兜底；OCR 看图回退与文字结构化模型能力区别；Token/上下文范围。
- **Dead ends**: 1。全局默认兜底的入口无响应。
- **Interrupt recovery**: 通过 Escape 可关闭未提交弹窗；刷新/离开时表单草稿是否保留仍待核。
- **Did it end clearly?**: 弹窗有“取消/保存高级设置”，结束信号明确。
- **Would I come back?**: Yes，前提是保存后能在表格行即时看到模型和状态变化。
- **One thing to make it twice as easy**: 在表格行直接展示“跟随全局/专属模型”和停用影响，减少反复开弹窗。

### Thread 3: 维护模型、服务商与渠道密钥

- **Completable end-to-end**: 已完成模型管理、服务商管理、接入渠道和密钥编辑弹窗的只读浏览；未执行接入、删除、上下架。
- **Click count**: 1（各入口均可从算力池概览条打开）。
- **Decision points**: 4 — 模型管理和渠道列表的边界；同步模型是否改变仓库；删除是否会自动切换备用；故障行应先测连通还是换优先级。
- **Dead ends**: 0，但滚动距离长；模型管理有搜索/服务商筛选，主列表仍需逐组浏览。
- **Interrupt recovery**: 未提交表单；列表滚动位置可回到当前页面，但筛选/折叠状态能力未发现。
- **Did it end clearly?**: 只读查看清楚；维护动作的后果需依赖弹窗确认文案。
- **Would I come back?**: Maybe。熟悉后能操作，首次用户需要术语解释。
- **One thing to make it twice as easy**: 增加按“故障/无可用渠道/正在使用”筛选。

## Scenario Results

### First Contact

- **Time to first value**: 进入深链 0 clicks；从主导航约 2 clicks。
- **Self-explanatory score**: 3/5。
- **Terminology barriers**: “算力池”“模型系列”“渠道”“密钥健康在线”“全局默认兜底”“同步模型”。
- **Threads easy to explain**: 查看功能行的模型和运行状态；打开“高级参数”后保存策略。
- **Threads requiring caveats**: 健康状态必须同时看顶部、业务行和算力池；删除渠道可能触发备用模型切换；批量测试默认藏在 hover。
- **Threads unexplainable**: 没有把“0 个密钥就绪”与“运行中”解释成可执行结论。
- **2-minute guide**:
  - *查看状态*: “进入管理中心的 AI 配置，先看顶部健康条，再看业务功能调度表；如果某行显示 0 个密钥就绪，继续到下面模型池查健康渠道。”
  - *改模型*: “在业务功能行点击‘调整参数’，选择模型系列，按需改提示词和 Token/上下文范围，确认影响后点‘保存高级设置’。”
  - *维护渠道*: “在算力底座点击‘管理服务商’或‘接入渠道’；模型池每行可测试连通、编辑密钥或删除，但先看是否有业务依赖。”

## What Works Well

- 业务功能、模型池、服务商与渠道资产集中在一个页面，入口少，管理员不用在旧的多个配置页之间跳转。
- 业务行明确给出定位说明；OCR 看图回退与文字结构化在高级配置里提供了模型能力提示，能降低误配风险。
- 密钥只显示脱敏尾缀，且行级状态区分“健康/故障”；删除路径设计了依赖检查和短时撤回入口，安全意识较好。
- 深链 URL 保留 `?tab=providers`，刷新和书签回访成本低。
- 高级参数弹窗把 OCR 视觉能力提醒、Token 1200–8000、上下文 1–50 和启用开关放在同一视图；模型管理弹窗也明确区分“现役在册 (8)”和“储备待开启 (50)”，并提供模型搜索与服务商筛选。
- 密钥编辑表单默认不回显 API Key，提示“留空表示不修改”；本轮没有提交任何破坏性动作。

## Priority Recommendations

1. **先修复无效入口和体检完成态**：让全局默认兜底“调整”打开真实配置或被明确禁用；关闭全池体检 loading toast 并留下可追溯结果。这两项会直接影响管理员是否敢继续操作。预计 S。
2. **统一健康口径并暴露“当前可用性”**：顶部显示健康密钥数、可用模型数、受影响业务数，处理“运行中但 0 个密钥就绪”的冲突；0 就绪模型要明确回退/不可用规则。预计 S。
3. **把批量测试和故障筛选改为显式入口**：移除 hover-only 批量操作，增加仅看故障/无可用渠道/按服务商筛选。预计 M。
4. **降低模型池行密度并拆分字段**：固定模型/服务商/key 别名/优先级列，长列表支持折叠和搜索；试跑结果在卡片内留痕。预计 M。
5. **补齐弹窗键盘、草稿、确认文案和第二角色矩阵**：这是高风险配置页的发布前门禁。预计 M。
