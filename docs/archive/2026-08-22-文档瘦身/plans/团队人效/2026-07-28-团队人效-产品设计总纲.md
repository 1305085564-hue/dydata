## 一、这页解决什么

阿禅的原话：「运营下面带了几个达人，达人各自和总共的流量情况，剪辑岗剪了哪些视频，每个月剪了多少个，文案这个月写了多少篇，流量如何，写的谁的。」

现有三个后台都不回答这个问题，因为它们的主键不是「人」：

| 现有页面 | 主键视角 | 回答的问题 |
|---|---|---|
| 视频复盘 `/admin/content` | 单条视频 | 这个视频为什么爆/为什么崩 |
| 发布管理 `/admin/fulfillment` | 交没交 | 谁按时交了、谁缺了（考勤） |
| 经营分析 `/admin/analytics` | 日期 + 上传者 | 哪个达人流量表现好 |

新页面「协作管理」的主键是**人 × 岗位**，这是全站唯一的一个。

### 责任模型（阿禅定调，是整页设计的地基）

> **运营对流量全局负责，文案只是参与，达人只是辅助。**

所以三个岗位**不是三张并列的成绩单**：

- **运营** = 责任视角。流量归他，可以拿来考核。
- **文案 / 剪辑** = 产量视角。只看做了多少、给谁做的。流量作参考列展示，**不排名、不归因**——一条视频火了不是剪辑手的功劳，砸了也不是他的锅。

这条规矩决定了后面所有指标怎么排、哪些列能排序、哪些不能。

## 二、数据地基

### 2.1 三个岗位字段从哪来

迁移 `20260727120000_add_submission_operator_user.sql`（线上已执行，阿禅确认）给两张表各加三列：

```
daily_reports.script_author_user_id   文案责任人
daily_reports.video_editor_user_id    剪辑责任人
daily_reports.operator_user_id        运营责任人
videos.script_author_user_id          （同上三列）
videos.video_editor_user_id
videos.operator_user_id
```

写入在 `src/app/api/video-submit/route.ts`，来源是数据上传页的「团队分工」区块。

**全站目前没有任何页面读这三列**（搜过全库，只出现在类型定义、上传表单、提交接口、校验四处）。这页是第一个消费者。

### 2.2 口径决策：统一从 daily_reports 算

两张表都有岗位列，但**必须选一张作为唯一口径**，理由：

1. `daily_reports` 有唯一索引 `(account_id, report_date)`，一个账号一天一条，天然去重；`videos` 无此约束，同一天可能多条，直接计数会重复。
2. 经营分析、成长分析、履约、告警**全部**基于 `daily_reports`。人效页跟着走，跨页数字才不会自相矛盾——「经营分析说这人 12 条，人效页说 15 条」这种事绝不能出现。
3. `daily_reports` 自带 `play_count / likes / comments / shares / favorites / follower_gain / follower_convert`，全是整数，不用 join 快照表。

**`videos` 表只用于一件事**：取 `anomaly_status`（异常/处罚状态），因为 `daily_reports` 没有这个字段。关联方式见 2.4。

> ⚠️ 注意 `daily_reports` 的 `completion_rate / avg_play_duration / bounce_rate_2s / completion_rate_5s` 是 **text 类型**（历史遗留），不是数字。本页第一版不用这几个字段，因此不涉及解析。二期若要用，必须先做类型清洗，不要在前端 `parseFloat` 硬扛。

### 2.3 坑一：岗位默认填自己

`src/app/api/video-submit/validation.ts:81-83`：

```ts
scriptAuthorUserId: input.script_author_user_id ?? currentUserId,
videoEditorUserId:  input.video_editor_user_id  ?? currentUserId,
operatorUserId:     input.operator_user_id      ?? currentUserId,
```

达人不点开「协同指派」，三个岗位全默认他自己。**这是设计如此，不是 bug，不改。**

后果：只要达人图省事不填，这条就算他一个人文案+剪辑+运营全包。剪辑榜会出现「每个达人都剪了自己所有视频」，真正的剪辑手是空的。

**应对**：不改写入逻辑，改成在报表里识别并标注。定义

```
自己包办 = script_author_user_id = video_editor_user_id = operator_user_id = user_id
```

这类记录在文案/剪辑榜里**单独标灰并可一键过滤**，且计入「归属健康度」（见 3.4）。

### 2.4 坑二：两张表没有外键

`daily_reports` 无 `video_id`，`videos` 无 `report_id`。取 `anomaly_status` 只能靠

```
daily_reports.account_id = videos.account_id
AND daily_reports.report_date = date(videos.published_at 或 uploaded_at)
```

这是**软配对，会有配不上的**。处理原则：配不上就当「无异常信息」，不阻断主流程，不报错，不猜。第一版异常状态只在个人卡的明细列表里展示，不参与任何排名或聚合计算——软配对的数据不配上榜。

### 2.5 历史数据的业务事实

那次迁移只加列没回填。**2026-07-27 之前的所有日报，这三列都是 NULL。**

但这不是数据问题，是业务事实：2026-07-27 之前团队实行一人全包，没有分工，所以没有归属数据需要填。从 2026-07-27 起才开始推行分工。

**处理方式**：
- 2026-07-27 之前的记录，归类为「单人全包时期」，不纳入协作管理的统计范围，也不需要补录
- 协作管理页面默认展示当前月，自然不会显示历史 NULL 记录
- 若用户选择到旧月份，提示「该月尚未推行岗位分工」

**归属健康度只盯 2026-07-27 之后的记录**，用这个日期作为统计起点的硬下限。

## 三、页面结构

新建路由 `/admin/collaboration`，导航显示名「协作管理」，放在「经营分析」后面。

顶部：月份选择器（默认本月）。下面四块。

### 3.1 归属健康度（顶部窄条）

放最上面，因为它决定下面三个 Tab 的数字可不可信。

- 本月总条数 / 有归属条数 / 「自己包办」条数及占比 / 未分配条数
- 从不填分工的成员名单（本月所有记录都是「自己包办」的人）
- 没问题时收成一行灰字，有问题时展开成琥珀色提示条

### 3.2 运营 Tab（责任视角，默认打开）

按 `operator_user_id` 分组，每行一个运营：

| 列 | 算法 |
|---|---|
| 运营姓名 | `profiles.name` |
| 带了几个达人 | 他名下记录里 `distinct accounts.profile_id` 计数（从视频反推，见下） |
| 涉及账号数 | `distinct account_id` |
| 本月条数 | 记录数 |
| 总播放 | `sum(play_count)` |
| 人均播放 | 总播放 ÷ 条数 |
| 导粉转化 | `sum(follower_convert)` |
| 爆款条数 | 见 4.1 |
| 环比 | 本月总播放 vs 上月总播放 |

**「带了几个达人」是反推的**，不是配置的：系统里没有「运营管哪些达人」的名册（`accounts` 只挂在达人本人 `profile_id` 下，无运营字段）。反推口径 = 本月他经手的记录涉及哪些账号，这些账号的归属人就是他带的达人。

阿禅已确认：**第一版就用反推，可配置名册留到二期。** 前端要在这一列加 info 浮层写明「按本月经手作品反推，非固定配置」，避免被当成花名册。

点击任意一行 → 展开该运营带的达人列表，每个达人一行（条数、播放、导粉），即「达人各自和总共的流量情况」。

### 3.3 文案 Tab / 剪辑 Tab（产量视角）

两个 Tab 结构完全一致，只换分组字段（`script_author_user_id` / `video_editor_user_id`）：

| 列 | 说明 |
|---|---|
| 姓名 | |
| 本月篇数 / 条数 | **默认排序列** |
| 给谁做的 | 涉及账号列表（超过 3 个折叠为「A、B 等 5 个账号」） |
| 总播放 | 参考值，**列头标注「参考，不代表该岗位成绩」** |
| 人均播放 | 参考值 |
| 「自己包办」条数 | 灰色，可一键过滤掉 |

**排序限制（对应责任模型）**：这两个 Tab 只允许按「条数」排序，播放列**不可点击排序**。前端不给排序箭头。这是产品决策，不是遗漏——一旦能按播放排，就等于给剪辑手排流量成绩单，跟阿禅定的责任模型冲突。

### 3.4 个人卡（点任何人打开）

跨三岗位看一个人本月干了什么。这是阿禅跟人谈话时打开的那一页。

- 头部：姓名、团队/小组、本月三岗位分别多少条（可能一人多岗）
- 运营身份数据（如果他有运营记录）：带的达人、总播放、导粉、爆款、环比
- 产量数据：文案 N 篇、剪辑 N 条、给哪些账号做的
- 近 6 个月条数趋势（柱状，只看产量不看流量）
- 明细列表：本月每条记录（日期、账号、标题、播放、他在这条里担任什么岗位、异常状态）

**复用**：这块组件同时嵌到员工的「数据分析」页（`/growth`），员工看自己那一份。一份组件两个入口，零额外成本，而且员工自己能看到「我这月剪了 12 条」，比催他有用。

### 3.5 补录归属

**背景**：2026-07-27 之前是单人全包时期，那批历史不需要补录（也没有意义补）。补录只针对 **2026-07-27 之后**新产生但填错或漏填的记录。

权限：**仅管理员**（`owner` / `team_admin`）。本人不能改自己那条——否则这页的数字对外没有说服力。

入口只有一个：**单条补录**，放在视频复盘 `/admin/content` 每条视频的操作区。那里本来就是逐条视频的视角，改归属最自然。

去掉「批量补录」——历史不用补，场景不存在了。

**⚠️ 关键技术要求（最容易做错的一条）**：两张表都有岗位列，补录**必须同时更新 `daily_reports` 和 `videos`，在同一个事务里**。只改一张会导致协作管理报表（读 daily_reports）和视频复盘（读 videos）显示不同的责任人，比不做更糟。配对规则见 2.4；配不上时明确回报给操作者「视频侧未找到对应记录，仅更新了日报」，不能静默。

## 四、指标口径（精确定义）

### 4.1 爆款

沿用全站现有口径，**不新造**：

- `src/lib/video-metrics.ts:27`：爆款系数 = 本视频播放 / 基线中位数
- `src/lib/smart-alert.ts:293`：`isHit = playCount >= baselineMedian * 2`

本页定义：**爆款 = 该记录 `play_count` ≥ 该账号在统计窗口内播放中位数 × 2**。

按账号算中位数而非团队，因为账号体量差异巨大（大号随便一条都超过小号的爆款线）。

不要用 `src/lib/趋势图.ts` 的 P70——那是趋势图的对比基准线，不是爆款线，混用会导致同一条视频在两个页面一个算爆款一个不算。

### 4.2 环比

本月 vs 上一个自然月。上月无数据时显示「—」，不显示 0% 或 +∞。

### 4.3 时间窗口

统一按 `report_date` 的自然月。不用 `published_at`——那是运营挑的投放时段，不代表干活时间。

### 4.4 只统计在职成员

`profiles` 状态非 active 的人不出现在榜单，但其历史记录仍计入总数（否则总数对不上）。

## 六、明确不做（第一版边界）

砍掉的标准只有一条：**现在算出来的数字可信吗。**

带岗位归属的历史数据目前是 0 条，从 2026-07-27 开始攒。一个月大概几百条，摊到「文案 A × 剪辑 B」这种交叉格子里每格三五条。三条数据算出来的结论是噪音，发出去会误导排班。

| 不做 | 原因 |
|---|---|
| 最佳/最差组合榜、协同增益 | 样本量不足，交叉格子里数据太稀 |
| 爆款功劳拆解 | 同上，且与「只有运营担责」的责任模型冲突 |
| 派单建议、账号适配推荐 | 依赖上面的统计量 |
| 岗位适配诊断（建议调岗） | 依赖分岗质量指标，阿禅已明确不需要 |
| 分岗位质量指标（剪辑看跳出率等） | 阿禅已否：运营全局负责，文案剪辑不单独背指标 |
| 加班信号 | `published_at` 是投放时段不是工时，口径本身是错的 |
| 违规责任榜 | 数据现成（`anomaly_status`）但容易变成甩锅工具，挪二期候选 |
| 可配置的运营-达人名册 | 阿禅确认二期做，第一版反推 |
