# 发现

- `AGENTS.md` 已有调用链、精准修改、根因回溯、死代码、维护性门禁等要求，但分散在多个章节，且“最小改动原则”容易被理解为只看局部。
- `docs/DYData产品全书.md` 是文档唯一索引；`docs/系统架构与设计/全站模块与数据关系.md` 和 `工程运行事实.md` 是长期事实入口；`docs/通用管理/文档与维护规范.md` 负责目录和写入规则。
- `docs/plans/` 当前积累大量在办/历史混合文件，存在提示词、方案、执行规格、验收记录同层并存的问题；不能未经引用扫描直接删除。
- `docs/reference/` 主要是线上核对和完成记录，但数量很大，需按入口、事实、历史证据分别治理。
- 现有项目已经有 `docs/系统架构与设计/架构决策/`，适合承载稳定的架构决策，不应再把同类长期事实散落到计划文件。

## 冲突初筛（2026-10-31）

- `AGENTS.md` 的原“最小改动原则”已改为“先看全局机制、再定局部改动”；本轮仍需检查其他文档是否保留会把它解释成局部视野的表述。
- `docs/DYData产品全书.md` 已把“唯一规则来源”纳入模块定位，并新增高频高风险模块地图入口；还需要补 `docs/系统架构与设计/架构决策/` 的正式目录定位。
- `docs/通用管理/文档与维护规范.md` 已明确 `docs/reference/reviews/`，但当前目录是否存在、是否仍应保留，需用文件清单和引用扫描核对。
- `docs/系统架构与设计/架构决策/` 已存在稳定决策文档，但当前产品全书和文档维护入口没有完整说明其边界，存在长期事实与架构决策重复落点风险。
- `docs/plans/README.md` 已规定计划归档，但计划根目录仍有大量提示词、方案、规格书和一次性调查，需要先按引用和最后修改时间分组，不能直接批量删。

## 四层方案对照结论（2026-10-31）

| 层 | 结论 | 现有落位 | 处理建议 |
|---|---|---|---|
| L0 Agent 规则 | 必须保留，已完成第一轮重构 | `AGENTS.md` | 只放原则、前置判断、边界、验收和入口，不继续塞操作细节 |
| L1 工程维护规范 | 现有文件没有完整承载 | `工程运行事实`=事实，`后端工程规范`=后端写法，`文档与维护规范`=文档治理 | 新增一个短文件 `docs/系统架构与设计/工程维护规范.md`，不新增文件夹 |
| L2 系统架构与业务逻辑 | 已有骨架，但模块地图和唯一来源不完整 | `docs/业务逻辑/`、`全站模块与数据关系`、`工程运行事实`、ADR | 高风险模块先补到现有长期事实入口；不另建 `页面功能` 体系 |
| L3 产品索引 | 应保持唯一 | `docs/DYData产品全书.md` | 只加场景路由，不写规则正文；README/维护规范只作指针 |

### 明确减法

- `docs/页面功能/` 不纳入核心知识层；现有 `/admin/content` 说明与架构/业务事实重复，且内容已过时。后续按引用扫描后归档或删除，不把它扩展成新体系。
- 不把工程维护方法塞进 `工程运行事实` 或 `后端工程规范`，避免事实、后端实现和跨领域维护流程混成一份大文档。
- 不新增“模块地图”文件夹；首批模块地图先写入现有 `全站模块与数据关系.md`，只有单模块事实明显超过入口承载能力时才拆文件。

## 当前落地结果

- 第二层不新增文件，采用改造后的 `docs/通用管理/文档与维护规范.md`，因为它原本就是跨领域的维护入口；新增方法只覆盖已有系统的理解、变更分类、入口选择、影响面、补丁识别、健康验收和事实回写。
- `工程运行事实.md` 与 `后端工程规范.md` 只保留自身事实/实现职责，并指向维护规范，避免三份文档互相复制工程方法。
- `DYData产品全书.md` 将两条原本重复的维护路由合并为一条。
- `docs/页面功能/` 被确认不纳入核心层；当前未移动或删除文件，等待引用扫描后的独立整理批次。

## 业务逻辑与 reference 的边界

- 业务逻辑是当前生效的规范性事实：产品为什么这样运行、业务规则是什么、异常如何处理；它是施工时的权威来源，必须和代码/真实证据同步。
- `reference` 是证据性资料：某次验收、线上核对、调查、接口快照或历史记录；它可以支撑当前事实，但自身不自动成为规则来源。
- 当前 `docs/reference/` 混入少量仍被施工引用的活体契约，这是目录边界问题，不代表要把整个 reference 并入业务逻辑。
- 稳定业务语义 → `docs/业务逻辑/`；模块职责/调用边界/系统约束 → `docs/系统架构与设计/`；稳定的架构取舍 → `docs/系统架构与设计/架构决策/`；带日期的证据和历史分析 → `docs/reference/` 或 `docs/archive/`；未完成方案 → `docs/plans/`。
- 页面功能说明不再作为独立长期层；其中仍有效的业务规则或模块事实应回写到上述现行入口，剩余内容归档。

## 文件夹减法建议（2026-10-31）

- 当前 docs 顶层存在业务逻辑、系统架构与设计、通用管理、plans、reference、archive、architecture-decisions、reviews、investigation、ux-audit、页面功能等多个分区；对 AI 来说，真正需要直觉区分的是“当前事实”和“历史/证据”。
- 不建议合并 `业务逻辑/` 与 `系统架构与设计/`：前者回答业务必须怎样运行，后者回答系统由谁负责、边界和入口在哪里，合并会重新制造语义重叠。
- 建议将 `architecture-decisions/` 收入 `系统架构与设计/架构决策/`，因为它是架构事实的子类，不是独立知识层。
- 建议将 `reference/`、`archive/`、`reviews/`、`investigation/`、`ux-audit/` 逐步收敛为一个 `留档/` 顶层目录；当前仍有效的接口契约先回写到业务逻辑或系统架构，再移动其余材料。
- `plans/` 保留为唯一在办目录；`通用管理/` 保留为规则、待办和交接；`页面功能/` 不纳入目标结构，先按引用证据归档或删除。
- 目标顶层核心结构：`业务逻辑/`、`系统架构与设计/`、`通用管理/`、`plans/`、`留档/`；另有产品全书作为唯一入口。
