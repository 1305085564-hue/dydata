# 作品日报首次提交后的飞书战报通知

## 目标与完成定义

成员首次提交作品日报且整条核心持久化流程成功后，向现有 `FEISHU_WEBHOOK_URL` 对应的群发送飞书交互式数据卡片。编辑既有日报不重复通知；飞书通道失败不改变提交接口已成功的业务结果。责任人展示当前提交人；未提供指标显示 `-`。

**架构裁定（2026-11-24）：**采用提交成功后的 best-effort 异步播报。只在视频、快照、日报、标签、来源、截图留痕等阻塞写入全部成功后，在成功响应前登记一个不等待的后台 Promise；现有发送器 10 秒超时并吞并网络异常，dispatch 再兜底捕获意外异常，只记录服务端日志，绝不回滚或更改提交响应。明确不建设 outbox、队列或后台 worker；进程终止时可能漏送，暂不提供持久投递和重试保证。编辑不播报；补交若本次 insert 新日报则播报。

## 范围与非目标

- 范围：`/api/video-submit` 首次新增 `daily_reports` 后的通知；卡片构造；异步调用和隔离测试。
- 非目标：新环境变量、新外部依赖、历史补发、编辑通知、修改指标口径或前端表单、数据库 outbox/队列/worker、持久化重试。
- 推荐口径：`mode=create` 与首次 `mode=abnormal` 的新日报都属于首次新增日报；审批补交若最终仍由员工提交接口完成、且服务端确认 `existingReport === null`，按首次提交播报。判断条件以服务端确认 `existingReport === null` 且整条员工提交链成功为准。编辑及冲突拒绝均不通知。

## 现状链路

- 入口：`src/app/api/video-submit/route.ts` 转发至 `route-core.ts` 的 POST。
- 核心写入：`route-core.ts` 按视频、24h 快照、日报、标签、来源、截图替换记录顺序持久化；数据来源写入和截图留痕成功后才返回成功。
- 首次/编辑区分：日报由 `existingReport ? update : insert` 决定；同一处理器的 `existingReport` 来自编辑绑定或新提交判重读取。成功响应唯一位置在 `route-core.ts` 收尾。
- 复用通道：`src/lib/飞书webhook.ts#sendFeishuWebhook` 使用现有环境变量、10 秒超时、明确失败结果且不抛异常；不自动重试以避免超时后重复通知。
- 当前日报写入点审计（代码搜索，非数据库触发器审计）：员工普通/异常首次提交都从 `src/app/api/video-submit/route-core.ts` 走同一 insert；编辑走 update。审批补交完成后最终也进入同一个提交处理器，并由 `consumeApprovedAppealPayload` 清理已用申请数据。`scripts/import-daily-reports.ts` 用 `upsert` 导入；`src/lib/admin-tools/data-correction.ts` 有管理侧 insert；`scripts/seed-roles-test-data.ts` 仅写验收夹具。不得把这些维护/导入写入默认视为员工提交流量并推群。
- `daily_reports` 目前没有通用业务 outbox/通知队列；现有员工写入是一串数据库 REST 请求及失败补偿，不是贯穿整条链的单个数据库事务。日报 insert 后仍会写标签、来源、截图替换留痕，任一步失败会删除/恢复核心行。
- 时间格式：`src/lib/business-time.ts` 为上海业务时间唯一来源。
- Next.js 版本为仓库锁定的 16.3.3；写代码前已读 `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md`，`after` 可用于 Route Handler 的响应后任务，部署运行时需支持 Next.js `after`。

## 已裁定方案

响应后回调（已试验后撤回）可以捕获已经持久化的提交人、账号、作品、发布时间及指标；独立模块可纯函数构造 interactive 卡片。但 `after()` 仍使用同一请求/实例生命周期，也没有持久化重试保证。不能把这个作为满足“绝对安全”要求的已选方案。现留有未接线的卡片构造草稿 `src/app/api/video-submit/feishu-report-notice.ts`，不等于可部署功能。

按架构师裁定采用最小改动：在现有 `route-core.ts` 的成功收尾处调用独立模块 `dispatchFeishuSubmissionNotice`，使用 fire-and-forget 的 Promise，不等待 webhook；通过 `existingReport == null` 区分新建与编辑。它位于截图留痕等全部阻塞持久化步骤之后、成功响应之前。来源仅是员工提交路由，因此导入、管理修复、测试 seed 不会触发；审批补交只要走此路由新建日报就会播报。

不采用请求内直接 await（会拖慢响应）；不在数据库 insert 后立即注册（后续标签/来源/截图留痕失败会补偿回滚，不应为失败提交播报）。best-effort 方案的明确限制是无法抵御进程在后台 Promise 完成前终止，通知可能漏送；产品已接受该限制以避免新增队列和运维复杂度。

## 数据流

链路：成员（包括审批补交）提交 → 权限/业务校验 → 视频/快照/日报/标签/来源/截图留痕落库 → 全部成功 → 若首次日报 insert，则调用不等待的通知 dispatch → HTTP 成功响应；后台调用现有 webhook，失败仅记录错误。编辑 update 不调用；导入和管理写入不经过此员工路由。

## 错误、边界与兼容

- 只有新 insert 日报进入通知；update 编辑、重复冲突和任何已补偿失败均不会通知。
- 所有 `null`、`undefined`、空字符串和非有限数值输出 `-`；数值 `0` 保留。百分比附 `%`，整数保持整数，小数按输入精度展示。
- 发布时间为空/非法显示“未填写/未识别”；提交时间由已创建时的 `nowIso` 格式化为上海时间精确到分。
- webhook 结果 `not_configured/timeout/network/non_2xx` 或意外异常均不改变 HTTP 成功响应，日志不含 webhook 地址或响应正文；投递失败能否重试、重复抑制及任务持久化须在方案评审明确。
- 交互卡片使用飞书 `msg_type=interactive`、`card` 的 header/div/multi-column markdown 等已支持基础结构；新增字段均来自已验证且已持久化的服务端数据。
