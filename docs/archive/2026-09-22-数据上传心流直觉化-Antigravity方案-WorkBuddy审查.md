## 二、主要发现

### F-01（P0）真根因未被发现：界面在主动教员工把「限流」填进豁免

方案把员工点豁免归因于"避责心理"。实测：

```
src/app/(app)/dashboard/redesign/exemption-dialog-v2.tsx:538
placeholder={... : "简述特殊豁免原因，如：账号限流、平台维护、排班调休等（最多100字）"}
```

**豁免弹窗的输入框提示语里，"账号限流"是被列在第一位的示例。** 员工点「豁免申请」→ 选「特殊豁免」→ 输入框浮出"如：账号限流" —— 这不是员工自作主张，是界面照着手教。

更严重的是语义自相矛盾：
- `exemption-dialog-v2.tsx:408` 「特殊豁免（不该交不交）」
- `exemption-dialog-v2.tsx:414` 「特殊豁免适用于按规则本就不应提交的日期」
- `docs/数据口径.md:98` 限流/删稿/投流/活动干预 属于 `abnormal`（异常），**仍须上传数据、计入产量**

即：限流是"该交且已交"，却被 placeholder 引导填进"不该交不交"。

**结论**：只加一句提醒条、不改 placeholder，等于在同一屏里同时说"限流别在这儿申请"和"如：账号限流"。方案第 2 条必须包含 placeholder 改写，否则是自相矛盾的空转。

### F-02（P0）方案第 3 条：改名方向与既有术语体系冲突

方案建议「历史记录」改名「往期手稿」。实测系统内**已经存在**这套词，而且不是"往期手稿"：

| 位置 | 现有文案 |
|---|---|
| `video-submit-panel-v2.tsx:592` | 顶部按钮 = **历史记录** |
| `video-submit-panel-v2.tsx:991` | 点开的弹窗标题 = **历史手稿纪事** |
| `video-submit-panel-v2.tsx:970` | 抽屉标题 = **修改历史手稿 · 日期** |
| `video-submit-panel-v2.tsx:1004` | 空态 = **历史手稿静待立卷** |
| `dashboard-humanistic-copy.test.ts:37-39` | 测试**锁死**「历史手稿」三处文案 |

按方案改名，同一次交互会出现三个名字：按钮「往期手稿」、弹窗「历史手稿纪事」、抽屉「修改历史手稿」；且直接撞红 `dashboard-humanistic-copy.test.ts`。

**结论**：这条不是"改个词"，是术语口径重新裁定。若要统一，应从「历史记录」向既有的「历史手稿」靠，而不是引入第三套「往期手稿」。

### F-03（P0）方案第 4 条：与设计哲学核心信念正面对撞

方案称"创作立卷 / 表达纪事 / 完卷微符 / 停笔调养"是文艺化词汇过度，主张全面换成大白话。

实测，这套词是**写进核心理念的**，不是随手取的：

```
docs/Claude设计哲学.md:10  ### 1.1 人文出版物感 (Editorial Warmth)
docs/Claude设计哲学.md:14  - 装帧细节：引入卷首寄语 (Epigraph)、学者边注 (Marginalia) 与完卷微符 (✦)…
docs/Claude设计哲学.md:4   装帧从来是对郑重的回应，不是表演
```

且这套文案被专项测试锁死：

```
src/app/(app)/dashboard/dashboard-humanistic-copy.test.ts:17-48
  锁定：创作立卷 · 表达纪事 / 停笔调养 / 历史手稿 / 豁免弹窗标题「停笔调养 · 申请请假或特殊豁免」
  并断言：panel 源码不得再出现「申请豁免按钮」「今日提交工作台」等旧词
```

AGENTS.md 规定两份设计文件冲突时"哲学优先"；哲学文档里**没有任何用词条款**（§3「排版与语言」只讲留白四级语义与三条铁律）。

**结论**：方案第 4 条实质是**新增一条设计原则**（"操作类词汇优先大白话，氛围类文案保留出版物感"）。这个提法本身有道理，但它必须先由阿禅裁定并写进设计文档，否则三个 agent 各改各的会持续打架。**不能当施工项，只能当决策项。**

### F-04（P1）工程计划含虚构文件路径

方案列了三处涉及文件，第三个不存在：

```
src/app/(app)/dashboard/components/workbench-header.tsx   ← 不存在
```

实测 `src/app/(app)/dashboard/components/` 下**只有一个文件**：`workbench-notice-bar.tsx`。豁免入口与弹窗的真实位置是：

- 入口按钮：`src/app/(app)/dashboard/video-submit-panel-v2.tsx:573-582`
- 弹窗组件：`src/app/(app)/dashboard/redesign/exemption-dialog-v2.tsx`

前两个路径（`video-submit-form-v2.tsx`、`video-submit-panel-v2.tsx`）真实存在。**结论**：方案至少有一处未核对源码，按此派活会在第一步卡住。

### F-05（P1）把状态标签改成「限流/删稿」，会与已有下拉重复并丢两种类型

方案建议把 `[正常][异常]` 改为 `[正常发布][限流/删稿]`。实测"异常"背后**已经挂着一个处罚类型下拉**：

```
src/app/(app)/dashboard/video-submit-form-v2.tsx:2119-2137
  仅在 anomalyStatus === "abnormal" 时出现
  Select 选项：限流 / 删稿 / 投流 / 活动干预（默认「限流」）
src/app/(app)/dashboard/video-submit-form-v2.tsx:2765-2774
  VIDEO_STATUS_OPTIONS = [{value:"normal",label:"正常"},{value:"abnormal",label:"异常"}]
```

改成 `[正常发布][限流/删稿]` 后，用户看到的是：状态选「限流/删稿」→ 下面又出现一个下拉让你选「限流/删稿/投流/活动干预」。**同级重复，且"投流""活动干预"两类在标签上消失**，员工会问"投流算什么"。

`docs/数据口径.md:97-102` 明确：`abnormal/异常` 是新提交的统一标记，限流/删稿/投流/活动干预是它下沉的 `punish_type` 详情。

**结论**：标签要改，但不能改成一个具体子类型的名字。建议方向（供讨论）：`[正常发布][发布遇阻]` 一类能统摄四种子类型的聚合词，保留下拉做细分。这正是需要阿禅拍板的措辞点。

### F-06（P1）只堵前端入口，没堵审批出口；且对抗的是真实利益

方案的手段是"弹窗首行加提醒条"。但豁免是**审批制**，出口在管理端：

```
src/app/(app)/admin/fulfillment/fulfillment-workbench.tsx   （豁免审批所在页，实测无限流相关拦截）
docs/数据口径.md:179
  应发目标 = 统计范围内自然日数，扣除状态为 leave、waived、exempted 的已批准请假/豁免日
```

即：员工以"账号限流"为由申请特殊豁免，**组长批了 → 应发目标减 1 → 员工当月完成率的分母变小**。这不是认知问题，是能少算一天的**真实利益**。

一条劝导文案对抗利益动机，效果不可靠；而且就算员工被劝回了，**审批侧仍无任何校验**能识别"理由写着限流、类型却是特殊豁免"这种自相矛盾的申请。

**结论**：方案漏了整个出口侧。至少要在审批环节提示"该申请理由与类型冲突"，或从特殊豁免的可申请理由里剔除"限流/删稿"。

### F-07（P1）方案第 6 条前提与实测不符

方案称"界面太安静，员工点完保存不知道生效没，会狂点五六次"。实测：

| 场景 | 实际反馈 | 出处 |
|---|---|---|
| 今日提交成功 | **整页切换**为成功页（不再显示表单） | `video-submit-form-v2.tsx:1887-1975`，结果强可见 |
| 历史手稿修改保存 | **已经弹 Toast**：`feedbackToast.success("历史手稿修改已保存")` | `history-report-edit-form.tsx:726` |
| 草稿自动保存 | 右上角灰字 `已自动保存 HH:MM` | `video-submit-form-v2.tsx:2717` |

且设计文档并非"禁止反馈"，而是分场景规定：

```
docs/Claude设计哲学.md:27     操作成功若结果直接可见，就地更新，省略打扰性弹窗与 Toast
docs/Claude设计规范.md:199    Toast 使用原则：仅在操作结果不可见时使用（结果可见则省略）
docs/Claude设计规范.md:201    时长：3 秒消失 · 单行不超 20 字
```

**结论**：方案描述的"狂点五六次"场景在主表单链路上不存在（整页切换极其明显）。而方案建议的"按钮变绿勾 1.5 秒"属于"就地更新"，**本来就合规，不需要包装成破例**。这条建议先撤回，等有实测证据再谈。

### F-08（P2）成功页加按钮不是"零成本纯前端"，存在未标注的失败分支

方案称"不新增回调/不动接口"。实测编辑态有硬前置：

```
src/app/(app)/dashboard/video-submit-form-v2.tsx:1643-1661
  mode === "editToday" 时必须能解析出 editPayload（来自 editDetail 接口）
  否则：triggerFormShake() + feedbackToast.error("缺少原视频完整详情，已停止保存以避免覆盖旧数据")，直接 return
```

且 `mode` 是 panel 通过 props 下发的（`video-submit-panel-v2.tsx:182,365` 的 `requestedMode`），form 内部改不了。成功页（`isSubmitted=true`）要跳进编辑态，**必须新增一个回调 prop** 让 panel 置 `requestedMode="editToday"`。

更进一步：若刚提交的是"有日报但没绑定视频"的情形（读侧对该情形的设计就是 `detail: null`），切到编辑态会**直接报错、保存不了**。

**结论**：这条可以做，但要标注"需新增一个回调 + 处理无视频详情的降级"，不是"零成本"。

### F-09（P2）漏了补录分支

归档卡片（也就是「微调」所在处）的显示条件：

```
src/app/(app)/dashboard/video-submit-panel-v2.tsx:631
  isPrimarySummaryMode && activeBizDate === today && !submittedViewActive
```

即**只有"今日 + 非补录"才会出现「微调」**。员工今天补交昨天/前天的数据时，这张卡片不出现，「微调」根本不存在。方案把「微调」当作唯一出路来讨论，未覆盖这个分支。
