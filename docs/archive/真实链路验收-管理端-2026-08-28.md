## 8. 问题分级

### Critical

暂无已确认 Critical。

### High

#### H-01：真实 pending 豁免申请未进入负责人审批队列，形成漏审批

- **证据**：数据库只读确认存在 1 条 pending `exemption_request`；申请人是 active 成员但没有 `profiles.team_id`，请求记录保存的团队快照属于负责人当前团队。负责人页面显示“没有待审请假”，Hub 的 `GET /api/exemptions/pending` 返回 200、`{data:[],count:0}`，DOM 显示“审批队列已经清空”。
- **根因**：pending 列表按申请人 ID 与 `activeVisibleUserIds` 过滤。未入团队申请人的 ID 不在负责人当前团队可见集合中；仅有 request 的 team snapshot 不足以进入当前 scope。该过滤是安全的，但与现有脏/孤立业务数据组合后把合法待审批事项隐掉。
- **影响**：负责人会认为队列为空，批准请假不会进入审批；会同时影响发布目标扣减、Hub、月历和跨页状态闭环。
- **处理**：未修复。不能为了让这一条出现而直接按 request.team_id 放宽 API，否则可能把跨团队或伪造团队快照变成可见。需要业务确认孤立申请的归属策略，再用可恢复数据修复归属并回归 allow/deny。
- **层级**：预存数据异常/止血未完整；当前验收必须不通过。

#### H-02：文档中的 leader 测试账号实际是 member，真实 admin 正向验收被阻塞

- **证据**：leader 账号真实认证成功，但数据库 `role=member`、`company_role=member`；访问三个管理 URL 均显示无权限。成员账号同样是 active 但未入团队。没有可用的真实 admin/leader 正向账号。
- **影响**：无法真实验证 admin/leader 的允许矩阵、跨团队拒绝、审批写入和模块保存；静态测试 52/52 通过不能代替真实角色证据。
- **处理**：未重置密码、未改 role、未改 team、未改变权限。需要补齐与数据库事实一致的可恢复 admin/leader 测试数据后重跑。
- **层级**：预存测试数据/账号阻塞。

### Medium

#### M-01：发布管理对同一 Hub 事件注册了两次相同的月历刷新

- **证据**：`src/app/(app)/admin/fulfillment/fulfillment-workbench.tsx` 对 `detail.source === "command-hub"` 连续存在两次 `void refreshVisibleCalendar()`。
- **影响**：一次审批事件可能触发两次月历读取，造成重复请求和短时状态竞争；不直接放大权限，但会削弱“单次审批、单次同步”的可观测性。
- **处理**：未修复。本轮不是 P0/P1，且用户要求验收为主；建议后续删除重复监听并补事件调用次数测试。

#### M-02：模块页的“全部范围”展示与当前有效范围语义可能不一致

- **证据**：页面对 raw `data_scope=all` 显示“全部范围”；当前权限实现对 `company_owner` 默认使用当前团队，只有 group mode 才允许全组范围。负责人页面同时显示当前团队“深圳二部”。
- **影响**：后端 scope/目标测试未显示越权，但管理者可能据 UI 误判自己正在查看/修改全公司范围，产生权限错配和操作风险。
- **处理**：未修复。需要先确定展示的是 raw 配置还是 effective scope，再统一文案和接口返回；不能在未确认语义时扩大 owner/admin 范围。

## 10. 最终结论与后续放行条件

**结论：不通过。**

当前本地版本的页面收敛、`published_count` 口径、旧反馈对象清理、无权限拒绝和大数据只读加载基本成立；但“负责人不能漏审批”是本次验收的核心目标，H-01 已在真实数据库、接口 200 空结果和 Hub DOM 三处同时复现，因此不能给出“通过”或“有条件通过”。H-02 又使真实 admin/leader 正向链路无法闭环。生产环境因版本不可证也保持“生产未验收”。

重新验收至少需要：

1. 先由业务确认孤立 pending 申请的归属策略；使用可恢复测试数据修复/补齐团队归属，不直接放宽列表 scope。
2. 提供数据库事实为 `admin` 或 `company_owner` 的有效测试账号，并分别提供 active、archived 的安全测试样本；不修改真实成员。
3. 在确认后执行一次可恢复的单条审批，并核对请求、响应、`exemption_request`/`exemption_grant` 持久化、Hub 消失、月历/目标同步、刷新后不复现；再做批量全成功、部分失败、网络失败。
4. 修正 M-01 重复刷新并确认 M-02 的 effective scope 文案语义，然后重跑 allow/deny、跨团队和伪造 ID 回归。
5. 为生产提供可核验提交 SHA 或部署记录，再在生产完成同样的最小只读链路。

本轮没有发送外部通知，没有永久删除，没有数据库 migration，没有真实权限/归档/恢复/批量审批变更；浏览器最终会话处于成员测试账号的工作台，未再执行密码重置或权限恢复操作。
