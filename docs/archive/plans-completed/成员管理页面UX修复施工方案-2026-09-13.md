## 二、P0 问题（必须马上处理）

### P0-1：数据范围是伪接口 — 保存成功但完全无效

**问题描述**（千问 + Luna 一致）：
- 抽屉里"仅自己 / 同团队 / 全公司"可以保存，Toast 提示"数据范围配置已保存"
- 但后端 [data-access-scope.ts:62](../../../src/lib/data-access-scope.ts:62) 第一行就 `void configuredScope`，直接丢弃
- 实际范围完全由角色推导：组员=只看自己，组长=看本团队，老板=看全公司
- **列表页显示的是数据库配置值（[admin-modules.ts:346](../../../src/app/(app)/admin/modules/admin-modules.ts:346)），但运行时用的是推导值**
- 结果：老板把某组员设为"全公司"，列表显示"全部范围"，保存成功，但该组员登录后依然只能看自己的数据

**为什么是 P0**：
- 显示、操作、事实三者脱节，用户以为改了权限，实际没改
- 这是千问说的"禁止伪接和伪造"红线，属于信任问题

**修复方案**（阿禅决策：方案 A）：
承认"范围由角色决定"这个事实，把数据范围区块改成只读展示（跟"功能权限"区块一样），消除假操作。

**施工规格**：

**文件**：[modules-content-v3.tsx](../../../src/app/(app)/admin/modules/modules-content-v3.tsx)（成员抽屉部分）

**改动位置**：抽屉内的"数据范围"区块（大约在 L733 附近，具体行号可能因上下文不同略有偏移）

**具体做法**：

1. **删除三个单选按钮和保存按钮**：
   - 找到当前渲染"仅自己 / 同团队 / 全公司"单选的代码块
   - 删除整个可交互的 Radio Group 或 Select 组件
   - 删除"保存数据范围"按钮及其关联的 `handleSaveDataScope` 函数

2. **改成只读展示**：
   - 参考现有的 [member-permission-editor.tsx:107](../../../src/app/(app)/admin/components/member-permission-editor.tsx:107)（功能权限区块的只读样式）
   - 展示格式：
     ```tsx
     <div className="rounded-xl bg-[#F7F7F6] border border-[#E2E2DF] p-4 space-y-2">
       <div className="flex items-center justify-between">
         <h4 className="text-[13px] font-medium text-[#1C1917]">数据范围</h4>
         <Badge variant="secondary" className="text-[11px]">按角色自动派生</Badge>
       </div>
       <p className="text-[12px] text-[#78716C] leading-relaxed">
         数据范围由成员的角色身份自动决定，无需单独配置：<br/>
         • 组员：仅看自己的数据<br/>
         • 组长（管理层）：看全公司数据<br/>
         • 老板（公司所有者）：看全公司数据
       </p>
     </div>
     ```

3. **删除数据库写入逻辑**：
   - 如果当前有 `updateMemberDataScope` 或类似的 server action，保留但标记为 deprecated（以防其他地方还在用）
   - 抽屉里不再调用这个 action

**验收标准**：
- [ ] 抽屉打开后，数据范围区块是灰色只读展示，没有任何可点击的单选按钮或保存按钮
- [ ] 文案清楚说明"数据范围由角色自动派生"
- [ ] 保存成员其他信息（如团队、角色）时，不会触发数据范围的 Toast 提示

**一键回滚**：
```bash
git checkout HEAD -- src/app/\(app\)/admin/modules/modules-content-v3.tsx
```

## 三、P1 问题（发布前应修）

### P1-1：批量调配"部分失败"时，页面显示假状态

**问题描述**（千问 P1-2 + Luna P1-2）：
- 批量调配是逐个串行调用（[modules-content-v3.tsx:548](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:548)）
- 一旦有失败，前端把**整个列表回滚到操作前**，但后端已成功的成员**真的调走了**
- 且不刷新页面，导致页面显示的团队和真实数据不一致
- 管理员看到"部分成员调配失败"，以为没生效，实际一半已经变了

**对比**：批量归档的处理是对的（保留成功、只报失败数）

**修复方案**：
批量调配失败时，同样保留成功部分、刷新真实数据，并列出失败的是谁。

**施工规格**：

**文件**：[modules-content-v3.tsx:548](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:548) 附近的批量调配逻辑

**具体做法**：

1. **改成逐人记录结果**：
   ```tsx
   const results = await Promise.all(
     selectedMembers.map(async (memberId) => {
       try {
         await updateMemberTeam(memberId, targetTeamId);
         return { memberId, success: true };
       } catch (err) {
         return { memberId, success: false, error: err.message };
       }
     })
   );
   ```

2. **成功的保留，失败的报告**：
   ```tsx
   const succeeded = results.filter(r => r.success);
   const failed = results.filter(r => !r.success);
   
   if (succeeded.length > 0) {
     // 刷新列表，显示真实状态
     router.refresh();
   }
   
   if (failed.length > 0) {
     const failedNames = failed.map(f => {
       const member = memberProfiles.find(m => m.id === f.memberId);
       return member?.name || "未知成员";
     });
     feedbackToast.error(
       `调配失败 ${failed.length} 人`,
       { description: `失败成员：${failedNames.join("、")}` }
     );
   } else {
     feedbackToast.success(`已成功调配 ${succeeded.length} 位成员`);
   }
   ```

3. **删除全量回滚逻辑**：
   - 找到当前的 `setMemberProfiles(prevProfiles)` 回滚代码
   - 删除，改成只刷新列表

**验收标准**：
- [ ] 批量调配 3 人，假设第 2 人失败，第 1、3 人成功
- [ ] 页面自动刷新，列表显示第 1、3 人已调到新团队，第 2 人还在原团队
- [ ] Toast 提示"调配失败 1 人：失败成员：张三"
- [ ] 不要出现"整体失败"或"全部回滚"的假象

### P1-2：组长权限前端藏了 + 角色切换零确认

**问题 2.1**（千问 P1-3）：后端允许组长归档/恢复成员，前端把入口藏了
- 后端 [member-lifecycle.ts](../../../src/lib/admin/member-lifecycle.ts) 明确允许组长归档成员
- **关键理解**：组长不是"某个团队负责人"，而是**管理层职级**，管理全公司成员
- 但前端归档按钮和恢复按钮都只给 `isCompanyOwner` 显示
- 导致组长（团队管理员）无法行使归档权

**问题 2.2**（千问 P1-4 + Luna P1-3）：角色切换零确认，一键生效
- "提升为组长 / 降为组员"点一下就立即执行（[modules-content-v3.tsx:1583-1597](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:1583)）
- 组长身份直接携带成员管理权，这是权限升级操作
- 降级还会**静默清空该成员的功能权限**，用户完全不知情
- 归档有确认弹窗，但角色切换没有，风险控制不一致

**修复方案**（阿禅决策）：
- 组长权限：前端放开，且**不限团队范围**（因为组长是管理层，管全公司）
- 角色切换：加简单确认弹窗（不做完整的"影响范围"确认页）

**施工规格**：

#### 改动 1：组长归档/恢复权限放开

**文件**：[modules-content-v3.tsx](../../../src/app/(app)/admin/modules/modules-content-v3.tsx)（归档按钮和恢复按钮的条件渲染）

**具体做法**：

找到归档按钮的渲染条件（大约在成员抽屉底部"危险操作区"）：
```tsx
// 改前
{isCompanyOwner && (
  <Button variant="destructive" onClick={handleArchive}>
    归档成员
  </Button>
)}

// 改后
{(isCompanyOwner || isTeamAdmin) && (
  <Button variant="destructive" onClick={handleArchive}>
    归档成员
  </Button>
)}
```

同样找到恢复按钮（在归档视图的成员行或抽屉里）：
```tsx
// 改前
{isCompanyOwner && (
  <Button onClick={handleRestore}>恢复成员</Button>
)}

// 改后
{(isCompanyOwner || isTeamAdmin) && (
  <Button onClick={handleRestore}>恢复成员</Button>
)}
```

**注意**：不加"该成员在我团队"的限制，因为组长是管理层职级，管全公司成员。

#### 改动 2：角色切换加确认弹窗

**文件**：[modules-content-v3.tsx:1583-1597](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:1583)

**具体做法**：

1. **找到当前的角色切换逻辑**（"提升为组长"/"降为组员"按钮）

2. **套用现有的 ConfirmDialog 组件**（文件顶部已经 import 了）：
   ```tsx
   // 增加状态
   const [roleChangeConfirm, setRoleChangeConfirm] = useState<{
     memberId: string;
     memberName: string;
     targetRole: CompanyRole;
   } | null>(null);

   // 改按钮点击逻辑
   const handleRoleChangeClick = (memberId: string, memberName: string, targetRole: CompanyRole) => {
     setRoleChangeConfirm({ memberId, memberName, targetRole });
   };

   const handleRoleChangeConfirm = async () => {
     if (!roleChangeConfirm) return;
     try {
       await changeRole(roleChangeConfirm.memberId, roleChangeConfirm.targetRole);
       feedbackToast.success(`已${roleChangeConfirm.targetRole === 'team_admin' ? '提升' : '调整'}成员角色`);
       router.refresh();
     } catch (err) {
       feedbackToast.error("角色变更失败", { description: err.message });
     } finally {
       setRoleChangeConfirm(null);
     }
   };
   ```

3. **添加确认弹窗**（参考现有的归档确认弹窗样式）：
   ```tsx
   <ConfirmDialog
     open={Boolean(roleChangeConfirm)}
     onOpenChange={(open) => !open && setRoleChangeConfirm(null)}
     onConfirm={handleRoleChangeConfirm}
     title={roleChangeConfirm?.targetRole === 'team_admin' ? '提升为组长（管理层）' : '调整为组员'}
     description={
       roleChangeConfirm?.targetRole === 'team_admin'
         ? `即将提升「${roleChangeConfirm.memberName}」为组长。提升后该成员将获得管理层职级，可管理全公司成员、配置权限等。确认继续？`
         : `即将调整「${roleChangeConfirm.memberName}」为组员。调整后该成员将失去管理权限，且当前的功能权限配置将被清空。确认继续？`
     }
     confirmText="确认变更"
     cancelText="取消"
     variant={roleChangeConfirm?.targetRole === 'team_admin' ? 'default' : 'destructive'}
   />
   ```

**验收标准**：
- [ ] 组长登录后，能看到所有成员的归档按钮（不限团队）
- [ ] 点击"提升为组长"，弹出确认窗，文案包含"管理层职级"和"全公司成员管理"
- [ ] 点击"降为组员"，弹出确认窗，文案警告"功能权限配置将被清空"
- [ ] 取消后不执行变更，确认后执行并刷新

### P1-3：列表行不可键盘操作

**问题描述**（千问 P2 + Luna P1-4）：
- 成员行是可点击的 `div`，不是 `button` 或 `link`
- "管理"文字依赖 hover 才出现，复选框也默认隐藏（[modules-content-v3.tsx:1227](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:1227)）
- 现场 AX 树里成员行被识别为普通文本，键盘只能到达复选框，不能通过键盘打开成员详情
- 复选框 14px，触屏基本点不中

**修复方案**：
- 成员行提供明确的键盘入口（role="button" + tabIndex）
- 复选框放大到至少 20px 触摸目标
- "管理"按钮始终可见（不只 hover）

**施工规格**：

**文件**：[modules-content-v3.tsx:1227](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:1227) 附近的成员行渲染

**具体做法**：

1. **成员行加 role 和 tabIndex**：
   ```tsx
   <div
     role="button"
     tabIndex={0}
     onClick={() => openMemberDrawer(member.id)}
     onKeyDown={(e) => {
       if (e.key === 'Enter' || e.key === ' ') {
         e.preventDefault();
         openMemberDrawer(member.id);
       }
     }}
     className="..."
   >
   ```

2. **复选框放大触摸目标**：
   ```tsx
   // 改前（假设当前是 14px）

   <Checkbox className="size-5" /> {/* 20px，符合 WCAG 触摸目标最小尺寸 */}
   ```

3. **"管理"按钮始终可见**：
   - 找到当前的 `group-hover:opacity-100` 或类似的隐藏逻辑
   - 改成始终 `opacity-100`，或者只在移动端始终显示

**验收标准**：
- [ ] 键盘 Tab 可以聚焦到成员行
- [ ] 按 Enter 或 Space 可以打开成员详情抽屉
- [ ] 复选框在触屏设备上可以轻松点中（至少 20px × 20px）
- [ ] "管理"按钮在非 hover 状态下也能看到

### P1-5：入团审批看不到申请人邮箱 + AI 诊断暴露 JSON

**修复方案**：
- 入团审批卡片显示申请人邮箱

**改动 2：AI 诊断确认改业务语言**

**文件**：[modules-content-v3.tsx:2091](../../../src/app/(app)/admin/modules/modules-content-v3.tsx:2091) 附近的 AI 诊断确认弹窗

## 九、补充说明

### 关于"组长"的业务理解

**重要更正**（阿禅补充）：
- 组长 ≠ 团队负责人
- 组长 = 管理层职级（类似"经理级"）
- 组长权限是管理**全公司**成员，不是"只管自己团队"
- 所以组长的归档/恢复权限**不限团队范围**

### 为什么不做方案 B（顶级重塑）

1. **投入产出比**：成员管理页是低频页面（月用几次），投 1 小时重塑不值得
2. **岗位协同页更值得**：那边是天天用的工作台，重塑那边收益更高
3. **方案 A+ 已经解决核心问题**：抽屉架构倒置、数据范围伪接口、权限口径不一致

### 为什么批量调配不做服务端事务

千问建议"改成服务端批量事务"，但考虑到：
- 当前后端已经是逐人调用，改成事务需要改 server action
- 前端逐人记录结果 + 刷新列表，已经能解决"假状态"问题
- 服务端事务涉及数据库锁和回滚逻辑，风险较高

所以采用"前端记录结果 + 刷新真实数据"的方案。
