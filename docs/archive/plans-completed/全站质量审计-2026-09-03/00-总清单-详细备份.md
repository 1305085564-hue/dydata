# 三、系统级根因

## 1. 豁免审批状态源分散，grant、逐日明细和 profiles 投影不闭环

- 优先级：P0，第一阶段。
- 分类：重构。
- 来源：A1-1、D-01、D-09、D-10、D-13、D-16-2；E-02 作为部署/迁移待核对证据。
- 根因：豁免状态被拆在 `exemption_request`、`exemption_request_date`、`exemption_grant`、`profiles` 投影和多个 RPC/工具函数里；重审只 insert 不激活旧 grant，reopen 只停用本单 grant，手工授予又吞掉 grant 插入错误。
- 为什么系统级：后续任何审批、打回、手工授予、历史 grant 兼容都会继续制造“页面显示已批准，但实际无有效豁免”的错账。

## 2. 视频/日报提交缺少稳定事务边界和本次请求所有权

- 优先级：P0，第一阶段。
- 分类：重构。
- 来源：A3-1、A4-1、A5-1、C2-3、D-03；A4-2 作为只读同型问题。
- 根因：`/api/video-submit` 同时写 `videos`、`daily_reports`、标签、话术记录，失败时靠补偿回滚；回滚只按资源 id 和时间窗判断，不知道哪条数据属于本次请求。历史编辑在缺 `video_id` 时还会退回按 `published_at` 猜视频。
- 为什么系统级：这是核心提交链路，错误后果是作品被误删、误回收或改错视频。

## 3. 全站 Supabase 读取缺统一可靠取数契约

- 优先级：P1，第一阶段。
- 分类：重构。
- 来源：A1、A2、A5，另含 C2 的重复表象。
- 根因：部分查询只取 `data` 不看 `error`，部分列表无稳定排序、无分页或默认依赖 Supabase 1000 行上限。
- 为什么系统级：同一模式已出现在 growth、admin/content、topics、AI 分析、admin tools、rewrite、team join 等多个模块。

## 4. 业务日期、发布时间和默认日期没有统一上海时区入口

- 优先级：P1，第一阶段。
- 分类：重构。
- 来源：B3、E-01。
- 根因：`toISOString().slice(0,10)`、本地 `new Date()`、UTC 格式化和上海业务日工具混用；作品发布时间还把用户输入的上海时间存成 UTC 字面值。
- 为什么系统级：日报归属日、发布时间、发布管理月份、导出范围、洞察周期都会被边界时区影响。

## 5. 豁免逐日模型上线后，旁路消费方和旧 RPC 未收口

- 优先级：P1，第一/第二阶段交界。
- 分类：重构。
- 来源：D-05、D-08、D-15、B4-3。
- 根因：逐日审批已经上线，但 dashboard、remind、申请重叠校验、fallback 和旧整单 RPC 仍按整单区间或旧投影理解豁免。
- 为什么系统级：同一个“某天是否豁免/待审批/可重提”规则在四处各写一遍，修单页会继续漏。

## 6. 权限与数据库安全收口缺门禁

- 优先级：P1，第一阶段。
- 分类：局部修复为主，补静态门禁。
- 来源：D-06、D-07、D-16-1、D-16-3、D-16-4。
- 根因：权限写路径未统一清缓存；新表 RLS/revoke 依赖人工记忆；部分低风险入口只靠内层 switch 或业务默认值兜底。
- 为什么系统级：权限问题不能只靠“当前路径没有被利用”判断安全，需要用门禁防止下一次新增接口复发。

## 7. 多表写入仍有补偿式半成功模式

- 优先级：P1，第二阶段。
- 分类：重构。
- 来源：A3-2、A3-3、A3-4、A3-5、D-12。
- 根因：注册、豁免申请、rewrite skill、成员生命周期等链路仍是多步写入 + 失败后补偿；补偿失败会留下孤儿或审计缺失。
- 为什么系统级：视频提交是最危险实例，其他模块虽然优先级低一些，但模式相同。

## 8. 业务常量、状态集合和废弃字段缺单一来源

- 优先级：P1/P2，第二/第四阶段。
- 分类：重构。
- 来源：B4、B7、D-11、E-03、D-14。
- 根因：爆款阈值、履约状态集合、日报审核状态、豁免 `status/request_status` 和刷新路径被复制或废弃后未清理。
- 为什么系统级：业务口径会随着页面接入而漂移，旧字段也会误导后续开发。

## 9. 页面 loading 骨架与正式页面布局契约分离

- 优先级：P1，第三阶段。
- 分类：局部修复。
- 来源：F-01、F-02。
- 根因：`loading.tsx` 独立维护旧版版心和旧页面结构，没有与真实页面容器、列布局、`AdminWorkspaceLayout` 宽度形成同一契约。
- 为什么系统级：加载态是每个页面的第一屏，骨架与真实页面脱节会制造高频 CLS 跳动，并且同类 drift 已出现在 dashboard、admin/content、admin/videos。

## 10. 移动底栏、安全区和紧凑卡片操作区缺稳定响应式约束

- 优先级：P1，第三阶段。
- 分类：重构。
- 来源：F-03、F-04；F-16、F-23 作为同域低频浏览器兼容风险。
- 根因：页面级浮动操作条、卡片底栏指标、全局 `MobileTabBar`、`--app-bottom-offset`、`safe-area` 与动态视口没有形成统一约束；局部组件靠 `bottom-6`、`shrink-0` 等硬编码维持布局。
- 为什么系统级：移动端成员批量操作会被底栏压住，topics 紧凑网格可能覆盖操作按钮；这些不是审美问题，而是“按钮是否能点”的可用性问题。

## 11. 前端浮层层级、动态视口和 z-index 缺全站契约

- 优先级：P2，第三阶段。
- 分类：重构。
- 来源：F-08、F-16、F-20、F-21、F-23。
- 根因：活跃代码中有 `z-40`、`z-50`、`z-[60]`、`z-[85]`、`z-[90]`、`z-[100]`、`zIndex:9999` 等多档硬编码；部分弹窗仍使用 `90vh` 或 `min-h-screen`，没有统一到 `dvh`、safe-area 和浮层层级 token。
- 为什么系统级：F-08 原复现路径不成立，但硬编码层级和动态视口不统一会持续制造遮挡、穿透和 iOS 底部裁切。

## 12. 公共 UI 基元、视觉 token、空态和前端死分支多轨并存

- 优先级：P2，第四阶段。
- 分类：重构。
- 来源：C1/C3/C4/C5/C6/C7/C8、B2、B6、F-09、F-10、F-11、F-12、F-13、F-14、F-15、F-17、F-18、F-19、F-22、F-24、F-25、F-26。
- 根因：Button/Input/Select/Table/Toast/EmptyState/ErrorState/状态色/字体规则没有一个足够强的公共实现约束；暗色模式、旧弹窗、旧上传、旧 data-manager 类型引用等历史分支也没有统一清理门禁。
- 为什么系统级：如果不先按组件族收口，后续每个页面都会继续手写按钮、表格、状态色、空态和旧组件判断。

# 四、P0 最终清单

## P0-01 豁免 grant 与投影状态机不闭环，导致已批准豁免静默失效

- 分类：重构。
- 系统级根因：是。
- 来源报告：A、D；E-02 为待核对旁证。
- 原始问题：A1-1、D-01、D-09、D-10、D-13、D-16-2。
- 受影响页面/业务：导航栏豁免审批抽屉、发布管理、首页日历、催交、admin tools 手工豁免、历史 grant 数据。
- 根因判断：审批、打回、手工授予和投影重算不是同一个状态机；唯一索引冲突被 `on conflict do nothing` 或 fire-and-forget 吞掉，profiles 投影可与事实源 `exemption_grant` 分叉。
- 为什么是 P0：会产生“申请显示已批准，但成员实际无豁免”的确定性错账；手工豁免也可能返回成功但 grant 没落库。
- 修复原则：不要在各页面补判断；先收敛 grant 激活、reopen、投影重算和手工授予的单一写入路径，再做存量对账。
- 回归测试要求：
  - 打回后重新批准同一申请：`exemption_request_date`、active grant 数量、profiles 投影、发布管理缺发结果必须一致。
  - 永久豁免批准后打回：不应永久丢失原有临时 grant。
  - 同成员两单并发审批：最终 profiles 投影必须等于 active grant 事实源。
  - 手工授予 grant 插入失败：接口必须返回失败，不能返回 `success:true`。

## P0-02 视频/日报提交与历史编辑会误删、误回收或改错作品

- 分类：重构。
- 系统级根因：是。
- 来源报告：A、C、D。
- 原始问题：A3-1、A4-1、A5-1、C2-3、D-03；A4-2 为同型只读误匹配。
- 受影响页面/业务：员工作品提交、历史手稿编辑、日报统计、视频管理、视频复盘、标签与话术关联。
- 根因判断：提交链路用确定性 video id + 多表补偿式回滚；回滚没有“本次请求所有权凭证”。历史编辑详情加载失败时不阻断保存，缺 `video_id` 后退回按 `published_at` 更新视频。
- 为什么是 P0：触发后可能发生作品数据丢失、作品被错误回收、或同发布时间视频被改错，属于核心数据被错误覆盖。
- 修复原则：提交入口要么走数据库原子 RPC/事务，要么引入服务端可验证的幂等请求 id；历史编辑必须以 `video_id`/绑定校验为唯一修改凭证，禁止按时间猜写。
- 回归测试要求：
  - 两个完全相同 payload 并发 POST `/api/video-submit`：最多一条成功，失败请求不得删除、回收或污染成功请求的数据。
  - 标签或话术记录写入故障注入：不得留下半成功日报/视频。
  - 历史编辑详情加载失败：保存按钮必须不可用或服务端拒绝，不能进入按时间猜视频路径。
  - 同账号同发布时间两条视频：编辑其中一条不得影响另一条。

## P1-02 成员调配与在途豁免申请缺统一归属语义

- 分类：局部修复。
- 系统级根因：是。
- 来源报告：D。
- 原始问题：D-04。
- 受影响页面/业务：成员管理、豁免审批、发布管理待审列表、成员重新申请。
- 根因判断：调配只改成员 `team_id`，审批又要求申请快照团队等于成员当前团队；pending 申请没有迁移、撤销或重提机制。

- 回归测试要求：成员有 pending 豁免时转团队，之后旧团队/新团队审批、成员重提同日期均不得卡死。

- 系统级根因：否。
- 来源报告：D。
- 原始问题：D-02。

- 根因判断：删 `profiles.group_id` 后，`handle_fulfillment_appeal` 未同步改造；plpgsql 建函数不报错，运行 approve 分支才炸。

## P1-04 查询失败被当成空数据或成功结果

- 系统级根因：是。
- 来源报告：A、C。

## P1-06 发布时间和业务日期时区口径不统一

- P0/P1 的根因都能通过状态机收敛、事务边界、统一工具、门禁和定向测试解决，尚未达到“补丁风险明显高于重写”的程度。

- `growth` 和 `content-tools/rewrite` 在模块地图中已有“后续整体重做”业务决策，但本轮审计发现不足以把它们升级为“现在必须局部重写”。本轮只处理必要故障。

# 九、Codex 推荐修复阶段与顺序

F 不作为独立“大前端批次”。正确拆法是：数据安全和权限先行，业务一致性第二，前端可用性第三，纯视觉与清理第四，最后做全站回归。

## 第一阶段：P0 + 会影响后续验收正确性的系统级根因

1. 1A 豁免状态机事实源：P0-01，附带核对 E-02。
2. 1B 视频提交与历史编辑数据安全：P0-02。
3. 1C 可靠数据读取体系：P1-04、P1-05。
4. 1D 上海业务日期与 UTC 存储边界：P1-06。
5. 1E 权限缓存与数据库安全门禁：P1-07、P1-08。

第一阶段默认串行。1A、1B 是最高风险，不建议并行；1C、1D、1E 只有在文件白名单完全不重叠时才允许并行。

## 第二阶段：P1 核心业务一致性

1. 2A 豁免旁路消费方统一：P1-01，依赖 1A。
2. 2B 成员调配与 pending 豁免归属：P1-02，依赖 1A。
3. 2C 履约申诉 RPC：P1-03。
4. 2D 非视频多表写入补偿治理：P1-09，依赖 1B 的事务策略结论。
5. 2E 输入边界统一：P1-10。
6. 2F 业务常量和状态集合收敛：P1-11。

2A/2B 必须等 1A；2D 必须等 1B。2C、2E、2F 可在文件白名单不冲突时并行。

## 第三阶段：前端可用性与公共前端基础设施
