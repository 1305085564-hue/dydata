# G 批开工方案（架构侵蚀 + 重复实现 + 复杂度）

> **执行方**：Haiku 5.5 最大思考  
> **复杂度**：F2-R3（中等复杂度 - 较大工作量）  
> **开工前提**：F 批热点接口测试已覆盖到位（失败路径 ≥80%、鉴权行为 100%）

---

## 一、目标与约束

### 目标
- **#13 架构侵蚀**：热点模块逐个收口，改一处不牵连另一处
- **#14 重复实现**：统一重复逻辑（日期工具、角色判断、发布日规则等），一份权威实现
- **#18 复杂度**：降低理解和修改成本，不为数字好看大面积重写

### 施工红线（Haiku 5.5 必须遵守）
1. **每次只收一个模块**，不做跨模块大重构
2. **每次改动不超过 3 个文件**
3. **改完必须验证**：`npm test` 全绿 + `npm run build` 通过 + 推送门禁全绿
4. **不准"顺便"做任何未在清单内的重构**
5. **每个模块收口完成后，交回阿禅确认再继续下一个**

## 三、施工步骤（逐个模块收口）

### 阶段一：上海日期工具统一（优先级高）
**目标**：10 处各自实现收口到 `loaders/shared.ts`

1. **盘点现状**（只读）
   - `grep -r "getTime.*28800000\|new Date.*'Asia/Shanghai'\|toLocaleString.*timeZone" src/` 找出所有上海日期实现
   - 列出每处的调用场景和当前实现差异

2. **选定权威实现**
   - 从 `loaders/shared.ts` 现有工具中选最完整的一份作为基准
   - 如无合适，新建一个通用函数（如 `getShanghaiDate()`、`formatShanghaiDateOnly()`）

3. **逐个替换**
   - 每次改 1-3 个调用点，改完立即验证：
     - 单元测试通过
     - 用上海午夜边界、发布日与归属日错位、无发布日历史样例对照结果
   - commit 一次，注明"统一上海日期工具 - 第 N 批"

4. **验收标准**
   - 全站只剩 `loaders/shared.ts` 一份上海日期工具
   - `npm test` 全绿
   - 所有日期边界样例对照通过

### 阶段二：角色字符串判断收口（优先级中）
**目标**：散落的 `role === 'admin'` 等判断收口到统一函数

1. **盘点现状**（只读）
   - `grep -r "role.*===.*'admin'\|role.*===.*'editor'" src/` 找出所有角色判断
   - 列出每处的判断逻辑和上下文

2. **选定权威实现**
   - 从现有 `requireAdminActor`、`requireAdminContext` 等鉴权函数中提取通用判断
   - 或新建 `isAdmin(actor)`、`isEditor(actor)` 等纯函数

3. **逐个替换**
   - 每次改 1-3 个调用点，改完立即验证：
     - 鉴权测试通过
     - 权限边界样例对照通过
   - commit 一次，注明"统一角色判断 - 第 N 批"

4. **验收标准**
   - 角色判断收口到少数几个函数
   - `npm run test` 全绿
   - `route-auth.coverage.test.ts` 通过

### 阶段三：发布管理两套汇总合并（优先级低，可选）
**前提**：用户反馈数字跳动时再做

1. **盘点差异**
   - 对照页面加载汇总 vs 乐观更新汇总的"未确认天数"和"连续缺勤"算法
   - 用真实数据验证差异场景

2. **选定统一算法**
   - 与阿禅确认以哪套为准
   - 改另一套逻辑，保持接口不变

3. **验证**
   - 乐观更新后数字与刷新后一致
   - commit 一次，注明"统一发布管理汇总算法"

## 四、架构侵蚀防护（改到哪收哪）

### 触发条件
改动触及以下热点模块时，先收口再改功能：

| 模块 | 已知耦合点 | 收口方式 |
|---|---|---|
| `video-submit` | 多次返工，逻辑分散 | 提取共用逻辑到 `route-core.ts`，保持接口稳定 |
| `ocr-screenshot` | 11-07 故障，类型错误被 catch 吞 | 补失败路径测试，明确异常处理边界 |
| `admin/ai-config` | 11-05 大改版，口径重整 | 保持数据契约文档同步 |
| `admin/collaboration` | 多报表口径曾不一致 | 统一用 `getPublishedDateForStats()` |

### 施工纪律
1. **改功能前先读现状**：`Read` 相关文件，理解调用链
2. **只改必要的**：不"顺便优化结构"、不提前抽象
3. **改完必须回归**：跑全量测试 + 门禁
4. **commit 分开**：收口一次 commit，功能改动另一次 commit

## 五、验收标准（G 批整体完成）

| 项 | 标准 | 验证方式 |
|---|---|---|
| 上海日期工具 | 全站只剩 `loaders/shared.ts` 一份 | `grep` 搜索，无散落实现 |

| 构建通过 | `tsc` + `npm run build` 无错 | 自动门禁 |
| 推送门禁 | 6 步全绿 | 自动执行 |
| 热点模块耦合 | 改到的模块逻辑清晰，调用链单向 | 人工复核 |

## 六、估算与风险

### 工作量估算
- 上海日期工具统一：约 10 处替换，每处 1 个 commit，预计 10-15 次提交
- 角色判断收口：约 5-8 处替换，预计 5-8 次提交
- 发布管理两套汇总：可选，约 1-2 次提交

**总计**：15-25 次提交，每次提交包含测试验证

### 风险与缓解
| 风险 | 影响 | 缓解 |
|---|---|---|
| 替换后日期边界算错 | 高 | 用历史样例对照，commit 前必须验证 |
| 角色判断改错导致越权 | 高 | 跑 `route-auth.coverage.test.ts`，改完人工复核 |
| 改动牵连其他模块 | 中 | 每次只改 1-3 个文件，改完立即测试 |
| Haiku 5.5 理解错调用链 | 中 | 每个模块收口完成后交回阿禅确认 |
