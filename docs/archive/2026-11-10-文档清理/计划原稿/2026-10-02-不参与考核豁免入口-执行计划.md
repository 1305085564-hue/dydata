# 不参与考核（永久豁免）执行计划

日期：2026-10-02
状态：已有实现返工完成，待真实数据库/角色/浏览器验收
范围：后端、权限、数据链路由 Codex 施工；前端入口由 Antigravity 施工。

## 1. 目标与验收结果

Owner 在成员管理弹窗中可对单个成员打开或撤销“不参与考核”：

- 复用现有 exempt_type = 'permanent'，不新增布尔字段。
- 设置和撤销都只允许 company_owner。
- 设置后立即从应交、缺交类口径消失：履约、日报应发、催交、发布战况。
- 历史日报、历史作品、纯历史统计和详情继续可追溯。
- 设置、撤销都写入 audit_logs，包含操作人、对象、动作、时间和原因/结果。
- 永久豁免优先于临时豁免；撤销永久后，如仍有有效临时豁免，按临时豁免状态恢复。
- Admin 现有临时请假/豁免流程保持不变。

## 4. 选定方案

### 4.1 直接开关

新增 Owner 专用服务端接口（建议单一路由支持 POST/DELETE）：

- POST：传 user_id、reason，校验 Owner 和目标成员范围，调用专用 set_permanent_exemption_owner_atomically。
- DELETE：传 user_id，校验 Owner 和目标成员范围，调用专用 clear_permanent_exemption_owner_atomically；只恢复当前日期有效的 temporary grant。
- 两个动作均由服务端写 audit_logs；审计失败必须按现有审计策略回滚或明确报告“已生效但未留痕”。

理由：符合“Owner 说了算”，不制造 pending 审批单；底层仍使用同一套 permanent grant/profile 投影。

### 4.2 隐藏范围

只改变应交/缺交类视图。历史统计、详情、已提交记录保持可见，避免总数因隐藏造成无法解释。

### 4.3 临时豁免

Permanent 优先。设置 permanent 时按现有 RPC 停用 active grant；撤销时不得把成员强行标回 active，应读取/恢复仍有效的 temporary 状态。若现有 clear RPC 会直接清空所有投影，需要新增或调整原子 RPC，使“撤销 permanent 后恢复 temporary”在同一事务内完成。

## 7. 状态流转

active → Owner 设置 permanent → active grant + profile permanent/exempt → 应交类视图排除。

撤销：

- 有仍有效 temporary：active grant temporary + profile temporary/active。
- 无 temporary：无 active grant + profile active/null exemption。

任何 RPC、profile 或审计失败都不能返回假成功；按现有事务/回滚约定报告真实状态。
