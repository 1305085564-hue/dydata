## 根因复核与最小修复方案

### 已确认的根因

1. Preview Function 当前部署在 Vercel `sin1`，COS 桶在广州 `ap-guangzhou`；跨地域 COS 主读存在连接/握手抖动。
2. `src/lib/screenshot-storage.ts` 对 COS 读取固定等待 `3,000ms`，超时后才开始 Supabase 下载。运行日志明确记录 `status=0, reason=cos_timeout`，而 Supabase 回退通常只需 `20–75ms`；因此 A1 p95 和 A2/并发长尾主要由这 3 秒等待造成。
3. A6 授权段日志为 `auth_ms=0`，票据不是当前长尾根因；A2 的 10 张图会同时触发 10 个独立的 COS 主读，3/5 人并发进一步放大跨地域连接抖动。
4. 临时把 `vercel.json` 的 Function region 从 `sin1` 改为 `hkg1` 做 Preview A/B 后，COS 仍几乎全量 3 秒超时，A1 p50 `3454ms`、p95 `3883ms`，A2 `4229ms`；因此“只换部署地域”不作为修复方案。配置已恢复 `sin1`，未提交、未影响 Production。

### 推荐的最小修复

第一刀只改 COS 读取等待和观测，不改 URL、不改数据库、不改权限模型：

- 增加 `COS_READ_TIMEOUT_MS` 环境变量，默认保持现值，Preview 先设 `800ms` 做 A/B；代码把固定 `3_000` 改为读取该值并限制上下界。
- 日志补充 `cos_ms`、`supabase_ms`、`total_ms`、`fallback_reason`，区分 `timeout`、COS 4xx/5xx 和签名错误；不记录路径、票据或密钥。
- 保留同请求 Supabase 字节回退。若 800ms A/B 仍无法满足并发预算，再做第二刀“COS 短预算后与 Supabase 竞速”，不先改成浏览器直连或放宽权限约束。

这套修复的取舍是：COS 慢时更早回退，回退率可能上升，但用户不会再被固定 3 秒拖住；是否接受回退率由重新验收读数决定。

### 重新验收步骤

1. 只部署 Preview，分别用 `COS_READ_TIMEOUT_MS=800` 和基线值跑同一批 30 次 A1、20 次 A2，记录 `cos_ms/supabase_ms/total_ms/fallback_reason`。
2. A1：单图冷请求 p95 ≤ `900ms`、失败 0；A2：10 张总耗时 p95 ≤ `3,000ms`、失败 0。
3. A4/A5：3 人并发 p95 ≤ `1,200ms`、5 人并发 p95 ≤ `1,500ms`，同时记录 COS 超时率和回退率，不能只看 200 数量。
4. 用错误 COS 密钥做故障注入：10 张均 200，SHA-256 与正常 COS/Supabase 样本逐条一致，日志必须出现 `fallback_reason`。
5. 再跑一次真实 Chromium；Safari/WebKit 需补装浏览器后单独验收。所有指标通过后才提交修复；Production 仍需负责人单独审批。
