## 实际遇到的问题及处理

1. pg_dump 16 不兼容来源 PG 17，改用本机 libpq 的 18.3。连接池不传递 PGOPTIONS，目录查询显式使用只读事务；归档由 pg_dump 自身的一致性只读事务完成。
2. 前置批次把策略注释放到了策略创建之前，SQLSTATE 42704；整个批次回滚后调整归类，重跑成功。
3. 后置策略依赖 private 四个权限函数，SQLSTATE 3F000；回滚后从来源只读补取完整定义并先导入，再执行后置批次成功。未通过删除策略绕过。
4. auth.uid() 返回 text，业务 UUID 比较显式转换；auth.users 的 bigint 内部主键不充当员工 ID，所有业务身份继续使用 sub/UUID。
5. 真实账号状态的数据库投影有异步延迟。冻结/恢复只发送一次修改，最多 10 秒有界只读确认；未同步时明确返回待确认，不假报成功。
6. 新管理 SDK 引入不必要的高风险依赖，已移除；仅保留腾讯官方 TC3 ModifyUser 请求。真实调用发现 STS Token 规范头值大小写问题，修复并复测冻结/恢复成功。实际发送的 Token 保留原值。签名依据[腾讯官方文档](https://cloud.tencent.com/document/product/876/34813)。
7. CloudBase 与来源 SQL 上下文默认时区不同；适配器统一请求 UTC 响应，保留同一时间点，未改变业务使用上海日期的口径。

执行批次为 1 个前置、97 个数据、1 个后置，成功写入均保存 RequestId。失败调用的 SDK 未返回 RequestId，明确记录为缺失，未虚构。每批独立事务内同时提交业务 SQL 与回执；连接断开时先查回执，禁止盲重试。1 MiB SQL 请求也已实测成功；没有据此声称已测出平台最大包体或超时上限。

## 权限与转组

- 原 31 个高权限函数按真实调用需求分为 10 个认证业务调用、16 个仅服务端调用、5 个仅拥有者/内部触发器使用；目标所有 public/private SECURITY DEFINER 函数的 anon 可执行数量为 0。
- 三张历史台账保留数据，开启 RLS 并收回 API 角色权限。
- 员工不能通过入团申请或协作管理完成转组。协作管理隐藏调组操作、服务端拒绝旧入口、数据库拒绝绕过写入；具备成员管理权限的管理员通过专用入口重新分配。
- 真实 JWT 验证管理员不能调整管理员、负责人可调整同公司管理员、跨公司/错误工种/员工自调/服务端冒充人工操作均拒绝。
- 排行榜函数收紧为服务端访问，原接口先验证登录及可见人员范围，再过滤结果。没有向普通浏览器开放全公司汇总函数。
