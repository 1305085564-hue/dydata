# COS 新加坡到广州静态数据迁移测速报告

> 日期：2026-10-23
> 目标：验证把可迁移的截图对象从新加坡 COS 复制到广州后，视频复盘等页面同时读取多张图是否会明显变快。
> 范围：只读对照 + 隔离桶复制；未改生产引用、未改数据库、未改 Vercel 配置、未发布。

## 结论

**对象读取层有明显收益，页面整体收益目前不能直接确认。**

同一批真实截图复制到广州后内容逐字节一致。深圳直连对象存储时，10 张并发读取的 p50 从新加坡 **550ms** 降到广州 **127ms**，约降低 77%；p95 从 **809ms** 降到 **250ms**，约降低 69%。

但生产页面不是浏览器直接读 COS：当前链路是“用户 → 新加坡 Vercel 权限校验 → 新加坡服务端读 COS → 返回图片”。真实视频复盘详情页一次观察到两张图片接口耗时约 **1.79s / 2.24s**，其中还包含权限与服务端处理。生产 Vercel `sin1` 到广州 COS 的耗时本轮没有实测，因此不能把对象层的 77% 直接写成页面提速 77%。

## 对象层并发读取

深圳本机直连，源桶和广州桶使用同一批字节，冷启动与热缓存不混在同一轮；每档 3 轮。

| 同时读取张数 | 新加坡 p50 / p95 | 广州 p50 / p95 | p50 变化 |
|---:|---:|---:|---:|
| 1 | 183 / 184ms | 95 / 97ms | -48% |
| 2 | 183 / 183ms | 95 / 114ms | -48% |
| 3 | 184 / 513ms | 109 / 187ms | -41% |
| 5 | 257 / 654ms | 115 / 243ms | -55% |
| 10 | 550 / 809ms | 127 / 250ms | -77% |

当前视频复盘详情页抓到的两张真实图片大小为 195,649B 和 212,375B。复制后 SHA-256 一致；两张并发读取 5 轮的 p50 为新加坡 **235ms**、广州 **130ms**。广州有一次 403ms 尖峰，样本仍小，不能据此承诺稳定 p95。

## 真实页面观察

页面：`/admin/content`，账号为同一只读测试账号。

- 打开当前日期复盘页后点击「花落谁家？」详情，实际加载 2 张截图。
- 两个图片接口分别观察到约 **1.79s、2.24s**；同时发生的授权票据请求约 **1.34s、1.63s**。
- 图片响应头显示 `X-Screenshot-Backend: cos`、`X-Screenshot-Mode: fast`、`200`，说明当前生产确实在走新加坡 COS 主读路径。
- 页面当前仍通过 `/api/submission-screenshots/file` 返回图片字节，浏览器没有直接访问 COS 桶。

## 对迁移决策的影响

如果只把对象复制到广州，而页面继续由新加坡 Vercel 服务端读取，能够确定的收益是“COS 对象下载这一段”可能减少约 100–400ms；权限校验、签发/授权、Vercel 函数启动和页面逻辑仍然存在。按当前两张图的真实接口耗时，页面整体不具备 10 倍提速条件。

要证明生产页面整体是否大幅变快，还缺一项关键实测：在与生产一致的 `sin1` 服务端，从新加坡对象和广州对象分别读取同一批图片，再接入 Preview 的只读开关测完整详情页。这个实验需要临时中转或 Preview 配置，本轮没有修改部署链路，因此标记为 **BLOCKED/待核**。

当前建议：**不要直接把生产截图桶整体切到广州。** 可以继续把“广州作为国内用户直读或边缘分发位置”的方案单独评估；如果保持现有新加坡 Vercel 服务端架构，应优先解决每张图的授权与服务端读取开销，再决定对象地域。

## 复现命令

```sh
set -a; source .env.local; set +a
PERF_ALLOW_COS_TRANSFER=1 COS_TRANSFER_SAMPLE_SIZE=10 COS_TRANSFER_ROUNDS=3 \
  node scripts/audit/cos-region-transfer-probe.mjs
```

脚本只允许新建独立广州测试桶，拒绝写入已存在的桶；测试结束自动删除对象和桶。原始 JSON 输出到 `/tmp/dydata-cos-transfer/`，包含真实对象路径和哈希，不应提交或外传。
