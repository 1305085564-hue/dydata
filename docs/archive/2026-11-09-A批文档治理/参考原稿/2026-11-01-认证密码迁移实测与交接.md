## 一、一句话结论

**CloudBase PG 的 `auth.users.password` 存的是 `base64(bcrypt哈希)`，与 Supabase 的 `$2a$10$…` 同源，只差一层 base64。实测把 Supabase 哈希 base64 后写入即可用原密码登录 —— 84 个账号可以整批迁过去，用户无需改密码。**

官方文档没有写这条通道，属于「文档允许写表 + 未公开存储格式」的组合，不是官方承诺方案。风险边界见第五节。

## 二、官方文档口径（三处，均不支持直接迁移）

| 出处 | 原文要点 |
|---|---|
| 从 Supabase 迁移 → 数据迁移 | 「因 `auth` schema 由平台管理，不直接 dump/restore；建议在迁移期间通过 CloudBase 提供的认证 API 让用户重新激活账号，或与平台运营沟通批量导入方案」 |
| 从 LeanCloud 迁移 → FAQ | 「密码能否直接迁移？通常不能。建议用验证码登录过渡，或设置临时密码引导用户首次登录修改」 |
| 用户管理 API / CLI | 创建用户只接受明文 `password`（8~32 位、至少 3 类字符），无任何 `password_hash` 入参 |

结论：官方立场是「不能迁密码」，且「批量导入方案」的具体形态文档中从未说明。

## 三、实测结论（全部在本日期、本环境取得）

### 3.1 `auth.users` 真实结构（与官方文档不符）

官方文档写 `auth.users.id` 为 `VARCHAR(64)`、与 JWT `sub` 一致。**实测不成立**：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `bigint`（`nextval('auth.users_id_seq')`） | 自增主键，**不是**身份标识 |
| `sub` | `varchar(255)` | **JWT 的 `sub`，`auth.uid()` 来源**，业务关联应指向此列 |
| `password` | `varchar(255)` | 密码哈希，格式 `base64(bcrypt)`，写入后长度 80 |
| `project` | `varchar(64) NOT NULL` | 值 = 环境 ID |
| `status` | `smallint` | 见 3.5 |
| `type` | `varchar` | 平台自建用户为 `internal` |
| `providers` | `jsonb` | 平台自建用户为空数组 `[]` |
| 其他 | — | `email / username / name / raw_app_meta_data / register_info` 等共 35 列 |

约束：仅 `PRIMARY KEY (id)`，**无其他约束、无触发器**。`auth` schema 下另有 `identity` / `authorized` / `client` / `config` / `provider` / `token` / `users_history` 等 19 张表。

### 3.2 平台自己怎么写密码

对合成用户执行 `tcb user update <uid> --password '…'` 后读回：

- `left(password,12)` = `JDJhJDEwJHJT…`
- `length(password)` = **80**

`JDJhJDEwJHJT` base64 解码为 `$2a$10$jR` ⇒ 平台写入的是 **bcrypt 哈希的 base64 编码**。

### 3.3 Supabase 侧格式

生产库 84 个账号的 `auth.users.encrypted_password`：

| 算法版本 | cost | 账号数 |
|---|---|---|
| `2a` | `10` | 84 |

即全部为裸 bcrypt `$2a$10$…`（60 字符），无算法混杂。

### 3.4 正反用例（决定性证据）

| 写入方式 | 登录结果 |
|---|---|
| 裸 bcrypt（Supabase 原格式） | ❌ `400 invalid_username_or_password` |
| `base64(bcrypt)` | ✅ `200`，返回 `access_token`，`sub` 正确；**改用旧密码则 `400`** |

补充验证：

- 36 位 UUID 作 `sub` 可正常登录；JWT `sub` = 该 UUID，`role` = `authenticated`
- `username` 可直接放邮箱字符串，`signInWithPassword({ username: 邮箱, password })` 登录成功 ⇒ 前端「邮箱+密码」体验无需改动
- `password` 置空后登录返回 `PASSWORD_NOT_SET`（4029）⇒ 证明登录路径确实读取该列，可作排障探针

### 3.5 `status` 语义

| 值 | 登录结果 |
|---|---|
| 0 / 1 | 正常登录 |
| 2 | `USER_PENDING`（4012，user not active） |
| 3 | `USER_BLOCKED`（4013，用户被禁用） |

生产库 24 个 `banned_until > now()` 的账号应映射为 `status = 3`。

### 3.6 `identity` 表非必需

平台自建的两个冒烟用户（`dydata_mig_20261101_a/b`）在 `auth.identity` 中**没有任何记录**，密码登录仍正常。⇒ 迁移只需写 `auth.users`，不必构造 identity 行。

## 四、可执行迁移方法

### 4.1 变换公式

```sql
-- 源：Supabase auth.users.encrypted_password（60 字符裸 bcrypt）
-- 目标：CloudBase auth.users.password
password = replace(
             encode(convert_to(src_encrypted_password, 'UTF8'), 'base64'),
             chr(10), ''
           )
```

**踩坑点（必读）**：PostgreSQL 的 `encode(…,'base64')` 每 76 字符自动插入换行，60 字符会产出 **81 字符**（末尾多一个 `\n`），登录必然失败。必须 `replace(…, chr(10), '')` 去掉换行，得到**恰好 80 字符**。此坑已实测复现。

### 4.2 字段映射

| Supabase | CloudBase `auth.users` | 备注 |
|---|---|---|
| `id`（uuid） | `sub` | 必须写这里，`auth.uid()` 才返回原 UUID |
| `email` | `username` **和** `email` | 两份都写，登录用 `username` |
| `encrypted_password` | `password` | 经 4.1 变换 |
| `banned_until > now()` | `status = 3` | 否则 `status = 1` |
| — | `project` | 必填，值 = 环境 ID |
| `created_at` | `created_at` | 直传 |

### 4.3 业务表字段与外键

- 业务表 `user_id` 存的是 Supabase UUID ⇒ 值与 `auth.users.sub` 对应，**不是 `auth.users.id`（bigint）**
- 原 `REFERENCES auth.users(id)` 外键在 CloudBase 建不出来（类型不匹配），需改为引用 `sub` 或直接去掉外键（关闭端自行校验）
- 现有 240 条 RLS 策略中 168 条依赖 `auth.uid()`，因 `auth.uid()` 读 `sub`，策略表达式**无需修改**

## 五、风险边界（必须写进迁移方案）

| 风险 | 说明 | 应对 |
|---|---|---|
| 未公开通道 | 官方文档明确 `auth` schema 平台托管，未承诺 `password` 存储格式 | 工单书面确认；未获答复前保留兜底 |
| 静默变更 | 平台升级若改哈希格式，**不会报错**，表现为新登录陆续失败 | 迁移后 30 天内保留 Supabase 只读备份；准备全量重置脚本 |
| 无 SLA | 该写法不受支持，出问题腾讯不认 | 对外表述统一为「已验证可行，文档未承诺」，不得称为「腾讯官方方案」 |
| 免费版装不下 | 体验版 `tcb user create` 直接报「超过配额限制。授权用户数超过套餐配额上限」（实测） | 认证迁移必须在个人版及以上验证与执行 |
| 复杂度校验被绕过 | 密码复杂度（8~32 位、3 类字符）仅在新设密码时校验，写哈希绕过 | 迁移后不强制改密；如需收紧，另行设计 |
| 真人验证缺失 | 本次仅合成账号验证，未用真实账号 | 批量前必须用 2~3 个真实账号走一遍 |

## 七、Codex 接手后的验收步骤

1. **真人验证**（阻塞项）：取 2~3 个真实账号的 `encrypted_password`，在测试环境按 4.1 写入，用**原密码**走 `/auth/v1/signin` 登录，必须 200。
2. **身份贯通**：用真实 token 访问业务表，确认 `auth.uid()` 返回原 UUID（**不能**用 `ExecutePGSQL` 的 `Role` 参数验证，该参数只切角色不注入 JWT，`auth.uid()` 恒为 NULL，会得到假绿灯）。
3. **封禁映射**：`status = 3` 的账号登录应返回 `USER_BLOCKED`。
4. **批量脚本**：按 50~100 条/批写入（单请求多语句、整批隐式事务，一条失败整批回滚）。
5. **回滚验证**：删除新环境用户不影响 Supabase；Supabase 侧保持只读直到验收通过。
