## 失败与实际修正

- 首次驱动将内部 bigint 读成 JavaScript Number，失去精度，身份替换未命中。只读复核两个原槽位未变化。修正为完整十进制字符串；正式正例验证和恢复均已通过。新计划模块拒绝 Number、超出 bigint 范围的值及跨批重复内部 ID。
- 裸 bcrypt 登录拒绝已观察到。“含换行 base64 必然登录失败”这个负例未独立复现；早期脚本未保存实际响应状态，不能反推平台一定接受或拒绝换行。该失败不计入通过证据。正式正例采用无换行编码，并以其实际成功结果为准。
- 初版离线计划只有生成时查重、整行匹配回退。独立审查指出执行竞态与误删相同行风险，交付版已改为事务内锁表重查、返回真实内部 ID、凭绑定回执生成回退。没有把初版当成可执行成果。

## 交接结论中需要收紧的三处

1. **“84 个可以整批迁”应改为：** 两个既有测试身份已证明原哈希可转换并保留原密码；全量仍要核准配额、冲突、未确认邮箱的映射、平台支持边界及最后快照。当前体验环境只有 3 个身份是实测；最大配额与其他套餐容量不是本轮测定值，不据此购买或绕过限制。
2. **“外键改为指向 sub 或去掉”应改为：** 目标 sub 没有唯一约束，业务列又是 UUID，不能直接建立现有外键。已迁移方案保持不变：14 条身份关联只移除 profiles 根外键，其余 13 条引用 public.profiles(id)，保留关系完整性。
3. **“168 条 RLS 表达式无需修改”应改为：** 身份和业务可见规则不变，但目标 auth.uid() 返回 text，已有 UUID 比较仍需类型转换。不能回退已经验证的 `::uuid` 适配。

官方目前一方面说明 PG 账号表可通过 SQL 操作，另一方面迁移指南仍建议通过认证 API 重新激活或联系平台批量导入；文档还把 id 写成 varchar，与本环境不一致。公开文档没有承诺 password 的 base64(bcrypt) 存储格式。[PG 身份认证](https://docs.cloudbase.net/authentication-v2/auth/auth-pg)、[Supabase 迁移指南](https://docs.cloudbase.net/quick-start/migration/supabase)。因此准确表述是“本环境已实测可行，仍待书面确认长期支持”，不能称为腾讯官方密码迁移方案。

## 脚本交付与验证

新增 `scripts/cloudbase/auth-import.mjs` 与定向测试，调用说明在该目录 README。

- 默认只生成离线计划；没有数据库连接、密钥读取或自动执行入口。完整模式要求 84 条唯一源身份；样本必须显式指定。
- UUID 写 sub，username/email 保留邮箱；bcrypt base64 不含换行。按固定 capturedAt 映射封禁；已确认邮箱写 email_verified=true。**未确认或缺确认信息的选中身份拒绝生成计划**，不会默认激活，也不会悄悄省略第 84 人。
- 每批最多 50 条，锁表后在同一事务内重查冲突。执行方必须另行控制所有 Auth 写入口，不能把预检当成并发保障。
- 真正 INSERT 返回 id::text/sub 后，执行方持久记录内部 ID、计划和批次摘要、RequestId。回退只根据完整匹配回执生成，并按内部 ID、sub、project 与原字段保护。任何字段已变化则保留待处理；没有完整回执不得猜测删除。
- SQL、expectedRows 及 base64 哈希均为敏感资料，只能在 Git 外 700 目录、600 文件保存。只有脱敏摘要和回执进入报告。

主代理命令与结果：`node --test scripts/cloudbase/*.test.mjs` 55/55；两文件定向 ESLint 退出 0；`npm run gate:maintainability` 通过；`git diff --cached --check` 通过。网站代码未改变，不把前一轮网站构建当作本次新增脚本的测试。

还在 CloudBase 的独立 public 合成表实际执行了生成 SQL：50+34 条两批、重复执行拒绝、完整回执绑定回退通过；额外制造的一条“相同字段但不同内部 ID”的外来行未被回退误删。合成表随后删除，整个测试没有向 auth.users 新增身份。此项验证 SQL 执行与恢复边界，**不代表体验套餐已容纳 84 个 Auth 用户**。
