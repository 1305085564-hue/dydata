## 2. 新增业务规则：三层权限设计

**确认口径：员工不能通过入团申请完成跨小队转组。跨小队转组只能由有成员管理权限的管理员/公司负责人，在成员管理中主动重新分配。** 不允许把旧代码注释中的“两入口均可替换”当作本轮新规则。

先区分概念：`team_join_requests.target_team_id`与`profiles.team_id`用于公司归属；公司内业务小队是`work_groups`，归属字段为`profiles.work_peer_group_id`、`work_operator_group_id`，不存在本次假设的work_group_members表。不同岗位槽位的初配和同槽位换组要分别判断。

### 前端

- 员工注册仅选择公司/团队，不选择目标小队。证据：`src/app/(auth)/register/register-form.tsx:196`。
- 加入提示目前只对无team_id、未归档成员显示，证据：`src/app/(app)/_components/join-banner-loader.ts:34`。这只是展示门槛，不能替代服务端限制。
- 成员管理已有受权限控制的小队选择器，证据：`src/components/modules/member-inspector-body.tsx:148`。
- **规则差异已确认：** `/admin/collaboration`的小队抽屉也能换组，候选包含已有其他小队归属的人，加入会覆盖原归属。证据：`work-group-manage-drawer.tsx:200–204、335–340、511–532、586`。这是管理员入口差异，不是普通员工已经能转组的运行证据。
- 后续设计：转组确认与执行集中到成员管理。其他小队视图若保留初配能力，已有归属的成员必须转到成员管理处理；不以可改写的客户端source字段作为权限依据。

### 服务端

- 当前小队写入先按可信权限上下文要求manage_members，并确认操作人/目标成员/目标组属于同一公司。证据：`src/app/(app)/admin/collaboration/work-group-write.ts:31–49`、`src/lib/work-groups/rules.ts:169–210`。
- 当前同槽位换组直接覆盖，且成员管理与协作管理复用相同分配服务。`rules.ts:197–200`和`work-groups.ts:310、391–441`证明不只是首配。
- 后续需要在统一服务中区分“未分配→初配”和“已有A组→B组”。换组只经成员管理对应的明确管理员操作；普通成员、未知入口、跨公司/归档对象拒绝；同组重复请求应不产生多次变更。保留可信操作者、旧组、新组及结果审计。
- 入团申请另有公司级缺口：`join-actions.ts:10–28`只检查登录和目标值，没有检查当前公司归属；`team-join/service.ts:218–224`用service_role查询全部pending，未按管理员公司过滤；`admin/modules/page.tsx:90`消费该结果。审批Action只查manage_members，不能替代对象范围。
- 建议入团仅承接未分配公司成员的首次加入，不赋予换公司/换小队能力；当前已归属成员的变更必须走批准的管理员管理流程。审批再次读申请/成员当前状态，防止申请创建后角色/归属已变而继续处理。

### 数据库

本轮01:41生产目录实读：authenticated只对profiles.name有UPDATE，对team_id和两个小队字段均无UPDATE。直接网关修改这些字段在权限层应被阻止；本轮没有发送修改请求，故不宣称运行测试已通过。

同次目录确认：team_join_requests INSERT策略只要求本人申请、active，没要求当前未分配公司；review_team_join_request仍仅检查is_admin，随后把申请人team_id设为target_team_id，缺少审批人公司与申请目标公司匹配，也没有NULL动作明确拒绝。普通查询RLS的公司条件不能保护绕过RLS的服务密钥或SECURITY DEFINER函数。

后续数据库设计必须保留列级权限；入团策略和审批函数同步校验首次加入、在职、目标公司、申请状态及操作者身份；不让入团流程写小队字段。现有profiles的小队外键只保证组存在，未证明“组所属公司=成员公司”的关系约束。本轮读取到的profiles约束为单列外键，未来可评估组合关系/受控写入口，不能把应用校验说成数据库已独立保证。

service_role本身能绕过RLS，数据库仅凭这把服务密钥无法知道是哪名管理员。现役服务端必须保持登录/功能/对象范围门禁并记录操作者；若下一轮要求库内独立验证人类管理员身份，应设计承接真实用户身份的受控RPC，从auth上下文取身份，不能信浏览器传入的actor_id/role。

## 3. 两名真实测试用户的隔离验收设计

最小设置：A、B均普通在职员工，初始属于不同公司和各自小队。另备公司A的合法管理员M作正向控制；负责人/归档等是额外角色回归，不能用服务密钥代替。隔离库内准备A/B各1条私有探针记录及2个同公司小队A1/A2。所有建号、建探针和写入在下一轮获准后才做。

选用明确“本人私有”的探针或业务表，不把本公司共享只读页面、数据复盘成员特例错误收紧成“任何员工都不能看他人”。共享业务按现行权限真源单独测试。

| 场景 | 操作 | 必须看到的结果/断言 |
|---|---|---|
| 真实身份 | A/B分别登录，以各自access token调无参数invoker身份探针 | uid非NULL、等于对应JWT sub、A/B不同；角色authenticated；不得注入手工claims |
| 本人可读 | A读A、B读B；带条件和不带条件都测 | 各自精确1条，正文/主键正确；不是空列表通过 |
| 他人不可读 | A带B主键、B带A主键；去掉前端过滤 | 0条或明确拒绝；并已由本人正向证明目标行存在 |
| 身份伪造 | A传owner=B、用户ID=B或修改token sub但不重签 | 拒绝；不把前端过滤当授权，不接受伪造token |
| 普通写边界 | A正常写本人；A伪造B创建、更新归属、冲突upsert、删除B | 正常写成功；越权拒绝或0受影响；管理员只读复核原数据未改，不能只看HTTP 200 |
| 直接RPC/嵌套返回 | 各自令牌调用实际保留RPC、嵌套关系查询 | 与表权限等价；SECURITY DEFINER不能扩大对象范围 |
| 无效会话 | 无token、Publishable Key、过期/错误环境/篡改token | 符合目标网关拒绝策略；不使用service_role令牌跑隔离测试 |
| 员工转组UI | A进入成员/小队页面、申请加入入口 | 没有可执行转组入口；初次公司申请不接受小队字段 |
| 员工绕过UI | A直接调用分配Action/API；REST PATCH本人/他人两个小队字段；恶意申请参数 | 拒绝；两个小队归属均原样；直接数据库角色权限也要核对 |
| 管理员合法换组 | M在成员管理主动把A从A1换A2 | 成功且仅对应槽位变化；历史业务归属不被重写，审计记录旧/新/操作者 |
| 其他入口换组 | M从协作管理小队抽屉尝试同一换组 | 按新规则应拒绝执行或引导至成员管理；**当前源码预计允许，未运行** |
| 跨公司管理 | M传B成员或B公司小队，查看/审批B公司入团申请 | 均拒绝；普通列表和高权限路径都覆盖 |
| 审批状态变化 | 无公司用户申请后被分配公司/归档，再审批；NULL动作、重复审批 | 明确拒绝/幂等，不更换既有公司或小队，不产生半完成记录 |
| 并发与恢复 | 两个管理员同时换组/审批，刷新、重试 | 结果一致可解释，无跨公司组合；审计与最终状态对应 |
| 刷新身份 | A/B刷新令牌后重复本人/他人查询 | subject/业务UUID稳定；撤销/禁用按官方定义验收，不能假设旧JWT立即失效 |

执行记录应包含测试编号、版本/环境、令牌A/B标签（不保存原值）、HTTP状态、实际行数、受影响行数、前后状态摘要、网关RequestId、重复次数、失败与未覆盖项。当前以上全部是设计，没有任何CloudBase真实用户隔离测试结果。

## 4. 迁移执行器还缺的设计

1. 请求自包含，不依赖前次PID、临时表、SET或跨请求事务。SQL分割器识别字符串、注释、函数dollar quote，不能按分号直接拆。
2. 每批有固定环境/批次ID、对象manifest和内容hash；执行角色/默认权限显式指定。数据、结构、安全授权分别记录，不默认复制原匿名漏洞。
3. 支持事务的批次在同一请求BEGIN/COMMIT；校验与本批账本同事务写入。因只返回末条结果，末尾返回已提交账本的汇总收据；原SQL错误与无响应分开。不得擅写平台cloudbase_migrations，应用自己的演练账本也需下一轮授权。
4. 超时/断连/InternalError可能是“结果未知”，不是“已回滚”。先从新请求读取账本/目录/数据校验状态；明确已提交则不重放，明确未提交才允许安全重试，仍在执行则等待/停止。唯一批次ID和事务锁等去重机制需实测，避免并发复跑。
5. 包装DO不是通用重试。只有确认语句未生效、语法适合且目标错误可复现时才尝试；CREATE INDEX CONCURRENTLY等不能随意放入事务/DO。序列nextval/setval、外部副作用不能以事务回滚保证恢复。[PostgreSQL序列说明](https://www.postgresql.org/docs/17/functions-sequence.html)
6. 依据UTF-8字节/JSON开销、实际语句成本与锁等待分批，不预设50–100条。分别测SDK/管控/网关角色时限，设置本请求数据库超时与锁超时并留出网络余量；25秒成功不代表25秒安全预算。
7. 按拓扑建类型/扩展/序列/函数/表/约束等；数据导入与触发器副作用有明确顺序。仅回退本批拥有的对象，保留扩展、平台对象和历史数据。禁止整schema清空重来作为默认恢复。

## 5. 工期及费用如何重新测量

2–3天是缩范围/减少网络往返的乐观估算，不是实测。原3–5天同样只是估算，不能靠换回旧范围来充当依据。

下一次演练分别计时：清单/闭包生成、身份映射和RLS适配、结构拓扑导入、真实规模数据导入、索引/约束校验、统计与字段对账、两用户/三角色运行、错误批次定位/重放、恢复、SDK/页面回归。记每步输入字节/行数/语句数、冷/热样本、单批最大值及失败次数。阶段3与认证/生产发布分开估，不拿几十毫秒探针推算工程日。

CloudBase面板“用量0”只能作为当时显示值，可能有计量粒度和延迟；517条pg_stat_statements也不是本项目工作日请求量。记录观测窗口、计量更新时间、空闲/活跃负载与各资源项，不升级套餐，不用定价估算冒充实际账单。预算、停止阈值和计量滞后缓冲在获授权前确定，未定就不压测。
