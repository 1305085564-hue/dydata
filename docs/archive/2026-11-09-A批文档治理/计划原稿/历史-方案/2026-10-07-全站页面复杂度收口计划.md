本计划解决的是“职责混在一起导致真实闭环难以验证”的问题，不以把所有文件压到某个行数为目标。

## 拆分标准

### 必须拆出的情况

只有同时满足“有独立职责”并且至少满足下列一项时才拆出：

- 拥有独立状态生命周期；
- 拥有独立接口、数据库写入、回滚或外部副作用；
- 拥有独立成功、失败、加载中结果；
- 能独立测试；
- 与父页面的修改原因明显不同。

### 不应拆出的情况

- 只为降低行数而切割；
- 抽出后只是 props 中转或一层包装；
- 需要打开更多文件才能理解原来的一个简单流程；
- 模块之间仍共享大量隐式状态；
- 新文件没有独立验收价值。

### 行数的使用方式

行数只作为报警器，不作为目标：

- 页面壳通常控制在 100～300 行；
- 业务控制器或领域服务通常控制在 200～600 行；
- 单一展示组件通常控制在 50～250 行；
- 超过 600 行必须说明为何仍保持内聚；
- 低于约 100～150 行且没有独立职责时不强行拆分。

每次拆分完成后，父文件必须更容易用一句话说明职责，调用链必须更短或更清晰，测试边界必须更明确。

## 每个阶段的执行纪律

1. 开始前冻结本阶段文件和路由范围，其他发现只记入待办。
2. 先写或补最小复现/契约测试，再移动逻辑。
3. 每次只引入一个职责边界，避免同时改视觉、接口和数据口径。
4. 必须分别验证本地静态、真实 API、数据库状态和真实角色页面；测试全绿不代替真实链路。
5. 同一问题最多一次最小修复；连续两次同一路径失败则停止并记录阻塞。
6. 每阶段结束时清理旧实现、更新日志、精确提交文件；不使用 `git add .`、`git add -A` 或 `git add -u`。
7. push 前列出 `git log --oneline origin/main..HEAD` 和差异文件清单，得到明确发布授权后再 push。
