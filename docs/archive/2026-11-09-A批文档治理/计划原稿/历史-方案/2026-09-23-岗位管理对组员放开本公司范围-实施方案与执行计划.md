## 一、目标与边界

### 1.1 目标

组员（`company_role = member`）打开 `/admin/collaboration` 时，看到**本公司全体成员**的岗位数据，覆盖：

- 四个页签（达人 / 运营 / 文案 / 剪辑）
- 首屏汇总
- 个人档案卡
- 作品明细
- 待补归属弹窗
- 「按团队」视图

### 1.2 明确不做

- **不改**全局数据范围：组员在数据分析 / `growth` / 导出 / 工作台仍只看自己。
- **不给**组员任何写权限。
- **不改**视频复盘（`/admin/content`）权限。
- **不动**集团模式（`kind === "all"`）行为。
- **不改** `inferDataScope()`、角色权限模板、RLS、数据库 migration。
- **不激活**既有 `perspective` / `teamId` 请求参数来放宽范围（等于让 URL 改变数据范围，属安全倒退）。

### 1.3 已定行为口径（直接实现，不再讨论）

| 项 | 口径 |
|---|---|
| 归档（离职）成员历史数据 | **对组员可见**，与组长口径一致（含归档行） |
| 待补归属弹窗 | **同步放宽**到本公司；首屏徽标数与弹窗条数必须一致 |
| 文案计费条数 / 绩效核算明细 | **随放宽对组员可见**，本批次不隐藏 |
| 「按团队」视图 | 展示**全公司**花名册与组汇总 |
| 无 `team_id` 的组员 | **安全降级**为只看自己，不报错 |
| 组员点作品 → 视频复盘 | **保留 403 断点**；仅确认提示文案对组员可理解，不得白屏 |

## 三、技术设计

### 3.1 范围解析落在唯一入口 `src/lib/data-access-scope.ts`（先做）

解析函数**不放在** `_shared.ts`，岗位管理模块（页面与接口）只消费结果、**不做任何** `kind` / `team_id` 判断。

新增导出：

```ts
/** 岗位管理模块（/admin/collaboration）的可见范围解析结果。 */
export interface CollaborationScopeResolution {
  visibleUserIds: string[];
  activeVisibleUserIds: string[];
  /** true = 该账号在本模块内仍只看自己（无公司归属的安全降级）。 */
  restrictToSelf: boolean;
}

/**
 * 岗位管理模块的可见范围。
 * 唯一判定处：调用方只消费结果，不得自行判断 kind / team_id。
 * 当前唯一调用方：/admin/collaboration 页面与其只读接口。
 */
export async function resolveCollaborationScope(
  supabase: ScopeSupabase,
  scope: DataAccessScope,
): Promise<CollaborationScopeResolution>;
```

**规则表（唯一判定依据）**

| `scope.kind` | `scope.teamId` | `visibleUserIds` | `restrictToSelf` |
|---|---|---|---|
| `"all"`（集团模式所有者） | — | `scope.visibleUserIds`（原样） | `false` |
| `"team"`（组长 / 所有者） | 有 | `scope.visibleUserIds`（原样） | `false` |
| `"self"`（组员） | **有** | 本公司可见成员 id（**本次新增行为**） | `false` |
| `"self"`（组员） | 空 | `[scope.userId]` | `true` |

`activeVisibleUserIds`：一律取与 `visibleUserIds` 同一批行经 `filterActiveMemberships` 过滤后的 id；`all` / `team` 时沿用 `getActiveVisibleUserIds(scope)`。

**结构同源（必须抽取，不靠口头约定）**

把 `buildDataAccessScope` 现 `kind === "team"` 分支的加载逻辑（`data-access-scope.ts:152-174`）抽成**模块私有**函数，供 team 分支与 `resolveCollaborationScope` 共用：

```ts
async function loadCompanyVisibleRows(supabase: ScopeSupabase, teamId: string) { … }
```

实现要求：

- 函数体 = 现 152–174 行**原样搬运**：并行两查（`profiles.eq("team_id")` + 全量 `profiles` 取 `membership_status, archive_snapshot`）→ 只保留 `membership_status === "archived"` 且 `archive_snapshot.team_id === teamId` 的归档行 → 与队内行合并。
- **`archive_snapshot` 的查询与过滤必须在函数内部保留**（范围口径的一部分）。返回类型只需 `{ id, membership_status }`。
- **不导出** `loadCompanyVisibleRows`。
- `buildDataAccessScope` 的 team 分支改为调用它 → 「组员放宽后的范围」与「组长范围」结构同源。
- 重构后的行为不变性由第 3.1 节与第六节测试独立验证，**不得预先声称“无行为变化”**。

## 六、测试清单

### 6.1 新增断言（7 条，必须全部落地）

1. `resolveCollaborationScope`：`kind="self"` + 有 `teamId` → 返回本公司可见成员 id；**含** `archive_snapshot.team_id` 属本公司的归档行，**排除**他公司归档行。
2. **结构同源**：同一 `teamId` 下，组员解析结果 `visibleUserIds` == 该公司 admin 的 `scope.visibleUserIds`。
3. `kind="self"` 无 `teamId` → `restrictToSelf === true` 且 `visibleUserIds === [userId]`。
4. `kind="team"` / `kind="all"` → 两个集合与 `scope` 原值完全一致，`restrictToSelf === false`。
5. **全局未被放宽（防误用核心）**：`inferDataScope("member") === "self"`；`buildDataAccessScope` 对 member 返回 `scope.kind === "self"` 且 `visibleUserIds` 仍只有自己。
6. **同源消费**：`buildUnattributedResponse` 的范围来源与首屏一致（注入假 `buildPermissionContextForActor`，断言两者拿到同一个 `visibleUserIds`）。
7. **拒绝边界继续成立**：`attribution`（member 403）、`writer-certification`（member 403）、`work-group-write`（member 403）、`work-video`（member 403）。
