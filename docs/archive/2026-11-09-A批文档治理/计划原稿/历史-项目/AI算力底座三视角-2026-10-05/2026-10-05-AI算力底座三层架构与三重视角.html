算力底座三层架构与三重视角

厘清物理专线、供应商归属与型号能力。消灭因底层技术绑定表误导而生的“伪四层”迷障，建立纯净符合业务直觉的三层心智。

“渠道是分组的归属前缀，分组是核心专线，模型是分组下面的具体能力；数据库中的绑定行只是分组与模型之间的技术实现，不构成单独业务层。”

— 阿禅 · 算力底座定调判断

一、架构纠偏：还原真实的业务层级

数据表 ai_provider_key_models 仅记录“某分组挂了某模型”，是纯技术实现绑定，绝不是面向用户的第四层概念。

✗ 技术表倒错的“伪四层” 容易造成认知分裂
渠道 / 供应商 (Provider) └─ 分组实例 (Key) └─ 模型部署 (ai_provider_key_models) └─ 具体模型型号 (Model)

为什么错：将数据表的中间关联记录强行投射到 UI 上，让用户去理解“部署”，造成“分组下面有一层部署、部署下面才是模型”的臃肿与困惑。

✓ 真实业务的“真三层” 心智自然直觉
渠道 / 供应商 (前缀) └─ 分组 / 专线 (核心单元 · 带 Key) └─ 模型型号 (专线支持的能力)

为什么对：供应商只是前缀归属，分组代表一条真实通路的专线与 Key，模型是专线下能跑的具体型号。绑定只是技术关系，业务上只有三层。

核心管理单元

1. 分组 (Group / 专线)

例如 claude、gemini、gpt。代表该渠道下一条配置好的独立专线与一把实体 API Key，承担连通性测试与模型挂载。

具体能力型号

2. 模型 (Model)

例如 claude-sonnet-4-5、claude-haiku-4-5。挂载于分组之下，一个分组可容纳一类或多个型号，具备独立健康状态。

归属前缀

3. 渠道 (Provider / 供应商)

例如 api7、api1。不是核心资产，仅作为命名空间前缀（如 api7 · claude），用以区分不同中转站的同名分组。

✦ 学者边注：数据库 ai_provider_key_models 表无需迁移改表，它在工程上作为多对多外键存在；但在前端呈现、交互逻辑、计划文案与状态汇报中，彻底剔除“模型部署”这一术语，统一表述为“分组名下的挂载模型”。

级联仲裁公式与判据：
  • 模型级别：单个模型不可用或限流，仅标该模型红灯 🔴，不盲目连坐整把 Key。
  • 分组级别：名下部分模型坏显示黄灯 🟡（局部受阻）；名下所有实际挂载模型坏、或分组 Key 鉴权失败显示红灯 🔴（全线故障）；未挂载模型显示灰色 ⚪（未配置供给，不计入健康）。
  • 渠道级别：名下所有分组全绿为绿灯 🟢；有部分分组故障但仍有分组在提供模型算力为黄灯 🟡；渠道下所有实际挂载的模型全部断连才亮大红灯 🔴（渠道瘫痪）。
✦ 渠道为前缀 · 分组为专线 · 模型为能力 ✦
