# AI 配置中心 · 算力底座三视角实施方案

> 日期：2026-10-05
> 范围：AI 配置中心算力底座
> 状态：待施工

## 一、目标

把算力底座统一成一个业务结构和三个查看视角：

```text
渠道
  └─ 分组（一条专线、一把 Key）
       └─ 模型（该分组支持的具体模型）
```

- 分组是核心管理单元。
- 渠道只是分组的归属前缀，用于区分不同供应商下的同名分组。
- 数据库中的 `ai_provider_key_models` 只是“分组挂载哪些模型”的技术记录，不作为单独业务层展示。

## 二、三种视角

### 1. 分组视角（默认）

按分组名称聚合同类专线，并在每个渠道下展示具体分组实例和模型：

```text
claude
├─ api1 · claude
│  ├─ claude-sonnet
│  └─ claude-haiku
└─ api7 · claude
   └─ claude-sonnet
```

同名分组只在展示层聚合；`api1 · claude` 与 `api7 · claude` 仍是两个独立分组实例。

### 2. 渠道视角

按供应商展示完整资产：

```text
api7
├─ default 分组
│  └─ 未挂载模型
├─ gemini 分组
│  ├─ gemini-2.5-flash
│  └─ gemini-3.5-flash
└─ claude 分组
   └─ claude-sonnet
```

该视角必须让用户直接看出每个模型属于哪个分组。

### 3. 模型视角

按具体模型展示供货来源和真实调度顺序：

```text
gemini-2.5-flash
├─ P1：api7 · gemini
└─ P2：api2 · default
```

P1/P2 必须来自实际调度排序，不由前端单独编造。

## 三、状态口径

### 模型状态

- 模型级请求失败：只标记该模型红色。
- 分组自身连接失败、鉴权失败或欠费：该分组下所有模型标记为“随分组不可用”。
- 尚未有模型级探测数据时，页面只能显示“继承分组状态”，不得伪装成独立模型探测结果。

### 分组状态

- 无模型：灰色“未挂载模型”，不计入健康供给。
- 全部已挂载模型正常：绿色。
- 部分已挂载模型异常：黄色。
- 全部已挂载模型异常，或分组自身失败：红色。

### 渠道状态

只统计实际挂载且启用的模型：

- 没有模型：灰色“未配置模型”。
- 部分模型可用：黄色。
- 所有模型不可用：红色。
- 所有模型正常：绿色。

空分组不能抵消故障模型，也不能把渠道从红色冲成黄色。

## 四、实施阶段

### Phase 1：重塑关系展示

目标：先解决“模型到底属于哪个分组”的问题，不改变运行时调度。

- [ ] 以现有 `src/components/compute-tower/` 施工骨架为唯一新视角实现，先核对其数据来源不是演示假数据。
- [ ] 复用 `channel-view.tsx` 的渠道 → 分组 → 模型树，不再另建一套 `group-pool-view.tsx`。
- [ ] 复用 `group-view.tsx`、`model-view.tsx` 和 `perspective-selector.tsx`，统一三种视角的同一份关系数据。
- [ ] 核对旧 `admin/ai-config/components/provider-channel-card.tsx` 与新算力底座的入口关系；确认新入口上线后，再删除或停用旧的底部模型平铺逻辑。
- [ ] 为每个分组显示模型数量、空分组状态和分组级健康摘要。
- [ ] 模型视角来源行明确显示“渠道 · 分组”，P1/P2 使用真实调度排序。

完成条件：在 `api7` 卡片中，模型 1、2 直接出现在它们所属分组下，不再出现在渠道底部统一模型区。

### Phase 2：统一分组命名

目标：避免 `gemin`、`gemini`、`Gemini` 等名称造成错误聚合。

- [ ] 定义标准分组名：`default`、`claude`、`gemini`、`gpt`、`deepseek`。
- [ ] 分组比较统一执行 trim + 小写；对历史别名只做明确映射，不做模糊猜测。
- [ ] 保留自定义分组能力。
- [ ] 将 Key 弹窗文案改为“分组名称”，补充“这把 Key 所属的专线分组”。
- [ ] 不新增“密钥备注”字段；当前 `label` 在本阶段继续作为分组名使用，避免把备注和分组混成两个未落库概念。

完成条件：同名标准分组可以聚合展示，未知或自定义名称不会被错误归并。

### Phase 3：补齐模型级健康链路

目标：让模型红灯有真实数据来源。

- [ ] 先审查现有 `supabase/migrations/20261005210000_ai_provider_key_model_health.sql` 是否已在目标环境真实执行；未执行前不得让新字段成为唯一读取来源。
- [ ] 复用现有 `src/lib/ai/provider-health.ts` 的故障归因，但补齐“未知错误”的展示和回退口径，禁止把未知错误武断归为渠道故障。
- [ ] 复用现有 `test_key_model` 探测入口，按“渠道 + 分组 + 模型”发起最小请求，并补齐成功、失败、超时和未挂载模型测试。
- [ ] 修改运行时失败记录：失败时写入对应模型；只有明确的 Key / 渠道级错误才更新整把 Key。
- [ ] 保留渠道 / 分组级失败记录，用于识别连接、鉴权、欠费等公共故障。
- [ ] 按模型级状态计算分组和渠道的黄、红、绿状态。
- [ ] 为旧数据提供兼容显示：没有模型级记录时显示“继承分组状态”。

完成条件：同一分组下一个模型失败时，只该模型红灯；分组连接失败时，所有模型显示“随分组不可用”。

### Phase 4：操作闭环与清理

- [ ] 在分组行内完成“同步模型 → 勾选模型 → 测试模型”。
- [ ] 测试结果回填到当前模型或分组行，不依赖用户切换其他弹窗查看。
- [ ] 清理“API 密钥分组”等误导性文案，但保留后端字段名兼容。
- [ ] 删除被新视角替代的平铺模型展示和无调用旧组件。

## 六、测试与验收

### 单元测试

- 关系派生：模型只出现在所属分组下。
- 同名分组聚合：`api1 · claude` 与 `api7 · claude` 聚合但实例不混淆。
- 状态汇总：全绿、部分异常、全异常、空分组、空渠道。
- 模型级失败不影响同分组其他模型。
- 分组公共故障会让其下全部模型不可用。
- 调度顺位与运行时排序一致。

### 定向命令

```bash
npx tsx --test "src/app/api/admin/ai-config/**/*.test.ts" "src/lib/ai/**/*.test.ts" "src/lib/ai-config/**/*.test.ts"
npx tsc --noEmit --pretty false
npm run lint
```

### 浏览器验收

使用真实管理员账号检查 `/admin/ai-config`：

1. 默认打开分组视角，三种视角可互相切换。
2. 渠道视角中，模型紧跟在对应分组下。
3. 空分组显示未挂载，不影响渠道故障判断。
4. 同一分组部分模型异常时，模型红、分组黄、渠道按全渠道实际模型数量汇总。
5. 测试、同步、勾选后，当前分组内立即看到结果。

## 七、明确不做

- 不把“模型部署”作为用户可见的业务层级。
- 不在没有后端数据支持时伪造模型级健康状态。
- 不把不同渠道下的同名分组合并成一个可操作实体。
- 不在本次任务中重构业务功能绑定和模型调度策略本身。
- 不顺手清理与 AI 配置无关的历史组件或数据库表。
