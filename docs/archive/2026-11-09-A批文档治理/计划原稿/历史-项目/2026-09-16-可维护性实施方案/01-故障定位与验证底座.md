## 3. 冻结设计

新增核心接口（类型可沿现有风格，但语义不可变）：

```ts
type MutationRoute = "/api/video-submit" | "/api/exemptions/apply" | "/api/exemptions/review";
type MutationStage = "auth" | "validate" | "scope" | "read" | "write-video"
  | "write-snapshot" | "write-report" | "write-tags" | "write-request"
  | "write-dates" | "review-rpc" | "compensate" | "finalize";
type MutationObservation = { requestId: string; mark: (stage: MutationStage) => void };
// observeMutation(route, handler, deps?) => Promise<Response>
// handler 接收 MutationObservation；deps 提供 clock/id/log/capture 便于真实函数测试。
```

- 每请求生成服务器 UUID，响应头用 `x-dydata-request-id`，不采信用户传来的任意字符串；不增加 JSON wrapper、不消费/重序列化响应正文，不覆盖原 Cookie/headers/status。
- 一条完成日志含 requestId、固定 route、method=POST、status、durationMs、outcome、detail.stage、detail.release；detail.release 复用 `getSentryRelease()`。outcome 为 success / rejected / failed / thrown。
- `mark()` 仅记录当前阶段与去重后的阶段序列，后者只写固定枚举；不能触发网络/数据库操作。回滚阶段不能覆盖原失败阶段：同时保留 detail.primaryStage 与 detail.compensationOccurred。这些字段放入现有 detail，不扩大 ApiLogEntry 公共契约。
- handler 返回 4xx 只记正常拒绝日志，5xx 记固定错误分类并捕获一次 Sentry；不把原始 SQL、error.message、对象 ID、正文或截图地址传给新日志通道。
- handler 抛异常：记固定 thrown 日志后原样抛出，让现有全局钩子上报，避免双报；此时不保证诊断响应头，验收单独标明。
- Sentry 采用单次 captureException 的 captureContext 或 withScope，禁止全局 setTag/setUser。两个并发请求各自保有 UUID/阶段，不得串线；核心测试必须覆盖并发隔离。
- 日志或 Sentry 自身失败不改变原响应和原异常。核心使用可注入函数，生产适配使用现有 logger；不要为测试改环境配置。
- 新允许的 Sentry 标签限 `dydata.request_id`（服务器 UUID）、`dydata.stage`（上述枚举）、`dydata.outcome`（固定分类），并保留已有 boundary；错误文本固定为 `mutation_failed`，版本用 SDK release。白名单同时校验键和值，不放行任意 tag/extra。
