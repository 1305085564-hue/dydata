## 一、改造背景与目标

Codex 在底层数据平铺迁移、新接口和全量测试（2116 项全绿）上打好了基础，但在前端交付上存在两处**核心业务断裂**，以及多处违背**出版物级设计哲学**的视觉问题：

1. **业务保障视角被完全做倒且数据缺失**：本该以“业务功能”为第一维度看各业务的安全冗余，被错误做成了“已上架模型列表”；底层 `computeAvailability()` 当前只输出断供业务，健康业务的支撑数据缺失；
2. **存量渠道改名入口完全不可用**：关键的就地改名逻辑被错写在已被弃用的死代码中，阿禅在界面上无法给存量渠道重命名；
3. **死代码清理存在依赖阻断**：`compute-pool-panel.tsx` 仍依赖旧文件中的视角切换器，且专项测试仍直接读取旧文件，必须先迁移解耦再做清理；
4. **视觉噪点与设计规范违背**：私自使用违规的 11px/15px 字号，无意义嵌套带框卡片与重复标题，展开渠道后平铺 6 个小按钮如“电路板”，弹窗使用浏览器原生 confirm 等。

**本次目标**：补齐业务保障全量数据映射，按安全顺序完成解耦与死代码清理，彻底解决业务断裂，将页面视觉提升至 95 分以上的安静、通透、出版物级工作室水准。

## 二、六大改造模块与产品呈现

### 模块 0：业务保障底层数据补齐（引擎层先行）

要让“业务保障”真正反映全站业务的运行状况，底层数据必须补齐健康业务的完整映射：

- **扩展可用性计算（`src/lib/ai-config/availability.ts`）**：
  - 在 `computeAvailability()` 中新增输出 `businessAssurances: BusinessAssuranceItem[]`，覆盖全站所有处于活跃状态的业务功能（如视频复盘、爆款文案、选题库、智能问答等）；
  - 每条记录包含：
    - `key`: 业务唯一标识
    - `label`: 业务中文名称
    - `modelId`: 解析到的实际模型 ID
    - `modelDisplayName`: 完整、可读的模型名称（如 Claude 3.5 Sonnet / GPT-4o）
    - `schedulableChannelCount`: 可调度渠道数
    - `faultChannelCount`: 故障渠道数
    - `totalChannelCount`: 挂载该模型的总渠道数
    - `status`: `healthy`（多条可用且 0 故障）· `degraded`（可用且有故障）· `outage`（0 条可用，彻底断供）
- **保障业务视角只读现有数据，不改动已有逻辑**：原 `affectedBusinessFeatures` 字段保留不变，确保历史引用零回归。

### 模块 1：业务保障视角（视角一）—— 需求侧守护矩阵

把“业务保障”从模型列表纠偏为真正的**业务功能保障看板**：

- **信息架构**：`业务功能名称 → 支撑模型 → 可调度渠道数 / 故障渠道数 → 保障状态与动作`；
- **健康常态（如纸张般安静）**：
  - 业务名称采用 14px 定名墨（`#1F1E1D`）；
  - 支撑模型与所属模块采用 13px 正文墨与 12px 元数据墨清晰呈现；
  - 渠道状态显示类似 `3 条可用 · 0 故障`，数字采用 `tabular-nums` 等宽排版，健康状态使用极淡绿色背景加深绿文字；
- **断供告警（单点聚光灯聚焦）**：
  - 当某个业务解析到的模型可用渠道为 0 时，整行呈现极淡暖红底（`bg-[#C0685C]/5`）；
  - 醒目标注 `断供` 徽标；
  - 右侧提供单点聚光灯主行动按钮 `去换模型`（暖陶土橙描边或轻实底），点击后平滑切换至“供给管理”视图，并自动滚动、居中、高亮聚焦到该模型卡片，指引决策更换。
- **剥除套壳卡片**：
  - 移除内部多余的白底大框和重复标题，直接采用标准发丝线与通透底板排版，彻底消除“卡片套卡片”的压抑感。

### 模块 2：供给管理视角（视角二）—— 供给侧明细与存量定名

让阿禅能够随心掌控每一个模型的渠道来源，并直接给存量渠道重命名：

- **打通存量渠道就地定名**：
  - 在每一个渠道行前，渠道显示名旁提供极简铅笔微符（`size-3`，热区 ≥ 24px）；
  - 点击后原地展开极简输入框（`h-6 text-[13px]`），支持直接修改渠道显示名，按回车或失焦即刻保存，防重冲突中文友好提示；
- **模型行全局上架主开关**：
  - 在模型卡片头部右侧，提供直观的上下架轻开关，随手控制是否上架参与业务调度；
- **渠道供不供此模型的小勾标记**：
  - 在渠道明细左侧提供极简勾选标记，清晰表达“该渠道供不供当前模型”；
- **信息补齐与时间戳**：
  - 渠道明细补充显示“最后成功时间”、“最后失败时间”，让故障与健康有据可查；
- **操作按钮降噪（告别电路板）**：
  - 收敛常态下平铺的 6 个按钮；
  - 常态仅保留健康指示与核心测试动作；
  - 上移/下移排序、同步、删除等低频操作在行内 hover 悬浮显露或收进更多操作微菜单中，常态保持干净清爽。

### 模块 3：动作收口与质感反馈

- **全池模型检测弹窗**：
  - 彻底取缔浏览器自带的原生 `window.confirm`；
  - 接入全站统一的 `ConfirmDialog`，具有温润暖白、衬线标题与出版物级确认文案；
- **三级测试结果抽屉 / 展开条**：
  - 点击“全部检测”或“全部模型检测”后，在工具栏正下方以动画优雅展开结果面板；
  - 清楚展示“共测试 X 个模型 · 成功 Y · 失败 Z”；
  - 失败项提供“展开原因”折叠列表，点击可查看具体的错误信息，完全闭环。

### 模块 4：组件解耦与死代码安全清理（先拆再删）

为防止删除文件导致项目构建阻断或旧测试用例报错，执行严格的**解耦先行、同步更新测试、最后移除**三步法：

1. **迁移视角切换器**：
   - 将 `PoolViewSwitcher` 从 `channel-pool-view.tsx` 独立抽离至专属文件 `pool-view-switcher.tsx`，彻底切断 `compute-pool-panel.tsx` 对旧容器文件的引用；
2. **重定向测试断言**：
   - 检查 `src/lib/a11y-responsive-integration.test.ts` 中对 `channel-pool-view.tsx` 的源码检查；
   - 将无障碍属性（如渠道启用状态 `aria-label`）的断言落点更新至新版供给明细组件 `model-family-card.tsx` 中，确保测试链条真实且持续有效；
3. **安全删除旧文件与基线校准**：
   - 安全删除已被彻底架空的 `channel-pool-view.tsx` 与 `channel-list.tsx`；
   - 更新架构基线 `scripts/architecture-baseline.json`（若有相关记录），确保门禁全绿零垃圾。

### 模块 5：视觉清理与字号归位

- **字号严格封闭**：
  - 全面排查并消除所有 `text-[11px]`、`text-[15px]` 等非法字号；
  - 严格使用规范白名单：`28 / 20 / 18 / 14 / 13 / 12px`；
- **术语清零**：
  - 清理接入弹窗中遗留的“密钥标签”等陈旧术语，全站统一为“渠道显示名”。

## 四、成功验收标准

1. **业务保障一目了然**：打开页面默认看到的看板，能立即回答“网站有哪几个业务、各用什么模型、安全冗余度如何”；断供时能一键切到供给端解决。
2. **存量定名真正可用**：阿禅在界面上点击任意渠道的铅笔，就能直接改名，保存即生效。
3. **视觉舒适高级**：无非法字号、无卡片套卡片、无密集按钮电路板、无原生粗糙弹窗，符合《Claude 设计哲学》工作室质感。
4. **代码整洁无死代码**：旧容器与无用文件彻底移除，解耦干净，全量测试与静态检查 100% 通过。
