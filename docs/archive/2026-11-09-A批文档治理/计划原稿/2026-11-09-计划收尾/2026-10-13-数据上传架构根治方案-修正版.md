> 本版基于对真实代码的逐行核对，替换 V2 中所有与现状不符的描述

## 背景与目标

**问题**：`persist.ts` 现在用 `new Date(published_at).toISOString().split('T')[0]` 取 **UTC 日期**。
对上海时间 0–8 点发布（UTC 前一天 16:00–24:00）的视频，归属日期会整整少一天。

**目标**：
1. 只有一个地方算 `report_date`
2. 数据库拒绝不一致的数据（兜底）
3. 上线顺序不打断生产

## 步骤 1：修 `persist.ts` 的日期计算（核心，30 分钟）

**文件**：`src/app/api/video-submit/persist.ts`，`buildDailyReportPayload`（约 266–269 行）

**现状**：
```typescript
// 归属日期统一使用发布日期（数据口径 §6）
const reportDate = normalized.published_at
  ? new Date(normalized.published_at).toISOString().split('T')[0]
  : normalized.biz_date;
```

**改为**：
```typescript
import { formatShanghaiDateOnly } from "@/lib/loaders/shared";

// 归属日期 = 发布日期的上海自然日（数据口径 §6）
// 注意：formatShanghaiDateOnly 只接受 Date，必须先 new Date()
const reportDate = normalized.published_at
  ? formatShanghaiDateOnly(new Date(normalized.published_at))
  : normalized.biz_date;
```

**不要做**（V2 的错误）：
- ❌ 不要新建日期函数（复用 `formatShanghaiDateOnly`）
- ❌ 不要再改编辑模式：`persist.ts:289` 已经是
  `normalized.mode === "edit" && existingVideo ? existingVideo.published_at ?? null : ...`，
  且 `persist.test.ts:172` 已有测试覆盖。改它是改已经正确的代码。
- ❌ 不要改 `edit-detail.ts`（那里的 `dailyReport.report_date` 是死字段，`route-core.ts` 不消费）

**异常处理**：`new Date(x)` 对非法值返回 Invalid Date，`Intl.format` 会抛 `RangeError`。
`published_at` 在进入持久化前已经过 `validation` 层校验，理论上不会非法；
若想保险，可写成：
```typescript
const parsed = new Date(normalized.published_at);
const reportDate = normalized.published_at && !Number.isNaN(parsed.getTime())
  ? formatShanghaiDateOnly(parsed)
  : normalized.biz_date;
```

### 2.3 创建约束 migration

**文件**：`supabase/migrations/20261013150000_add_report_date_constraint.sql`

```sql
-- 第 1 步：NOT VALID，不扫存量、不锁表
ALTER TABLE public.daily_reports
ADD CONSTRAINT report_date_must_match_published_at
CHECK (
  published_at IS NULL
  OR report_date = (published_at AT TIME ZONE 'Asia/Shanghai')::date
) NOT VALID;

-- 第 2 步：后台校验存量（不阻塞写入）
ALTER TABLE public.daily_reports
VALIDATE CONSTRAINT report_date_must_match_published_at;

COMMENT ON CONSTRAINT report_date_must_match_published_at ON public.daily_reports IS
'数据口径 §6：report_date 必须等于 published_at 的上海自然日；published_at 为空的历史数据豁免';
```

### 2.4 上线顺序（**硬性要求**）

1. 部署步骤 1 的代码
2. 观察 1 天，确认无 500 / 无约束报错
3. 再执行 2.3 的 migration

顺序反了的后果：约束生效到新代码上线之间，旧代码按 UTC 写日期 → 撞约束 → 提交 500。

## 步骤 3：历史手稿表单（**需产品决策，不要直接改**）

**真实文件**：`src/app/(app)/dashboard/actions.ts`

**真实情况**（与 V2 描述不符，务必先读一遍）：

1. `report_date` 来自**表单直传**（`actions.ts:101` `formData.get("report_date")`），不是算出来的
2. 带 `report_id` 的编辑走 `update_history_report_edit_atomic` RPC，**该 RPC 不传 `report_date`**
   → **编辑已有日报时根本不写 report_date，不受新约束影响**
3. 只有**不带 report_id 的新建路径**会用表单值写 `report_date`（`buildHistoryReportPayload({ reportDate: report_date })`）
4. `published_at` 走 `resolveImmutablePublishedAt(existing?.published_at, submittedPublishedAt)`，
   注释明确写了"历史编辑只改日报数据，不能用表单值覆盖它"

**所以真正的风险面只有一处**：新建路径下，表单填的 `report_date` 与系统识别出的 `published_at` 上海日不一致。
这类数据本身就是脏数据（业务日期 ≠ 真实发布日），约束拦下它是**预期行为**，但需要产品决定怎么让用户改。

**三个选项（请产品选一个，不要开发自己定）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 新建时 `report_date` 不允许手填，自动取 `(published_at AT TIME ZONE 'Asia/Shanghai')::date`；`published_at` 为空时保留手填 | 用户失去"手动指定归属日"能力 |
| B | 保持手填，提交前校验一致性，不一致时阻断并提示"该视频真实发布日期是 X，请改归属日或换截图" | 部分老数据用户会卡住，需要引导 |
| C | 约束加 `OR report_date <= '2026-10-13'`（只约束新增数据） | 存量脏数据永久保留，两本账 |

**V2 的"把默认发布时间改成业务日期当天 00:00"不要做**：
现在默认是"业务日期前一天 19:00"（`src/lib/日报.ts` 的 `getDefaultPublishedAtForBizDate`，
因为当天填报的是昨晚发的视频）。改它会改变所有老记录的发布时间显示值和统计口径，
属于产品语义变更，不在本次范围内。

## 步骤 4：测试

import { formatShanghaiDateOnly } from "@/lib/loaders/shared";

test("report_date 取发布时刻的上海自然日，凌晨时段不再少一天", () => {
  // 上海 2026-10-13 00:00 = UTC 2026-10-12 16:00
  assert.equal(formatShanghaiDateOnly(new Date("2026-10-12T16:00:00.000Z")), "2026-10-13");
  // 上海 2026-10-13 07:59（旧算法会算成 2026-10-12）
  assert.equal(formatShanghaiDateOnly(new Date("2026-10-12T23:59:59.000Z")), "2026-10-13");
  // 上海 2026-10-13 08:00
  assert.equal(formatShanghaiDateOnly(new Date("2026-10-13T00:00:00.000Z")), "2026-10-13");
});

test("buildDailyReportPayload 的 report_date 用上海日而非 UTC 日", () => {
  const payload = buildDailyReportPayload({
    normalized: normalized({ mode: "create", published_at: "2026-10-12T23:30:00+08:00" }), // 上海 10-12 23:30 → UTC 15:30
    videoId: "video-1",
    userId: "user-1",
    submitter: "阿禅",
    nowIso: "2026-10-12T15:30:00.000Z",
    assigneeColumns: { script_author_user_id: null, video_editor_user_id: null, operator_user_id: null },
  });
  assert.equal(payload.report_date, "2026-10-12");
});

## 不在本方案内（已拆出）

事务 RPC 改造需独立方案，至少要先明确：
- 只覆盖新建模式（编辑模式保持现状）

- 响应契约（接口要返回完整视频行）
- 安全姿态仿照 `update_history_report_edit_atomic`
- 补偿逻辑删减映射
