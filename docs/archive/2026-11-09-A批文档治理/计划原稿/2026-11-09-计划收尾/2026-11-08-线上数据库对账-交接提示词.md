# 线上数据库对账：交接提示词

> 用法：整段复制给新的 Agent（建议 Codex 或 Claude Code）。本任务只读，不改任何数据和结构。

---

你在 DYData 仓库（`/Users/mac/Projects/dydata`）工作。先完整读 `AGENTS.md`，按其中要求输出开工卡；再读 `docs/系统架构与设计/工程运行事实.md` 的「四、部署与运维事实」和「五、发布硬边界」。

## 背景

`supabase/migrations/20261003020000_business_day_shanghai_timezone.sql` 的文件头写明：本地库与生产库的同名数据库函数已经双向漂移。例如：
- 生产的 `admin_cockpit_summary` 是转发到 v2 的薄壳；
- 本地的 `get_leaderboard_rows` 多 4 个输出列；
- 两个豁免原子函数只在生产存在。

这样的后果有两个：本地测试通过不代表线上行为一致；任何整体重建函数的迁移，都可能把较新的一侧覆盖回旧版。目前没人知道漂移的完整范围。

## 目标

查清"代码仓库里的迁移文件、本地测试库、线上生产库"三者到底差在哪里，并按风险排序。只出报告，不修。

## 要核对的内容

1. **迁移账本**：
   - 列出生产库和本地库各自已执行的迁移版本（`supabase_migrations.schema_migrations`）；
   - 与 `supabase/migrations/` 下的文件逐一对照。
   - 分别列出：仓库有但生产没执行的、生产执行了但仓库没有的、两边都有但本地没执行的。
   - `supabase/deferred-migrations/` 里的项目也要说明当前在生产是什么状态。
2. **函数定义**（public schema）：
   - 两边都对每个函数取 `pg_get_functiondef` 的指纹（比如 md5），列出：只在一边存在的、两边都有但定义不同的。
   - 对定义不同的，挑出与业务统计、权限、审批相关的（名字包含 fulfillment、leaderboard、exemption、appeal、cockpit、report、permission、is_admin 等），给出差异摘要。
3. **业务日时区**：确认以下函数在生产上带有 `timezone=Asia/Shanghai` 配置（查 `pg_proc.proconfig`）：
   - `get_fulfillment_range`
   - `get_fulfillment_calendar`
   - `get_today_submission_status`
   - 两个永久豁免原子函数

   同时列出所有函数体里用了 `current_date` 或 `now()::date`、却没有这项配置的函数。
4. **数据完整性约束**：
   - 两边对比表的约束（主键、外键、唯一、check），重点确认 `report_date_must_match_published_at` 在生产存在且生效；
   - 列出生产上有外键却没有对应索引的列。
5. **行级权限（RLS）**：
   - 两边对比每张 public 表是否开启 RLS，以及策略的名称和条件；
   - 列出生产上没开 RLS、但 anon 或 authenticated 角色有读写权限的表。
6. **函数执行权限**：
   - 列出所有 SECURITY DEFINER 函数，以及 anon/authenticated 能否执行；
   - 标出能被直接调用、但函数体内没有权限判断的。
7. **触发器与定时任务**：两边对比触发器列表；如果用了 pg_cron，对比任务列表。

## 禁区（硬性）

- **生产库只读。** 连接后第一句执行 `set default_transaction_read_only = on;`，全程不执行任何写入、DDL、迁移或修复，包括"顺手修一个明显的问题"。
- 生产连接信息只能从仓库外的凭据或 `.env.local` 中读取。**不打印、不粘贴、不写进任何文件或日志**；报告里出现主机名也要打码。
- 不用本机 3000 端口的开发服务做任何操作（它连的是生产库）。
- 本地库只读查询即可，不重置、不重新执行迁移。
- 不提交代码改动；不 push。
- 不确定某条差异算不算问题时，如实写"待判断"，不猜。

## 交付

1. 报告写到 `docs/reference/2026-11-XX-线上数据库对账.md`（XX 用实际日期）。每条结论都标注"实测（命令＋读数）"。报告结构：
   - 第一段用大白话写给阿禅（不出现代码名），说清有几类差异、最严重的三条会导致什么后果；
   - 然后是按风险排序的差异清单（高/中/低），每条写明：在哪一侧、差什么、可能的后果、建议的处理方式（只建议不执行）；
   - 最后附查询方法，方便以后每月复查。
2. 把本次用到的只读查询整理成一个可重复执行的脚本 `scripts/audit/db-drift-report.mjs`：
   - 只读；
   - 拒绝在未设置只读事务时运行；
   - 输出 JSON 和 Markdown 两种格式；
   - 不内置任何凭据。

   这个脚本可以作为本地提交。
3. 按 AGENTS.md 第五节写日志，并输出收尾卡。
