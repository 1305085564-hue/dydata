# 修复需求：完播截图未识别出「发布时间」时用户无路可走（死路）

- 交付对象：Codex（[CX]）
- 提出：2026-10-01
- 问题引入提交：`af949973`（fix: lock published time and autofill title，2026-10-01 20:24）

---

## 一、业务问题（一句话）

**按时长上传的截图如果没被识别出「发布时间」，用户会掉进一个没有任何出口的死循环：提交被拒 → 系统让他去"更多设置"里确认发布时间 → 那个输入框是锁死的。**

---

## 二、现状与复现路径（已核实，均为代码事实）

1. 用户上传完播截图 → OCR 识别。若截图里没有可识别的"发布"时间，识别结果里 `published_at` 为 `null`，前端**静默忽略**（`video-submit-form-v2.tsx` 约 1480 行的 `if (... recognizedPublishedAt ...)` 只在成功时写入），用户毫无察觉。
2. 用户填完其余全部内容，提交按钮**可用**。原因：提交就绪判定 `summarizeSubmissionIssues` / `canSubmit`（`src/components/submission/提交状态机.ts`）**完全没有"发布时间是否已确认"这一项**。
3. 点提交 → 后端 `src/app/api/video-submit/route.ts:278` 用 `publishedAtConfirmed = Boolean(published_at_text?.trim())` 判定为 `false`。
4. `src/lib/video-submit-deadline.ts:97` 的 `requires_confirmation` 判定**排在 72 小时判定之前** → 返回 409 `PUBLISH_TIME_CONFIRM_REQUIRED`，文案为：
   > 未能识别作品真实发布时间，请在"更多设置"中确认发布时间后重新提交
5. 前端收到该 code 后只做两件事（`video-submit-form-v2.tsx:1784`）：展开"更多设置" + 滚动过去。而"更多设置"里的 `PublishedAtPicker` 在 `video-submit-form-v2.tsx:2563` 与 `history-report-edit-form.tsx:831` 都是**硬编码 `disabled`**；`updatePublishedAt` 全仓唯一调用点就是那个被禁用的控件 —— **没有任何 UI 路径能写入手工发布时间**。

**连带后果（比上面更严重）**：因为 `requires_confirmation` 优先于 `requires_appeal`，这批用户**连"申请补交"的按钮都拿不到**。2026-10-01 刚验收通过的补交链路对他们等于不存在。

---

## 三、修复目标

让用户在"没认出发布时间"时**当场知道原因，并且知道唯一可行的动作是换一张能看清发布时间的截图**。

### 关键判断（决定了本次不做什么）

截图槽位本身支持删除重传（`video-submit-form-v2.tsx:2226` 已有"删除后需要重新上传并识别该槽位截图"的交互），所以**"换图重传"这条出路天然存在**，只是用户不知道要走它。因此本需求的全部价值在于：把这条出路明确指出来，并且在用户点提交之前就指出。

---

## 四、本次改动（P0，必须完成）

### 改动 1 — 判定同源：抽出"发布时间是否已确认"

**文件**：`src/lib/video-submit-deadline.ts`

- 新增并导出 `isPublishedAtConfirmed(value: string | null | undefined): boolean`，实现为 `Boolean(value?.trim())`。
- **同步改** `src/app/api/video-submit/route.ts:278` 用这个函数替换内联的 `Boolean(normalized.published_at_text?.trim())`。

理由：前端要复制这条判定，若各写一份就是又一处"读写契约不同源"（本项目头号缺陷类型）。必须单一来源。

### 改动 2 — 把"发布时间未确认"纳入前端提交就绪判定

**文件**：`src/components/submission/提交状态机.ts`

- `SubmissionIssueMeta` 增加可选字段：`publishedAtConfirmed?: boolean`、`submissionMode?: "create" | "edit" | "backfill"`、`anomalyStatus` 已有，复用。
- 判定逻辑（**必须与后端豁免条件同源**）：
  - 仅当 `publishedAtConfirmed === false` **且** `submissionMode !== "edit"` **且** `anomalyStatus !== "abnormal"` 时，计入一项 issue。
  - `publishedAtConfirmed === undefined` 视为**不校验**（保持现有单测与其它调用方完全不变 —— 这是必须的，该文件被大量测试直接调用）。
  - issue 计入 `totalIssueCount`，`firstIssueAnchor` 指向 `"meta"`。
  - `canSubmit` 返回 `{ ok: false, reason: "未识别到发布时间，请重新上传能看清"发布"时间的完播截图" }`。
- **注意后者优先级**：这一项应排在截图/指标/标题之后（即不要抢在"请先上传必传截图"前面），只在其它都齐了之后才提示，避免用户刚进页面就被一句无关的报错糊脸。

**文件**：`src/components/submission/填报表单状态.ts`

- `SubmissionIssueMetaInput` 同步增加上面的字段（该文件 `summarizeSubmissionIssues` 直接把 meta 透传给 base，只是类型没同步会漏字段）。
- `firstInvalidFieldKey` 分支**不需要**为它新增取值（发布时间不是 `EditableFieldState`），保持现有逻辑即可。

**文件**：`src/app/(app)/dashboard/video-submit-form-v2.tsx`

- 第 1149 行 `summarizeSubmissionIssues(...)` 的 meta 注入：补 `publishedAtConfirmed: isPublishedAtConfirmed(meta.publishedAtText)`、`submissionMode: mode === "editToday" ? "edit" : mode === "backfill" ? "backfill" : "create"`。
- 第 1167 行 `canSubmit(...)` 的 meta 注入同样补上（**当前它只传了 `anomalyStatus`，是漏项**）。
- 依赖数组同步补 `meta.publishedAtText` 与 `mode`。
- 按钮禁用不用另写逻辑，走现成的 `canActuallySubmit = issueSummary.canSubmit`。

### 改动 3 — 让提示出现在用户能看到的地方

## 八、附：本次不做、需另立项的部分（P1）

上面 P0 能覆盖绝大多数场景（截图质量/裁切问题 → 重传即可）。但有一种情况 P0 解决不了：**达人或平台给出的截图本身就不含"发布时间"**（例如只截了数据页）。此时用户重传多少次都没用。

那种情况需要一条真正的兜底通道，例如"申请人工核定发布时间"（用户申请 → 管理员核定后写入，写审计痕迹）。这条路涉及新表/新流程/管理员入口，**不在本需求范围内**，需阿禅单独拍板后立项。
