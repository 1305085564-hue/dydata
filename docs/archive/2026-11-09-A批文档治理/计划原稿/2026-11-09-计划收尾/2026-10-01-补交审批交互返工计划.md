# 补交审批返工实施计划（交互与体验收口）

> **状态**：待评审与确认  
> **责任代理**：[An] Antigravity  
> **目标**：只收口交互体验与视觉规范，不动数据闭环（保留现有“先批许可证、批了再走正常上传”机制）。

---

## 一、方案核心决策

1. **视觉回正（单点聚光灯律）**：
   - 彻底移除待办卡片中的 `bg-status-success text-white` 实心绿底。
   - “直接通过”按钮改名为 **“同意通过”**，采用克制的次级镂空微边框样式（`border border-status-success/30 text-status-success hover:bg-status-success/10`）。
   - 全屏唯一实心主焦点锁死暖陶土橙（`#D97757`）。

2. **就地展开明细，终结“查看详情”跳飞大盘迷局**：
   - 抛弃原本跳转到 `/admin/fulfillment` 的硬链接。
   - 改为卡片内 **就地展开 / 折叠明细**（In-place Detail View）：
     - 展开展示：申请人、关联账号、补交日期、申请理由、规则依据（逾期 > 72 小时）。
     - 审批人视线和工作记忆完全停留在行动中枢内，零页面跳转。

3. **驳回必填原因弹窗 + 后端透传存下 + 结果通知附带原因**：
   - 点击“驳回”弹出轻量 Dialog，必须输入非空驳回原因，否则禁止提交。
   - 后端接口 `/api/admin/fulfillment/appeal/handle` 接收 `reason`，在 `decision === "reject"` 时做强制必填校验。
   - 透传保存：写入审计日志 `audit_logs`，并随通知发送给成员（通知内容：`${recordDate} 的数据补交申请已被驳回。驳回原因：${reason}`）。
   - 履约大盘 `fulfillment-action-dock.tsx` 同步拉齐驳回弹窗校验。

4. **全链路业务措辞统一**：
   - 清退“申诉”、“改判”、“直接通过”等混叫。
   - 统一规范为：**“补交申请” / “数据补交申请”**、**“同意通过”**、**“已驳回”**。

## 三、验收标准

1. `npm run gate:static` 全绿（单测通过、TypeScript 无报错、Lint 无报错、构建顺利通过）。
2. 真实浏览器端到端走通（超 72h 提交申请 → 行动中枢待办卡片 → 原地查看明细不跳飞 → 驳回弹窗输入必填原因 → 成员收到带具体原因通知）并截图留证。
3. 严格恪守禁区：不改提交校验链、不把草稿数据入库、不引入新机制。
