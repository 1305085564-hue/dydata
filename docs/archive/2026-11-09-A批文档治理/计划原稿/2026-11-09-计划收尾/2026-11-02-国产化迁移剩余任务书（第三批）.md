1. 广州桶是 10-18 那次 Supabase→COS 全量迁移的落点，3,122 张，**15 分钟内一次传完，之后再没有任何写入**。

3. **广州桶是新加坡桶的严格子集**（只在广州的 0 个、只在新加坡的 881 个）。它既不是主库，也不能当备份——缺 881 张。
4. 生产配置为 `COS_BUCKET=dydata-screenshot-sg-1409482292` / `COS_REGION=ap-singapore`；10-23 与 11-01 两次实测均确认生产实际读的是新加坡桶（响应头 `X-Screenshot-Backend: cos`）。

### 由此产生的两条硬约束

**约束 A：现在绝对不能把 `COS_BUCKET` 改成广州桶。**
改了会有 881 张图 404，而且更慢——Vercel 函数在新加坡 `sin1`，读广州是跨境。10-19 实测：读新加坡 p50 33ms / p95 65ms；读广州 p50 802ms / p95 1,214ms，37 次里 15 次超时。

**约束 B：顺序固定为「先搬计算，再搬存储」。**
计算在新加坡时搬存储只会更慢；计算搬进国内同区后搬存储才会快。这条已写在 03 号计划阶段 5 的决策依据里，本次只是重新确认。

> 这个误会不会拖慢进度——存储本来就该最后搬。但**不能按「已在国内」去安排动作**。

## 十一、2026-11-02 补充研究结论（已核实平台机制，修正 WP1 执行细节）

来源：官方文档研究 + 本环境只读查询；其中两处"待确认"已用我们自己的实测闭合。

### 11.1 机制结论（实测 + 文档双重支撑）

1. **R02 不是故障，是平台设计**：数据网关对 JWT 只做无状态校验（签名 + 有效期，默认 2 小时），不查认证面的撤销记录。退出登录的"立即失效"只对认证服务成立；官方 rls-patterns 文档已默认"旧 JWT 过期前仍有效"。
2. **B01 的"假成功"是平台能力边界**：传统用户管理接口（ModifyUser 等）不作用于 PG 模式的 `auth.users`，返回成功≠写入成功。官方 auth-pg 文档明示：PG 模式账号表可用 SQL 增删改查，这是文档认可的能力，**不是未公开通道**。
3. **status 枚举已有实测答案**（研究标注"未公开"，但我们测过）：0/1 正常、2 待激活、3 封禁——账号迁移时 24 个封禁账号按 status=3 迁入，登录被拒已复验。
4. **封禁/归档账号的旧 JWT 数据面已被堵住**：R01 统一状态检查上线后实测，封禁账号旧 JWT 对 89 张表 267 次请求零行。**"RLS 再 JOIN auth.users 二次校验"不需要新做**，已落地。

### 11.2 对 WP1 执行细节的修正
