## 二、完整业务链路与核心架构设计

### 链路 A（关卡 1 · D2 + D5 草稿云端图加载态）：数据上传表单流程层拆分
```text
员工工作台 (/dashboard)
  ├─ 截图上传/OCR并行识别 → 指标清洗与标疑 → 本地草稿静默保存/恢复（[补齐 D5] 恢复云端 assetUrl 显示「来自云端」加载态）
  ├─ 表单状态机（新建 / 异常上报 / 编辑历史 / 续交）→ 校验与判重 → POST /api/video-submit
  └─ [改动点 D2] 将 1466 行 video-submit-form-v2.tsx 拆清纯状态/流程 hooks + 子模块；
                 同步消除 video-submit-form-v2.tsx 的 eslint-disable react-hooks/refs；
                 顺手将 route-core.ts（864 行）与 ai-config.behavior.test.ts 压回可维护基线内。
```

### 链路 B（关卡 2 · C3）：72 小时补交改「先交后核」（阿禅 2026-11-27 拍板）
```text
员工提交首次正常作品 (/api/video-submit)
  ├─ 1. 正常判重（同账号 + 同标题 + 同上海发布日）→ 重复仍 409 拦截（旧行为保持）
  ├─ 2. 72 小时 / 手填发布时间判定：
  │   ├─ [新规则] 不再 409 拦截员工！直接正常写入 videos + daily_reports + snapshots 并恢复当天履约
  │   └─ 若触发「超 72 小时才交」或「手工填写/修改了发布时间」：
  │       └─ 自动创建一条「事后核查（post_submit）」记录（复用 fulfillment_appeals 或向后兼容附加字段，关联 video_id + daily_report_id + 触发原因 + 识别原值）并推送管理端待办
  ├─ 3. 管理端审批工作台（等你批）：
  │   ├─ 历史遗留的「前置审批」老待审单 → 保持旧行为（同意+自动续交 / 驳回），平滑过渡不中断
  │   └─ 新的「超期/手改事后核查」卡片 → 显示触发原因（超72h / 手改时间及原值）+ 作品核心数据，两个动作：
  │       ├─ 「确认正常」：审核通过，保留作品正常状态与优条数结算资格，写审计日志，关闭待办
  │       └─ 「标为无效（不计优结算）」（原因必填）：写审计日志，关闭待办，将关联作品/日报标为不计入文案「优条数」结算（唯一口径源头，复盘与协作管理文案优条数/结算同步生效）
  └─ 4. 历史记录「打回待处理」（reopen）：
      └─ 事后核查被「标为无效」后若管理员点打回待处理，恢复为待核查态并同步恢复原有效状态，重新进入待处理队列。
```

### 链路 C（关卡 3 · C8）：集团模式审批权限解耦
```text
员工工作台读「近 7 天审批结果横幅」

```

### 链路 D（关卡 4 · B3）：AI 配置 4 个废弃旧列清理准备

应用层（src/lib/ai-config/*、src/lib/ai/*、api/admin/ai-config/*）

## 三、分关卡施工规格

### 关卡 1（D2 + D5 草稿云端图加载态）：上传表单拆解与大文件压降
1. **先补行为测试再动手**：针对 `video-submit-form-v2.tsx` 补齐关键流程行为测试（新建提交、OCR 填充、本地草稿恢复、编辑历史、异常上报），作为重构护栏。
2. **流程层拆解**：将 `src/app/(app)/dashboard/video-submit-form-v2.tsx` 拆出独立流程 hooks/控制器模块，主组件行数显著压降（目标 ≤ 600 行），外部 props 与用户可见交互 **零回归**。
3. **消除豁免注释**：按纠错要求彻底消解 `video-submit-form-v2.tsx` 的 `eslint-disable react-hooks/refs`（① 补交/提交 payload 改显式实参；② `scrollToIssueAnchor` 改不捕获 ref 写法），零新增 eslint-disable。
4. **D5 顺手补齐**：草稿恢复后，若截图槽位仅有云端 `assetUrl`（非本地 blob），补充清晰的「来自云端」加载态与失败兜底态。
5. **大文件顺手压降**：将 `src/app/api/video-submit/route-core.ts` 与 `src/app/api/admin/ai-config/ai-config.behavior.test.ts` 拆回可维护性门禁基线内（参考 `npm run audit:architecture` 输出）。
6. **门禁与提交**：全套单测 + `npm run gate:static` 全绿 → commit `refactor(dashboard): 拆解数据上传表单流程层、消除 refs 豁免并补齐云端草稿加载态`。

### 关卡 2（C3）：72 小时补交改「先交后核」
1. **先盘清「优条数结算」单一真源**：动手前先查清全站所有计算「优条数 / 良优率 / 文案结算」的读取路径（`src/lib/collaboration/`、`src/lib/content/`、视频复盘列表/详情），确保「标为无效（不计优结算）」只从**唯一真源字段**控制，绝不在多处复制补丁。
2. **向后兼容数据库迁移**：新增迁移文件（`supabase/migrations/YYYYMMDDHHMMSS_late_submit_post_review.sql`），只做增量、可空/带默认值变更（例如 `fulfillment_appeals` 补关联 `video_id`/`daily_report_id`/`review_mode`，关联表补 `settlement_excluded` 或 `late_review_status` 字段与清晰注释），确保旧代码运行不报错、老数据兼容。
3. **提交端改造**：
   - `resolveVideoSubmitDeadline` 与 `route-core.ts`：超 72 小时或手填/改发布时间不再返回 `409 SUBMISSION_APPEAL_REQUIRED`，而是正常完成作品与日报写入，并自动生成事后核查单 + 管理员待办；前端工作台提交按钮保持直接提交（对超 72h / 手改时间给出温和说明“将直接入库并同步管理员复核”，不再把按钮锁死为“提交补交申请”）。
   - 保留判重（409 重复拒绝）、保留异常模式豁免、保留编辑模式不重算时限。
   - 若事后核查单写入失败：绝不伪造成功——明确记录告警日志并把状态如实反馈（参考强模型可兜底三要素：提示、日志落点、排查依据）。
4. **管理端改造**：
   - 审批工作台卡片对 `post_submit` 事后核查单展示触发原因（超 72 小时 / 手改发布时间及 OCR 原值）、发布日与上传日间隔、作品标题与关键数据；动作按钮为 **「确认正常」** 与 **「标为无效（不计优结算）」**（点后者就地展开必填原因输入框，不弹窗）。
   - 对线上可能尚存的旧 `pre_submit` 待审补交单，保持原有「同意（含自动续交）/ 驳回」逻辑，零破坏。
   - 补齐 `reopen` 打回待处理对称逻辑与审计日志。
   - 视频复盘与协作管理文案表：被「标为无效」的作品显式标示「不计优结算」，文案「优条数」自动排除该条（原始作品数据留痕可追溯，不静默丢数据）。
5. **门禁与提交**：补齐单元/路由/领域测试（含新旧两种模式、结算剔除、打回恢复），跑通 `npm run gate:static` → commit `feat(fulfillment): 72小时补交改为先交后核并接入不计优结算复核`。

### 关卡 3（C8）：集团模式审批权限解耦
1. **核查现状**：对照 `supabase/migrations/20260902100000_exemption_daily_review.sql`、`20261016090000_remove_group_mode.sql` 及 `src/lib/loaders/dashboard-exemption-review.ts`，盘清 `exemption_request_date` 上所有依赖 3 参旧 `exemption_target_in_active_scope` 或 `is_group_mode_active` 的策略与对象。
2. **新增幂等安全迁移**：新建迁移文件，在任何清理集团旧函数前，先使用 2 参 `public.exemption_target_in_active_scope(auth.uid(), ...)` 重建 `"成员或管理员读取申请日期明细"` 等依赖策略，确保员工读取本人逐日审批明细、管理员读取本团队/本公司范围明细权限严密不越权、不空白。
3. **验证与测试**：编写结构契约与行为测试验证策略定义不再引用 3 参旧函数/集团模式函数，并在本地回放/测试中证明员工仍可读到「部分通过 / 通过 / 驳回 / 理由」。
4. **门禁与提交**：跑通 `npm run gate:static` → commit `fix(db): 解耦逐日审批读权限与集团模式旧函数依赖`。

### 关卡 4（B3 + 本组接口报错收口）：AI 配置旧列清理准备与 3 组接口报错收口
1. **清零代码引用**：全仓搜索 `global_is_enabled`、`provider_key_model_id`、以及 `ai_provider_keys.priority` / `ai_providers.priority`，移除应用侧全部读写与兼容逻辑，更新对应测试（先确认生产运行时代码真零依赖）。
2. **核验暂缓迁移脚本**：检查 `supabase/deferred-migrations/20261105072558_ai_config_drop_legacy_columns.sql`，补充 `drop column if exists` 幂等保护并在注释写明前置核查 SQL 与回滚预案（保持留在 `deferred-migrations` 或标明由架构师统一备份后上线执行，**绝不直写正式库**）。
3. **本组接口报错收口**（与对话 3 物理切分）：收口 `src/app/api/admin/ai-config/**`（`route.ts`、`sync-models`、`check-dependencies`、`ocr-logs`）与 `src/app/api/admin/fulfillment/appeal*/**`（`appeals/route.ts`、`appeal/reopen/route.ts`、`appeal/handle/route.ts`）所有仍直接回传数据库/模型原始报错的出口，统一使用 `src/lib/errors.ts` 公共中文提示 + `requestId` + 同编号服务端日志（保持 `error` 为字符串，不破坏前端读取）。
4. **门禁与提交**：全套单测 + `npm run gate:static` 全绿 → commit `refactor(ai-config): 清零AI配置4个废弃旧列代码引用并收口本组接口报错`。
