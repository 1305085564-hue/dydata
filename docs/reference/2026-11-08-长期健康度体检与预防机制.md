# 长期健康度体检与预防机制（2026-11-08，[CC]）

目标：找出长期 AI 开发中会持续积累、靠人工审查守不住的问题，把能自动化的预防接进日常推送流程。

## 一、判断依据：故障是怎么漏出去的

近三个月的事故和返工记录（日志、reference）里，反复出现的不是"代码写错"，而是**检查信号失真**：

| 信号 | 失真方式（实测） | 后果 |
|---|---|---|
| 构建绿灯 | `next.config.ts` 设 `ignoreBuildErrors: true` | 2026-11-07 类型错误上线，截图识别全量故障 |
| `npm test` | 9 个真实库测试混在单元测试里，本地库没起时固定 8 红，被各方记作"预存限制"放行；库起来后并行跑又因改表结构死锁（实测 40P01） | 红灯失去含义，真正的新失败会被一起放过 |
| 可维护性门禁 | 基座已有 12 个文件超出棘轮上限，门禁对所有改动常红 | 被当噪音，棘轮形同虚设 |
| 门禁本身 | 只靠"推送前记得跑"，没有任何 git 钩子或 CI | 跑不跑取决于当轮 Agent 的记性 |

结论：先修信号，再加规则。信号不可信时，再多的规则也会被绕过。

## 二、已实施（本地提交，均有验证）

1. **类型错误拦构建**：关闭 `ignoreBuildErrors`。验证：当前 `npm run build` 通过；人为插一个类型错误，构建失败并报 TS2322。
2. **测试分组**（`scripts/run-tests.mjs`）：`npm test` 只跑无外部依赖的 2691 项，全绿；`npm run test:real-db` 串行跑真实库 21 项，全绿，库没起来时明确失败、拒绝非本机地址。同时修了一个假绿：带 `[id]` 的测试路径被测试框架当成通配符静默漏跑，现已转义（抽查确认执行）。
3. **推送前自动门禁**（`scripts/git-hooks/pre-push`，`npm run hooks:install` 安装）：tsc、单元测试、lint、设计门禁、可维护性门禁，实测 59 秒。推送即上线，这是最后一道不靠记性的关口。
4. **接口鉴权清点测试**（`src/app/api/route-auth.coverage.test.ts`）：93 个接口逐一要求调用统一鉴权入口或登记为有意公开（7 个，各写明保护方式）；不带权限要求的管理端入口后面必须有能力/范围收窄。验证：临时加一个无鉴权接口、一个只有"任意权限"的接口，都报红。
5. **业务日期**：
   - 修复排行榜"近 7 天/近 30 天"在北京时间浏览器里多算一天（实测旧写法上海时区 11-08 往前 6 天得 11-01，应为 11-02）。
   - 修复抖音账号趋势窗口在凌晨 0-8 点多取一天。
   - 删除两处无人使用、但容易被误引的 UTC 日期函数（`formatDateOnly`、`getPresetRange`）。
   - 可维护性门禁新增规则：新代码不准再用 `toISOString()` 切业务日期（存量 22 处多为 `Date.UTC` 纯日历运算，不追溯）。
6. **棘轮只拦改到的文件**：基座超限文件点名但不拦无关改动，谁改谁先压回上限。门禁从常红恢复为有意义的绿灯。
7. **规则纠偏**：AGENTS.md 的"实发/应发"口径写的是按 `report_date` 聚合，与数据口径文档和数据库实现（发布日优先、回退 `report_date`）不一致，已改正。

## 三、持续监测（已存在，暂不动）

|---|---|---|
| 上海日期工具多份副本 | 约 10 处各自实现，目前结果一致 | 再出现日期差一天的问题时，统一收口到 `loaders/shared.ts` |

## 四、要阿禅拍板

1. **在每台开发机和工作树装推送钩子**（`npm run hooks:install`）。建议装，理由：上线前的类型/测试检查不再依赖 Agent 记性。代价是每次 push 多等约 1 分钟。本机已装。
2. **定时任务密钥可以放在网址里**（`?secret=`），且两把密钥都通用。建议改成只认请求头里的密钥，理由：网址会进访问日志。需要先确认没有外部系统用网址方式调用，所以未改。

## 五、明确不做

- 不引入 CI 平台：单人+多 Agent 本地开发，推送钩子已覆盖同样的检查，CI 多一套配置和密钥管理。
- 不一次性收口全部日期副本和角色字符串判断：目前结果一致，大面积重构的回归风险高于收益；靠门禁防新增。
- 不把以上规则写进 AGENTS.md：它们由测试和门禁自动执行，事实记在《工程运行事实》。

## 六、文档事实回头核对（C 批规格，2026-11-09 拍板）

接 A 批（修已知的 6 组错）之后，解决"新的文档与系统不一致怎么被发现"。归属打分表 #3（检查不说真话）。目标只一个：让每一轮接手的 AI 都能拿到可信事实，不照旧说法改错。

### 三层手段（按故障率从低到高、频率从高到低）

| 层 | 装什么 | 怎么触发 | 故障率 | 谁跑 |
|---|---|---|---|---|
| 推送钩子层 | 纯本地只读，扫文件在不在、链接能不能打开 | 每次 push 自动跑 | 极低 | 死脚本 |
| 静态扫描层 | 扫表名、函数名在不在代码库 | 每两周手动跑一次 | 偶尔误报 | 死脚本 |
| 语义抽查层 | AI 读代码对照文档 | 每批结束或累积提交到阈值跑 | 有不确定性 | AI，只出证据对 |

**分层原则**：最稳的检查跑得最频繁，最不稳的跑得最少。推送钩子里只放死的东西（纯本地只读），活的东西放外面单独跑——会抖的不堵推送。推送钩子层等 #12 上线自动关口的基础设施搭好再正式挂；在那之前先做成可手动跑。静态扫描不挂推送。语义抽查绝不挂推送。

### 输出与阿禅的角色

- **推送钩子 / 静态扫描**：红绿灯 + 待办条数，技术细节折叠。绿灯放心、红灯列出来进待办。
- **语义抽查**：每条只产出"证据对"——文档里写的（白话）vs 代码里实际（白话），标"对得上 / 对不上 / 待核"。**不许 AI 自报"文档没问题"**——这话阿禅没法判真假，必须给证据对。这是 #4 验收原则（只认证据、不接受自报）从代码验收挪到文档核对上用。
- **阿禅只做**：看红绿灯 + 看证据对 + 拍板改文档还是改代码。永远不通读文档、不记时间、不看技术细节。

### 三条铁律

- 只读、只报警、不自动改文档、不自动改代码；核出问题标"待核"挂待办。
- 抽查只出证据对，不下结论。
- 不把这套机制写进 AGENTS.md 新增规则——由脚本和抽查流程自动执行，事实记本文件。

### 高频教训

执行方（如 Codex）代码 bug 少，但业务逻辑 bug 高频——"能跑通"不等于"符合业务预期"。回头核对盯的正是这一类：文档说的业务流程和代码实际行为对不上。抽查时若发现"能跑通但和文档语义冲突"，按"对不上"处理并进待办，不因代码能跑就放过。
