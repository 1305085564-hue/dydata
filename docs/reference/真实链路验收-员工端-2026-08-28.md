# DYData 员工端真实链路验收（F3R3）

**验收日期**：2026-08-28（本轮浏览器交互跨到 2026-08-29；目标版本仍为 8 月 28 日 `main` 提交）
**验收角色**：普通内容员工，技术水平一般，时间紧张，核心关注“今天做什么、是否提交成功、下一步去哪”。
**最终结论**：**不通过**。

结论原因：线上正式版本的公开入口和部署版本已核对，但线上登录后的深度操作没有在当前 Chrome 调试桥上稳定完成；同一提交的 localhost 真实员工会话发现员工核心链路存在明确断点：未入团成员可看到完整选题池、认领后进入工作台丢失选题上下文、历史日报的日期/提交状态未正确对应，并且已有历史测试数据把测试密码字符串写入了视频文案字段。日报提交、OCR 和提交后同步因没有安全可丢弃的截图/日报测试条件，按规则停在提交前，不能宣称员工链路已打通。

- `17-根因调试恢复`：线上认证交互不稳定后，按版本一致性回退到 localhost，保留线上未完成状态，继续从页面、服务端日志和源码调用链定位原因。
- `18-测试驱动开发`：未启动。本轮是验收，不执行代码修复；没有把明确问题顺手改掉，也没有为了通过验收而新增测试或改变业务数据。

本轮边界：

- 不发送外部提醒，不切换提醒开关，不提交真实日报，不删除数据，不提交入团申请，不改变权限、归档状态或团队成员。

- 未读取 cookies、localStorage、token、浏览器密码或会话存储。

#### 列表、抽屉和详情一致性

- `我的认领` 抽屉能显示当前成员的候选/脚本中状态、Hook、日期和“去工作台立卷”入口。
- 同一成员刚完成候选或脚本后，`全部`列表对应卡片仍显示“认领写此题”，且卡片的“1 人认领/1 人在写”没有反映当前成员自己的状态；需要切换到“我的认领”才能确认操作已经落库。这是员工判断“我是否已经占位”的直接信任问题。
- 点击题目打开 `子题详情`，可看到 Hook、撞车动态、候选/脚本中人数、责任人和关联作品；点击完整详情可到 `/topics/[id]`，页面最终能加载。一次完整详情加载约 5–8 秒，超过文档中登录后页面的 2.5 秒首屏/4 秒完整加载目标。
- 列表、详情和抽屉的撞车文案不完全同义：列表显示认领/在写人数，详情显示候选/脚本中人数，详情还会出现“还没有其他人认领”但同时显示有人在脚本中。脚本中是否占用创作而不占候选配额需要更直白的员工文案。
