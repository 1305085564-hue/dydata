# 2026-10-09 AI 模型检测：批量全超时根因与结果可读性修复

> 范围：`/admin/ai-config`（AI 配置中心）的「检测此渠道全部模型 / 测试连通 / 全部模型检测」。
> 被测渠道：`api tang ChatGPT`（key `b9f0aa07-6ab0-4322-aa84-07033eb60f43`，上游 `https://xcmapi.org/v1`，挂载 8 个模型）。
> 最后核对代码日期：2026-10-09。本文所有根因结论均为**实测**（附命令与读数），推测项单独标注。

## 一句话结论

批量检测「0 个通过、8 个全超时」**不是并发把渠道压垮**，而是我们自己的判定线（10 秒）正好压在这条渠道的真实响应时间（5～25 秒）正中间——
同一个模型过不过，取决于那一次快不快，而不是它能不能用。单个测通过、批量判超时，就是这么来的。

已按产品口径修好两件事：
1. **判定线统一为 15 秒**（单测与批量共用同一条线、同一个探测函数），超过 15 秒即判「不可用」，并把原因写成中文；
2. **结果改成每个模型一行铺开**：模型名 + 已通过/耗时，或模型名 + 失败原因；原因缺失显示「未返回原因」。

## 一、根因（实测）

### 1. 真页面复现（修复前，2026-10-09 15:16）

在 `localhost:3000/admin/ai-config` 用 company_owner 账号真实点击，抓接口原始返回：

| 操作 | 结果 | 读数 |
| --- | --- | --- |
| 先点该渠道行的「测试连通」（gpt-6-sol） | 通过 | `模型连接正常 · 响应耗时 7.6s` |
| 紧接着点「检测此渠道全部模型」 | 1 通过 7 未通过 | 批量墙钟 15.1s；批量里 gpt-6-sol **3.5s 通过**，而 gpt-6.1-sol 被判 `The operation was aborted due to timeout` |

而 gpt-6.1-sol 在更早一次单独测试里是 8.6 秒通过的。**同一个模型，单测与批量给出相反结论**，与阿禅反馈完全一致。

### 2. 排除并发（关键对照）

把 8 个模型**完全一个一个串行**探测（完全不并发、同样 10 秒上限），结果照样大面积超时：

```
❌ codex-auto-review 10003ms TimeoutError
❌ gpt-5.5             276ms HTTP 404 model_not_found
❌ gpt-5.6-sol       10004ms TimeoutError
❌ gpt-5.6-terra       276ms HTTP 404
❌ gpt-6-astra       10002ms TimeoutError
❌ gpt-6-luna          275ms HTTP 404
✅ gpt-6-sol          5854ms
❌ gpt-6.1-sol       10000ms TimeoutError
通过 1 / 8
```

再单独做「1 个请求 vs 同时 4 个请求」的同模型对照（上限统一放宽到 60 秒，只留并发这一个变量）：

| 轮次 | 单独 1 个 | 同时 4 个（各自耗时） | 放大倍数 |
| --- | --- | --- | --- |
| 1 | 5149ms | 4078 / 4071 / 4753 / 4777 ms | 0.86× |
| 2 | 7140ms | 9460 / 10010 / 10492 / 10175 ms | 1.41× |
| 3 | 25265ms | 5551 / 6535 / 5476 / 5341 ms | 0.23× |

放大倍数在 0.23～1.41 之间乱跳，**没有系统性变慢**。结论：并发（上限 4）不是元凶。

### 3. 排除本机网络

同机同网测另一条渠道 `api9 gemin`（`https://api.slomerex.xyz/v1`）：2742ms / 2175ms 正常返回。本机网络无问题。

### 4. 上游真实响应时间分布（把上限放宽后实测）

| 模型 | 实测耗时 |
| --- | --- |
| gpt-6-sol | 5.1s / 5.7s / 5.85s / 7.1s / 7.55s / 8.0s / 10.58s / 25.3s |
| gpt-6-astra | 19.9s 能通 |
| gpt-6.1-sol | 单次 8.57s 通过；另有多次 30s、90s 内无任何响应 |
| gpt-5.6-sol、codex-auto-review | 90 秒上限内始终无响应 |

上游 `/v1/models` 当前只提供 5 个模型（`gpt-5.6-sol`、`codex-auto-review`、`gpt-6-astra`、`gpt-6-sol`、`gpt-6.1-sol`）；
本渠道挂载的另外 3 个（`gpt-5.5`、`gpt-5.6-terra`、`gpt-6-luna`）上游已不提供，因此稳定返回 404 `model_not_found`。

### 5. 结论

- **实测**：这条渠道的可用模型响应时间横跨 5～25 秒，判定线 10 秒正好落在分布中间 → 结果随机翻转，这是「一刀切全超时」的直接原因。
- **实测**：并发不是原因（串行照样超时；4 并发没有系统性放大）。
- **实测**：单测与批量走的是**同一个探测函数、同一条判定线**，本来就不该给出不同结论；旧代码里二者都用了 10 秒，所以差异全部来自上游抖动。
- **产品裁定（阿禅）**：超过 15 秒才回话的模型，业务上等同于不可用 → 判定线定 15 秒。

## 二、改了什么

### 1. 服务端判定线（`src/app/api/admin/ai-config/route.ts`）

- 新增具名常量 `MODEL_PROBE_TIMEOUT_MS = 15_000`（原为裸写的 `10_000`），单测与批量共用，杜绝两处漂移。
- 超时原因不再泄露 Node 的英文原文 `The operation was aborted due to timeout`，改为可读中文：
  `上游 15 秒内没有返回任何响应（超时）`。
- 并发上限仍为 4（有实测支撑：并发不是瓶颈；降低并发只会让整批更慢）。

### 2. 结果展示（新增 `channel-model-test-list.tsx`，页面与弹窗共用）

每个被测模型一行，直接铺开、不需要再点「查看失败原因」：

- 通过 → `已通过` + 耗时；
- 未通过 → `未通过` + `失败原因：…`（为空时显示「未返回原因」）；
- 每行同时给出模型显示名与原始 `model_id`，两者都在，杜绝「分不清测的是哪个」。

页面结果条（`KeyTestResultsBar`）与「同步模型」弹窗内的结果区都改成同一份清单，口径一致。

### 3. 顺带修掉同类残留：模型显示名被折叠

`getModelDisplayName` 会被部分入口**重复调用**（把库里已存的可读名再喂回推断函数），
导致 `gpt-5.6-sol` 的显示名 `GPT-5.6 Sol` 被 `gpt-5` 兜底规则折叠成 `GPT-5`——
于是同一条渠道上 `gpt-5.5` 和 `gpt-5.6-terra` 显示成同一个名字，用户根本分不清测了哪几个。

- 新增 `resolveModelDisplayName(displayName, modelId)`：库里已有可读名就直接用，只对原始 ID 做推断。
- 四处同类写法全部收口（`compute-pool-panel`、`channel-pool-view`、`sync-models-dialog`、`ai-config/availability`），并加断言防止复发。
- 补充歧义 ID 的可读名：`gpt-5.5` → `GPT-5.5`、`gpt-5.6-terra` → `GPT-5.6 Terra`。
