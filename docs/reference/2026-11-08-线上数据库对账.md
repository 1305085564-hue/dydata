# 线上数据库对账（2026-11-08）

> 范围：`supabase/migrations/` 文件（235 个 + deferred 1 个）↔ 本地测试库（127.0.0.1:54322）↔ 生产库（远程，主机已打码）。
> 性质：**全程只读**。两侧连接第一条语句均为 `set default_transaction_read_only = on`，并校验 `transaction_read_only = on`；未执行任何写入、DDL、迁移或修复。
> 工具：`scripts/audit/db-drift-report.mjs`（本次新增，只读，可每月复跑）。完整机器清单（含每条明细、SECURITY DEFINER 全量表）见 [机器清单](./2026-11-08-线上数据库对账-机器清单.md)。

## 一、给阿禅的大白话

这次对出来 **三类** 差异，不是"几个函数写错了"，而是"两个库已经不是同一套东西"：

1. **账本对不上实物。** 生产有 3 条迁移是按执行时间登记的、不是文件名版本；仓库里有 9 个迁移文件在生产账本上没有记录，但其中 7 个的效果其实已经在线上（我逐个查了对象，确认已生效）；本地账本也有"记了已执行、可东西还在"的情况。**结论：以后不能拿迁移账本判断线上是什么状态，只能直接看库里的实物。**
2. **同名不同物。** 17 张同名表两边的列不一样（有的整张表形态都不同），44 个同名函数两边实现不一样（22 个只差一句安全设置，16 个是真正的逻辑差异），还有 18 个函数只在生产、19 个只在本地。
3. **权限两边不对称。** 线上把 200 多个内部函数收得很紧，本地还留着默认授权；线上有 3 张台账/备份表没开行级权限，**拿前端公开的匿名钥匙就能读、改、清空**。

**最严重的三条，会导致什么：**

- **台账/备份表全裸**：任何登录或未登录的人，用浏览器里就能拿到的匿名钥匙，可以读走、改掉、甚至清空这三张表（现在分别是 5、3、13 行）。这三张表是历史数据修正的凭证，被改掉就再也说不清哪条数据为什么被改过。
- **本地"测过了"不等于线上"是这套"**：豁免审批、团队加入审批、提醒次数这些核心流程，本地和生产跑的是两套不同实现（生产是转发到 v2 的薄壳，本地是完整实现；提醒次数在线上有"只能查自己"的校验，本地没有）。**谁要是拿本地这套去覆盖线上，审批校验会被悄悄去掉。**
- **同名表不能互相重建**：像内容流水线那几张表，两边结构完全不同。任何"按仓库文件整体重建"的迁移，会把线上较新的权限收紧、较旧的兼容列、以及线上独有的功能一起推翻。

## 二、结论：三方关系

- **仓库文件不是唯一真源**：仓库更像"生产 + 本地各自手工改动的合订本"，两边都有一部分改动没回到文件里。
- **生产不是"旧版本"、本地也不是"新版本"**：两个方向都有新东西。生产在权限收口、v2 包装、`has_permission` 的职位兜底、`review_team_join_request` 的团队范围校验上更新；本地在新表结构（内容流水线、抖音同步）、1 参数版函数、`has_violation_permission` 上更新。
- **10-03 那个文件头写的漂移清单已经过时**：它说"生产的 `admin_cockpit_summary` 是转发到 v2 的薄壳"——实测生产现在**一个 cockpit 函数都没有**（`pg_proc` 查 `%cockpit%` 返回 0 条）；它说"本地 `get_leaderboard_rows` 多 4 个输出列"——实测两侧返回列都是 18 列、完全一致，只剩 `search_path` 一句不同。文件头不能再当清单用。

### 中

- **时区配置两侧不一致**：生产 5 个必查函数（`get_fulfillment_range`、`get_fulfillment_calendar`、`get_today_submission_status`、`set_permanent_exemption_owner_atomically`、`clear_permanent_exemption_owner_atomically`）全部带 `TimeZone=Asia/Shanghai`；本地后两个**没有**（实测 `proconfig`）。本地用本地时间测出来的"今天"，与线上判断口径不同。
- **本地有 7 个函数用 `current_date` 却无时区配置**（`admin_cockpit_summary`、`admin_cockpit_summary_v2`、`admin_pending_submissions_today`、`admin_pending_submissions_today_v2`、`set/clear_permanent_exemption_owner_atomically`、`get_leaderboard_rows`）；生产只有 `get_leaderboard_rows`。
- **同名约束两侧不一致**：只在生产（共享表）7 条、只在本地（共享表）42 条、定义不同 6 条（实测 `pg_constraint`）。关键几条：`daily_reports_data_source_check` 生产只允许 `ai/manual`、本地允许 `ai/manual/douyin`；`profiles_data_scope_check` 生产仍有 `all`、本地已收紧为 `self/team`；`audit_logs.user_id` 生产 `ON DELETE SET NULL`、本地 `CASCADE`；`content_tag_link` 主键不同（生产联合主键、本地代理主键）。
- **RLS 策略"代际不同"**：两侧开关完全一致（0 张不一致，实测 `relrowsecurity`），但策略集合差异大：只在生产（共享表）14 条、只在本地（共享表）45 条、条件不同 15 条。15 条条件差异大多只是 `(select auth.uid())` 与 `auth.uid()` 的写法等价；但 `content_item` 的策略用的是**不同列名**（生产 `owner`、本地 `owner_user_id`），属结构差异派生，不能当等价看待。
- **触发器**：生产 28、本地 30；只在生产 1 个（`content_item.trg_log_content_edit`）；只在本地 3 个（抖音同步表的 `updated_at` 触发器）。生产少了写日志触发器，说明该触发器对应的历史逻辑已被另一代实现替代（待判断是否需要）。
- **`report_date_must_match_published_at` 已在生产存在且生效**（实测 `pg_constraint.convalidated=true`，定义按上海自然日比对），本地同样存在，这一条是本次少数"两边一致且符合预期"的结论。

### 低

- **仅 `search_path` 不同**：44 个差异函数里有 22 个只差这一句（生产统一为 `pg_catalog, public, pg_temp`，本地多为 `public`）。语义无差，属线上安全加固未回写文件。
- **6 个函数体相同、只有配置/权限不同**（`touch_updated_at` 等）。
- **生产 83 个外键没有前导列索引**（启发式：索引首列必须等于外键列；实测 `pg_indexes` 解析）。其中 `daily_reports_video_id`、`idx_daily_reports_video_id` 实际存在部分索引，属统计口径偏保守，只作巡检项。
- **只在生产 11 张 / 只在本地 7 张表**：生产多的是历史内容流水线 + 集团模式 + `ocr_recognition_logs` + 两张修正台账；本地多的是 `douyin_*` 六张同步表和旧 `audit_log`。这些是"功能未上线/已退役"的差，不是错误，但要在文档里标清楚。

### 6. 行级权限（RLS，实测：`pg_class.relrowsecurity` + `pg_policies` + `information_schema.table_privileges`）

- RLS 开关：**0 张表不一致**（共享表全部同开或同关）。
- 生产未开 RLS 但 anon/authenticated 可写：3 张表（即 H1），权限为 `DELETE,INSERT,REFERENCES,SELECT,TRIGGER,TRUNCATE,UPDATE`。

## 七、建议的处理顺序（只建议，均未执行）

1. **先止血**：三张无 RLS 的台账/备份表导出留档后收权，消除匿名可写。
2. **立基线**：把生产当前的 `pg_proc`（含 `proconfig`/`proacl`）、`pg_policy`、`pg_constraint` 导出为"生产基线"存档，之后所有重建以它为起点，而不是以仓库文件或本地库为起点。
3. **补账本**：对"已生效但无账本记录"的 7 条迁移单独补记录（需授权，非本轮）。
4. **分域回写**：按域（履约/豁免、权限、排行榜、AI 配置、内容流水线）把生产定义回写进仓库，一次只做一个域，避免整体重建。
5. **清理**：`remove_group_mode` 与抖音同步按"未上线/待上线"单独立项，别混在漂移里；死代码（`insight-period.ts` 等）单独处理。
6. **时区**：`get_leaderboard_rows` 补时区或强制调用方传日期。
