## 根因与影响范围

本轮按阿禅要求，先查共同原因再修症状；两个发现不代表全站只有两个问题，以下结论仅覆盖 API 渠道配置调用链。

| 核对项 | 实测或代码证据 | 结论 |
|---|---|---|
| 数据库契约 | Supabase 只读核对 ai_providers、ai_provider_keys、ai_provider_key_models、ai_feature_bindings 全字段，以及 manage_ai_feature_lifecycle、bump_provider_key_failure、bump_provider_key_model_failure 的参数 | 当前调用所需字段、函数齐全，未发现连错库或漏迁移造成的批量失效 |
| 两个生产域名 | 正常登录后配置读取均 200，均返回 10 渠道、119 模型；带各自 Origin 的无效动作均正常返回参数错误 400，而非来源拒绝 403 | 未发现生产域名来源检查不匹配；无效动作不执行配置写入 |
| 上下移没有效果 | 生产有三个 P55；旧实现仅互换数字，55 与 55 互换无变化；新增测试在旧代码下失败 | 同顺位处理遗漏，非数据库不支持写入 |
| 失败没有明显反馈 | 真实浏览器测试 api9 的 Gemini Flash-lite，返回 testResult.ok=false、上游 404；短暂 toast 可见，模型行仍只显示历史健康 | 结果未留在操作行；失败不改变调度健康是原有规则，继续保留 |
| 同类反馈遗漏 | 渠道视角只显示“测试失败”，不显示 message；结果仅按 model_id 保存，不区分渠道；两个视角的同顺位次序也不一致 | 修复共同展示机制及结果归属，未扩大到其他业务 |

## 实施

- 同顺位交换按统一稳定顺序执行，展开碰撞的整数顺位；不改变其他渠道的相对顺序，不调整无关的重复权重。保留已有写入冲突与失败恢复机制。
- 两个视角采用相同的同顺位排序规则；保存后明确提示成功，保存期间该卡片禁止重复排序。
- 两个视角共用“本次测试通过／未通过”的行内结果，失败显示返回原因，成功显示耗时；按渠道和模型保存，视角切换仍可见，整页刷新后重新测试。
- 现有健康与调度规则保留：失败探测不修改熔断计数，不停用模型，不改当前可用的 Haiku 截图识别绑定。
