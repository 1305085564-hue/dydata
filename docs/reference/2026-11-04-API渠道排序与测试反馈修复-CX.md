## 实施

- 同顺位交换按统一稳定顺序执行，展开碰撞的整数顺位；不改变其他渠道的相对顺序，不调整无关的重复权重。保留已有写入冲突与失败恢复机制。
- 两个视角采用相同的同顺位排序规则；保存后明确提示成功，保存期间该卡片禁止重复排序。
- 两个视角共用“本次测试通过／未通过”的行内结果，失败显示返回原因，成功显示耗时；按渠道和模型保存，视角切换仍可见，整页刷新后重新测试。
- 现有健康与调度规则保留：失败探测不修改熔断计数，不停用模型，不改当前可用的 Haiku 截图识别绑定。

## 11:14 补查：共同机制与更广影响

阿禅再次明确：发现两个功能异常不代表只有两个问题，必须从原因反推影响面。上轮数据库契约核对和两个症状的回归不足以证明整个模块完整；2582 项测试通过也不能替代不同入口之间的一致性验证。

本次继续只读追查历史、共享统计、正式选路、截图试跑和日志结果解释；未修改应用代码或生产配置。

### 已实测确认：页面统计与正式调度不一致

读取当前生产配置，在同一进程中分别调用现有 `computeAvailability` 和 `listRankedProviderKeyModels`；只代入配置，不向上游发请求，不读出真实密钥。页面统计漏掉模型级故障冻结判断，且对全站上架字段为 null 的解释与运行时不同。

| 模型系列 | 页面统计可调度渠道 | 正式选路接纳渠道 |
|---|---:|---:|
| Claude Haiku 4.5 | 2 | 1 |
| Gemini 2.5 Flash | 3 | 2 |
| GPT-6 Luna | 3 | 1 |
| GPT-6 Sol | 4 | 3 |
| Gemini 2.5 Flash-lite | 2 | 1 |
| DeepSeek Flash | 1 | 0 |

这是 11:14 读取快照与当时健康状态的对照，不代表这些上游模型都无法响应；正式选路还可能使用其他模型兜底。119 条模型记录中 98 条全站上架字段为 null，不能把这 98 条直接当成 98 个线上故障。

最小固定对照也确认：同一渠道本身正常、其某模型被暂停调度时，页面算 1，实际选路算 0；全站上架字段为 null 的启用模型同样出现 1／0。

影响面由同一 `useAvailabilityReport` 扩散至业务功能调度页的渠道数、模型选择器的可选状态、业务保障及回落提示。模型卡片的历史健康显示也主要读取渠道记录，不能当作每个模型最新测试都通过。此问题上轮没有修复。

### 已实测确认：截图识别试跑选到另一条渠道

`handleOcrTrialRun` 从按创建时间返回的模型记录中拿第一条启用模型，没有复用正式选路、模型故障过滤和跨渠道顺位。当前 Haiku 的试跑会选 `api1 default`，而相同配置下正式选路仅接纳 `claude`。这解释了为何“后台试跑失败”与“真实上传成功”可以同时发生；本次未再次调用这些上游，不把选路差异当成新的实时连通测试。

影响范围是截图识别的后台试跑可信度；尚无证据说明现有正常上传因此损坏。此问题上轮没有修复。

### 缺陷来源与排查边界

- 实测历史：排序直接互换权重的实现自 2026-07-30 已存在，没有处理重复数字；不是 11-04 切库新引入。
- 实测历史：页面可用性统计形成于 10-04（`3dc19b7f`），10-05 正式选路加入模型健康过滤（`d15df6cc`），前者未同步；截图试跑自 10-07（`8c972fb3`）另写选路，渠道视角自 10-09（`80907daa`）另存测试结果。
- 共同机制问题：测试展示、可用性统计、正式调用分开实现，规则更新后未完整同步；原有测试缺少“同一配置同时核对这些入口”的对照，所以测试全绿不能排除这些差异。
- 日志解释对照：`testResult.ok=false` 的 HTTP 200 探测响应会被共享包装补为 `businessSucceeded=true`。这说明“测试请求执行完成”不能当成“上游通过”；页面已正确读取嵌套的 ok，这不是前述 toast 缺少常驻结果的根因。未证实其他接口因此出现用户可见故障，不扩大修复共享包装。
- 当前仍可交付的部分仅是 `40c3733e` 的排序、常驻反馈、结果归属修复；完整收口还需使配置页可用性判断与截图试跑复用正式调用规则。保持当前 Haiku 绑定、数据库、上传入口不变，不改动其他正常业务。
