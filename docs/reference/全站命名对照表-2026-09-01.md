## 一、核心结论（先说人话）

网站经过多轮改版，命名留了三类坑：

1. **展示名 vs 路由英文名不一致**：一大批管理页的路由段是英文旧词（`modules` / `collaboration` / `rewrite` / `growth`），用户看到的却是中文（成员管理 / 岗位管理 / 文案助手 / 数据分析）。按既有约定**路由不改**，只需统一"展示名"。
2. **三处"同名不同实"硬冲突**：
   - `数据分析`(导航+metadata) vs 旧 `经营分析`(`PERMISSION_LABELS.view_analytics` 代码常量 + 已死模块 `/admin/analytics`)——已改为统一展示「数据分析」，路由名 `growth` 保留。
   - 旧 `系统维护`(导航+metadata) vs `系统设置`(`PERMISSION_LABELS.manage_system` + 模块地图 + 权限文档)——已改为统一展示「系统设置」。
   - `文案助手`(导航+metadata) vs `AI 文案助手`(`PERMISSION_LABELS.use_ai_copy`)。
3. **已下线模块的残留**：`/violations` 路由已删，但 `middleware.ts` 仍留 matcher；`conversion-hub` 页面路由下线，但 `lib/` 被 `video-submit` 真实依赖；`view_conversion`(转化中心)、`review_violations`(违规复核) 两个权限键模块没了但键还在（后者受禁删保护）。

**已收口的两个真 bug**：已把 `PERMISSION_LABELS.view_analytics` 从「经营分析」改成「数据分析」，把 `/admin/settings` 的导航、metadata、页面标题和无权限态标题从「系统维护」改成「系统设置」——两者都让"代码常量/页面展示/文档"对齐，且不影响任何路由。

## 六、生产库残留开关查询（只读，不修改）

本机无生产库直连，且禁区禁止改库。第二阶段清理前，先用以下只读 SQL 枚举真实残留键：

```sql
-- 枚举生产库 profiles.permissions 中实际出现过的所有键
SELECT DISTINCT key
FROM profiles,
     jsonb_each_text(permissions) AS t(key, val)
WHERE val = 'true'
ORDER BY key;
```

将结果与 11 个现役键（`view_analytics, export_data, view_conversion, review_content, manage_fulfillment, manage_videos, manage_members, review_violations, manage_system, use_ai_copy, use_ai_assist`）取差集，差出的即为需清理的残留键（预期含 `manage_invite` / `view_audit_log` / `view_all_data` 等）。**清理只走数据 migration，绝不动 RLS / 历史 migration / 已执行生产数据行结构。**
