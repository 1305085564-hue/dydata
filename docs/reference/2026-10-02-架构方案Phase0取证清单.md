# 架构方案 Phase 0 取证清单（2026-10-02）

本清单只记录本地代码和门禁能够直接复现的证据，不把静态扫描、构建通过或旧报告当成生产权限、RLS、真实角色和部署状态证明。状态含义：`已核实` 表示当前口径有明确证据；`待核实` 表示只有部分证据；`已撤销` 表示原数字/结论不能继续沿用。

## 五条原始数字逐条复核

### 1. `visibleUserIds` 的“147 个文件引用”

**状态：已撤销。** 原数字没有说明是文件数、文本次数、真实消费点还是测试调用点，当前固定命令得到的结果也不是 147。

实测命令：

```sh
printf 'files='; rg -l --glob '*.{ts,tsx,js,jsx,mjs,cjs}' '\bvisibleUserIds\b' src scripts | wc -l
printf 'occurrences='; rg -o --glob '*.{ts,tsx,js,jsx,mjs,cjs}' '\bvisibleUserIds\b' src scripts | wc -l
printf 'test_files='; rg -l --glob '*.{ts,tsx,js,jsx,mjs,cjs}' '\bvisibleUserIds\b' src scripts | rg '\.test\.' | wc -l
printf 'member_access_or_assignment_lines='; rg -n --glob '*.{ts,tsx,js,jsx,mjs,cjs}' '(?:\.visibleUserIds\b|\bvisibleUserIds\s*[:=])' src scripts | wc -l
```

输出：

```text
files=70
occurrences=315
test_files=34
member_access_or_assignment_lines=238
```

这里的 238 行只是静态消费形态的代理值，不冒充真实调用点；真实调用点仍需按模块逐项审阅。

### 3. “15+ 个文件缺错误处理”

**状态：已核实（口径修订）。** 固定基线仍只能说明“71 个 route 中 54 个没有静态 `try/catch`”，不能直接推出 54 个文件都缺少有效错误处理，也不能证明原稿的“15+”口径。S2 新增的契约覆盖守卫 `src/app/api/mutation-contract.coverage.test.ts` 会枚举所有导出写入 handler，并要求其进入统一契约清单或显式豁免；`src/app/api/mutation-contract.behavior.test.ts` 用真实 `Request`/`Response` 调用统一观测出口，验证响应分层字段和单条结构化记录。因此，写入路由的错误出口证据不再依赖每个文件都出现静态 `try/catch`。边界保留：只读 GET 路由不属于写入契约范围，本条不据此声称 GET 路由已覆盖。

同上方基线命令的关键输出：

```text

routesWithTryCatch=17
routesWithoutTryCatch=54
```

下一步需要按 route 清单检查统一错误分类、状态码和用户可见兜底，完成前不把“15+”写成事实。
