# 数据管理页面性能体检与修复报告

> 范围：`/admin/collaboration` 首屏与个人档案首层抽屉。环境：本地生产构建 + 本地 Supabase 隔离库，未做线上部署。

## 结论

首屏业务数据没有额外客户端接口瀑布，主要问题在服务端数据集加载器：日报查询完成后，查找表、认证状态、小队目录仍按顺序等待；首层抽屉的动态组件 loading 又额外挂了一层固定遮罩，冷点击时会出现“先一层、再一层”的弹跳感。

已完成：

- 日报完成后并行读取查找表、文案认证、小队目录；快照与话题标签保留并行读取。
- 对每个独立读取增加 `[perf] collaboration.*` 分步耗时，`DYDATA_PERF_LOG=1` 开启。
- 文案认证候选与月度数据集并行准备，认证失败仍只降级候选列表。
- 移除动态档案卡的第二层固定 loading 遮罩；Sheet 自己负责唯一入场动画。
- 抽屉宽度只过渡 `max-width`，避免内容和错误态更新时触发整层 `transition-all`。

## 实测证据

| 指标 | 改前（HEAD 临时副本） | 改后（当前工作树） |
|---|---:|---:|
| 数据集分步耗时 | 报表 18ms → 查找表 12ms → 认证 6ms → 小队 6ms → 快照/话题各 6ms，按序等待 | 首轮数据集 48ms；报表 18ms、查找表 17ms、认证 11ms、小队 13ms、快照/话题各 12ms，其中独立读取并发；热缓存 0ms |
| 首层冷点击（40 个 50ms 采样点） | 旧实现保留第二层 loading 代码路径 | 1 个 dialog、1 个 Sheet 遮罩、0 个 loading 面板 |
| 个人档案抽屉用例 | — | 场景 1–5 通过；宽度 672px ↔ 896px、返回、ESC 均通过 |

本地隔离库只有 5 条种子日报，改前后总耗时受网络抖动影响，不能把小样本 48ms 直接外推线上；并发改造的收益会随成员、作品和批次数增长而放大。线上 person 冷调用仍按项目事实保留为待治理项。
