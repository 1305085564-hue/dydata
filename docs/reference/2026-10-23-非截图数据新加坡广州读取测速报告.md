# 非截图数据从新加坡到广州的读取测速报告

**日期：** 2026-10-23  
**范围：** 只读核对；生产 Supabase 只读查询；广州使用临时私有 COS 桶保存一份只读结果快照，测试结束后对象和桶均已删除。未改生产数据库、业务配置或页面代码。

## 结论

可以确认一件事：**把视频复盘使用的非截图数据做成广州的只读派生快照，读取阶段有明显收益。**

不能确认另一件事：**把这些数据迁到广州后，当前视频复盘页面整体一定大幅变快。** 当前页面的服务端固定部署在 Vercel `sin1`，页面 loader 仍查新加坡 Supabase；如果只把快照放到广州、读取方仍在 `sin1`，跨区链路可能吃掉收益，甚至变慢。

生产数据库里的 `videos`、`video_metrics_snapshots`、`daily_reports` 等表目前属于同一个 Supabase PostgreSQL 项目。它们有外键、权限过滤、排序、分页、最新快照和“上一条作品”计算，不能在现有架构下按表或按部分记录直接搬到广州后继续保持同一套实时查询语义。可以迁移的是经过定义的数据产品，例如“视频复盘列表当前页快照”“历史只读报表快照”或按日期生成的汇总，而不是把主库的一部分简单换个地域。

## 生产数据盘点（只读）

生产 Supabase Storage 当前列出的 3 个桶全部是截图用途：`submission-screenshots`、`work-screenshots`、`violation-screenshots`。没有发现另一类业务文件桶可直接迁移来解决数据库读取问题。

## 数据库真实读取基线

测试方式：从当前中国网络环境，以生产 Supabase service role 做只读 REST 查询；每个查询先预热 2 次，再测 8 次。service role 只用于本次读取，输出不保存业务数据。

| 查询 | 返回量 | 返回大小 | p50 | p95 |
|---|---:|---:|---:|---:|
| `videos` 200 条 | 200 行 | 613 KB | 约 319 ms | 约 367 ms |
| `video_metrics_snapshots` 200 条 | 200 行 | 377 KB | 约 136 ms | 约 164 ms |
| `videos` 携带快照 100 条 | 100 行 | 345 KB | 约 160 ms | 约 174 ms |

对视频复盘实际使用的 `admin_content_list_page` RPC 做了同样的只读实测：

- 首次冷调用约 **1.39 秒**；
- 热调用约 **0.30–0.39 秒**；
- 每次扫描约 **2,488 条活动视频**，当前页只返回 **18 条**，返回 JSON 约 **30.6 KB**；
- 10 个并发请求时，墙钟 p50 约 **0.79 秒**，p95 约 **0.88 秒**。

这说明视频复盘的主要成本是数据库查询、筛选、排序和派生计算，不是浏览器下载 30KB JSON 的带宽成本。

## 广州只读快照对照

为了验证“可迁移的非截图数据”本身，把同一个 `admin_content_list_page` 返回结果（30,580 字节）复制到一个新建的广州私有临时桶，SHA-256 与源数据一致；随后对新加坡 Supabase RPC 和广州 COS 快照分别做并发读取。测试结束后对象删除 HTTP 204，临时桶删除 HTTP 204。

| 并发读取同一份列表快照 | 新加坡 Supabase RPC p50 / p95 | 广州快照 GET p50 / p95 |
|---:|---:|---:|
| 1 | 348 / 362 ms | 98 / 110 ms |
| 2 | 330 / 360 ms | 101 / 107 ms |
| 5 | 531 / 608 ms | 102 / 111 ms |
| 10 | 794 / 884 ms | 97 / 113 ms |

同一份数据换成广州静态快照后，**读取阶段约减少 65%–88%**，并发升高时差距更明显。这是一个只读快照的上限对照：广州快照没有执行 SQL、权限过滤、实时排序、最新快照计算和“上一条作品”计算，不能把这组数字直接写成页面整体提速。

## 对视频复盘页面的实际含义

当前页面的部署区域在 [`vercel.json`](../../vercel.json) 中固定为 `sin1`。`/admin/content` 的服务端 loader 会在新加坡侧执行 RPC，并继续查询成员、标签、上一条作品和快照等动态数据。

因此有两个不同方案：

1. **只复制数据到广州，页面仍从 `sin1` 读。** 这只能证明广州对象本身更快，不能保证页面更快；还要承担 `sin1 → 广州` 的跨区请求和快照新鲜度问题。
2. **把只读快照的读取入口也放到广州，或让浏览器/CDN直接命中广州。** 这才可能兑现上表的收益，但需要重新设计权限、增量更新、失效和回退，不能把 COS 文件直接替代数据库。

对视频复盘详情页，仍需实时查视频主体、快照、拆段、标签和历史对比数据。只迁移其中一块，页面仍会被剩余数据库查询限制；要证明整页收益，必须在 Preview 做一次“同一页面、同一账号、同一批数据、只切只读数据来源”的 A/B 对照。

## 建议的下一步

推荐优先做**只读派生数据的广州副本**，不迁主库、不迁实时写入：

- 先选视频复盘列表的日期快照或按账号/日期的历史复盘汇总；
- 保留新加坡 Supabase 作为权限、写入和实时事实源；
- 在广州提供带版本号和过期时间的只读接口；
- Preview 只切这一块，测首屏、详情打开、5/10 个并发用户和数据新鲜度；
- 若 Preview 的整页 p95 有稳定收益，再决定是否扩大到历史日报或协作报表。

当前证据支持“**非截图只读数据值得做广州副本实验**”，不支持“**现在就把数据库部分迁到广州**”或“**当前生产页面会自动大幅变快**”。
