# 截图上传维护手册

> 最后核对日期：2026-09-27（全文路径与命令逐条验证；清理 3 处死路径——`video-tags/confirm` 死接口、已删的旧素材库弹窗、已删的旧版主表单文件；修好第 8 节 lint 命令）。
> 2026-10-10 补充：第 9 节加「AI 返回格式无法识别」的渠道排查、第 10 节加事故 C（看图渠道不看图）。

这份文档只管一件事：`/dashboard` 里的“截图上传 + 识别 + 提交”链路。

这条链路是 DYData 最关键的入口，出问题会直接影响员工提交、日报落库、视频标签、后续分析，所以后续谁改这里，都先看这份文档。

## 1. 这条链路到底包含什么

用户看到的是“上传截图”，但实际上一共有 4 段：

1. 前端上传截图并调用 OCR
2. OCR 返回结构化识别结果，前端让用户确认
3. 用户补齐标题、文案、话题标签、内容标签
4. 提交到 `/api/video-submit`，一次写入：
   - `videos`
   - `video_metrics_snapshots`
   - `daily_reports`
   - `video_tags`

一句话：

- `/api/ocr-screenshot` 负责“看图识别”
- `/api/video-submit` 负责“最终入库”

## 3. 当前正确行为

### 槽位规则

- `screenshot_1`：必传，互动数据截图
- `screenshot_2`：必传，完播留存截图
- 当前只保留两张截图；`screenshot_3` 已彻底下线，前端状态机、上传接口、OCR 接口和提交接口都不再接受第三截图槽

### 截图识别口径（2026-08-25 更新）

- 截图类型不再由 AI 自动分类（`detectScreenshotType` 已删除），改由槽位直接决定：`screenshot_1` → `data`，`screenshot_2` → `retention`
- 推流曲线形态识别（曲线类型/首峰位置/掉速程度/长尾强弱）已全站下线，OCR 不再返回 `curve_info`，前端不再展示
- 留存分段分析（跳出峰值/回放峰值/分段摘要）已全站下线；retention 只提取 4 个数字指标：`avg_play_duration`、`bounce_rate_2s`、`completion_rate_5s`、`completion_rate`
- 入库口径：`retention_screenshot_url` 固定由 `asset_role=screenshot_2` 直接写入；`curve_screenshot_url` 不再写入新值，列和历史数据保留（死列清理是后续独立 migration 任务）
- 截图地址入库使用站内相对读取地址 `/api/submission-screenshots/file?path=...`；服务端仍兼容当前域名下的旧绝对地址，禁止再写入 `localhost` 绝对地址，避免生产域名切换后历史编辑被来源校验挡住。
- 视觉模型将退役，首页截图识别后续切换为百度 OCR（另任务接入）
- OCR 额外尝试识别页面明确标注的作品发布时间，写入 `recognized_fields.published_at`；趋势图横轴日期不参与业务日期判断。
- 作品发布时间识别仅作证据与预填，无法识别或置信度不足时必须人工核对；服务端补交门禁统一按真实上传时刻与业务日期规则判断。

状态机要求：

- 必传截图没传，不能提交
- 必传截图已上传但识别失败时，可以手动填写指标后提交；截图仍会作为佐证保留
- 必传截图还没确认，不能提交
- 标题、文案没补齐，不能提交
- 话题标签没选，不能提交

### 指标字段的来源与 OCR 原值（2026-09-26 更新）

每个指标字段同时记三件事：当前显示值 `value`、取值来源 `source`（`ocr` / `manual`）、最近一次识别到的原值 `ocrValue`（含同时刻置信度 `ocrConfidenceLevel`）。

- 识别到值的字段一律刷新 `ocrValue`；只有用户没手打过（`manuallyEdited` 不为真）的字段才跟着刷新当前显示值
- 用户手打过、之后又重新识别的字段保留用户当前值，字段右侧出现 ↺「恢复识别值」，点了才换成最新识别值，并把字段交回 OCR 管理
- 「恢复识别值」只还原该字段，不重跑识别、不发请求、不改截图资产
- 旧草稿或历史编辑回填没有 `ocrValue`，按「无原值」处理，不推断历史识别值，也不显示恢复入口
- 提交始终写当前显示值，`ocrValue` 只留在前端状态里，不写业务指标列


### 历史记录修改边界

`首页 /dashboard → 历史记录 → 查看并修改日报数据` 走 `history-report-edit-form.tsx`。

这不是截图上传链路的重新提交：

- 只修正旧 `daily_reports` 里的标题、文案、发布时间和指标；
- 不要求重新上传两张截图；
- 不调用 `/api/video-submit`，避免旧日报因为没有原始 `video_id` 而生成新的 `videos` 记录；
- 不调用 OCR，不改历史截图资产。

如果以后要把历史修改也升级成完整视频提交编辑，必须先补齐旧日报与 `videos` 的稳定关联，不能只把表单换成 `VideoSubmitForm`。

### 内容标签规则

- 最多 3 个
- 每个标签是一个独立词
- 前端会去空格、去重
- 数据库里按 3 条独立 `video_tags` 保存
- 不能把 3 个词拼成 1 条字符串再存

### 标签维度规则

单值维度，同一个视频只能有 1 条：

- `题材`
- `表达形式`
- `CTA类型`
- `内容结构`
- `目标受众`
- `话题`

多值维度：

- `关键词`

也就是：

- 同一个视频可以有 3 条 `关键词`
- 但同一个视频不能有 2 条 `题材`

## 4. 这条链路最容易炸的地方

### 4.1 OCR 识别没问题，但提交时报错

重点先查：

- `/api/video-submit`
- `video_tags`
- `daily_reports`

最常见原因不是图片上传本身，而是最终入库阶段写炸了。

### 4.2 改了数据库约束，但代码还在用旧 `upsert`

这是这条链路最危险的坑之一。

真实事故：

- 之前 `video_tags` 用的是 `onConflict: "video_id,tag_dimension"`
- 后来为了支持“一个视频 3 个关键词”，把数据库唯一规则改成：
  - 非关键词：`(video_id, tag_dimension)` 唯一
  - 关键词：`(video_id, tag_dimension, tag_value)` 唯一
- 如果代码还继续写老 `upsert`，就会报：
  - `there is no unique or exclusion constraint matching the ON CONFLICT specification`

现在的正确做法：

- 不再依赖这类旧 `upsert`
- 改成“删旧标签，再插入新标签”

涉及文件（历史记录，按 2026-08 当时实况；现役只剩第一项）：

- `src/app/api/video-submit/route.ts`
- ~~`src/app/api/video-tags/confirm/route.ts`~~（死接口，2026-08-09 `4e7823fd` 删除）
- ~~`src/app/(app)/admin/videos/video-detail-dialog.tsx`~~（旧素材库弹窗，已随 `/admin/videos` 合并删除；标签现只读展示于 `/admin/content` 详情抽屉，改动一律走提交链路）

### 4.3 同一批 `upsert` 命中同一行两次

真实事故：

- 一个视频提交 3 个关键词
- 代码把 3 个关键词都当成同一个维度 `"关键词"` 去做同批 `upsert`
- 数据库会报：
  - `ON CONFLICT DO UPDATE command cannot affect row a second time`

现在的正确规则：

- 3 个关键词必须是 3 条独立记录
- 不能用“同批相同唯一键”的写法

### 4.4 只改代码，不推数据库 migration

这是第二个高频坑。

截图上传链路不是纯前端功能，它经常同时依赖：

- 前端表单逻辑
- API 校验
- Supabase 表结构 / 约束

如果只 push 代码、不 push Supabase migration，就会出现：

- 本地正常
- 线上数据库规则还是旧的
- 用户一提交就报错

所以涉及截图上传的改动后，必须同时确认：

1. 代码已 push 到 GitHub
2. Vercel 已部署成功
3. Supabase migration 已推远端

## 7. 每次改完后的必测清单

至少测这 8 项：

1. 只上传 1 张图，页面应提示不能提交
2. 上传 2 张必传图，识别成功后可继续填写
3. OCR 失败时，页面应明确提示，可重试或手填
4. 标题为空时不能提交
5. 文案为空时不能提交
6. 内容标签为空时不能提交
7. 选 3 个内容标签后，提交成功
8. 提交后数据库里能看到：
   - 1 条 `videos`
   - 1 条 `video_metrics_snapshots`
   - 1 条 `daily_reports`
   - 1 条 `话题`
   - 1 到 3 条 `关键词`

额外建议测：

9. 重复编辑同一条视频，标签会正确覆盖旧值
10. 后台视频详情**已无 AI 标签编辑入口**（2026-09-27 核对）：`/admin/content` 详情抽屉只读展示标签；验证标签展示不报错即可，标签变更一律经组员提交/编辑链路（`/api/video-submit`）发生

## 9. 出故障时的排查顺序

不要上来就猜，按这个顺序查：

1. 先看用户报错是在“上传图片”阶段还是“最终提交”阶段
2. 如果是上传阶段：
   - 查 `/api/ocr-screenshot`
   - 查 AI 功能 `ocr_screenshot` 是否被禁用
   - 查图片格式 / 大小 / 内容类型
   - 页面提示「**AI 返回格式无法识别**」（`error_code = AI_PARSE_FAILED`）时，先看渠道而不是看图片：
     `ocr_screenshot` 的 `channel_settings` 决定走「看图」（`vision`）还是「百度两步」（`baidu`），
     两条路各自绑自己的模型（看图 = `ocr_screenshot`，结构化 = `ocr_screenshot_structure`）。
     共享渠道里存在「收下请求但不看图」的坏渠道（返回 200 + 一段说明文字），
     绑定模型顺位第一条撞上它就会报这个错——用真实截图跑一次 `callAi` 看**正文**：
     出现「请上传截图 / 我没有看到任何截图」就说明这个渠道不给图。
     查顺位：绑定只写模型时，运行时按 `key.priority + provider.priority` 升序取该模型的所有渠道，
     不看绑定里的 `provider_key_model_id`。详细案例见
     `docs/reference/2026-10-10-截图识别返回格式无法识别-根因与修复.md`。
3. 如果是最终提交阶段：
   - 查 `/api/video-submit`
   - 查 `video_tags` / `daily_reports` / `videos`
4. 如果报 `ON CONFLICT`：
   - 先怀疑数据库唯一规则和代码写法不一致
5. 如果本地好、线上坏：
   - 先查 Vercel 是否部署到最新 commit
   - 再查 Supabase migration 是否已推远端

## 10. 已知事故记录

### 事故 A：关键词多条导致 `ON CONFLICT DO UPDATE ... affect row a second time`

现象：

- 上传时报错
- 前端看起来像“截图上传坏了”

根因：

- 3 个关键词在一次 `upsert` 里命中了同一个唯一键

修法：

- `关键词` 改为数据库层面支持多条
- 代码层不再把多个关键词塞进同一个旧 `upsert`

### 事故 B：数据库约束已改，但旧 `ON CONFLICT` 代码残留

现象：

- 报错：`there is no unique or exclusion constraint matching the ON CONFLICT specification`

根因：

- 数据库已经不是原来的唯一规则
- 代码还在拿旧冲突键调用 `upsert`

修法：

- 把相关位置全部改成“删旧再插入”

### 事故 C：「AI 返回格式无法识别」＝渠道不看图，不是图片有问题（2026-10-10）

现象：

- 两张截图都提示「AI 返回格式无法识别，请手动填写或稍后重试，截图已保留」
- 接口 `/api/ocr-screenshot` 返回 500 + `AI_PARSE_FAILED`
- 后台看渠道是「测试通过」的

根因：

- 截图识别切到了「看图」通道，绑定模型顺位第一条渠道 `api1` 根本不看图片（把多模态请求当纯文字处理），
  回一段「我目前没有看到任何截图」→ 正文里没有 JSON → 报「格式无法识别」；
- 顺位链原来只兜 HTTP 失败/超时/空正文，兜不住「200 但不是结果」，所以后面的好渠道没被尝试；
- 同一时期「百度两步」通道的结构化模型绑定行已被停用，等于两条通道都断。

修法：

- 线上先把两步绑定改到实测稳定、数值正确的渠道模型（`gemini-2.5-flash-lite` / `api9 gemin`）；
- 代码把「正文必须含 JSON 对象」纳入顺位链（`validateContent` + `hasJsonObject`），
  坏渠道记一次失败并顺位下一个，连续 3 次自动健康冻结 5 分钟；
- 完整证据、验收读数与回滚方式见 `docs/reference/2026-10-10-截图识别返回格式无法识别-根因与修复.md`。

## 11. 后续谁再改这里，必须记这 3 句话

1. 不要把“截图上传问题”只当成前端问题，它常常是最终入库问题。
2. 不要只 push 代码不 push migration。
3. 不要改了 `video_tags` 约束后还沿用旧 `upsert` 写法。
