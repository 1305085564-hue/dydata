# 本地视频复盘截图读取故障定位

日期：2026-10-26 12:09（上海时间）。范围：用户所示作品 `1dd78627` 的两张截图，定位原因；没有修改业务代码、存储、数据库或环境配置。

## 结论与边界

**口径更正：** 下文只定位了本机故障环节，没有查明底层事故诱因，也不能证明正式用户未受影响。生产三角色实测、共用恢复风险及尚缺的根因证据见[生产影响与根因复核](2026-10-26-截图事故生产影响与根因复核.md)。

**实测：直接故障在本机服务读取 COS 的网络请求。** 原失败日志为 `Supabase: Object not found → COS: fetch failed → HTTP 502`，授权模式为 `fast`、耗时 `0ms`。这不是权限拒绝响应。

两张原图目前仍可从本机配置的新加坡 COS 桶完整读取。故本样本不属于文件丢失；网络现已恢复读通，但没有实施稳定性修复，不能写成“完整修复”。

本机配置还停留在 `SCREENSHOT_STORAGE=supabase`：先找旧存储，失败再读 COS。这是迁移后本地配置未同步的事实，会增加无效往返；它本身不能单独解释 COS 网络失败。

**推测，待验证：** 本机网络/代理路径曾发生短时连接故障。当前对照无法复现早先的快速 `fetch failed`，且直连表现更差，不能把代理定为唯一根因，更不能直接把 COS 加入直连名单当作已验证修复。

## 广州迁移与缓存的核对

- **本轮新证据：** 当前本机仍指向新加坡桶，两张原图真实GET成功。
- **历史记录：** [10月23日广州测速](2026-10-23-COS新加坡广州静态数据迁移测速报告.md) 是复制到独立临时桶的实验，结束已删除测试对象/桶；[10月25日复核](2026-10-25-缓存现状复核与打开速度优化建议.md) 已纠正10月24日总账“生产截图已在广州”的表述。历史记录不冒充当前生产配置实测。
- **未核实：** 当前生产桶地域。Vercel连接器读环境清单403；CLI同项目同团队只读回退成功，但相关变量标为敏感类型，本轮只读元信息，没有拉取生产密钥或变量值。近期生产COS成功日志不能证明地域。
- **缓存排除范围：** 同一作品绕过缓存仍读出200，早先502来自服务端读存储失败。没有证据支持“缓存把图片弄丢”。未清理用户缓存，也未改Cloudflare规则。

## 建议的后续动作

1. 备份后把本机截图主存储与已验收的COS配置对齐，消除每次先找旧存储的往返；保持现有桶地域，先不做新迁移。
2. 对实际服务进程捕获下一次COS失败的底层原因（连接重置、DNS、TLS或超时），再调整该进程的网络路径。当前对照不支持盲目改直连。
3. 用同作品绕过缓存复验、另抽一条新图和一条旧图；确认每次 `cos/fallback=0` 且无502，才称稳定性修复通过。
