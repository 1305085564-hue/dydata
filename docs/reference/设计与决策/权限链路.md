## 现行设计

> 系统现在怎么做，以这里为准；为什么这样定，看下面的历史决策。动任何「谁能看、谁能改」之前先读这里，不要凭旧记忆推断权限；代码、数据库迁移、行级权限、接口、Server Action 和前端入口必须和这里一致，不能只改其中一层。最后对过代码：2026-10-31。

<a id="现行-数据范围"></a>

### 二、数据范围

| 角色 | 能看谁的数据 |
|---|---|
| 组员 | 默认只有自己；数据管理、发布管理放宽到本团队只读；视频复盘按下面的只读特例 |
| 组长 · 管理 | 本团队在职成员（可信 `team_id`） |
| 公司所有者 | 同一 `team_id` 范围，另含该团队的归档历史 |

- 一般范围由可信的 `profiles.team_id` 确定（历史成员含归档快照），业务小队是 `work_groups`；公司边界就是当前 Supabase 项目，不按 `teams` 记录数推断。不能用浏览器传来的参数替换归属。
- **视频复盘成员只读特例**：已有公司归属、原范围为「自己」的成员，经 `resolveVideoReviewReadOnlyScope()` 可读当前项目内所有团队；列表、详情、成员对比、选题状态和关联截图共用这个范围。没有公司归属的不扩大，组长和负责人沿用原范围；其他管理页和所有写操作都不复用这个扩展。实现见 `src/lib/data-access-scope.ts`，依据见[视频复盘打开速度优化方案（验收清单）](../../archive/2026-11-10-文档清理/计划原稿/2026-10-25-视频复盘打开速度优化实施方案.md#4-验收清单不能只交测试全绿)（提交 `22efe8be`）。
- **当前与历史**：当前操作只包含在职（`active`）成员；历史查询可以查到范围内的归档成员，归档不能让历史数据消失。
- **空范围**表示「没有可操作的对象」，不是「全部对象」。不能把 `permissions = {}`、字段缺失、`null` 或空数组解释成全集团。
- **跨公司视角已取消**：没有集团模式、跨公司会话令牌或切换入口；没有公司归属的账号只能按「自己」处理，不能扩大到其他公司。

<a id="现行-身份契约"></a>

### 三、身份契约与新功能登记

| 身份 | 默认范围 | 能做什么 | 明确不能做什么 |
|---|---|---|---|
| 组员 | 自己 | 查看和提交自己的业务数据、个人导出、个人数据分析；只读查看本公司岗位数据和发布进度；按只读特例查看作品 | 不能审批、不能管理其他成员、不能跨公司读或写岗位归属、不能对作品或发布状态做任何写操作 |
| 组长 · 管理 | 当前公司 | 处理本公司日常业务、审批本公司在职成员的申请、管理本团队组员 | 不能跨公司审批，不能管理组长、公司所有者或自己，不能把组员升为组长 |
| 公司所有者 | 当前公司 | 管理本公司全部成员、组长、业务数据和审批流程 | 不能跨公司读取或写入 |
| 归档账号 | 无 | 只保留历史记录供有权的人查询 | 不能登录、提交、审批、指派、提醒、上传、修改或恢复其他数据 |

每个权限判断都要写清六件事；新增功能必须先在这里（或对应页面文件）登记这六件事，再写代码：

| 要回答的问题 | 统一规则 |
|---|---|
| 身份：这个人是谁 | 组员、组长 · 管理、公司所有者；归档是状态，不是角色 |
| 功能：能不能做这件事 | 由固定身份规则决定，不由个人拼装权限开关 |
| 范围：能对哪些人的数据做事 | 默认组员是自己、管理角色是当前公司；模块只读扩展只认上一节的登记 |
| 当前与历史 | 当前操作只认在职；历史查询保留归档 |
| 对象归属：这条记录属于谁 | 由服务端从数据库读取核对，不相信浏览器传来的 `user_id`、`team_id` |
| 入口安全：绕过页面能不能操作 | 页面、Server Action、接口、数据库函数、行级权限都做同一套检查 |

- `manage_members` 不能单独推出豁免审批权；不能因为某个开关打开就把组长的范围扩大到其他公司。
- 页面和管理 AI 都不提供个人权限的写入口；调整权限只能通过改角色，进入固定模板。

<a id="现行-审批权限"></a>

### 四、谁能审批

| 动作 | 组员 | 组长 · 管理 | 公司所有者 |
|---|---|---|---|
| 提交自己的申请 | 允许 | 允许 | 允许 |
| 查看待审批申请 | 不允许 | 当前公司在职成员 | 当前公司在职成员 |
| 审批本公司成员 | 不允许 | 允许 | 允许 |
| 审批其他公司成员 | 不允许 | 拒绝 | 拒绝 |
| 审批自己的申请 | 拒绝 | 拒绝 | 拒绝 |
| 审批归档成员 | 拒绝 | 拒绝 | 拒绝 |

- 审批按这个顺序检查：登录 → 身份和功能权限 → 目标成员所属公司 → 目标成员状态 → 申请状态 → 原子写入。审批流程本身见[审批链路·现行设计](审批链路.md#现行设计)。

<a id="现行-安全边界"></a>

### 五、安全边界

- **三层鉴权**，应用层为主、数据库为辅：① 登录闸机 `src/middleware.ts`，校验登录态和 `profiles.membership_status`；② 接口鉴权 `requireAdminActor` / `getUserPermissions`，确认登录、在职、公司角色、固定功能权限和当前公司范围；③ 数据范围过滤 `current-permission-context.ts` + `data-access-scope.ts`，按 `visibleUserIds` / `activeVisibleUserIds` 限定可读和可操作的对象。
- **service role 是绕过所有权限的万能钥匙**：`createAdminClient()` 用 `SUPABASE_SERVICE_ROLE_KEY` 建连接、绕过行级权限。后台接口直连数据库是刻意的选择：不靠行级权限控权，先在应用层挡住没权限的人，所以安全全压在应用层鉴权上。任何用了 `createAdminClient` / `createServiceClient` 的接口，必须先有等价鉴权（登录 + `requireAdminActor` 或 `getUserPermissions`，或对象归属校验，或按 `visibleUserIds` 过滤）。这把钥匙是服务端机密，绝不进前端代码、绝不写日志。
- **依赖数据库本人身份的操作只能用本人连接**：`src/lib/admin-rpc-guard.ts` 在 Supabase 管理员入口和 CloudBase 管理员入口共用一份 9 个函数的拦截清单，误用立即报错、留请求编号，不再静默返回空。请假审批、永久豁免、申诉处理/重开、入团审批、Supabase 排行榜和提醒计数保留本人连接。三项履约标记（`mark_fulfillment_status`、`mark_fulfillment_status_batch`、`remove_fulfillment_mark`）是仅允许 `service_role` 执行的管理函数，须先在路由检查管理员角色和目标成员的在职可见范围，再通过 `supabase` 显式传入登录人的 `p_marker_id`；不得向本人连接补授权。通用鉴权结果的 `userSupabase` 用于其余依赖 `auth.uid()` 的操作。不得为绕过拦截改数据库函数。
- **直接表读写由应用判断身份与范围**：本人资料、账号修改、截图上传和使用记录通过可信用户身份限定本人；账号操作、截图上传同时复用统一权限上下文确认在职范围。仍保留本人连接直接读表或写表的路径，必须在 `src/lib/user-data-access.coverage.test.ts` 登记理由；登录本人资料、已有显式本人过滤或统一范围过滤的存量路径属于登记例外。新路径漏登记会使测试失败，不能把依赖数据库规则的全量查询当作例外。
- **行级权限是第二道防线**：浏览器直连的普通客户端仍受它约束。策略散在多份迁移里，改任何表的读写权限前，先扫一遍 `supabase/migrations/` 里涉及该表的 `create policy` / `enable row level security`。策略变更只能新增迁移，禁止改旧迁移。
- **退出与冻结**（2026-11-02 为 CloudBase 隔离验证确认的边界，现已回到 Supabase，见[上线与运维第 2 条](../上线与运维.md#第2条)）：退出只结束当前设备会话，其他设备继续有效，不建业务撤销表；新访问凭证目标有效期 1 小时，负责人接受退出后已发出的凭证在到期前仍可能直接访问数据库网关。冻结、归档走服务端专用的账号状态写入入口，按真实 `sub` 和目标项目精确定位，冻结写 3、恢复写 1 并独立读回确认；未激活或未知状态不能经恢复变成正常账号；客户端没有这个写入函数的执行权限。

### 六、代码位置与排查

| 文件、表或函数 | 职责 |
|---|---|
| `src/lib/permission-contract.ts` | 角色固定权限的唯一契约 |
| `src/lib/company-permissions.ts` | 读取契约、角色映射、`hasFixedPermission` |
| `src/lib/current-permission-context.ts` | 页面和接口共用的身份、功能权限与数据范围核心（`resolvePermissionCore()`） |
| `src/lib/permissions.ts` | 用户权限上下文、`getUserPermissions`（请求内缓存） |
| `src/lib/data-access-scope.ts` | 可见范围计算，`visibleUserIds` / `activeVisibleUserIds` |
| `src/lib/route-permissions.ts` | 后台路由与功能权限注册表；没登记的后台路由默认拒绝 |
| `src/lib/admin-auth.ts` | 后端鉴权核心（`requireAdminActor`） |
| `profiles.company_role` | 角色字段（`member` / `admin` / `company_owner`） |
| `visible_user_ids_v2(uuid)`、`active_visible_user_ids_v2(uuid)` | 数据库函数：当前公司可见用户（含归档 / 仅在职） |
| `supabase/migrations/20261016090000_remove_group_mode.sql` | 跨公司视角清理与当前公司权限函数收口 |

- 必须保持：服务端复核；浏览器传参不替换可信归属；空范围不扩大。当前操作用 `activeVisibleUserIds`，历史读取用 `visibleUserIds`；角色和模块特例只登记在这里和对应页面文件。
- 验证（旧场景：角色冲突拒绝；无公司不扩大；历史归档可查）：

  ```sh
  npx tsx --test src/lib/current-permission-context.test.ts src/lib/route-permissions.test.ts src/lib/data-access-scope.test.ts
  ```
- **改权限按这个顺序查全**：权限键与角色模板 → 运行时生成 → 身份核心 → 权限读取入口 → 数据范围 → 接口关卡 → 页面路由表 → 对应的行级权限迁移和数据库函数。
- **该看的看不到、不该看的看到了**：先看 `resolvePermissionCore()` 算出的角色和固定权限对不对，再看 `visibleUserIds` 对不对。
- **某个后台接口谁都能进**：按上一节 service role 那条的合格鉴权逐项核对。
- **改了权限没生效**：留意请求内 `cache()` 去重；固定角色表改了但没部署，也会看起来没变。
- **数据库直连读不到数据**：查对应表的行级权限策略和辅助函数。
