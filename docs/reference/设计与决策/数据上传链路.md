## 现行设计

> 系统现在怎么做，以这里为准；为什么这样定，看下面的历史决策。改规则时先改这一段，再在文件末尾加一条历史决策写明为什么改。最后对过代码：2026-11-16。

<a id="现行-日期"></a>

### 一、三个日期

| 日期 | 含义 | 用在哪 |
|---|---|---|
| 发布日 | 作品在平台实际发布的上海自然日（`videos.published_at`） | 全站作品的展示、筛选、排序和统计默认都用它 |
| 上传日 | 成员把数据交进系统的实际时间（`uploaded_at`） | 只在补交、审批、审计和核实先后时显示，并同时写明对应发布日 |
| 日报归属日 | 历史日报的内部编辑和追溯日期（`daily_reports.report_date`） | 不当普通作品日期展示；没有发布日的历史记录才拿它当回退 |

- 发布日是全站作品的主日期。周、月视图、发布管理和工作台都按发布日汇总；没有发布日的历史记录才回退日报归属日，绝不回退上传日。
- 新建普通上传和历史手稿时，只要有有效发布时间，日报归属日自动取它的上海自然日；没有发布时间的历史记录才用手填日期。编辑历史记录沿用原归属日，不因编辑重新改日。数据库约束 `report_date_must_match_published_at` 拒绝两者不一致的日报。
- 日报归属日继续作为历史编辑、补交申请和追溯的键，不覆盖作品主日期。
- 正常流程是 D+1 上传 D 的数据。基础信息和 24h 数据可以一次交完，不因分阶段观察生成两条日报。T+0、T+1 只描述观察阶段，不表示成员必须当天交，也不表示管理侧按天检查。
- 24h 观察数据指播放、点赞、评论、分享、收藏、涨粉，以及由它们算出的比率；未满 24 小时的即时数据不参与统一比较。
- 历史补录必须选合法的历史业务日；验收或补录不用等满 24 小时，但数据仍归属所选业务日。
- 2026-10-13 的历史修复按上海时区转换执行；旧版 `20261013120000` 迁移已被后续修复覆盖，只作历史记录，禁止单独重放。

<a id="现行-补交门禁"></a>

### 二、补交门禁（2026-09-30 起）

- 首次提交时，按提交时刻和真实发布时间算相隔多少小时：不超过 72 小时可以直接交；超过 72 小时，或发布时间是手填、手改的，必须先提交补交申请并经管理人员审批。跨月本身不触发补交。
- 标「限流」「删稿」照常受门禁，只有标「异常」才跳过。现有的历史发布时间不回填、不按新规则重算。
- 编辑历史记录不重新算时限。审批通过只取得补交资格，日报实际写入成功后才恢复那天的履约状态。
- 补交批准只放行申请的那一条作品：提交时用「同账号 + 同标题 + 同发布日（上海自然日）」和申请暂存的作品对账，与提交判重是同一个业务键，不用含指标的内容指纹。资格用过后暂存清空，不能再放行同一天的另一条。
- 补交申请按「成员 + 账号 + 业务日」去重；趋势图横轴的日期不作为业务日依据。

<a id="现行-判重"></a>

### 三、提交流程与判重

- 成员填表提交 → 写入日报和作品 → 更新履约记录 → 可选发通知。发布时间必填，日报归属日自动匹配。截图怎么上传见[数据上传（工作台）·截图](../页面设计与决策/数据上传（工作台）.md#现行-截图)，审批怎么走见[审批链路·补交](审批链路.md#现行-补交)。
- 同一账号同一天可以有多条日报，但每条必须绑定不同的作品；同一作品重复提交返回 409，提示「这条已经上传过」。
- 编辑必须按原作品或原日报精确更新，不能套用同账号同一天的其他日报；找不到唯一对应的日报时拒绝编辑。

<a id="现行-入口"></a>

**入口、代码与验证**
- 入口：工作台 Action、`/api/video-submit` 写日报；发布管理加载器调用 `get_fulfillment_range`。
- 规则来源：读取日期键 `src/lib/date-semantics.ts`；提交与补录归属日 `src/app/api/video-submit/report-target.ts`（经 `route-core.ts`）；历史修改统一走主表单的修改模式，没绑定作品的老日报走 `src/lib/daily-report-only-edit.ts`；履约口径以 `supabase/migrations` 里最后一个 `create or replace function public.get_fulfillment_range` 为准（不要钉文件名）；接口响应见[审批接口契约](../审批工作台阶段二三后端接口契约.md)；识别通道由 `src/app/api/ocr-screenshot/channel-config.ts` 读取。
- 必须保持：发布日、上传日、日报追溯键不混用；不同作品不覆盖同账号同一天的旧日报；批准补交不等于日报已落库。写入要核对本人或管理权限。
- 验证（旧场景：同一天多条作品；补交获批但续交失败仍可重试）：

  ```sh

  ```

<a id="现行-异常"></a>

### 四、异常状态

| 状态 | 含义 |
|---|---|
| 正常（`normal`） | 数据在正常波动范围内 |
| 异常（`abnormal`） | 新提交统一用这一档；具体是限流还是删稿等，记在处罚类型、平台通知、申诉里 |
| 限流、删稿 | 旧数据的兼容状态，读取时归入异常，处罚类型分别为 `limited`、`deleted` |
| 投流、活动干预 | 2026-09-26 下线，不再接受新写入，提交接口明确拒绝；旧数据读取时归入异常，照常显示原中文标签。唯一兼容入口是 `src/lib/video-anomaly.ts` |
| 未满 24h | 还没到 24 小时观察点，不参与 24h 比较 |

- 新写入只用正常、异常两档；异常录入下拉只剩「限流」「删稿」。异常状态以 `videos.anomaly_status` 为准。
- 避坑案例模块 2026-08-22 下线：`violation_cases`、`knowledge_cases` 不再有新写入，只保留历史数据；未满 24h 自动写入案例库的钩子同时移除。

<a id="现行-来源"></a>

### 五、日报来源标签与提交字段

- 来源标签：`manual` 显示「手工」；`ai` 不另外标；`douyin` 为历史预留来源标识（抖音账号绑定与自动归集功能已于 2026-11-22 下线删除）；历史上为空的显示「来源未知」，不能说成历史都是 AI。
- 只有 24 小时指标被人工录入或修改才标「手工」，包括播放、点赞、评论、分享、收藏、涨粉、导粉、均播时长、2 秒跳出率、5 秒完播率、整体完播率；一开始没识别、直接手填指标也算。标题、文案、题材标签、视频形式、内容标签、发布时间、异常信息和运营、文案、剪辑责任人的改动都不影响标签。已标手工的不会降回去；历史手工标记保留，不按现在的字段倒推清理。
- 导粉话术 2026-10-27 下线：话术并入文案，不再有单独的话术字段，服务端也不再要求「导粉大于 0 必须填话术」。提交和编辑都不再读写 `script_usage_records`、`violation_cases`，两张表和历史数据原地保留、不再增长，编辑老记录不清空也不重建。
- 导粉文案不单独存、不单独打标：导粉数大于 0 的那条日报，它的文案就是导粉文案。导粉数选填，留空就是空，不折算成 0。

<a id="现行-履约"></a>

### 六、履约：实发、应发、漏发

- **实发作品数**：统计范围内每天实际发布的作品条数加总（发布管理用 `get_fulfillment_range.published_count`）；一天发多条按实际条数算，不能拿「发布天数」代替作品数。限流、删稿的作品照样算。
- **应发目标**：统计范围内的自然日数，减去已批准的请假、豁免日（状态为 `leave`、`waived`、`exempted`），再按入职日裁掉入职前的日子。
- **还差作品数** = 应发减实发，最少为 0，超发不显示负数。**达成率** = 实发 ÷ 应发，应发为 0 时记 0。
- 待审批的豁免申请只在月历上显示黄色，不提前扣应发；批准后才算进请假、豁免。
- **工作台「漏 y 天」**和发布管理的「未确认」同一口径：按自然日算，周末和节假日不豁免；从入职日算起；当天不算漏（作品第二天才上传）。有提交、有已批准或待审批的请假豁免、管理员人工标记过（请假、豁免、确认已发）、长期免交的日子不算漏；管理员认定缺勤的仍算漏。
- 管理端的判断在数据库函数里，工作台是它的镜像（`summarizeMonthFulfillment`，`src/lib/dashboard-panel-header.ts`），改规则两边必须一起改。「漏 y 天」只用于工作台提示，不改变应发目标、实发统计和计薪口径。

## 历史决策

<a id="第1条"></a>

### 1 发布时间来源与补交判重

**分类**：业务　**状态**：有效，取代 2026-10-01「发布时间锁死、不给手填入口」、2026-10-07「必须由截图识别、认不出就阻断」两条旧决定，以及 2026-11-15 工作台施工时「认不出不画输入框」的写法　**日期**：2026-11-16　**拍板人**：阿禅
**背景**：旧做法是发布时间只能靠截图识别，认不出来成员就交不了，换模型也补不上这个缺口。放开手填又怕成员改时间绕过 72 小时补交门禁（这是 10-01 锁死的原因）。另外 11-16 实测一条补交申请批准后入库失败，原因是同一作品 10-13 已经入库，成员白等了审批。
**决定**：发布时间可手填；手填或改过识别值，和超 72 小时一样走补交申请，不另开流程。普通提交和申请补交都先判重，命中直接提示「这条已经上传过，无需重复提交」，不创建申请。补交暂存数据保留发布时间来源和识别原值，审批卡片展示触发原因与原值。
**后果**：72 小时阈值、编辑和异常跳过门禁、门禁错误码保持不变；日报的「手工」标签不受发布时间来源影响（见第 5 条）。页面上的配套做法见[数据上传（工作台）第 2 条](../页面设计与决策/数据上传（工作台）.md#第2条)、[数据上传（工作台）第 3 条](../页面设计与决策/数据上传（工作台）.md#第3条)。
**证据**：[拍板结果（第七章）](../../plans/2026-11-16-数据上传首页UX整改计划.md)；被取代的旧决定：[10-01 需求禁区（105 行）](../../archive/2026-11-09-A批文档治理/计划原稿/2026-11-09-计划收尾/2026-10-01-发布时间识别失败出口-修复需求.md)、[10-07 日志](../../archive/日志/2026-10/2026-10-07.md)。

<a id="第2条"></a>

### 2 业务日按上海日历日算

**分类**：业务　**状态**：有效　**日期**：2026-10-03　**拍板人**：阿禅
**背景**：原文只记了选择结果，没写理由。
**决定**：「业务日」一律取上海时区的日历日，数据库按此口径落库。
**后果**：全站按日统计都以上海日历日为界，不按服务器时区或提交者所在时区。
**证据**：[10-03 日志（02:29 条）](../../archive/日志/2026-10/2026-10-03.md)；迁移 `20261003020000_business_day_shanghai_timezone.sql`。

<a id="第3条"></a>

### 3 作品主日期用发布日，不用上传日

**分类**：业务　**状态**：有效　**日期**：2026-10-10　**拍板人**：阿禅
**背景**：同一条作品有发布日、日报归属日、上传日三个日期，各页面各用各的会对不上。原文只写了"绝不回退上传日"，没写更多理由。
**决定**：作品列表、日历、统计、选题库、排行榜、导出和发布履约的主日期都用真实发布日（上海自然日）；没有发布日的历史记录才回退日报归属日，绝不回退上传日。
**后果**：上传日只记录实际上传时间，不改变作品归属哪天。新增页面或统计必须沿用这条，不能另取日期。现行设计见本文件[「三个日期」](#现行-日期)。
**证据**：[执行计划「阿禅已确认 7 条」](../../archive/2026-11-09-A批文档治理/计划原稿/2026-11-09-计划收尾/2026-10-10-全站作品日期统一为发布日-执行计划.md)。

<a id="第4条"></a>

### 4 补交门禁只看 72 小时，跨月不另拦

**分类**：业务　**状态**：有效（2026-11-19 阿禅提过取消 72 小时，讨论后暂不取消，见待办）　**日期**：2026-10-01，2026-11-18 再次确认　**拍板人**：阿禅
**背景**：重构后验收发现「跨月单独提交」不再强制补交，阿禅确认这正是要的口径，不回退。
**决定**：首次提交只在「真实发布时间距提交超过 72 小时」（或发布时间被手填、手改，见第 1 条）时要求补交申请；跨月本身不触发。作品标「限流」「删稿」照常受 72 小时门禁，只有标「异常」才跳过。
**后果**：「限流、删稿照常受门禁」阿禅 2026-11-19 再次确认：标限流、删稿不能当作免审的理由。现行设计见本文件[「补交门禁」](#现行-补交门禁)。
**证据**：[10-01 验收报告（82 行）](../../archive/2026-11-09-A批文档治理/计划原稿/历史-报告/2026-10-01-首页上传方案-完成度审查与返工.md)；[11-18 拍板清单 D4](../../archive/2026-11-18-计划归档/计划原稿/2026-11-18-业务逻辑治理-审计结论与拍板清单.md)；[10-15 日志（17:35 条）](../../archive/日志/2026-10/2026-10-15.md)。

<a id="第5条"></a>

### 5 日报「手工」标签只看 24 小时指标

**分类**：业务　**状态**：有效　**日期**：2026-10-08　**拍板人**：阿禅
**背景**：原文没写理由。改之前发布时间、异常信息、运营/文案/剪辑责任人的调整也会把日报标成手工。
**决定**：只有 24 小时指标被人工录入或修改才标「手工」；发布时间、异常信息、责任人调整都不触发。已有的历史手工标记保留。
**后果**：手填发布时间走补交（第 1 条），但不影响手工标签。现行设计见本文件[「日报来源标签」](#现行-来源)。
**证据**：[10-08 日志](../../archive/日志/2026-10/2026-10-08.md)；迁移 `20261008090000_narrow_daily_report_manual_source.sql`。

<a id="第6条"></a>

### 6 漏发按自然日算，周末节假日也算

**分类**：业务　**状态**：有效，取代 2026-11-15 工作台施工时「只算工作日、周末交了仍算已交」的口径　**日期**：2026-11-18　**拍板人**：阿禅
**背景**：公司要求每天都发作品（含周末节假日）；工作台的「漏 y 天」和管理端发布管理的「未确认」原先口径不一致。
**决定**：工作台「漏 y 天」按自然日算，从入职日起算，管理员人工标记（请假、豁免、确认已发）不算漏，当天不算漏；与发布管理的「未确认」天数一致。
**后果**：同一员工同一月，工作台漏的天数必须等于管理端非当天的未确认天数，改任何一边都要两边一起改。现行设计见本文件[「履约」](#现行-履约)。
**证据**：[11-18 拍板清单 D3](../../archive/2026-11-18-计划归档/计划原稿/2026-11-18-业务逻辑治理-审计结论与拍板清单.md)；被取代的写法：[工作台重排施工规格（已决事项第 5 条）](../../archive/2026-11-18-计划归档/计划原稿/2026-11-13-工作台重排施工规格.md)。

<a id="第7条"></a>

### 7 同一账号同一天可以交多条作品

**分类**：业务　**状态**：有效　**日期**：2026-10-12 施工，2026-11-19 确认　**拍板人**：阿禅
**背景**：成员经常一天发两三条，也常把周五到周日的作品攒到周一一起发；原先数据库限制一个账号一天只能有一条日报，第二条交不了。
**决定**：解除「同账号同一天只能一条」的限制，改为按作品判重；工作台已交卡片上给「再传一条」入口，同一作品仍拦截。
**后果**：判重的依据是作品本身（同账号、同标题、同发布日），不是日期。不准改回一天一条。
**证据**：[10-12 日志（16:00 条）](../../archive/日志/2026-10/2026-10-12.md)。

<a id="第8条"></a>

### 8 限流、删稿的作品照样算一条

**分类**：业务　**状态**：有效　**日期**：2026-10-15　**拍板人**：阿禅
**背景**：阿禅原话：「你限流不上传，那我天天都说自己限流了，是不是一个月就不用发视频了。」这是考勤，不是评优。
**决定**：发了几条就算几条，被限流、被删稿的作品照样算实发。
**后果**：和 [第 4 条](#第4条)「限流、删稿照常受 72 小时门禁」是同一个道理：标限流、删稿不能当作少交或免审的理由。
