<a id="现行设计"></a>

## 现行设计

> 系统现在怎么做，以这里为准；为什么这样定，看下面的历史决策。最后对过代码：2026-11-18。

<a id="现行-豁免"></a>

### 一、请假与豁免

- **申请**：员工填原因提交，生成一条待审批的豁免申请，管理员的导航角标随之提示。只拦同一申请人、同一分类、待审批日期重叠的申请；不同日期可以继续申请。一个业务日只有一条生效豁免。
- **审批**：管理员在豁免抽屉里按日期逐天通过或驳回，批准的日期投影为生效授权（`exemption_grant`）。审批只写逐日明细和生效授权，不写 `fulfillment_records`；发布履约查询时按生效授权现场判定请假（`leave`）或豁免（`exempted`）。打回会让该申请的授权失效（留作历史行），再次批准重新生效。逐日明细与旧区间的兼容见[模块地图](设计与决策总纲.md)。
- **结果回到员工**：管理员待办随申请状态自动消失。员工工作台横幅显示近 7 天内审批过的全部申请结果（不写通知中心）：一条申请一项，按天列出通过和驳回的日期，驳回带管理员写的理由，部分通过时两类并列；过去日期的请假被驳回也显示，超过 7 天不再显示。唯一读取入口是 `loadRecentExemptionReviewNotices`（`src/lib/loaders/dashboard-exemption-review.ts`）。

<a id="现行-补交"></a>

### 二、补交申请

- **流程**：成员提交补交申请（待审批）→ 管理员审批。通过：批准并尝试自动续交，续交成功才写日报、恢复履约；续交失败保留资格，员工在工作台点「去完成填报」。驳回：关闭申请并通知员工。
- 什么时候必须补交、申请前先判重、批准后只放行哪一条、按什么去重，见[数据上传链路·补交门禁](数据上传链路.md#现行-补交门禁)。续交时改了数字不影响对账。
- 审批卡片展示触发原因；发布时间是手填或改过的，保留并展示识别原值。
- 审批写审计日志（`audit_logs`），并批量关闭对应待办（`source_type=fulfillment_appeal`）。

<a id="现行-申诉"></a>

### 三、申诉

- 在发布管理点「处理申诉」看详情，批准或驳回，写审批与审计记录，后续处理各自记录结果。批准：尝试自动续交，失败保留已批准资格（同补交）。驳回：关闭申诉并通知员工。

<a id="现行-撤回"></a>

### 四、撤回待审申请

- **豁免**：工作台「特殊豁免申请审批中」提示条上有「撤回申请」（两步确认），调用 `POST /api/exemptions/withdraw`，用员工自己的身份删除其全部仍待审批的申请（数据库规则「成员删除自己待审批的申请」兜底），逐日明细级联删除。申请里已有日期被审过（部分通过或驳回）的不能撤回，避免抹掉已审结果，接口返回明确提示。
- **补交**：待审期间可撤回，调用 `POST /api/fulfillment/appeal/withdraw`，服务端校验「本人 + 仍待审」后删除该申请（补交表没有「已撤回」状态，不新增迁移），同时关闭管理员那条待办；撤回后员工回到「需要补交」，可重新申请。已处理的撤不了，返回明确提示。
- 管理员侧的角标、待办、发布管理的待审标记都按待审申请现算，申请删除后同步消失，不另存通知。员工工作台刷新后，日历待审标记、「漏 y 天」和横幅与服务端一致。

<a id="现行-权限申请"></a>

### 五、权限申请

- 组员在无权限页点「申请权限」，调用 `POST /api/permission-requests/apply`，只给在职的公司负责人（`company_owner`，不分团队）发一条待办，按钮是「前往成员管理调整角色」；组长和团队管理员不收（他们没有调整角色的权限）。
- 待办可由负责人手动完成；同一人同一模块重复申请按稳定的 sourceId 去重。没有在职负责人时接口返回提示，不报错。

<a id="现行-入口"></a>

### 六、入口、代码与验证

- 豁免有两个申请入口：工作台 `submitExemptionRequestWithClient` 和 `POST /api/exemptions/apply`，共用预检和写入，之后走审批、通知和审计。两个入口都保留，细节见[豁免申请维护入口](../豁免申请维护入口.md)。
- 规则来源：重叠预检 `src/lib/exemption-application-precheck.ts`；唯一的申请写入编排 `src/lib/exemption-application-write.ts`。审批工作台的界面在 `src/components/approval-workbench/`，审批逻辑在 `use-approval-review.ts`，排序与文案规则在 `src/lib/command-hub/domain/workbench-rules.ts`。
- 必须保持：预检只读；各段结果可观察，失败不假装成功；申请权限和审批权限分开。
- 验证（旧场景：逐日部分审批；历史没有逐日明细的兼容；写失败回退）：

  ```sh
  npx tsx --test src/lib/exemption-application-precheck.test.ts src/lib/exemption-approvals.test.ts src/lib/豁免流程兼容.test.ts 'src/app/(app)/dashboard/actions.test.ts' src/app/api/exemptions/apply/route.test.ts
  ```

## 历史决策

<a id="第1条"></a>

### 1 审批不承诺跨表原子事务

**状态**：有效。实现验收另查当时证据。

【背景】申诉的核心 RPC 可在一次调用里写审批和审计。豁免审核也通过专用原子 RPC 保持申请与日期明细一致。自动续交、通知和待办是后置步骤。
【决定】核心操作按自身事务保障。后置步骤分别记录结果，用幂等、重试和人工补偿处理失败。
【后果】审批成功与后置结果分别返回和观测。若以后需要消除后置窗口，另立事务或 Outbox 方案。
**证据**：[原始证据（129-142行）](../../archive/2026-11-09-A批文档治理/计划原稿/历史-项目/根治工程/2026-10-02-全站架构可维护性体检-治理体系版.md)；[原始证据（43,357-388行）](../../archive/2026-11-09-A批文档治理/计划原稿/历史-项目/根治工程/2026-10-02-统一行动中枢审批-架构重构方案.md)。
**日期**：2026-10-02

当前调用见[申诉处理](../../../src/app/api/admin/fulfillment/appeal/handle/route.ts)与[豁免审核](../../../src/app/api/exemptions/review/route.ts)。

### 2 补交申请必须带着填好的数据

**分类**：业务　**状态**：有效　**日期**：2026-10-03　**拍板人**：阿禅
**背景**：一次重构把补交申请里的作品数据从必填放宽成了可空，这是没申报的改动。原文只有阿禅的裁决「没填数据不让补交」，没写理由。
**决定**：补交申请必须连同成员填好的作品数据一起提交，没填数据不让申请。
**后果**：批准后靠这份暂存数据自动入库；接口不能再放宽成可空。
**证据**：[10-03 日志（18:4x 条）](../../archive/日志/2026-10/2026-10-03.md)。

<a id="第3条"></a>

### 3 补交批准只放行申请的那一条作品

**分类**：业务　**状态**：有效，取代 2026-11-16 计划里「按成员、账号、日期匹配，同日多条共用一次批准」的现状　**日期**：2026-11-18　**拍板人**：阿禅
**背景**：原来批准按日期放行，同一天另一条超时作品也能借这次批准免审。
**决定**：成员凭批准提交时，用「同账号 + 同标题 + 同发布日」和申请暂存的作品对账，对得上才放行；资格用过即清空。不用含指标的内容指纹，因为成员改了数字也应放行。
**后果**：对账的业务键和提交判重（[数据上传链路第 1 条](数据上传链路.md#第1条)）是同一个，改一处要两处一起改。现行设计见[数据上传链路·补交门禁](数据上传链路.md#现行-补交门禁)。
**证据**：[11-18 拍板清单 D5](../../archive/2026-11-18-计划归档/计划原稿/2026-11-18-业务逻辑治理-审计结论与拍板清单.md)。

<a id="第4条"></a>

### 4 员工可以撤回还在待审的申请

**分类**：业务　**状态**：有效　**日期**：2026-11-18　**拍板人**：阿禅
**背景**：原文没写理由。
**决定**：请假/免交申请和补交申请，在待审期间员工都可以自己撤回；撤回入口在工作台。撤回后管理员那边的待办和角标一起消失，员工回到「需要补交」状态，可以重新申请。
**后果**：补交没有「已撤回」状态，撤回就是删除申请。员工和管理员两边的列表、角标、提示条必须一致。现行规则见[核心业务流程](设计与决策总纲.md)「员工撤回待审申请」。
**证据**：[11-18 拍板清单 D8](../../archive/2026-11-18-计划归档/计划原稿/2026-11-18-业务逻辑治理-审计结论与拍板清单.md)。

### 8 「不参与考核」只有负责人能设、能撤

**分类**：业务　**状态**：有效　**日期**：2026-10-02　**拍板人**：阿禅（「负责人能设」写死）；「直接开关、不走申请单」和「隐藏范围」写的是「确认」，没注明谁确认
**背景**：给负责人一个开关，把不用考核的人整体拿出去。
**决定**：只有负责人能把某人设为「不参与考核」或撤销，管理员不行；用直接开关，不生成待审批的单子；设了以后只隐藏「要交 / 有没有交」这类视图，历史日报、作品和统计照样可查。
**证据**：[不参与考核豁免入口规划思路](../../archive/2026-11-09-A批文档治理/计划原稿/2026-11-09-计划收尾/2026-10-02-不参与考核豁免入口-规划思路-交Codex.md)；[执行计划](../../archive/2026-11-10-文档清理/计划原稿/2026-10-02-不参与考核豁免入口-执行计划.md)。

### 10 补交先审批、后自动续交，续交失败靠按钮兜底

**分类**：代码　**状态**：有效　**日期**：2026-10-13　**拍板人**：待核（开发方案，没见阿禅确认）
**背景**：「先写数据、后审批」走不通：超 72 小时的作品没有批准就写不进去。
**决定**：先审批、后自动续交。代价是续交失败时会出现「审批已通过、数据没写进去」，所以员工那边保留「去完成填报」按钮兜底。
**后果**：这是 [第 1 条](#第1条)「后置步骤分别记录」的具体例子；删兜底按钮前必须先解决这个窗口。
**证据**：[补交审批自动生效修正版 part2](../../archive/2026-11-09-A批文档治理/计划原稿/2026-11-09-计划收尾/2026-10-13-补交审批自动生效-修正版-part2.md)。

<a id="第11条"></a>

### 11 补交和豁免的待办只能由审批结案

**分类**：业务　**状态**：有效　**日期**：2026-11-18　**拍板人**：待核（11-18 修复项，理由来自 10-12 未获批的计划）
**背景**：审批结果决定补交能不能恢复履约；待办「完成」只代表看过提醒，两者不能共用一个动作。
**决定**：普通待办有「完成」按钮；补交、豁免的待办没有独立「完成」，只有同意或拒绝才算结案。
**证据**：[11-18 拍板清单 F3](../../archive/2026-11-18-计划归档/计划原稿/2026-11-18-业务逻辑治理-审计结论与拍板清单.md)；[豁免审批台修复计划](../../archive/2026-11-19-计划归档/计划原稿/2026-10-12-豁免审批台修复计划.md)。
