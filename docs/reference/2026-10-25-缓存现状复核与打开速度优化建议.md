# 缓存现状复核与打开速度优化建议

日期：2026-10-25；范围：现状核查与架构建议。没有修改业务代码、数据库结构、Cloudflare 规则或生产配置。

执行入口：`docs/plans/2026-10-25-视频复盘打开速度优化实施方案.md`。交给 Sol 施工时以实施方案的目标、范围和验收条件为准；本报告保留现状与证据，不作为第二份施工清单。

## 负责人结论

建议按“减少重复查询 → 稳定的私有云端结果缓存 → 浏览器复用已看数据”优化，以视频复盘为首个验收页面。数据库仍有明确优化空间，暂不迁主库、不批量搬广州、不把内部业务接口全部设为公共缓存。

Cloudflare 已在加速程序、样式等静态文件；最近新增的注册团队列表已命中 **Vercel CDN**，但本次仍未命中 Cloudflare。两者都是云缓存，不能只看 Cloudflare 就判断完全没缓存。

“1～2 秒打开”应定义为列表真实数据出现、筛选可用，不是只显示空框。建议把稳定性目标定为：同一典型使用环境下，95% 的常用列表打开不超过 2 秒。它是拟议验收目标，不是本轮已达成的承诺；现行工程预算仍为视频复盘首屏 2.5 秒，本轮未改预算。

## 三、哪些仍主要实时读取

当前 API 路由数量仍为 89；逐项路径可追溯 [10/24 总账](2026-10-24-DYData全量缓存总账.md)，其现状判断以本次纠正为准。以下按业务归类，不把保存数据、页面状态或数据库内部内存缓冲误算成业务结果缓存。

| 业务 | 当前边界 | 推荐方向 |
|---|---|---|
| 工作台统计、活动、排行，以及部分人员选择数据 | 无统一跨实例业务结果缓存；有上表少量页面复用 | 对重算成本高且允许短时延迟的摘要做私有短缓存 |
| 视频入库状态、内容归因、对比成员、作品管理和编辑详情 | 大部分按权限实时读取；列表、详情为已列例外 | 合并重复读；历史只读结果可短缓存，写入后失效 |
| 发布管理日历、待审批、申诉、豁免历史 | 没有统一共享结果缓存 | 历史统计可评估缓存；待处理状态和执行前校验保持新鲜 |
| 选题池、建议、认领状态 | 无统一共享业务结果缓存，存在页面内复用 | 稳定资料/聚合可缓存；认领、退回与竞争状态执行时实时确认 |
| 抖音绑定、指标、同步记录 | 无统一共享业务结果缓存 | 已完成历史指标可按同步批次缓存；授权/同步进度实时 |
| AI 后台、模型测试、生成、导出 | 仅已有配置层缓存；其余受权限、输入及状态约束 | 配置可短缓存；不能把不同用户的结果公开复用 |
| 登录、权限检查、上传、保存、审批、删除、授权、通知操作、定时任务、健康检查 | 不应以缓存替代实际执行或实时检查 | 保持执行与确认；减少同请求内重复检查 |

登录后整页仍动态生成。即使浏览器缓存过列表接口，重新打开页面时，服务端首屏直接调用加载器，不会自动读取浏览器里的那份接口缓存。因此“接口有 60 秒缓存”不等于“每次打开整页都快”。

## 四、数据库还有没有优化空间

**有。生产数据库实际执行证明，查一天的数据前仍对大量历史候选做了关联计算。**

### 本轮只读实测

生产项目 `dydata-sg-prod` 位于新加坡，状态 ACTIVE_HEALTHY；Vercel 生产运行区为 sin1，两者同区。

| 检查 | 读数 | 能说明什么 |
|---|---|---|
| 视频列表 SQL 累计统计 | 初次读取 1,158 次，平均 356.14ms，最大 2,178.04ms；再次读取 1,159 次、平均 356.94ms | 查询有明显波动；是累计记录，**不是最近两天 p95**，可能混合测试/历史函数版本 |
| 同一团队、2026-10-15、每页 50 的真实只读调用 | 返回 26 条，候选作品 2,056、候选快照 2,032、日期目录 162 天 | 返回少不等于计算少；这些诊断数是候选集规模，不是所有物理扫描次数 |
| 原函数 EXPLAIN ANALYZE | 执行 572.069ms；共享缓存命中 31,568 块，磁盘读取 0、临时写入 0 | 此样本主要不是磁盘读取慢；不代表全站没有 I/O 问题 |
| 展开当前函数正文、绑定同一参数后 EXPLAIN ANALYZE | 639.091ms，规划 51.882ms；base 2,056 行，约 603.2ms；日期过滤后 26 行 | 多次按视频取快照、标签、选题、拆段在日期过滤之前执行。展开查询供定位，不能与原函数当严格性能 A/B |
| 展开执行计划的关联循环 | 快照、标签、选题等节点各约 2,056 次；磁盘读取仍为 0 | 缩小关联前候选集比“再缓存数据库文件页”更有针对性 |
| 数据规模与瞬时连接 | videos 约 2,548 行、snapshots 约 2,518 行；13 个连接，采样时无锁等待 | 未见“体量已大到必须迁库”的证据；单点采样不能排除高峰资源不足 |

累计统计自 2026-05-26 起，已有条目淘汰；最大值、均值不能当当前版本稳定性承诺。数据库全局累计临时写入量很大，但时间跨度和来源未隔离，本轮不归因给视频复盘，也不据此建议扩容。

### 先做的查询优化

1. 把“日期目录/每天条数”与“当天作品详情计算”分开。前者查轻量字段；后者先限定日期/人员/账号，再关联快照与标签、算评级。不要为了日期翻页器每次给全部历史作品做重计算。
2. 保留原有权限、上海发布日期口径、筛选含义、全局排序和总数；不能先随便截取 50 条再排序。涉及评级/标签筛选时，要保留所需计算，不改变结果。
3. 查执行计划后再决定索引。现有视频日期/账号、快照 video_id、标签、选题、拆段索引已存在；优先解决查询顺序，避免只堆索引。
4. RPC 后的成员选项读取是串行执行，具备并行检查空间；页面的权限上下文也有重复构建入口。可以在**同请求内**复用，但不能缓存旧授权来换速度。

这些是基于当前结构与执行计划的优化建议，收益数值仍待同数据、同权限 A/B 验证。

## 五、为什么不能只加 Cloudflare

目前的三段等待要分别处理：

```mermaid
flowchart LR
    U[用户浏览器：已看数据与静态文件] --> E[Cloudflare / Vercel：公共静态文件]
    E --> A[新加坡应用：每次确认当前权限]
    A --> C[拟新增：同区共享的私有结果缓存]
    C -->|未命中才查询| D[数据库：减少候选与重复计算]
```

图中共享结果缓存是建议，不是现状。缓存命中仍经过应用权限检查；不会把内部接口直接开放给所有访客。

现有列表缓存是每个实例自己的 Map，60 秒有效、64 个查询键。实例切换、重启、不同日期/排序产生不同键、条目淘汰、过期都会重新查库；并发未命中目前也没有统一的在途查询合并。这是波动的合理成因之一，**当前缺命中率和实例关联记录，不能声称已证明用户所有慢请求都由它造成**。

本轮网络对照还出现明显差异：默认代理路径的注册团队请求约 1.31 秒，后续 Vercel HIT 约 0.71 秒；curl 明确禁用代理的一次请求约 8.53 秒，健康检查 15 秒超时。样本分别经过 SJC/SEA、Vercel sfo1/pdx1 边缘，再到 sin1，不能视为“深圳直连”的标准基线。它说明需要记录实际网络路径，不能把全部等待归到数据库；也不能用本轮单次读数给 Cloudflare 下“有害/无用”结论。

## 六、推荐怎么实施

| 顺序 | 做什么 | 推荐理由 | 完成判据 |
|---|---|---|---|
| 1 | 固定生产版本、账号、日期和网络，测首次打开、同页重开、切日期、从详情返回；分开身份检查、取数、传输、页面可操作 | 找到慢尾巴，避免不同样本比较 | 有当前浏览器基线；缓存 hit/miss/age、实例、环境与版本可关联 |
| 2 | 先优化视频复盘数据库查询和同请求重复读 | 首次/过期/新筛选都受益；已经有真实执行计划支持 | 结果逐项一致；候选关联工作下降；冷查询与整页慢样本下降 |
| 3 | 视频列表小范围接入新加坡同区共享私有结果缓存 | 解决实例之间不共享，减少重复计算 | 命中、失效、故障回退、权限变化、并发未命中均验证；整页确有收益 |
| 4 | 浏览器复用近期列表和详情，保留当前筛选与滚动；按需预取相邻日期/详情 | 改善来回切换，减少额外网络往返 | 返回/切换明显加快；更新后能看到新数据；不同账号不串数据 |
| 5 | 复用成熟方案到数据管理、工作台的重聚合读取 | 只扩展确有重复计算的路径 | 各页面独立验收，不套用视频页结论 |
| 单独项 | 截图首次读取和授权链路 | 它主要影响详情页图片，不能当列表首屏优化 | 单独计图片完整显示时间；先测真实生产链路再决定地域/CDN |

共享缓存技术优先评估现有 Vercel 的区域 Runtime Cache，减少新增服务；若失效、并发控制或可观测性需求不满足，再选同区 Redis。先验证能力和套餐，不默认购买或建设大型缓存集群。两种方案都必须由应用完成权限隔离，不能因名字里有“缓存”就自动安全。

### 拟议缓存规则（待决策，不是已经开启）

- 列表、历史统计先以 30～60 秒为上限试点；历史数据仍可能补录、删除、修正，不能视为永久不变。
- 缓存键至少包含用户、公司/团队、权限范围指纹、筛选、日期、排序、分页、数据版本。空范围不得回退全量。
- 修改作品、上传快照、更新标签/入库状态、回收/恢复后，失效对应范围；所有入口都要覆盖。更新者立即看到新结果，不能等 TTL。
- 权限变更、退出/换号后清理浏览器缓存；服务端每次重新确认当前范围。不能把缓存里的“之前允许访问”当成现在仍允许。
- 对业务数据先用短期页面内存缓存；暂不把所有内部数据长期放 localStorage/IndexedDB。已有页面复用保留并统一失效，不重复叠层。
- 只有允许短时旧数据的普通列表才考虑“先显示旧结果、后台更新”，并标明更新时间/更新失败；审批、权限、认领提交前必须用实时状态。
- 同键并发请求合并；缓存不可用时有短超时并回源，不能先等缓存很久再等数据库。过期、空结果、错误和成功分别处理。
- 上线前专门测试调组/降权、他人更新、跨实例更新、取消旧请求、旧请求晚到、缓存故障、长期无人访问后首次打开。

“允许普通列表最多延迟 30～60 秒、自己操作立即更新”是需要负责人确认的产品口径；可推荐沿用现有 60 秒上限，避免无意扩大陈旧窗口。

## 七、验收目标与边界

- 目标按首屏真实可操作时间算；单独记录详情、截图完整出现，不把空壳加载当成功。
- 对照相同账号/权限、数据日期、页面大小、排序和网络。全新浏览器缓存、共享缓存未命中、已命中、写入后刷新四种场景分组。
- 小范围可先各 5 次排错；正式稳定性判断建议每档至少 30 次并跨时段，报告样本数、p50/p95/max、错误率，不把 5 次样本的最大值包装成可靠 p95。
- 拟议目标：常用列表打开 p95 ≤2 秒，重访/返回 p95 ≤1 秒；若网络本身已占用大部分预算，单列网络问题并重新评估边缘交付，而不是宣称数据库修复失败。
- 每阶段要求数据、排序、总数和权限一致；缓存收益同时报告首次与重复访问，不能只挑热缓存成绩。
- 本轮浏览器新基线 **BLOCKED**：原 Chrome 标签由另一会话占用；独立 Chrome、内置浏览器新建页均超时。没有完成今日登录态冷/热浏览器复测，因此不提供伪造的当前整页 p95。
- 旧报告 10/23 的冷 p50/p95 为 2.710/2.911 秒、热为 1.364/1.582 秒，只作为历史参考，不能覆盖今天筛选/版本变化。
- 现有首屏观测表近 48 小时有 641 个样本，total p95 3640ms；但只记录 perspective/view/teamId，没有环境/发布版本，且本地开发指向生产库，不能证明这些全是生产访问。各阶段 p95 也不能相加。先修观测区分再用于上线判断。
- 当前无法读取 Cloudflare 控制台规则；响应头能证明本次请求命中/未命中，不能证明全部地区、全部配置和长期命中率。
