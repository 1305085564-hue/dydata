## 3. 架构定稿

### 3.1 最终链路

```
浏览器 <img src="/api/submission-screenshots/file?path=X">
   │  （自动携带 shot_grant Cookie）
   ▼
Vercel Route Handler
   ├─ 1. path 合法性校验            （本地，<1ms）
   ├─ 2. 票据校验：HMAC + 过期 + owner∈allow（本地，<1ms）  ← 快路径
   ├─ 2'. 票据缺失/失效 → 原逻辑：getUser + 权限上下文        ← 慢路径，保留
   ├─ 3. 取图：COS 优先 → 服务端字节回退 Supabase
   └─ 4. 返回字节流 + Cache-Control 按图龄分档（≤3 天 1800 / >3 天 2592000）
   ▼
腾讯云 COS（候选 `ap-singapore`，私有桶）  ←—— 服务端签名 300s
```

### 3.2 为什么是同源代理（不是自定义域名、不是 CDN、不是 302 直连）

- `dydata.cc` 未备案 → 控制台绑定自定义域名被拒（实测）；COS 默认域名对 2024 年后新建桶强制 `attachment`（实测响应头含 `x-cos-force-download: true`），页面内 `<img>` 能渲染但顶层打开会变下载。
- 备案周期不可控，与"尽快上线"冲突。
- 同源代理是**官方支持的 HTTP 取流方式**，不依赖备案、不依赖 CDN、前端 URL 零改动、Cookie 天然同源。
- 代价：Vercel 出口流量 + 单程耗时，必须以 S2 的地域 A/B 实测为准。当前广州桶在 `sin1` 出现连接抖动，新加坡候选桶已达到单图与并发门槛；月流量约 2.5GB，套餐内，成本可忽略（见 §7）。

> 已否决：自定义域名（需备案）、COS 默认域名直连（强制下载）。地域不靠先验判断：香港函数/广州桶的 A/B 已不达标，新加坡桶仅作为当前实测候选，转正前仍需用最终配置复测。

### 3.3 对象键：与 Supabase 完全一致

```
{userId}/{accountId}/{screenshot_1|screenshot_2}/{timestamp}-{uuid}.{ext}
```

**这是"原样迁移"的技术定义**：COS 的对象键 = Supabase 的 storage path，因此数据库中 `screenshot_urls` / `curve_screenshot_url` / `retention_screenshot_url` 里存的 `/api/submission-screenshots/file?path=…` **一个字都不用改**，回滚也不需要改数据。

### 3.4 批量授权票据（S1 核心）

**问题**：现在每张图各自走一次 `getUser()`（网络）+ `getCurrentPermissionContext()`（多次查询）+ 签名，10 张图 = 10 遍，实测 1.15–1.28s/张。

**做法**：一次签发票据，图片请求只做本地校验。

- `POST /api/submission-screenshots/grant`
  - 鉴权 + 权限计算：沿用现有 `getCurrentPermissionContext()`，不新增权限逻辑
  - 载荷：`{ v:1, u: viewerId, allow: ["uuid", …] | "*", exp }`
    - `allow` 取 `scope.visibleUserIds`，不得只按“在职成员覆盖”推导 `"*"`；只有当 `"*"` 与慢路径的完整可见范围严格等价时才允许使用，否则使用列表或走慢路径
    - 条目上限按 Cookie 4KB 反推：120 条 UUID 的实际编码值约 3,427B，连同 Cookie 属性必须留安全余量；编码后超过 3,800B 一律不发票并记录 `grant_oversize`
    - 票据有效期改为 **30 分钟**，剩余 5 分钟自动续签；权限变更的最长陈旧窗口因此为 30 分钟。若业务要求立即撤权，必须关闭快路径或增加可撤销会话版本，不能把本地票据称为实时等价授权
  - 签名：`HMAC-SHA256(payload, SCREENSHOT_GRANT_SECRET)`，deflate + base64url；票据不包含图片路径，Cookie 内容不作为 URL 或日志输出
  - 输出：`Set-Cookie: shot_grant=…; HttpOnly; Secure; SameSite=Lax; Path=/api/submission-screenshots; Max-Age=1800`
  - 响应体只返回 `{ exp }`，**不返回任何路径或图片地址**
- 前端挂载：只在实际展示截图的内容详情区域挂 `<ScreenshotGrant>`，挂载即申请；票据未就绪前不渲染 `<img>`
- 校验：`file` 路由解票据 → 校验 HMAC、版本、大小、`exp` → 校验 `path` 首段（ownerUserId）是否在 `allow` 内；失败一律落慢路径
- 票据快路径不读取 Cookie 中的权限字段以外的业务数据；上传接口显式忽略 `shot_grant`
- 7 个业务登出入口全部清票据：5 个前端 signOut 调用点（工作区弹窗、移动端抽屉、登录页两条异常分支、重置密码成功后）+ 2 个 server action（`src/lib/account-actions.ts`、`src/app/actions/auth.ts`）；独立的 `/auth/logout` 兜底路由也必须清理。客户端先调用清票据接口，再执行 Supabase signOut；服务端直接清 HttpOnly Cookie

**为什么不用"每图一个签名 URL 参数"**：签名本身是本地运算（0ms），真正的开销是每图一次会话校验 + 权限查询；票据把这 N 次压成 1 次。签 URL 参数反而要把票据塞进每个 `<img>`，改动面更大。

**安全边界**：慢路径代码一行不删；无票据、篡改、过期、超大或配置缺失均落慢路径。快路径是 30 分钟的权限结果缓存，不是实时撤权机制；方案不得再宣称“完全等价安全”，必须在 S1 报告中记录这一陈旧窗口。

### 3.5 缓存策略（三层）

| 层 | 策略 | 效果 |
|---|---|---|
| 浏览器 | 按**图龄**分两档：≤ 3 天 `private, max-age=1800`（30 分钟）；> 3 天 `private, max-age=2592000`（30 天）；带 `ETag` | 新图保留撤回能力；历史图不用反复回源 |
| Vercel | 不缓存响应（`private`，且函数不设 CDN cache） | 避免票据错配到别人 |
| COS | 源站，不设公共读、不设公共缓存 | 私有，仅服务端预签可读 |

**这是对 REQ-06「7 天 immutable」的有意偏离，不是等价满足。** 偏离点与依据：

| 项 | REQ-06 原文 | 本次实现 | 为什么 |
|---|---|---|---|
| 缓存时长 | 7 天 `immutable` | ≤3 天 30 分钟 / >3 天 30 天，两档都可被后续请求改写 | 误传的截图基本当天就发现，30 分钟窗口保住撤回能力；历史图路径不变、不覆盖，适合长缓存 |
| 是否 immutable | 是 | 否 | `immutable` 会让浏览器在该窗口内完全不发条件请求，撤回后也无法及时失效 |

**代价（负责人已接受）**：>3 天的图若需紧急撤回，最长 30 天后才从全部客户端消失。

**图龄判定规则（不可替换）**：只取 path 最后一段文件名的时间戳（形如 `2026-05-18T06-52-59-583Z-xxxx.jpg`）转 UTC。**禁止用 `storage.objects.created_at`**——迁移进 COS 的 5 月老图，其 `created_at` 是迁移当天，会被误判成新图；同样禁止用文件 mtime、上传时间或当前时间近似。path 解析不出时间戳（正在写第一张图）或时间戳在未来时，保守取 30 分钟。

**缓存不跨人共享**：这是私有浏览器缓存，A 看过的图不会让 B 变快。「快」由两件事叠加——分档缓存解决「重复看」，新加坡桶（单图 p95 575ms）解决「第一次看」。不得把缓存写成「首次加载优化」。

URL 中的 path 含 `timestamp-uuid`，现行上传使用 `upsert:false`，正常不会覆盖同一路径。若后续任何流程要复用路径或发现同路径内容哈希不一致，必须禁止写入；不能用改查询参数掩盖对象冲突。A3 必须在 30 分钟缓存窗口内重新测量。

本轮新增或切换共 9 个键，`.env.example` 只写名称和用途，不写值：

### 3.7 读路由决策树（伪代码级，供 Codex 对齐）

```
GET /api/submission-screenshots/file?path=P
  if !isSafeObjectPath(P)                 -> 400
  owner = P.split('/')[0]
  grant = verifyGrant(cookie.shot_grant)  // 本地 HMAC，失败返回 null
  if grant && grant.exp > now && (grant.allow === '*' || grant.allow.includes(owner))
       -> ok = true, mode = 'fast'
  else
       -> user = await getUser(); if !user -> 401
          visible = await getVisibleUserIds(); if !visible.includes(owner) -> 403
          ok = true, mode = 'slow'          // 与原逻辑完全一致
  backend = resolveStoragePrimary(env)       // 缺 COS 配置时强制回 supabase
  for b of [backend, otherOf(backend)]:      // 主 + 备，始终双读
      if b === 'cos': res = cosGet(P, abortAfter=3s)
      else if backend === 'cos': res = supabaseDownloadBytes(P, abortAfter=3s)
      else: res = supabaseSignedRedirect(P)  // 仅主存储为 supabase 时保留旧 302
      if res.ok -> return res
      record fallback_reason/status/latency
  if bothConfirmedNotFound -> 404
  else -> 502/503
```

**注意**：`supabase` 作为主存储时保持现在的 302 + `no-store`；COS 主读失败时必须由服务端下载 Supabase 字节并在同一响应内返回，不能用 302 作为回退。REQ-02 的“等价”验收比较最终图片字节和最终状态，不把“Supabase 主模式 302”与“COS 主模式 200”直接当成同一状态码。

每个后端读取都必须有 AbortController 超时；3 秒是单个主存储的上限，不得让“主存储 3 秒 + 备存储 3 秒”无界叠加，整条函数链路要有总预算并在日志中记录超时来源。

**大图例外**：S0 先统计最大单图和 `>4.5MB` 张数。默认路径只走同源代理；若 Vercel Node 流式返回实测仍受 4.5MB 响应限制，`>4.5MB` 对象才允许受限 302 到 COS。该例外明确违背两条约束：REQ-04“预签 URL 不下发浏览器”、REQ-05“回退不让浏览器二次跳转”。代价是签名 URL 暴露在浏览器网络链路、COS 响应头/缓存不再完全由应用控制、撤权与回退语义变弱；必须单独计数、短时签名、禁止把它当作标准路径，并在生产切换前确认数量与风险可接受。

## 5. 回滚设计（三层，逐层可执行，不靠"改个环境变量"口头承诺）

| 层 | 手段 | 生效时间 | 前提 |
|---|---|---|---|
| L1 降级 | `SCREENSHOT_STORAGE=supabase` + 重新部署 | ~1 分钟 | 双读回退常开，即使 env 写错也不会丢图 |
| L2 代码回滚 | Vercel 回滚到上一 Ready 部署（记录 SHA） | ~30 秒 | 沿用现有 `rehearse:rollback` 流程 |
| L3 数据回滚 | Supabase 原图 30 天内未删，逐字节一致 | 即时 | S3 未执行删除 |

**为什么"双读"是回滚的地基**：路由永远先读主存储、失败读备存储。因此：
- 迁移没跑完 → COS 404 → 自动回 Supabase，员工无感
- 切回 supabase 但新图已在 COS → Supabase 404 → 自动回 COS，新图不丢
- 任一存储临时故障 → 另一侧兜底

**回滚救不了什么（必须写在手册首页）**：`SCREENSHOT_STORAGE=cos` 之后上传的图**只写 COS，不写 Supabase**，Supabase 侧没有副本。COS 写失败时接口返回 500 并记 `write_failed`，用户在页面上看到的是失败，不是「已上传」；这类失败**不能靠回滚恢复**，只能让用户重传。回滚能覆盖的只有切换前已迁入 COS 的 3,122 张历史图。

**写入失败负向验收**：`src/app/api/submission-screenshots/write-failure.test.ts` 在 `SCREENSHOT_STORAGE=cos` 下模拟 COS PUT 返回 500，断言 HTTP 500、响应体无 `path`/`url`/`data`、日志含 `write_failed` + `backend=cos`，且全程只有 1 次 COS PUT、没有第二次写 Supabase。该测试不依赖真实 COS，可在 CI 跑。

**故障可见性**：回退成功也必须记为一次存储故障，不能只看用户是否拿到 200。观察指标至少包括主存储 404/5xx/timeout、回退成功率、两侧都失败率、按后端拆分的耗时与对象大小；正常未授权 400/401/403 不计入“已授权图片失败率”。

**真实演练（S2 必做，产出报告）**：
1. Preview 部署，设 `SCREENSHOT_STORAGE=cos`，取 10 张图 → 记录状态码 + sha256
2. 改 `SCREENSHOT_STORAGE=supabase` 重新部署，同 10 张 → 状态码 200，sha256 与步骤 1 完全一致
3. 再切回 `cos` → 同 10 张仍一致
4. 故意填错 COS 密钥 → 图片仍能出（走回退），只变慢
5. 报告写入 `output/screenshot-rollback/`，作为"可回滚"的证据，而不是口头结论

**删除动作单独治理**：删除脚本必须 `--dry-run` 默认、逐条列出、二次确认、输出删除清单，禁止在 CI/deploy hook 中自动执行。

## 6. 迁移细则补充

- 清单直接从 `storage.objects` 取，不猜路径、不扫本地
- 只迁 `submission-screenshots`，不碰其他桶
- 迁移期间线上运行不受影响（只读源、只写目标）
- Supabase 侧现有字节对象约 878.6MB（实测口径），单次跑完不需分天；若中途触发限流，脚本支持断点续跑
- **不做**：不重新编码、不改扩展名、不改 Content-Type、不重命名、不压缩
- 879MB/886MB 的差异来自违规桶或历史缺失；本轮集合严格以 `bucket_id='submission-screenshots'` 为准，`source_missing` 与违规桶都要单列统计，不得把缺失字节伪装成迁移成功
- 现有 `video-lifecycle` purge 只删除 Supabase；切换后必须补 COS 清理或明确由后续人工清理，不能让 COS 长期产生孤儿对象

## 12. 需求清单六问终审结论

这一节是施工门禁，不是把“有回退”当成“没有故障”。当前实测证据以《2026-10-19-Preview验收实测》为准；Production 尚未切换。

| 问题 | 结论 | 施工补全与验收门禁 |
|---|---|---|
| 1. 票据是否等价安全 | **需修改，条件通过** | 30 分钟票据只是权限结果缓存，也是一个可重放的 bearer Cookie，不是实时撤权。员工被调岗/移除后最长可能保留 30 分钟可读窗口；登出清 Cookie 只覆盖当前浏览器，不等于撤销已复制的票据。方案不得写“完全等价安全”。若业务要求立即撤权，先关闭快路径，或另立可撤销版本机制；本轮不新增 schema。验收必须记录票据签发时刻、撤权时刻和仍可读的最长窗口，并把票据泄露/重放列入风险。 |
| 2. 双读会不会隐藏 404/5xx | **通过，需保留故障门禁** | 回退成功仍记主存储故障，按 `404/5xx/timeout/signature` 分原因统计 `fallback_rate`、两侧失败率、后端耗时与对象大小；日志不得记录 path、Cookie 或密钥。连续 30 分钟回退率上升或持续超过 1% 立即告警并具备 L1 降级，不得只看最终 200。 |
| 3. Vercel 响应体限制 | **通过当前集合，不能外推** | S0 必须同时给出总数、现有字节数、最大单图、`>4.5MB` 数量，并用最大对象做 Preview 流式响应、`Content-Length`、失败回退测试。当前最大对象为 4,448,965B，`>4.5MB` 为 0，因此不启用 302 例外；若未来出现超限对象，必须单独复审 REQ-04/REQ-05 偏离，不能自动放开浏览器直连。 |
| 4. `immutable` 与换图冲突 | **需修改，保留产品取舍** | 当前上传是随机 UUID + `upsert:false`，正常不会复用 path；但需求清单写的是 7 天 `immutable`，方案改成 30 分钟缓存是安全取舍，不是无条件满足原要求。推荐继续使用 `private, max-age=1800`，并在验收中明确这是对 REQ-06 的有意偏离；若必须执行 7 天缓存，需先确认撤权和同 path 替换风险由产品接受。发现同 path 哈希不一致时必须拒绝写入。 |
| 5. Cookie Path 是否污染上传 | **通过，需补负向测试** | `Path=/api/submission-screenshots` 会让上传接口收到 `shot_grant`，但上传、签发票据和清票据接口都不得把它当鉴权输入、写入日志或转发给 COS。补一条带旧 Cookie 的上传测试，证明权限仍来自现有登录与账号归属校验；Cookie 只由 file 路由消费。 |
| 6. 半迁移时序是否覆盖 | **读取通过，写入边界需补** | 反例：S3 已把旧图 A 复制到 COS，但 S4 尚未切换；此时新上传 B 仍写 Supabase。随后切到 COS，A 由 COS 命中，B 由 COS 404 后回退 Supabase，读取不丢图。反向回滚到 Supabase 时，A 由 Supabase 命中，B 由 Supabase 命中，仍可读。真正的缺口是切到 COS 后新上传 C 只写 COS，若 COS 写入失败则 Supabase 没有副本，回滚不能救 C。因此 S4 前必须验证 COS 写入成功率；S4 后写失败直接报错并告警，不能伪称双写兜底。 |

**终审状态**：方案设计可施工，但不能按“3,504/3,504、广州桶、全部 A1–A5 已达标”旧口径直接上线。当前已知 Production 前置阻塞是：最终桶/地域配置尚未转正复测，A3 刷新缓存没有独立读数，Safari/WebKit 证据未完成，S4 写入失败负向验收未留档，382 条 `source_missing` 仍需单独账本。生产前至少要完成最终配置复测、S4 写入失败负向验收、缓存取舍确认，并保留 `source_missing` 单独账本；未完成项标为 `BLOCKED`，不以静态测试或 Preview 旧部署代替。

**交付物口径同步**：需求清单 D7 写“新增 6 个键”，但当前施工实际需要 9 个键（含 `COS_READ_TIMEOUT_MS`、票据开关和存储开关）。这不是可以默默吞掉的文档差异；施工前必须把 D7 修正为 9 个，或明确哪 3 个键不进入交付范围。
