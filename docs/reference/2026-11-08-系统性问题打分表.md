## 怎么看分数

每条打三个分，都是 1–10 分，越高越要紧：

- **现在有没有**：1 = 只是理论上可能；10 = 已经出过事。
- **破坏力**：真出事时伤多大。1 = 页面难看点；10 = 数字算错、数据丢了或泄露、全站用不了。
- **恶化速度**：不管它，会不会越来越糟。1 = 基本不变；10 = 每多开发一周就更糟。

**综合分**是按三项权衡后的结论分，不是简单平均。

### 合并后的分数怎么重算

1. 每个合并项先以原成员在三个维度中的较高分为基线。
2. 两个风险会互相放大时，只在确实被放大的维度加 1，最高不超过 10。
3. 综合分重新判断，不把成员分数相加，也不把高风险平均掉。
4. 没有合并的项目保留原分数。
5. 同分时按原编号靠前者在前；这只是展示顺序，不代表同分项目之间存在精确的先后差距。

**证据**一栏写的是我凭什么这么判断：
- 实测：原审查记录中有实际命令或检查结果；不等于本轮重新复测。
- 记录：历史日志或文档里写过，本轮没有重跑。
- 推断：凭经验判断，没有直接证据。

**建议**一栏只有三种：
- 立即：现在就该处理。
- 观察：先不动，定期看。
- 不投入：不值得花成本。

## 怎么用这张表

- 每月体检时按这张 25 项表重新打分，只看哪些分数变高了，以及证据是否发生变化。
- 综合分 8 分及以上的，单独讨论解决方案；6–7 分的跟着日常改动顺手收；5 分及以下的不主动投入。
- 分数是排序工具，不是自动施工授权；涉及生产数据、不可逆操作或重要业务行为，仍需单独确认。

### 二、每批的开工与收口标准

| 批次 | 开工前只需确认 | 做完后必须留下的结果 | 暂不做的事 |
|---|---|---|---|
| A | 现行入口、历史目录、待办计划的区分方式 | 一张“当前事实 / 历史证据 / 待核材料 / 归档候选”清单；冲突处注明证据 | 不按文件日期批量搬迁，不删除看似重复的材料 |
| B | 本次任务的负责人、允许修改范围、上线授权范围 | 一页交接与验收约定；规则候选标出保留、合并、删除或转自动检查 | 不把所有要求继续塞进 `AGENTS.md`，不把 AI 的口头自报当证据 |
| C | 每个检查实际覆盖什么、漏掉什么 | 检查清单写明“已运行、未运行、只覆盖局部”；关键成功路径的验证记录 | 不因一个门禁通过就宣布整体通过，不为了绿灯删掉必要测试 |
| D | 开发、测试、生产的连接边界和当前状态 | 环境边界表；数据库对账任务的报告入口和待核问题 | 不连生产做试验，不执行迁移、写入、重置或磁盘清理 |

| H | 返工趋势或性能基线确实支持投入 | 成本/性能前后对比，或明确“不值得继续投入”的证据 | 不因历史上出现过一次慢就全面优化，不以提交标题推算返工率 |

### 三、与阿禅对齐的节点

1. **A 批完成后对齐一次**：确认哪些文档是真正的当前依据，哪些只是历史材料；确认后才允许执行实际归档。
2. **B–D 批完成后对齐一次**：确认规则、证据、上线范围和环境边界是否够用；这一步通过后再进入业务和代码治理。
3. **E–H 每批开工前各对齐一次**：只需要拍板本批的业务口径、验收范围和是否值得投入，不需要逐条审批纯只读清点。

推荐路线覆盖上表 25 项且每项只出现一次：A = #9、#19、#23；B = #2、#4、#10、#11；C = #3、#7、#12；D = #8、#16、#25；E = #6、#15、#20；F = #1、#21、#22；G = #13、#14、#18；H = #5、#17、#24。
