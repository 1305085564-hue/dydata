# 截图识别「AI 返回格式无法识别」根因与修复（2026-10-10）

> 状态：线上已止血并完成端到端验收。配置变更（绑定）即时生效；代码修复随并行会话的 `0d4a4867` 一并在 2026-10-10 13:00（上海）上线，
> 生产真实接口读数见 `docs/reference/2026-10-10-截图识别修复推送后线上核对.md`。
> 排查方式：生产库只读核对 + 真实渠道实测（读真实上传截图，非构造数据）
> 结论标注：本文每条根因都写明「实测」或「推测（待验证）」

## 一、一句话结论

截图识别被切到「看图」通道后，绑定模型的第一条渠道**根本不看图**——它把请求当纯文字处理，
回一段「我目前没有看到任何截图」。这段说明文字不是 JSON，页面就统一显示「AI 返回格式无法识别」。

同时，两条通道都坏了：看图通道第一条渠道不看图；百度通道绑定的模型行早已被停用，只能兜底到一条
26–33 秒超时/报错的渠道。也就是说**这期间无论用户在页面上怎么点，识别都不会成功**。

## 二、现象

登录用户上传互动截图与完播截图后，两张卡片都显示：

> AI 返回格式无法识别，请手动填写或稍后重试，截图已保留，可直接手动填写指标，请核对右侧指标

顶部横幅「2 张截图识别未确认，请对照原图核对指标后提交」；接口 `/api/ocr-screenshot` 返回
`500 + error_code = AI_PARSE_FAILED`（实测：`src/app/api/ocr-screenshot/route.ts:302-310`）。

## 三、根因（实测）

### 3.1 看图通道顺位第一条渠道不看图

生产配置（实测只读查询 `ai_feature_bindings`）：

| feature_key | label | model_id | channel_settings | updated_at |
|---|---|---|---|---|
| ocr_screenshot | 截图识别·看图回退 | `claude-haiku-4-5-20251001` | `{"ocr_screenshot_channel":"vision"}` | 2026-10-09T06:46:03Z（上海 10-09 14:46） |
| ocr_screenshot_structure | 截图识别·文字结构化 | `gpt-6.1-sol` | `{}` | 2026-10-03T06:14:47Z |

运行时顺位（实测）：

```
api1/claude-haiku-4-5-20251001  →  api1/claude-haiku-4-5-20251001  →  api7/claude-haiku-4-5-20251001
（key 610eca77，优先级 10）        （key 6bcfb6b5，优先级 52）        （key ac2702ba，优先级 105）
```

用真实上传的抖音截图（873×1920，取自 `submission-screenshots` 桶）实测该链第一条渠道返回：

- 数据图：`I understand. I'm ready to help you extract data from Douyin (TikTok) screenshots...I'm ready. Please provide the screenshot.`
- 完播图：`I can't help with this request. I'm Kiro, an AI development environment...`
- 另一轮：`我理解了你的需求。我是抖音数据截图 OCR 助手...请上传截图`

即：**图片被上游丢掉了，模型只看到提示词没看到图**。这类正文里没有任何 JSON，`parseOcrResponse`
返回 `null`，路由按 `AI_PARSE_FAILED` 返回「AI 返回格式无法识别」。

运行时的健康计数留下了同一条证据（实测生产库 `ai_provider_key_models`）：

```
id 610eca77（api1 / claude-haiku-4-5-20251001）
  consecutive_failures = 3
  last_failure_scope   = unknown
  last_error_message   = AI 返回内容不符合输出契约（疑似该渠道不支持本次请求类型）｜raw=我理解了你的需求，但我需要澄清一下：我目前没有看到任何截图。请上传抖音数据截图…
```

### 3.2 百度通道（两步）同样是坏的

`ocr_screenshot_structure` 绑定 `gpt-6.1-sol`，但该模型的三条挂载行中：

- `5106dbfc`（api9 gpt，绑定指向的行）：`is_enabled = false`（已停用）
- `b39f33d7`（api1 default）：`is_enabled = false`
- `355a4249`（api tang ChatGPT）：唯一可用，实测结构化调用 26–33 秒后超时/报错

也就是说，即使把通道切回百度，结构化这一步也拿不到结果。

### 3.3 代码缺口：顺位链只兜传输错误，不兜「200 但不是结果」

`sendWithFailover` 只在 HTTP 失败/超时/空正文时换下一个渠道（`src/lib/ai/client.ts`）。
正文解析发生在 `callAi` 返回**之后**（`route.ts` / `baidu-channel.ts`），所以：

- 坏渠道返回 `200 + 一段说明文字` → 顺位链认为成功 → 解析失败 → 整单报「格式无法识别」，
  **后面的好渠道根本没被尝试**。

这是本次「一条坏渠道 = 整单失败」的直接代码原因，也是 2026-10-03 事故（后台测试通过、页面仍报错）的同族问题。

### 3.4 为什么后台「试跑」没拦住（实测代码位置）

- 试跑取的是「该模型在这个渠道清单里的第一条」（`business-functions-panel.tsx:299-302`
  `currentModelKeys[0]`），而运行时按 `key.priority + provider.priority` 升序（`provider-routing.ts:325-333`）——
  两者可以指向不同渠道。
- 看图试跑的探针图是 1×1 像素（`src/app/api/admin/ai-config/route.ts:759 VISION_PROBE_IMAGE`），且只判断 HTTP 200
  （`probeProviderModel`，同文件 779 行起），**无法分辨「真看图」和「收下请求不看图」**。

## 四、修复

### 4.1 线上止血（已生效，配置层，可回滚）

单条语句（PostgREST 一次 UPDATE，同事务）把两步都绑到实测稳定、数值正确的渠道模型：

```

{ "model_id": "gemini-2.5-flash-lite", "provider_key_model_id": "ade9940b-69de-4a0e-a589-649939f93f8a" }
```

`channel_settings` 未改动，仍保留用户选择的「看图」通道；配置 60 秒内自动生效，无需发版。

### 4.2 代码修复（已随 `0d4a4867` 上线，详见推送后核对留档）

给顺位链加「正文契约」这一环：

- `src/lib/ai/client.ts`：新增可选入参 `validateContent`；`assertContentContract()` 在正文不符合契约时
  抛可重试的渠道错误（`errorType = content_contract_violation`），于是
  ①记一次渠道失败 ②顺位到下一个渠道，而不是把这段正文当结果交出去。
  失败按 scope=unknown 记在**该模型行**上，不会把整把渠道钥匙拉黑（同渠道的其它模型不受影响）；
  连续 3 次后该行健康冻结 5 分钟，坏渠道会被自动淘汰。
- `src/app/api/ocr-screenshot/ocr-contract.ts`：新增 `hasJsonObject()`（只判断正文里有没有可解析的 JSON 对象）。
- `src/app/api/ocr-screenshot/route.ts`（看图）与 `baidu-channel.ts`（结构化）都在调用处传
  `validateContent: hasJsonObject`。

回归测试：`route.test.ts` +2（契约探针、两处调用都接线），`client.test.ts` +2（契约失败可重试、
不牵连整把钥匙）。全量 `npm test` 2176/2176 通过。

## 五、顺带发现（未处理，需阿禅裁决）

1. **api1 上两条 `claude-haiku-4-5-20251001` 挂载行是假库存**（实测）：
   - `610eca77`（api1 claude）：看图请求返回 200 但明确说「没有看到任何截图」；
   - `6bcfb6b5`（api1 default）：上游 503「分组 plus 下模型 claude-haiku-4-5-20251001 无可用渠道」，
     `consecutive_failures = 27`，最近一次成功是 2026-10-05。
   建议：按渠道内停用收掉，或在 AI 配置中心标记「不支持图片输入」。
2. **api7 gemin 的 `gemini-2.5-flash` 数值有 10 倍错误**（实测）：同一张数据截图，
   api9 gemin 读 `play_count = 91000`（正确），api7 gemin 读 `910000`。而 `gemini-2.5-flash`
   两条渠道优先级并列（都是 55），运行时先撞哪条不确定——`content_analysis`、
   `sample_quality_check` 两个功能也绑在这条模型上，存在写入错误数字的风险。
3. **`default` 绑定仍指向已停用的 `5106dbfc` 行**（实测）：因为绑定里 `model_id` 优先，
   运行时按 `gpt-6-sol` 的顺位走（当前正常），但后台展示的「专属渠道」是过期指针。
4. **试跑口径与运行时口径不一致**（见 3.4）：建议把业务试跑改成按运行时顺位取第一条渠道，
   并把看图探针换成「带可读文字的图 + 要求回声该文字」，否则「测试通过、页面报错」还会复发。
