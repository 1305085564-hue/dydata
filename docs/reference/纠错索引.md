## 补交审批迁移账与函数对象对账

`schema_migrations` 有版本号不等于函数对象已经存在。补交审批曾出现本地已登记 `20261003095010`、但 4 参 `handle_fulfillment_appeal` 不存在，导致真实 4 参入口返回 400/500；禁止通过删 `p_reason` 参数绕过。每次 `supabase start`/`db reset` 后同时核对：

```sql
select version from supabase_migrations.schema_migrations order by version;
select oid::regprocedure from pg_proc where proname = 'handle_fulfillment_appeal';
```

若迁移账与 `pg_proc` 不一致，先追 reset 链的跳过/部分失败日志，再修复对象；迁移登记本身不能作为行为验收。

## 提交链路报错

凡涉及「组员提交/替换/重试」类接口，动手前逐项对照：

**1. 含新字段必须发布三连**
① 生产执行 migration → ② 刷新 PostgREST schema cache → ③ 真实角色 API 实测。
三步缺任一不算完成，日志里必须写明三步均已完成。

**2. delete + insert 替换模式，先确认 DELETE RLS 存在**
在 `supabase/migrations/` 里 grep 该表的 `FOR DELETE` policy。
无策略时，delete 静默成功但影响 0 行，insert 随即撞唯一约束——错误表面是「重复键」，根因是「旧数据未删」。
涉及 `video_tags`、`video_metrics_snapshots`、`video_content_segments` 等表时尤其注意。

**3. rollbackSafely 返回值不能丢弃**
调用后必须：`const rbErr = await rollbackSafely(...); if (rbErr) console.error("[接口名] rollback failed", rbErr);`
回滚失败时第一个业务错误仍返回给调用方，rollback 错误另行记录，两者都不能丢。

**4. 多表回滚走 service role**
`video_metrics_snapshots`、`video_tags` 等无成员 DELETE RLS 的表，回滚删除必须用 `adminSupabase`，
不能用 `supabase`（user client），否则 delete 静默 0 行，造成半提交残留。

**5. 稳定 PK 重试必须覆盖五种状态**
用 `buildSubmissionRecordId` 生成固定 ID 的提交接口，验收时必须人工模拟：
active（正常更新）、trashed（恢复后更新）、purged（应拒绝返回 409）、
他人占用（返回 409）、并发提交（两个相同请求同时到达）。五种都要覆盖，不能只测正常路径。

**6. 成员相关修复，必须用普通组员账号验收全链路**
任何影响成员权限或提交的修复，必须用真实普通组员（有 `team_id` 或 `group_id` 的 `member` 账号）
走完完整提交流程，不能只用 owner/admin 测。
测试账号见 `docs/reference/测试账号.md`（本仓库内，已被 .gitignore 忽略，不外传）。
**禁止**指向 `~/.claude/...` 等 AI 私有目录——AGENTS.md 第四节明令不得在私有目录维护项目文件副本。

## 数据接口报“找不到”或缺字段

接口返回 404、`not found` 或字段不存在时，按下面四类逐项排查，不能只判断“记录不存在”：

1. 记录真的不存在。
2. 权限不足，RLS 或接口鉴权把记录过滤掉了。
3. lifecycle 状态过滤，例如接口只查 `active`，但记录已进入回收站或归档状态。
4. PostgREST schema cache 未刷新，数据库已有字段但 API schema 仍看不到。

读取可能缺列的表时必须做兼容降级，返回空值或默认值，不能因为一个缺列让整页直接崩溃。降级只用于兼容窗口，不能把生产 migration 或 schema cache 验收省掉。

## 弹窗秒关/状态被清零 → 先查父级 key 重挂

症状：React state 明明 set 了，渲染时却是初始值；弹窗一开就消失，页面跳走。
根因模式：父组件用动态值作 `key`（如 `key={账号-日期}`），子组件事件里"一手改 key 变量、一手 set 本地弹窗状态"——key 一变整棵子树卸载重挂，本地状态全部清零。
实例（2026-08-07）：`production-control-system.tsx` 的 `key={selectedAccountId-activeBizDate}` 导致 `handleHistoryReportOpen`/`openSubmittedDate` 里 `setActiveBizDate` + `setEditingReport` 同帧执行时编辑弹窗必被秒杀。
（2026-09-27 核对：文件仍在 `src/app/(app)/dashboard/production-control-system.tsx`，`selectedAccountId`/`activeBizDate` 两个 state 也还在，但已不再拼成 key；上述 key 写法与 `handleHistoryReportOpen`、`openSubmittedDate`、`setEditingReport` 全库 0 命中，系**当时命名，现已重构**。本节保留历史现场，要复现该模式请以下面的「排查手势」为准。）
修法：开弹窗的路径不改 key 变量；或把弹窗状态抬到 key 边界之外。
排查手势：渲染入口打一行 log 看 state 值——set 之后渲染仍是 null = 收到更新的实例和渲染的实例不是同一个（重挂了）。

## 写表名/列名靠猜 → 先取一次真实 schema 再动手

症状：`update`/`insert` 返回 `42703 column "xxx" does not exist`；更隐蔽的是错误被 `.catch(()=>{})` 或 `.then(()=>{},()=>{})` 吞掉，表现为「日报存了、视频没同步」这类静默数据不一致，界面不报任何错。

已经踩过两次（务必引以为戒）：

- `videos` 表的标题列是 **`video_title`**，不是 `title`。`src/app/(app)/dashboard/actions.ts` 曾写成 `title`，源头在 649bb6f8，2026-09-03 重写 H2 历史编辑分支时被原样继承，导致历史编辑保存后 videos 永不更新。已于 2026-09-03 提交 `a8767d8b` 修复（改为 `video_title: title`，当前在该文件第 293 行附近，行号会随改动漂移，以提交号为准），生产复测确认日报与视频标题同步更新。
  - 更正：一度以为该缺陷"静默无提示"，实测**不成立**——失败时前端会弹「日报已保存，但原视频责任人同步失败，请重试」并保持弹窗。当初误判是取证手法问题（见下条），缺陷本身仍是真缺陷。
- `exemption_grant` 表的类型列是 **`grant_type`**（`030_exemption_tables.sql` 建表起就是这个名字，`049_fix_exemption_grant.sql` 补建时沿用）。易混点：`exemption_type` 和 `reason` 都在**另一张表** `exemption_request` 上，`grant_mode` 整个库都没有——把它们当成 `exemption_grant` 的列直接 insert 必败。手工豁免曾这么写，失败还被静默吞掉（即 P0-01，见 `docs/plans/历史-项目/全站质量审计-2026-09-03/`）。
- `profiles` 表**没有 `email` 列**（`001_init.sql` 建表后没有任何 migration 加过该列），按 email 查用户固定失败；当时归在质量审计的 1C 阶段，归档见 `docs/plans/历史-项目/全站质量审计-2026-09-03/`。

排查手势（写多表写入前必做一次，成本几秒）：

```bash
# 用 service_role 取一行，打印真实列名再对照
curl -s "$SUPABASE_URL/rest/v1/<表名>?select=*&limit=1" \
  -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" | jq '.[0] | keys'
```

配套硬规矩：
1. 任何 migration 改了列名，**必须全局 grep 旧列名**，不能只改 migration 文件。
2. 重写/搬运一段写入逻辑时，列名要跟着当前 schema 重新核对，不能因为「原来就这么写的」照抄。
3. 多表写入的失败绝不能静默吞掉；吞掉的后果是数据不一致且无人知晓，比直接报错危险得多。

## 验证 Server Action 的失败路径 → 浏览器拦不到，只能用状态构造法

背景：`"use server"` 的 action 里调 Supabase，请求从**服务端**发出，浏览器 `network route --abort` 拦不到（只能拦到 `/api/*` 路由和浏览器直连 Supabase 的请求）。所以"拦截请求制造失败"对 Server Action 无效。

可行做法（**状态构造法**）：先用 service_role 把目标行改成让写入匹配不到的状态，再走正常 UI 操作，观察前端是否给提示。

实例（2026-09-03 验证 H2 失败提示）：源码里 videos 更新带 `.eq("lifecycle_state", "active")`，于是把该视频临时改成 `trashed` → update 匹配不到行 → `data=null, error=null` → 判定函数 `Boolean(videoId && !result?.data)` 为真 → 前端如期弹出「日报已保存，但原视频责任人同步失败，请重试」。测完把 `lifecycle_state` 改回 `active` 即可，无需改代码。

配证手法（**这条比上条更容易踩坑**）：

- 抓错误提示必须用 `document.body.innerText` 抓全页文本，**不要用 `snapshot -i`**。交互快照只列可聚焦元素，`role=status` 的 toast 经常不在里面。
- toast 会自动消失，点击保存后**3 秒内**取证；等 8 秒再看必然扑空。曾因此误判为"静默失败、用户无感知"，实际提示是有的。
- 判断 action 成功与否的旁证：成功会走 `revalidatePath` 并关闭弹窗；失败则弹窗保持打开。弹窗状态本身就是信号。

注意浏览器端详情有缓存，编辑窗口里看到的可能是旧值，别拿它当数据库真值——一切以 service_role 查库为准。

## 线上取证与"生产到底跑哪一版" → 别拿平台日志当长期通道（2026-10-03，[QW]）

- **平台运行日志只回溯最近约 1 小时**（实测：把查询起点拉到一周前，返回的最早一条仍是 56 分钟前）。跨周的"改前 vs 改后"对照不可得，长期指标只能走数据库账本或异常上报平台；要留 HTTP 层数据必须自己每天落盘或开通日志外发。
- 命令行取数两个坑：`--request-id` 过滤的是**平台自己的请求 ID**，不是应用 `requestId`（要按应用 ID 串联只能拉回本地按 JSON 聚合）；`--until` 传相对时间（`10h`）实测返回 0 条，必须用 ISO 绝对时间。
- **上线生效时刻＝部署 Ready 时刻，不是推送时刻**（本次差 1 分 53 秒）。确认生产实际跑的是哪一版，看结构化日志里的 `detail.release`，不要靠"我推了哪个提交"推断。
- **当前事实文档里"某某已不再…"这类全称结论，必须逐个入口核**：`全站模块地图` 曾写"前端不再二次 PATCH 通知完成"，实际只修了行动中枢一个入口，另一个入口（履约管理页）在线上真实操作时才暴露。同一接口多入口时，写结论前先 grep 全部调用点。
- **样本为 0 就写"未取到＋原因"，不得记通过**；但也不能就此收工——今晚 01:58 判定"今天线上证明不了"，02:03 生产就来了一条真实操作。遇到"暂无样本"应留一个小时级的回看动作，别把它当成结论终点。

## 网络故障『curl 通、命令行工具挂』→ 先做直连/代理对照，别沿用旧记录的根因（2026-10-05，[QW]）

症状：vercel CLI 报 `TypeError: fetch failed`，同机 curl 却一直好使；直觉归因"Node 不走代理／网络不通"，怎么修都修不对，token 过期让案情更乱。

根因模式：本机 shell 挂着代理变量（FlClash `127.0.0.1:7890`），同时 `no_proxy` 白名单含 `vercel.com`、`supabase.co`——**这两类域名设计上走直连**。curl 尊重 `no_proxy`（后缀匹配）所以直连成功；vercel CLI 认代理变量，把请求交给 FlClash 后自身失败。当晚连续两轮误诊的共同源头：沿用了 10-04 留档里一条**未验证的推测**（"Node fetch 不走本机代理"），并且只收集支持它的证据——403 token 过期给"网络也不通"背书、`NODE_USE_ENV_PROXY` 失败被解读成"CLI 无视开关"的强化叙事，而对"昨天 17:4x 还能用"这个反例用"代理模式变了"一个无法验证的故事圆掉。

排查手势（两条命令定案，先于任何旧结论）：

```bash
# ① 强制直连目标域名：通＝直连没问题，别再怪网络
curl --noproxy '*' -sS -m 8 -o /dev/null -w '%{http_code}\n' https://api.vercel.com/v2/user
# ② 清空代理变量跑挂掉的工具：出结果＝就是代理变量带偏的
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy -u ALL_PROXY -u all_proxy npx vercel whoami
```

配套硬规矩：
1. 留档／日志／记忆里的根因结论必须区分**实测**与**推测**；引用别人的根因前先用一条对照实验复核——不核对就复用，等于替上游的错误背书（本次就是被 10-04 的未验证推测带偏）。
2. 一个理论若"任何结果都能解释"（如"通道时好时坏"），等于没有信息量；异常样本（昨天能跑、今天挂）是假设有漏洞的信号，不是需要圆过去的噪声。
3. 网络类故障先跑 2×2 对照（直连/代理 × 目标域名）：**环境里有代理变量 ≠ 流量走了代理**；同理，工具报错 ≠ 网络不通，先分层再定罪。
