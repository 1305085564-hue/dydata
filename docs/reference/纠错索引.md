## 提交链路报错

凡涉及「组员提交/替换/重试」类接口，动手前逐项对照：

**1. 含新字段必须发布三连**
① 生产执行 migration → ② 刷新 PostgREST schema cache → ③ 真实角色 API 实测。
三步缺任一不算完成，日志里必须写明三步均已完成。

**2. delete + insert 替换模式，先确认 DELETE RLS 存在**
在 `supabase/migrations/` 里 grep 该表的 `FOR DELETE` policy。
无策略时，delete 静默成功但影响 0 行，insert 随即撞唯一约束——错误表面是「重复键」，根因是「旧数据未删」。
涉及 `video_tags`、`video_metrics_snapshots`、`video_content_segments` 等表时尤其注意。

**3. rollbackSafely 返回值不能丢弃**
调用后必须：`const rbErr = await rollbackSafely(...); if (rbErr) console.error("[接口名] rollback failed", rbErr);`
回滚失败时第一个业务错误仍返回给调用方，rollback 错误另行记录，两者都不能丢。

**4. 多表回滚走 service role**
`video_metrics_snapshots`、`video_tags` 等无成员 DELETE RLS 的表，回滚删除必须用 `adminSupabase`，
不能用 `supabase`（user client），否则 delete 静默 0 行，造成半提交残留。

**5. 稳定 PK 重试必须覆盖五种状态**
用 `buildSubmissionRecordId` 生成固定 ID 的提交接口，验收时必须人工模拟：
active（正常更新）、trashed（恢复后更新）、purged（应拒绝返回 409）、
他人占用（返回 409）、并发提交（两个相同请求同时到达）。五种都要覆盖，不能只测正常路径。

**6. 成员相关修复，必须用普通组员账号验收全链路**
任何影响成员权限或提交的修复，必须用真实普通组员（有 `team_id` 或 `group_id` 的 `member` 账号）
走完完整提交流程，不能只用 owner/admin 测。
测试账号见 `~/.claude/projects/-Users-mac-Projects-dydata/memory/测试账号-选题库.md`。

## 数据接口报“找不到”或缺字段

接口返回 404、`not found` 或字段不存在时，按下面四类逐项排查，不能只判断“记录不存在”：

1. 记录真的不存在。
2. 权限不足，RLS 或接口鉴权把记录过滤掉了。
3. lifecycle 状态过滤，例如接口只查 `active`，但记录已进入回收站或归档状态。
4. PostgREST schema cache 未刷新，数据库已有字段但 API schema 仍看不到。

读取可能缺列的表时必须做兼容降级，返回空值或默认值，不能因为一个缺列让整页直接崩溃。降级只用于兼容窗口，不能把生产 migration 或 schema cache 验收省掉。

## 弹窗秒关/状态被清零 → 先查父级 key 重挂

症状：React state 明明 set 了，渲染时却是初始值；弹窗一开就消失，页面跳走。
根因模式：父组件用动态值作 `key`（如 `key={账号-日期}`），子组件事件里"一手改 key 变量、一手 set 本地弹窗状态"——key 一变整棵子树卸载重挂，本地状态全部清零。
实例（2026-08-07）：`production-control-system.tsx` 的 `key={selectedAccountId-activeBizDate}` 导致 `handleHistoryReportOpen`/`openSubmittedDate` 里 `setActiveBizDate` + `setEditingReport` 同帧执行时编辑弹窗必被秒杀。
修法：开弹窗的路径不改 key 变量；或把弹窗状态抬到 key 边界之外。
排查手势：渲染入口打一行 log 看 state 值——set 之后渲染仍是 null = 收到更新的实例和渲染的实例不是同一个（重挂了）。

## 写表名/列名靠猜 → 先取一次真实 schema 再动手

症状：`update`/`insert` 返回 `42703 column "xxx" does not exist`；更隐蔽的是错误被 `.catch(()=>{})` 或 `.then(()=>{},()=>{})` 吞掉，表现为「日报存了、视频没同步」这类静默数据不一致，界面不报任何错。

已经踩过两次（务必引以为戒）：

- `videos` 表的标题列是 **`video_title`**，不是 `title`。`src/app/(app)/dashboard/actions.ts:161` 曾写成 `title`，源头在 649bb6f8，2026-09-03 重写 H2 历史编辑分支时被原样继承，导致历史编辑保存后 videos 永不更新且无任何提示。
- `exemption_grant` 表的类型列是 **`grant_type`**（migration 030 改过），不是 `exemption_type`/`grant_mode`/`reason`。手工豁免曾按后者 insert，必败且被静默吞掉（即 P0-01）。
- `profiles` 表**没有 `email` 列**，按 email 查用户固定失败（1C 已记录）。

排查手势（写多表写入前必做一次，成本几秒）：

```bash
# 用 service_role 取一行，打印真实列名再对照
curl -s "$SUPABASE_URL/rest/v1/<表名>?select=*&limit=1" \
  -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" | jq '.[0] | keys'
```

配套硬规矩：
1. 任何 migration 改了列名，**必须全局 grep 旧列名**，不能只改 migration 文件。
2. 重写/搬运一段写入逻辑时，列名要跟着当前 schema 重新核对，不能因为「原来就这么写的」照抄。
3. 多表写入的失败绝不能静默吞掉；吞掉的后果是数据不一致且无人知晓，比直接报错危险得多。
