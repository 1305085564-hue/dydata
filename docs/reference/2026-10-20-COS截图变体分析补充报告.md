原始事故违反的约束是：**截图的写入后端已经切换，但存在性、读取、清理和观测仍有调用点依赖旧后端语义。**

5. 不确定结果轴：上传超时后是否会把“结果未知”误当成“确定失败”或“确定删除”。

### V1：COS 模式配置缺失时静默写回 Supabase

| 项目 | 结论 |

| 级别 | **P1**；若生产环境已确认配置完整，可降为配置漂移防护项；若发现任一生产实例缺配置，保持 P1 |
| 置信度 | 行为代码高；生产是否触发待核 |
| 触发条件 | `SCREENSHOT_STORAGE=cos`，但 `COS_SECRET_ID`、`COS_SECRET_KEY`、`COS_BUCKET` 或 `COS_REGION` 任一缺失；或开关写成未支持的值 |
| 当前是否实测 | 本地函数行为已实测；生产环境变量、实例间一致性未实测 |

现状是：

```ts
if (configured === "cos") {
  return cos
    ? { primary: "cos", cos, degraded: false, reason: null }
    : { primary: "supabase", cos: null, degraded: true, reason: "missing_cos_config" };
}
```

`writeSubmissionScreenshot()` 会据此重新写入 Supabase。读路径也会跟着走 Supabase，但这会让“生产是 COS 主写”的运行事实变成“某些实例仍写 Supabase”。更严重的是 `deleteSubmissionScreenshots()` 没有复用 `resolveScreenshotStorage()`，而是直接调用 `readCosConfig()`；配置缺失时它只能删 Supabase，配置恢复后又会开始双删。`degraded` 目前只写普通结构化日志，`screenshot-storage-observability.ts` 的告警事件白名单没有 `degraded`，所以配置漂移不会进入统一告警。

建议：

1. 生产 `SCREENSHOT_STORAGE=cos` 时，COS 配置不完整直接返回明确的 503/健康检查失败，禁止静默切回 Supabase。
2. 启动检查和 Sentry/日志告警都记录配置缺失、非法值和当前解析结果；配置错误不应只存在于 console。
3. 写、读、删全部接收同一个已解析的 storage resolution，避免 `resolveScreenshotStorage()` 和 `readCosConfig()` 形成两套语义。
4. 把现有测试“缺配置自动降级 Supabase”的断言改成生产 fail-closed 断言；若开发环境仍需降级，必须显式使用开发开关并在日志中标出环境。

### V2：投稿存在性校验把存储故障误报成截图不存在

| 项目 | 结论 |
|---|---|
| 文件:行号 | [`src/lib/screenshot-storage.ts:149-172`](/Users/mac/Projects/dydata/src/lib/screenshot-storage.ts:149)、[`src/app/api/video-submit/route-core.ts:222-240`](/Users/mac/Projects/dydata/src/app/api/video-submit/route-core.ts:222) |
| 级别 | **P1** |
| 置信度 | 高 |
| 触发条件 | COS HEAD 超时、5xx 或 404，同时 Supabase signed URL 失败；或 COS 命中/回退但该检查没有携带请求号和事件上下文 |
| 当前是否实测 | 静态代码确认；未在 Preview 注入 HEAD 超时/双端失败 |

`findReadableSubmissionScreenshots()` 只返回 `readable` 和 `missing`：

```ts
const head = await cosHeadObject(resolution.cos, path, cosTimeoutMs);
if (head.ok) return { path, ok: true };
const { data, error } = await createAdminClient()
  .storage.from(SCREENSHOT_BUCKET)
  .createSignedUrl(path, 60);
return { path, ok: !error && Boolean(data?.signedUrl) };
```

调用方随后把所有 `missing` 统一映射为 HTTP 400：“截图不存在或无法读取，请重新上传”。因此 COS 暂时不可用、Supabase 也超时或拒绝时，用户会被要求重新上传，真实故障被伪装成用户数据错误。这个入口还没有 `requestId` 参数，也没有发出 `screenshot_read_failed` / `screenshot_read_fallback`，所以关键的投稿阻断路径不计入读取失败和回退率告警。

建议：

1. 将结果改为至少三态：`readable`、`missing`、`unavailable`，其中超时/5xx/签名服务异常都进入 `unavailable`。
2. `unavailable` 映射为 502 或可重试的业务错误；只有两边明确 404 才返回“截图不存在”。
3. 传入统一 `requestId`，复用读适配器的事件字段；COS HEAD 失败后 Supabase 成功必须记录一次 fallback，双端失败必须记录一次 read_failed。
4. 为投稿路由增加 COS 命中、Supabase 回退、双端 404、COS 超时和双端故障五个断言，不能只测 `missing` 数组。

### V3：清理引用判断未统一规范化为 storage path

| 项目 | 结论 |

| 级别 | **P1/P2**：生产存在非规范 URL 时为 P1；只作为未来数据防护时为 P2 |
| 置信度 | 代码高；生产数据中是否存在触发样本待核 |
| 触发条件 | 快照顶层字段或替换历史存有旧 Supabase 域名、历史 Vercel 域名、不同代理域名或不同 URL 编码形式 |
| 当前是否实测 | 本地 parser 测试覆盖标准绝对/相对/编码 URL；未做生产只读统计 |

当前清理器先生成两种固定 URL：相对代理地址和 `https://dydata.cc`，然后在 `screenshot_urls`、曲线图、留存图和替换历史上做精确 `contains/eq/in` 查询。虽然 `screenshotPathIsReferenced()` 能解析更广的 URL 形态，但它只用于递归扫描 `vs_previous` 和有效申诉草稿；顶层快照和替换历史的快速查询没有走同一个 parser。

如果一个仍被业务引用的对象保存为 `dydata.vercel.app`、旧 Supabase public URL 或其他合法代理外形，快速查询会返回“没有引用”。对象超过 30 天后，清理任务可能调用统一删除器删除仍在使用的 COS 图。当前测试只证明 parser 能识别若干 URL，没有证明 `isSubmissionScreenshotReferenced()` 的所有字段都使用 parser。

建议：

1. 先将每个业务值解析成 canonical storage path，再按 path 比较；不要把 URL 字符串作为引用主键。
2. `screenshot_urls`、`curve_screenshot_url`、`retention_screenshot_url`、替换历史、`vs_previous` 和有效草稿全部使用同一解析器。
3. 生产只读统计各 URL 形态和解析失败数量；在统计完成前，解析失败或未知 URL 必须按“有引用”保留，不能按未引用删除。
4. 增加旧 Supabase URL、历史域名、未编码 query、双重编码和非法 URL 的清理契约测试。

| 项目 | 结论 |
|---|---|
| 文件:行号 | [`scripts/check-screenshot-storage-boundary.mjs:43-51`](/Users/mac/Projects/dydata/scripts/check-screenshot-storage-boundary.mjs:43)、[`scripts/screenshot-storage-boundary.test.mjs:33-44`](/Users/mac/Projects/dydata/scripts/screenshot-storage-boundary.test.mjs:33) |
| 级别 | **P2** |
| 置信度 | 高 |
| 触发条件 | 业务代码先保存 `supabase.storage`、使用 `supabase["storage"]`，或先保存 `supabase.storage.from(bucket)` 再调用方法 |
| 当前是否实测 | 已实测：三个隔离 fixture 均被门禁判为 PASS |

门禁只接受“当前节点是 PropertyAccessExpression，且父链正好是 `supabase.storage.from(...).method(...)`”。它没有追踪变量来源，也没有处理括号属性访问。以下三类业务代码目前都能通过：

```ts
const storage = supabase.storage;
storage.from("submission-screenshots").download(path);

const storage = supabase["storage"];
storage["from"]("submission-screenshots")["remove"]([path]);

const from = supabase.storage.from("submission-screenshots");
from.download(path);
```

建议：

1. 短期补充上述 fixture，并让 CI 在任一 fixture 通过时失败。
2. 中期做有限数据流追踪：记录 `const x = supabase.storage`、`const y = x.from(...)` 和括号属性访问；动态 bucket 只要来源可能是投稿桶就阻断。
3. 更稳妥的边界是：除唯一适配器文件和明确白名单脚本外，业务层出现 `storage` 属性、Storage 方法名或 Supabase Storage URL 字符串就失败；迁移/审计脚本单独白名单。

### V5：到期清理和正在提交的旧草稿之间存在删除竞争窗口

| 项目 | 结论 |
|---|---|
| 文件:行号 | [`src/lib/screenshot-upload-cleanup.ts:77-107`](/Users/mac/Projects/dydata/src/lib/screenshot-upload-cleanup.ts:77)、[`src/lib/screenshot-upload-ledger.ts:95-102`](/Users/mac/Projects/dydata/src/lib/screenshot-upload-ledger.ts:95)、[`src/app/api/video-submit/route-core.ts:991-1004`](/Users/mac/Projects/dydata/src/app/api/video-submit/route-core.ts:991) |
| 级别 | **P1（条件触发）** |
| 置信度 | 代码高；实际并发窗口和发生率待运行时验证 |
| 触发条件 | 已超过 30 天、账本仍为 `uploaded` 的图片被用户从本地草稿重新提交；定时清理刚完成“无引用”查询，投稿事务尚未把快照引用落库 |
| 当前是否实测 | 静态调用顺序确认；未做并发故障注入 |

清理器按 `uploaded` 状态和过期时间取记录，随后先查业务引用，再调用删除器，最后才更新为 `deleted`。投稿路径则在保存视频、快照、日报和替换历史之后，才将上传账本更新为 `referenced`。两段之间没有数据库锁、条件状态转换或“清理中”占位状态。

因此，在用户仍持有 30 天以上的本地草稿并正提交时，清理任务可能先查到“还没有数据库引用”，随后删除 COS 对象；投稿再成功写入快照并把账本标记为 `referenced`，形成“业务记录存在、截图对象已删”。30 天宽限期能降低概率，但不能关闭这个竞态。

建议：

1. 投稿在开始持久化前，原子地把对应账本记录预留为 `in_use`；失败再按补偿流程恢复或清理。
2. 清理器先用条件更新原子领取 `uploaded -> cleanup_claimed`，仅领取成功的任务可删；投稿遇到 `cleanup_claimed` 必须阻断并要求重传，不能继续写引用。
3. 删除前确认账本状态仍由本次清理持有，并确认业务引用；清理与投稿必须共享状态迁移规则。
4. 用并发测试卡住清理器在“引用检查后、删除前”的位置，同时执行投稿；断言已提交的路径不会被删除。

### V6：PUT 超时后服务端晚到写入的竞态（低置信候选）

| 项目 | 结论 |
|---|---|

| 触发条件 | 客户端 PUT 超时，但 COS 仍在服务端处理；清理任务删除对象时 COS 暂报 404、账本被标记 `deleted`，原 PUT 随后才完成 |

上传超时会进入 `delete_pending`，避免直接把不确定写入标成已删除；但清理任务在删除成功后立即将账本写成 `deleted`，而 COS 删除器把 404 当成成功。若原 PUT 仍在服务器端进行，并在这次 DELETE 之后才落地，终结状态不会再被重试。定时任务每天执行一次，当前没有证据证明该时序已发生，也没有代码或契约测试排除它。

建议在隔离桶模拟“客户端超时、服务端延迟提交”，确认延迟 PUT 在清理 DELETE 后是否仍能完成。若可复现，则把超时标为 `write_unknown`，延后终结并在宽限后 HEAD/DELETE/HEAD 对账；不能仅凭一次 DELETE 返回 404 就标记终态。

- `src/lib/screenshot-storage.ts` 是生产代码唯一允许的 `supabase.storage` 入口。

- `scripts/`、`supabase/` 只有逐文件白名单例外；写入或删除脚本必须额外标注用途并单独运行。
- 每种绕过写一个失败 fixture：直接链、变量别名、拆链、括号访问、动态 bucket、URL 拼接、`storage.objects` SQL。
- CI 同时运行适配器契约测试和“上传→读取→提交→编辑→换图→删除”集成测试；迁移脚本 dry-run 不能替代业务链测试。

## 证据边界

- **已实测**：全仓静态扫描；`npm run gate:screenshot-storage` 返回 PASS；三个门禁绕过 fixture 均错误地返回 PASS；本地配置解析和 URL parser 单元测试现状已读取。
- **未实测**：生产 COS/Supabase 配置一致性、生产引用 URL 形态、Preview 双端故障、Sentry 聚合和通知送达、三种真实角色、2026-05 缺图编辑态、T6。
- **当前没有 P0 证据**：只有在出现批量误删、越权读取或全员提交阻断时才升级 P0 并暂停发布。
