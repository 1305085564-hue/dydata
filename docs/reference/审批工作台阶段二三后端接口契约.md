# 审批工作台阶段二三后端接口契约

## `GET /api/exemptions/pending`

管理员读取统一待审批池。返回 `{ data, count }`，`data` 同时包含豁免申请和补交申诉，按 `created_at` 倒序并受 `limit` 限制。

补交申诉行的固定字段：

- `source: "fulfillment_appeal"`、`id`/`request_id`/`appeal_id`：申诉编号（当前行 `id` 与 `request_id` 均为申诉 UUID）。
- `appeal_type`：`"日报" | "视频"`。
- `business_date`：业务日期，等同 `record_date`。
- `reason`：成员提交的补交理由。
- `attachment_urls`：附件链接数组，来自已保存提交数据的 `assets`。
- `absence_days`：该成员该业务日仍为 `absent` 的天数（本接口不计算当月履约率或当月出勤汇总）。
- `account_id`、`account_name`、`applicant_user_id`、`applicant_name`。
- `request_status: "pending"`、`created_at`。

## `GET /api/exemptions/history?limit=50`

管理员读取已处理统一历史池。返回 `{ data, count }`。补交申诉行除上述字段外还返回：

- `request_status`：`"approved" | "rejected"`。
- `reviewed_by`、`reviewed_by_name`、`reviewed_at`：处理人和处理时间。
- `rejection_reason` / `feedback`：驳回原因；通过时为 `null`。

## `POST /api/admin/fulfillment/appeal/handle`

现有审批接口保持入参：

```json
{ "appealId": "uuid", "decision": "approve|reject", "reason": "驳回原因（reject 必填，最多 1000 字）", "notificationId": "uuid?" }
```

返回分层结果：`status`、`businessSucceeded`、`auditStatus`、`employeeNotificationStatus`、`todoStatus`、`notificationMarked`。审批结果通知仍由服务端发送；`decision_reason` 由 migration 中的四参数 RPC 持久化。

## `POST /api/admin/fulfillment/appeal/reopen`

将已通过或已驳回申诉打回待审批，并保留原审批审计、追加 `reopen_fulfillment_appeal` 审计。入参：

```json
{ "appealId": "uuid" }
```

返回：`{ ok: true, appealId, status: "pending", oldResultNotificationsVoided: true, todoReissued: boolean }`。原“已通过/已驳回”结果通知会作废，管理员同源待办会重发。
