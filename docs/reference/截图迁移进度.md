## 「替代完成」的准确含义

很多人（包括我）会把「四步做完」等同于「替代完成」，这两件事不是一回事。

```
四步做完 → 只是「具备切换条件」
第 4 步切换 → 读切到 COS，新图只写 COS（真正的不可逆点）
S5 观察 7 天 → 证明切过去没有新问题
D+30 删 Supabase 原图 → Supabase 真正退出存储，替代完成
```

切换后三条路径的实际行为（依据 `src/lib/screenshot-storage.ts`）：

| 路径 | `SCREENSHOT_STORAGE=cos` 下的行为 | 兜底 |
|---|---|---|
| 读 | 主读 COS，失败回退 Supabase | ✅ 有 |
| 写 | **只写 COS，不写 Supabase**；COS 失败直接返回错误 | ❌ 无 |
| 删 | Supabase + COS 两边都删 | — |

**结论**：切换后若需回退，历史 3,122 张可救；**切换之后新上传的图在 Supabase 侧无副本，救不回来**。

两个前置认知：

1. 382 条历史缺失在 Supabase 侧本来就是「有元数据、无字节」，不能当作回退保险；回退能覆盖的是 3,122 张。
2. 第 2 步（换桶地域）不做也能切换，但要接受已知的冷连接抖动（p95 1,027ms），表现为「偶尔第一张图慢约 1 秒」，不是报错。

**它救不回什么**：**切换之后新上传的图只写 COS，Supabase 侧没有副本**。注意区分两种情况：

## 缓存策略（2026-10-19 已定）

| 图龄 | 浏览器缓存 | 依据 |
|---|---|---|
| ≤ 3 天 | `private, max-age=1800`（30 分钟） | 误传的图基本当天就发现，保留撤回能力 |
| > 3 天 | `private, max-age=2592000`（30 天） | 业务主要看当月数据且反复看；历史图路径不变、不覆盖，适合长缓存 |

**成本实测**（`manifest.jsonl`）：

| 口径 | 张数 | 体积 |
|---|---|---|
| 全部历史 | 3,122 | 629 MB（均 206 KB/张） |
| 最近 30 天 | ~1,800 | ~218 MB |

即「全部缓存也才 629 MB」，浏览器磁盘占用不构成问题。

**必须同步给 Codex 的两个约束**：

1. 缓存时长按 **path 内的日期（图龄）**判断，不是按 `storage.objects.created_at`，避免对象迁移时间污染判断。
2. **缓存不跨人共享**：A 看过的图不会让 B 变快。所以「性能强劲」要靠两件事叠加——分档缓存解决"重复看"，新加坡桶（p95 575ms）解决"第一次看"。不能把缓存当成首次加载的优化。

**已知代价（负责人已接受）**：>3 天的图若需紧急撤回，最长 30 天后才从全部客户端消失。

## 382 张历史缺失：不阻塞迁移，属可选产品优化

**判定标准（负责人定，正确）**：只有"迁移前正常、迁移后变坏"才算阻塞。前坏后坏 = 无差别 = 不阻塞。

按此标准验证，结论是 **零阻塞**：

| 群体 | 迁移前 | 迁移后 | 判定 |
|---|---|---|---|
| 3,122 张 | 正常 | 正常（全量 size 100% 一致 + 抽样 hash 一致） | ✅ 不阻塞 |
| 382 张 | 坏（`NoSuchKey`） | 坏（同样 `NoSuchKey`） | ✅ 不阻塞 |

**反直觉但重要的一点**：COS 侧"缺失"从来不是阻塞项。`readSubmissionScreenshot` 在 COS 404 时会自动回退读 Supabase，用户仍看到好图。真正会让人看到坏图的只有一种情况——**COS 返回 200 但字节是错的/截断的**。本次全量校验正是针对这一点，结果 0 条不符。

因此 382 张的处理从"待拍板"降级为**可选产品优化**，不设截止时间，也不进上线门禁。

（以下为原方案，留作以后需要时参考）

**实测结论（2026-10-19 14:50，用 service role 直连 Storage API）**：

- 对缺失对象签发链接：`POST /storage/v1/object/sign/...` → **200**（Supabase 不校验存在性）
- 访问该链接：**HTTP 400 · `{"statusCode":"404","code":"NoSuchKey"}`**
- 前端 `<img>` 无 `onError` 兜底（4 处 assetUrl 渲染点均无）→ 浏览器渲染**裂图图标**

| 项目 | 数值 |
|---|---|
| 缺失对象 | 382 个（全部有引用，孤儿 0） |
| 涉及作品/快照 | 191 个（每作品 2 张，**全部缺失**） |
| 涉及用户 | 18 人 |
| 时间 | 全部为 2026-05 |

即：**18 个用户打开这 191 个 5 月作品时，截图区是两张裂图，不是空白，也不是"没有截图"。**

切换前后表现一致（COS 侧同样 `NoSuchKey`，双读两边都 404），**切换不会让它变好，也不会变差**。

| 选项 | 用户感受 | 代价 |
|---|---|---|
| 保持现状（裂图图标） | 像系统坏了 | 0 |
| **显示统一占位图 + "截图已过期"** | 明确告知，不像故障 | 一次前端改动（4 处 img 加 onError） |
| 清理这 382 条的元数据 | 看不到坏图，但历史记录消失 | 改数据库，不可逆 |

建议选第 2 个，S5 观察期内一起做，不阻塞切换。
