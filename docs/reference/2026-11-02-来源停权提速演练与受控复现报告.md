# 来源停权提速演练与受控复现报告

2026-11-02 深夜，[CX]。回应 23:17 来源停权 65 秒超时的提速演练任务。**本轮没有连接生产 Supabase、没有改上海数据、没有 push、没有部署；全部实验在本机 Docker PostgreSQL 17.6（与来源同版镜像 `public.ecr.aws/supabase/postgres:17.6.1.165`）上完成。** 私有证据目录：`/Users/mac/.local/share/dydata/review/2026-11-02-停权提速演练-2358/`（700/600，不进 Git）；既有失败证据未覆盖。

## 1. 结论

**两个根因均确证，修复方案在本机受控复现中达标且大幅超出目标：**

1. **传输放大（实测确证）**：`runPsql` 经 stdin 喂 SQL，psql 逐条解析、逐条发送、逐条等结果——1,388 条语句＝1,388 次网络往返。生产 65.031 秒 ÷ 1,388 ≈ **46.8ms/语句**，与"36 秒时 ClientRead（服务端等下一条语句）"完全吻合。受控复现（50ms 模拟往返延迟）：65,018ms 触发同样的本地超时，完成 1,163/1,388 次往返后仍在列 REVOKE 段，超时后 ACL 完整回滚——与生产 23:17–23:18 的全部观测一致。
2. **扩展成员函数停权不可达（本地实测＋官方文档佐证；生产未直测）**：1382 项里有 188 个 btree_gist 扩展成员函数，owner 是 `supabase_admin`；来源 `postgres` 角色对它们的 REVOKE **只产生 "no privileges could be revoked" 警告、不生效**，最后被预计态守卫 `Freeze ACL baseline drift` 拒绝并回滚。生产从未跑到这一段（超时死在列 REVOKE），**即使给足时间，原口径全量包也无法完成停权**。本地镜像实测 `postgres` 不是 `supabase_admin` 成员；Supabase 官方文档/issue 同证（见 §4.2）。

**修复**：SQL 字节与 SHA 绑定不变，只改两件事——

- **传输**：整包作为一条 simple-query 协议消息发送（1 次往返替代 1,388 次），新增 `pg` 8.23.1 依赖与 `cutover-freeze-executor.mjs` 执行器；
- **范围**：停权快照新增"排除扩展成员"变体（`pg_depend deptype='e'`），来源侧必须用该变体生成包（1,194 对象＝100 表＋1004 列＋1 序列＋89 业务函数）。

**实测成绩（目标≤30 秒）**：45ms 模拟往返延迟下，1,194 对象停权包单消息执行 **116ms**、执行器全程（前置读回＋执行＋后置读回）**307ms**；60ms 延迟下全程 392ms。相对 30 秒目标余量约 75 倍，相对 65 秒本地执行器上限余量约 167 倍。回滚包同传输 83–164ms。六组 freeze/rollback 场景全部达到预计态，最终库状态与基线逐字节一致。

- 本地已知偏差（均不在快照范围）：5 条引用 private schema 的 RLS 策略未恢复、3 条 supabase_admin 默认权限 ALTER 被跳过、业务数据未载入（REVOKE 只动目录表，与数据无关）。
- 模拟延迟：自研 TCP 代理按"协议往返"注入固定延迟（服务端响应以 ReadyForQuery 分突发、每突发延迟 N ms；认证握手阶段原样转发）。校准：stdin 模式 3 语句＝3 次往返、间隔精确 100ms；`psql -c` 3 语句＝1 次往返。
- 延迟取值依据：45–50ms 是从生产失败数据反推的每语句成本（46.8ms 含少量服务端处理），**生产实际 RTT 本轮未重新实测**（不碰生产）；45ms 场景为最接近生产的推算值。

## 4. 根因二：188 个扩展函数停权不可达

### 4.1 实测（本地同版镜像）

- `pg_auth_members` 实测：本地 `postgres` ∈ anon/authenticated/service_role 等，**不含 supabase_admin**（镜像即平台角色结构）。
- 以 `postgres` 对扩展函数执行包内同款 REVOKE：`WARNING: no privileges could be revoked for "gbt_bit_compress"`，proacl 原封未动；对照组（postgres 自有的业务函数）REVOKE 正常生效。
- 用 `supabase_admin`（超级用户）执行同语句则正常回收——确认是所有权/成员关系问题，非语句问题。
- 生产侧未直测（本轮禁区不碰生产）；Supabase 官方文档与 issue 佐证托管项目 `postgres` 同样不是 `supabase_admin` 成员、无法连接为该角色（[Postgres roles and privileges](https://supabase.com/blog/postgres-roles-and-privileges)、[supabase/postgres#1007](https://github.com/supabase/postgres/issues/1007)、[supabase/cli#4916](https://github.com/supabase/cli/issues/4916) "must be member of role supabase_admin"）。

### 4.2 排除口径的安全论证（供阿禅/QW 批准）

排除的 188 个对象全部是 btree_gist 扩展成员函数：

- 绝大多数参数含 `internal` 类型（gbt_*/gbtreekey_*），**无法经 PostgREST/Supabase API 调用**（JSON 无法绑定 internal 参数）；
- 少数可调用（`cash_dist`、`date_dist`、`float4_dist` 等）为**纯计算函数**，不读写任何表，无业务数据路径；
- 停权目的是切断旧网站/旧 JWT 对业务数据的访问；扩展成员函数不构成该路径。排除后 4 角色对这些函数保留 EXECUTE，风险面为"可调用若干纯算术函数"。
- 目标侧（CloudBase 管理通道高权限）不受此限制，但建议同口径以保持单一快照定义；两侧包各自绑定各自快照 SHA，互不影响。

## 7. 边界与未覆盖

- 生产 RTT、生产带宽下的 630KB 上传耗时未实测（不碰生产）；45ms 为生产失败数据反推值。按 10Mbps 保守带宽估算上传约 0.5s（推测），仍远低于 30s。
- 生产 `postgres`↔`supabase_admin` 成员关系未直测；本地同版镜像实测＋官方文档双重佐证。若窗口内实测发现生产可回收扩展函数权限，excluded 口径仍安全（只是多排除了一些本可停权的对象）。
- 目标侧（CloudBase）停权走管理通道单请求，已有 822KB/566ms/执行 45ms 的探针证据，本轮未重复。
- 本演练为窗口外、无锁、本机复现；**不构成停点①任何替代**。三个必停点与九步预算不变。
- 65 秒本地执行器上限可保留不动（实测余量 >160 倍）；若下轮窗口想更保守，执行器支持 `--timeout-ms` 调整。
