# AI 配置重整 · 数据契约

> Codex 逻辑交付契约。供 CC 核对、Antigravity 接线。界面取舍按总方案第三节与第六节；不要参考本轮旧页面的布局、交互或临时接线。

## 读取与刷新

- `GET /api/admin/ai-config`：需 `manage_system` 权限；响应含 `providers`、`keys`、`models`、`featureBindings`、`featureControls`、`availability`。密钥只返回末四位掩码，不返回原钥匙。
- `availability` 是三个视角共同的唯一计算结果。页面不再依据开关、失败计数、旧上架字段重算可用性。
- `useAiConfig().runCommand(action, data, entity?, timeoutMs?)` 为新界面写入口。成功返回完整报告时，会更新全部订阅者；失败保留 HTTP 状态、影响名单与共享地址影响，不自动替用户确认。
- `useAvailabilityReport(bundle)` 只读取 `bundle.availability`；初始未加载时为 `null`。
- 普通写操作返回最新完整 bundle。`find_model_channels`、`probe_provider_models` 只返回发现结果；同步、检测、清理另有下述结果字段。

## 业务功能视角

| 位置 | 字段 | 含义 |
|---|---|---|
| 顶部正常 / 顶班 / 停摆数量 | `availability.businessSummary.normal/fallback/outage` | 只计已启用、未归档的业务 |
| 顶部需要处理的渠道数 | `availability.businessSummary.needsAttentionChannels` | 按渠道去重；某个模型需要人工处理，也计入，不能被同渠道健康模型掩盖 |
| 每行状态 | `availability.businessAssurances[]`，按 `key` 对应功能 | 包含业务行及 `key="default"` 的全局默认行，页面不再另算 |
| 业务原选择 | `selectedModelId` | null = 跟随全局默认；故障不修改业务选择 |
| 下一次优先用谁 | `preferredModelId` | 是调度预测，不是最近一次成功记录 |
| 全局默认 | `defaultModelId` / `availability.globalDefaultModelId` | 唯一的跨模型顶班来源 |
| 文案键 | `messageKey` | 见下表 |

| `routingStatus` | `messageKey` | 文案 |
|---|---|---|
| `normal` | `business.normal` | 当前优先使用：{preferredModelName} |
| `fallback` | `business.fallback` | {selectedModelName} 暂时不可用，当前优先使用默认 {preferredModelName} |
| `outage` | `business.outage` | 停摆：无可用模型 |
| `outage`（所选或默认仍有歇着的供应） | `business.outage_retrying` | 停摆：无可用模型，系统仍在自动重试 |

`businessAssurances` 始终包含且仅包含一条 `key="default"`、`label="全局默认"` 的状态，结构与业务行完全相同。默认能用时为 `normal/business.normal`；全部供应歇着时为 `outage/business.outage_retrying`；未设置、没有供应、只剩关闭或需要处理的供应时为 `outage/business.outage`。停摆时 `preferredModelId/resolvedModelId=null`，不会挑其他模型顶班。全局默认行不计入 `businessSummary`、`affectedBusinessCount/affectedBusinessFeatures` 或停用影响名单。桌面和手机都直接按 `key="default"` 取这条报告，不自行推算。

主动跟随默认且默认可用，算 normal。所选和默认相同只尝试一次。正式请求按“所选能用 → 默认能用 → 两者歇着的供应（冷却截止早的先试）”。歇着的供应不计入页面可用数量、仍属停摆，`preferredModelId` 仍为 null；需要处理和已关闭的不试。全部尝试失败明确报错，不使用其它模型或隐藏环境变量顶班。冷却到期后的供应仍优先半开恢复，单次总超时预算不变。

名称从 `availability.modelFamilies[].displayName` 按模型 ID 取。旧 `status=healthy/degraded/outage` 只是三种新状态的过渡映射，新界面读 `routingStatus`。

保存业务：`save_feature_control`，传 `feature_key`、`model_id`（null 跟随默认）及需要变更的提示词/参数；不传 `provider_key_model_id`。更换为无可用供应的模型会被拒绝；保留原来的故障模型、只改其它设置可以保存。默认通过 `set_global_default_model {model_id}` 保存，不能为空。

## 模型与渠道视角

| 位置 | 字段 | 含义 |
|---|---|---|
| 模型列表 | `availability.modelFamilies[]` | 已按真实模型身份分组，不合并库记录 |
| 默认在用筛选 | `isShelved` | 兼容名字；已有打开供应或被业务/默认选择的模型都保留 |
| 模型名 | `displayName` | 按规则生成；人工名保留 |
| 新选择能否选 | `isSelectable` | false 时置灰，旧选择保留 |
| 不可用原因 | `unavailableReasonKey` | `model.no_available_supply` 或 null |
| 供应总数 / 能用数 | `channels.length` / `schedulableChannelCount` | 包含关闭供应的完整清单；能用数与正式调度同源 |
| 单点提醒 | `singlePointRisk`、`schedulableChannelCount` | 恰好 1 条能用时用 `model.single_supply`；0 条用不可用原因 |
| 单条供应定位 | `channels[].keyModelId` | 开关写这一条供应，不能拿 keyId 关闭整条渠道 |
| 渠道定位 | `channels[].keyId` / `availability.keys[].keyId` | 对应 `bundle.keys[].id` |
| 模型内顺序 | `channels[].sortOrder` | 只在同一 modelId 内生效 |
| 状态 | `channels[].identity/messageKey`、`availability.keys[].identity/messageKey` | 同一份治理结果 |
| 冷却截止 | `sleepUntil` | 自动暂停截止时间；不提供手动休眠操作 |
| 原因与详情 | `bundle.keys/models[].failureDiagnostic` | 按 keyId/keyModelId 关联，见下文 |

`channels[]` 已排序。普通供应按 `sortOrder`、供应 ID 排序；冷却到期的恢复供应临时排在前面，下一次真实请求只放一个恢复试用，其余并发请求走正常供应。**交换顺位按 sortOrder 判断相邻可调度供应，不按临时恢复排序的数组下标判断。**

| 内部 `identity` | 文案键 | 给用户的状态 |
|---|---|---|
| `active` | `channel.usable` | 能用（绿灯） |
| `retest` | `channel.retest` | 待复测（黄灯），不计入“N 条能用” |
| `sleeping` | `channel.cooling` | 暂时歇着 |
| `invalid` | `channel.action_required` | 需要你处理，附失败原因 |
| `disabled` | `channel.disabled` | 已停用，视觉按方案用灰色 |

所有文案键在 `src/lib/ai-config/presentation.ts`。`failureDiagnostic` 为 `{category,owner,technical:{message,status,requestId}}`：category 有 provider/model_access/credentials/quota/unknown；owner 有 provider/configuration/unknown。原文已隐藏凭据；技术详情默认折叠，不能把原始报错再判定成另一套健康规则。

## 操作与影响确认

统一写入口：`POST /api/admin/ai-config`，请求 `{action, entity?, data}`。

| 操作 | action / entity | data |
|---|---|---|
| 单个模型供应开关 | `update` / `model` | `{id: keyModelId, is_enabled}` |
| 整条渠道开关 | `update` / `key` | `{id: keyId, is_enabled}` |
| 整组地址开关 | `update` / `provider` | `{id: providerId, is_enabled}` |
| 整个模型停用 / 恢复 | `set_model_enabled` | `{model_id, is_enabled}` |
| 同模型所有供应统一改名 | `update` / `model` | `{id: keyModelId, display_name}`；禁止传 model_id |
| 模型内互换顺序 | `swap_model_channel_order` | `{model_id, key_model_id, target_key_model_id}` |
| 删除整条渠道 | `delete` / `key` | `{id: keyId}` |
| 删除单条供应并留痕 | `remove_key_model` | `{key_model_id}`，也兼容 `{key_id,model_id}` |
| 渠道模型勾选 | `set_key_model_selection` | `{key_id, model_ids:[真实ID]}`；取消只关闭，不删除 |

四种停用、删除和取消勾选都由后端重算业务影响。会让业务无可用模型时，未确认返回 HTTP 409：

```json
{"error":"…无可用模型，请确认后重试","requiresConfirmation":true,"affectedBusinesses":[{"key":"content_tools","label":"内容工具"}]}
```

用户确认后原请求增加 `data.confirm_impact:true`。名单已考虑全局默认，新界面不要再做备用判断。预览可调用 `POST /api/admin/ai-config/check-dependencies`，传 `{scope:"provider"|"key"|"supply"|"model", id}`；响应含相同的确认字段。

关掉整条渠道不会清除它供应哪些模型；重开时恢复原勾选。停用整个模型会记录 `disabled_by_model`，恢复只打开这些记录。用户逐条手动关掉的供应不会被批量恢复；显式逐条设置开关会清掉该条批量停用记忆。

## 接入、同步与找渠道

1. 探测新地址：`probe_provider_models {base_url,api_key}`，返回 `{modelIds,modelGroups}`，不写库。兼容旧 provider_id 入参。
2. 接入：`create / key {base_url,api_key,label?,provider_name?,selected_model_ids:[真实ID]}`。新界面始终传 selected_model_ids（可以为空数组），服务端先取上游清单，再一次事务写入地址组、渠道和模型。地址相同自动归组；地址规范化只处理网址标准形式和尾斜线，路径、协议仍有区别。label 不填使用地址主机名；同组重名会明确报错。
3. 改地址：`update / key {id,base_url}` 或 `update / provider {id,base_url}`。影响多条渠道时先返回 409、requiresConfirmation 和 `sharedAddressImpact:{providerId,affectedKeyCount,affectedKeys:[{id,label}]}`。确认后原请求增加 **`confirm_shared_address:true`**。该标记与停用的 confirm_impact 分开。文案键 `operation.shared_address`。渠道不允许改换 provider_id。
4. 同步：`sync_key_models {key_id}`，返回最新 bundle 加 `syncResult:{keyId,allModels,modelGroups,newCount,removedCount,removedModelIds,removedEnabledCount,removedEnabledModelIds,lostBusinesses}`。服务端真实取回的非空上游清单是唯一撤下依据：同一数据库事务内撤下清单外的挂载记录（无论是否勾选），新发现记录默认关闭，清单内原开关、显示名、顺位和健康字段全部保留。撤下后若某业务（含全局默认）失去最后一条可调度渠道，`lostBusinesses` 点名。**同步只对齐清单和挂载，不解除失效标记、不清冷却、不清失败计数；恢复只由真实调用成功或复测成功负责。** 客户端提供的清单不撤下、不解除封禁。
5. 同步归组：`modelGroups:[{displayName,recommendedModelId,modelIds}]`。只合并大小写、分隔符差异；推荐写法取上游同组首项。日期、Thinking、Agentic 保留独立组，界面放“更多版本”。勾选保存真实 ID，不把已有记录/业务选择改成推荐 ID。
6. 找渠道：`find_model_channels {model_id}`，返回 `{modelId,candidates}`。每项含 keyId/keyLabel/providerId/providerName/providerEnabled/keyEnabled/existingSupplyId/requiresProbe:true，来源为各渠道 available_models 减去已经打开的供应。**候选只是缓存发现，不是已测通。** 已关闭的渠道/地址组会带 false，须先处理开关。
7. 开启候选：`enable_model_channel {key_id,model_id}`。后端现场测试；成功后一次事务开启供应并清除渠道与该模型故障，返回最新 bundle 加 `enableResult:{keyId,modelId,supplyId,testResult}`。失败返回 HTTP 422，带 error/testResult，供应保持关闭，健康不变。
8. 清理：已废止。同步即按上游真实清单撤下旧记录，不再提供 `cleanup_stale_models` 手动入口；429/参数错误不会触发撤下，只有非空上游清单才会。

人工显示名不会被同步覆盖。一次性名称迁移只更新“名称等于 ID”或“等于旧自动名”的已知存量；不改变 model_id 或业务绑定。

## 检测与恢复

- `check_all_in_use {}`：启用业务明确选择的模型，加全局默认；测试它们全部已打开供应，包括暂歇/需要处理的供应，排除手动关闭的地址组/渠道/供应。批量检测多条时，每条失败在本条探测结束前就写库；同一批 Key 级失败只记一次；整批结束只汇总，不再二次写。
- 返回最新 bundle，加 `checkResult:{total,successCount,failureCount,stateWriteError,results:[{keyId,modelId,ok,latencyMs,message,failureDiagnostic,stateWriteError}]}`。total 是供应组合数，不是渠道数；失败 latencyMs 为 null，成功 message 可为 null。0/0 表示没有可检测对象，不能说全通过。前端批量等待上限 120 秒；中断后继续有界读取已落库状态，不自动重跑检测。
- `test_key {key_id,model_id?,test_mode:"text"|"vision"}`：旧入口保留；新界面不再用它的盲抽第 1 个挂载模型。`test_key_model {key_id,model_id}`：单供应测试。返回最新 bundle + testResult。
- `test_key {feature_key:"ocr_screenshot"}`：沿正式截图识别的模型接替顺序试跑，不接受旧钉渠道参数；试跑失败不写健康（本轮范围外）。
- `test_key_all_models {key_id}`：只测该渠道当前勾选在供的模型，不测未勾选/已停用；返回最新 bundle + total/successCount/failureCount/results/failedModelIds/stateWriteError 等。
- 手动测试失败当场写状态并进入冷却（见 §117）；成功只清除渠道和实际测通模型的故障，兄弟模型保留。旧手动休眠遗留也清掉。批量检测同一 Key 的 Key 级失败只记一次；模型级失败逐条记。单次手动检测沿用 15 秒等待上限；正式自动恢复沿用正常业务超时，不缩短。
- `test_all_keys`、`test_all_keys_all_models` 是旧界面兼容别名，都走 check_all_in_use 同一范围；新界面不用它们或它们的旧结果字段。`sleep_key/resume_key` 已删除，调用返回 400。
- 自动真实请求失败：第 1–2 次待复测（仍排在最前先试）；第 3 次起按 5/15/30/60/120/240/360 分钟冷却、封顶 360。超过一天不会自动判永久失效；**只有 Key 级明确鉴权拒绝（401、403 明确凭据/未授权）才永久失效，模型级 404/503/超时只进入可恢复冷却**。永久失效后由成功调用或复测恢复；模型撤下只由可信清单同步负责。402 低频自动重试。
- 手动测试失败：第一次 5 分钟、第二次 1 小时、第三次起每次 24 小时；模型级失败只休息、不撤记录、不关开关；只有 Key 级明确鉴权失败才永久失效。成功复测清零。
- 同渠道 10 分钟内至少 3 个不同模型同类超时/服务故障，且整个窗口无成功，才暂停整渠道 5 分钟。数据库租约保证跨实例只放一个恢复请求；最后补试歇着的供应同样需要租约，成功清零，失败延长冷却。超过一天不会自动判永久失效。

## 旧字段与分工边界

- `global_is_enabled/globalIsEnabled`、provider/key 的 priority、provider_key_model_id 都是旧界面过渡字段：分别为供应开关派生值、固定 0、固定 null。它们不读写原数据库列，新界面全部不用。
- 旧组件的按钮整合、提示条删除、弹窗键盘行为、providerId 入参删除和视觉拆分仍由 Antigravity 完成。Codex 只移除了不可达的顺位逻辑、前端重算和重复文案来源；必要组件接线已标“一次性、待删、勿参考”。
- 新增事务函数只授予服务端角色；页面仍先经过现有 manage_system 权限校验，不能在浏览器直接调用数据库事务函数。

## 发布边界

- 本轮只本地提交，尚未 push；Antigravity 接线、CC 整体验收后，阿禅授权一次上线。

- 删列 SQL 位于 `supabase/deferred-migrations/`，不在自动迁移目录。仅本地事务内演练并回滚；上线观察至少 3 天、CC 复核、阿禅再次确认后才能执行。
