# COS 截图切换同类风险审计清单

- 日期：2026-10-20
- 范围：`submission-screenshots` 的 COS 主写、双读、双删；`src/`、`scripts/`、`supabase/` 静态扫描
- 方法：调用点与调用链静态核对；未连生产数据库、未操作线上页面、未重放用户数据
- 结论：发现 2 项 P1、12 项 P2；未发现可证实的 P0。涉及外部生产配置、角色和运行时的结论均标为待核。

## 结论先看

1. **P1：业务提交回滚不会清理已上传的 COS 对象。** 上传先于视频/快照/日报等多步数据库写入；后续任一步失败会回滚数据库，但截图对象没有加入补偿动作。新图不在 Supabase，现有对账还把切换后 COS 独有对象当成预期，无法识别这类孤儿。
2. **P1：读失败只有结构化日志，没有仓库内自动阈值告警。** 观察单要求 `read_failed`、`write_failed`、回退率等阈值，但扫描到的实现只是输出 `[screenshot-storage]` 日志；自动采集、阈值计算和通知链路待核。
3. **P2：管理端作品清理仍保留 Supabase 直删后备分支；测试夹具脚本也只列举/删除/验证 Supabase。** 前者生产默认注入统一删除器，后者属于测试工具，暂未证明会伤及真实 COS 图片，但都绕过了统一语义。
4. **P2：新图写成功、后续 OCR/提交或数据库写入失败时，重试会产生新对象；没有稳定上传幂等键或孤儿清理账本。** 表单草稿保存文本和已返回的 URL，不保存本地 File；页面刷新后未成功上传的原文件需要重新选择。
5. **P2：COS 最多等待 3 秒才回退。** 2.9 秒慢请求会拖住页面后端读取近 3 秒；现有收尾单已有“生产未设 `COS_READ_TIMEOUT_MS`、默认 3000ms”的记录。是否调整属于性能口径决策，应结合服务端分位数，不建议仅凭单例改值。

## D. 静态门禁建议

目标：阻止业务层直接调用 Supabase Storage API 操作投稿截图；只允许 `src/lib/screenshot-storage.ts` 封装 `submission-screenshots`。维护脚本若确需 Storage REST，必须逐文件白名单并限制为只读或受控 fixture。

建议实现：新增 `scripts/check-screenshot-storage-boundary.mjs`，扫描 `src/**/*.{ts,tsx,js,jsx}` 的 AST（优先用 TypeScript compiler API），检测 `.storage.from(bucket)` 后续链上的 `upload/download/list/remove/createSignedUrl(s)/getPublicUrl/copy/move`，以及 `storage/v1/object/(public|authenticated|sign|list)` URL 字符串。若 bucket 是动态值但变量来源包含已知桶，也报错。以下允许：

- `src/lib/screenshot-storage.ts`：唯一生产适配器白名单。
- `src/app/api/submission-screenshots/file/route.ts`：删除直接 Supabase client 注入；当前两处 `createSignedUrl` 可改成只传适配器。
- migration/只读审计工具：不属于业务运行代码，单独目录规则；写入/删除工具必须额外静态标记人工审批说明。
