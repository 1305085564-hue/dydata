# DYData 全站页面产品问题审计（静态预评）

日期：2026-08-28

## 先说结论

这次审计回答的不是“页面做得好不好看”，而是：这个页面有没有一个真实、唯一、不可轻易替代的问题；用户为什么必须来；页面是否用最低交互成本把问题闭环解决。

当前最重要的三个结论：

1. **`/admin/content`（视频复盘）的反馈闭环成本超过当前承受能力，已于 8-28 删除并上线。** 页面收窄为管理者内部分析工具，只保留异常定位、指标证据和原因判断；投递、员工已读/回复、管理者验证和经验资产沉淀已不再建设。
2. **不再追求一条覆盖全站的员工连续链路。** 保留三个各自有明确价值的断点：选题帮助员工决定做什么，上传帮助公司记录数据和考勤，分析帮助管理者定位作品问题。每个断点只承诺自己能完成的结果。
3. **`/admin/collaboration`（协作管理）目前保留不动。** 长期可考虑与 `/admin/fulfillment`（发布管理）合并为更统一的数据管理，但当前没有合并方案，因此不删除页面、不迁能力、不改前后端逻辑。

管理侧的第二类高风险是：`/admin/fulfillment`（发布管理）与 `/admin/content`（视频复盘）直接影响发布漏发、日报异常和反馈损失；`/admin/modules`（成员与权限）直接影响成员、权限和组织边界。这些页面必要性高，但交互复杂、状态多，应该优先围绕风险处置收敛主目标。

## 建议阅读顺序

1. **先看「一眼看总表」**：先找低分页面和总分不低但闭环低的页面。
2. **再看对应页面的「断点 / 缺什么」**：只看你准备处理的页面，不需要从头读完。
3. **最后看「优先级与建议顺序」**：按 P0 → P1 执行，不按页面数量平均分配精力。

如果只看一页，先看总表；如果只处理一个问题，先按新边界收窄 `/admin/content`（视频复盘），避免继续维护无法完成的反馈承诺。

## 审计范围与证据边界

本次以当前仓库源码和项目文档做了**静态产品预评**，覆盖模块地图中的现役页面，以及对用户有直接意义的公开首页和认证页：

- 公开/认证：`/`（首页）、`/login`（登录）、`/register`（注册）、`/forgot-password`（找回密码）、`/reset-password`（重置密码）
- 员工：`/dashboard`（今日工作台）、`/growth`（成长分析）、`/topics`（选题库）、`/topics/[id]`（选题详情）、`/content-tools/rewrite`（文案改写）
- 管理业务：`/admin/content`（视频复盘）、`/admin/videos`（素材库）、`/admin/fulfillment`（发布管理）、`/admin/collaboration`（协作管理）
- 管理配置：`/admin/modules`（成员与权限）、`/admin/ai-config`（AI 配置）、`/admin/settings`（系统设置）
- 跨页能力：全局导航、`UnifiedCommandHub`（统一待办/审批抽屉）

排除项：`/admin`（管理首页）只是重定向到 `/admin/content`（视频复盘）；`video-review`（旧视频审核页）已归档只读；提醒、通知、cron（定时任务）是基础能力而不是独立页面；模块地图标记为下线/历史的旧路由不作为当前产品页面评分。

证据分层：

- **[已知]** 当前代码、现役文档或明确配置可以直接证明。
- **[推测]** 根据页面结构和调用链得到的产品判断，需要业务访谈或真实使用数据确认。
- **[待验证]** 必须用真实角色、真实数据、真实浏览器和外部服务验收，静态代码不能代替。

本次没有写业务数据、没有执行审批/删除/发布等改变状态的操作，也没有把历史视觉报告当作当前产品价值证明。真正的 29 号全链路验收仍需登录后的角色和浏览器现场。

## 评分口径

每项 1–10 分，总分 80 分。**“交互成本”分数越高代表用户负担越低**，不是操作越多分越高。

| 维度 | 判断什么 |
| --- | --- |
| 问题清晰度 | 用户来这里要解决的唯一问题是否一眼可说清 |
| 必要性/不可替代性 | 不解决是否会造成真实损失；是否不是普通报表或手工提效 |
| 主目标聚焦 | 主任务是否压过顺便功能 |
| 解决闭环 | 从发现问题到完成结果是否真实闭合 |
| 交互成本 | 找到入口、理解状态、完成动作的负担是否低 |
| 反馈/信任 | 成功、失败、处理中、权限和数据来源是否可信 |
| 信息可理解性 | 术语、指标、状态和下一步是否容易理解 |
| 角色/状态覆盖 | 角色、空态、异常、历史、权限和边界状态是否覆盖 |

评分是静态预评，不代表真实角色验收。总分只能帮助排序，不能抵消“唯一问题不成立”或“主闭环断裂”。

## 页面逐项审计

### 一、公开与认证

#### `/` 首页

1. **谁/场景**：[已知] 未登录的内容团队负责人或成员，首次了解产品时进入。 [推测] 他们真正关心的是“能不能减少漏报、漏发、复盘失效和协作失控”，而不是功能数量。
2. **唯一问题**：[推测] 让陌生团队理解 DYData 解决的一个不可替代损失，并愿意进入系统。
3. **不解决的损失**：[推测] 认知不成立会导致注册和登录转化低；但页面没有证明具体业务损失。
4. **替代不足**：[已知] 页面并列展示日报、经营分析、AI 助手等能力；[推测] 没有说明表格、群聊、手工记录或通用 AI 为什么不能替代。
5. **解决方式**：[已知] 用宣传语、模拟工作台和功能卡片建立产品印象。
6. **成功结果**：[推测] 用户能用一句话说出产品解决的核心损失，并点击进入正确的注册/登录路径。
7. **状态**：[待验证] 首页真实性声明、CTA 转化和访客理解需要真实访谈/埋点验证。

**断点**：价值承诺太宽；“数据团队高效协作”是结果描述，不是不可替代问题；页面展示了很多模块，却没有把一个主损失讲透。

**缺什么**：一个明确的核心用户、主场景、损失证据、替代方案对比和可验证的成功承诺。`2,400+` 团队等社会证明也应有来源或降级处理。

#### `/login` 登录

1. **谁/场景**：[已知] 已注册成员返回系统，输入邮箱/密码，可选择保持登录。
2. **唯一问题**：[已知] 安全、低阻力地恢复工作入口。
3. **损失**：[已知/推测] 登录失败会阻断日报、审批和管理动作；账户归档需要明确告知而不是误导重试。
4. **替代不足**：[推测] 其他入口不能代替系统身份和团队权限校验。
5. **解决方式**：[已知] 登录、记住登录、归档账号提示、注册和找回密码入口。
6. **成功结果**：[已知] 进入正确角色可见的工作台。
7. **状态**：[待验证] 错误密码、归档账号、网络失败和重定向在真实浏览器中的反馈。

**断点**：核心闭环清晰；风险主要在错误状态、角色重定向和真实会话，而非功能不足。

**缺什么**：把“为什么不能登录、现在能做什么、下一步去哪”在所有失败态中说清；补真实角色验收。

#### `/register` 注册

1. **谁/场景**：[已知] 新成员选择姓名、邮箱、密码和团队，提交加入申请。
2. **唯一问题**：[已知] 让新成员进入正确团队，避免错入组织。
3. **损失**：[推测] 错团队或未授权账号会造成数据越权、成员无法工作或管理员无法追责。
4. **替代不足**：[已知] 团队审批是系统组织边界的一部分，单纯注册账号不能替代。
5. **解决方式**：[已知] 团队下拉、加入申请、管理员审批。
6. **成功结果**：[待验证] 用户知道申请是否提交、谁审批、审批后如何继续工作。
7. **状态**：[待验证] 空团队、重复申请、拒绝、审批后登录和团队列表加载失败。

**断点**：提交申请之后的业务闭环不在注册页可见；团队列表依赖接口，初始空状态的语义需要确认。

**缺什么**：申请编号/状态、审批人或等待说明、拒绝后的处理路径、重复申请处理和团队选择风险提示。

#### `/forgot-password` 找回密码 与 `/reset-password` 重置密码

两页共同的唯一问题都是**恢复安全登录**，不是提高效率，因此必要性高、主目标聚焦高。

- `/forgot-password`：[已知] 通过邮箱发起找回；[待验证] 邮件是否可达、未知邮箱是否避免泄露账号存在性、重复请求是否有冷却反馈。
- `/reset-password`：[已知] 校验链接并设置新密码，提供过期链接回到找回入口；[待验证] 过期、已使用、密码不一致、成功后重新登录和会话失效。

**共同断点**：系统功能链条看起来完整，但外部邮件服务和真实浏览器状态没有在静态代码中证明。

**共同缺口**：明确告诉用户“邮件已发送/链接已失效/密码已更新”以及下一步；避免把异常归因于用户操作。

### 二、员工主链路

#### `/dashboard` 今日工作台

1. **谁/场景**：[已知] 员工按视频归属业务日期提交抖音视频日报，通常在次日上传前一日数据，同时处理历史记录和请假/豁免；管理者按周/月查看成员相关状态和汇总。
2. **唯一问题**：[已知] 在正确业务日期提交一份完整、可信、可追溯的日报。
3. **损失**：[已知/推测] 漏报、错日期、字段不完整会导致发布管理、绩效口径、异常复盘和应得/实发判断失真。
4. **替代不足**：[推测] 普通表格或群聊可以收集数据，但难以同时保证日期规则、成员归属、字段校验和历史编辑。
5. **解决方式**：[已知] `DashboardDataContainer` 和 `VideoSubmitPanelV2` 提供日报表单、草稿、OCR、历史、编辑、请假/豁免和提交摘要。
6. **成功结果**：[推测] 用户用最少输入提交正确日报，并能确信系统已接收。
7. **状态**：[已验证（2026-08-29，本地）] 业务日期与次日上传边界、重复提交、编辑历史、OCR 成功/失败/恢复、无数据状态已完成真实浏览器验收；移动端长表单和生产链路仍待验证。

**断点**：主目标被提交、历史、请假和 OCR 入口分散；旧 T+0/T+1 术语容易让用户误解为当天必须提交，需要直接显示业务日期与上传时点的关系。

**缺什么**：

- 首屏明确显示“当前要提交哪一个业务日、缺什么、提交后会发生什么”；
- 将辅助动作降级为主任务完成后的补充入口；
- 每个字段说明数据用途和错误修正方式；
- 提交后明确显示保存结果，而不是只显示短暂提示；
- 真实员工角色、移动端和不同日期状态验收。

**优先级**：P0 职责收敛与视觉修缮已完成；剩余项为真实管理员登录态验收。

#### 全局导航

**唯一问题**：让当前角色快速进入当前任务，而不是让用户记住产品模块结构。

**已知**：导航由 `getNavGroups`（导航分组函数）统一生成，覆盖工作台、选题库、内容中心、数据中心和管理中心；部分管理子项可见性与页面守卫（权限拦截）仍需现场核对。

**断点**：导航按模块命名，任务意图不够直接；“内容中心/数据中心/管理中心”对新用户是分类，不是行动；若入口显示但页面守卫重定向，会造成死路感。

**缺什么**：角色化任务入口、待处理数量/风险、最近工作上下文、页面之间的下一步接力，以及显示条件和页面权限的一致性。

## 全站共性断点

### 1. 页面有功能，但不一定有唯一主问题

最明显的是 `/admin/collaboration`、`/growth`、`/content-tools/rewrite`、`/admin/ai-config`。这些页面都能提供信息或提效，但必须继续追问：

> 如果用户不用这个页面，哪个明确损失会发生？通用表格、群聊、BI、ChatGPT 或人工流程为什么不能替代？

答不出来，就不能继续增加功能，只能重定义、合并或降级。

### 2. “完成页面动作”不等于“完成业务结果”

- 日报提交不等于后续异常被处理。
- 管理者写反馈不等于员工收到并响应。
- 选题认领不等于脚本完成、作品发布和日报关联。
- AI 生成文案不等于进入生产并验证效果。
- 发布提醒发送不等于成员真的完成发布。
- 配置保存不等于目标功能健康生效。

每个页面都需要把“动作之后谁接手、何时完成、如何证明”显示出来。

### 3. 页面之间存在职责重叠

| 重叠区域 | 当前问题 | 应先确认的边界 |
| --- | --- | --- |
| `/admin/content`（视频复盘）↔ `/admin/videos`（素材库） | 两页都围绕视频，分析与资产修改容易混淆 | 视频复盘只负责异常诊断；素材库继续负责现有资产生命周期，暂不迁入新能力 |
| `/admin/fulfillment`（发布管理）↔ `/admin/collaboration`（协作管理） | 产量、进度和成员统计存在重叠 | 当前两页均保留；等完整合并方案明确后再调整，不能先删后补 |
| `/admin/modules`（成员与权限）↔ `/admin/settings`（系统设置） | 成员权限/团队配置语义交叉 | 成员与权限负责组织管理；系统设置只保留业务阈值/配额 |
| `/admin/ai-config`（AI 配置）↔ `/content-tools/rewrite`（文案改写） | 路由配置与最终 AI 体验脱节 | 配置页说明影响范围；改写页说明当前使用的团队规则/路由 |
| `UnifiedCommandHub`（统一待办/审批）↔ 通知/各业务页 | 待办、已读、审批和业务完成状态混杂 | 统一入口只聚合需要行动的任务，各业务页负责结果闭环 |
| `/topics`（选题库）↔ `/topics/[id]`（选题详情）↔ `/content-tools/rewrite`（文案改写）↔ `/dashboard`（今日工作台） | 选题、写作、日报没有明确接力 | 用一个可追踪的作品/选题编号串起生产链路 |

## 优先级与建议顺序

### P0：先修不可替代的业务闭环

1. **收窄 `/admin/content` 为内部分析工具**（✅ 已完成 8-28，commit `096fe901`）：删除投递、员工响应、管理验证和经验沉淀，重建不依赖反馈状态的分析队列。
2. **收敛 `/dashboard` 的唯一主任务**（✅ 已完成 8-28 重构）：正确日期、完整字段、禅意立卷与挑选明日备题形成闭环。
3. **把 `/admin/fulfillment` 做成风险处置队列**（✅ 已完成 8-28 收敛与视觉校准）：作品条数聚合、扣假应发对账、待审请假月历附着与就地审批、Token 标准化。

### P1：补组织安全和跨页接力

1. **`/admin/modules` 组织边界收敛**（✅ 已完成 8-28 收敛与视觉校准）：组织管理与考勤考评解耦、去除发布考核进度与豁免设置、入团审批按钮暖墨归一。
2. **`UnifiedCommandHub` 统一待办/审批抽屉**（✅ 已完成 8-28 收敛与视觉校准）：审批即消解并广播联动发布日历、Tab 激活态微气垫统一。
3. 保证三个有价值断点各自清晰：选题解决“做什么”，上传解决“数据与考勤记录”，管理分析解决“作品问题定位”；不强求跨页形成完整改进闭环。
4. 全局导航与统一待办/审批抽屉：按角色和风险组织入口，分离已读、待办和业务完成。

### 先定义、后决定是否优化

- `/admin/collaboration`：当前保留不动；未来可考虑与发布管理合并，但没有方案前不删除、不迁移。
- `/growth`：先定义诊断如何改变下一次行为；当前不做大规模实现优化。
- `/content-tools/rewrite`：先证明团队语境和反馈闭环优于通用 AI；当前不做功能堆叠。
- `/admin/ai-config`：作为内部运维能力做安全、测试、影响预览和回滚，不当作核心用户价值页面。
- `/` 首页：先确定产品唯一主承诺，再重写宣传和转化路径。
