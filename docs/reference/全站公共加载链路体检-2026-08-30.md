# 全站公共加载链路体检（2026-08-30）

> 性质：已完成的诊断记录，不是施工计划。
> 使用边界：本文件只保留当时的实测证据和结论，不构成当前施工授权；后续动作以现行总纲和用户明确确认的任务为准。
> 基线：`main` / `e1d53a83`，并包含当前工作树中两个仅涉及 Topics 外观的未提交改动。
> 动态环境：当前工作树的本地生产构建（`next build` + `next start`），复用浏览器已有 company owner 登录态；不是 Vercel 生产环境结论。

## 一、结论

恢复文件提出的“全站缺少统一加载架构”方向只对了一半。当前代码已经有集中 loader、请求内身份缓存、统一权限范围和 Topics 服务端首屏注入，不能按“全站从零重构”处理。

真实问题分成两层：

1. **公共上下文仍有重复成本**：导航、页面 loader、JoinBanner 和管理页容器会分别读取 profile、accounts 或数据范围；管理员页面还会统一挂载审批数量请求。
2. **各页面存在不同的局部结构问题**：Dashboard 提前加载岗位成员；Topics 详情重复查作品；协作页重复构建权限且同月日报查三次；视频复盘首屏后立即全量加载，并曾产生超长 URL 的 431 错误（已于同日修复，见下方修复记录）。

因此不建议立即全站大重构。下一阶段应恢复总纲和自动门禁，但施工先按共性公共上下文、明确页面缺陷两条线分批，不把所有页面强行改成同一种 HTTP 形态。

## 二、代表页面实测

| 页面 | 文档 TTFB | DOMContentLoaded | 首次有意义绘制 | 首屏挂载后的业务请求 | 判断 |
| --- | ---: | ---: | ---: | --- | --- |
| `/topics` | 1083ms | 1105ms | 1123ms | `/api/exemptions/pending` 1 个；`/api/topics/*` 0 个 | 首屏已收口，满足其他登录页 2.5s 目标 |
| `/dashboard` | 230ms | 573ms | 884ms | usage-events、operator-members、exemptions/pending | 速度合格，但岗位成员加载过早 |
| `/admin/content` | 300ms | 663ms | 未稳定取得 | thresholds、full list、topic-library-status、usage-events、exemptions/pending | 首屏快，但 hydration 后自动追加重链路 |
| `/admin/collaboration` | 429ms | 766ms | 未稳定取得 | usage-events、exemptions/pending | 当前数据量下速度合格，静态查询结构有增长风险 |

说明：

- 生产模式下 `/api/exemptions/pending` 每页只出现 1 次；开发模式 `/topics` 曾出现 2 次，属于开发环境重复挂载证据，不能写成生产重复请求。
- `favicon.ico` 在浏览器扩展环境中出现多次，不计入业务请求。
- `/admin/content` 的 full list 命中现有 60 秒内存缓存，本轮为 9ms；不能据此推断冷缓存耗时。

## 三、全站共性问题

### 1. profile 与账号重复读取

- `src/components/nav-bar.tsx` 同时直查 profile、accounts，并调用 `getUserPermissions()`。
- `getUserPermissions()` 又从 profiles 读取完整权限资料。
- Dashboard loader、JoinBanner 和各管理页面还会按各自需要再次读取 profile 或 accounts。
- `getCurrentUserContext()` 的 React `cache()` 只复用 Auth 用户和 Supabase 客户端，不会合并上述数据库查询。

结论：项目已有“当前用户身份缓存”，但还没有可复用的“页面公共业务上下文”。应先设计最小公共上下文边界，避免复制一份巨型全站对象。

### 2. 管理员导航统一追加审批请求

所有管理员页面 hydration 后都会请求 `/api/exemptions/pending`。本轮四页实测约 477–828ms。它不阻塞服务端文档返回，但属于全站管理员页面固定后台成本。

正确方向不是简单删掉，而是明确它是否必须常驻显示；若必须，复用服务端已经取得的计数或建立单一请求源，避免后续抽屉再次读取同一事实。

### 3. 文档和真实代码发生漂移

原模块地图仍写 Topics 首屏分别请求 active/options/pool/comparison，但当前已经是服务端 bootstrap，comparison 也已删除。本轮已同步修正模块地图。

## 四、Topics 独有问题

### 已正确

- 页面服务端完成登录、团队和权限确认后注入 bootstrap。
- active、options、pool、myWritingIds 四路并行。
- 首次进入实测 0 个 `/api/topics/*` 客户端请求。
- 搜索/筛选走 pool，刷新只并行 active + pool；重型弹窗动态加载。

### 待修

1. `loadTopicPool` 先拉全量在库子题，再串行计算 7 天热度和作品汇总，最后内存分页；数据量增长后会退化。
2. 详情抽屉并行请求 detail、works、claims，但 detail 服务内部已经调用 `loadSubTopicWorks`，一次打开实际重复查询作品。
3. 本地生产模式实测详情三个接口分别约 904ms、951ms、828ms，均超过其他登录页单接口 800ms 红线。
4. 搜索或筛选发生在第 2 页以后时，页码归一化与查询 effect 存在发出旧页、再发第 1 页的风险；需用浏览器专项复现后再改。
5. `/topics/[id]` 仍是旧式客户端聚合入口，会在挂载时读取 workspace、operator-members、my_claims、detail、claims，尚未与新版抽屉收口。

## 五、Dashboard 独有问题

### 已正确

- 页面用 Suspense 包住数据容器。
- loader 先并行账号与 profile，再按依赖关系并行日报和豁免数据。
- 历史列表和编辑详情按用户动作读取，没有全部塞进首屏。

### 待修

1. 视频提交表单一挂载就读取 `/api/dashboard/operator-members`，实测约 431ms；成员列表实际只在选择岗位负责人时使用，应改为首次打开选择器时加载并缓存。
2. Dashboard loader 与导航都会读取当前用户 accounts/profile。
3. 首屏已经传入本月日报，打开历史活动时 `/api/dashboard/activity` 又返回重叠的 monthReports。
4. 已入团队但无账号时，页面读取会创建默认账号并重新查询。这是首屏读链路中的写操作和最长串行分支，应独立评估是否保留。

## 六、管理端独有问题

### `/admin/content`

正确模式：首屏 RPC、失败回退、独立查询并行、服务端初始数据注入。

问题：

1. partial 首屏 hydration 后立即请求 full list，属于“延后到挂载”而不是“按用户需要加载”。
2. full list 返回后再次调用 topic-library-status；体检时把最多 400 个 UUID 放进 GET 查询参数，真实返回 HTTP 431，前端还会静默吞掉，导致入库状态降级为未知。该正确性问题已于同日修复，400 条状态计算本身仍超过 800ms 性能预算。
3. 首屏 RPC 后仍全量读取成功的 `ai_insight_result`，再在内存按候选 ID 过滤。
4. `loadPlayChangeSignals` 按账号扇出查询上一条视频，账号数增长时形成并发 N+1。

### `/admin/collaboration`

正确模式：summary/operators/talents 用 `Promise.allSettled`，单块失败不会拖垮全页；个人图表动态加载。

问题：

1. page 已经构建 `getCurrentPermissionContext`，数据容器又执行 `requireAdminActor` + `buildPermissionContextForActor`，重复身份、profile、group mode 与 scope 工作。
2. summary、operators、talents 各自查询当前月 `daily_reports`，同月数据至少扫描三次；operators 另查上月。
3. writer/editor 切换同时 `router.push` 和请求 staff API，服务端页面仍无条件重算三块首屏数据。
4. 人员 hover 预取只缓存完成结果，不缓存进行中的 Promise；hover 后立即点击可能对同一 person URL 发两次请求。

## 七、下一阶段建议

以下顺序保留当时的决策记录；已标注“已于同日完成”的事项不再视为待办，其余只代表候选方向，是否施工仍需当前任务确认。

按收益与风险排序：

1. **明确 `/admin/content` 的 full list 是否必须自动加载**：431 正确性问题已经止住，但 hydration 后自动加载 400 条状态的约 1.24 秒后台成本仍在。
2. **恢复《架构与性能总纲》**：已于同日完成，保留现有 loader、React cache、scope 和 Topics bootstrap，并明确公共业务上下文边界、数据加载分层、浏览器证据标准和禁止模式。
3. **建立自动浏览器门禁**：已于同日完成首版，覆盖 `/topics`、`/dashboard`、`/admin/content`、`/admin/collaboration`；确定性规则硬阻断，时间预算先报告。
4. **做两个低风险样板**：Dashboard 岗位成员按需加载；Topics 详情作品单一数据源。
5. **再处理结构性重构**：协作页共享月度数据集与公共权限上下文；Topics pool 改数据库分页/聚合。没有数据量和冷缓存证据前，不先上缓存掩盖结构问题。

## 九、同日修复记录：`/admin/content` 431

- 正式页面把 topic-library-status 调用从超长 GET 查询串改为固定 URL 的 POST JSON 正文；GET 保留兼容，不破坏潜在旧调用方。
- 服务端继续执行原有 `review_content` 权限校验和每 150 条分批查库；新增正文类型与 400 条上限校验，不改数据库、RLS 或权限模型。
- 接口失败不再静默吞掉，页面明确提示“选题库状态加载失败”，状态仍降级为未知，不伪造入库结果。
- 回归测试先在缺少 POST 构造器/解析器时失败，修复后全量 `npm test` 1250/1250 通过，生产构建通过。
- 本地生产模式真实登录复测：首屏 20 条与 full list 400 条均请求固定 60 字符 URL，方法 POST，HTTP 200；400 条正文约 15.6KB，耗时约 1.24 秒，无 431、无控制台报错。
