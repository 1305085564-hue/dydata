### 1.0 按通道验收请求预算

| 通道 | 平台边界 | 本项目仍执行的预算 | 体积口径 |
|---|---|---|---|
| 直连PostgreSQL（来源及本地副本） | 不受CloudBase管理API的480KiB限额约束 | 自设每条SQL消息<491520字节且余量>1500字节 | 完整BEGIN/设置/DO/COMMIT的UTF-8 SQL字节；每批只发送一条simple-query消息 |
| CloudBase管理API（目标ExecutePGSql） | 本执行令按480KiB硬限，不提高上限 | 每次请求<491520字节且余量>1500字节 | 保守核算SDK实际参数JSON：`{EnvId,Sql}`；Sql包含完整事务、设置、窗口、全量守卫、业务语句及账本，不只算裸SQL |

两通道分别记录数量、最大字节、最小余量、逐批SHA。CloudBase的JSON计算包含SDK补入的EnvId；无Role覆盖，若未来改变SDK/Role/额外参数须重验预算。这里不将SQL请求上限误套到pg_dump/pg_restore归档、COPY数据流、HTTP响应或备份文件；本地副本建立与归档恢复按原生工具协议独立验收，其读回/控制SQL另列。备份仍须校验完整性和空间。腾讯云[管理API参数](https://cloud.tencent.com/document/product/876/130469)确认EnvId/Sql；480KiB沿用本单既定约束，不以本地拦截声称平台实测拒绝。

验收覆盖：双边freeze/restore、每批前后全量ACL读回、100锁/心跳查询、持锁导出控制SQL、capture全部查询、暂存含建表/填充、账本lookup、单事务promote（含外键/触发器/Auth）、sequences、最终对账及回退检查。只读请求也纳入SQL通道预算；全链路本地请求清单逐笔留档，生产窗口前以新鲜数据重新计算。

### 1.2 窗口预算与分级中止判据

以下是**保守排期上限，不是平台实测耗时或120分钟恢复保证**。从T累计计时，步骤预算与累计截止取先到者；30分钟是快路径预期，未被实测证明。T+90分钟仍未满足开放条件即放弃本轮，留30分钟恢复旧家。准备工作、备份工具核验和恢复包生成应在窗口外完成；最终持锁导出仍在窗口内。

| 步骤 | 本步预算 | 累计截止 | 中止判据与下一步 |
|---|---:|---:|---|
| 旧后端维护部署及HTTP确认 | 10分钟 | T+10 | 未确认维护/旧后端身份，停止并恢复旧部署；不开始停权或复制 |
| 来源持锁、双边分批停权、最终一致全备 | 15分钟 | T+25 | 导出/SHA/100锁任一失败，或心跳超过45秒，放弃本轮；恢复来源服务，不用部分备份继续。来源停权走单消息传输并在排除扩展成员口径下生成（2026-11-02深夜本机复现实测：1194对象单消息执行116ms@45ms模拟往返、执行器全程307ms，详见[停权提速演练报告](2026-11-02-来源停权提速演练与受控复现报告.md)；原stdin逐条传输实测65秒超时根因与188个扩展函数不可停权问题均已在受控环境确证） |
| 目标只读capture、差异审阅、不可变包 | 15分钟 | T+40 | 未知目标新写入、结构/身份/ACL漂移或包校验失败，停止；无新写入才按§6回旧家 |
| 本次包实际批数的暂存及账本查询 | 20分钟 | T+60 | 任一请求达到60秒、权限失败、结果不明或总预算到点，停止后续写入；先查账本和实际状态，再走§6 |
| 单次原子promote | 1分钟 | T+61 | 锁等待3秒或单请求/语句60秒上限触发即放弃本轮；只读核实提交/回滚，不拆事务、不自动重试 |
| 序列与独立99表/84身份/结构对账 | 9分钟 | T+70 | 任一不一致/超预算，保持维护并退回；序列已前进允许空号，不承诺逐字节恢复 |
| CloudBase候选维护部署及release/健康核对 | 10分钟 | T+80 | release、后端或健康不符/超预算，按§6恢复旧版本及旧变量 |
| 目标权限复核、开放前验收及解除维护部署 | 10分钟 | T+90 | 任何关键验收失败/超预算就回旧家；开放前只能做不产生业务新写入的检查。真实浏览器/写入验收一旦产生新写入，立即适用§6第三级 |
| 失败恢复预留：确认状态→旧变量/部署→来源ACL→健康/开放 | 30分钟 | T+120 | 两边先维持维护；结果不明不盲切。T+120仍未恢复时继续维护并通知延期，不为赶公告丢数据或绕过断言 |

暂存批次数以本轮包实际生成的 `stageBatches.length` 为准；逐批记录执行请求和账本读回，capture与末尾对账请求另计。不得沿用历史107批数字或虚报新批数。平台耗时及距离60秒余量在窗口逐步记实测。任一步触发止损都停止本轮接管；确认没有新家业务新写入后，执行§6对应旧家恢复路径。若发生新写入或无法证明没有，先保全差异，不能把“失败即回旧家”解释成直接回旧快照。

## 3. 维护与来源停写

1. 获批窗口内先部署已审定版本且 `DYDATA_WRITE_FREEZE=1`。这是正式部署动作，**不是可随手拨的开关**。按本手册顺序共有三次部署：旧后端加维护、新后端保持维护、去掉维护变量重新发布；§1.2已分别预留时间，不能只计算一冻一解两次。三次部署每次都必须记录目标部署的READY状态和实际commit SHA，分别读取两个域名的实际别名归属，并对真实HTTP状态做核验；任一别名尚未指向目标部署时，手动promote后重新核对两个别名和HTTP，全部通过才进入下一步。
   - **这次部署必须仍指向旧源 Supabase**，只额外加维护开关。清单内任何 CloudBase 目标值（`DYDATA_BACKEND`、`CLOUDBASE_ENV_ID`、`CLOUDBASE_SERVICE_API_KEY` 等）都不得随这一次一起改。若误部 CloudBase 版，维护期间员工看到的是新家空数据，用“等切完就好”解释不了。
   - 503 范围要说准：除精确的 `/api/health` 外，matcher 命中的一切路径都 503；matcher 只放行 `_next/static`、`_next/image`、`favicon.ico` 三类构建产物。`public/` 下的静态文件（当前仅 5 个未被引用的模板 SVG；仓库内本来没有 `robots.txt` / `sitemap.xml`）同样 503，因此**不写“静态资源正常”**。
   - 读写一并暂停。真实HTTP检查登录、提交、回调、人员操作均503并有 `x-dydata-maintenance: 1`，健康可达。
   - **部署后必须读回生产别名归属**：11-02 官方回滚后自动提升不再发生（11-03 01:10 push 的部署 READY 后两域名仍指旧部署，手动 `vercel promote` 4 秒接管，实测；"回滚关闭自动提升"为推测）。本手册三次部署每次 READY 后都要 `vercel inspect` 两域名确认归属到目标部署，未接管先 promote 再复核，并用真实HTTP分别确认维护/健康或开放状态；记录READY关联的commit SHA。核验不通过不进入下一步。环境变量改动本身不触发部署，变量变化必须由一次新部署承载。见[窗口前对齐推送与生产核对](2026-11-03-窗口前Git对齐推送与生产核对.md)。
2. 分别读取来源及目标 ACL 快照，保存项目、时间与SHA；用 `buildFreezePackage` 离线生成各自正向/回退文件。**来源侧必须用排除扩展成员口径**（`buildFreezeSnapshotSql({excludeExtensionMembers:true})` 读取、`buildFreezePackage` 传 `excludeExtensionMembers:true`）：来源public里有188个btree_gist扩展成员函数owner为supabase_admin，postgres角色对它们的REVOKE只告警不生效，全量口径包必然被预计态守卫拒绝（本机同版镜像实测＋官方文档佐证，见[停权提速演练报告](2026-11-02-来源停权提速演练与受控复现报告.md)§4）。排除对象均为internal参数不可经API调用或纯计算函数，无业务数据路径。目标侧不受该限制，建议同口径保持单一快照定义；两侧包各自绑定各自快照SHA。窗口授权须明确包含此临时停权及来源侧排除口径。停权收回PUBLIC/anon/authenticated/service_role对public表、列、序列、业务函数的权限，不改RLS/函数体/业务行。对目标只用平台管理通道执行，service API key会暂时无法读业务表。
3. 来源实际99表清单存为私有JSON，启动独立守锁进程，**不要使用执行完即退出的 `psql -c 'LOCK…'`**：

```sh
node scripts/cloudbase/cutover-lock-keeper.mjs --hold-authorized-source \
  --inventory "$CUTOVER_DIR/source-99-tables.json" \
  --receipt "$CUTOVER_DIR/source-lock.json" --opens "$WINDOW_OPEN" --closes "$LOCK_CLOSE"
```

连接从 `DYDATA_CUTOVER_SOURCE_URL` 注入。另一个终端继续操作，此进程保持运行。来源仅允许本项目两组精确连接：直连 `db.gcrhhxaopomtposmahsw.supabase.co` / 用户 `postgres`，或原session pooler `aws-1-ap-southeast-1.pooler.supabase.com` / 用户 `postgres.gcrhhxaopomtposmahsw`；端口均5432、数据库均postgres。2026-11-02窗口外只读预检中，pooler完整导出失败且归档不完整，改同项目直连后完整包70.948秒成功，独立离线解包核对99表62,681行、Auth84；正式窗口选择直连，预检包不代替最终持锁备份。根因仅确认连接路径对照差异，未判定平台或网络故障。从来源数据库独立读取守锁PID的100个已授予SHARE锁，记录读数。导出与守锁须使用同一精确连接身份；任何心跳超过45秒、PID/lockId变更、少一个锁或断连均停止：**重新持锁、重新导出、重新生成包**，禁止把旧快照配到新锁。

接管包截止 `PACKAGE_CLOSE` 必须至少早于 `LOCK_CLOSE` 两分钟；两种窗口均不超过4小时，预留足够失败诊断/回退时间。锁进程每30秒查询防止15分钟空闲超时，到期自动释放；HELD文件不是持续持锁的充分证明，仍需数据库独立读回。管理员超权限连接及平台任务须停用，不能依赖4角色停权覆盖它们。

4. 使用v2不可变分批包（`applyBatches`正序、`rollbackBatches`反序）；旧`apply/rollback`整包SQL接口已替换，不得使用私有旧编排器直接执行。**在任何停权批次前，先完成维护部署三方核对，并完成第3项来源守锁、独立读回100锁。** 每批执行前/后均确认两域维护仍生效、相同lockId/PID、100锁和新鲜心跳；失锁或维护失效立即停。批间一致性由应用freeze与连续来源锁共同保护，不能只靠某一批已撤销权限。
   - 对象边界确定性生成；每批各为单事务，并作为一条simple-query消息（直连）或一次管理API调用（目标）。每批保留3秒锁超时、60秒语句上限、完整全对象ACL前后预计态与首尾窗口守卫；不删字段，不拆原子promote。包由外部审定SHA绑定，每批SQL另有SHA，发送前重建核对，参数JSON纳入目标预算。
   - 停权只从原始完整基线开始，不能自动接续。请求结果不明立即停止写入、保留收据；先只读核对完整ACL是否等于某个确定性批次边界。只允许在原窗口、原包、相同连续锁和维护保护下，选对应边界反序还原；任何非预计状态交QW，不猜、不盲重试。末批后独立全量验证，全部一致才进入下一阶段；还原结束同样核对完整原ACL。
   - 还原承诺只覆盖4角色及grant option；不宣称全库所有grantor字节恢复。不把Batch A/B授权借用于本次。过窗或失锁须按§6重新获批恢复窗口，禁止修改旧包时间锁。
   - 获批后执行入口如下；来源连接仍仅从环境装载。目标执行也需要该来源连接，用于独立核验连续100锁。维护证明只存两个域名的时间、HTTP状态与维护标头，不含Cookie或登录凭据。每次freeze/rollback均使用全新收据文件；rollback只改action与收据路径，保持同一审定包及其SHA。

```sh
node scripts/cloudbase/cutover-freeze-executor.mjs --execute-authorized-source \
  --package "$CUTOVER_DIR/source-freeze.json" --expected-sha256 "$SOURCE_FREEZE_SHA256" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json" \
  --maintenance-proof "$CUTOVER_DIR/maintenance-proof.json" \
  --action freeze --receipt "$CUTOVER_DIR/source-freeze-result.json"
node scripts/cloudbase/cutover-freeze-executor.mjs --execute-authorized-cloudbase \
  --package "$CUTOVER_DIR/target-freeze.json" --expected-sha256 "$TARGET_FREEZE_SHA256" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json" \
  --maintenance-proof "$CUTOVER_DIR/maintenance-proof.json" --manager-module "$TCB_MANAGER_MODULE" \
  --action freeze --receipt "$CUTOVER_DIR/target-freeze-result.json"
```

## 4. 最终备份、对账与包生成

持锁后执行：

```sh
node scripts/cloudbase/cutover-export.mjs \
  --output-dir "$CUTOVER_DIR/final-source" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json"
```

同一个 `SERIALIZABLE READ ONLY DEFERRABLE` 快照输出：`database_full.dump`（所有可见非系统schema，包括完整Auth/Storage元数据）、`public_full.dump`、`auth_users_private.json`、`manifest.json`。数据库外角色、平台配置和COS图片字节不在归档内。完整数据库归档只用于灾备，**不能向CloudBase恢复Supabase托管schema**。真实来源权限导致任一导出失败即停止，保留部分文件与失败收据，不能只拿public文件声称整库备份成功。核验每个文件SHA、600权限及一致采样时点。

最终同步采用**完整最终快照接管**，覆盖新增、修改及删除；不是按updated_at猜增量（任务书原写“最后增量同步”，口径变更依据与认可记录见[总报告 §7](2026-11-02-CloudBase切换就绪总报告.md)）。来源是唯一业务权威，先审阅逐表差异，确认目标没有需要保留的新业务写入。执行：

```sh
node scripts/cloudbase/cutover-prepare.mjs capture --read-only-target \
  --source-bundle "$CUTOVER_DIR/final-source" --manager-module "$TCB_MANAGER_MODULE" \
  --output "$CUTOVER_DIR/target-capture.json"
node scripts/cloudbase/cutover-prepare.mjs prepare \
  --source-bundle "$CUTOVER_DIR/final-source" --capture "$CUTOVER_DIR/target-capture.json" \
  --opens "$WINDOW_OPEN" --closes "$PACKAGE_CLOSE" --output "$CUTOVER_DIR/package.json"
```

capture仅执行只读查询，保存逐表实际/来源预期的行数与双摘要、FK/触发器、Auth保护字段及请求号。prepare离线核文件SHA、源与目标99表清单、同源绑定，并生成新runId；**不把目标当前摘要改写成来源一致结果**。目标原额外身份保留，源84UUID必须都已唯一存在；人数变化、缺UUID、额外依赖、表结构变化或未知目标业务数据均先停止核实，不能自动删账号或补造身份。

本轮Auth状态映射为59正常、24封禁、1未激活，窗口内按最新来源重新核对。原UUID不改；密码只按既有base64(bcrypt)转换，不重置，不明文导出。整行目标Auth除last_login外均作为精确保护基线；时区表示统一为UTC并保留微秒，不删除保护字段。

离线检查输出SQL只含本次批准范围，正向/反向时间锁和收据机制通过，登记package的SHA256。driver必须绑定这一个审定SHA。不得沿用本轮本地生成的演练包或历史生产快照。

## 5. 新家接管、独立核对与开放

按 `stage` → `promote` → `sequences` 执行，同一不可变包，各阶段新收据文件：

```sh
node scripts/cloudbase/cutover-cloudbase-driver.mjs --execute-authorized-cloudbase \
  --package "$CUTOVER_DIR/package.json" --expected-sha256 "$PACKAGE_SHA256" \
  --phase stage --manager-module "$TCB_MANAGER_MODULE" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json" --receipt "$CUTOVER_DIR/stage-result.json"
```

后两步只替换phase及receipt文件名，不改包。每批SQL上限480KiB，最大60秒；使用既有 `dydata_migration.sql_batch_receipts` 事务内批次账本，保存真实RequestId。暂存schema仅管理者可访问。**回执丢失或超时后只读查账本和实际状态；不盲目重试、不改SQL同名续跑。** 序列的setval不支持事务回滚，即使没有批次收据也必须读实际值再判断。

promote只有一个事务：锁99表及Auth，精确核原目标、暂存来源、FK/触发器与Auth基线；暂时停业务触发器，按目标原定义重建外键，替换99表数据，镜像84身份状态，再验证逐表摘要及约束恢复、窗口未到期后提交。目标现有权限/RLS/函数不替换。平台若不支持所需权限或60秒超时，整个接管不通过，**不拆事务**。

sequences为独立检查点，只向前推进到来源/目标较大值，不倒退重用编号。执行后逐序列读取last_value/is_called，与来源及表最大值核对；失败保持维护。最后重新capture到全新文件，**99/99行数+两摘要一致**，84账号关键字段/状态一致、额外身份不变、FK/触发器/函数/RLS/ACL与停权基线相符（开放后再与原ACL相符），才进入部署核验。收据不代替数据核对。

恢复目标原ACL，复读确认；来源保留停权以阻止旧网站/旧JWT再次写业务数据，备份归档和恢复ACL文件保留30天。来源管理员只读运维，源Auth等托管后台不承诺物理不可变；停止源定时写任务并持续监控。守锁仅在已完成接管核验且来源客户端持续停权后释放。

用已审定变量对CloudBase版本重新构建部署；只增改清单内键，不整包覆盖原38项。保留COS原值。候选 `RATE_LIMIT_DISABLED=true` 仅关闭页面IP阈值以避免办公室共用IP误限，API限流仍在，见[实测](2026-11-02-CloudBase服务密钥与限流评估.md)。本轮无线上变量变更。

先维护状态核对部署实际release与目标健康，再开放测试人员访问进行真实角色冒烟：登录/刷新/退出、作品复盘、非空排行榜、大盘、成员管理、截图逐字节权限读取。需要业务写入的验收须在窗口明确授权使用专用测试对象并精确清理；本轮没有授权/执行任何生产测试写入。记录**首次CloudBase业务新写入**时间；角色合法/越权证据通过后解除维护并通知员工。否则执行下面对应级别的回退。

## 6. 回退分级与截止

| 状态 | 执行路径 | 不可省略 |
|---|---|---|
| 尚未promote或原子事务明确失败 | 停止后续批次；保留暂存/失败收据，核原目标及源业务摘要未变；若结束本窗口，恢复来源原ACL、回旧版本和原变量、解除维护 | 若结果不明先查账本和实际状态，不能按“失败退出码”认定未提交 |
| 已promote，但确定新家尚无业务新写入 | 两边保持维护；将应用回旧提交/原变量，确认来源仍为最终快照，按绑定停权预计态恢复来源ACL并核对，再恢复源服务 | 比较来源/最终快照；新家保持停权，不需要反向覆盖源数据。序列已前进允许有空号，不能称逐字节全状态回滚 |
| 已有新写入，或不能证明没有 | 立即冻结两边，保全新家完整数据/审计/附件路径及最后源备份，列新增/修改/删除差异；**不直接切回旧源** | 无现成无损反向同步授权与实测，不承诺零丢失自动回退。阿禅选择继续在新家修复，或审定差异合并/反向迁移后切回 |

临时ACL回退包只在其批准窗口有效。**过窗不能去掉时间锁或直接修改旧包**；维持维护，交负责人批准恢复窗口，用原快照和当前预计态重生成并核对SHA。已存在的失败证据不得覆盖。成功后本轮授权之外的暂存删除、Supabase退出、历史图片删除、每日COS备份另立任务，不能顺手执行。

### 6.1 固定旧版本恢复路径
