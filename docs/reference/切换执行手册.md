## 2. 工具与私有留档

使用已验证的Node24、匹配来源版本的PostgreSQL工具；本轮客户端18.3、本地数据库16.15。每次运行使用新的仓库外目录，目录700、文件600。所有SQL、Auth快照及整库归档均为敏感材料，**不提交Git、不打印行值、不放共享网盘**。密钥/连接串仅从既有受限文件注入环境，不写命令行、聊天或日志。

主要入口：

| 脚本 | 用途 | 本轮验证 |
|---|---|---|
| `cutover-export.mjs` | 同一只读快照导出完整数据库归档、public归档、Auth迁移白名单与SHA256 | 本地实际导出 |
| `cutover-lock-keeper.mjs` | 单独进程保持99表+auth.users共100个SHARE锁，每30秒心跳 | 本地阻断写入、心跳、释放验证 |
| `cutover-freeze.mjs` | 从准确ACL快照离线生成临时停权及反向包 | 本地正反向、时间锁、权限恢复验证 |
| `cutover-prepare.mjs capture/prepare` | 读取目标并离线绑定最终来源，生成不可变接管包 | 本地全链串联 |
| `cutover-cloudbase-driver.mjs` | 在未来获批窗口调用现有ExecutePGSql工具，分阶段记录收据 | 离线守卫/本地SQL演练；未调用真实写接口 |
| `cutover-sync.mjs plan/apply` | 快照差异表及本地恢复演练 | **apply仅允许本机，禁止拿它写CloudBase** |
| `service-key-check.mjs` | 离线检查当前服务JWT到期，不验证签名 | 当前11-07 02:40:34到期 |

上述文件均在 `scripts/cloudbase/`。现有SDK模块路径需在执行机核实，可用已安装的 `@cloudbase/cloudbase-mcp/dist/index.cjs`；不得临时下载未经核验版本。默认无明确执行标记的driver不会初始化SDK。保留工具版本、提交、源文件SHA、窗口、操作者、所有RequestId和退出码。

## 3. 维护与来源停写

1. 获批窗口内先部署已审定版本且 `DYDATA_WRITE_FREEZE=1`。这是正式部署动作，本轮未做。除精确的 `/api/health` 外，动态页面/API/Server Actions均503；静态资源正常。读写一并暂停。真实HTTP检查登录、提交、回调、人员操作均503并有 `x-dydata-maintenance: 1`，健康可达。
2. 分别读取来源及目标的 `FREEZE_SNAPSHOT_SQL`，保存项目、时间与SHA；用 `buildFreezePackage({snapshot,project,opensAt,closesAt})` 离线生成各自正向/回退文件。窗口授权须明确包含此临时停权。它收回PUBLIC/anon/authenticated/service_role对public表、列、序列、函数的权限，不改RLS/函数体/业务行。对目标只用平台管理通道执行，service API key会暂时无法读业务表。
3. 各包执行前精确比较原ACL，漂移立即停。单事务、锁超时3秒、语句60秒，执行后读取预计停权态。不把Batch A/B授权借用于本次。还原承诺只覆盖上述4角色的权限与grant option；不宣称全库所有grantor字节恢复。
4. 来源实际99表清单存为私有JSON，启动独立守锁进程，**不要使用执行完即退出的 `psql -c 'LOCK…'`**：

```sh
node scripts/cloudbase/cutover-lock-keeper.mjs --hold-authorized-source \
  --inventory "$CUTOVER_DIR/source-99-tables.json" \
  --receipt "$CUTOVER_DIR/source-lock.json" --opens "$WINDOW_OPEN" --closes "$LOCK_CLOSE"
```

连接从 `DYDATA_CUTOVER_SOURCE_URL` 注入。另一个终端继续操作，此进程保持运行。要求来源为既定pooler主机及项目用户；从来源数据库独立读取该PID的100个已授予SHARE锁，记录读数。任何心跳超过45秒、PID/lockId变更、少一个锁或断连均停止：**重新持锁、重新导出、重新生成包**，禁止把旧快照配到新锁。

接管包截止 `PACKAGE_CLOSE` 必须至少早于 `LOCK_CLOSE` 两分钟；两种窗口均不超过4小时，预留足够失败诊断/回退时间。锁进程每30秒查询防止15分钟空闲超时，到期自动释放；HELD文件不是持续持锁的充分证明，仍需数据库独立读回。管理员超权限连接及平台任务须停用，不能依赖4角色停权覆盖它们。

## 4. 最终备份、对账与包生成

持锁后执行：

```sh
node scripts/cloudbase/cutover-export.mjs \
  --output-dir "$CUTOVER_DIR/final-source" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json"
```

同一个 `SERIALIZABLE READ ONLY DEFERRABLE` 快照输出：`database_full.dump`（所有可见非系统schema，包括完整Auth/Storage元数据）、`public_full.dump`、`auth_users_private.json`、`manifest.json`。数据库外角色、平台配置和COS图片字节不在归档内。完整数据库归档只用于灾备，**不能向CloudBase恢复Supabase托管schema**。真实来源权限导致任一导出失败即停止，保留部分文件与失败收据，不能只拿public文件声称整库备份成功。核验每个文件SHA、600权限及一致采样时点。

最终同步采用**完整最终快照接管**，覆盖新增、修改及删除；不是按updated_at猜增量。来源是唯一业务权威，先审阅逐表差异，确认目标没有需要保留的新业务写入。执行：

```sh
node scripts/cloudbase/cutover-prepare.mjs capture --read-only-target \
  --source-bundle "$CUTOVER_DIR/final-source" --manager-module "$TCB_MANAGER_MODULE" \
  --output "$CUTOVER_DIR/target-capture.json"
node scripts/cloudbase/cutover-prepare.mjs prepare \
  --source-bundle "$CUTOVER_DIR/final-source" --capture "$CUTOVER_DIR/target-capture.json" \
  --opens "$WINDOW_OPEN" --closes "$PACKAGE_CLOSE" --output "$CUTOVER_DIR/package.json"
```

capture仅执行只读查询，保存逐表实际/来源预期的行数与双摘要、FK/触发器、Auth保护字段及请求号。prepare离线核文件SHA、源与目标99表清单、同源绑定，并生成新runId；**不把目标当前摘要改写成来源一致结果**。目标原额外身份保留，源84UUID必须都已唯一存在；人数变化、缺UUID、额外依赖、表结构变化或未知目标业务数据均先停止核实，不能自动删账号或补造身份。

本轮Auth状态映射为59正常、24封禁、1未激活，窗口内按最新来源重新核对。原UUID不改；密码只按既有base64(bcrypt)转换，不重置，不明文导出。整行目标Auth除last_login外均作为精确保护基线；时区表示统一为UTC并保留微秒，不删除保护字段。

离线检查输出SQL只含本次批准范围，正向/反向时间锁和收据机制通过，登记package的SHA256。driver必须绑定这一个审定SHA。不得沿用本轮本地生成的演练包或历史生产快照。

## 5. 新家接管、独立核对与开放

按 `stage` → `promote` → `sequences` 执行，同一不可变包，各阶段新收据文件：

```sh
node scripts/cloudbase/cutover-cloudbase-driver.mjs --execute-authorized-cloudbase \
  --package "$CUTOVER_DIR/package.json" --expected-sha256 "$PACKAGE_SHA256" \
  --phase stage --manager-module "$TCB_MANAGER_MODULE" \
  --source-lock-receipt "$CUTOVER_DIR/source-lock.json" --receipt "$CUTOVER_DIR/stage-result.json"
```

后两步只替换phase及receipt文件名，不改包。每批SQL上限480KiB，最大60秒；使用既有 `dydata_migration.sql_batch_receipts` 事务内批次账本，保存真实RequestId。暂存schema仅管理者可访问。**回执丢失或超时后只读查账本和实际状态；不盲目重试、不改SQL同名续跑。** 序列的setval不支持事务回滚，即使没有批次收据也必须读实际值再判断。

promote只有一个事务：锁99表及Auth，精确核原目标、暂存来源、FK/触发器与Auth基线；暂时停业务触发器，按目标原定义重建外键，替换99表数据，镜像84身份状态，再验证逐表摘要及约束恢复、窗口未到期后提交。目标现有权限/RLS/函数不替换。平台若不支持所需权限或60秒超时，整个接管不通过，**不拆事务**。

sequences为独立检查点，只向前推进到来源/目标较大值，不倒退重用编号。执行后逐序列读取last_value/is_called，与来源及表最大值核对；失败保持维护。最后重新capture到全新文件，**99/99行数+两摘要一致**，84账号关键字段/状态一致、额外身份不变、FK/触发器/函数/RLS/ACL与停权基线相符（开放后再与原ACL相符），才进入部署核验。收据不代替数据核对。

恢复目标原ACL，复读确认；来源保留停权以阻止旧网站/旧JWT再次写业务数据，备份归档和恢复ACL文件保留30天。来源管理员只读运维，源Auth等托管后台不承诺物理不可变；停止源定时写任务并持续监控。守锁仅在已完成接管核验且来源客户端持续停权后释放。

用已审定变量对CloudBase版本重新构建部署；只增改清单内键，不整包覆盖原38项。保留COS原值。候选 `RATE_LIMIT_DISABLED=true` 仅关闭页面IP阈值以避免办公室共用IP误限，API限流仍在，见[实测](2026-11-02-CloudBase服务密钥与限流评估.md)。本轮无线上变量变更。

先维护状态核对部署实际release与目标健康，再开放测试人员访问进行真实角色冒烟：登录/刷新/退出、作品复盘、非空排行榜、大盘、成员管理、截图逐字节权限读取。需要业务写入的验收须在窗口明确授权使用专用测试对象并精确清理；本轮没有授权/执行任何生产测试写入。记录**首次CloudBase业务新写入**时间；角色合法/越权证据通过后解除维护并通知员工。否则执行下面对应级别的回退。

## 6. 回退分级与截止

| 状态 | 执行路径 | 不可省略 |
|---|---|---|
| 尚未promote或原子事务明确失败 | 停止后续批次；保留暂存/失败收据，核原目标及源业务摘要未变；若结束本窗口，恢复来源原ACL、回旧版本和原变量、解除维护 | 若结果不明先查账本和实际状态，不能按“失败退出码”认定未提交 |
| 已promote，但确定新家尚无业务新写入 | 两边保持维护；将应用回旧提交/原变量，确认来源仍为最终快照，按绑定停权预计态恢复来源ACL并核对，再恢复源服务 | 比较来源/最终快照；新家保持停权，不需要反向覆盖源数据。序列已前进允许有空号，不能称逐字节全状态回滚 |
| 已有新写入，或不能证明没有 | 立即冻结两边，保全新家完整数据/审计/附件路径及最后源备份，列新增/修改/删除差异；**不直接切回旧源** | 无现成无损反向同步授权与实测，不承诺零丢失自动回退。阿禅选择继续在新家修复，或审定差异合并/反向迁移后切回 |

临时ACL回退包只在其批准窗口有效。**过窗不能去掉时间锁或直接修改旧包**；维持维护，交负责人批准恢复窗口，用原快照和当前预计态重生成并核对SHA。已存在的失败证据不得覆盖。成功后本轮授权之外的暂存删除、Supabase退出、历史图片删除、每日COS备份另立任务，不能顺手执行。

观察期记录：每5分钟登录失败率、403/429/5xx、DB/API延迟及请求量、待处理任务；首小时人工核对，24小时复核关键操作，30天保留Supabase和最终备份。R02仍为当前设备退出、旧JWT最多余下1小时；飞书/AI等授权真实外发在观察期补测，B03本地桩不等于真实投递。每日备份支线未做，30天旧源只覆盖切换基线，**不覆盖新家之后的新写入**。
