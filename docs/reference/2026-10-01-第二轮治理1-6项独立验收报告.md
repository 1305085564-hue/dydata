**实际实现**
- `supabase/migrations/20261001040618_system_settings_service_role_only.sql`：`enable row level security` → `drop policy if exists "Admins manage system settings"` → `revoke all on table public.system_settings from anon, authenticated` → `grant select, insert, update, delete ... to service_role` → 新建 `Service role full access on system_settings`（`for all to service_role using(true) with check(true)`）。整个 migration 包在 `begin; ... commit;`。
- 三个访问方全部走服务端 service_role，且先过权限：
  - `src/app/api/admin/system/settings/route.ts:53-55, 83-86` → `requireAdminServiceClient()` + `requireSystemPermission(auth)`（即 `actor.permissions.manage_system !== true` → 403）
  - `src/app/api/admin/topics-library/feishu-url/route.ts:14, 23` → `requireAdminActor({ requiredPermission: "manage_system" })`
  - `src/app/(app)/topics/page.tsx:47-53` → `loadFeishuWorkspaceUrl(createAdminClient())`（服务端渲染，无独立权限门槛，只下发 URL 不写）

**独立证据（生产库只读，同连接探针 `profiles=84`）**

## 第 6 项 权限/范围栈与鉴权入口统一

**原承诺**：绘出最短调用链；核验四个入口共用 `resolvePermissionCore`；管理 API 取得 context 后真正复用；分类剩余 `buildDataAccessScope` / `buildPermissionContextForActor` 调用；禁止进程级权限缓存，业务缓存不得扩大可见范围。

**当前最短调用链（读码得出）**

```

  └─ resolvePermissionCore()       // React cache()，请求内
       ├─ adminSupabase.from("profiles").select(id,name,role,company_role,membership_status,team_id)

                             → { supabase, actor, context: { permissionInfo, scope } }
requireAdminActor(opts)    = 直接委派 requireAdminContext（返回体已带 context）
getCurrentPermissionContext(perspective, teamId) = React cache()
                             → company+null 直接返回 core.scope，否则 buildPermissionContextFromPermissionInfo → buildDataAccessScope
getUserPermissions()       = resolvePermissionCore → permissionInfoFromCore
```
