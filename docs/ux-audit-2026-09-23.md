**URL**：`http://localhost:3000/admin/collaboration`（本地 dev，连生产 Supabase）

**浏览器**：本地 Chromium（Playwright 1.62.1，`deviceScaleFactor: 1`）
**视口**：1440×900 基线 + 1280/1024/768/375 扫描

## 摘要

页面**完成度很高**：数据密度大但可读，键盘可达性 26/26 全通过，网络零失败，空态有真正的解释文案而非"暂无数据"。审计中出现的三个"疑似严重问题"经复验**全部是环境假象或我方脚本缺陷**，不是产品缺陷。

真正站得住的只有一处摩擦：**点开右上角「岗位归属完整」芯片要等 2–3 秒转圈**，而这颗芯片本身的文案已经说明了结论。根因是该抽屉复用了首屏的全月全量查询。

另有若干口径/标注不一致（文案页签人数口径、上一月按钮缺无障碍名、小组列表表格语义、环比极值、无效深链），其中「运营页缺指标解释图标」一条经复验为**误报**、已撤回。

> **处置**：以上问题已于 2026-09-23 当日一次性修复（M4 误报除外），验证与取证见文末「修复处置」与「修复复验」两节。

## 发现

### High

#### H1. 「岗位归属完整」抽屉每次打开都重跑全月全量查询，最该秒回的状态要等 3 秒

- **现象**：右上角芯片文案已是「岗位归属完整」（绿色对勾，含义是"本月无需补任何归属"）。点开抽屉 → 转圈 + 「正在扫描待补归属作品…」→ 实测 **+3 秒**才显示「本月作品岗位归属均已完备 / 所有作品均已关联明确的文案、剪辑与运营责任人。」
- **根因（已定位）**：抽屉的数据接口复用了**首屏同一个全量加载函数**。
  - `src/app/(app)/admin/collaboration/health-bar.tsx:134-137` — `handleOpen()` 每次都无条件 `fetchUnattributedList()`
  - `src/app/api/admin/collaboration/handlers.ts:149-153` — `buildUnattributedResponse` 调用 `loadCollaborationMonthDataset(...)`，与首屏 `collaboration-data-container.tsx:103` 是同一个函数
  - 首屏实测同一函数耗时 **5453ms**；抽屉实测 3 秒（同函数，数据量相同）
- **为什么是 High**：这是"把已知答案再算一遍"。芯片已经展示了结论，用户点开是**为了确认**——偏偏在这个最该瞬时响应的场景转 3 秒。且**无缓存**，反复开合会反复重跑，与月度作品量正相关（本月 514 条，数据增长会线性恶化）。
- **修复建议**（任选，成本递增）：
  1. `summary.unattributed === 0` 时直接本地渲染「已完备」，**不发请求**（最省，覆盖最常见状态）
  2. 接口拆轻量化：只查待补归属所需字段，不复用全量 dataset
  3. 打开瞬间先用已有 `summary` 渲染骨架，详情异步补
- **证据**：截图 `11-healthchip-clicked.png`、`20-chip-drawer-30s.png`；30 秒时间线记录在 `.acceptance/ux-audit-phase2b.json`

### Medium

#### M1. 「文案 (N)」与另外三个页签的人数口径不同，空态下会被误读

- **现象**：切到 2026-10（未来月，无任何作品）时 —— **达人 (0)、运营 (0)、剪辑 (0)，但「文案 (3)」**。上层是 0 的时候文案显示 3，用户第一反应是"文案有数据了？"
- **根因**：`src/app/api/admin/collaboration/_shared.ts:380-382`
  ```ts
  if (role === "writer") {
    for (const id of certifiedWriters.keys()) byStaff.set(id, []);  // 已认证文案预置空条目
  }
  ```
  即：达人/运营/剪辑计数 = **当月有署名作品的人数**；文案计数 = **已认证文案总数**（含零产出）。
- **判断**：这是**有意设计**（文案是认证制，需要能看到"已认证但零产出"的人），不是错误。但页签上没有任何标注，用户无从知道两者口径不同。
- **修复建议**：页签文案改为区分口径，例如「文案 (3 · 含未产出 1)」；或在文案页签内加一行说明。
- **证据**：截图 `23-month-2026-10.png`

#### M2. 「上一月」按钮没有无障碍名称，与「下一月」不一致

- **现象**：同一组翻月控件，键盘 Tab 到「下一月」时读屏能读到 `aria-label="下一月"`；Tab 到「上一月」时是**一个无名按钮**（实测 `aria=""`，只有 `title`）。
- **根因**：`collaboration-workbench.tsx:434-441`（上一月只有 `title="上一月 (快捷键 ←)"`）vs `:461`（下一月有 `aria-label="下一月"`）。同一个文件内两种写法。
- **影响**：读屏用户在"下一月"处能听懂，在"上一月"处突然失去信息。
- **修复建议**：给上一月补 `aria-label="上一月"`（成本：一行）。
- **证据**：键盘序列第 8 位（`.acceptance/ux-audit-phase2a.json` → `keyboardSeq`）

#### M3. 小组列表把整行 `<tr>` 设为 `role="button"`，破坏表格语义

- **现象**：点整行进组详情，交互本身做得不错（有 `aria-label="进入文案1组小队详情"`、支持 Enter 键、有焦点环）。但 `role="button"` 加在 `<tr>` 上，会让读屏**不再按表格语义播报这一行**，列头关联丢失。
- **根因**：`src/app/(app)/admin/collaboration/work-group-list-tab.tsx:200-210`
- **修复建议**：保留 `<tr>` 语义，把「进入」列做成真正的按钮（或整行加 `onClick` 但不动 `role`）；若坚持整行可点，考虑把表格改为列表语义。
- **证据**：源码 + 截图 `03-teams-default.png`

#### ~~M4. 运营/剪辑页签缺「有效作品」「优秀作品」的口径解释~~（已撤回：误报）

- **原判断**：达人页签这两列列头带可见的 `(i)` 图标，运营/剪辑页没有 → 结论"口径解释缺失、同名指标信息量不一致"。
- **复验结论**：**误报，代码未改**。达人页那个图标是**排序图标**（该列可排序），不是口径说明图标：
  - `talent-tab.tsx:99-124` 这两列是可排序 `<button>`（点列头排序），自然渲染出排序图标；`operator-tab.tsx:115-116`、`staff-tab.tsx:123-124` 是不可排序的纯 `<TableHead title="…">`，故无图标。
  - 四个页签的口径说明**全都写在原生 `title` 里**（"播放大于500的作品条数"/"播放至少30,000，简单计数"），写法一致，不存在"达人表解释了、运营表没解释"。
- **教训**：审计里"看到图标"不能凭形状推断语义，必须点开或读源码确认。本条已并入下方「被推翻的假警报」。

### Low

#### L1. 环比极值原样展示：`+2462.6%` 会被当成数据出错

- **现象**：运营页签「环比」列出现 `↗+2462.6%`。
- **已核实为真实计算，非 bug**：`_shared.ts:280-285` 的 `monthOverMonth` 逻辑正确（`previousRows.length === 0` 与 `previousTotal <= 0` 都返回 `null`，无除零）。极值来源是上月基数极小。
- **值得改的理由**：这样的数字出现在管理看板上，管理者第一反应是"数据错了吧"。建议对超大涨幅改用「环比 ↑ 24.6 倍」或加"基数过低"提示。
- **附带确认**：涨用 `#6FAA7D`（规范里的 growth/success 绿）、跌用 `#C0685C`（规范里的 error 朱红），两色在 `docs/Claude设计规范.md` §语义信号梯次 中有定义，方向自洽 —— **不判为配色违规**。
- **证据**：截图 `02-roles-operators.png`

#### L2. 无效的小组深链静默回落到列表，没有任何提示

- **现象**：用不存在的 `groupId` 深链进入（`?view=teams&groupId=00000000-0000-0000-0000-000000000000`），页面**静默显示小组列表**，不报错、不白屏、也不提示"该小队不存在"。
- **判断**：降级方向是对的（不崩），但用户从旧链接或收藏进来，会以为自己点错了位置。
- **修复建议**：识别到 `groupId` 无效时给一条轻提示（如「该小队不存在或已删除，已返回列表」），或把 URL 里的 `groupId` 清掉。
- **证据**：截图 `32-deeplink-badgroup.png`（渲染结果与正常小组列表一致）

#### L3. 暗色模式未落地（用户当前不可触发，非现存缺陷）

- **事实**：`src/styles/tokens.css:60` 定义了完整的 `.dark` 变量集；但全仓 `dark:` 前缀用法仅 **5 处**，业务页面大量使用硬编码色值（`text-[#1C1917]`、`bg-white` 等）不响应主题。强制加 `.dark` 后，页面主标题「数据管理」直接不可见、副标题几乎不可读。
- **关键判断**：**产品当前没有任何暗色切换入口** —— 全仓搜索 `主题 / theme / ThemeToggle / setTheme / prefers-color-scheme` 零命中（仅 `sonner.tsx` 硬编码 `theme="light"`）。因此用户无法触发该状态，**不构成现存缺陷**。
- **建议**：若未来要上线暗色，需先清点业务页面的硬编码色值（本次只看了数据管理页，问题已很明显）；若短期不做，可考虑移除 `.dark` 变量块与 `sonner` 的硬编码，避免"看起来支持其实不支持"。

## 做得好的地方（建议保留/复用）

1. **键盘可达性扎实**：26 个焦点位全部有可见焦点环，无焦点陷阱，顺序与视觉一致。同类 B 端表格页常见"点击后焦点丢失"，本页没有。
