# DYData 权限与访问控制

> 本文件回答一个问题：谁能看什么、谁能改什么、判断"会不会越权"时先读哪里。
> 用途：任何 AI 动"谁能看/谁能改/是否越权"相关的活之前，先读本文件，不得从旧记忆推断权限。
> 面向阿禅：你不用懂代码。想知道"某个人能不能看到某数据、能不能改"，先看快速参考的角色和范围表。
> 面向 AI：权限规则必须集中在本文件；代码、migration、RLS、API、Server Action 和前端入口都要与本文件同步，不能只改其中一层。
> 最后核对代码日期：2026-10-31（本次仅公司范围与视频复盘成员只读特例；未改权限实现）

## 权限契约

### 1. 身份和范围

| 身份 | 默认范围 | 能做什么 | 明确不能做什么 |
|---|---|---|---|
| 组员 `member` | 自己 | 查看和提交自己的业务数据、个人导出、个人数据分析、可只读查看本公司岗位数据、可按视频复盘只读特例查看作品、只读查看本公司发布进度 | 不能审批、不能管理其他成员、不能跨公司读取或写岗位归属、不能对作品或发布状态执行任何写操作 |
| 组长 · 管理 `admin` | 当前公司 | 处理本公司的日常业务、审批本公司在职成员的申请、管理本团队组员 | 不能跨公司审批，不能管理组长、公司所有者或自己，不能把组员升为组长 |
| 公司所有者 `company_owner` | 当前公司 | 管理本公司全部成员、组长、业务数据和审批流程；范围固定为当前公司 | 不能跨公司读取或写入 |
| 归档账号 | 无当前操作范围 | 只能保留历史记录供有权人员查询 | 不能登录、提交、审批、指派、提醒、上传、修改或恢复其他数据 |

### 2. 跨公司视角（已取消）

系统不再提供集团模式、跨公司会话令牌或切换入口。一般范围按当前账号的公司/团队归属计算；视频复盘的成员只读特例见「数据范围」，不恢复集团模式或扩大写权限。

### 3. 权限类别总表

以后每个权限判断都必须同时写清下面六件事：

| 权限类别 | 要回答的问题 | 统一规则 |
|---|---|---|
| 身份权限 | 这个人是谁 | 组员、组长 · 管理、公司所有者；归档是状态 |
| 功能权限 | 能不能做这件事 | 由固定身份规则决定，不再由个人随意拼装权限开关 |
| 数据范围 | 能对哪些人的数据做事 | 默认组员=自己、管理角色=当前公司；模块只读扩展见「数据范围」 |
| 当前/历史 | 归档成员是否还存在 | 当前操作只认 active；历史查询保留 archived |
| 对象归属 | 这个申请、成员、记录属于谁 | 由服务端从数据库读取并核对，不能相信浏览器传来的 `user_id`、`team_id` |
| 入口安全 | 绕过页面能不能操作 | 页面、Server Action、API、RPC、RLS 都必须做同一套检查 |

### 4. 豁免申请和审批

| 动作 | 组员 | 组长 · 管理 | 公司所有者 |
|---|---|---|---|
| 提交自己的申请 | 允许 | 允许 | 允许 |
| 查看待审批申请 | 不允许 | 当前公司在职成员 | 当前公司在职成员 |
| 审批本公司成员 | 不允许 | 允许 | 允许 |
| 审批其他公司成员 | 不允许 | 拒绝 | 拒绝 |
| 审批自己的申请 | 拒绝 | 拒绝 | 拒绝 |
| 审批归档成员 | 拒绝 | 拒绝 | 拒绝 |

审批必须按以下顺序执行：登录 → 身份和功能权限 → 目标成员所属公司 → 目标成员状态 → 申请状态 → 原子写入。

### 5. 固定权限开关的处理规则

当前权限键共 12 个，权威清单在 `src/types/index.ts` 的 `PERMISSION_CATEGORIES` 与 `src/lib/permission-contract.ts`。

这些开关在运行时由 `src/lib/company-permissions.ts` 按 `company_role` 固定生成；`profiles.permissions` 里的 legacy JSON 只保留兼容数据，不决定当前权限。

**迁移期间必须遵守**：
- `manage_members` 不能单独推导出豁免审批权
- 不能因为某个权限开关打开，就把组长范围扩大到其他公司
- 不能用 `permissions = {}`、字段缺失、`null` 或空数组解释成"全集团"
- 页面和管理 AI 均不得提供个人权限写入口；调整权限只能通过角色变更进入固定模板
- 新增功能必须先在本节登记"身份、范围、当前/历史、对象归属、入口和数据库检查"，再写代码

### 6. 统一数据范围语义

- **当前公司范围**：一般按可信 `team_id`，模块特例只认「数据范围」的明确登记；当前操作只包含 `active` 成员
- **历史范围**：可以查询权限范围内的历史记录，包括 archived 成员；归档不能让历史数据消失
- **空范围**：表示"没有可操作对象"，不是"全部对象"
- **没有公司归属的成员**：不能自动回退到集团范围；只能按明确的"自己"范围处理

### 7. 成员主页（`/people/[userId]`）

成员主页是只读成长档案页，是数据管理个人档案抽屉的「可分享、可独立打开」版本。按第 5 节的六项登记：

| 维度 | 规则 |
|---|---|
| 身份权限 | 必须已登录；未登录跳登录页 |
| 功能权限 | 不新增权限键——沿用"只读查看本公司数据"的既有范围，不依赖任何写权限 |
| 数据范围 | `visibleUserIds.includes(目标成员)` 才可看；不在范围内一律渲染「无权查看」，不返回任何数据 |
| 当前 / 历史 | 访问者本人必须 `active`（归档账号拒绝，与 `/topics` 同款页面自查）；被查看的成员可以是 `archived`，历史档案保留可查 |
| 对象归属 | 目标 `userId` 来自 URL，由服务端按 `visibleUserIds` 核对，不相信浏览器传参 |
| 入口安全 | 页面为 Server Component、不在 `src/middleware.ts` matcher（同 `/topics`），因此鉴权全部由页面自查承担——`getCurrentUserContext` 取会话 → 本人 membership 门禁 → `getCurrentPermissionContext` → `resolveCollaborationScope` 求 `visibleUserIds` → 命中集合才继续读数。伪造他人 `userId` 的深链取不到数据 |
| 数据库检查 | 读数走 `createAdminClient()`（service role，与数据管理只读模块同源），因登录身份受"只能看自己"的行级权限限制、跨成员读不到；service role 的安全性压在应用层门禁上，即上一条的 `visibleUserIds` 校验 |

关联：数据管理个人档案抽屉的取数接口 `/api/admin/collaboration/person` 用同一套 `resolveCollaborationScope` + `visibleUserIds` 门禁，两者口径必须保持一致。

### 8. 视频复盘关联截图只读

- 身份/功能：在职登录用户且有 `view_video_review`；沿用「数据范围」登记的作品详情只读范围，不新增角色权限。
- 当前/历史/归属：只允许可见 active 作品最新 24h 快照实际展示的两张截图；截图所属人也必须在可信公司可见范围内（含可见历史成员）。作品或路径由浏览器传入时均不能作为授权依据。
- 入口/数据库：文件接口接收可选 `videoId`，先核对真实会话和服务端公司范围，再用共享详情 loader 精确比对对象路径；service role 仅在该检查内读数，RLS 不变。
- 既有截图票据的 owner 快路径不变；新增关联例外不扩大 owner 列表，关联读取使用私有不缓存。无关文件、跨公司路径或范围外作品拒绝；检查失败关闭访问。

## 安全边界

### service role：绕过所有权限的"万能钥匙"

**关键事实**：
- `createAdminClient()` 用环境变量 `SUPABASE_SERVICE_ROLE_KEY` 建连接，绕过 RLS
- 后台 route 用它直连数据库。这是刻意的架构选择：后台接口不靠数据库 RLS 控权，而是先在应用层挡住没权限的人

**安全含义（务必守住）**：
- service role 用得对不对，全压在应用层鉴权上
- 任何用了 `createAdminClient`/`createServiceClient` 的接口，必须先有等价的鉴权——登录 + 权限校验（`requireAdminActor` 或 `getUserPermissions`），或对象归属校验，或按 `visibleUserIds` 的范围过滤
- service role key 是服务端机密，绝不能出现在发到浏览器的代码里，绝不写进前端，绝不 log
- 判断一个后台接口安不安全，先看两点：有没有某种等价鉴权；返数据时有没有按 `visibleUserIds` 限范围

### 数据库 RLS：第二道纵深防御

虽然后台接口普遍用 service role 绕过 RLS，RLS 仍是重要的兜底——面向浏览器直连的普通客户端（`client`/`server`）仍受 RLS 约束。

**RLS 策略散落在多份 migration 里**，改任何表的读写权限前，先扫一遍 `supabase/migrations/` 里所有涉及该表 `create policy` / `enable row level security` 的文件。

**规矩**：RLS 策略变更只能新增 migration，禁止改旧 migration。

### 鉴权链路（三层）

权限不是靠数据库一层，是应用层为主、数据库为辅：

1. **第一层 · 登录闸机**（`src/middleware.ts`）：校验有效登录态和 `profiles.membership_status`
2. **第二层 · 接口鉴权**（`requireAdminActor` / `getUserPermissions`）：统一确认登录、在职状态、公司角色、固定功能权限和当前公司数据范围
3. **第三层 · 数据范围过滤**（`current-permission-context.ts` + `data-access-scope.ts`）：确认"能进"之后，还要按 `visibleUserIds` / `activeVisibleUserIds` 限定可读和可操作对象

## 常见越权/权限问题排查

- **该看的看不到 / 不该看的看到了**：先看这个人算出来的公司角色和固定权限对不对（`resolvePermissionCore()` 的输出），再看 `visibleUserIds` 范围算得对不对
- **某后台接口谁都能进**：按"安全边界"章节的合格鉴权清单逐项核对
- **改了权限没生效**：留意请求内 `cache()` 去重；运行时权限是固定角色表生成的，若表已改但未部署生效，也会出现"看起来没变"
- **数据库直连读不到数据**：查对应表的 RLS 策略和 helper 函数
