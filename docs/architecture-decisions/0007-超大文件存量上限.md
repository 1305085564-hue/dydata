# 0007 超大文件存量上限

## 背景

`0006-拆分准入门槛与棘轮.md` 把"只降不升"的基线棘轮只用在**名单外**文件上；名单内的超大文件走的是另一条判定 `blocking-file-size`——只要该文件相对基座有改动且行数 >1000 就直接拦。2026-10-03 实测暴露后果：并行提交 `86b97f9f`（保留并续传晚到视频提交，属必要修复）让上传表单 3258→3266 行、上传面板 1078→1105 行，此后主干 `npm run gate:static` 持续报红，20 笔已复验的提交无法上线，要等 B08／B09／B10 三批拆分全部做完才可能转绿。规则把"救火"和"盖歪楼"同罪，施工方遇到只会去找绕法——同一天已经发生过一次用 `new globalThis.Map` 规避探测的事件（见技术债台账）。

## 决定

1. **名单内文件也记存量上限**：凡进入拆分名单（>1000 行，或 >600 行且 90 天被改 ≥45 次）的源码文件，一律登记"当前行数＝上限"，与名单外共用同一套"只准降不准升、并发取更低值"的棘轮机制。
2. **`blocking-file-size` 改为按上限判定**：已有上限记录的超大文件，只有"行数超过自己的上限"才拦；没有上限记录的（新文件、或该登记的没登记）仍然"被改动即拦"，保持失败即关闭。
3. **名单内文件继续豁免"路过必削"**：它们有专门批次，不该被每一次改动强迫削瘦。
4. **上限的新增与下调由复验方收口**：施工方不得自行修改 `scripts/maintainability-baseline.json`，需要动额度时在交付报告里提出，由 [QW] 核对后落笔。
5. **本原则延伸到名单外棘轮**（2026-10-03 16:40 阿禅追认）：名单外文件的存量上限同样**只许复验方上调**，且必须同时满足两个条件——增长经逐行核实来自"必要修复"（功能性声明、新参数等承重内容，无排版肥肉可削），并在技术债台账登记一笔（谁、为什么、涨了几行）；施工方上调仍然一律拦。首个案例：`ocr-screenshot/route.ts` 551→557（`397a040f` 识别超时 20→45 秒与 Vercel `maxDuration=60` 声明）。

## 后果

必要修复不再被门禁冻结，push 不必等三批拆分；同时"超大文件只准减不准增"从"只在改动它的那一次比对"升级为与基座无关的常态约束，比原规则更严。代价是基线清单从 40 条增至 55 条，15 个名单内文件也进入并发写点，必须遵守"只降不升、冲突取低值"；拆分批次每削下一段，都要同步下调对应上限，否则等于留下可涨空间。

## 证据

实测读数：`node scripts/maintainability-gate.mjs --base=origin/main` 退出码 1，红因恰为两条 `blocking-file-size`（`video-submit-form-v2.tsx` 3266、`video-submit-panel-v2.tsx` 1105）；同一棵树以 `--base=86b97f9f` 运行为退出码 0，证明该红完全由"未推送窗口内的继承性改动"造成。[QW] 对豁免机制的 11 项独立注入见 `日志/2026-10-03.md` 14:32 行。日期：2026-10-03，拍板人：阿禅，记录：[QW]。
