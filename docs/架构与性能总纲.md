# DYData 架构与性能总纲

> 定位：全站加载架构与性能治理的唯一总控文件。
> 最后核对代码日期：2026-08-30。
> 当前依据：现行代码、`docs/全站模块地图.md`、`docs/代码治理手册.md`、`docs/reference/全站公共加载链路体检-2026-08-30.md`。

## 一、总目标

> **DYData 要建立一套可验证、可演进的全站加载与性能控制机制：每个页面由明确的首屏协调入口管理身份、权限和首屏数据，复用最小公共业务上下文，并行独立查询，按需加载非首屏数据；通过真实浏览器证据、性能预算和自动发布门禁持续防止回归，在不改变业务口径与权限语义的前提下，按页面证据分批治理，避免一刀切重构和缓存掩盖结构问题。**

当前阶段顺序：

1. 全站公共加载链路第一批体检：已完成。
2. `/admin/content` 超长 GET 导致的 HTTP 431：已修复，尚未部署。
3. 恢复本总纲并建立两层门禁：已完成；浏览器时间预算暂为报告项。
4. 两个低风险样板：Dashboard 岗位成员按需加载；Topics 详情作品单一数据源。
5. 再按证据处理公共业务上下文、协作页月度数据集、Topics pool 等结构性问题。

这条主线不是“全站从零重构”。现有 loader、React 请求级缓存、统一数据范围和 Topics 服务端 bootstrap 都应保留并继续演进。

## 三、当前架构基线

### 已有且应复用

- Next.js App Router，以服务端组件和 `src/lib/loaders/` 集中加载为主。
- `getCurrentUserContext()`、权限相关 React `cache()` 提供同一次服务端渲染内的请求级复用。
- `visibleUserIds` 管历史可见范围；`activeVisibleUserIds` 管当前操作候选，二者不可混用。
- Topics 已由服务端 bootstrap 注入首屏；正常进入客户端不请求 `/api/topics/*`。
- 独立查询使用 `Promise.all`，允许单块失败的管理统计使用 `Promise.allSettled`。
- 重型抽屉、弹窗和图表已有动态加载样板。

### 当前缺口

- 请求级 Auth 缓存不等于完整业务上下文缓存；导航、页面 loader、JoinBanner 和管理容器仍会重复读取 profile、accounts 或 scope。
- 各页面有不同局部缺陷，不能用一套巨型对象或一种 HTTP 形态强行统一。
- 自动门禁已覆盖首批四个真实登录页面的业务请求数量、重复请求、4xx/5xx 和控制台错误；时间预算仍需积累稳定基线后再转为硬阻断。

## 四、首屏加载契约

### 1. 一个清晰的协调入口

每个页面必须有一个可定位的首屏数据协调入口。推荐放在页面专属 loader 或数据容器中。入口内部可以并行读取多份数据，但不能让多个组件各自管理同一份首屏依赖。

“一个入口”不等于“只能有一个 HTTP 请求”。判断标准是：首屏依赖、身份、权限、错误和降级是否由同一层协调，能否一眼看出采购清单和依赖关系。

### 2. 同一业务事实尽量只计算一次

- 当前用户、profile、accounts、团队与数据范围优先复用已确认上下文。
- 页面可复用服务端已经取得的数据；API 仍必须独立鉴权，不能信任客户端传来的权限范围。
- 同一统计、列表或作品集合在一次页面加载中不得无理由重复查询。
- 公共上下文必须保持最小，只收纳多个首屏真实共用的稳定事实；禁止创建随功能增长的“全站巨型上下文”。

### 3. 依赖决定串并行

- 互不依赖的查询并行执行。
- 只有后一步确实需要前一步结果时才允许串行。
- loader 内超过两个独立串行 `await` 必须重新检查依赖关系。
- N+1 和按账号、按成员扇出查询必须有数据量上限或批量方案。

## 五、数据加载四层

| 层级 | 定义 | 典型数据 | 规则 |
|---|---|---|---|
| 必须首屏 | 打开页面立即看见或立即操作所需 | 身份、权限、第一屏列表、核心摘要 | 服务端协调并明确错误态 |
| 首屏并行 | 首屏需要且彼此独立 | 账号、选项、摘要、状态 | 尽早发起，并行等待 |
| 延迟加载 | 用户动作后才需要 | 详情、抽屉、历史明细、批量解析、重型图表 | 首次点击或明确预取时加载并缓存结果 |
| 后台刷新 | 可先显示可信旧值或部分值 | 非阻塞状态补全、可重验证数据 | 不得伪装成完整首屏；失败必须可观察 |

“组件挂载后立即请求”仍属于首屏成本，不自动算延迟加载。后台刷新也不能静默掩盖失败或把未知状态伪装成成功。

## 六、性能预算与证据

预算以 `docs/全站模块地图.md` 为数值权威入口：

| 页面 | 首屏目标 | 完整加载 | 首屏业务请求上限 | 单接口上限 |
|---|---:|---:|---:|---:|
| `/dashboard` | 2 秒 | 3 秒 | 15 | 600ms |
| `/growth` | 2 秒 | 3.5 秒 | 12 | 首屏 600ms；补全 1200ms |
| `/admin/content` | 2.5 秒 | 5 秒 | 20 | 1200ms |
| 其他登录后页面 | 2.5 秒 | 4 秒 | 20 | 800ms |

性能结论必须标明环境：开发模式、本地生产构建、Vercel 预览或 Vercel 生产。开发模式结果不能写成生产结论，本地生产构建也不能写成 Vercel 已通过。

有效证据至少包含：

- 文档 TTFB、可重复的首屏绘制指标和完整加载时间；
- 首屏业务请求数量、方法、状态和最慢接口；
- 重复 URL、重复业务事实、串并行关系；
- 4xx/5xx、浏览器控制台错误；
- 同环境修改前后对比；
- `DYDATA_PERF_LOG=1` 下 loader 或接口分步耗时。

未取得对应证据时写“未实测”，禁止用单元测试、构建成功或主观体感代替。

## 七、两层自动门禁

### 第一层：必跑确定性门禁

进入普通测试流程，不需要登录态和外部网络。职责：

- 校验页面预算配置与覆盖路由；
- 固化已修复的请求契约和禁止模式；
- 防止固定 URL 退回超长 GET、已收口首屏重新出现提前请求等明确回归；
- 校验浏览器门禁配置本身可解析、预算值合法。

这一层适合阻止确定性结构回退，但不能证明真实性能。

### 第二层：登录态浏览器门禁

在本地生产构建或受控部署上按需运行，首批覆盖 `/topics`、`/dashboard`、`/admin/content`、`/admin/collaboration`。职责：

- 使用专用测试账号环境变量登录，不把密码、Cookie 或 storage state 提交进仓库；
- 采集请求数、重复请求、4xx/5xx、接口耗时、控制台错误和页面时间；
- 对稳定的确定性规则直接失败；对易受网络与数据量影响的时间预算先输出报告，连续取得稳定基线后再升级为 CI 阻断；
- 输出机器可读报告，人工确认后把结论写入性能台账。

当前阶段采用“两层门禁”：`npm run gate:static` 作为必跑阻断；`npm run gate:browser` 作为登录态显式命令，不立即要求 CI 保存账号。浏览器门禁默认不保留 trace、截图、视频或登录状态，只输出去敏的页面级 JSON。没有第二层报告时，不得宣称浏览器性能通过。

## 八、禁止模式

- 同一首屏多个组件分别请求同一数据。
- 导航、页面和容器无理由重复构建相同身份或权限上下文。
- 详情、弹窗、历史明细和重型统计在用户未使用前加载。
- 独立查询无意义串行。
- 同一统计在多个接口或服务中重复计算。
- 为了 UI 方便拉回远大于第一屏的数据，再在内存分页或过滤。
- 把大量 ID 放进 GET URL，或忽略 URL、正文和代理层限制。
- 请求失败被静默吞掉，页面把未知显示成空或成功。
- 用缓存掩盖重复查询、错误边界或数据结构问题。
- 只跑单测、lint、类型检查或构建就宣称性能通过。
- 没有同环境证据就全站重构、加索引或增加缓存。

## 九、当前治理路线

### 已完成

- 第一批公共加载体检，覆盖 Topics、Dashboard、admin/content、admin/collaboration。
- Topics 服务端 bootstrap 首屏注入，本地生产模式首屏 0 个 `/api/topics/*`。
- `/admin/content` topic-library-status 改用 POST 正文，修复 400 个视频 ID 导致的 HTTP 431；400 条约 1.24 秒仍记为性能债。
- 恢复本总纲并建立双层门禁；本地生产构建四页浏览器硬规则通过，`/admin/content` 最慢业务接口两次约 2.91–3.11 秒，`/admin/collaboration` 一次约 0.94 秒，均作为时间警告保留。

### 标准改法库（2026-08-30 全站 sweep 验证后沉淀）

> 依据：当日 12 页 + 13 弹层实测（`scripts/perf-full-sweep.mjs`，本地生产构建 company_owner 登录态）与四项修复的前后对比，记录见 `docs/plans/_跨模块/性能优化台账.md`。遇到慢页面/慢弹层，先对照本清单套用，再考虑发明新方案。

1. **首屏数据服务端随页面注入**：页面 loader 在服务端取齐首屏必需数据并随文档返回，客户端首屏对该数据 0 个请求；API 只留作刷新/兜底。样板：`/topics` 服务端 bootstrap（首屏 FCP 1.0s、0 个 topics 请求）。
2. **重复请求去重**：同一份数据只允许一个在途请求——hover 预取与点击打开共享进行中的 Promise（缓存 Promise 本身，不只缓存结果）；同一 ID 集合的批量计算按签名去重，写入操作后主动失效签名强制重算。样板：协作页 person、admin/content topic-library-status。
3. **大列表按需加载**：超过首屏需要的数据（全量列表、大批量状态计算）不得在挂载时自动加载，改为显式按钮触发，并保证触发后只算一次。样板：admin/content「加载全量列表」。
4. **非关键小数据延后取**：纯指示性的小数据（角标计数等）延后到首屏请求之后拉取并做短 TTL 模块级缓存；不得改为服务端注入阻塞 shell TTFB（已评估并放弃该方案）。样板：导航豁免审批角标。

### 低风险样板

1. Dashboard 岗位成员从挂载加载改为首次打开选择器时加载。（2026-08-30 已完成）
2. Topics 详情统一作品数据源，去掉 detail/works 重复查询。（2026-08-30 已完成）
3. 全站权限上下文 30s TTL 缓存，写路径挂失效钩子；串行身份查询并行化。（2026-08-30 已完成，原「后续结构治理」公共上下文项的第一步）
4. 残留超标三项治理：归因接口鉴权走权限缓存+team/top 共享扇出；dashboard 活动接口只回历史增量（当月事实以首屏 props 为单一来源）；`/topics/[id]` 旧页下线，编辑/移出/作品翻页搬进抽屉并支持 `?topic_id=` 深链。（2026-08-30 已完成，本地生产实测归因 777ms、activity 376ms）

### 后续结构治理

- 设计最小公共业务上下文，收口 nav、loader、JoinBanner 的 profile/accounts 重复读取。（第一步已完成：权限上下文跨请求 30s TTL 缓存，见低风险样板 3）
- `/admin/collaboration` 复用权限上下文和当前月日报数据集。
- `/admin/content` 明确 full list 是否必须自动加载，并治理按账号扇出和分析结果全量读取。
- Topics pool 从全量读取、内存计算和分页逐步转为可扩展查询。

`/growth` 和 `/content-tools/rewrite` 已确定后续整体重做；重做前冻结性能类深度重构，只处理必要故障。

## 十、维护与发布

- 改核心页面 loader、依赖表或首屏接口：同步更新 `docs/全站模块地图.md`。
- 每次性能诊断或优化：同步更新 `docs/plans/_跨模块/性能优化台账.md`。
- 修改本总纲的总目标、预算或门禁：必须说明依据，并保留历史版本于 Git；不得删除归档原稿。
- 新增核心页面：先定义首屏协调入口、数据四层和性能预算，再开发功能。
- 性能任务交付必须分清完整修复、止血未完整、预存问题和新增问题。
- 部署后才能做 Vercel 生产结论；未部署只报告本地生产构建结果。
